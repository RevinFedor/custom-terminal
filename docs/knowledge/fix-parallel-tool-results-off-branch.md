# Fix: результаты параллельных tool-вызовов Claude лежат вне parentUuid-ветки

## Симптом

Карточка Bash/MCP/Read в History крутит спиннер вечно, хотя команда давно завершилась и её вывод виден в терминале. Пользователь читает это как «фоновый процесс завис», хотя команда не была фоновой. Production-пример: сессия `79b624c2`, сообщение `eba3a39a` — два параллельных вызова (`docs_search` + `Bash ls`), обе карточки остались running навсегда.

## Ошибочное предположение

Parser полной истории считал, что результат инструмента всегда находится **впереди по активной ветке**: после `tool_use` достаточно идти вперёд по `activeBranch` и искать `tool_result` с тем же `tool_use_id`. Для одиночных вызовов это верно.

## Реальная механика

При ПАРАЛЛЕЛЬНЫХ tool-вызовах Claude CLI пишет записи иначе:

- assistant-записи вызовов сцепляются друг за другом: `A1 ← A2 ← A3` (одно `message.id`, разные `uuid`);
- результат каждого вызова прикрепляется к **своему** родителю: `R1.parentUuid = A1`, `R2.parentUuid = A2`;
- только ПОСЛЕДНИЙ результат продолжает ветку — следующая assistant-запись ссылается на него.

Итог: `R1`, `R2` — sibling-записи **вне** активной parentUuid-ветки (backtrace от последней записи их не проходит). Проверено скриптом на реальном JSONL: 375 записей на ветке, 2 tool_use на ветке имели результат вне ветки — ровно те две «вечные» карточки.

`toolStatusFrom` в `@noted/claude-blocks` выводит `running` из «result отсутствует», поэтому не найденный результат = вечный спиннер.

## Фикс

Точная идентичность вместо топологии: `tool_use_id` глобально уникален на вызов, поэтому строится индекс `tool_use_id → tool_result` по **всем** записям `recordMap` (не только по ветке). Это одновременно убрало O(n²) forward-scan на длинных сессиях. Rewind не создаёт ложных совпадений: откат отбрасывает user-turn целиком, пара «вызов+результат» живёт между двумя user-turn'ами и отбрасывается вместе — результат вне ветки может принадлежать только вызову на ветке.

Исправлены все три потребителя (`src/main/ipc/claude-data.js`):
- `claude:get-full-history` — индекс `toolResultRecordByUseId`;
- Copy Session export — индекс `exportToolResultByUseId`;
- `claude:copy-range` — range-scan остаётся первым (сохраняет range-семантику), recordMap-wide lookup как fallback.

## Смежный фикс: фоновый Bash получает терминальное состояние

Настоящий `run_in_background` Bash — двухшаговый: немедленный acceptance-результат («Command running in background with ID…»), затем поздний `<task-notification>` user-записью с реальным исходом. Notification намеренно фильтруется из History как service-noise, поэтому карточка раньше навсегда показывала только acceptance-текст.

Теперь parser индексирует notification'ы по `<tool-use-id>` и дописывает к тексту карточки блок `— background <status> —` + summary + result (последний notification выигрывает — задача может уведомлять не раз). Notification по-прежнему не становится отдельной строкой History. Рядом с результатом carrier несёт `backgroundStatus` для будущего presentation.

## Что не делать

- Не «чинить» это снятием фильтра `<task-notification>` — появятся служебные строки-дубли в History.
- Не искать результат по тексту/времени — только `tool_use_id`.
- Не возвращать branch-only forward-scan «для простоты»: одиночные вызовы он обслуживает, параллельные — теряет всегда.
