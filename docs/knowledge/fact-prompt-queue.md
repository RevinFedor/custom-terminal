# Факт: Prompt Queue overlay + External Editor hijack

## Организационный scope после workflow cutover07.10

AutoCompact и Run After inventory читают canonical Main membership вкладки,
а не `spaces[].projectIds` или видимость reserve sidebar. Placement-only detach
и same-workflow move сохраняют imported eligibility. Старое `__unplaced__`
означало отсутствие project/workflow связи, не нынешний резерв: initial eligibility
переносится явно, чтобы cutover не начал дополнительные автоматические действия.
Принятые targets, условия, operation keys и receipts остаются frozen; membership
revision не подменяет execution owner epoch. Таймеры/Loop/Main ownership из
остальных разделов сохраняют собственный контракт.

Общий picker Run after/Restart after сохраняет горизонтальную полосу workflow.
Она строится по canonical membership, включая размещённые и скрытые AI-вкладки,
а не по legacy projectIds: несколько workflow могут иметь один execution namespace.
Клик scope меняет только список picker, не открытый workflow приложения. Группы
используют общие order/tree/intersection и canonical collapse writer. Изменение
membership обновляет список даже без смены namespace; pre-cutover fallback остаётся
отдельным. Переданная зависимость по-прежнему адресует исходную execution-вкладку.

## Зачем
Юзер пишет промпт, AI-таб отвечает, юзер хочет следующий промпт отправить **автоматически после окончания ответа**. Очередь промптов справа-вверху Claude/Codex PTY-таба + auto-runner на busy→idle событии. Без поллинга, без таймаутов — на штатный конец turn'а pop'аем head.

Вторая сторона — **захват текущего ввода AI TUI** для перекладки в очередь / clipboard / просто очистки. Без danger zone (Ctrl+C single press = clear input, но Claude/Codex TUI может handle'ить его как exit/interrupt → можно случайно убить сессию).

## Архитектура — три блока

Не путать эту очередь будущих шагов с Main FIFO уже принятых обычных Send
(04.10, `fact-terminal-mcp.md::Main FIFO принятых Send`). Новый backlog позволяет
набирать много сообщений во время streaming, отдавая CLI по одному до exact
canonical receipt. Run After/Loop сохраняют свои условия и общий send scenario;
локальные slash-команды не переводятся в этот ordinary-message backlog.

### 1. Store (`usePromptQueueStore.ts`)
Per-tab очередь: `Map<tabId, { items: QueuedPrompt[], autoRun: boolean, workflowArmedAt: number | null, panelCollapsed: boolean, previewId: string | null }>`.
- `autoRun` — на каждый busy:true→false pop'аем head и шлём команду в runtime owner-таба (`claude:send-command` или `codex:send-command`). После последнего prompt'а **auto-disarm** (`setAutoRun(false)` если очередь стала пустой).
- `QueuedPrompt.enabled` — per-card skip-state. `false` оставляет карточку видимой, но runner и счётчики активных элементов её пропускают; `undefined` у legacy-записей читается как enabled, чтобы старые очереди после hydrate не стали молча выключенными.
- `QueuedPrompt.condition` — независимый per-card gate `context-used ≥/≤ N%`. Триггер отвечает, когда карточку проверять; condition — имеет ли она право выполниться в этот момент. Поле живёт внутри item, поэтому сохраняется, переносится между клиентами и не создаёт вторую очередь.
- `QueuedPrompt.metaAction` — видимое действие внутри той же последовательности: `Model / effort`, `Rewind`, `Restart`, `Stop`, `Close tab`. Оно перетаскивается, отключается и получает trigger/context condition как обычная карточка. `Stop` после исполнения выключает Play и оставляет последующие карточки на ручной запуск; `Close tab` сначала останавливает агента, затем закрывает owner-вкладку.

**SQLite persistence через `app:setState`.** `items` / `autoRun` / `runAfterTabId` / `workflowArmedAt` / first-delay / post-prompt / `panelCollapsed` / `previewId` per-tab сохраняются в `app_state` под ключом `promptQueueByTab`; `enabled`, condition и meta-action живут внутри `items`, а не отдельными флагами. Старые persisted `stopAfter/closeAfter` читаются только как migration input: при hydrate превращаются в видимый конечный `Stop` либо `Close tab`, а compatibility-поля дальше сохраняются false. Если старый standalone-флаг был включён без Play, миграция намеренно не останавливает idle-вкладку сразу после запуска приложения: карточка остаётся видимой с hint и ждёт явного Play. `workflowArmedAt` — время последнего реального включения автоматического обещания пользователем: оно связывает восстановленный результат с той постановкой, которую этот результат вправе выполнить или отменить. Автоматическая очистка закрытого/stale target не считается новым включением. Legacy-очередь без времени постановки остаётся fail-closed: старое успешное завершение не запускает её после рестарта, а подтверждённая ошибка всё равно может безопасно снять обещание, сохранив карточки. Throttle 250мс на каждый mutator — drag-reorder и быстрый ввод не должны писать SQLite 60 раз/сек, но последнее значение перед unmount-ом гарантированно flush'нется. `previewId` — persisted pointer на закреплённый editor: hydrate восстанавливает его только если item с таким id ещё существует, иначе сбрасывает. Timestamp активного countdown сохраняется для прежнего restart-policy; first-chip hint — UI-only. First-delay после фактического fire потребляется обратно в `0` (`0 ч / 0 м / 0 с`), а при ручном disarm во время countdown сохраняется оставшийся остаток. Cold tabs дропаются только если нет очереди, нет armed-state, нет настроек, `previewId=null` и `panelCollapsed=false`; collapsed empty tab сохраняется, потому что это ручная layout-настройка вкладки, а не состояние очереди. Hydrate один раз через `hydratePromptQueueStore()` в `App.tsx::useEffect([])` — fire-and-forget, runner ниже терпит появление items после mount'а через subscribe-механизм (см. cold-start).

First-delay не ограничен одним часом: UI редактирует часы, минуты и секунды, но durable-контракт намеренно остаётся одним общим числом секунд, поэтому старые записи не требуют миграции. Все три разряда остаются видимыми и во время настройки, и во время countdown: `1 ч / 0 м / 0 с` через секунду становится `0 ч / 59 м / 59 с`. Отсчёт начинается на явном arm Run After, а не после runtime readiness; readiness ограничивает только фактическую отправку после нуля. Пока countdown активен, очередной `task_complete` не имеет права обойти его и немедленно отправить head — именно такой bypass раньше опустошал очередь через несколько секунд вместо часового ожидания. Длинное ожидание нельзя возвращать к одному сырому `setTimeout`: Chromium переполняет задержки больше signed 32-bit миллисекунд и может выполнить их сразу, поэтому runner ставит ожидание безопасными отрезками и на каждом отрезке пересчитывает остаток от исходного timestamp.

**Restore/hydrate race guard.** `hydratePromptQueueStore()` может загрузить очереди раньше, чем `restoreSession()` наполнит `openProjects`. В этом окне runner НЕ имеет права считать owner/target вкладки закрытыми: нельзя вызывать `cleanupClosedTab`, сбрасывать `runAfterTabId` как stale или сохранять пустой snapshot до завершения hydrate/workspace restore. Живой симптом был после build-install: в UI был один-два Run-after чипа, при рестарте `promptQueueByTab` в SQLite стал `{}` и меню открылось пустым. Поэтому validation запускается только когда `!useWorkspaceStore.isRestoring` и есть реальные `openProjects`, а store skip'ает pre-hydrate empty save/sync save. Item metadata теперь появляется в store сразу, а проверка/миграция image bytes идёт следом; если пользователь успел добавить item до ответа SQLite, hydrate мёржит persisted и новые items по id и применяет только реально изменённые до hydrate поля. Старый `if (next.has(tabId)) continue` терял всю сохранённую очередь этой вкладки при первом быстром `+Grab` после запуска.

Тот же барьер удерживает **все** исходы автоматизации — и успех, и ошибку — пока не закончены оба восстановления. Runner собирает отложенные live-события и snapshot Codex из main, сначала применяет все подтверждённые ненормальные исходы, затем не более одного самого нового штатного исхода на trigger. Каждый исход сравнивается со временем постановки: ошибка снимает только обещание, поставленное не позже неё, а старый catch-up не может отменить более поздний ручной retry. Успех без надёжного времени постановки или завершения ничего не запускает. Так поздний success не маскирует более ранний разрыв цепочки, но явное повторное включение после ошибки сохраняется.

**First-chip hint без auto-arm.** Когда `items.length === 0 && autoRun === false` и юзер дергает `+ grab` или `+ add`, store НЕ включает `autoRun` автоматически. Вместо этого ставится UI-only `firstChipHintActive`: Run after pill мигает красным один раз и остаётся приглушённо-красным до явного Run after / ручного empty-out очереди. Модель намерения: положить задачу в очередь = staging, а не согласие на автозапуск; запуск остаётся явным кликом по Run after. Ранняя версия auto-arm'ила первый chip, но это конфликтовало с ожиданием «я просто сохранил задачу на потом» и визуально путало hint с active-state.

### 2. Overlay UI (`PromptQueueOverlay.tsx`)
Sticky-панель справа-вверху доступна в любой вкладке, назначенной Claude/Codex через `commandType`, даже если сессия ещё не запускалась или уже остановлена. Наличие session id и живого процесса относится только к готовности **исполнить** очередь, а не к праву пользователя заранее настроить Run after. Поэтому Stop больше не прячет конфигурацию, а незапущенная AI-вкладка сразу допускает staging карточек, выбор trigger'а и first-delay.

Общие CSS-правила overlay принадлежат Document, а не экземпляру панели. Переход
между workflow может монтировать сразу несколько очередей; одинаковый `<style>`
у каждой заставлял Chromium повторно пересчитывать стили retained History. Sheet
сохраняется после unmount, а при HMR меняет текст только если правила изменились.
Ключевые кадры, палитра и размеры прежние; lifecycle самой очереди и её runner
от этого не меняются. Повторное измерение заголовка могло лишь инициировать уже
необходимый style flush — sampled время этого вызова не равно цене canvas.

**Rail разделяет inspection и execution.** Числовая кнопка отвечает только за окно очереди: hover временно показывает ту же полную панель, click закрепляет/закрывает её. Это работает и при счётчике `0`, потому что Post, Loop, `+` и настройки `…` должны оставаться доступными независимо от наличия карточек. Соседняя `Play/Pause` отдельно включает и приостанавливает `autoRun`; карточки при pause не удаляются. Включение даёт один спокойный brightness-flash длительностью 1.2s; busy не запускает бесконечную пульсацию и не рисует вторую внешнюю/внутреннюю рамку поверх active-state. Дублирующий полноширинный `Run after` внутри панели удалён. `Ctrl+Enter` является оконной командой фокусной pane и следует той же split-модели, что composer-control: если в History composer есть текст, image refs или prompt/paste chips, shortcut переносит этот snapshot в очередь; если composer действительно пуст, shortcut переключает тот же `Play/Pause`. Пустая очередь не армится. Удержание `Control` заранее пульсирует именно на той половине split-кнопки, которую реально сможет выполнить Enter: `terminal →` при непустом authoring state; `Play/Pause` только при пустом input и хотя бы одном активном шаге очереди; если пусты и input, и очередь, preview отсутствует. Это мягкое переливание всей поверхности без дополнительной рамки. Preview принадлежит только shown-tab фокусной pane и гаснет, пока открыт picker промптов, поэтому фоновая кнопка не обещает действие поверх открытого меню. Capture-listener живёт в `Workspace`, выбирает shown-tab фокусной pane через общий resolver поверхностных хоткеев и потому не требует DOM-focus у History input; когда keyboard owner находится в sidebar/project rail, chord не перехватывается. Оба пути адресуют tab-scoped события уже смонтированному overlay, поэтому grab pipeline (History/TUI ownership, images, safe clear) и countdown/arm правила не размножаются; shortcut перехватывается раньше обычного Enter и никогда не отправляет prompt агенту. Timeline-toggle больше не является частью Run after rail и живёт в меню окна.

ПКМ по конкретной карточке добавляет одноразовый триггер `after app restart`. Он принадлежит самой итерации, поэтому не добавлен в меню `+`, где создаются новые действия. Условие хранит identity текущего Electron main: reload/HMR renderer'а его не выполняет, а Quit/Open, обычный Restart и build/install создают другой identity и тем самым удовлетворяют условие. Событие защёлкивается до фактической передачи карточки агенту, поэтому ещё один restart не заставляет пользователя ставить условие заново; после успешного Enter карточка потребляется обычным queue-commit. Если это следующий enabled-item, выбор сразу включает Play. На более поздней карточке условие сохраняется, но не запускает head на чужих условиях: порядок очереди остаётся источником исполнения.

Новый main lifetime — самостоятельное доказательство этого условия. После queue/workspace hydrate готовый restart-head входит в прежний condition/readiness/send pipeline, даже если Codex нового процесса ещё не знает исход старого ответа. Он может дождаться или присоединиться к Resume через общий executor; новый assistant completion и ручной Play для этого не нужны. Busy, дочерняя работа, Stop, смена owner/head/trigger и неизвестная runtime readiness по-прежнему ограничивают фактический ввод. Обычная восстановленная очередь и `onTab` не получают этот допуск и ждут свой natural outcome.

У полностью выполненной сохранённой AND-группы onTab natural outcomes уже
учтены в `completedAt` каждой цели: restore продолжает прежний sender с этой
карточкой через readiness, а не требует повторных завершений всех источников.
Это не разрешение повторять unknown/submitted Send; исход читает тот же Main FIFO.

Шрам06.10: у Inbox51 после установки runner записал `after-restart ready`03:41:21UTC, затем `outcome unknown → wait`. AutoResume стал ready03:43:53, но cold-start до этого не создал readiness-attempt, который мог бы проснуться. Обе карточки и `autoRun=true` сохранились. Требовать прошлый assistant result здесь означало навсегда ждать чужого условия; исправление допускает только доказанный restart-head, без синтеза `task_complete`. Условие различает запуски приложения, не названия shell-команд и не успех сборки: Build Install/OBS/continue сходятся на новом main, package-only build и неудачная сборка без замены — нет.

До смены main-процесса текущие Stop/error/natural outcomes не могут ни отправить, ни отменить такую карточку. После запуска нового процесса старые восстановленные outcomes также отсеиваются по времени старта; только новое событие нового процесса снова получает обычное право disarm. Это различие нужно и после нештатного завершения приложения, когда shutdown-overlay мог не успеть поставить общий restart-pending, но сама карточка уже была сохранена.

В composer-control источник TUI и Run After визуально разведены. Меню черновика терминала — нейтрально-серая кнопка с одной увеличенной terminal-иконкой; отдельный disclosure-треугольник удалён, потому что hover/click и tooltip уже объясняют раскрытие. Run After использует одну split-форму той же высоты: левая широкая зона `terminal →` переносит текущий ввод в очередь и повторяет оранжевую палитру раскрытой count-кнопки rail — приглушённая в покое оранжевая рамка, слабый оранжевый фон и более яркий hover; правая узкая зона `Play/Pause` берёт фон, рамку, текстовый цвет, opacity и hover из того же общего resolver'а, что верхняя rail-кнопка. Поэтому empty = серый disabled, staged queue = серый active, first-chip hint = приглушённый красный, armed = фиолетовый. Нижний glyph остаётся контурным и имеет размер 11px против 12px filled glyph'а в rail. Seam владеет правая зона; двойная линия между кнопками не рисуется. Обе зоны адресуют tab-scoped события уже смонтированному `PromptQueueOverlay`, поэтому grab pipeline и правила Play/Pause не дублируются в control bar.

Цвета двух rail-кнопок также разделены по обязанности. Счётчик показывает только видимость списка: блекло-оранжевый, пока список скрыт, и полный оранжевый, когда список раскрыт или показан hover-preview. Фиолетовый принадлежит только `Play/Pause` и означает, что автоматическое выполнение Run After включено; общий `active`-класс не должен перекрашивать счётчик.

**Stop/Close принадлежат видимой последовательности, не меню вкладки.** Нижние `Stop after / Close` удалены из tab context menu; верхние непосредственные `Stop Codex` и `Close tab` там остаются, потому что выполняются сразу. Отложенные варианты добавляются через ПКМ по `+` Run After как самостоятельные `Stop` / `Close tab` карточки и по умолчанию попадают в хвост. Чтобы поставить границу после конкретного prompt, карточку перетаскивают за ним. Скрытый флаг на предыдущем prompt запрещён: после reorder/delete/disable было бы непонятно, к какой границе он относится.

**Автовключение после настройки карточки зависит от loader'а реального триггера.** Для `timer` и первого `context` триггером остаётся owner-агент, поэтому Play автоматически включается только при его `busy`. Для `on tab` решает loader **выбранной target-вкладки**, а не owner'а очереди. Иначе idle-owner оставлял Play выключенным, хотя соседняя вкладка, чьё завершение выбрано условием, уже работала. Если соответствующего loader'а нет, настройка сохраняется, но очередь остаётся staging до ручного Play. Повторный вход в существующий context и `Refresh title` Play не меняют.

**`/compact` получает стандартный context gate при создании.** Новый однострочный queue-item вида `/compact` либо `/compact <инструкция>` автоматически создаётся с `Context used ≥ 50%`. Это только creation-default: условие остаётся обычным редактируемым полем, ручное удаление не восстанавливается при последующих правках текста/title. Многострочное сообщение, лишь начинающееся похожими символами, slash-командой не считается.

**Slash picker History-input не забирает фокус у редактора.** Когда первый непробельный символ draft — `/` либо `\\`, перед ним есть только горизонтальные пробелы/табы и внутри команды ещё нет пробела/переноса, в локальном absolute-слое редактора прямо над ведущим символом показывается ограниченный по высоте список команд, отфильтрованный по введённому prefix; пока в каталоге есть только `/compact`. Обратный slash является только удобным input-alias: фильтрация `  \\com` идёт как `/com`, а выбор мышью/Enter сохраняет ведущий отступ и заменяет только команду на каноническую `  /compact`, чтобы provider получил рабочую slash-команду. Любой другой текст перед slash по-прежнему запрещает picker. Список не участвует в layout рамки, его контейнер не имеет внутреннего padding, а строки используют компактный вертикальный ритм. Caret остаётся в основном `ComposerEditor`: `↑/↓` меняют активную строку, первый `Enter` подставляет команду и не отправляет её, `Escape` закрывает список для текущего значения. Следующий Enter уже выполняет обычную отправку. Это устраняет конкуренцию двух input/focus-owner'ов.

**Hover и click используют одну поверхность.** Hover-режим закрывается после ухода из геометрического кластера, чей единственный rail-триггер — оранжевая числовая кнопка. Переход на соседние кнопки rail (настройки запросов, Play/Pause и другие) закрывает временное превью, даже если широкий геометрический мост к панели покрывает их координаты. Только click по числовой кнопке закрепляет панель; body карточки, ПКМ, выбор on-tab, Post/Loop, `+`, `…` и фокус внутри поля не меняют её ownership. Это не focus-within режим: пользователь может работать внутри временного меню, не соглашаясь оставить его на экране. Открытие и закрытие происходят без slide-анимации и отложенного unmount; геометрия списка и 1px border-slot одинаковы в обоих режимах. Закреплённая панель — постоянная per-tab layout-настройка: получает одну приглушённую белую рамку 1px, не зависит от курсора, не закрывается Escape/outside-click и переживает уход с вкладки. Закрывает её только повторный click по числовой кнопке. Рамка заменяет существующий 1px border в том же слоте, поэтому pin не меняет размеры панели.

**Hover-preview счётчика в свёрнутом rail.** Наведение на числовую кнопку показывает прямо под rail ту же единственную DOM-панель, включая border-mounted Post/Loop, оба карандаша, `+`, `…` и список queue-item'ов. Отсутствие item'ов показывает короткое `empty`, но больше не запрещает открыть панель: иначе из нулевого состояния невозможно было бы добраться до действий, которые это состояние наполняют. Это намеренно не второй упрощённый renderer: порядок, disabled-state, meta-actions, image state, timer/on-tab строки, Replay, delete и drag остаются общей реализацией. Пока panel закреплён, preview не создаётся. Hover Replay в preview не открывает скрытый editor и не берёт editor-lock, но сам Replay/⌘Replay остаётся рабочим.

**Клик по строке превью открывает ту же боковую модалку-редактор (pinned).** Превью — не витрина без действий: клик по карточке = тот же `openEditor(id, 'pin')`, что в раскрытой панели. Pin относится только к редактору карточки, не к родительской очереди. По уточнению08.10 открытый click-редактор, picker, item/action menu и настройки удерживают своего hover-родителя по факту открытия: курсор может двигаться по приложению и повторно заходить в ребёнка, не закрывая окна. Повторный trigger/явный outside-close закрывают ребёнка; после последнего такого окна parent hover сразу проверяет фактическую точку. Внутри родителя он остаётся, снаружи незакреплённый закрывается; отдельный pin не снимается жестом закрытия ребёнка. Правки сохраняются прежним blur/commit путём. Pending image, захваченный resize/drag и выбор Rewind сохраняют прежние безопасные guards. Старый unconditional `editorOpen`/focus guard был implicit pin; нынешнее удержание ограничено exact instance-owner и жизнью click-поверхности. Опустевшая очередь сама по себе preview не закрывает. Hover по ▶ в превью по-прежнему не открывает editor — вход только кликом.

**Окно под курсором — одно целое, а не набор блоков.** Предпросмотр очереди живёт, пока курсор внутри своей совокупности: оранжевая кнопка-счётчик, сама панель и всё, что открыто ИЗ панели, — список вкладок `RunAfterTabPicker`, меню карточки, меню действий, — плюс зазоры между панелью и этими блоками. Вся соседняя полоска rail не принадлежит этому кластеру. Зазор в несколько пикселей нужен глазу, чтобы блоки не слипались, но для курсора он обязан быть продолжением панели: иначе окно исчезает ровно посреди движения к списку, который само же и открыло.

Считает это `utils/hoverBridge.mjs`: `pointInHoverCluster({ hub, satellites })`. Форма — звезда, не цепочка: главный блок один (панель), остальные открываются от него, курсор ходит между панелью и каждым, но не между ними напрямую — поэтому и мосты строятся только к панели. Сторона нигде не задаётся: список вкладок раскрывается влево или вправо, вверх или вниз в зависимости от места у края экрана, а зазор всегда лежит там, где два прямоугольника разошлись. Перекрывающиеся по обеим осям блоки соприкасаются, и мост между ними не строится — иначе «зазором» стал бы весь охватывающий их прямоугольник и окно не закрылось бы никогда.

Задержки в этом решении нет и быть не должно. Отложенное закрытие («подожди 140 мс, вдруг курсор вернётся») отвечает на вопрос «сколько ждать», хотя вопрос был «где курсор»: для медленного движения оно коротко, а после ухода держит окно открытым. `onMouseLeave` на панели тоже убран целиком — он срабатывает на границе за миг до того, как обход по геометрии успевает сказать «курсор в зазоре», и вместе они дают мигание на каждом переходе (общее правило — `methodology/сценарии-багов-design.md::2.7`). Блоки, открытые от панели, лежат прямо в `body` (панель обрезала бы их своим `overflow: hidden`), поэтому находятся по меткам picker/context/meta/editor/preview и точному owner-instance. Локальная и встроенная копии одной tab-очереди не владеют чужими portal'ами. Fullscreen backdrop не считается hover-территорией: удержание click-ребёнком принадлежит его open-state, не прямоугольнику на весь экран. Border-mounted controls и реальные зазоры включены. Новую click-поверхность нужно зарегистрировать владельцем и сообщить причину закрытия после commit, чтобы отмена освобождала hover без дополнительного mousemove. Выход из окна/blur сохраняют прежний профиль. В `RunAfterTabPicker` геометрия «кнопка ↔ список» закрывает только `openOnHover`; обычный click-open picker уходит по своему outside/Escape/trigger. Он отдельно flip/clamp'ится в viewport, включая левую границу.

Шрам08.10: global backdrop останавливал mousedown до document outside-handler picker. Простое «не закрывать родителя при открытом ребёнке» оставляло picker навсегда открытым на этом клике. Backdrop пропускает только детский dismiss-жест своему handler и не использует последующий click для close-all; ребёнок уведомляет после DOM commit, parent проверяет актуальный pointer. Так же верхнее меню не отменяет лежащий под ним click-editor. Выбор вне родителя оставляет прежний return-gate, overlay-cancel сбрасывает его. Общий паттерн — `docs-global/ux-паттерны/всплывающие-окна.md::Дочернее окно по клику внутри hover-панели`.

После клика по собственному дочернему portal **вне** родительской панели, если именно этот click убрал portal, preview получает один возврат: курсор может пройти через свободное место до повторного входа в родителя. После входа следующий уход снова закрывает меню мгновенно. Иначе выбор OnTab оставлял курсор на месте исчезнувшего списка и попытка вернуться закрывала очередь. Это не pin/focus и не расширение backdrop: capture связывает click с exact owner-element, один rAF проверяет его commit; фильтр, сохранивший popup, не вооружает будущий Escape. Blur/явное закрытие сбрасывают право возврата. Контракт общий для локальной очереди и глобального обзора.

В History-primary layout оверлей не может оставаться DOM-потомом видимого прямоугольника xterm: иначе он скроется вместе с terminal или уедет при drag. `Terminal` остаётся lifecycle-owner компонента, но UI рендерится через Portal в workspace-level host над History; host заканчивается над измеренной зоной controls/input. В этом режиме History-toggle в rail скрыт как дубль уже основной поверхности. `+grab` забирает видимый History draft, а не скрытый TUI draft; для явного переноса из TUI у History есть отдельный Pull. См. `fact-история-как-основная-поверхность.md`.

**Исторический шрам: OSC 133 `B` терялся → оверлей висел HIDDEN пока Claude жив.** До разделения конфигурации и исполнения `claudeProcessAlive` ставился в `true` только по OSC 133 `command-started` (B), а весь оверлей был привязан к этому флагу. Маркер пропускался при восстановлении приложения, запуске в фоновой вкладке или ручном `--resume`, поэтому Claude отвечал, а Run after был недоступен; после Stop+«продолжить» сигнал внезапно появлялся и UI показывался. Теперь этот сигнал не управляет видимостью панели, но всё ещё участвует в runtime readiness и поэтому обязан иметь авторитетный fallback.

**Фикс — bridge-alive как авторитетный fallback.** `bridgeKnownSessions` = «CLI жив в этом табе, держится до kill терминала» (в отличие от `claudeCliActive` = «сейчас обрабатывает», пуст на idle — см. коммент у `before-quit`). Решение:
1. `terminal:getCommandState` (main) возвращает `isRunning: oscRunning || bridgeKnownSessions.has(tabId)` — если мост знает живую сессию, Claude жив независимо от того, поймали ли мы OSC `B`.
2. `Terminal.tsx`: `handleSessionDetected` и `handleProcessStarted` ставят `setClaudeProcessAlive(true)` (functional updater — deps эффекта `[tabId]`, прямое чтение стейта было бы stale). Ловит случай «мост обнаружил Claude уже ПОСЛЕ маунта/initial-sync».

Диагностика (можно удалить позже): `[RunAfterDiag]` на OSC B/D + `getCommandState` логирует `bridgeAlive` vs `oscRunning` расхождение.

### 2-1. Средний клик удаляет карточку или её условие

В локальной панели, hover-превью счётчика и общем редакторе средний клик по карточке удаляет всю итерацию; по отдельной суб-строке — только её context gate либо trigger (таймер, ожидание вкладки, после перезапуска). Фон подсвечивает всю удаляемую строку, включая поля, подпись и промежутки: пользователь не должен целиться в маленький крестик или искать отдельную hover-зону между оператором и процентом. Корзина и ✕ остаются равноценным способом для ноутбука без средней кнопки. Обычный клик по полям по-прежнему редактирует их, по карточке — закрепляет редактор; disabled/meta-карточки не лишаются удаления.

Границы удаления физические: portal-меню выбора вкладки не принадлежит суб-строке, даже когда React передаёт его событие через родителя. Средний mousedown поглощается до дочерних контролов, чтобы не переключить поле/редактор, а удаление выполняется на auxclick тем же путём, что корзина/✕. Очистка последнего runnable trigger сохраняет прежний disarm/countdown контракт; очистка context gate не удаляет карточку. Это не меняет средний клик по **tab-chip карты**: там остаётся навигационное `add-here`, не удаление очереди.

### 2a-0. Мета-действия в той же очереди

Добавление действий открывается ПКМ по `+` на верхней границе панели рядом с Post/Loop; обычный клик `+` сохраняет быстрый ручной prompt. Раньше добавление жило в `…`; теперь `…` открывает настройки автоматизации вкладки. `Restart` сразу добавляет обычный queue-slot и при исполнении вызывает тот же deterministic restart вкладки, что ручная restart-кнопка. `Rewind` сначала включает одноточечный фиолетовый режим Timeline; следующий клик по обычному user-prompt сохраняет UUID, текст, исходную сессию и runtime (`claude`/`codex`) в queue-slot. `Escape` отменяет только выбор точки.

Карточка Rewind показывает только `Rewind: N`, где N —1-based номер выбранной обычной user-точки без compact-summary/docs/boundary маркеров. С05.10 номер сохраняется как display-only `targetIteration` при выборе; target UUID/session/text и исполнение не заменяются номером. Раньше title брал начало payload и мог показывать `<saved_prompt name=…>`, растягивая очередь без понятного ориентира. Старые карточки сразу перестают выводить этот текст; для видимой панели номер читается по точному UUID из source Timeline через общий read-only reader. Параллельные local/global-копии объединяют запрос, положительный cache ограничен; queue payload не переписывается во время in-flight action. Если история/точка недоступна, остаётся короткое `Rewind`, без выдуманного номера и без изменения команды.

Это не вторая очередь. У action-slot тот же порядок, drag, `enabled`, per-item timer/on-tab trigger, first-chip staging, SQLite hydrate и mobile core, что у prompt-slot; различие хранится в `metaAction`. Повреждённый persisted action fail-closed удаляется при hydrate, а не превращается в пустой prompt. Runner распознаёт action до image/paste/send pipeline: `Restart` не вставляет текст, `Rewind` использует общий для Queue, Timeline и History saved-history сценарий stop → delete tail → вернуть target в History input → resume. Возврат восстанавливает не только строку: transport снова раскладывается на обычный текст, saved-prompt/pasted-content chips и доказанные image refs; новый пользовательский draft, появившийся во время операции, остаётся после восстановленного target. После успешного action следующий собственный slot продолжается сразу после readiness; `on tab` следующего slot остаётся будущей зависимостью и не потребляет старый completion. Если обрезка истории уже произошла, а restart упал, action удаляется и очередь disarm'ится: повторять destructive половину нельзя.

`Model / effort` добавляется через то же меню ПКМ по `+`: сначала выбирается модель текущего owner-runtime (`Claude subscription` либо `Codex`), затем один из разрешённых для неё effort. Источник выбора — тот же сохранённый каталог Settings; карточка хранит его `model.id`, а `label` служит только подписью. В очередь сохраняется точная пара вместе с типом агента; это одна атомарная карточка, а не два независимых изменения. Даже для сценария «поменять только effort» пользователь выбирает текущую модель и новый effort: скрыто наследовать модель в момент будущего исполнения нельзя, потому что до карточки её мог изменить другой шаг или клиент. Поэтому последовательность `/compact → Model / effort → user prompt` физически означает: дождаться завершения compact, подтвердить обе настройки и только затем отправить следующий prompt. Для Claude proxy-provider (`DeepSeek`/`Zen`) пункт пока disabled: их переключение меняет provider routing, а не пару нативных `/model` + `/effort`; выдавать им ту же карточку без отдельного контракта было бы ложным обещанием.

Runner исполняет карточку только на свободном input-ready агенте и повторно сверяет, что тип runtime не изменился. Claude проходит через общий доказательный `apply-settings` для пары slash-команд. Codex создаёт ревизионное намерение в main и не удаляет карточку по одному ответу «намерение сохранено»: runner ждёт applied-ревизию, привязанную к текущему writer/launch owner. Post-picker проверка сопоставляет label и ID через каталог Settings (`GPT-6-Astra` → `gpt-6-astra`), а не строковым регистром. Ошибка неприменённой текущей revision является состоянием retry, пока main ею владеет; runner продолжает ждать exact applied, более новый выбор либо 45-секундный timeout. Ошибка уже applied revision, старая applied-метка другой сессии, смена пары другим клиентом, неподтверждённый picker и timeout оставляют карточку в очереди, выключают Play и показывают причину; следующий prompt не отправляется. Остановленному агенту перед такой карточкой нужен явный `Restart` в той же последовательности. ControlBar получает новое значение только после подтверждения, а не в момент постановки. Desktop web-bridge принимает этот же `model-effort` action, поэтому persistent/mobile core не теряет новый тип при чтении и reorder. Первоначальный compatibility-codec native iOS `CTQueueItem` декодирует известные поля и штатно игнорирует дополнительный `metaAction`, поэтому весь ответ не падает: карточка видна по сохранённому title и остаётся доступной для enable/remove. Action-icon и picker создания не добавлялись тем первоначальным desktop-этапом; последующий typed native контракт использует RunAfter capability (см. fact-mobile-web.md), не этот legacy fallback.

Selection mode принадлежит Timeline, но исполнение не принадлежит смонтированному Timeline: фоновый runner вызывает `utils/historyRewriteRewind.ts`, который сам перечитывает актуальный хвост и проверяет сохранённый UUID. Поэтому переключение вкладки после постановки не превращает действие в renderer-only обещание.

`sourceSessionId` карточки Rewind сохраняет происхождение выбранной точки, не
приказывает переписать старый physical source после Resume/Fork. Исполнитель
разрешает UUID заново в текущей conversation; отсутствующий user UUID отказывает
до Stop/rewrite. Readiness lease включает execution-поля `metaAction`: заменённый
Restart не вправе исполнить/потребить новый Stop с тем же item ID. Display-only
`targetIteration` и title не являются execution identity.

### 2a-1. Триггер принадлежит элементу очереди, а не всей очереди

Условие запуска настраивается на конкретном элементе очереди через ПКМ по
чипу. Один элемент несёт один вид триггера: timer, app-restart либо onTab.
Разные виды заменяют друг друга. С10.10 onTab допускает группу явно выбранных
вкладок: ПКМ по уже выбранной карточке открывает прежний пикер и добавляет
ещё одну ниже, а повторное `on tab` из меню сообщения открывает новую строку.
Выбор другой вкладки больше не заменяет предыдущую. Каждая карточка имеет
свой ✕; отмена пустого Add-черновика сохраняет уже выбранные зависимости.

Группа означает AND: сообщение ждёт успешного завершения каждой вкладки после
её выбора. Уже busy цель может закончить текущую работу; idle цель должна
начать работу и затем завершиться. Root учитывает окончание всей цепочки
вкладки (Loop/очередь/дочерние run/AutoCompact), а не отдельное гашение loader.
Каждый успех удаляет только соответствующую видимую карточку. Прогресс хранится
в том же item trigger как `dependencies[{tabId,armedAt,completedAt?}]`; поле
`tabId` остаётся совместимым адресом текущей pending цели/причины финального
допуска. Сохранение и hydrate не возвращают выполненные ожидания. Новая работа
или Stop уже выполненной цели не возобновляет зависимость и не отменяет
подготовку получателя; добавленная позже цель получает собственный armedAt.

Когда все условия выполнены, Root использует прежний readiness/Resume/send и
Main FIFO. Занятый получатель ждёт своего освобождения; повторный успех не
создаёт второй Send. Старое completion до выбора, spinner, ручной Stop,
выключенные и поздние карточки не снимают ожидание. Self/циклы запрещены,
повторный выбор одной pending цели не создаёт дубль, искусственного лимита
числа выбранных вкладок нет. Подтверждённые completedAt сохраняются и после
restart; неизвестный Send по-прежнему требует квитанции той же операции.
Глобальная карта строит по одному ребру на каждую оставшуюся зависимость с
identity owner+item+target, сохраняя единственный полный узел каждой цели.

Раньше и таймер, и целевая вкладка были одни на всю очередь и жили отдельной колонкой в шапке панели. Пользователь: *«можно по отдельности настраивать на разные пункты ранавтор… это будет более логично и детерминированно, понятно, работать»*. Глобальная пара описывала только первый выстрел и не отвечала на вопрос «а перед третьим элементом подождать?».

Срабатывает триггер enabled-головы. Цель ожидания разрешается как item onTab →
legacy runAfterTabId → owner; длительность — item timer либо legacy first-delay.
Timer сохраняет один слот отсчёта на вкладку. Per-item timer ждёт допуска
головы после busy-turn; legacy first-delay начинается при явном arm.
App-restart относится к identity Main, не к remount панели. Закрытая pending
цель удаляется только из своего списка, другие ожидания сохраняются; обычная
close/failure политика не выдаёт закрытие за успешное завершение.

Pause на desktop и через API замораживает именно текущую enabled-голову: timer100 через40с сохраняет60 в item, legacy100 — в общем поле; чужие/disabled таймеры не переписываются. Ноль означает истёкшую задержку, не доказанный конец turn. Раньше remote setter терял остаток, а локальная кнопка считала только legacy-поле — потому freeze живёт в одном store-owner, не в каждом UI. Clear trigger из меню/✕/middle-click/remote использует один owner с прежним single-runnable disarm, condition и Loop не удаляет.

Выбор onTab может вооружить только редактируемую текущую enabled-голову после
применения trigger. Выключенная/поздняя карточка не запускает другой staged head;
idle dependency тоже ждёт своего следующего natural completion. Коммит длительности
таймера — редактирование, не Play. Busy auto-arm процентного условия также head-aware.

Глобальные поля `runAfterTabId` / первой задержки НЕ удалены: их читают внешние потребители (Git-панель, `Restart after` в контекстном меню вкладки). Убрана только их отдельная колонка в UI. При первой загрузке после обновления сохранённая глобальная пара переносится на первый элемент очереди и обнуляется — иначе уже настроенное молча перестало бы срабатывать.

### 2a-2. Условие по заполнению контекста — отдельный gate карточки

ПКМ по карточке → `context` добавляет строку `Context used ≥ 50%`. Оператор переключается между `≥` и `≤`, порог ограничен диапазоном 0–100. Это намеренно НЕ третий взаимоисключающий trigger: карточка может одновременно ждать таймер/другую вкладку и проверять процент. В приложении число означает **использованную**, а не оставшуюся долю; поэтому compact-сценарий «осталось не больше половины» записывается как `Context used ≥ 50%`.

При разрешённом событии runner делает один ограниченный проход по enabled-карточкам. Условие истинно — отправляет эту карточку. Ложно либо точного значения нет — физически переносит карточку в конец и проверяет следующую. Каждый id проверяется не больше одного раза за событие: если все условия ложны, полный круг возвращает их взаимный порядок, ничего не отправляется, `autoRun` остаётся вооружённым до следующего штатного завершения. Если после ротации следующая карточка ждёт другой tab/timer, текущий outcome её не обходит — runner останавливается и ждёт именно её trigger.

По принятому13.10 правилу, если весь проход закончился **подтверждённо ложными**
context-условиями, карточки сохраняются вооружёнными на будущие ответы, но не
удерживают текущее завершение для внешних onTab. Остальное активное продолжение
(включая Loop) по-прежнему имеет приоритет. Unknown не получает этого допуска.
SOURCE помечает только текущий неизменный queue snapshot после bounded pass;
изменение карточки/arm, новый own turn или новое завершение внешнего trigger
требуют повторной проверки. Эта отметка не сохраняется в SQLite и не является
Send receipt. Асинхронное окончание проверки использует прежний continuation
release; bell может повторно проверить только ранее полученный успешный turn,
без синтетического busy→idle. Сценарий ещё не прогнан: пользователь13.10 попросил
только локальную правку и запретил E2E, поскольку соседняя вкладка владеет dev.

Шрам13.10: раньше одна `/compact ≥50%` при exact25% сохранялась вооружённой и
навсегда удерживала внешнюю очередь. Own scheduler забирал outcome до async
context-read, а pending predicate после false продолжал читать enabled-count.
Это не было потерей busy/final или Send admission error; точный witness в tmp.

Процент для решения не читается из видимого meter и не берётся как старое число «этой вкладки вообще». Renderer передаёт provider + текущий session id в существующий `tab:get-context-pct`, а main возвращает значение только из `agentContextUsageState` для той же точной пары. Несовпавшая сессия, ещё не пришедший statusLine/rollout snapshot или ошибка чтения = unknown = условие не выполнено. Это fail-closed: неизвестное никогда не превращается в `0%` и не отправляет prompt раньше времени. Обычный meter по-прежнему может показывать last-known SQLite seed — display и право на автоматическое действие намеренно имеют разную строгость.

Автоматическая ротация хранится в том же durable `items` порядке; отдельного server watermark нет. Debounced persistence схлопывает несколько перемещений одного scheduler-pass в одну запись. Редактирование condition меняет identity отложенной попытки: уже начавшая readiness-проверка со старым `≥/≤ N` становится stale и не может отправить карточку после изменения порога.

Context proof несёт provider/session вместе с числом через readiness, materialization,
work-context и admission в прежний Main FIFO. При A→B runner перечитывает B; A90
не разрешает отправку в B20. Main повторно читает binding после awaited context
observer и сравнивает proof с актуальным send target после своего status await.
Это не per-prompt настройка и не право retarget frozen Send. Numeric0 допустим;
null/строка/ошибка остаются unavailable, а не нулём.

Отсутствующий condition кодируется Store как `'-'`. Его нельзя проверять через
truthiness:12.10 это создало лишний contextProof и цикл первого Resume Send —
проверка ждала canonical writer-row, который мог создать только заблокированный
prompt. Shared predicate отличает `'-'`/legacy`''` от настоящего условия во всех
трёх consumers (подготовка/Root/Main), без изменения frozen fingerprint. Тест
обязан брать ключ из actual Store, а не подставлять удобный пустой string.

### 2a. Run after pivot to other tab (`runAfterTabId`)

Поверх обычного `autoRun` (= «по окончании ТЕКУЩЕГО turn-а отправь head» — слушает busy→idle на собственном табе) добавлен опциональный pivot: выбор **другой** AI-вкладки из любого открытого проекта (теперь через триггер элемента, см. 2a-0; раньше — дропдаун `[on tab ▾]` в шапке панели). Когда выбрана `runAfterTabId = T`, runner ждёт busy→idle на T, а не на queue-owner. Use case: в одном проекте открыт Gemini-таб с длинным research'ем, в другом/текущем Claude-табе сложился промпт «обсуди результат» — арм Run after, на Gemini → когда Gemini закончит, Claude получит промпт.

**Список target'ов = AI-вкладки всех openProjects, не runtime owner'а и не только текущего workspace.** Если меню открыто в Codex-очереди, в dropdown всё равно должны быть Claude PTY, Claude SDK, Codex и Gemini вкладки; если меню открыто в Claude-очереди — Codex тоже доступен; если нужная loader-вкладка живёт в другом открытом проекте — она тоже доступна. Пользователь выбирает «после какой работы продолжить», а не «какому провайдеру/проекту принадлежит это меню». Это была явная правка пользователя: доступность target'ов не должна зависеть от места открытия меню.

**Workflow scope вверху picker'а — фильтр, не target value.** После organization migration список использует tab-owned membership и полный каталог AI-вкладок, независимо от окон/reserve; прежний workflow.projectIds остаётся только legacy fallback. Run After включает `workflowIconsOnly`: видны иконки всех workflow, в том числе пустых и Inbox, без названий и счётчиков на кнопках. Имя остаётся в доступном label/title; цвет, Inbox glyph и fallback-initial принадлежат прежнему общему WorkflowChip. Порядок вкладок/групп и фильтр active/all сохраняются.

У Run After минимальная ширина picker252px, дальше она растёт по полному ряду иконок без искусственного верхнего лимита. Граница viewport сохраняется: если ряд физически шире экрана, иконки переносятся, горизонтальной прокрутки нет. Изменение числа workflow/viewport обновляет ширину и позицию уже открытого окна, не сбрасывая выбор. Это opt-in PromptQueueOverlay; Restart after, Link File и Git сохраняют подписи и прежний wheel/scroll-to-selected режим общего picker.

**RunAfterTabPicker теперь общий inventory-компонент.** Этот же список используется в PromptQueueOverlay (`Run after`), в TabBar context menu (`Restart after`), в file explorer `Link File` и в Git-панели для правого клика по split Generate. Компонент не пишет ни prompt-queue state, ни tab-context state сам: caller передаёт `autoRun`, `runAfterTabId`/`runAfterTabIds`, `setRunAfterTab`, сторону раскрытия и режим видимости. Поэтому поведение выбора различается по вызывающей фиче: Prompt Queue по умолчанию открывает список активных и ожидающих вкладок, остаётся single-select и автовключает `autoRun` только для уже busy target'а; Restart after открывает все AI-вкладки сразу, включает multi-select без закрытия меню после клика, красит trigger в purple и считает сам факт выбранного target'а активной подпиской; Link File открывает все AI-вкладки как single-select read-only target list и создаёт file-tab рядом с выбранной сессией; Git использует picker только как выбор trigger-вкладки и сам запускает generate или generate+commit для текущего repo после busy→idle. Общая часть — workflow inventory, `Не размещены`, project-owned группы/collapse внутри workflow, порядок вкладок, статус-маркеры, tab-color background и loader-strip по настройке `processBar.position`.

Выбор target-таба всегда сохраняет `on tab`, но explicit arm делает только при уже идущем loader'е target'а. Тогда `autoRun=true`, `workflowArmedAt` фиксирует границу текущей работы, а first-chip hint гаснет. Если target idle, trigger остаётся в карточке, но красный staging-hint не исчезает до ручного Play.

Explicit arm внешнего target не означает «выполнить, если он сейчас idle». Если выбранная вкладка уже работает, обещание относится к завершению этого текущего цикла; если она простаивает, runner ждёт её следующий реальный `busy→idle`. Исторический факт, что вкладка когда-то была busy, не даёт новой подписке права немедленно отправить prompt. Иначе повторный выбор давно завершившейся вкладки принимает старое состояние за новый результат. Любая повторная попытка отправки сверяет успешный outcome target с моментом текущего arm; простой `idle` или закрытие редактора эту границу не обходят. Немедленный cold-start остаётся только у собственной очереди owner-таба; восстановление результата, случившегося пока приложение было закрыто, отдельно доказывается временем outcome относительно `workflowArmedAt`.

**Default list = активные и ожидающие вкладки, toggle раскрывает все.** Picker показывает вкладки с loader'ом и вкладки, у которых вооружена своя очередь продолжения. Idle AI-вкладки остаются доступны через маленькую кнопку счёта `active/total` в header'е; повторный клик возвращает компактный список. Выбранный target всегда остаётся видимым: если runner ещё ни разу не видел его запуск, рядом стоит статичный hourglass «ждём первый запуск», а не ложный idle. Строки `No Target` нет: очистка target'а — повторный клик по уже выбранной строке (single-select toggle-off), а пустой выбор является нормальным состоянием по умолчанию.

**Источник busy для T = унифицированный.** Runner подписан на три IPC сразу — `claude:busy-state` (PTY claude + SDK через forward `claude-sdk:busy-state` → `claude:busy-state` в main.js:11559), `codex:busy-state`, `gemini:busy-state`. Все три пишут в общий `Map<tabId, boolean> prevBusyRef`. Pivot не различает «какой агент работает на T», только «есть ли там сейчас активный спиннер».

**UI-статус target-таба — 3 состояния (определяется в `statusFor()`):**

| Состояние target | Иконка справа от имени |
|---|---|
| `busy` (агент сейчас думает/стримит) | вращающийся loader |
| `waiting` (у вкладки есть вооружённая очередь либо выбранный target ещё не запускался) | статичный hourglass |
| `idle` (всё остальное) | ничего |

Семантика лоадера = «агент в этом табе **сейчас отвечает**» — зеркало shimmer-пульсации вкладки в TabBar (`isBusy`). Idle или ещё не запущенный AI-таб не показывает loader, но остаётся в полном inventory: назначение через `commandType` достаточно, session id не является пропуском в picker.

**Реактивность статуса — собственный `busyMap` + fingerprint ожидающих очередей, НЕ `isTabBusyNow` + polling.** Picker подписывается на те же IPC, что TabBar — `claude:busy-state` + `codex:busy-state` + `gemini:busy-state` (focus-независимые broadcast'ы из main, долетают для **фоновых** табов — а target по определению не сфокусирован). Prompt Queue caller отдельно передаёт стабильный набор tab id с `autoRun && enabledItems > 0`; busy имеет приоритет над waiting. Выбранный target без единого busy-снимка тоже waiting. Никакого `setInterval` и подписки React-компонента на весь queue `Map`: selector возвращает сортированный fingerprint id.

**Что было до и почему сломалось (горело):** статус читался из `isTabBusyNow(id)` — это **не-реактивный** module-Map (`prevBusyRef`) runner'а, поэтому picker перерисовывался только по `setInterval(force, 750)`, который вдобавок был gated `if (!runAfterTabId && !open) return` — при закрытом pill без выбранного target интервал вообще не запускался. Спиннер «не крутился». Плюс старый третий статус `inactive = (activeTabId !== id)` означал «это не сфокусированный таб» (а не «не запущен») → `!`-кружок горел почти на **каждой** строке. Юзер: *«везде восклицательный знак, что это значит; лоадер не крутится»*. Новый `waiting` не возвращает эту ошибку: он выводится только из реального обещания очереди или отсутствия первого runtime-снимка у уже выбранного target, а не из focus/active tab. Runner'ский `prevBusyRef` остаётся источником busy→idle edge, но явный выбор внешнего target заменяет его исторический бит текущим workspace-снимком. Иначе поздний дублирующий idle после arm может выглядеть как новое завершение. Ловушка на будущее: `isTabBusyNow` нереактивен — любой UI, читающий его в рендере, обязан иметь собственный реактивный источник, а не polling.

**Где firing:**
- Owner tab: `fireQueueOwner(ownerTabId, triggerTabId)` поп'ит head из очереди ownerTabId и пошлёт команду в runtime **owner'а** (`claude:send-command` для Claude owner, `codex:send-command` для Codex owner). Trigger используется только в логе (стрелка `↩` = self, `⇒` = pivot) и никогда не решает, куда отправлять prompt.
- `findOwnersWaitingOn(triggerTabId)` обходит все queues при каждом busy event, ищет те у кого `runAfterTabId === triggerTabId` (или `runAfterTabId === null && triggerTabId === ownerTabId` для default).
- Успешный pivot-fire one-shot'ит выбранный trigger: после commit отправленного head runner делает `setRunAfterTab(owner, null)`, если текущий `runAfterTabId` всё ещё равен `triggerTabId`. Если в очереди owner'а остались элементы, они дальше продолжаются уже как обычный own-tab Run after; UI-селект не остаётся висеть на завершившейся внешней вкладке. Если send отказал — target не чистится, потому что Run after фактически не выполнился.

**Target chain-drain: pivot owner ждёт не первый idle-edge, а quiescent target.** Если вкладка A ждёт `runAfterTabId = B`, а у вкладки B есть вооружённая очередь, B остаётся незавершённой зависимостью независимо от того, готова ли она стартовать прямо сейчас. Runner не fan-out'ит A ни на cold-start проверке, ни на старом idle-edge B. A получит свой prompt только после того, как B реально отправит своё продолжение, получит `busy:true` и затем штатный `busy:false`. Пользовательский контракт: «жду вкладку B» означает «жду пока B закончит всю свою цепочку», а не «первую паузу B».

Критичный случай: `A → B → C`. Пока B ждёт C, отсутствие loader'а на B означает «цепочка ещё не стартовала», а не «B завершена». Поэтому pending continuation определяется одним общим предикатом `autoRun && enabledItems > 0`; готовность её собственного trigger'а отвечает только за запуск B и не имеет права разблокировать A. Тот же предикат используется runner'ом и UI, чтобы логика отправки и hourglass не расходились.

**Циклы запрещены на записи.** Перед сохранением нового target store проходит текущую цепочку `runAfterTabId`. Связь, которая вернётся к owner'у или войдёт в уже замкнутый участок, отклоняется; UI сохраняет прежний target и показывает предупреждение. Иначе `A → B → A` корректно выглядел бы как вечное ожидание и не имел бы natural события, способного разорвать граф.

**Success→busy gap считается частью цепочки.** После успешного `send-command` очередь уже может снять head, но агент ещё не успел прислать `busy:true`. На этот короткий промежуток ставится `queueAwaitingBusyStart`: pivoted owners видят target как «queued turn starting» и ждут первый `busy:true`, а не проскальзывают между commit'ом prompt'а и началом нового turn'а. Ошибка/отказ send снимает marker и disarm'ит autoRun/stopAfter как раньше; таймаута для «подождать busy» нет, источник истины — только событие runtime.

**Конфигурация доступна всегда, выполнение ждёт владельца.** Arm очереди в остановленной или ещё не запущенной owner-вкладке сохраняется как обещание и сразу запускает настроенный first-delay, но не разрешает paste в shell. Readiness не ставит пользовательский таймер на паузу и не сбрасывает его при новом busy-событии: когда отсчёт закончится, runner либо отправит head в готовый idle input, либо дождётся/инициирует готовность владельца через обычный scenario flow. Каждая асинхронная попытка сверяет owner, target, `workflowArmedAt` и собственное поколение после каждого `await`, поэтому поздний результат старой попытки не отправит карточку после смены target или повторного arm.

**Launch-if-needed: ожидание неактивного владельца включает запуск, а не только слушание.** Когда очередь готова стрелять, а owner-агент вообще не запущен (`readiness: inactive` — процесс мёртв, не «busy»), runner не ждёт вечно чужого события: он сам инициирует Start/Resume через общий scenario runtime (лог `LAUNCH_FOR_QUEUE`, resume при сохранённой сессии, fresh start иначе) и остаётся deferred до обычного tui-ready. Один запуск на текущую голову очереди — `queueOwnerLaunchInitiated` (owner → headId) не даёт повторный launch, пока голова не сменилась/не удалена; сам prompt отправляется дальше обычным подтверждаемым путём после readiness. До этого arm на остановленной вкладке молча не делал ничего — пользователь ставил Run After и уходил, а очередь так и не стартовала.

Отказ launch не «пропускается тихо»: после failed/refused запуска runner пере-проверяет presence. Если владелец всё ещё `inactive`, событие готовности не придёт никогда — очередь бы молча зависла на этой голове; это ненормальный исход и он идёт по общему DISARM-контракту (autoRun/stopAfter гаснут, toast «не удалось запустить агента»). Если же re-probe видит `starting`/`active`, отказ был легитимной гонкой с параллельным запуском (History Enter, auto-resume владеет shell) — deferred-ожидание остаётся, readiness придёт от конкурента.

Renderer readiness не является последней границей безопасности. Main повторно проверяет тот же PTY и поколение процесса перед paste, перед Enter и в самой синхронной точке записи Enter; начавшийся Stop или смена runtime превращает попытку в `deferred`, а не в постоянный отказ. Deferred item остаётся head'ом, Run after остаётся вооружённым и повторяется по следующему readiness-event. Для незапущенного trigger-таба hourglass означает ожидание первого реального `busy→idle`, а не разрешение немедленно выполнить owner-очередь.

Run After (`prompt-queue`) и Loop (`prompt-loop`) являются двумя режимами одной
автоматической доставки. Название режима не меняет admission-контракт: оба
обязаны пройти одинаковые проверки живого процесса, idle/input-ready текущего
поколения, image refs, draft guard и post-Enter audit. Нельзя распознавать
автоматику сравнением только с одним строковым label: тогда Loop обходит уже
существующую защиту Run After и при временно неготовом input получает terminal
failure вместо deferred-ожидания.

**Stale target — lazy validation.** Target валиден если вкладка существует в любом `openProjects` и это не сам owner (`ownerTabId !== targetTabId`). Если target-таб закрыли или он совпал с owner'ом — runner делает `setRunAfterTab(owner, null)` и фоллбэк на own-tab. Не валидируем в store (создало бы зависимость store→workspaceStore). Validation повторяется на каждом busy event и в cold-start subscription.

**UI layout — одна колонка настроек, панель вдвое уже.** Header держит только Run after / Stop after / Post / Loop, каждая строка на всю ширину панели. Прежней левой колонки (глобальный trigger «on tab» + поле задержки) больше нет: условие запуска переехало на конкретный элемент очереди (см. ниже), и половина ширины панели освободилась. Юзер: *«ранафтор мы тоже сокращаем его в 2 раза, потому что нахуй мне это надо»*. Историческая заметка про пропорции колонок (`1fr 1fr` против `90px 1fr`) сохраняет силу для любых будущих двухколоночных строк внутри панели: неравные колонки читаются как «правые кнопки непропорционально огромные».

**Футер — одна составная кнопка «из терминала | +».** Широкая левая зона (~80%) забирает текущий ввод агента в очередь, узкая правая (~20%) открывает редактор нового элемента. До этого были две равные кнопки `+ grab` / `+ add`, и они читались как равнозначные, хотя частота использования у них разная. Шов между зонами принадлежит левой кнопке — тот же контракт, что у Stop/Close split (см. ниже).

**Фиксированная ширина + drag-resize (не `fit-content`).** Раньше panel был `width: 'fit-content'` с clamp `minWidth/maxWidth [240, 360]` — ширина **прыгала** при каждом добавлении +grab-чипа или смене лейбла кнопки (юзер: *«когда я плюс граб добавляю промт, ширина меняется — она должна быть фиксированная»*). Теперь ширина **фиксированная**, хранится глобально в `useUIStore.promptQueueWidth` (localStorage `noted-terminal-prompt-queue-width`, clamp `[240, 600]`, default 300 — внутри старого fit-content-диапазона, чтобы первый рендер после миграции не дёрнулся; зеркало `timelineWidth`-паттерна, один привычный размер на всё приложение). Drag-resize меняет **только ширину** (высота — это `chipLineClamp` из Settings, её не трогаем). Во время drag рендер идёт из локального `dragWidth` (60fps без store-churn), коммит в store на mouseup.

**Единая полоса сверху — постоянная control-strip, панель раскрывается ПОД ней.** Над панелью Run after идёт один горизонтальный ряд, прибитый к правому краю: чипы активных запросов оркестрации (когда они есть), кнопка истории запросов, кнопка настроек запросов и четыре квадратные кнопки управления очередью — свернуть/развернуть, автозапуск со счётчиком, забрать ввод, Timeline. Timeline стоит ПОСЛЕДНИМ: он относится к соседней поверхности, а не к очереди, и в начале ряда сбивал чтение.

**Полоса не двигается от раскрытия собственной панели.** Ширина полосы определяется её содержимым и не связана с шириной панели; сворачивание Run after не сдвигает ни одной кнопки. Прод-шрам: раньше блок с историей и настройками запросов позиционировался от левой грани панели, и при сворачивании он уезжал вправо вместе с ней. Пользователь: *«она не должна перемещаться вправо, то есть вот этот компонент, который горизонтальный, он должен быть единым»*. Кнопка, которая меняет положение от состояния соседнего блока, ломает мышечную память — по ней промахиваются.

Полоса непрозрачная и плотная: прозрачная теряется на чёрном терминале/Timeline, кнопки без общей подложки выглядят разрозненно. Статус/счётчик не read-only: клик по нему переключает тот же `autoRun`, что и основной Run after pill, чтобы в свёрнутом и раскрытом состоянии не было двух разных ментальных моделей. Анимация раскрытия короткая (100ms) и именно slide, не fade-pop; chevron меняет направление синхронно с движением. Opening-анимация запускается только после явного клика expand/collapse; при переключении на вкладку, где панель уже была открыта, remount восстанавливает layout без повторного выезда.

**История и настройки запросов открываются вниз, не поверх чипов.** Обе панели выпадают под полосой и смещаются левее раскрытой Run after, а не перекрывают ряд чипов. Чипы — живой статус текущих запросов; перекрывать их окном значит прятать ровно то, за чем пользователь следит. Открытие по клику, не по наведению: панели интерактивные (раскрытие строк, кнопки действий), а hover-открытие самозакрывается при движении курсора внутрь и мигает, когда курсор просто пролетает к соседним кнопкам.

**Карточка чипа появляется слева и выравнивается по его верхней грани.** Запросов может быть несколько подряд, и карточка снизу перекрывала бы следующие чипы. Слева места достаточно, а выравнивание по верхней границе даёт однозначное соответствие «эта карточка про этот чип»: наведение на нижний чип открывает карточку ниже, на верхний — выше. Для этого у общего Tooltip появился режим выравнивания по началу стороны вместо центрирования.

Collapsed/expanded state принадлежит вкладке: default = expanded, но если пользователь свернул Run after в конкретном табе, это сохраняется при переключении вкладок и после restart до ручного expand. Collapse записывается в store сразу на click, а closing-анимация остаётся локальной; иначе быстрый переход на другую вкладку в первые 100ms мог бы потерять намерение пользователя.

Когда Timeline раскрыт через `Cmd+\` / `Option+\`, root сдвигается левее на ширину раскрытого Timeline минус его collapsed-slot: правая грань Run after примыкает к левой границе expanded Timeline, а не остаётся под ним. Timeline — колонка, а не окно: поверх неё полоску было бы просто не видно.

**От бокового окна Run after больше НЕ отходит (2026-08-17).** Раньше полоска уезжала влево ещё и на ширину открытого бокового окна — терминала или переписки, — чтобы не оказаться под ним. Плата: полоска меняла место при каждом `Cmd+]` и при каждой смене основной поверхности, причём сдвиг был заметно больше её самой. Отступать ей не нужно — у неё есть свёрнутый вид, в котором она почти ничего не занимает. Пользователь: *«он не должен сдвигаться влево, я решил эту фичу убрать, так как у нас уже доступен свёрнутый режим»*. Кнопки, привязанные к самому терминалу (стрелка вниз, переключатель второй поверхности), считают полный отступ как раньше: они в другой коробке, и её правый край боковое окно реально закрывает. Отсюда два разных значения из одних и тех же аргументов в `Terminal.tsx` — `resolveTimelineInset` для полоски и `resolveCenterRightInset` для кнопок терминала. Когда открыт `Cmd+]` / `Option+]` HistoryPanel, Run after остаётся в той же правой зоне и рендерится поверх HistoryPanel; для этого overlay вынесен из terminal isolation-wrapper'а и получает z-index выше панели истории. Без выноса наружу `z-index` дочернего элемента проигрывает родительскому `isolation:isolate`, и визуально меню оказывается под HistoryPanel при корректных числах z-index внутри себя.

**Не отходит — значит стоит поверх, а не прячется под.** Перестав уступать место боковому окну, полоска обязана лежать ВЫШЕ него: на слое ниже «не отходит» означает не «стоит на месте», а «спряталась под ним». Полоска принадлежит рабочей области, боковое окно — временный гость поверх её центра, вызываемый одной клавишей; гость не может закрывать собой постоянный орган управления.

Раскладок две, и правило одно на обе: одиночный режим — `Workspace.tsx::promptQueuePortalHostId` (слой 140 против 130 у `FloatingTerminalFrame`), режим панелей — `SplitPaneSurface.tsx::splitPaneQueueHostId` (то же число против бокового терминала и бокового чата панели). Панельная копия оставалась на 120 и была не видна под боковым окном своей панели: правило починили в одном месте, а живёт оно в двух. Выше полоски остаётся только рамка окна панели (`SPLIT_PANE_FOCUS_FRAME_Z = 200`) — граница не должна прерываться тем, что внутри неё лежит. Оба числа читает один тест (`topStripLayout.wiring.test.mjs`), потому что разойтись они могут молча.

Unpinned Timeline (`timelinePinned=false`) — overlay, а не зарезервированная колонка. Если он раскрыт и пользователь кликает по терминалу, сайдбару или другой обычной области Workspace, `Workspace.tsx` закрывает `timelineTreeModeTabs[tabId]` обратно в rail. Исключение обязательно для `[data-history-timeline-pin-toggle]`: клик по StatusBar pin должен успеть превратить текущий overlay в pinned layout, а не сначала закрыть Timeline на capture-mousedown. Pinned Timeline (`timelinePinned=true`) не закрывается outside-click'ом — это уже layout mode.

- **Resize-handle на СВОБОДНОЙ грани, не на опорной.** Panel раскрывается влево от rail: опорная правая грань остаётся у Timeline, не двигается → handle на ЛЕВОЙ грани, drag влево растит панель (dx инвертируется). Это прямое следствие `🧩 Code-Patterns/.../всплывающие-окна.md::Панель с resize: пользователь меняет размер вручную`. Handle на опорной грани оторвал бы панель от якоря.
- **`ANCHOR_SIDE: 'left' | 'right'` — 1-флип-параметр на будущее.** Юзер заложил: меню в будущем может переехать влево. `ANCHOR_SIDE` управляет тремя вещами разом: какая грань pinned (`right:0` vs `left:0` внутри терминальной области), на какой грани handle (`left:0` vs `right:0`), и знак дельты в drag (`right` → `-dx`, `left` → `+dx`). При переезде меню — поменять одну константу, handle и направление роста подстроятся сами. Принцип «resize учитывает визуальное расположение, расширяется только в доступную сторону».
- **Handle flush-inside (`left:0`, width 6), НЕ снаружи (`-3`).** Panel имеет `overflow:hidden` — offset наружу клипнулся бы в тонкую полоску. 6px-зона лежит над левым padding'ом header'а, не над интерактивными контролами. `data-cmd-hover-popover` на handle — чтобы mousedown не закрывал Cmd+Shift-пиннутый popover в другом месте.

**Slideout через `createPortal(menu, document.body)` — обязательно.** Раньше picker рендерил slideout inline (`position:fixed` внутри JSX picker'а). Это **не работало**: panel root имеет `backdrop-filter: blur(8px)`, что по CSS-spec делает его containing block для **любого** `position:fixed` потомка. Coords `top: panelRect.top; right: window.innerWidth - panelRect.left + 6` пересчитывались **от panel'я, не от viewport'а** → менюшка улетала за пределы экрана, клики провалились в пустоту, симптом «кнопка тупо не открывается» (`open=true` в state, нет визуала). Editor slideout не страдает потому что он — sibling panel'я, не descendant; picker живёт **внутри** header'а panel'я, поэтому нуждается в портале. Anchor сейчас передаётся через `panelRef` prop напрямую (не walk-up до `position:absolute` ancestor'а — этот walk был фрагилен: HMR / CSS-in-JS объект-стиль не выставляет inline `style.position`, walk доходил до BODY, fallback anchor был мусором). См. `methodology/сценарии-багов-design.md::10` (Portal-кейсы) и `methodology/дизайн-принципы.md::position:fixed × ancestor transform`.

**Click-toggle-off в picker'е.** Повторный клик по уже-выбранной строке в dropdown сбрасывает target обратно в null. Без этого юзер для отмены выбора должен скроллить к верхней строке `— no target —`, что для пары AI-табов нормально, для проектов с 10+ табами — раздражает. Реализация в onClick row'а: `setRunAfterTab(tabId, isSelected ? null : t.id)`. Канонический паттерн single-select — см. `methodology/дизайн-принципы.md::Click-toggle-off на single-select pill`.

**Hover-clear на закрытом pill.** Когда target уже выбран, закрытый `on tab` pill при hover заменяет левый runtime-dot на маленький `×`. Клик по нему делает `setRunAfterTab(owner, null)` и не открывает dropdown. Это второй быстрый clear-путь рядом с click-toggle-off в списке: пользователь видит выбранную вкладку в header'е и может снять подписку там же, не раскрывая inventory.

**Цвет дотика по AI-runtime, не по `tab.color`.** Раньше я использовал `tab.color` как ключ (`claude → #DA7756, gemini → #4E86F8`), но это давало одинаковую саффрон-точку и PTY Claude, и SDK Claude — юзер: *«отображаются все вкладки терминала, хотя клода не запущен... отметь соответствующим кружочком, SDK ≠ PTY»*. Сейчас отдельный enum `AiTabKind: claude-pty | claude-sdk | codex | gemini` и `AI_KIND_COLOR` map: PTY = `#DA7756` (saffron), SDK = `#D28C5A` (terracotta, ровно как в TabItem.tsx:425 SDK override), Codex = `#10A37F`, Gemini = `#4E86F8`. Источник истины для kind — детектор:
- `tabType === 'claude-sdk'` → `claude-sdk` (regardless of commandType/sessionId — SDK-таб AI-предназначения by definition)
- иначе `commandType === 'claude'` → `claude-pty`
- иначе `commandType === 'codex'` → `codex`
- иначе `commandType === 'gemini'` → `gemini`
- иначе таб ВООБЩЕ не показывается в списке (фильтр против bash/run-dev — в них нет turn-end edge, бессмысленно ждать)

**Fingerprint Pattern в селекторе.** Подписка на `openProjects` через селектор возвращающий объект ломает Zustand: `set({openProjects: new Map(...)})` каждый busy event → Object.is видит новую ссылку → re-render → селектор создаёт новый объект → infinite loop → `Maximum update depth exceeded`. Фикс: селектор возвращает строку-фингерпринт (id+name AI-табов), shape деривируется через `useMemo([fingerprint, tabId])` с `useWorkspaceStore.getState()` внутри useMemo. Этот шрам ловится моментально через React HMR, но симптом ругательский (стэк-overflow + бесконечный лог) — см. `fix-performance-lags.md::Fingerprint Pattern`.

### 3. External Editor hijack
Claude Code TUI имеет хоткей `Ctrl+G` → `chat:externalEditor` → `execSync($EDITOR <tempfile>)`. Мы перехватываем это:
- В `pty.spawn` инжектим `EDITOR=~/.claude/hooks/noted-code-grab.js`
- Helper script читает tempfile, шлёт текст в наш Unix socket, опционально truncate'ит файл → инпут Claude очищается

Карточки списка и выбранного target теперь рисует общий `TabCard` (также pane
header/HiddenWindowPicker). Он получает status snapshot `RunAfterTabPicker`;
собственный process lookup для каждой строки не добавляется. Context/Fast,
статус, task lane и project icon следуют общим источникам/Settings. `setRunAfterTab`
и trailing navigation/clear остаются у caller, поэтому обычный выбор dependency
не превращается в переход к окну. Подробности — `fact-process-bar.md::Карточка вкладки`.

## External-editor capture — versioned owner/operation handshake

Canonical helper — `src/main/noted-code-grab-v2.js`, протокол — `src/main/agent-input-capture-protocol.js`. Dev запускает repo helper, packaged main использует `~/.claude/hooks/noted-code-grab-v2.js`. `install:claude-hook` ставит v2 и его модуль вместе с обычным turn hook; **старый `noted-code-grab.js` не перезаписывается**, потому что он может обслуживать ещё работающий старый main. Новому main запрещено отправлять автоматический Ctrl+G в CLI со старым helper: preflight возвращает `wrong_editor`, нужна новая сессия с новым env.

Перед Ctrl+G main пишет versioned intent `/tmp/noted-grab-v2-<cliPID>.json`: random operation ID, owner-main ID, отдельный token поколения PTY, mode, agent, PID aliases, точный socket и снимок поколения input. Helper не удаляет intent на чтении и **не меняет tempfile до разрешения main**. Он заявляет свой helper ID, передаёт `GrabInput stage=prepare` с exact operation/owner/PTY identity и исходным текстом. Main проверяет именно эту операцию и актуальную input generation; поиск только по PID/tab больше не является разрешением.

| mode | Что делает | Lifecycle tempfile |
|---|---|---|
| `grab` | Читает → prepare → exact authorization → truncate | пусто только после разрешения |
| `copy` | Читает → prepare → exact authorization → не трогает | как было |
| `clear` | Prepare → exact authorization → truncate | пусто только после разрешения |
| `restore` / `put` | Prepare → exact authorization → пишет переданный текст | новый текст только после разрешения |
| `<no intent>` | настоящий manual Ctrl+G → `$NOTED_ORIGINAL_EDITOR` | редактор пользователя управляет |
| cancelled / stale / wrong owner | сохраняет файл, не открывает внешний редактор | как было |

**Commit и cancel выбирают один атомарный результат.** `decision.json` в приватном operation-directory публикуется через exclusive hardlink уже полностью записанного JSON: main разрешает commit, timeout main/helper может отменить. Победившая отмена не может стать commit от позднего socket callback. Потеря ACK после commit не отменяет ранее выданное разрешение: main уже получил исходный текст, а helper читает тот же exact decision с диска. Результат применения helper сохраняет отдельно; main требует его вместе с возвращением TUI и неизменным поколением. Подписка на parent-return ставится **до публикации commit и до ACK**, иначе быстрый helper выйдет раньше подписки.

**Таймаут не доказывает, что Ctrl+G проигнорирован.** На 3000ms main возвращает `external_editor_timeout`, но оставляет cancelled intent. Поздний helper должен поглотить отмену и выйти с исходным текстом, а не принять удалённый lock за ручной Ctrl+G. Пока нет exact helper outcome + exit / parent-return либо доказанного retirement процесса, следующий automatic capture получает `external_editor_pending_drain` без новой клавиши. Generic ready-frame, отсутствие процесса helper в одном `ps` и неизменный глобальный helper-log не являются доказательством, что CLI уже обработал клавишу. Настоящий no-op пока не имеет отдельного provider ACK; это известная граница recovery, а не повод бесконечно повторять Ctrl+G.

**Manual recovery после завершившегося helper.** Если прошлый helper уже записал outcome и доказанно вышел, новый вызов helper самим CLI — доказательство нового входа в редактор. Он убирает только aliases той же operation и открывает пользовательский editor. Если helper вообще не запускался после uncertain automatic Ctrl+G, происхождение следующего вызова неоднозначно: он сначала поглощает сохранённую отмену без изменения текста. Следующий ручной вызов снова открывает редактор. Не выдавать это за доказанное распознавание genuine no-op; physical E2E и решение по recovery обязательны перед promotion.

**Cleanup только exact-owner.** Старый callback не удаляет aliases новой operation. Retirement оставляет cancellation dispatch, пока старый CLI ещё может жить после отправленного kill; новый PTY/main token отделяет реальный новый процесс даже при PID reuse. Socket failure до commit сохраняет текст; поздний callback не трогает image bindings новой вкладки. Подробнее и воспроизведение: `fix-external-editor-late-helper.md`.

**Захват текста и готовность терминала — разные исходы.** Main разрешает helper очистить файл только после подготовки полного текста и image refs. Ошибка image resolver/materialization до commit оставляет native input на месте. Если helper уже применил grab, а проверка возврата TUI/поколения потом не прошла, `success:false` остаётся запретом дальнейшей отправки, но ответ обязательно несёт `draftTransfer: {id, tabId, text, images, imagePaths}`. `id` — physical capture operation ID, не hash текста. `capturedText` рядом с результатом хранит точный текст helper до преобразования image-маркеров, для full-text proof. Codex external editor пишет seed без добавленного newline: helper не обрезает его, transport-newline снимается только у Claude.

History/Pull/Run-after не имеют права выбросить `draftTransfer` из-за `success:false`: `agentDraftTransfer.mjs` принимает snapshot один раз по ID, сохраняет текущие History text/chips и remap'ит image IDs через существующий `mergeFailedHistoryAuthoringSnapshot`. При смене показанной вкладки snapshot возвращается в исходную owner-вкладку. Queue принимает уже захваченный snapshot даже при неподтверждённой готовности терминала; отказ queue-add возвращает его в History. Поздний Send-preflight и его cancellation переносят весь `draftTransfer` и `draftImagePaths` наружу; History восстанавливает старый send snapshot, затем новый native snapshot, а не только числовое количество картинок. `/draft` bridge передаёт domain failure как полный JSON при успешном транспорте, иначе bridge rejection превращает переданный текст в пустую HTTP 500-ошибку.

**Coalescing только одной операции.** Renderer wrappers используют `tabId:mode:captureRequestId`; независимые вызовы получают разные random request IDs. Старый `tabId:mode` отдавал один физически изъятый draft одновременно History и MCP. Copy не разделяет destructive result и не очищает Codex image-slot bindings; подготовка image refs до commit также read-only относительно native bindings.

## Имя скрипта — `code` в basename важно

Claude classifies `$EDITOR` по basename:
- содержит `code|cursor|windsurf|codium|subl|atom|gedit|notepad++|notepad` → GUI editor → `inkInstance.pause()` + `suspendStdin()` (тихо, без вспышки)
- иначе → терминальный → `\x1b[?1049h` alt-screen flash, видно как мерцание

`noted-code-grab.js` начинается с `code` → GUI path. Без флэша.

Источник: `packages/claude-code-src/utils/editor.ts:20-30`, `:49-52`.

**`EDITOR_OVERRIDES` ловушка:** Claude дописывает `-w` для `code/subl` (`promptEditor.ts:68`). Lookup **exact**, поэтому `noted-code-grab` не получит `-w` — basename совпадение через `includes`, но override map по точному имени.

## Защита от user-zshrc clobber

У юзера в `~/.zshrc` может быть `export EDITOR="/usr/local/bin/subl -w"`. Когда наш shell-integration source'ит user-zshrc — он **затирает** наш EDITOR injection. Решение в `setupShellIntegration`:

```bash
__ct_injected_editor="$EDITOR"      # сохраняем наш до source'а user-zshrc
source "$HOME/.zshrc"               # user-zshrc может затереть EDITOR
# Восстанавливаем наш ТОЛЬКО если path указывает на наш helper:
if [[ -n "$__ct_injected_editor" && "$__ct_injected_editor" == *noted-code-grab* ]]; then
  export EDITOR="$__ct_injected_editor"
fi
# Параллельно сохраняем user'ский EDITOR в NOTED_ORIGINAL_EDITOR для passthrough mode:
if [[ -n "$EDITOR" && "$EDITOR" != *noted-code-grab* ]]; then
  export NOTED_ORIGINAL_EDITOR="$EDITOR"
fi
```

Guard `*noted-code-grab*` — не трогаем случайные пользовательские настройки. Только наши перезаписываем.

## getExternalEditor memoize — рестарт Claude обязателен

`getExternalEditor()` в Claude **memoize'ан на первом вызове** (`utils/editor.ts:164-183`). EDITOR должен быть в env **до** spawn'а Claude. Существующие табы запущенные ДО env injection не получат фичу до перезапуска Claude в табе.

**Pre-flight check в `claude:grab-input`:** через `ps -p <claudePid> -wwwE | grep EDITOR=` — если EDITOR ≠ наш → return `wrong_editor` error code → toast `"Restart Claude in this tab — grab needs our editor helper"`. Без этого юзер кликает grab, Sublime открывается в стороне, никаких ошибок — недоумение.

## Глобальный обзор очередей и редактор

Страницы — `Queues` и `Settings`. В Settings сначала Auto-compact, затем Auto-stop;
каждое правило имеет собственный click-select workflow. Открытый checkbox-picker
временно удерживает hover-родителя до закрытия, не закрепляет его. Галочка слева,
сверху одна кнопка: `Select all` при пустом/частичном выборе, `Clear all` при
полном (включая выбор всех строк вручную). Раскрытие не растягивает основную рамку.

Общий Run After находится в строке над sidebar-вкладками на правом краю ряда History / VS Code; SVG+счётчик не входит в прокрутку остальных инструментов (`WorkspaceNavigationRow` передаёт его в `SidebarToolsRow`). Его расположение не ограничивает область текущим проектом: обзор охватывает все workflow. Первоначально обсуждалась нижняя StatusBar, но пользователь перенёс вход наверх. Hover показывает ту же поверхность как preview; только клик по верхнему чипу Run After без remount закрепляет её. Внутренние clicks по страницам, вкладкам, настройкам и дочернему редактору не закрепляют общий обзор: после ухода из hover-кластера preview закрывается. Уже явный закреп переживает навигацию. Повторный клик по верхнему Run After закрывает окно; отдельного `×` нет. Окно раскрывается вниз-вправо и clamp'ится viewport'ом. С05.10 обычная рамка обрезается по фактическому содержимому и по ширине, и по высоте; сохранённые размеры задают пределы, не обязательное пустое поле. Даже старый `heightFixed=true` не включает настройку сам. Кнопка «Настроить размер» в верхнем ряду явно показывает резерв и фиолетовую правую, синюю нижнюю и угловую ручки. Без этого режима resize hit-targets отсутствуют. Повторный клик скрывает направляющие и снова обрезает пустоту, сохраняя пределы; флаг режима и пределы переживают reopen/restart. Это отдельное состояние от hover/pin.

Захваченный resize (включая редактор карточки) и выбор Rewind временно удерживают preview, но не закрепляют его. После жеста проверяется последняя реальная позиция курсора; подписи страниц и выступающие ручки принадлежат hover-кластеру. Закрытие/смена страницы проходит через save/ownership guard **каждой** встроенной очереди: поля blur-save, незавершённое image-вложение удерживает владельца. Parent pointer-capture не закрепляет обзор. Его hover-кластер включает portal'ы всех собственных редакторов/picker/настроек по instance-token, исключает чужие меню и полноэкранные backdrop; задержек открытия/закрытия нет.

Шрам10.10: одного отсутствия close-таймера недостаточно. Native `mousemove`
уже отклонил hover, но обычный React state-update оставлял global portal до

учитывает timeout-вызовы; ожидание нескольких кадров после жеста скрывало баг.

renderer; explicit pin, click-child hold и возврат после Save не являются задержками.

С03.10 очередь постоянно видна под своей вкладкой. Уточнения04.10 отменили растянутые колонки, подпись «после завершения», отдельный счётчик шагов и карандаш prerequisite. Карта содержит **полноценные уникальные узлы вкладок**, включая цели без своей очереди: у каждой общий TabCard и Post/Loop/+…/Play-Pause. Пользователь выбрал вариант A: связь выходит **из конкретной итерации**, затем идёт к внешней границе ожидаемой вкладки перед project-icon. `Model → Sol` с OnTab означает, что смена модели ждёт указанную вкладку, а не запускает её после себя. Старт от общей шапки скрывал, какому шагу принадлежит условие. Legacy Loop-only target якорится к Loop-control. Головная связь сплошная, будущие/выключенные шаги пунктирные; две связи по itemId не схлопываются. Перестановка шага пересчитывает origin даже при неизменной высоте узла. Вариант B с повтором target-chip под шагом отвергнут: одно и то же название читалось дважды. Clear-X остаётся рядом с действием без пустого фиолетового уголка; выбор/смена условия — ПКМ шага.

TabCard берёт общий цвет, шрифт, geometry, padding/reserve сигналов; приватного растягивания `fullWidth/flex:1` нет. Ширина чипа определяется содержимым до лимита имени. Project-icon остаётся слева снаружи цветного чипа. Обычный клик навигирует placement-aware, Cmd/средний — add-here. Песочные часы входящей enabled-зависимости стоят **внутри чипа после названия, перед PaneMap**: используется тот же SVG-компонент, что в локальном picker, без копии TabCard. Здесь часы означают «эту вкладку ожидает шаг», не подменяют собственный busy/process-strip вкладки. Play/Pause20×20 перенесён в конец Post/Loop/+… строки и вызывает прежний toggleAutoRun с freeze countdown, а не отдельный исполнитель. Пустая очередь сохраняет disabled Play. Порог `≥50%` остаётся строкой условия, маленький `%` отмечает его наличие, фактический context number не заменён порогом. Нижняя task-plan полоса скрыта только здесь; taskPlan и обычные оконные карточки не меняются. Исправленный общий paddingRight не переопределяется.

Левая рамка очереди совпадает именно с левым краем **цветного чипа**, без project-icon; для исходящей стрелки, наоборот, icon входит в наружную границу. Верхняя control-strip заходит на нижний край чипа на2px. Нижние квадратики задач здесь мешали такому соседству и не нужны в обзоре автоматизации. Контролы участвуют в intrinsic min-width самой очереди, а ширина итерации остаётся по её тексту/действиям. Сводить эти разные границы к одному `left` или растягивать вкладку по ширине панели нельзя.

Встроен тот же `PromptQueueOverlay`, без второго состояния или runner: Post/Loop, порядок, условия, вложения и правки относятся к тому же per-tab store. Компактная плотность уменьшает текст Post/Loop и названия действий, сохраняя читаемость условия и размеры самой вкладки. В карте нет дочернего всплывающего списка шагов и второго rail; локальный Run After в History по-прежнему раскрывается числовой кнопкой. Embedded-копии не меняют его `panelCollapsed/previewId` и не подписываются на composer grab/Play. Подробный редактор одного prompt остаётся отдельным bounded portal с тем же payload-lock/save-path.

Первичная карта группирует связанные узлы owner-first, отступ ограничен одним уровнем. После показа группы/порядок/отступы сохраняются в памяти общего контрола: добавление обратного ребра не переставляет уже видимые A/B, в том числе после reopen или страницы Settings. Новая ранее не показанная цель может присоединиться к группе owner. С09.10 группа задаёт порядок, но больше не является неразрывной вертикальной колонкой: карточки заполняют строку слева направо, следующая строка начинается под самым высоким блоком предыдущей. Число колонок зависит от доступной ширины, размеры карточек остаются собственными. Общая цель двух owner занимает один узел; при двух колонках оба owner могут стоять сверху, цель — следующей строкой.

Маршрут связи зависит от реального размещения. В одной колонке он проходит слева вверх/вниз к target; между колонками сначала поднимается в зарезервированный проход над более ранней строкой, затем пересекает колонки и спускается к target. Вертикальные участки разных связей получают отдельные дорожки при пересекающихся диапазонах; несмежные диапазоны переиспользуют место. Горизонтальные проходы также разделены. Высота прохода учитывает выступающие сигналы шапки, а ширина дорожек входит в упаковку/min-width/fit. Секции активных и выключенных используют общие колонки, чтобы связь через полку не пересекала чужую карточку. Прежний `min(source.lane,target.lane)` пересекал тексты соседних очередей при межколоночной связи; отдельная дорожка для каждого ребра не даёт разным зависимостям сливаться в ложную общую линию. Новое ребро может добавить место под дорожки, но не пересортировывает карточки.

ResizeObserver/rAF обновляет DOM/SVG без per-move React-render или подписки на scroll соседних History. Item IDs/order входят в geometry-key, rect каждой итерации — точный anchor; ширина/высота строк также наблюдаются. Один keyed editor на вкладку сохраняет draft. Внутренних скроллов у шагов нет, общий scroll-area резервирует gutter. Полка сохранена; пауза/исчерпание не убирают осматриваемый узел до следующего открытия.

Resize общего окна сохраняет pointer-capture оптимизацию: cursor/selection принадлежат ручке, body/html не меняются; настройки коммитятся на release из фактического начального rect. Детальный prompt-editor остаётся bounded portal: его ширина и координаты ограничиваются viewport, а не узкой intrinsic-очередью. Старое предположение «embedded-очередь достаточно широкая» после сжатия давало отрицательный left редактора и hover-close по пути к невидимой resize-ручке; bounds исправлены без pin от фокуса.

Упаковка очередей использует сохранённый предел ширины, а внешняя рамка — занятый результат этой упаковки. Если повторно паковать по уже обрезанной рамке, она может самопроизвольно сужаться или перестать расти при изменении содержимого. Минимальная ширина измеряет не только легенду страниц, но и Post/Loop/+…/Play strips со своим отступом и глубиной связи: одна легенда позволяла сжать внутренние кнопки на18px за край. На странице автокомпакта ширина следует её собственному содержимому, а высота ограничивает общий scroll-area. Общий опциональный профиль настройки пределов описан в `docs-global/ux-паттерны/всплывающие-окна.md::Панель с resize: пользователь меняет размер вручную`.

Страница автокомпакта использует content-sized border-mounted controls без нативных checkbox. Workflow — не generic choice-кнопки: они переиспользуют целый визуальный `WorkflowChip` верхней полосы, как и workflow-фильтр `RunAfterTabPicker`. Одинаковы иконка/буквенный fallback, нейтральные цвета idle/selected/hover, размер и `projectTabsFontSize`; собственная коричневая палитра и пустой слот вместо иконки были причиной неузнаваемого списка. `resolveWorkflowIcon` сохраняет отличие legacy undefined (иконка первого проекта) от явного null (очищена), а metadata/font обновляются на открытой странице. Check обозначает включение в область, не текущий UI-workflow; click меняет только policy, не навигирует. У каждого caller остаются свои счётчики: navigation activity не копируется в compact-running, «Все workflow» остаётся отдельным control, а «Без workflow» — отдельным scope. Активность политики видна и после ухода со страницы: верхний чип показывает порог, а основной Run After trigger — компактную иконку. Большие полноширинные кнопки включения/исключений/idle-batch не являются частью этого интерфейса.

Включённое правило и реально выполняющееся сжатие — разные сигналы. Пока `/compact` отправлен и ещё не получил точный результат, workflow в открытом select Settings показывает свой loader-счётчик; ожидание процента/readiness, Resume и сохранённая ошибка в него не входят. Header Settings остаётся только названием. На свёрнутом общем Run After число не дублируется рядом с очередями: тонкая движущаяся фиолетовая кромка слева сообщает о выполняющемся сжатии. Подробные операции и их владельцы видны внутри Settings.

В двух редакторах одна и та же вставка может иметь одинаковый `chipId`. Ответ нативного paste-меню поэтому возвращает ещё и identity конкретного открытия; его принимает только инициировавший редактор. Иначе «вернуть текстом» из глобального обзора могло обработаться также локальной панелью/History. Общий item id отвечает за данные, request id — за владельца этого жеста.

Выбор Rewind из общего обзора сначала показывает owner-вкладку через общий `placeTab`: если она уже размещена в другом workflow/окне, переход идёт туда без замены текущего чипа. Прежний прямой `activateCenterTab` обходил это правило. Одноразовый запрос сохраняется до подписки её Timeline, иначе синхронное событие терялось бы при переходе на ещё не смонтированную поверхность. На время выбора общий popup скрыт, но его редактор остаётся смонтированным и принимает результат; клик по Timeline не считается outside-close этого получателя. Выбор добавляет карточку в ту же очередь и возвращает popup; Escape/явное закрытие отменяют режим, а cleanup старого request id не стирает новый. Само исполнение Rewind остаётся прежним отдельным шагом очереди.

## Индикация подготовки пункта до отправки

Spinner пункта и Play/Pause-рельсы получает не только History-handoff, но и
read-only snapshot текущей runner attempt с exact preparingItemId. Он включается
синхронно перед первым context/readiness await, включая Resume и materialization;
потом приоритет получает прежняя transport phase. Раньше prepare шёл до создания
handoff, и меню могло несколько секунд выглядеть неподвижным. Проверка порога
показывает loader лишь пока реально читает контекст, не всё время ожидания будущего
процента. Удалённый/чужой item не наследует индикатор, Pause/отмена/finally снимают
его. Read-notification не является continuation release и не запускает следующую
очередь; нового runner, timer readiness или durable receipt здесь нет.

## Автокомпакт: выбранная область и новые завершения

Пользователь хочет один раз включить ожидание compact для Main, а не ставить постоянный `/compact` во все очереди и не пробуждать забытые сессии. Поэтому общее правило и исключения вкладок хранятся отдельно от queue items. Выключение Play обычной очереди не выключает автокомпакт; глобальное off/on не очищает локальные исключения. Статичная иконка сжатия видна в несворачиваемой рельсе при действующем правиле, перечёркнутая — при исключении даже с глобальным off. Процент остаётся измерением контекста, не переключателем автоматики.

Область выбирается по сохранённым workflow. С10.10 desktop использует click-select с checkbox слева от общего WorkflowChip: одна bulk-кнопка переключает `Select all` (все workflow, включая будущие) и `Clear all` (снять весь выбор). Её действие определяется фактическими галочками: полный ручной набор тоже предлагает Clear, но сам по себе не включает подписку на будущие workflow. Снятие одного checkbox после All переводит текущий список в явный набор оставшихся workflowIds и возвращает действие Select all. В legacy представлении доступен также «Без workflow». Выбор первого scope включает автокомпакт, снятие последнего выключает; отдельной Power-кнопки нет. Открытие Settings не армит правило. Disabled remembered scope показан без check: первый выбор включает только явно указанную область. Порог и локальные исключения сохраняются.

UI пишет scope и enabled одним прежним `updatePolicy`, с прежней границей armedAt и persistence. Схема политики и отдельный enabled для внешних клиентов остаются прежними. Страницы общего меню называются `Queues` и `Settings`; во второй расположены независимые Auto-compact и Auto-stop. Заголовок Settings не содержит порога или счётчика. Активные поле ≥N% и `%` на основном Run After остаются фиолетовыми, выключенное поле — серым. Сжатия каждого workflow видны в открытом списке и в прежней runtime-проекции.

После Main organization publication принадлежность определяется exact membership вкладки и его revision, не legacy execution namespace и не размещением окон. `spaces[].projectIds` остаётся только pre-migration совместимостью. Показ вкладки в чужом окне ничего не меняет; move membership меняет область последующих событий без смены cwd/SID. Именованные проекты/директории остаются описанием, не authority. SDK/Gemini/обычные Terminal не получают неподдержанный PTY compact-сценарий.

Обычный запуск проверяет только новое штатное завершение после включения/изменения области и после запуска renderer. Старый idle, исторический catch-up, просмотр вкладки, ошибки и завершение самого compact не являются запуском правила. Проверяется свежий main-owned процент точной сессии, не SQLite seed показометра; если снимок старше начала ответа или отсутствует, ждём авторитетное обновление, не принимаем unknown за 0. Ожидание редактора/readiness/процента отражается в настройках вкладки и общем списке текущих compact-операций.

Разовое «Применить к уже простаивающим…» сначала показывает кандидатов только выбранной области. Остановленные подписаны как требующие запуска и изначально не выбраны. Пользователь явно выбирает сессии; перед каждой отправкой вновь проверяются область, исключение, владелец и процент. Resume может передать сессию подтверждённому новому UUID из собственного результата, но произвольная смена owner отменяет попытку. Простое включение общего правила Resume не делает.

Само наличие ручного `/compact` в очереди не подавляет общее правило и не создаёт специального приоритета. Оба пути сериализуются: после сжатия карточка с процентным условием читает новое значение; явная карточка без условия остаётся явной командой. Предложение связывать глобальное разрешение с наличием карточки отклонено пользователем — очередь была временным способом до отдельной фичи.

Новая проверка включена в существующий singleton runner перед продолжением ответа. Только конкретная проверяемая/выполняемая операция временно удерживает очередь и зависимых подписчиков; пустое ожидание будущего порога не создаёт pending queue и не мешает idle сборки. Отправка идёт через общий scenario с `requireLive` и защитой чужого draft. Следующий шаг ждёт main-owned `agent:operational-phase` с тем же handoff/session/provider и `completed`; Enter и успешный submit не доказывают окончание. С09.10 ожидание результата не имеет прежнего180s таймера: долгое сжатие сохраняет ту же попытку, observer и удержанное продолжение до точного результата, без повторного `/compact`. После completed отдельно проверяется готовность ввода. Ошибка отправки либо точные aborted/failed/unknown выключают продолжения только этой вкладки, карточки сохраняются; сама длительность ошибки не создаёт. Codex `completionKind=compact` переносится в live busy-событие, чтобы штатный конец сжатия не породил ещё одно сжатие. Шрам — `fix-compact-logic.md::Шрам: автокомпакт дольше180s получил ложную ошибку`.

Настройки/исключения сохраняются через общий app-state, включая синхронный flush перед закрытием. Конкретные ожидающие попытки не восстанавливаются как новые задания. Рабочая приёмка и границы проверки — `../tmp/глобальные-очереди-и-автокомпакт.md`.

Удалённый cancel проводит `activity.handoffId` до того же coordinator task, а не
до таб-only Stop. ID старой A не отменяет новую B в той же вкладке; уже submitting
compact не превращается в безопасную отмену. Legacy desktop caller без ID сохраняет
свою отмену текущего pending task; строгий remote всегда передаёт ID.

Новый обычный ответ, завершившийся пока compact ещё только ждёт готовности, заменяет отложенный cause и границу свежести процента. Это важно для уже принятой нативной очереди CLI: её следующий ответ может начаться раньше, чем автоматике достанется свободный input. Нельзя после него продолжать очередь по времени более старого ответа. Явный Play на idle по-прежнему запускает обычную очередь сразу; он не является новым завершением и не обязан сначала compact'ить старый контекст.

## Автоостановка простаивающих процессов

Settings → Auto-stop задаёт workflow, срок1–10080мин (default10) и включение
уже простаивающих (default true). Пока scope пуст, правило выключено. Ввод срока
локальный до blur/Enter: промежуточная цифра не запускает остановку. Main сохраняет
`globalIdleSessionStop` через прежний app-state; у правила отдельный владелец
`idle-session-stop.js`, один таймер ближайшего deadline, событийные rechecks.
Открытие меню/фокус/renderer не исполняют Stop.

Берётся полное active membership, включая hidden/reserve, только AI-процессы,
в том числе SDK. Deadline = последнее завершение текущего процесса + срок.
Если такого времени нет, используется начало подтверждённого простоя. Старый
ответ до нового launch не укорачивает его первый интервал. При включённом
«уже простаивающие» известный истёкший срок допускает немедленную проверку;
при выключенном нужны новая работа/завершение после включения. Busy отменяет
отсчёт, новое завершение начинает новый; выбор workflow не следует за фокусом.
Уже принятый отсчёт сохраняет начало при изменении срока, добавлении другого
workflow и metadata revalidation. Флажок уже-idle определяет подключение таких
вкладок; снять активное ожидание можно выключением его workflow/Clear all.

Таймер не доказывает отсутствие работы. Main перечитывает owner/subject/membership,
input generation/readiness, собственную и дочернюю работу и pending Send;
перед сигналом тот же guard проверяется через существующий workflow Stop.
Claude/Codex дополнительно требуют актуальный Root RunAfter read и пустой
headless TUI draft. Подготовка/unknown Send/редактор/compact удерживают процесс,
будущие countdown/app-restart/onTab не выключаются. Unknown/ошибка наблюдения
оставляет ожидание до изменения данных, без циклического retry и Toast.
SDK result/compact/task события будят тот же Main; собственный interrupt Stop
не считается новым завершением для отсчёта.

Native Claude/Codex background work проверяется прямо по существующему Main
`getCombinedTabBackgroundWorkCount`, отдельно от `turnBusy` и MCP inherited work.
Положительный count запрещает Auto-stop и `Stop idle`, в том числе перед сигналом.
Публикация начала/окончания этой работы будит тот же idle-owner; после последнего
child начинается полный срок, а не остаток от более раннего parent final.
Шрам15.10: fb4f61a5, parent final15:23:16.910UTC, живой Galileo/count1 и его
команды до15:33:10.665; Auto-stop15:33:19 ошибочно убил host. Count стал0 только
при process cleanup, не по child completion. В SOURCE добавлены эти consumer
guards и event wake; это не доказательство обновления установленного приложения.

Останавливается прежний процесс, вкладка/History/shell сохраняются. `manual-stop`
cleanup остаётся прежним и не превращается в Pause Run After: будущий trigger
может выполнить обычный Resume. Это не удаление вкладки и не orchestration
autoStopCreatedTargets. Настройка относится к desktop IPC; native UI её не добавляет.
В меню окна (…/ПКМ) и одиночной вкладки внизу показан Main deadline. Локальный
секундный ticker живёт лишь пока меню открыто; busy/ожидание/остановленный
процесс показаны вместо ложного отсчёта. Sequence защищает от позднего GET.

## Auto-runner — singleton hook, не в overlay

Auto-runner живёт в `src/renderer/hooks/usePromptQueueRunner.ts` и **монтируется один раз в App root** (`App.tsx`), не внутри `PromptQueueOverlay`.

Закрытый `GlobalRunAfterControl` — только presentation: его inventory ограничен
IDs, нужными текущим queue/compaction counters. При пустом наборе нет обхода всех
вкладок; открытие preview/pinned editor сразу получает полный свежий inventory.
Счётчики остаются эквивалентны полному списку с прежним eligibility predicate;
workflow/SID/rename обновляются для нужных IDs. Full picker/graph, память layout,
Main executor, arm/completion/readiness и очереди этим не сужаются.

```ts
// App.tsx (mount once)
usePromptQueueRunner();

// Внутри runner:
const prevBusyRef = useRef<Map<string, boolean>>(new Map());
ipcRenderer.on('claude:busy-state', ({ tabId, busy }) => {
  const wasBusy = prevBusyRef.current.get(tabId) ?? false;
  prevBusyRef.current.set(tabId, busy);
  if (wasBusy && !busy) {
    // pop next + send-command, или stopAfter если очередь пуста
  }
});
```

`claudeBusy` приходит из `claude:busy-state`, где авторитетную границу дают hook-события `UserPromptSubmit` / `Stop` / `StopFailure` (см. `fact-claude-stop-hook.md::Интеграция в claude:busy-state`). Main обязан отправлять эти события всегда, даже если PTY-spinner уже записал то же boolean-значение. Runner отбрасывает `reason:'spinner'` **до** изменения своего workflow-снимка: визуальный idle не имеет права превратить последующий настоящий Stop/Escape в «повторный busy:false». Никаких ожиданий по таймеру — автоматика живёт на классифицированных событиях результата.

### Auto-run стреляет ТОЛЬКО на штатный конец turn'а — `reason` на busy-state (горело)

**Запоздавшая публикация собственного конца (09.10,4412).** Пользователь может
включить свою очередь, пока Main ещё сообщает busy, хотя timestamp ответа
провайдера уже раньше этого включения. Живой `busy→idle` такой же вкладки
освобождает явно поставленную в текущем renderer очередь: это прежнее право
собственного Play начать на подтверждённом idle. Допуск привязан к захваченному
arm и переживает только его AutoCompact/children ожидание; новый arm не получает
старое разрешение. Время ответа не переписывается. Restore/catch-up и чужой
`onTab` сохраняют прежнее сравнение outcome с arm. До готовности/выхода из
редактора эта собственная работа остаётся pending для downstream подписчиков.
Шрам: ответ4412 timestamp12:21:18UTC опубликован12:23:54, Stop добавлен12:22:19;
раньше сравнение времени молча пропускало эту карточку. Последующий ручной Stop
12:28:24 остановил процесс, но не являлся исполнением самой карточки.

Runner реагирует на фронт `busy:true→false` канала `claude:busy-state`. Но «turn закончился» ≠ «Claude штатно ответил»: turn может оборваться на **API-ошибке** (StopFailure, напр. `API Error: 500`), на **Escape/Ctrl+C** (InterruptStop), или зависнуть и быть сброшенным **watchdog'ом** (60 мин). Все эти исходы технически дают `busy:false` — и если runner их не отличает, он **заливает следующий промпт в сломанный/прерванный turn**. Юзер: *«если выпала ошибка или я нажал Escape — run-after не должен срабатывать, а наоборот деактивироваться»*.

**Ловушка двух каналов.** Различие успех/ошибка (`event`, `success: event !== 'StopFailure'`) main шлёт **только** на `claude:turn-state`. Loader-канал `claude:busy-state` исторически слал **голый `{tabId, busy:false}` без reason** для ВСЕХ исходов — natural Stop, StopFailure, InterruptStop, watchdog неотличимы. Runner слушает `busy-state` (не `turn-state`), поэтому видел только `busy:false` и стрелял очередью на каждом. Изначально скипался лишь `reason === 'manual-stop'` (кнопка Stop) — единственный путь, который reason проставлял (`terminal:stop-ai-process` → `stopBusyState()`, main.js).

**Фикс — протянуть `reason` на busy-state на всех аномальных концах** (зеркало `manual-stop`-паттерна), runner скипает весь набор:
- `manual-stop` — кнопка Stop / context-menu / двойной Esc (был).
- `error` — `event === 'StopFailure'` (API/inference error). main.js Stop-hook: `reason = (!busy && event === 'StopFailure') ? 'error' : undefined` — **только** на busy:false-конце; natural Stop и busy:true-старт остаются reason-less.
- `interrupt` — Esc/Ctrl+C: оба пути (JSONL-marker watcher `[Request interrupted by user]` + idle-probe для «Esc до первой записи в JSONL»).
- `watchdog` — Stop не пришёл за `CLAUDE_TURN_WATCHDOG_MS`, turn завис/мёртв.

Все workflow используют общий allowlist успешного результата: reason-less `busy:false` остаётся legacy-контрактом штатного Claude/Gemini/SDK-конца, а для Codex разрешён только `reason:'task_complete'`, который main публикует при одном из двух доказательств результата: либо `last_agent_message` непустой, либо корневая assistant-запись `phase:'final_answer'` содержит явный `turn_id`, точно совпадающий с завершившимся turn. Финальный ответ без привязки к turn не считается доказательством. Любой новый явный reason fail-closed: он не сможет случайно начать отправку, Git-операцию, restart или уведомление, пока его отдельно не признают успешным исходом.

**Ignored non-turn reasons (`spinner`, `local-command`) + исключение `/compact`.** Не каждый `claude:busy-state busy:false` с `reason` означает «turn завершился ненатурально». Два reason'а существуют только для UI-liveness:
- `spinner` — PTY glyph heuristic, может флапать между thinking phases. Renderer может сгладить его визуально, но runner не должен ни fire, ни disarm.
- `local-command` — bracket для inline slash-команды. По умолчанию completion/cancel такой команды не является successful assistant turn-end и не должен ни fire, ни disarm.

Успешный `/compact` — намеренное исключение. Main стартует watcher только для `/compact`, шлёт `busy:true reason:'local-command'`, а на durable marker (`compact_boundary`, `isCompactSummary`, stdout `Compacted`) закрывает busy как `reason:'local-command', localCommand:'/compact', localCommandReason:<marker>`. Runner проверяет именно эту пару и продолжает обычный firing path: для пользователя compact — часть цепочки очереди, после него должен уйти следующий prompt. PTY-текст `Compacting conversation` / `Conversation compacted` сам по себе не является результатом: его печатает и автоматический compact. Он может только инициировать проверку durable marker для того же физически отправленного `/compact`, той же сессии, launch generation и input generation. Если после ручной команды был другой ввод, поздний auto compact не имеет права завершить старый watcher. `timeout`, `input-escape`, `input-ctrl-c`, `StopFailure`, смена owner, другой slash-command или `local-command` без `localCommand:'/compact'` не продолжают очередь: loader гаснет, очередь остаётся armed или disarm'ится отдельным authoritative error-edge.

Шрам 2026-06-15: пользователь поставил Run after, первым item ушёл `/compact`, loader Claude корректно погас после compact, но следующий prompt не отправился до ручного действия примерно в 13:30 МСК. Корень был в старом blanket-guard'е: runner видел `reason:'local-command'` и всегда делал `return`, хотя compact уже завершился durable boundary. Поэтому в этой секции важно не возвращать старую формулу «local-command никогда не fire» — она верна для cancel/timeout, но неверна для successful `/compact`.

Codex имеет ту же продуктовую семантику, но другое доказательство: explicit
`/compact` создаёт собственный task, пишет `compacted` и заканчивает его без
assistant final. 10.09 в12:34MSK tab754 штатно закончил такой compact, однако
общий fan-out успел назвать его `codex-no-final-result` и disarm'ил ожидавшую
tab4505; dedicated compact owner через1ms отметил `completed`.
Теперь до fan-out main проверяет active explicit compact, точные session/
generation/turn и порядок source-offset < compacted-offset < task-complete-offset.
Только этот доказанный результат даёт натуральное завершение для Run after.
`hasFinalResult` остаётся false: финальный ответ и его duration не выдумываются.
Поздний historical tail не понижает этот же exact turn/timestamp обратно в
no-final-result; proof относится только к той же process generation.
Отдельный `context_compacted`, старый/чужой compact и настоящий provider error
не получают этого допуска; обычный ответ без final остаётся abnormal.

**Ручной Stop процесса не является Pause очереди.** По прямому уточнению09.10
`manual-stop` не выключает `autoRun`, Loop, таймеры, app-restart и внешние onTab
подписки; не меняет head/order/arm и не показывает Toast/copy-report. Сам Stop
не является успешным завершением и ничего не отправляет. Будущий исход, срок
таймера или новый Main lifetime проверяются прежним исполнителем; остановленный
owner проходит общий Resume/readiness. Это не разрешение повторять уже принятый
или неизвестный Send: Main FIFO/receipt guards и его отмена незаписанного ввода
сохраняются. Явный Pause и карточка Stop внутри последовательности — отдельные
действия: подтверждённая карточка Stop по-прежнему заканчивает свою очередь.

**Окончательная ошибка по-прежнему DISARM, не skip-once.** Error, watchdog,
close и неподтверждённый результат выключают собственную автоматику и связанные
внешние очереди, сохраняя тексты. `interrupt` Claude и доказанный `turn_aborted`
Codex сохраняют внешние подписки и собственный Loop до следующего natural
completion, но одноразовую собственную очередь выключают. Более новый retry
защищён от старого catch-up. Не распространять это старое правило ошибки на
пользовательскую кнопку Stop только потому, что процесс тоже стал inactive.

Main `agent:stopping-state` с `manual-stop` снимает лишь старую подготовку:
ожидающий Resume abort'ится, запоздавший context/readiness/editor результат
не может отправить сообщение. Submitted AutoCompact observer снимается без
warning и без продолжения очереди; поздний outcome не возвращает его activity.
Если exact compact operation публикует aborted/manual-stop раньше UI stopping,
runtime передаёт типизированную отмену; coordinator тоже завершает ожидание
без failure callback, а не распознаёт намерение по тексту ошибки.
Пока Main завершает принятый Stop, промежуточные abort/error/natural records
не меняют очередь и не разрешают отправку; это граница Stop, не новый failure.
Финальный live manual-stop имеет тот же fallback, восстановленный snapshot
не отменяет новую подготовку. Собственная карточка Stop/Close защищена прежним
in-flight owner. Сохранённые условия и сроки этим cleanup не переписываются.
- **Почему НЕ перехватываем клавиши вручную (Escape/Ctrl+C/Ctrl+]):** причина остановки уже классифицирована в `reason` (main: `interrupt` = Esc/Ctrl+C через JSONL-marker watcher + idle-probe; `manual-stop` = кнопка; `error` = StopFailure; `watchdog` = зависание). Слушаем **причину**, не keystroke — единый сигнал вместо ручного парсинга. Это и есть «отслеживать по какой причине была остановка Claude».
- **Store-безопасность:** `disarmQueuesForTrigger(triggerTabId, outcomeTs)` делает один immutable `Map`-commit и одну debounced SQLite-запись; timestamp защищает более позднюю ручную постановку от старого catch-up. Gemini `busy:false` остаётся reason-less штатным концом и не попадает в abnormal allowlist.

**Тонкости которые держать в голове:**
- Abnormal reason обрабатывается идемпотентно даже без нового `true→false` edge: live-исход текущего turn или восстановленный исход с временем не раньше постановки является достаточным доказательством отмены. Старый catch-up сам по себе не имеет права снимать более новый retry. Это закрывает порядок, где другой false-сигнал пришёл раньше, не создавая обратную гонку после рестарта.
- **Loader отдельно:** остальные renderer-консьюмеры продолжают получать spinner-сигналы для presentation state; только workflow-map runner'а их игнорирует. Нельзя снова смешивать visual busy и источник результата автоматики.
- **Натуральные reason-less пути не трогаем:** SDK-форвард и Gemini idle продолжают очередь. Lifecycle cleanup, который означает ненормальный исход (`pty-exit`, `terminal-kill`, `replace`, `close`), должен иметь явный reason и отменять связанные workflow.
- **Codex, обычный ответ (не доказанный explicit compact выше):** rollout `task_complete` закрывает busy-state, но main сохраняет reason `task_complete` только когда есть непустой `last_agent_message` либо явно привязанный к тому же turn корневой assistant `final_answer`. Если нет обоих доказательств, исход становится `codex-no-final-result`: это «финальный результат не подтверждён», а не угаданный `403`, поэтому связанный Run after disarm'ится, тексты items сохраняются, и никакой следующий Enter не отправляется. `send-command-failed` и `send-command-error` имеют ту же окончательную семантику. `turn_aborted` выключает собственную автоматику Codex-tab'а, но сохраняет внешних owner'ов, которые ждут её будущий успешный ответ после продолжения. Точная причина ошибки может отсутствовать в rollout — см. `fact-codex.md::Loader и App Server`.
- **Lifecycle aliases канонизируются до workflow-решения:** один Codex completion может прийти сначала как `task_complete`, затем тем же timestamp/turn как renderer-reason `rollout-task_complete`. Это одна квитанция, а не success→failure; префиксированный alias нормализуется и попадает в ту же dedupe identity. Иначе второй false-edge успевал disarm'ить уже совпавший Run after и показывал ложное «завершилась нештатно». Настоящий abnormal-toast остаётся persistent, но передаёт общему Toast полный copy-report с tab/session/UTC+MSK/reason/log lookup.
- **Codex Escape считается только через rollout-событие:** физическую клавишу `Escape` runner напрямую не парсит. Если Codex записал `turn_aborted`, его собственная автоматика disarm'ится, а внешний Run After продолжает ждать следующего success; если визуально остановился без `turn_aborted`, Claude-style idle-probe fallback для Codex пока не включён. Не добавлять его «для симметрии» без реального симптома — текущая архитектура намеренно держится на high-level JSONL-событиях.
- **Ручная отмена не является incident.** По уточнению пользователя23.09
  подтверждённые `interrupt`/`turn_aborted` (включая нормализованный alias)
  применяют прежнюю политику очереди, но не создают warning/copy-report.
  Это действует и при поздней hydration: восстановление не будит старую ошибку.
  Provider error, watchdog, отсутствие final и неизвестный reason сохраняют
  persistent warning. Сам Escape без подтверждённого outcome не запускает
  следующий prompt и не превращается в успешное завершение.
- **Send commit по ownership, а не по позднему аудиту:** до Enter очередь владеет записью. Постоянный отказ (`draft conflict`, неверный PTY, повреждённый payload) оставляет head и disarm'ит автоматику; временный `deferred:true` из readiness/Stop-gate оставляет и head, и arm до следующего авторитетного события. Как только main вернул `submitted:true`, Enter уже записан в ordered PTY stream и ownership перешёл агенту; head и одноразовый pivot-target удаляются одним store-commit даже если последующий JSONL/rollout audit вернул timeout. Иначе повторный Run after отправит дубль. Прод-шрам 2026-07-10: Codex начал turn через ~40ms после Enter, но `user_message` появился только после compaction примерно через минуту; восьмисекундный audit timeout оставлял уже отправленный item и target в UI.
- **Unknown — третий исход, не отрицательный ACK.** `{}`, потерянный admission ACK
  и `success:null/submitted:null` не потребляют item. Перед send-capable call Root
  сохраняет в том же queue store указатель на original handoff/operation с Main
  app-state ACK; payload/receipt остаются в прежнем Main FIFO. Unknown ставит на
  Pause через countdown owner, не отменяет/retract'ит старый Send как no-submit.
  Play, hydrate и late-audit wake читают только эту квитанцию, без новой отправки.
  Missing receipt тоже unknown. Proven submitted/confirmed потребляет лишь
  совпадающую текущую карточку; новая правка остаётся. Legacy новая arm при старом
  unresolved Send получает именно original operation identity, не fake refusal.
  Прямой поздний success также сверяет текущие body+Post/condition/item-trigger
  с отправленным source до удаления по id: редактирование не создаёт новый id
  автоматически. Pause/title/disable/reorder не отменяют факт уже отправленного
  неизменного source; удалённый source не разрешает удалить следующий item.
- **Собственный commit не является Cancel.** После подтверждённой передачи
  доставки Main точная deferred-подготовка завершается как `committed` ДО
  удаления source из Store. Иначе синхронная Root-подписка видит исчезнувший
  head как внешнюю правку и отправляет `agent:cancel-send` уже принятому Send.
  Это воспроизведено и после canonical `sent`, и для native `queued`/post-Enter
  unknown: потребление Run After не освобождает physical slot через отмену.
  Slot и поздний audit остаются у Main; `queueSendInflight` держится до cleanup.
  Настоящий Pause/изменение source до ответа по-прежнему отзывает свою попытку.
- **History handoff начинается до send admission IPC**, но после предварительной
  подготовки остановленного runtime. Если Resume уже запустил Goal, queued prompt
  ещё не объявляется SENDING. После допуска immutable snapshot виден до физической
  отправки; Enter завершает транспортный `pasteBusy`. Ожидание post-Enter audit не
  превращает Model/Effort-кластер в операцию настройки и не разрешает повтор.
- **Resume input-ready не означает завершённую перерисовку composer.** При
  `after app restart` Codex может уже показать prompt, но продолжать большой
  synchronized-output кадр восстановленной переписки. Automatic FIFO admission
  читает тот же coherent Main runtime, что публичный status, затем текущую
  границу headless-кадра. Открытый/unflushed/post-resize кадр оставляет исходный
  handoff waiting до physical attempt; существующий flush-сигнал будит повторную
  полную проверку Root/owner/Goal. Нет таймера, renderer visibility, чтения History
  или подстановки старого закрытого кадра. Это предварительный gate, не замена
  финального draft/PTY proof и не право повторять unknown/no-receipt отправку.
  Provisional Resume без первого user writer-row не объявляется inactive только
  из-за отсутствия такого row. Manual Send-now сохраняет steering. Если очередь
  ждёт, `[AutomaticSendAdmission]` отдельно называет Root/trigger/editor/work,
  runtime/input/Goal, context-owner или frame blocker; HTTP/bridge ACK сам по
  себе не говорит, что эти проверки дали ready.
- **Context-read и destination-write — разные владельцы.** Настоящий context
  condition сверяется с разрешённой Main read identity, в том числе с точным
  provisional Resume source до первого user row; saved SID сам по себе такого
  права не даёт. Guard физического Send не получает read SID вместо writer.
  После собственного Resume Root заново читает context даже при прежнем SID.
  Иначе ложное ожидание writer-row могло заблокировать именно тот первый Send,
  который должен этот row создать. Отсутствующие condition keys остаются
  семантически совместимыми без переписывания frozen handoff/fingerprint.
- **Подготовка до FIFO тоже отменяема в Main.** Pause и смена source отзывают
  исходный launch intent, пока обычный Send ещё не создан. Редакция body/Post,
  owner/cwd между readiness, images, work-context и persistence не превращается
  в новую отправку от старой подготовки. Retry запуска ограничен прежним fence
  и одним бюджетом; его отказ не является no-paste/no-Enter для старого Send.
  Механика и одноразовая materialization — fact-codex.md::Запуск и shell boundary.
- **Codex submit guard:** до paste `codex:send-command` доказывает, что composer пустой, процесс не останавливается и admission относится к текущему поколению PTY. Те же условия проверяются снова до Enter. После paste не нужны hidden renderer/fresh render-marker gates: paste+Enter идут ordered, а rollout `user_message` остаётся проверкой точности и диагностикой, но не возвращает ownership очереди после физической отправки. Renderer не имеет права додавливать сырой Enter. Multiline draft с пустой первой строкой должен находиться как `*:multiline-draft-row-N`.
- **Ручной input делит одну PTY-границу с автоматикой:** printable input, Enter и programmatic paste нельзя писать параллельно в один composer. Физический Enter, пришедший во время safe-paste, ждёт его завершения и подавляется только если первая операция действительно уже отправила prompt; если она отказалась до Enter, клавиша сохраняет пользовательское действие. Обычный model/effort picker и специализированные Rewind/startup picker'ы остаются управляющими состояниями: их Enter не создаёт prompt-in-flight и не блокирует следующий Run after как `writer identity pending`.
- **Наблюдение ручного `/compact` начинается после Enter:** до Enter можно только запомнить JSONL-offset и владельца; watcher, busy и loader появляются после успешной записи Enter в тот же PTY. Это правило относится к ручному xterm-вводу, startup handshake и обеим quick-action командам. Если Enter перехвачен, запись не удалась или tab уже получил replacement PTY, подготовка удаляется без ложного активного `/compact`.
- **Codex 0.151 slash-autocomplete не считается submit:** для programmatic `/compact` первый Enter может лишь выбрать autocomplete item. Main ждёт exact `task_started`; если вместо него новый committed headless-кадр всё ещё содержит принадлежащий операции неизменённый `/compact`, при тех же terminal/run/lifecycle/input/mirror generation разрешён ровно один второй Enter. Первый causal start запрещает второй; manual takeover или неизвестный исход возвращают `delivery-unknown`, снимают pending и не оставляют очередь в ложном `SENT`.
- **Закрытые owner/target табы чистятся из очередей:** `closeTab` / `closeProject` и lazy runner-cleanup удаляют queue закрытого owner'а и сбрасывают `runAfterTabId` у очередей, которые на него смотрели. Target теперь валиден во всех открытых проектах, но только если вкладка реально существует в `openProjects` и не совпадает с owner'ом. Иначе pivot мог ждать busy→idle закрытой вкладки бесконечно или замкнуться на самого себя.
- **Schema-drift риск:** тег `'error'` висит на строковой константе `event === 'StopFailure'`. Если Claude переименует событие — путь регрессирует к firing (как и `success`-флаг на turn-state, та же единственная константа).

См. `fact-claude-stop-hook.md` (Stop/StopFailure/InterruptStop события) и `fix-claude-aborted-streaming-loader.md` (aborted_streaming не fires hook → JSONL-marker watcher).

### Почему не в overlay (первая реализация была там и сломалась)

Первая реализация монтировала runner внутри overlay, который тогда рендерился через гейт `effectiveActive && isClaudeTab && hasClaudeSession && claudeProcessAlive`. `effectiveActive` становился `false` как только юзер уходил на другой таб / Dashboard / Home view → React unmount'ил overlay → `useEffect` cleanup → `prevBusyRef` терялся. Современный presentation-гейт уже шире, но runner всё равно остаётся singleton: видимость конфигурации не должна владеть исполнением фоновой автоматики.

**Симптом который мы поймали:** юзер армит "Run after", уходит на gemini-таб работать, Claude в фоне закончил turn → `claude:busy-state busy=false` приходит → **никто не слушает** (overlay unmounted) → следующий промпт не отправляется. Возвращается на Claude-таб → overlay re-mounts → `prevBusyRef.current = claudeBusy` (текущее значение, не old) → пропустили edge transition → **ничего не происходит**. Юзер думает что фича сломана.

**Решение:** singleton hook на верхнем уровне, не зависит от того что показано на экране. State хранится в `useRef<Map<tabId, boolean>>` — per-tab busy tracking без React state churn. Идентичная семантика, но **глобальный scope**.

### Cold-start через store subscription

Когда юзер добавляет промпт через `+ grab` / `+ add` в **idle** Claude таб — autoRun должен сразу отправить, не ждать первого busy→idle цикла (которого никогда не будет если Claude уже idle).

Реализация: вторая часть hook'а подписывается на `usePromptQueueStore.subscribe` и ловит **два независимых edge'а**, любой из которых триггерит fire когда `claude is idle && queue.autoRun && items.length > 0`:

- `items 0 → N` — юзер добавил chip когда autoRun уже армлен.
- `autoRun false → true` — юзер только что нажал «Run after» когда items уже стояли в очереди (например, Claude закончил отвечать, юзер забыл нажать Run after до отправки промптов, потом вспомнил).

Второй edge — реальный шрам: без него юзер арм-ал Run after поверх готовой очереди и ничего не запускалось до следующего вручную отправленного промпта (которого он не собирался отправлять — для этого и была очередь). Re-entrancy guard `firing = true/false` защищает от двойного fire (popNext → state change → ещё один subscribe-callback → потенциальная рекурсия).

### Resume может начать Goal раньше queued prompt

Шрам06.10: app-restart head получил правильный допуск, но собственный Resume
запустил native Goal до вставки `продолжай`. Main верно отказал busy до ввода,
а Root перезаписал `workflowArmedAt` и потерял ту же ожидающую попытку.
Это два владельца: Resume/Goal не является доставкой queued prompt.

User arm теперь неизменен при Resume; persisted `workflowOutcomeFloorAt`
отдельно отсекает результаты старого процесса. Common readiness подготовка
выполняется до admission сообщения: если Goal уже работает, head остаётся
ожидающим, без failed-карточки и без нового Enter. После admission прежний Main
FIFO перепроверяет Root head/body/Post/arm/trigger/provider/owner и паркует
автоматический intent до готовности. Editor, Stop, Pause и смена owner не
разрешают позднюю отправку. Background/root ownership сохраняется.

Если busy возник прямо перед paste, только Main-certified полный no-input
результат нового typed intent позволяет сохранить application wait. Последняя
physical receipt остаётся not-submitted; UI показывает IN APP QUEUE. Новый
runtime/authoring wake допускает прежний frozen body через общий executor;
receipt-only publication не будит саму себя. Unknown/Enter/provider ACK,
старые failed receipts и явный Send-now этого разрешения не получают.
Явный новый Play имеет отдельный arm key, но Main транзакционно проверяет
предшественника: старый unknown нельзя обойти сменой key, exact consumed item
не отправляется повторно. После renderer restore join читает исходный frozen
intent, не переписывает его новыми подсказками/context. Legacy key не изменён.

`app-restart` доказывает только новый Main lifetime, не снимает ожидание
дочерних задач. Шрам14.10:367 увидела новый runtime/ready, сохранила autoRun/head,
но её прежний Astra research был running и общий completion predicate удерживал
отправку. Восстановленная подписка SC и запуск queued `продолжай` — разные действия.
После causal child return/release runner оценивает ту же голову, не новую arm.
Сверять нужно completionBlocked predicate, не только purple inheritedBusy UI.
Не отменять research и не подменять его итог старым idle ради продолжения очереди.

### Auto-disarm

Когда последний enabled-элемент передан агенту, `commitSentHead` в одном изменении удаляет его и ставит `autoRun=false`; при pivot-send там же очищается одноразовый `runAfterTabId`. Отдельный `setAutoRun` после commit запрещён: между несколькими store mutations мобильный `queue-update` мог бы показать промежуточное состояние «item уже исчез, но Run after/target ещё активны».

Сразу после copy/grab показываем превью того что попало в clipboard/queue. Одна строка, 20 символов, ellipsis. Multi-line schлёпывается в single-line через `text.replace(/\s+/g, ' ')`.

## Post-prompt: per-tab суффикс для каждого элемента очереди

На верхней границе очереди живёт border-mounted сплит-кнопка `▣ Post | ✎`: левая зона — per-tab toggle `postPromptEnabled`, правая (✎ карандашик) открывает slideout-редактор в режиме `isPostPromptMode`. Фон кнопки маскирует линию рамки, поэтому общая политика остаётся постоянно видимой без отдельной строки настроек. Когда toggle включён — runner аппендит `\n\n${postPromptText}` к **каждому** элементу очереди прямо перед `claude:send-command`. Per-tab — у разных Claude-табов могут быть свои post-prompt'ы (типовой сценарий: в одной вкладке гоняем рефакторинг с системным «не трогай тесты», в другой пишем тесты с «всегда добавляй edge case for null»). Empty text + toggle ON = no-op (suffix не аппендится), но визуально toggle всё ещё «active» с tooltip-намёком «click ✎ чтобы наполнить» — иначе юзер думает «включил, ничего не работает».

**Replay (▶ на чипе) намеренно обходит post-prompt.** Replay = «верни текст в композер чтобы посмотреть глазами и отправить руками»; auto-аппенд суффикса там сломал бы инвариант «вижу ровно то что отправлю». Runner-аппенд только для авто-pop'аемых элементов очереди.

## Loop: повторяемое продолжение после каждого ответа

`Loop` — отдельное повторяемое продолжение, а не суффикс Post и не бесконечно размножаемая карточка очереди. Включение и момент постановки принадлежат конкретной вкладке, но текст один для приложения: встроенный системный промпт `Run After Loop` (`run-after-loop`) в Settings → AI → Системные промпты. Карандашик Loop редактирует ту же запись, а очереди содержат только runtime-проекцию. Модель/effort берутся у owner-агента; Flash/Pro, файлы и context-menu настройки здесь не показываются, потому что этот текст не вызывает отдельную API-модель.

Первый запуск новой версии переносит прежний global app-state либо, при его отсутствии, самый новый legacy per-tab текст. Пользовательский текст и намеренно пустая строка сохраняются; неизменённый прежний default, в том числе с хвостовыми переносами, получает инструкцию blocked. После появления системной записи legacy app-state больше не участвует в выборе и не получает новые записи. Изменение текста в любом редакторе меняет остальные очереди и заново ставит временную границу включённым Loop. Hydration не затирает pre-load правку; подтвердившаяся правка Settings отменяет старый pending debounce карандашика. Content-only write и shutdown-flush сохраняют отдельно редактируемые name/color, не переписывая их старым snapshot.

В UI Loop — вторая border-mounted split-кнопка рядом с Post. На счётчике панели Post сохраняет маленькую оранжевую точку, а Loop с09.10 SOURCE отмечается статичным фиолетовым SVG `RefreshCw`8px справа внизу, не spinner. При Loop число поднято на3px внутри прежней кнопки26×26: даже `99` не пересекается с иконкой; Post+Loop видны вместе. Это только индикация toggle, не доказательство отправки или busy. Глобальная политика остаётся заметной без отдельной полноразмерной строки.

Обычный успешный конец хода не означает, что задача готова: пока Loop включён, он отправляет следующую проверку. Ручной interrupt не является таким концом и не меняет toggle: после продолжения Loop снова сработает на следующем natural completion. Неизменяемый app-owned протокол добавляется даже к пользовательскому Loop-тексту: готовая задача вызывает self-only `complete_task` (completed по умолчанию); внешняя блокировка — тот же метод со `status:"blocked"` и обязательной конкретной `reason`. Агент должен в финале назвать невыполненный остаток и нужное внешнее действие. Самостоятельно исправимая ошибка и ожидание уже запущенной операции/дочернего run не являются blocked. Готовность и прогресс не угадываются по словам ответа, таймеру или отсутствию правок файлов: read-only проверка тоже может быть настоящей работой.

`complete_task` регистрирует намерение только для точного текущего busy-turn, который доказан одновременно app-owned источником `prompt-loop` и принятым provider user-prompt с `terminal_task_completion_protocol`. Само наличие инструмента, глобальная инструкция, обычный запрос при включённом toggle или текст из старой истории права не дают; backend отвечает `completion_protocol_not_active`. Идентичный повтор идемпотентен; смена исхода/причины уже принятого intent конфликтует. Активные исходящие Terminal MCP-run блокируют оба исхода, interrupt/ошибка/manual stop/выход процесса отменяют намерение. Только авторитетный natural final того же хода публикует `explicitTaskComplete` либо отдельный `explicitTaskBlocked` с причиной. Runner выключает Loop до остальных продолжений, blocked объясняется toast и финальным ответом, но не получает completed-флаг. Обычные queued prompts/autoRun, runtime success-allowlist и результаты orchestration этим сигналом не меняются. Старый intent не переносится на новый ход. После устранения внешней блокировки пользователь осознанно включает Loop снова; unlock сам не армит его.

Причина этого различия — инцидент hh-tool tab367 01.10: старый протокол запрещал `complete_task` при любом ожидании, и каждый честный ответ «Mac заблокирован, задача не завершена» снова запускал Loop. Новый blocked — выход из повторения без ложного успеха, не эвристический лимит числа итераций. Это требует явного сигнала агента; если агент вообще игнорирует протокол, сервер не выводит блокировку из переписки. MCP до blocked POST проверяет capability `loopTaskCompletion.version=2`, чтобы старая версия приложения не проигнорировала статус и не приняла его как completed.

Шрам09.10, hh-tool507: два `completed` были приняты Main, но после natural final Loop продолжился. `applyCodexWatcherOutcome` сначала завершал provider activity и через её publisher отправлял ранний `codex:busy-state(false, task_complete)` без TaskCompletion metadata; renderer расходовал busy→idle на следующую проверку. Последующий полный `emitCodexBusy` с `explicitTaskComplete` уже считался повторным idle. Исправление сохраняет settle/activity/runtime projection, но передаёт публикацию whole-turn busy-event только `emitCodexBusy`, после обработки точного intent. Provider start/response segment и stale owner/generation guards прежние. Проверка отдельного `finishTurn()` и отдельной ветки выключения Loop этот разрыв пропускала: регрессия должна проводить фактический provider-settle → полный Main emitter → обычный renderer busy-edge handler. В этом инциденте wrapper MCP и relevant installed/source код уже совпадали; одно обновление MCP проблему не исправляло. Новая правка требует установки приложения.

Codex `user_message` не во всех версиях обязан нести `turn_id`. Для такого exact
Loop-audit разрешён узкий fallback на текущую активную сессию: Prompt Loop
проходит admission только из idle и поэтому не может быть сообщением, ожидающим
за чужим turn. Обычная очередь и ручные источники этого fallback не получают.

Один completion принадлежит только одному продолжению. Обычная собственная очередь имеет приоритет над Loop даже пока ждёт first-delay, editor lock, readiness или подтверждение отправки; Loop получит только следующий natural completion. Пока выбранное продолжение не передано агенту и не начался его busy-turn, внешние Run After-подписчики этой вкладки остаются заблокированы. Это закрывает промежуток, где исходный ответ уже закончился, а следующий prompt ещё только проходит безопасную доставку: downstream-вкладка не должна принять этот краткий idle за окончание всей цепочки.

Отправленный Loop-проверкой prompt получает отдельную app-owned метку происхождения только после post-Enter audit точной записи. Текст prompt и provider JSONL не меняются, а Timeline показывает маленький голубой `Repeat2` в правом верхнем углу основного маркера. По формулировке текста Loop не распознаётся: её можно редактировать, поэтому старые сообщения без sidecar остаются обычными до отдельного backfill.

History-бабл и Timeline-preview такой tagged записи по уточнению09.10 используют
блеклый фиолетовый фон и серый текст, как автоматический capacity Continue;
верхний header остаётся `Repeat2 · Loop`. Общий helper читает только существующий origin;
raw body/Copy/audit/identity остаются прежними. Loop сохраняет user carrier и
не превращается в Terminal MCP. Доказанный native ответ на вопрос имеет более
точное синее оформление; новый toggle не перекрашивает старую историю.

## First-chip armed hint: красный blink + приглушённый pending-state

Когда `items.length === 0 && autoRun === false` и юзер дёргает `+grab` / `+add` — Run after pill получает один красный `pq-hint-blink` (0.7s), а затем остаётся в очень приглушённом красном состоянии до явного acknowledgement: пользователь либо нажал Run after, либо вручную удалил последний элемент очереди. Hover больше не гасит hint: наведение = inspection, не согласие. Это состояние также отражается на свёрнутой rail-кнопке со счётчиком, иначе в default-collapsed режиме пользователь не увидит что очередь есть, но Run after не armed.

Смысл цвета — не error и не destructive, а unresolved pending: «у тебя есть queued work, но автоматический запуск ещё не включён». Поэтому base-state специально слабый (`low-red` фон/рамка/текст), а яркий `#ef4444` живёт только в коротком blink-overlay. Анимация перезапускается на каждом re-arm'е через `key={blinkKey}` remount span-overlay'я (иначе React не дропнет завершённый animation state). Принцип переносимый — см. `methodology/дизайн-принципы.md::Animation-driven hint: blink для внимания, tint для нерешённого состояния`.

**Шрам про палитру.** Первая реализация использовала янтарный `#d97706` (типичный «attention» цвет в проекте). Юзер прочитал его как «оранжевый» и спутал с **уже** оранжевым активным состоянием Run after — hint визуально неотличим от state. Переделали в чистый красный `#ef4444`: красный нигде больше в panel-кластере не задействован, читается однозначно как «обрати внимание». Принцип переносимый — см. `methodology/дизайн-принципы.md::Hint colour ≠ active colour`.

**Шрам про длительность.** Первая версия — 5×0.5s = 2.5s — юзер прочитал как «слишком долго мельтешит» (*«около 5 раз мигает красная кнопка [...] она должна мигать где-то секунды 2, то есть покороче»*). Вторая версия — 2×0.7s = 1.4s и auto-consume после окончания — убирала красный полностью, но теряла смысл «очередь есть, Run after не включён». Текущий контракт: blink один раз, дальше не яркий красный latch-state до Run after / empty queue.

## Уведомление вкладки = «работа закончена», а не «turn закончился»

`manual-stop` обозначает остановку процесса агента командой Stop, а имя trigger
является названием вкладки. Оно не означает остановку MCP-сервера с похожим
названием. Он не показывает уведомление Run After вообще и не выключает очередь.
Предыдущая замена ошибки на info «Run after на паузе» была недостаточной и
отменена уточнением09.10 (4196,14:30:50UTC). Настоящие ошибки сохраняют
incident-отчёт. Ручной Stop не удаляет невыполненные карточки; только
подтверждённое исполнение принадлежащего очереди Stop потребляет его head.

Колокольчик вкладки (`completionNotificationArmed` / `Persistent`, контекстное меню TabBar) отвечает на вопрос «то, что я поручил, доделано?». Конец turn'а на этот вопрос не отвечает: пока в очереди есть активные сообщения, вкладка ещё должна их отправить, и звонок на каждом промежуточном turn'е давал N уведомлений вместо одного. Теперь обе точки, где решается судьба колокольчика — собственный конец turn'а (`setAiBusy`) и релиз оркестрации (`applyTabCompletionOrchestrationState`) — спрашивают один общий предикат `shouldDeferTabCompletionNotification` (`utils/tabCompletionDeferral.mjs`), а «должна ли вкладка ещё что-то отправить» берётся из того же `hasPendingPromptQueueContinuation`, которым живут runner и UI очереди. Два разных ответа на «очередь закончилась» — ровно тот класс рассинхрона, который здесь закрыт.

Gate учитывает app-owned очередь, оркестрацию и Main `goalWork` той же native
Goal execution. Промежуточный `task_complete` не доказывает завершения всей работы,
даже когда app-owned blocker отсутствует. Active/attention сохраняют очередь
и armed bell без success; отдельное подтверждение App Loop всё ещё потребляется.
Новый независимый ручной ход не наследует старое Goal-ожидание. Шрам HH367 —
`fact-codex.md::Native Goal: конец turn не завершает всю работу`. Telegram получает
`tab-notification:completed` через Main outbox; скрытие одного визуального bell
не отменяет это событие и не защищает Run After/Restart After.

Два обязательных свойства этого gate:

- **Отложить ≠ погасить.** Ветка defer выходит рано и НЕ вызывает `settleTabCompletionNotification`: та удаляет `completionNotificationArmed`, и после неё ни один следующий turn уже не смог бы позвонить. Последний элемент очереди завершает turn, у вкладки больше нет pending continuation, и звонок происходит один раз за весь Run after. Wiring-тест проверяет отсутствие `settle`/`delete` внутри defer-ветки, а не только наличие проверки.
- **Ненормальный конец обычно не откладывается по очереди.** Ошибка/stop/interrupt по DISARM-контракту гасят `autoRun`, сохраняют карточки для ручного повтора и показывают persistent warning-toast. Узкое исключение — ручной `Escape` во время ответа A, когда main ещё ДО клавиши уже держит точное доказательство сообщения B в нативной очереди Codex: та же PTY, lifecycle, run, input revision, prompt generation и исходный turn. Тогда `turn_aborted(A)` — не конец цепочки, а граница перед немедленным `task_started(B)`; Run after остаётся взведённым до естественного завершения B и warning не показывается. Сам видимый текст очереди или быстро пришедший `task_started` постфактум это право не создают. Обычный Escape без такого доказательства сохраняет прежний DISARM-контракт.

## Взведённая очередь блокирует ребилд

Цепочка Run after — это одна работа, а не набор независимых ходов. Между её звеньями есть окно, где формально не работает никто: триггер закончил, владелец ещё не стартовал. Ребилд (`build:i-obs` и observe-фаза Voice Record) раньше видел в этом окне «всё свободно» и гасил приложение посреди цепочки — Codex записывал `turn_aborted` без ошибки, а зависящая вкладка законно не запускалась, потому что прерывание не является штатным завершением.

Теперь `/api/active-loaders` отдаёт взведённые очереди как `kind:"prompt-queue", status:"queued"` (`src/main/prompt-queue-install-blockers.js`). Статус специально не `busy`: вкладка не работает, ей **должны**. Источник — durable `promptQueueByTab`, тот же, что пишет store; живой копии очередей в main нет, а вторая копия стала бы новым источником рассинхрона. Полный разбор дыры, замеров и границ — `fact-build-when-idle.md::Шрам «дыра между звеньями цепочки»`.

## Выбор вкладки как условия карточки сам включает Run after

Выбрать другую вкладку в условии карточки (ПКМ → «после вкладки» → пикер) — это не правка параметра, а само обещание «отправить после того, как та вкладка отработает». Подтверждать больше нечего, поэтому очередь вооружается сама и красный hint гаснет — ровно как при выборе target на уровне очереди (`setRunAfterTab`). Раньше эти два входа расходились: уровень очереди армил, идентичный по смыслу выбор на карточке — нет, и пользователь видел красную кнопку при уже названном условии.

Правило вынесено в `utils/promptTriggerArm.mjs` с двумя намеренными асимметриями:

- **Наличие loader'а у цели ничего не решает.** Правило вообще не смотрит на runtime: неактивная цель означает «дождись её следующего запуска и его окончания», это и есть предмет ожидания. Трактовать «лоадера нет» как «ждать нечего» — та же ошибка, что считать не истёкший таймер отсутствием условия.
- **Таймер не армит, вкладка армит.** Таймер — это число, которое пользователь ещё набирает, а поле блокируется, как только очередь вооружена и карточка стала головой; арм на commit захлопнул бы поле посреди правки. У выбора вкладки фазы редактирования нет: выбор и есть commit.
- **Армит только карточка, которая пойдёт следующей.** Арм с более поздней карточки запустил бы очередь по условиям ГОЛОВЫ, а голова без условия уходит на ближайшем конце turn'а — то есть пользователь настраивает вторую карточку, а улетает первая. Согласие покрывает только что названное условие, не чужое.

Снятие условия не армит (это противоположное намерение), уже вооружённая очередь просто остаётся вооружённой. Дальше работает обычный pivot-путь исполнителя: `pivot armed → wait for next completed workflow`, то есть идёт ожидание следующего подтверждённого завершения цели, а не мгновенная отправка.

## Выключенная (красная) карточка не влияет на условие запуска

ПКМ → «Отправлять из очереди» выключает карточку: она остаётся видимой, но голова очереди — это первый **включённый** элемент (`items.find(isQueuedPromptEnabled)`), поэтому runner её перепрыгивает, счётчик её не считает, `popNext` её не берёт. Проверено на собранном сторе: при `[выключенный, обычный]` и включённом Run after `popNext` возвращает вторую карточку.

Чего это НЕ делает: условие запуска (таймер / «после вкладки») живёт на карточке, а не на очереди. Если условие стояло на выключенной карточке, оно вместе с ней и выпадает — головой становится следующая карточка со своим условием, а если у неё условия нет, очередь стартует сразу. Само условие в выключенной карточке сохраняется и вернётся, когда её включат обратно. Это осознанный контракт «условие принадлежит сообщению», а не баг; ловушка в том, что 30-минутная задержка на первой карточке визуально выглядит как задержка всей очереди.

## Свёрнутая панель по умолчанию

Новая вкладка открывает Run after свёрнутым: рейла (счётчик + «забрать из терминала» + переключатели панелей) достаточно, чтобы увидеть, что очередь пуста, а развёрнутая панель на каждой новой вкладке съедала ширину, которую пользователь не просил.

Ловушка, ради которой дефолт вынесен в `utils/promptQueuePanelDefault.mjs`: хранилище пропускает вкладку, состояние которой равно дефолту, поэтому дефолт и проверка «стоит ли это сохранять» обязаны меняться вместе. Если перевернуть только дефолт, ручное «разверни эту пустую вкладку» запишется как дефолтное, будет пропущено при сохранении и вернётся свёрнутым после перезапуска. Обе стороны читают одну константу; `panelCollapsed` без значения (строка, записанная до появления поля) читается как дефолт, и только явный `false` считается выбором пользователя. Локальный `?? false` в `PromptQueueOverlay` тоже заменён на общий дефолт — иначе он переспорил бы стор для вкладки без записи.

Rail Run after содержит счётчик/открытие панели, отдельную Play/Pause и при необходимости индикатор автокомпакта/локального исключения. Терминал + стрелка вправо переехали в composer navbar к input, который фактически захватывается. Post/Loop/`+`/`…` стоят поверх верхней границы панели и доступны как в закреплённом, так и во временном hover-состоянии, включая пустую очередь; каждый hit-target получает собственную hover-подложку, а `+` открывает прежний общий editor для нового последнего элемента. Пустой untouched editor при закрытии не создаёт карточку. Отдельного header/footer и `clear all` внутри больше нет. Отложенные Stop/Close добавляются через `…` как видимые карточки общей последовательности; немедленные Stop/Close остаются действиями самой AI-вкладки.

У самой полоски внутренних отступов нет: рамка идёт прямо по краю кнопок. Раньше было 3px сверху и снизу и 5px по бокам — при кнопке в 21px это почти треть высоты уходило на воздух вокруг них. Кнопки выросли до 26px ровно на освободившееся: полоска занимает столько же места, сколько занимала, но теперь всё это место — кнопки. Счётчик при пустой очереди показывает приглушённый `0`, а не точку: точка не отвечала на вопрос «сколько сообщений ждёт».

## Replay (▶) на чипе + guard от bash/zsh

Слева на каждом чипе — кнопка ▶. Target обычного клика определяется явным `inputSurface`, а не косвенным `historyPanelOpen`: в terminal-layout он пастит через IPC `claude:append-input` / `codex:append-input`, а в History-primary атомарно аппендит payload в tab-scoped History draft. Аппенд сохраняет уже набранный текст; после успешного переноса focus остаётся на видимом History textarea. Image refs сначала проходят прежнюю validation, затем в History переезжают вместе с semantic `[Image #N]`; ID перенумеровываются относительно уже набранного draft. Готовый `[imagePath: ...]` не показывается в authoring UI и строится только перед Send.

Cmd+hover по ▶ меняет кнопку в «send now» состояние, а Cmd+click отправляет через общий `sendAgentPromptScenario`: readiness, draft guard, exact handoff и durable receipt совпадают с auto-runner и History Send. Даже в History-primary этот путь не записывает History draft и не синтезирует нажатие его Send. Иначе History handoff и queue ownership одновременно считали бы себя владельцами одной отправки. Для обычного Replay renderer удаляет чип после синхронного History-transfer либо `success:true` terminal IPC; для Cmd+Replay граница та же, что у runner: обязателен `submitted:true`, а поздний audit timeout после Enter не оставляет чип для дубля. Старый dev-HMR fallback `success без submitted → renderer сам шлёт terminal:input '\r'` запрещён: он обходил main-side guard'ы и мог отправить prompt, который не был доказан в composer'е.

Для Codex `codex_paste_not_visible_before_submit` означает что Enter **не ушёл** и не должен синтезироваться renderer'ом. Для Claude общий scenario ждёт `UserPromptSubmit` audit для обычного текста; slash-команды получают отдельную command-квитанцию, потому что они не становятся нормальным user-message. `submitted:false` оставляет чип и показывает ошибку; `submitted:true` удаляет его даже при `success:false` позднего аудита, потому что повтор уже опаснее отсутствия подтверждения. Неподтверждённый manual Send-now сохраняет карточку и ставит autoRun на Pause: автоматический шаг с другим Post не должен стать вторым намерением после неизвестной ручной доставки. Явный `promptQueueAction:'send-now'` проходит caller → immutable Main FIFO → App re-entry; absent поле не добавляется старым fingerprints. Иначе явная отправка во время streaming ошибочно становится automatic RunAfter и получает его idle-ограничение.

Legacy `claude:append-input submit:true` больше не является публичным Replay
маршрутом. Если внутренний caller ещё использует этот handler, он обязан
сохранить явную физическую квитанцию нижнего слоя: явное `submitted:false`
нельзя перезаписать намерением caller-а. Иначе карточка удаляется после отказа
до Enter. Само право на
input revision возникает не при постановке Replay/History/Run after в очередь,
а в голове существующего PTY write lock: там операция атомарно получает revision
и переносит через него свой exact-empty proof. Если queued writer уже изменил
composer, старый proof требует revalidation; отдельный mutex запрещён.

**После подтверждённого переноса чип удаляется из очереди** (`removePrompt(tabId, it.id)` в renderer-handler). Семантика replay = **переезд** промпта в input, а не копия. Без удаления тот же текст потом мог бы повторно выстрелить через auto-run drain. До Enter ошибкой считается `!res.success`; после Enter достаточно `submitted:true`. Дополнительный side-effect: если это был **последний** чип очереди, removePrompt на transition 1→0 каскадно гасит `stopAfter/closeAfter` через store-mutator (см. секцию Stop/Close split ниже) — replay = «я сам этим займусь дальше», promise-state X-after становится беспочвенным.

**Spinner on the button while IPC is in flight.** Replay roundtrip — ~400-800ms (Ctrl+G grab → helper write → main IPC paste). Без видимой in-flight индикации юзер двойным кликом ставит вторую `claude:append-input` параллельно, потом `removePrompt` дважды — второй уже на несуществующем id. Guard через `replayingIds: Set<string>` в локальном state'е: на entry в handler добавляем id, кнопка для этого chip'а рендерится с `<span class="pq-spinner" />` вместо `▶` + `disabled` + статичный hover-палитра. Hover-handlers `if (replayingIds.has(it.id)) return;` чтобы стиль не дёргался при движении курсора. В `finally` удаляем id из set'а (на success чип всё равно уже исчез через removePrompt — set-операция no-op).

**Hard guard в main-handler — источник liveness = `bridgeKnownSessions`, НЕ `claudeCliActive`.** Без guard'а вообще: Claude exit-нулся между renderer-снимком и приходом IPC → bracketed paste чипа улетает в живой shell-parent PTY (bash/zsh). Современный zsh поддерживает bracketed paste mode → весь чип становится **одной shell command-line**. Чип `rm -rf node_modules` отрабатывает мгновенно, чип `sudo apt remove ...` запрашивает пароль. Handler сразу `return { success: false, error: 'no_claude_session' }` если сессии нет; renderer показывает toast «No Claude session for replay». Тело чипа открывает редактор по клику; ▶ и × используют `data-chip-action` + `stopPropagation`, чтобы клик не пробил в тело.

**Шрам: guard был на `claudeCliActive` → Replay падал на AutoResume'нутых табах, хотя auto-run работал.** Первая версия гейтила `if (!claudeCliActive.get(tabId))`. Это **неверный флаг** для liveness: `claudeCliActive` = «Claude *сейчас обрабатывает* turn», ставится **только** explicit-spawn путями (`claude:run-command`, MCP, handshake), пуст на idle-prompt'е и — ключевое — **никогда не ставится при AutoResume**. AutoResume пишет `claude --resume <id>` прямо в PTY через `terminal:input` (renderer, `App.tsx`); этот путь наполняет `bridgeKnownSessions` через `handleSessionDetected`, но `claudeCliActive` не трогает вообще.

Результат — **three-way асимметрия guard'ов на одном живом PTY**: три хендлера, пишущие в один и тот же Claude-инпут, проверяли разные источники:

| Handler | UI-триггер | Guard | На resumed-табе |
|---|---|---|---|
| `claude:send-command` | auto-run, Model/Effort | (нет guard'а) | ✅ работает |
| `captureClaudeInput` | grab / copy | `bridgeKnownSessions` | ✅ работает |
| `claude:append-input` | **Replay ▶** | `claudeCliActive` ❌ | ❌ `no_claude_session` |

Симптом юзера: *«run after сам работает в авторежиме корректно, но при нажатии на эту кнопку вручную вставка в инпут не хочет работать»* + красный тост `Replay failed: no_claude_session`. Прод-подтверждение (tab-5, сессия `59cf2ebf`, 2026-06-03): таб AutoResume'нут в 19:10:17 (`[AutoResume] Resumed … claude --resume`), `bridgeKnownSessions` знает сессию (auto-run `send-command` отрабатывал), но `claudeCliActive` пуст. В 19:34:36–44 — **4× `[append-input] ❌ Claude not active`**; в 19:34:48 (12 секунд спустя, тот же таб, тот же живой Claude) — `send-command` паста прошла за 247ms. Один и тот же инстанс Claude: append-input отказывает, send-command работает.

**Фикс:** guard `claude:append-input` переведён на `bridgeKnownSessions.has(tabId)` — тот же источник liveness, что у sibling-хендлера `captureClaudeInput`. Anti-`rm -rf` интент сохранён: чистый bash/zsh-таб без зарегистрированной Claude-сессии в `bridgeKnownSessions` по-прежнему отклоняется. Переносимый принцип: **liveness-guard для записи в Claude PTY = `bridgeKnownSessions` (процесс жив), не `claudeCliActive` (процесс занят turn'ом).** `claudeCliActive` ≠ liveness — это документировано и в CLAUDE.md (anti-pattern про `claudeCliActive` = «currently processing», пуст на idle) и в `fact-claude-tui-control.md` / комментарии `claude:get-presence` (main.js: «liveness belongs to hasBridge, never to isBusy»). Любой новый PTY-write handler обязан гейтить на `bridgeKnownSessions`, а не `claudeCliActive`.

**Codex replay guard — не bridge, а живой descendant process.** У Codex нет Claude-style `bridgeKnownSessions`, поэтому `codex:append-input` не может копировать guard один-в-один. Правильная проверка: под PTY shell должен быть живой Codex descendant; если его нет, handler возвращает `no_codex_session`, чтобы чип не улетел в обычный zsh/bash как shell-команда. Это та же anti-`rm -rf` граница, но с другим источником liveness: у Claude durable bridge подтверждает TUI, у Codex подтверждает дерево процессов.

## Stop/Close split: каскад stopAfter ↔ closeAfter

Бывший «Stop after» pill стал сплит-кнопкой. Левая зона — `stopAfter` (SIGTERM по окончанию очередного turn-а когда очередь пуста, one-shot disarm). Правая — `closeAfter` (после SIGTERM ещё и закрывает таб через `useWorkspaceStore.closeTab(tabId, { skipProcessCheck: true, forceCleanup: true })` — без модалки подтверждения). closeAfter невозможен без stopAfter: закрытие таба при живом Claude процессе бессмысленно. Поэтому `setCloseAfter(true)` каскадно ставит `setStopAfter(true)`; обратно — `setStopAfter(false)` каскадно гасит `setCloseAfter(false)` (orphan "close but don't stop" — недопустимая комбинация). Лейбл переключается «Stop after» ↔ «Close after» в одной CSS-grid ячейке (обе строки в `grid-template-columns: auto`, неактивная `visibility: hidden`) — ширина блока не дёргается. Каждая зона со своим border-radius'ом и border'ом: когда только stopAfter включён, левая зона оранжевая, правая остаётся серой на всех сторонах (не должна наследовать оранж от соседа через общий outer-frame).

**Pre-arm memory: `stopBeforeCloseArm`.** Клик ⏻ из baseline `(stop=off, close=off)` поднимает обе зоны (cascade). Повторный клик ⏻ должен **вернуть к baseline**, а не оставлять `(stop=on, close=off)` — иначе orange-зона зависает без обоснования. Хранится UI-only slot `stopBeforeCloseArm: boolean` (не персистится). `setCloseAfter(true)` пишет `stopBeforeCloseArm: cur.stopAfter` (записываем что было ДО форса); `setCloseAfter(false)` восстанавливает `stopAfter: cur.stopBeforeCloseArm`, обнуляет слот. `setStopAfter(any)` обнуляет slot всегда — клик по левой зоне = новый baseline, прошлая память невалидна. Таблица:

| Старт | Клик ⏻ | Клик ⏻ повторно |
|---|---|---|
| `stop=OFF, close=OFF` | `stop=ON, close=ON` | `stop=OFF, close=OFF` ✓ |
| `stop=ON,  close=OFF` | `stop=ON, close=ON` | `stop=ON,  close=OFF` ✓ |

**Auto-disarm при ручном empty-out очереди.** Если последний чип уходит **руками** (× или ▶ Replay), `removePrompt` на transition `items.length === 1 → 0` дополнительно гасит `autoRun/stopAfter/closeAfter/stopBeforeCloseArm` и активный first-delay countdown. Причина: Run-after/X-after без очереди превращается в зомби-promise, юзер потом удивляется когда будущий turn внезапно запускает новый prompt или убивает агента. Юзер: *«если включен run after, а я удалил последний из очереди элементов — run after должен быть остановлен»*. **Граница против `popNext`** — там очередь опустошается естественно (autoRun-runner отстрелял последний промпт в AI), X-after должен **остаться** armed, чтобы runner на следующем busy→idle edge выстрелил `terminal:stop-ai-process`. Если бы `popNext` тоже триггерил disarm — main use case «отправь N промптов и убей агента» сломался бы. Различие в store-mutator: `removePrompt` гасит, `popNext` не трогает.

**Seam-фикс правой рамки.** Раньше: левая `borderRight: none`, правая `borderLeft: 1px BORDER` (grey 0.08-alpha) — seam рисовала **правая** через свою левую границу. На retina + темном фоне 0.08-alpha 1px-border попадает в subpixel rounding compositing → Chromium периодически дропает draw при relayout (tab-switch overlay mounted, props меняются). На клик-relayout восстанавливается. Плюс `transition: all 0.15s` анимировал смену border-color между табами → 150ms fade orange→grey = «подёргивание внутри». Юзер: *«при переключении вкладок она просто-напросто, блять, пропадает, потом если я заново нажимаю кнопку, она появляется»*. Фикс — перенёс ownership seam'а на **левую** кнопку: full `1px solid` со всех 4 сторон (включая seam = `borderRight`), правая кнопка имеет `borderLeft: 'none'` + три остальные стороны. Seam теперь integer-pixel border-right с непрозрачным цветом, Chromium не теряет. Цвет seam = `leftBorder` (orange/red/grey), семантически правильно — active-зона «прокрашивает» seam своим цветом. `transition` убран — на tab-switch снапит мгновенно. Hover-handler правой кнопки трогает только три свои стороны, seam под управлением leftBorder. Принцип переносимый — см. `methodology/дизайн-принципы.md::Split-button seam: один owner draws border, не adjacency`.

**Hover policy: только color, не border/background.** На idle-зоне hover красит **только** `color` (текст «Stop after» → orange, ⏻ icon → red). Background и border-color **не трогаются** — они закреплены за state-сигналом. Юзер: *«фон и рамку менять не надо»*. На активной зоне (stop armed → левая orange; close armed → обе red) hover вообще no-op — state уже даёт сильный цвет. Без этого правила hover-эхо конфликтует с armed-эхом (юзер не отличает «hover-orange» от «armed-orange»). См. `methodology/дизайн-принципы.md::Hover-isolation для split-button` (расширение секции).

Принцип каскада переносимый — см. `methodology/дизайн-принципы.md::Toggle cascade: dependent ⇒ parent`. Скрытое-но-резервированное «Close after» расширение grid-ячейки — частный случай `methodology/дизайн-принципы.md::Layout reservation для toggle-able children` (там добавлен абзац про variable-label). Auto-disarm при manual empty-out — `methodology/дизайн-принципы.md::Promise-state auto-disarm: manual context-drop vs pipeline-drain`.

## Image-paths resolution из grabbed `[Image #N]`

Когда юзер пастит картинку в Claude TUI через Cmd+V (или drag-and-drop), Claude Code не отправляет её сразу — она живёт в **двух местах**:

1. В RAM Claude как `pastedContents: Record<number, PastedContent>` под ключом `pasteId` (счётчик `nextPasteIdRef++`).
2. В тексте input'а — плейсхолдер `[Image #N]` в позиции курсора (`formatImageRef(pasteId)`).
3. На диске — асинхронно через `storeImage()` в `~/.claude/image-cache/<sessionId>/<N>.<ext>`, режим `0o600`, расширение `mediaType.split('/')[1]` (`png|jpeg|jpg|gif|webp|bmp`). Размер cap в RAM: 200 файлов с FIFO eviction. Источник: декомпиленный `packages/claude-code-src/utils/imageStore.ts`.

**Файлы не удаляются в течение жизни сессии.** Удаление плейсхолдера через бэкспейс пруньет **только** in-memory `pastedContents`, файл на диске остаётся. `cleanupOldImageCaches()` запускается ровно один раз — при boot'е Claude — и сносит **все** session-папки **кроме текущей**. Внутри текущей сессии очистки нет.

При финальном submit в API `processUserInput.ts::storeImages` идемпотентно гарантирует что все картинки на диске (повторно пишет если что-то пруньнули) и шлёт `image_url` content-blocks. Это значит: пока live sessionId — все `[Image #N]` имеют живые файлы рядом.

**Наш resolver `resolveGrabbedImagePaths(sessionId, text)`** парсит регексом `\[Image\s+#?(\d+)\]` плейсхолдеры из grabbed-текста (helper приходит с `[Image #N]` дословно — `expandPastedTextRefs` Claude'а раскрывает text-refs, image-refs оставляет литералом). Для каждого id перебирает расширения, ищет файл, отдаёт `{id, path, mediaType, size}` если существует. В `claude:grab-input` resolve добавляем `imagePaths` к ответу, кладём в `QueuedPrompt.imagePaths` через `addPrompt(tabId, text, images, imagePaths)`. Лог `[GrabImages] tab=... sessionId=... refs=N resolved=[#1:46KB,#2:MISSING]` — `MISSING` = ссылка в тексте есть, файл нет (Claude был рестартован после paste, image-cache папка ещё не очищена но текущий sessionId уже другой; либо grab случился в момент когда file write ещё не флашнулся — редко).

Codex устроен иначе: если вставить в live Codex composer быстрым PTY-write голый путь `/path/file.png`, Rust TUI превращает локальный image-path во внутренний attachment `[Image #N]`. Bitmap clipboard и локальные image-path **до вставки** материализуются в `app.getPath('userData')/prompt-queue-assets/<sha256>.<ext>`; content hash дедуплицирует одинаковые байты, права файла `0o600`.

Durable macOS path обычно содержит пробел в `Application Support`, поэтому передавать его в Codex напрямую нельзя: TUI оставляет такой путь обычным текстом и не создаёт image attachment. Для live paste, Replay и Run after main создаёт content-addressed whitespace-free transport alias в `/tmp/noted-terminal-codex-image-input` (symlink, hard-link fallback) и пишет в composer только alias. Байты остаются в durable asset store и второй раз не копируются; slot binding продолжает ссылаться на durable asset, а transport alias является только входом в Codex path detector.

**Точная slot-привязка вместо «последних N».** На stage создаётся одноразовый token, `terminal:input` атомарно начинает injection, а main-side PTY observer связывает появившийся `[Image #N]` с конкретным stable asset. `GrabInput agent=codex` резолвит по номеру slot'а. Поэтому после paste A/B удаление B оставляет `#1 → A`, а перестановка `#2, #1` возвращает `B, A`; старая эвристика `peekRecent(count)` в этих случаях могла тихо подставить не ту картинку. Если Grab пришёл раньше TUI redraw, fallback допустим только при точном равенстве «неразрешённых slot'ов = pending assets». Любое несовпадение неоднозначно и превращается в видимый `imageError`, а не угадывается.

12h retention/cap 96 остаются только safety-границей **до Grab** для незавершённых stage token'ов. Исторический incident 26.06.2026: paste A/B в 03:43:25/03:43:46, `Ctrl+C` активного turn в 03:53:34, затем `+Grab` в 03:53:43 получил `refs=2 pathResolved=0`. Bitmap теперь сразу лежит в durable asset store, slot binding живёт до Grab/restart текущего Codex launch, а raw `Ctrl+C` его не очищает: interrupt может оставить queued draft с обоими image chips. Binding очищается на Enter-submit, успешном Grab, новом launch и teardown. Диагностика: `[CodexImageBinding] ... begin/bound`, `[GrabImages:Codex] ... mode=slot-binding`, `[PromptQueueAssets] grab ... durable=N`.

**Persistence теперь владеет и метаданными, и байтами.** `QueuedPrompt.imagePaths` содержит `assetId`, stable `path`, media type, size и availability; весь item переживает restart через `app:setState`, а normal close синхронно flush'ит store. На hydrate каждое старое `imagePaths`/`[imagePath: ...]` автоматически копируется в asset store, пока исходный файл ещё существует; до завершения проверки карточка честно показывает `materializing`, но уже присутствует в восстановленной очереди. Claude cache `~/.claude/image-cache/<sessionId>/...` копируется туда прямо во время Grab, поэтому последующий Claude restart/cleanup уже не ломает карточку. Путь через `assetId` заново разрешается относительно текущего `userData`, а не доверяет старому absolute path.

History composer использует тот же marker/ref-контракт. Clipboard bitmap сразу материализуется в durable store, но в редактируемом source-тексте остаётся только `[Image #N]`; обычный `+grab` переносит text и refs атомарно, а pending/damaged/missing attachment не имеет права очистить History. Transient ошибка materialize сохраняет прежние refs: пустой ответ проверки не является доказательством, что вложений не было.

**Межприложенческий clipboard — один text-only wire format.** History и Run after принимают абсолютные `[imagePath: /...]`, сначала копируют каждый источник в durable asset store, затем одним изменением заменяют их локальными `[Image #N]` и перенумеровывают относительно уже имеющихся refs. Относительный marker остаётся обычным текстом. Настоящий bitmap-only clipboard проходит тот же финальный путь через `prompt-queue:save-clipboard-image`. В обратную сторону целый `[Image #N]` экспортируется как `[imagePath: <durable path>]`; окружающий текст и любое число картинок сохраняют порядок, а в pasteboard пишется только `text/plain`.

Тот же экспорт разворачивает каждый целый `[Pasted Content N chars]` в точное тело sidecar-чипа. Разбор source-position based: одинаковые по длине вставки не сопоставляются «по первому тексту», а следуют порядку якорей. Missing sidecar даёт `[pasteError]`; разрезанный image-marker — `[imageError]`. Благодаря этому смешанное выделение `text + image + pasted content + image` является одним переносимым текстом, а не несколькими конкурирующими представлениями clipboard.

Inline-миниатюра не читает `file://` из renderer: CSP custom-terminal это запрещает. `prompt-queue:get-image-preview-data-url` принимает только ref, который `PromptQueueAssetStore` доказал как managed, декодирует его через `nativeImage` и возвращает `data:image/...`. У IPC два варианта одного и того же validated asset: `thumbnail` ограничен 64 px по длинной стороне для 20×20 чипа, `detail` — 1024 px для раскрытого просмотра. Renderer кэширует их раздельно по variant + content-addressed `assetId`; загрузка event-driven, без polling. Поэтому клик по image-чипу открывает настоящую картинку через тот же preview-контракт, что `Pasted Content`, но геометрия принадлежит поверхности: History показывает image-card компактной ширины слева над input, тогда как Run after создаёт отдельную sibling-card слева от всего editor-блока title+body (на узком viewport — снизу). Preview не раздвигает и не прячется внутрь редактируемого поля. IPC при этом не превращается в произвольное чтение absolute path. У image-чипа нет стрелки раскрытия: сама миниатюра уже обозначает объект; стрелка остаётся только у текстового paste-чипа.

**Шрам: Replay передал transport-текст, но потерял History presentation.** Ветка `claude:append-input` / `codex:append-input` раньше получала только строку с `[imagePath: ...]`. После Enter provider честно сохранял эту строку, но post-Enter audit не знал `imagePaths`, поэтому History показывал синий raw-marker вместо изображения. Terminal Replay теперь передаёт `presentationSnapshot` вместе с payload, а оба append-handler'а прокидывают его в общий audited submit. Для уже записанных сообщений main может восстановить отсутствующий image-sidecar только из абсолютного `[imagePath: ...]`, который находится вне `<pasted_content>`, не экранирован и строго подтверждён как существующий content-addressed файл внутри текущего `prompt-queue-assets`. Произвольный путь, отсутствующий файл и пример из вставленного лога остаются обычным текстом. Успешное восстановление сразу сохраняется как schema v3 sidecar по точному UUID записи, чтобы последующие загрузки не гадали заново и GC не удалил байты.

Положение Run after preview вычисляется из живой геометрии editor + viewport: если слева остаётся не меньше минимальной читаемой полосы, карточка ставится слева с фиксированным gap и при необходимости сжимается до доступной ширины; иначе она начинается под editor и сохраняет его левый край. Решение вынесено в чистый `resolveRunAfterPreviewPlacement`, поэтому обе ветки проверяются без искусственного browser resize. Сам renderer обновляет входные размеры через `ResizeObserver` и событие `resize`, без polling/timeout.

Очередь хранит composer chips отдельным структурным массивом рядом с editable `text`, а не заранее разворачивает их в строку. Поэтому `+grab`, persistence, restart и обычный Replay могут вернуть prompt/paste chips в History тем же UI-представлением; legacy items без поля chips остаются валидными. Prompt-чипы при Replay дедуплицируются по source key, paste-чипы сохраняют каждое повторение, а chip-only item не добавляет `\n\n` в непустой textarea. `+grab` сначала синхронно ставит snapshot в очередь (и передаёт ей pending-маркеры), затем сразу возвращает transfer caller'у; lookup/AI-название идёт отдельной фоновой presentation-задачей. History очищается только если текущие text, chips и image refs всё ещё совпадают с нажатым snapshot; дописанный до CAS draft остаётся в composer, а очередь уже хранит прежнюю версию.

Перед каждым History Send, Run after и Replay renderer вызывает `prompt-queue:materialize-image-refs`: main проверяет реальные файлы, а queue item временно имеет state `materializing`. Результат разделяет **известный slot с пропавшим файлом** и **неоднозначную identity**. Первый заранее показывается постоянным предупреждением, но не блокирует намерение пользователя отправить: ровно в позиции slot'а transport получает `[imageError: queued_image_path_unavailable #N path=…]`, соседний текст и остальные изображения сохраняются. Повреждённый/непривязанный marker остаётся blocking, удерживает ref для ремонта и не покидает composer. Codex и Claude main-boundary повторяют ту же семантику как защита от race, а не возвращают общий `queue_image_path_unavailable` после нажатия Send. Unreferenced assets удаляются event-driven GC только через 30 дней; validation и byte-dedup обновляют mtime, а все assets, затронутые текущим app process, получают session lease. После restart GC дополнительно считает referenced все `assetId` из durable History composer snapshots, поэтому картинка несохранённого draft не удаляется только из-за завершения прежнего process.

Тот же asset owner в SOURCE05.10 хранит обычные mobile-upload документы как
`<sha256>.document.<ext>`; image preview IPC остаётся image-only. Public Send
импортирует только проверенные upload refs до Main FIFO ACK, не произвольные paths.
SQLite inventory читается и до создания web queue; temporary import leases и GC
generation/deletion barrier защищают гонку ACK с прежним collector. Failed/unknown
bytes не освобождаются по timeout, shared copies не удаляются при отказе другого
Send. После release прежний30-day GC действует и для документов. Это не изменение
missing-image placeholder/Run After и не новая очередь. Wire/legacy предел —
`fact-mobile-web.md::Mobile upload attachments`.

Transport строится в строгом порядке: сначала image-marker'ы materialize только внутри editable `text`, затем prompt/paste chips сериализуются вокруг подготовленного текста. Обратный порядок опасен: литерал `[Image #1]` внутри opaque paste/prompt chip ошибочно выглядит как attachment slot и может присвоить чужой ref или превратиться в `imageError`.

Для Codex источник истины разделён только по представлению: live composer показывает native `[Image #N]`, очередь хранит durable asset. В момент Run after или Replay `buildQueuedPromptPayload` разворачивает slot в `[imagePath: <stable path>]`. Если slot не имеет доступного asset, он всегда становится `[imageError: queued_image_path_unavailable #N]`, даже когда весь `imagePaths` отсутствует (legacy/missing-all case).

**Граница native re-attach.** Codex Replay/Run after превращает `[imagePath: ...]` в whitespace-free transport alias до paste, поэтому Codex TUI снова создаёт native `[Image #N]`. Каждый alias обязан идти отдельным bracketed-paste event: Codex проверяет весь payload одного paste как один filesystem path, поэтому склейка `alias + дописанный текст` оставляет путь обычным текстом. Смешанный prompt временно раскладывается в исходном порядке на text/image/text paste-группы и только после всех групп получает Enter; редактирование обычного текста не меняет attachment. Claude получает стабильный `[imagePath: ...]` file-reference и может прочитать файл, но его внутренний `pastedContents`/base64 image block не восстанавливается: для нативного Claude image-chip нужен отдельный clipboard/attachment transport. Durable storage не подменяет эту транспортную разницу.

**Редактирование image-marker'ов.** В editor очереди синим подсвечивается только точный неэкранированный `[Image #N]`, для которого item хранит доступный asset. Частично обрезанный marker, `\[Image #N]`, неизвестный номер или другой image-подобный фрагмент немедленно теряет синюю подсветку, переводит item в damaged/missing-state и блокирует Replay/Run after. Image refs при повреждении сохраняются, чтобы случайная правка текста не отдала файл GC и marker можно было восстановить. Если marker удалён целиком и image-подобных фрагментов больше нет, это считается осознанным удалением вложения: соответствующий ref удаляется, остальные изображения продолжают работать. Неактивный error/pending marker отображается компактным status-чипом, но serialized marker остаётся source of truth. Клик по левой половине раскрывает его с caret сразу после `[`, по правой — непосредственно перед закрывающей `]`; `Option+Backspace` в позиции перед либо сразу после этой `]` удаляет весь marker одним действием. В остальных позициях сохраняется стандартная word-delete семантика. Нативный `mousedown` не блокируется: короткий click применяет boundary после `mouseup`, а drag остаётся настоящим выделением и не превращается в preview/caret-jump.

Финальный замороженный Luna Medium E2E подтвердил общий контракт History и Run after: image/paste/error имеют одну геометрию, Run after image-preview рендерится отдельным sibling-блоком, двойной клик image и Pasted Content даёт ровно один preview-toggle без нативного word-selection, right-half status-click + `Option+Backspace` удаляет только marker, а смешанное выделение экспортирует один `text/plain` с абсолютным image path и полным телом Pasted Content без bitmap-format. Доказательства: `/tmp/custom-terminal-e2e-f6f9-g2hsAF/` и `/tmp/custom-terminal-e2e-f7-lzBED8/`.

Отдельный живой замер закрыл более строгую границу вертикального выравнивания. Одного `vertical-align: middle` было недостаточно: он уравнивал чипы между собой, но оставлял их на `1.765px` ниже обычной каретки. Общая оболочка дополнительно поднята на `0.11em`; после этого center delta image/paste/error к каретке равен `0.280px` и вплотную, и после одного пробела, а сама каретка не меняет Y. Регрессионный порог — не более `0.5px`, потому что прежний допуск `2px` пропустил видимый дефек. Артефакты: `/tmp/e2e-composer-caret-correction-20260802/`; общий repo-fingerprint того прогона изменился из-за параллельных несвязанных правок `database/main` и Codex/Rewind docs, тогда как CSS пакета и renderer composer во время замера не менялись. Ручная проверка в production дополнительно подтвердила визуальный результат.

## Pending-диктовка при переносе из History

`+grab` может захватить черновик, пока `[Dictating vr-<ts>]` ещё дожимается в
Voice Record. Это не готовая строка для копирования: очередь становится новым
владельцем незавершённого результата. Queue-item и перенос всех найденных маркеров
коммитятся синхронно, прежняя CAS-проверка сразу очищает History, а lookup/AI-
название запускается уже отвязанной presentation-задачей и не входит в promise
переноса. Иначе короткий resolve во время асинхронного поиска title оставлял бы
финальный текст в History, а в Run After — осиротевший loader или заметный дубль.

Карточка показывает тот же pending/error token и не допускает Replay либо отправку
сырого маркера. Если её timer/context/turn-end уже сработал, runner сохраняет exact
попытку с item identity и продолжает её после resolve; произвольное изменение очереди
не изображает новый trigger. При переносе снимается dictation-auto-send из History:
моментом отправки теперь владеет Run After. Удаление маркера или всей карточки —
осознанная отмена поздней вставки, результат не воскресает.

Resolve заменяет маркер в текущем тексте карточки и материализует присланные Voice
Record изображения в durable queue-assets до публикации `[Image #N]`. Поэтому уже
перенесённые ручные правки, позиция вставки и image-sidecar'ы остаются одной
композицией. Детали исходного чипа — `fact-dictation.md::Диктовка Voice Record как
чип в композере (dictation chips)`.

## Editor surface: hover-preview + blur-save

Создание через `+` сразу фокусирует body ComposerEditor. Title остаётся пустым
с placeholder `Title will be generated automatically`; человек может задать
своё название, прежний Run After Title prompt/язык генерации не переписывается.
Пока открыто именно создание, `+` имеет спокойный фиолетовый фон и белый glyph.
Повторный `+` сохраняет и закрывает редактор; `⌘Enter` делает то же из body/title.
Родительская очередь не закрепляется и не закрывается от этого сохранения:
после keyboard-save вне неё действует один возврат до re-entry, затем обычный
hover. Можно сразу ПКМ новой карточки → on tab. При редактировании существующей
карточки `+` остаётся обычным Add. Пустой untouched draft карточку не создаёт.

Blur/outside-save сохранён, но создание материализует **один** item: после
первого `addPrompt` editor синхронно принимает его ID/последний payload. Флаг
«открыт через Add» отдельный: дальнейшие blur/overlay/`+` обновляют тот же ID,
не вставляют новую карточку. История Undo/Redo остаётся у того же draft до
закрытия. Поздний blur проверяет generation открытия, поэтому не применяет
старый body к следующему editor. Шрам10.10: `empty`-click сохранял с close:false,
но оставлял id=null; следующий overlay создавал дубль. Actual UI воспроизвёл2→1.

**Модалка и её preview-сосед живут в `document.body`, не внутри overlay.** В сплите overlay очереди порталится в host конкретного ОКНА, а обёртка окна (`data-terminal-pane-wrapper`, `position:absolute; zIndex:2`) — собственный стековый контекст. `position:fixed` даёт модалке экранные координаты, но не выводит из контекста окна: соседнее окно — такой же sibling с `zIndex:2`, и DOM-позднее красится поверх модалки. Поэтому editor slideout и `pq-editor-preview-sibling` порталятся в `body` (как meta-actions и контекстное меню карточки) и перекрывают соседние окна снизу целиком — это by-design: «менюшка может идти через другие окна». Новую поверхность, открываемую из панели, порталь туда же, иначе в сплите её обрежет чужое окно.

Чип очереди имеет два независимых слоя: `text` = payload, который уйдёт в terminal input; `title` = label карточки. Для обычного prompt в store на создании есть fallback-label `[N символов]`, но пока AI-title реально генерируется UI показывает маленький title-loader вместо временного текста: fallback нужен для persistence/failure, не как первая «версия названия». Самостоятельная однострочная локальная slash-команда без изображений и composer-чипов получает буквальное имя команды: `/compact` из `…`, `+grab` и `+add` сразу показывается как `/compact`, не отправляется в AI-title и не превращается в `[8 символов]`. При загрузке старой очереди только автоматический size-label такой команды заменяется на её текст; заданное человеком название сохраняется. Для `+grab` trimmed input короче 25 Unicode-символов сразу становится title (переносы/серии пробелов в однострочном label схлопываются), при этом исходный payload не меняется; lookup сохранённого Insert Prompt и AI-генерация полностью пропускаются. Ровно 25 символов уже идут по обычному пути, если это не самостоятельная команда. Для более длинного текста `+grab` сначала пытается распознать сохранённый Insert Prompt: если grabbed-текст начинается тем же содержимым (для длинных prompt'ов — exact match первых 50 символов, для коротких — полный prefix), title берётся из сохранённого prompt'а и AI-название не запускается. Это защищает сценарий «вставил готовый prompt через контекстное меню, дописал детали, потом +grab»: пользователь ожидает уже известное имя prompt'а, а не loader и позднее переименование. Если match не найден — `+grab` запускает AI-название, а `+add` запускает его если title input остался пустым на blur/outside-save. Источник — встроенный Settings → AI prompt `Run After Title` (`run-after-title`), поэтому пользователь может менять prompt/model/thinking так же, как для остальных AI prompts. Late response перечитывает текущий item из store и skip'ается если `titleManual=true`, payload успел измениться либо стал командой: ручная правка и свежий текст выигрывают у async-генерации. Если API key/model недоступны, fallback `[N символов]` остаётся честным size-marker'ом для обычного prompt'а, а не ошибочным «названием».

ПКМ по карточке открывает маленькое item-menu, а не общий overlay: `Отправлять из очереди` работает как checkbox/toggle для `enabled`, `Обновить название` заново запускает `Run After Title` для обычного prompt'а с force-режимом; у локальной slash-команды этот пункт отсутствует. Выключенная карточка остаётся в списке и редактируется как обычно, но runner берёт первый `items.find(enabled !== false)`, а badge/count/empty-out считают только enabled items. Если пользователь выключил последний активный item, это эквивалентно manual empty-out для armed state: `autoRun` должен погаснуть, иначе UI показывает активную очередь без runnable действия. Видимые lifecycle meta-items подчиняются тому же enabled-state и не требуют отдельных скрытых флагов. Визуально disabled — тёмно-малиновый фон + светлый приглушённый текст без ярко-красной рамки: это skip-state, не delete/error. Переносимый принцип — `methodology/дизайн-принципы.md::Выключенный элемент списка = visible skip-state, не удаление`.

`▶` — альтернативный вход в ту же сущность, поэтому hover по нему открывает **тот же** editor surface, что body-чип / `+add`, а не отдельный tooltip. Визуально editor состоит из `input title` → divider → структурные prompt-чипы → общий `ComposerEditor`: image- и paste-якоря являются атомарными inline-чипами в body, совпадающими с History по навигации, copy/cut/paste, миниатюрам и раскрытому preview. Нативное CM-выделение внутри этой общей поверхности обязано быть видимым: глобальное правило полного MarkdownEditor, скрывающее `.cm-selectionBackground` ради своей проекции selection, scoped-переопределяется только для `.gt-composer-editor`. Сам replace-widget перекрывает фон CM, поэтому пересечение selection дополнительно ставит на весь атомарный чип selected-background; иначе `Pasted Content` выглядел бы дырой внутри выделенной строки. Widget не поглощает первый `mousedown`, чтобы выделение можно было начать на чипе; второй mousedown/dblclick подавляется до CM word-selection, поэтому быстрые клики только открывают/закрывают preview. Одиночный click после настоящего drag не срабатывает при непустом selection. Header, footer, Cancel/Save и Escape-текст не нужны; автосохранение работает по blur/outside-click, явное сохранение — повторным активным `+` или `⌘Enter`. `+add` с заполненным title и пустым body сохраняется: title становится payload-текстом задачи, а не только карточным label'ом. Но у существующего chip-only item auto/manual title — только presentation: открыть и закрыть editor не копирует его в payload, а удаление последнего чипа удаляет опустевший item.

Undo/Redo общего `ComposerEditor` охватывает не только видимый документ. Host передаёт непрозрачный sidecar `{ imagePaths, chips }`; CodeMirror хранит его в `StateField` и инвертирует в том же history-event, что text/selection. Явные Cut/Paste/restore-actions создают полную snapshot boundary. Асинхронная замена pending image идёт без нового history-step, а обёртка штатного Undo/Redo синхронно нормализует text, selection и sidecar до публикации host'у. Поэтому `Select all → Delete → Undo` возвращает точные файлы и тела `Pasted Content`, а Redo снова удаляет всё; временный `[Image saving…]` не возвращается. `historyOwnerKey` сбрасывает стек при переходе между item/new/post/loop, чтобы Undo не пересекал владельцев.

`Cmd/Ctrl+F` при фокусе body принадлежит самому composer: компактная панель справа сверху показывает запрос, `current/total`, previous/next и закрывается Escape; совпадения подсвечиваются жёлтым. Глобальный terminal/History search не должен одновременно реагировать на то же событие.

Pasted Content в редакторе Run after использует те же действия, что History: ПКМ — только возврат текстом на место якоря; средняя кнопка — удаление; в раскрытом preview рядом с Copy есть корзина. Удаление и возврат входят в Undo вместе с телом чипа, поэтому две одинаковые по длине вставки не обмениваются содержимым. Сохранённые prompt-чипы и действия уже отправленных сообщений этим меню не меняются.

Обычный `Cmd+V` в Electron имеет два намеренно разных входа. Для синхронного text-only paste общий `ComposerEditor` читает `electron.clipboard` через инъектированный adapter и вызывает тот же host `onPaste`: длинный текст становится `[Pasted Content …]`, короткий вставляется точно в selection, а custom flavor `application/x-voice-record-dictation` остаётся видимым проверке и не превращает диктовку в paste-чип. Если clipboard пуст или среди formats есть `image/*`, keymap возвращает управление trusted DOM paste — bitmap проходит прежний `handleEditorImagePaste`, сохраняется в durable asset store и становится image-чипом. Нельзя асинхронно `preventDefault()`-ить этот выбор или добавлять `readItems` Electron-адаптеру: так снова будет проглочен screenshot paste.

Внешняя Voice-диктовка в body использует общий ComposerEditor receipt, title — native field receipt. Их editor-session owner меняется при переходе к другой задаче. Подтверждение полного документа предшествует восстановлению clipboard; обычный Enter не запускает альтернативный queue executor. Не заменять это постоянным таймером: шрам12.10 и границы source/runtime — `fact-dictation.md::Вставка из Voice Record через буфер обмена`.

Hover-open не autofocus'ит editor, иначе случайный проход мышью по `▶` ворует focus у терминала. Focus ownership начинается только после явного клика/фокуса внутри title или textarea; в явно открытой очереди focus-owned editor не закрывается от ухода из своего trigger/editor. Это не передаёт pin родительскому hover-preview. Чистый hover-editor сохраняет геометрию; явно открытый click-editor временно держит своего родителя независимо от курсора до собственного закрытия, после чего возвращается обычный hover. Клик по самой карточке/чипу переводит editor в pinned-mode с приглушённой серой рамкой: рамка говорит «закреплено», но не должна быть такой же яркой как текст. Hover по `▶` уже не двигает и не закрывает окно. Повторный клик по тому же активному чипу = toggle-close, как outside-click; open-handler обязан подавить same-click reopen, иначе окно исчезает на кадр и тут же появляется снова.

Pinned-mode переживает навигацию через persisted `previewId`: кликнул чип, ушёл на другую вкладку/проект, вернулся — editor должен восстановиться на той же карточке. Но это не означает «игнорировать любой outside click». Ordinary outside-click по терминалу, сайдбару или пустой области делает blur-save, закрывает editor и очищает `previewId`; navigation-click по tab/project/Home делает blur-save без очистки, чтобы возврат восстановил pinned editor. Клик по самой карточке, которая закрывает editor, тоже сохраняет правки title/body перед закрытием.

`+add` использует ту же editor surface и якорится к концу list/empty-block: визуально создаётся следующее поле очереди, а не настройка header'а. Если снизу недостаточно места, геометрия поднимает editor ровно настолько, чтобы сохранить минимальную рабочую высоту. Повторный клик по активной `+add` закрывает editor; пустой untouched draft не создаёт item. Важный шрам: click-outside listener висит на `window.mousedown`, поэтому trigger-кнопки editor'а помечены как editor-trigger и исключены из outside-close; без этого mousedown закрывает editor, а следующий click тут же открывает его снова.

Новый `+add` до появления queue item владеет полноценным локальным snapshot `text + chips + imagePaths`. Bitmap/path materialize сначала ставит pending-marker в этот snapshot, затем атомарно заменяет его marker/ref/chips; blur/commit откладывается, пока pending существует. После завершения `addPrompt` получает refs вместе с текстом. Нельзя требовать сначала сохранить пустую карточку: это и было причиной, почему вставка работала в существующем item, но молча отсутствовала в новом Run after.

Editor resize повторяет глобальный паттерн anchored modal, но только по ширине: правый верхний угол закреплён, левая грань и левый нижний угол работают как hit-area для горизонтального drag'а. Нижней ручки больше нет. Высота всегда content-driven: сколько строк получилось после переноса в текущую ширину, настолько вниз и идёт нижняя граница, пока не упрётся в доступное место viewport'а; дальше скроллится textarea внутри. При изменении ширины высота переизмеряется заново, потому что перенос строк меняет scrollHeight. Это возвращает ожидаемую модель «нижняя граница по контенту как раньше» и не даёт ручному resize высоты оставить пустую коробку под коротким prompt'ом.

Для unfocused hover-preview закрытие идёт через global `mousemove` geometric hit-test по rect'ам replay button + editor, а не через `onMouseLeave` на lazy-mounted popover — иначе cursor не успевает перейти в только что смонтированный DOM.

Save существующего изменённого чипа даёт один короткий зелёный flash на самой карточке. Новый чип с ручным title или без AI-title входит зелёной left-to-right wipe-анимацией. Новый чип, у которого сразу стартовал AI-title, входит нейтрально с title-loader'ом и получает зелёный flash только один раз — когда финальное название реально записалось. Иначе пользователь видит два success-сигнала подряд: сначала на временный `[N символов]`, потом на придуманное название, хотя сохранение по смыслу одно. Явное удаление через Trash-кнопку подсвечивает **всю** карточку красным на hover и задерживает `removePrompt` до right-to-left exit-анимации. Replay-success по `▶` удаляет чип сразу: prompt уже перемещён в input, и анимация удаления не должна задерживать runner-семантику.

Stale-closure gotcha: blur-save и следующий click могут произойти в одном пользовательском жесте до React re-render. Поэтому replay click и open-editor обязаны читать актуальный item через `usePromptQueueStore.getState()` в момент клика, а не использовать `it.text` / `items` из JSX closure. Иначе пользователь меняет body, сразу жмёт `▶` или другой чип — и действие применяет старый payload.

Открытый editor существующего item и post-prompt пишет изменённые text/chips/image refs в store сразу, а не ждёт blur: Replay и runner всегда читают тот payload, который пользователь уже видит. Пока payload редактируется, tab-scoped token lock запрещает auto-run, включая попытку, которая уже дошла до асинхронной проверки вложений; unlock будит runner только если реальная отправка упёрлась в lock. Manual Replay сначала фиксирует editor, снимает lock без wake и заново читает item из store, иначе Replay и auto-run могут отправить его дважды.

Финальный commit не записывает полный open-time snapshot: он меняет только dirty-поля, а trim/delete/rollback применяет через compare-and-set к последней write-through версии. Поэтому параллельное изменение text/chips/title с мобильного либо сохраняется как незатронутое поле, либо заставляет локальный stale commit отказаться; desktop editor не может молча вернуть очередь к состоянию на момент открытия.

## Focus terminal перед `clear-input`

После `copy-input` тут же шлём `clear-input` IPC → main посылает Ctrl+G → helper truncate'ит tempfile → Claude перечитывает → инпут гаснет. **Но** если фокус был на InfoPanel-кнопке, Ink render-loop в неактивной browser-вкладке throttled → "Save and close editor..." flash проигрывается **только когда юзер кликнет в терминал**. Симптом: юзер копирует → инпут стоит → кликает в терминал → инпут мгновенно гаснет ("какой-то flash был, потом стёр").

Фикс: `focusActiveTerminal()` **между** showToast и `clear-input` IPC. RAF-обёртка → фокус → Ctrl+G в активный render-loop → мгновенная обработка.

## Мобильный мирор (Run after с телефона)

Десктопный store — **единственный источник authoring**, App-root runner — **единственный движок**. Legacy `getPromptQueue`/`mutatePromptQueue` сохраняются. Capability `runAfter.version:1` добавляет guard/receipt adapter над теми же owners, а не ordinary Send FIFO вместо RunAfter. Owner очереди — Claude/Codex PTY, включая fresh/stopped конфигурацию; SDK/Gemini допустимы как dependency targets. Отсутствие overlay не влияет на работу, отсутствие Root bridge — явная недоступность, не пустая очередь. Полный remote-контракт — `fact-mobile-web.md::RunAfter v1: удалённое редактирование и квитанции`; native подключается после проверки capability, наличие source не означает install.

Строгая mutation сначала связывает epoch/owner/order/revision и прежний editor-lock, затем сохраняет store snapshot и operation receipt одной SQLite-транзакцией. Timeout/restart не доказывает отказ: same-ID читает прежнюю запись без повторного действия. Replay переносит полный immutable text/chips/images в phone draft, не в Mac composer и не через Enter; snapshot и leases удерживаются до conditional assetDisposition или explicit discard. Historical mobile receipt не покрывает managed Replay refs и не заменяет current bytes owner. У передачи в FIFO защищён completion→canonical sidecar gap; у add/update item bytes остаются в прежнем journal до exact item→FIFO либо явного изменения refs. Контракт и границы — `fact-mobile-web.md::Replay: условная передача bytes без второго владельца`. Литералы/GT paths не становятся разрешением импорта: новые images принимаются из mobile upload owner либо по уже owned assetId. Отдельного filePaths/document-codec в RunAfter нет; это не ограничивает ordinary Send attachments.

Send-now и явный AutoCompact остаются прежними сценариями с последними physical guards. Admission и settlement различны: собственный первый Send/Resume может поменять writer после допуска, но его историческая квитанция не должна зависеть от последующей current-сессии. Это не даёт старой операции права нового ввода; исход без proof остаётся unknown. AutoCompact request/cancel дополнительно пинят выбранную вкладку, cancel — exact activityId; global policy не подменяется карточкой Compact50. Общий Loop сохраняется каноническим System Prompt до публикации, не запоздалым queue debounce.

Для title/body split bridge обязан передавать optional `title` / `titleManual` вместе с core item и update-op. Мобильный список показывает title или fallback, но не запускает AI-title сам и не пересчитывает runner-логику: desktop store остаётся owner'ом правил `titleManual`, AI-generation и remove/replay semantics. Если добавляется новое persistent-поле queue item'а, проверяй сразу три слоя: desktop store, `App.tsx::mutatePromptQueue`, `mobile-web/src/api.ts` + render fallback.

## Что пробовали и почему отбросили

- **Ctrl+C для clear input** — single press в Claude TUI = "clear input" но **также** взводит "Press Ctrl-C again to exit" danger zone. Race: если в момент клика юзера на + grab юзер случайно дёрнет Ctrl+C через keyboard — два подряд → exit Claude. Стало через external editor mode=clear — безопасно, не трогает stdin keystrokes.
- **`/edit` slash command** — нет такого в Claude Code (`packages/claude-code-src/commands/`). `/copy` и `/export` работают над assistant response, не над draft.
- **Stash flow (Ctrl+S)** — кладёт draft в `stashedPrompt` slot, инпут визуально пуст. Но stash восстанавливается **при следующем обычном submit** — если юзер потом напишет `hello\r`, Claude вернёт `<stashed>` + `hello`. Не работает для нашего случая.
- **Double Ctrl+S (stash → pop)** — `handleStash` bi-directional, второй Ctrl+S попнет stash **в инпут**, не очистит. Тупик.
- **Auto-runner внутри PromptQueueOverlay компонента** — первая реализация. Слушал `claudeBusy` prop, делал `wasBusy → !claudeBusy` edge detection через `useRef`. Падало когда юзер переключался на другой таб: overlay unmount'ится по гейту `effectiveActive`, runner с ним умирает, следующий busy→idle transition в фоне не ловится. Переехал в `usePromptQueueRunner` hook на App root. Урок переносимый — любой listener для **глобальных** событий (IPC от main, OS-level signals) не должен жить в gated-by-active-tab компонентах. См. `methodology/дизайн-принципы.md::Singleton listener для global events, не в conditionally-rendered компонентах`.
- **Silent 3s timeout без specific error code** — был один код `editor_not_wired` на ВСЁ что пошло не так после `term.write('\x07')`. Helper не запустился, ppid не сматчился, socket упал — всё превращалось в одинаковый toast «Helper not reachable» через 3 секунды. Юзер не знал что делать. Прод-лог за 13:20-13:21 показал что одинаковый симптом приходил из **двух** разных источников (мёртвый cached PID + слишком ранний клик после spawn) — оба молчали 3 секунды и оба выдавали тот же toast. Фикс: `stale_pid` отдельным кодом с прямой инструкцией «close & reopen this tab». См. [`fix-prompt-queue-stale-pid.md`](fix-prompt-queue-stale-pid.md), общий принцип — `methodology/дизайн-принципы.md::Cached external resource: alive-probe перед использованием`.
- **Per-chunk `waitForRender` на slow-mode paste из очереди** — давал 57с гэп между cold-start `popNext()` и фактическим UserPromptSubmit для 50KB payload (56 чанков × 1000ms timeout). Юзер думал что очередь сломана. Root cause: Ink батчит рендеры до `\x1b[201~`, sync marker эмитит один раз в конце, не на каждом промежуточном чанке. Фикс: single write для slow-mode (chunks.length === 1 by construction), один post-write `waitForRender`. См. [`fix-claude-paste-stuck-queue.md`](fix-claude-paste-stuck-queue.md).
- **Stash-detect через `tail.slice(-40)` + `stripVTControlCharacters` + `.includes('Stashed (auto-restores after submit)')`** — первая реализация helper'а который ждёт появления stash-маркера в output buffer перед тем как считать команду применённой. Поймала задокументированный Ink-баг сразу (см. `fact-claude-tui-control.md::Ink TUI: пробелы как ANSI-команды`): Ink эмитит inline-пробелы как `\x1b[<N>C` (cursor-forward escape), `stripVTControlCharacters` сносит их вместе с реальными ANSI-кодами → литерал склеивается в `"Stashed(auto-restoresaftersubmit)"`, `.includes` не матчится. Плюс маркер может лечь через границу `data.split('\n')` (две физические строки в одном PTY chunk'е), плюс длинный стрим assistant-ответа выталкивает stash-маркер за хвост 40-строчного окна. Фикс: сканируем **весь** `terminalOutputBuffer` (cap 500 строк — bounded, не растёт бесконечно), join → один strip-pass → tolerant regex `/Stashed\s*\(\s*auto-restores\s*after\s*submit\s*\)/`. Регекс с `\s*` терпит и схлопывание пробелов после strip, и сохранившиеся реальные пробелы — оба варианта валидны.
- **Pre-block grab по `claudeSpinnerBusy`** — первая попытка фикса misleading `editor_not_wired` toast'а во время стрима. Логика: если Claude стримит ответ, Ctrl+G no-op'нется в TUI (`chat:externalEditor` binding неактивен mid-turn) → helper не запустится → timeout → красный toast. Решение «не пускать grab вообще пока spinner busy» казалось правильным. Юзер прямо возразил: *«нет, +grab наоборот должен работать когда стриминг — это и есть его смысл, поставить промпт в очередь пока Claude думает»*. Откатили pre-block, остался только hook-confirmed `claudeTurnBusy === true` (короткое окно когда Stop hook ещё не пришёл). Замена для misleading toast'а — diagnostic-on-timeout: snapshot'им size `/tmp/noted-grab-helper.log` ДО `term.write('\x07')` и после 3с timeout. Если log не вырос — helper не запустился (Ctrl+G ate by TUI) → resolve `claude_busy` toast «Claude is busy…». Если log вырос — helper отработал но не достиг socket → `editor_not_wired` остаётся. См. `methodology/дизайн-принципы.md::Action валиден mid-state — не блокировать по чужому busy-флагу` и `methodology/дизайн-принципы.md::Diagnose with instrumentation, not guesses`.

## Атомарная вставка больших блоков

В composer текст маркера и identity его скрытого тела меняются одной операцией.
Это обязательно и для Replay, и для обычной вставки: сначала вычисляется новая
строка и одновременно новый порядок карточек, затем оба состояния публикуются
вместе. Поиск тела только по длине или по отдельному проходу маркеров запрещён —
два равных блока иначе могут поменяться содержимым. Замена выделения удаляет
только карточки, чьи маркеры действительно попали внутрь заменённого диапазона;
коллизия ID получает новый ID до публикации.
