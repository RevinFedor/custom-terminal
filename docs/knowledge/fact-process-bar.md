# Feature: Tab Process Bar (PTY-alive indicator)

## Intro
3px цветная полоска у одного из краёв вкладки в vertical layout. Появляется когда жив PTY-процесс (claude CLI, npm run dev, bash, gemini/codex) **или** AI стримит (`isBusy`); для SDK-табов аналог process-alive даёт `sdkProcessAlive`. Process-alive сигнал — статичный `colorA`, AI-busy сигнал — настраиваемый блик (`shimmerColor` + opacity + spacing) внутри той же полоски. Это **единственный** busy/process-индикатор: бывший фон-пульс всей вкладки (`tab-ai-busy-shimmer`, фича AIPulse) удалён целиком, см. секцию «AIPulse removed» ниже.

## Data model

```ts
ProcessBarSettings = {
  colorA: string,              // базовый цвет process-alive полоски
  shimmerColor: string,        // цвет блика поверх полоски
  shimmerSpacingPct: number,   // расстояние между бликами, clamp 20..200
  shimmerOpacityPct: number,   // прозрачность центра блика, clamp 5..100
  position: 'left' | 'right',
}
```

localStorage ключ `noted-terminal-process-bar`, дефолт `colorA: #155E75, shimmerColor: #FFFFFF, shimmerSpacingPct: 50, shimmerOpacityPct: 55, position: left`. Legacy `enabled/colorB/durationMs` больше не мигрируются в UI-смысл: пульса нет, второй цвет стал самостоятельным цветом блика только после явного выбора юзером.

## Дефолтная палитра — приглушённый cyan + белый блик

Базовая полоса — cyan-800 (`#155E75`), блик по умолчанию белый (`#FFFFFF`) с opacity 55%. Cyan выбран как промежуточный hue между зелёной и синей зонами палитры, чтобы НЕ конфликтовать:
- `#10B981` emerald (knowledge sessionStatus) — более зелёный, чем cyan
- `#4E86F8` blue (gemini brand) — более синий, чем cyan
- `#22C55E` lime (devServer brand) — холоднее-светлее

Юзер: *«полоска вертикальная сейчас выглядит очень плохо»* — первая версия была белая (`rgba(255,255,255, .18 ↔ .85)`), пульсировала через всю яркость от приглушённой до почти полного белого + box-shadow glow. Воспринималось как «вспышка», конкурировало по вниманию с самим содержимым таба. Пульс позже убрали целиком: process-alive должен быть стабильным маркером, а движение принадлежит только loader-блику.

## Полоска ловит два сигнала: PTY-alive + AI-busy

Полоска рендерится при `hasProcess || isBusy`. Внутри неё одновременно живут два независимых индикатора:

1. **Process-alive (`hasProcess || sdkProcessAlive`)** → статичная `colorA` полоска. Это исходный режим для claude/gemini/codex CLI, npm run dev, bash и SDK runtime.
2. **Работа вкладки** → полупрозрачная просвечка `shimmerColor` ползёт сверху вниз поверх цветного фона. Сигнал `claude:busy-state`/`gemini:busy-state`/`codex:busy-state`/`claude-sdk:busy-state` плюс подготовка/физическая отправка Claude/Codex. Пассивная сверка доставки не считается работой модели.

У Claude локальная операция и новый ответ могут пересечься: поздний cleanup
старого `/compact` не означает, что новый ответ закончен. В local-command IPC
`busy/reason/localCommandReason` сохраняют исход именно этой операции для
автоматизации. Рядом main передаёт `activityBusy` из того же текущего presence,
который читает History: настоящий turn плюс ещё активная локальная операция.
Навигационные потребители читают его через `resolveAgentBusyPresentation`;
при отсутствии поля действует прежний `busy` (другие providers/старый main).
Значение `false` тоже явное, его нельзя заменять через `activityBusy || busy`.

Это закрывает production-порядок «новый UserPromptSubmit → cleanup старого
compact»: raw `busy=false` остаётся точным окончанием локальной операции,
а `activityBusy=true` сохраняет shimmer вкладки, счётчик workflow/Dock и
открытый activity interval ответа. Настоящие turn-end события и successful
compact outcome для Run after не подменяются визуальной суммой. Source repair
11.09 проверен чтением и синтаксисом; повторная physical-приёмка ещё открыта.

Исторически для устранения96ms-разрыва paste→busy (Inbox tab102,09.09)
в общий loader включили весь `audit-pending`. Инцидент23.09 tab171 показал,
почему это неверно: ответ завершился, пользователь скрыл CONFIRMING, но
неопознанная квитанция пяти изображений бесконечно удерживала shimmer при
правильном `turnBusy=false`. Скрытие сообщения не меняет исход доставки.

Текущий контракт23.09: общий sending-признак охватывает принятую подготовку,
`in-flight` и `enter-armed`. После физической передачи пассивный audit/очередь
остаются статусом конкретного сообщения; движение модели доказывает её busy.
Main передаёт точные tab/handoff фазы, чтобы отпустить также локальный
composer/scenario promise, ещё ожидающий ответ IPC. Старый handoff не снимает
подготовку нового; поздний receipt не воскрешает shimmer после завершения.
Workflow, обе ориентации вкладок, pane header и Dock используют одну проекцию
без таймера. Короткий промежуток до provider busy не заполняется выдуманной
активностью из квитанции. Cold Start/Resume сохраняет feedback подготовки;
reserved/preparing без выполняемого сценария сам по себе не означает работу.

Это только отображение: send-pending не становится provider busy, запретом ввода,
сигналом для Stop/Run after или доказательством SENT. В частности, нельзя удерживать
`paste-busy` до JSONL ради красивого loader — это продлит чужую блокировку записи.

Если живы оба — статичная полоса и блик идут одновременно. Если только AI без process-alive — полоска всё равно появляется со статичным `colorA`, по ней ползёт блик. Если только процесс без AI — только статичная полоса. `overflow:hidden` держит shimmer строго внутри полоски.

Наследованная orchestration-активность использует ту же геометрию, но отдельный базовый `inheritedColor`: так пользователь отличает собственный busy вкладки от ожидания дочерней ветки. Сигнал не обрывается на terminal-state ребёнка: он продолжается во время точного result-proof и source-handoff до post-Enter proof completion-сообщения, затем без искусственного idle-gap переходит к обычному busy родителя. `waiting_recovery` и ошибка доставки остаются completion/install-blocker'ами, но не являются продолжающейся работой и поэтому не рисуют inherited shimmer; их состояние объясняет orchestration-card. При этом `inheritedBusy` не подменяет runtime busy для Stop/input, но участвует в общем completion-gate семейства Run After.

Движение inherited-полосы остаётся тем же общим shimmer и питается `shimmerColor`. Эти два цвета нельзя связывать одним значением: доказанный дефект задавал `--process-bar-inherited-shimmer-rgb` равным фиолетовому фону, поэтому overlay и `background-position` существовали, но пиксели не менялись. База отвечает за тип активности, контрастный overlay — за факт, что она продолжается.

## AI-busy блик (light-overlay поверх цветной полоски)

Блик теперь configurable: пользователь отдельно выбирает `shimmerColor`, `shimmerOpacityPct` и `shimmerSpacingPct`. Это появилось после живого симптома: выбранный красный блик выглядел не красным, потому что прозрачность была зашита слишком высокой. Цвет без opacity-контрола не даёт пользователю предсказуемого результата.

**Эволюция подходов к continuous flow.** Сначала был один overlay translateY `-100% → 250%` — пик внутри полоски ~70% цикла, остальные 30% его не видно → юзер читает как «лоадер прыгает». Потом два overlay'я с `animation-delay: -0.6s` — на широких частях периода юзер видит **ДВА блика одновременно** (один уходит снизу, второй уже появился сверху), это уродует визуал в узкой 3px полоске. Потом repeat-y gradient с pattern 200% и пик на 50% — на стыках tile'ов 60% pattern имело alpha 0 подряд (хвост tile_n + начало tile_n+1), пик надолго пропадал.

Текущий вариант — **seamless wrapping gradient**: один `.tab-process-bar-ai-shimmer-overlay`, `background-repeat: repeat-y`, `background-size: 100% var(--process-bar-shimmer-spacing)`, пик на 50% tile, edge-alpha = `shimmerOpacityPct * .22`. На стыках двух tile'ов alpha с обеих сторон одинаковая → нет тёмной паузы, есть мягкий valley между движущимися пиками. `background-position 0 → 100%` за 1.2s сдвигает на один tile, конец цикла визуально идентичен началу благодаря repeat-y. Юзер: *«прерывается на долю секунды во время лоудера когда заходит в конце и появляется в начале»* — этот шов теперь физически отсутствует.

Один overlay (`.tab-process-bar-ai-shimmer-overlay`), никаких secondary-инстансов. Если в будущем нужно убавить общий glow — снижать `shimmerOpacityPct`, не менять geometry.

## Claude spinner — только диагностика, не состояние

Claude PTY spinner остаётся внутренней эвристикой экрана: он полезен для логов,
watchdog-диагностики и консервативной защиты записи в input, но не является
границей хода. Glyph может исчезать между кадрами и снова появляться через
400–500 мс даже при неизменном состоянии Claude. Таймер сглаживания не решает
эту проблему, а лишь переносит гонку на другую длительность.

Main поэтому не публикует spinner как `claude:busy-state`, не открывает по нему
таймер ответа и не включает его в Terminal MCP / `/api/active-loaders`.
Process-bar, проектный индикатор, History, Run After и ControlBar используют
только принятые для текущего main-owner `UserPromptSubmit → busy`,
`Stop`/`StopFailure → idle`, а также явно
ограниченные операции local-command/compact/paste. Renderer дополнительно
игнорирует legacy-событие `reason:'spinner'`, чтобы hot reload старого main не
мог вернуть дребезг. См. `fact-prompt-queue.md::Auto-run стреляет ТОЛЬКО на
штатный конец turn'а` и `methodology/дизайн-принципы.md::Один сигнал
состояния — все его поверхности`.

Совпадения session/PID недостаточно для конца Claude turn: subagent делит их
с родителем. Ошибочный parent idle одновременно гасит карточку и ControlBar,
даже когда сеть и tools ещё работают; исправлять нужно admission hook-события,
не добавлять отдельный визуальный busy. Граница — `fact-claude-stop-hook.md::Один session/PID не означает один ход`.

## CSS-var bridge (live-tunable анимация)

`App.tsx` синхронизирует на `document.documentElement.style`:

- `--process-bar-color-a`
- `--process-bar-shimmer-rgb`
- `--process-bar-shimmer-spacing`
- `--process-bar-shimmer-alpha`
- `--process-bar-shimmer-edge-alpha`

Все instance'ы полоски (табовая, проектная, mobile-web mirror) автоматически перестраиваются без props-propagation. Юзер двигает color picker / opacity input → CSS-переменные подхватываются следующим кадром.

**Почему не inline-style на каждом узле:** была бы props-цепочка `useUIStore → TabBar → TabItem → div.style`, плюс memo invalidation на каждый picker-tick. С :root variables — одно DOM-mutation на изменение Settings, никаких React-перерисовок.

## ProcessBar position toggle

`position: 'left' | 'right'` — рисуется у левого или правого края вкладки. Для левого края применяется `left: -2px`; для правого — `right: 0`. Закругление углов только на «своей» стороне (`borderTopLeftRadius` или `borderTopRightRadius`). Юзер: *«добавь также тогл переключатель, чтобы она отображалась справа вкладки в правом конце»*.

**Почему слева `-2px`, а справа `0`.** Сама вкладка имеет `border-left: 2px solid transparent` (резерв под dashed-states selected/interrupted чтобы все табы не дёргались по ширине при включении выделения). Абсолютные дети с `left: 0` позиционируются от **padding-edge**, не от outer perimeter — отрисовываются ВНУТРИ border-area, между transparent border'ом и контентом. Визуально это даёт 2px зазор между полоской и реальным левым краем карточки. Фикс слева — `left: -2px`, полоска занимает border-area целиком.

Справа такого transparent border нет. Старый симметричный `right: -2px` у visual-child вкладок выталкивал полоску за правую границу меню: child-row уже смещён вправо через indent, и лишние 2px оказывались за контейнером. Поэтому right-position anchored как `right: 0`, а visual-child wrapper получает `width: calc(100% - indent)` + `boxSizing: border-box`: вся вложенная карточка с process-bar остаётся внутри правой границы sidebar.

Маркер sessionStatus всегда слева независимо от bar-position — потому что слева удобнее читается рядом с текстом названия вкладки. Если bar тоже слева — между ними 2px зазор; если bar справа — слева остаётся padding под маркер.

## Restart button stop-mode для devServer

В vertical layout process-bar остаётся **только** индикатором process-alive / AI-busy, не stop hit-zone. Stop для зелёной devServer-вкладки живёт в той же правой кнопке, которая обычно делает restart: bare hover показывает обычный `RotateCw`, `Cmd+hover` превращает **эту же кнопку с тем же местом и background'ом** в красный `Square`, click отправляет deterministic stop (`Ctrl+C`) без restart и без `!!`. Отдельную stop-кнопку рядом с вкладкой не добавлять: пользователь видит два соседних destructive/restart affordance и не понимает, какой из них главный.

Причина: в vertical sidebar middle-click по всей вкладке уже имеет стандартную семантику close tab, а отдельная edge-hit-zone конкурировала с process-bar как чистым индикатором. Horizontal fallback всё ещё использует `RestartZone` с middle-click stop; vertical sidebar использует modifier-mode на inline reload button. Это локальное применение общего принципа `methodology/дизайн-принципы.md::Modifier-mode на существующей action surface`.

Та же кнопка показывает настроенный `Restart after`: если у вкладки есть `restartAfterTabIds`/legacy `restartAfterTabId` или `restartAfterCommand`, она рендерится фиолетовой даже когда `hasProcess=false`. Это не live process-strip и не означает что dev-server сейчас запущен; это marker будущего автоперезапуска после AI-trigger. Обычный click запускает выбранный script или fallback last-command вручную через тот же `Restart after` path, а `Cmd+click` очищает restart-after подписку без Stop side effect. Красный Cmd+hover Stop остаётся только для обычной зелёной devServer-вкладки без restart-after подписки.

## Settings UI (правая колонка 2-column grid)

- Compact превью полоски 32px высотой с реальной анимацией (использует локальные CSS-vars в `style={{['--process-bar-color-a' as any]: ...}}`, не зависит от :root — превью обновляется ДО того как App-effect синхронизирует root)
- Position toggle (`⊏ слева` / `⊐ справа`) inline в одной строке
- Compact color-rows для «Полоса» (`colorA`) и «Блик» (`shimmerColor`)
- «Расстояние» — number input для `shimmerSpacingPct`
- «Плотность» — number input для `shimmerOpacityPct`

Toggle «Пульс», второй цвет как pulse-phase и «Цикл» удалены: в реальной модели нет пульсации, есть переливание блика. Держать старые контролы опасно — пользователь меняет настройку и не получает ожидаемого эффекта, потом диагностирует не тот слой.

## AIPulse removed — лоадер это полоска, не фон всего таба

**Фича AIPulse (`tab-ai-busy-shimmer`/`-static`, пульс фона ВСЕЙ карточки таба) удалена целиком.** Юзер: *«если в настройках есть что-то что отвечает за изменение бэкграунда всего таба во время работы — удали это нахуй; лоадер у нас отвечает переливающаяся полоска слева или справа»*. Единственный AI-busy / process-alive индикатор теперь — **process-bar полоска у края** (этот файл, секции выше): статичный базовый цвет пока жив процесс, настраиваемый shimmer-overlay ползёт по ней пока AI реально стримит.

Что снесено (5 точек, искать если всплывёт): `AIPulseSettings`/`aiPulse`/`setAiPulse`/`loadAIPulse`/`saveAIPulse` в `useUIStore.ts`; `--ai-pulse-*` :root-effect в `App.tsx`; `tab-ai-busy-*` render-блок в `TabBar.tsx`; `@keyframes tab-ai-busy-pulse` + `.tab-ai-busy-shimmer/-static` в `globals.css`; `AIPulseEditor` + «Фон AI-загрузки» секция в `SettingsModal.tsx`. Никаких importers не осталось.

Исторический контекст (почему вообще была): сначала был sweep-шиммер (горизонтальная полоса 60% ширины через `translateX`), потом фон-pulse всей карточки — юзер тогда просил *«сделай пульсацию фона»*. Теперь решение откатано в пользу полоски-у-края: фон-tint всего таба конкурировал с текстом за внимание, лоадер должен быть локализован в полоске.

## Mobile-web зеркалит полоску (process-bar = лоадер на телефоне)

Mobile-web tab-row рисует **ту же полоску-лоадер** у края строки (`ProcessBarStrip` в `mobile-web/src/App.tsx`). Конфиг (`colorA/shimmerColor/shimmerSpacingPct/shimmerOpacityPct/position`) приходит из desktop `useUIStore.processBar` через тот же канал что `statusMarker`/`statusColor`: `GET /api/projects/:id/tabs` отдаёт top-level `processBar`, оба пути (DB-path web-server.js через bridge `getStatusMarkerConfig`, live-Zustand-path App.tsx `getProjectTabsLive`) читают `useUIStore.getState().processBar`. **Desktop store = единственный источник правды, мобилка только читает** (юзер: «по-хорошему чтобы хранилось в одном состоянии»).

Маппинг рантайма на полоску: `running` (sessionStatus active/busy или SDK live) → статичная `colorA` полоса. `busy` (turn в полёте) → плюс `.mob-pbar-shimmer` с теми же цветом/spacing/opacity. `position:right` → `{right:0}` + правые радиусы, иначе левые — зеркало desktop edge-anchoring. Строка резервирует `paddingLeft/Right:17` на стороне полоски чтобы текст не лез под неё. Старый whole-row background-breathing (`mob-row-busy`) и правая точка/ring удалены — полоска единственный лоадер, как на desktop. Graceful degrade: старый сервер без `processBar` → дефолт cyan/left.

## Workflow агрегирует процессы реально размещённых вкладок

Runtime aggregation живёт на workflow-row, но directory-project не определяет её адрес. У workflow два независимых runtime badge: зелёный считает живые PTY/SDK процессы вкладок, канонически размещённых в его раскладке; оранжевый считает их turn-busy/paste-busy/inherited-busy. Вкладка чужого project считается там, где лежит её окно, а не у workflow-родителя папки; вкладка без оконного placement остаётся busy только в sidebar. Для дубликата активная раскладка выигрывает, среди dormant — первая сохранённая, поэтому один tab не размножает один сигнал по нескольким workflow. Оранжевый count статичен и обведён плотной рамкой без `noted-shape-ring`: при renderer stall вращение всё равно замирает и выглядит как второй баг, тогда как число уже полностью сообщает факт фоновой работы. Один tab может считаться и зелёным, и оранжевым — «процесс жив» и «сейчас идёт loader» не части одной дроби. Старые текстовые `N ·M` удалены.

Edge-strip (`tab-process-bar-static` + shimmer) по-прежнему принадлежит только session tab и показывает одну вкладку: это локальная поверхность с собственным кадровым циклом, где движение реально различает process-alive и turn-busy. Workflow badges стоят inline в строке `цветная иконка → имя → green active → orange busy`; corner-overlay запрещён тем же layout-шрамом. Project row не получает runtime edge-strip обратно. Красный completion и purple awaiting остаются отдельными сигналами.

## macOS Dock показывает статичный счётчик busy-вкладок

Dock-иконка приложения — глобальная агрегирующая поверхность: она показывает **сколько вкладок сейчас в состоянии loader**, а не сколько вкладок открыто и не сколько процессов живёт в проекте. Источник тот же визуальный busy-сигнал, что у tab/project UI (`busyTabs` + `pasteBusyTabs`): если вкладка уже светится loader'ом внутри приложения, она участвует в Dock-счётчике; отдельный детектор «активности для Dock» не заводить. Фильтр намеренно грубый: открытые не-file tabs по всем открытым проектам, где есть busy/paste-busy.

Визуально это не native macOS badge. `app.setBadgeCount`/native red badge рисует системный красный счётчик в чужой семантике и позиции, а пользователь просил тот же язык что у workflow activity badge: зелёный круг с цифрой. Поэтому renderer рисует base app icon + зелёный bottom-right badge на canvas, main подменяет Dock icon через `app.dock.setIcon(nativeImage)`, а при count=0 сбрасывает icon обратно и чистит native badge. Если будущая правка снова покажет красный top-right badge — это регресс, не fallback.

Анимацию loader вокруг Dock badge не возвращать без отдельного архитектурного решения. Внешний research по Electron/AppKit дал практическую границу: Electron `app.dock.setIcon` заменяет иконку целиком, а AppKit `NSDockTile` custom view тоже требует явного `display()`, это не поверхность с гарантированным 60 fps. Мы пробовали вращающийся loader кадрами поверх иконки; визуально он читался как дёрганность приложения, не как полезный progress. Поэтому Dock остаётся статичным общим статусным счётчиком, а плавная анимация живёт внутри приложения на поверхностях, которые реально владеют кадровым циклом.

## Подписка на переходы без чтения текущего состояния (2026-08-08)

Событие о работе агента приходит **только как переход**: «начал отвечать», «закончил». Поверхность, которая ничего, кроме этих событий, не читает, при монтировании **посреди уже идущего ответа** пропускает начало и до самого конца рисует вкладку спокойной. Симптом характерный: **одна и та же вкладка в один момент времени с лоадером в одном списке и без него в другом**.

Пользователь: *«вкладка отображается и в меню Run after, и в компоненте вкладки как будто там нет loader, хотя лоадер там есть, и в боковом левом меню он отображается»*.

Три места, где это было, и почему каждое ловилось по-своему:

1. **Шапка панели** (`TabSignals::useTabActivitySignals`). Соседний сигнал «процесс жив» честно спрашивал состояние у main при монтировании, а «идёт ответ» стартовал с `false`. Панель открывают посреди ответа — лоадера нет.
2. **Меню Run after** (`RunAfterTabPicker`). Читало единственного свидетеля — карту исполнителя очереди. Тот **намеренно отбрасывает** кадры спиннера и локальные slash-команды: они не границы хода и не должны запускать очередь. Верно для «когда отправлять», неверно для «что рисовать» — вкладка, чья активность состояла только из отброшенного, в эту карту не попадала вовсе. Это худший подвид: подпитка есть, но она уже́ того, что рисуется.
3. **Панель управления** (`ClaudeControlBar::sdkBusy`) — плюс обратная беда. Компонент **переиспользуется** между вкладками (без `key`), соседние флаги там уже сбрасываются на каждую привязку, а этот не сбрасывался: флаг от вкладки A оставался включённым на вкладке B, а «закончил» от A приходил с чужим id и отфильтровывался — лоадер залипал навсегда. И наоборот: привязка во время хода давала `false`, а Stop был завязан на этот же флаг и **молча ничего не делал**.

**Правило.** Стартовое значение берётся из общего признака вкладки `tab.aiBusy` (его поддерживают всегда живые слушатели в `App.tsx` для всех вкладок, независимо от того, что открыто), живые переходы имеют приоритет и накладываются сверху; при смене вкладки накопленный переход обязан сбрасываться, иначе унаследуется чужой. В боковом списке общий признак взят «полом» для всех провайдеров — стартовая синхронизация переспрашивала main только про процесс и про ход Codex, но не про Claude и Gemini.

Проверять это надо **в том же порядке, что и баг**: сначала событие о начале ответа, потом монтирование поверхности. Обратный порядок проходит всегда и не доказывает ничего. И обязательно проверять снятие: «пол» опасен тем, что может не опуститься, а вечный лоадер хуже запоздалого. Живые сценарии — `verify-busy-seed.mjs`, `verify-sidebar-clears.mjs`; чистое правило меню вынесено в `utils/runAfterTabStatus.mjs` (портал живёт только пока открыт — на месте правило было непроверяемым).

## Сигналов у вкладки три, а общий источник знал два (2026-08-16)

Продолжение той же истории, но провал был не в подписке, а в наборе вопросов. Общий источник сигналов (`TabSignals::useTabActivitySignals`) отвечал ровно на два: «жив ли процесс» и «идёт ли собственный ответ». Третьего — «вкладка ждёт сессию, которую сама запустила» — в нём не было вовсе.

Поэтому фиолетовая полоса ожидания была только у карточки в боковом списке: она спрашивала про это отдельно, своим кодом. Все поверхности, построенные на общем источнике, нарисовать её не могли **в принципе**, а не «забыли» — чип в шапке панели и список недавних молчали, пока боковой список для той же вкладки в ту же секунду показывал ожидание. Пользователь: *«тут лоадер вертикальный исправь… фиолетовый лоадер не отображается, который показывает, что вкладка ждёт оркестрацию; у обычной вкладки такое есть»*.

Тонкость в том, что расхождение выглядело как рассинхрон подписок — тот же симптом, что в разделе выше («одна вкладка, один момент, разные списки»). Но подписки здесь были исправны: рисовать было нечем. Лечится не добавлением ещё одного локального чтения в каждую поверхность (так и появилось расхождение), а тем, что вопрос задан один раз в общем источнике; поверхности только передают ответ в полоску.

**Приоритет.** Собственная работа старше ожидания: пока вкладка отвечает сама, полоса её обычного цвета, и фиолетовый возвращается, когда она замолчала, а дочерняя сессия ещё идёт. Иначе фиолетовый закрашивал бы живую работу и сообщал обратное тому, что происходит. Правило одно на все четыре поверхности (`inheritedBusy && !busy`).

Проверено живьём на изолированном инстансе: run приходил тем же событием из основного процесса, что и в жизни. Чип второго окна получил фиолетовую полосу с бликом, соседний остался чистым; во время собственного ответа полоса стала обычной и вернулась в фиолетовую после; переключатель `Ctrl+Tab` и список недавних в шапке панели показали то же; на завершении run'а всё погасло. Пин — `store/tabSignalsInheritedBusy.wiring.test.mjs`.

## Карточка вкладки: один набор правил на все поверхности (2026-08-08)

Карточку вкладки рисуют четыре места: боковой список, шапка панели, переключатель `Ctrl+Tab` и меню Run after. Каждое завело собственную копию трёх решений — какого размера, какого цвета и что делает наведение, — и копии разошлись, каждый раз незаметно в коде и очевидно на экране:

- **шапка при наведении заливала вкладку белым поверх её цвета.** Зелёная вкладка становилась блёкло-зелёной и читалась как другой элемент. В боковом списке правило другое и правильное: наведение делает **свой** цвет вкладки ярче (`+0.08` прозрачности), а не закрашивает его. Пользователь: *«при наведении на этот блок другая анимация, какая-то полузелёная»*;
- **размер не совпадал**: 21px высоты при шрифте 11.5 в шапке против 27px при 14 в боковом списке — одна и та же вкладка выглядела двумя разными объектами рядом;
- **шапка обрезала своё содержимое** (`overflow: hidden`), поэтому полоса задач не могла выйти за нижний шов: квадратики подрезались вровень и читались как строка внутри чипа, а не как отметка границы.

Правила вынесены в `utils/tabCardVisual.mjs` (`resolveTabCardBackground`, `resolveTabCardTextColor`, `resolveTabCardMetrics`) — чистые функции, проверяемые без DOM. Размеры и шрифт берутся из тех же настроек, что у бокового списка (`tabGeometry`, `tabsFontSize`), поэтому правка в Settings → Размеры двигает обе поверхности сразу.

**Про полосу задач.** Её отступ снизу **отрицательный** — квадратики седлают нижнюю границу, в этом весь смысл: полоса, целиком лежащая внутри карточки, ничего не отмечает. Величина свеса считается из зазора между карточками минус запас, чтобы никогда не дотянуться до соседней. При нулевом зазоре свес обнуляется — и именно `0`, а не `-0`: голое отрицание даёт `-0`, которое доезжает до CSS строкой `-0px`.

**Ловушка проверки.** Скрытое окно не рисует кадры, и `getComputedStyle` продолжает отдавать последнее **нарисованное** значение — измеренный цвет расходится с заданным, и это выглядит как «правка не применилась». Проверять надо inline-стиль (что React реально решил) либо будить окно; замер `requestAnimationFrame` в таком окне зависает на ~1.8 секунды и сам по себе является диагнозом.

## Codex Fast — молния на ВЕРХНЕМ конце полоски (2026-08-17)

Приоритетный тариф Codex (`/fast`) виден на карточке вкладки: жёлтая молния, тот же контур, что у кнопки Fast в панели управления (`TabFastBadge` в `TabSignals.tsx`).

**Почему на конце полоски, а не значком в строке названия.** Полоска процесса — единственный элемент карточки, который принадлежит только ей и тянется на всю высоту. Молния на её конце читается как свойство ЭТОЙ вкладки; ещё один значок в общей строке названия читался бы как кнопка. Держится за тот же край, что полоска: при переносе полоски в настройках направо переезжает вместе с ней, иначе оказалась бы на противоположном краю от того, что подписывает.

**Принадлежность важнее размера.** Значок стоит у ВЕРХНЕЙ границы и выходит наружу лишь частью высоты (30%, верх названного пользователем диапазона 20–30%). Серединой на шве было бы не понять, чей он — верхней вкладки или нижней.

**Выступ ограничен зазором между карточками, и это не перестраховка.** Зазор настраиваемый (Settings → Размеры, 0–16px). При зазоре меньше выступа значок заходил на ПРЕДЫДУЩУЮ вкладку — замерено: при зазоре 0 накрывал соседа на 3px, при 2 — на 1px, то есть возвращалась ровно та неоднозначность, из-за которой значок и не ставят серединой на шов. `tabFastBadgeOutsidePx()` берёт минимум из желаемого выступа и доступного зазора; при нулевом зазоре выступа нет вовсе.

**Состояние берётся ТЕМ ЖЕ резолвером, что кнопка в панели управления** (`resolveCodexFastModeState`). Тариф принадлежит конкретному writer'у, и после смены сессии старое доказательство силы не имеет — два независимых вычисления «включён ли Fast» разошлись бы на первом же таком случае. На недоказанном состоянии значка нет вовсе: соврать «Fast выключен» так же плохо, как соврать «включён». Контракт в `utils/tabFastBadge.test.mjs`.

## Заполнение контекста — число в правом НИЖНЕМ углу (2026-08-17)

Та же механика, что у молнии Fast (`TabContextUsageBadge`): абсолютная позиция у угла, часть высоты снаружи, выступ ограничен зазором между карточками. Отличается угол (низ вместо верха) и содержимое — число вместо глифа. Кегль 10px, моноширинные цифры, `line-height: 1`.

**Цвет и формат — в общем модуле** `utils/contextUsageMeter.mjs`, из которого их берёт и панель управления. Два независимых порога рано или поздно показали бы один и тот же контекст разными цветами: в панели ещё зелёный, на карточке уже жёлтый — это хуже отсутствия цвета, пользователь перестаёт верить обоим. Прежняя тройная тернарка в `ClaudeControlBar` удалена.

**Знак процента опущен в числе, но оставлен в подсказке.** В углу карточки он не добавляет смысла, а места занимает как цифра — при 100 это разница между «влезло» и «вылезло». Значение зажато сверху 999: оно приходит извне, и трёхзначным обязано остаться. Замерено на зазорах 0/2/4/8/16 и при полоске процесса с обеих сторон: 3-значное не выходит за правый край, не наезжает ни на полоску, ни на молнию, ни на соседнюю карточку.

**Нет измерения — нет числа, а не ноль.** Ноль означал бы «контекст пуст», тогда как настоящий смысл — «данных ещё нет» (сессия не сделала ни одного хода).

**Стартовое значение читается из SQLite, а не ждёт события** — та же ловушка «стартового значения», что у `useTabActivitySignals`: события несут только изменения, и у вкладки, чей ход прошёл раньше или чей процесс закрыт, число не появилось бы никогда. Слушаются все три канала (`claude:bridge-update`, `codex:context-update`, оконное `sdk-context-update`): подписка на один даёт пустой угол у части вкладок.

Обе метки — и молния, и число — стоят и на карточке бокового списка, и на чипе в шапке панели сплита, одним компонентом. Контракт в `utils/contextUsageMeter.test.mjs`.
