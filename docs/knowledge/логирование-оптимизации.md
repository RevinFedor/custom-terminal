# Логирование оптимизации

## Зачем нужен внешний журнал

Пользователь работает обычным образом и сообщает время сбоя через несколько
дней. Ручной `ps` после жалобы не восстанавливает распределение CPU во время
неё: при разборе 11.09 одновременно встречались собственная нагрузка Noted и
отдельные пики OrbStack. Даже успокоившийся позже внешний процесс не доказывает,
что он не мешал раньше. Логи renderer приходят после разморозки; наблюдатель
должен продолжать измерение вне его event loop.

## Что остаётся после события

Source-контракт 11.09: существующий watchdog собирает native CPU-счётчики
процессов текущего пользователя и общий CPU системы. Дельты берутся за один
реальный монотонный интервал; новый или переиспользованный PID не получает
вымышленного нуля. `100%` у процесса означает одно ядро, у `systemBusy` — весь
CPU. Недоступные системные процессы и процессы, родившиеся и завершившиеся
между снимками, остаются слепой зоной. Возраст привязки PID к вкладкам сохраняется.

**Единицы исправлены 14.09:** прежний native-source принимал Mach ticks за ns,
поэтому все per-process `appCpu/tabCpu/rows` были занижены. На исследованном
M1 Pro отношение равно 125/3; маленькие значения в старых журналах не являются
доказательством простоя. Новый source нормализует время ровно один раз, frame
и 30-секундный checkpoint сохраняют `cpuTimeNormalization`, строка лога —
`cpuUnit/timebase`. `systemBusy/systemPeak` из `os.cpus()` отдельные и этой
ошибкой не затронуты. Проверка единиц и предел поправки старых округлённых
чисел — [ресурсная панель](fact-resource-usage-panel.md#загрузка-процессора-только-из-двух-замеров).

С30.09 каждый interval/checkpoint отдельно сохраняет `appCpu` (прямые Electron
процессы), `appChildCpu` (служебные потомки без tab binding), `tabCpu` и
`externalCpu`, плюс `cores`. Группы считаются до отсечения top rows. Процесс
вкладки и Docker не превращаются в CPU renderer; высокая внешняя нагрузка и
лишняя работа приложения могут присутствовать одновременно. Для вывода нужна
та же временная граница, не текущий Activity Monitor после вчерашнего события.
`external` означает отсутствие процесса в известном дереве Noted, а не
доказанную независимость нагрузки: Docker-daemon мог обслуживать команду из
нашей вкладки. Фоновый сигнал только системного CPU без Electron hotspot не
расходует профиль Noted (`system-pressure-no-electron-hotspot`); настоящий
медленный UI-жест всё равно проходит отдельную responsiveness-политику.

`[Perf:SystemPressure]` раз в30с читает только OS query (`sysctl` и `vm_stat`)
вне main/renderer. Он сохраняет raw pressure level, сжатую физическую/логическую
память, занятый swap и прирост swap/page counters, время/цену измерения. CPU frame
содержит возраст последнего memory sample. Мало свободной RAM не называется
memory pressure; page-in не называется swap-in, накопленное за boot число не
выдаётся за текущую скорость. Reset, частично недоступный счётчик и не-macOS
остаются явными unknown/partial. Эти поля объясняют условия, а не автоматически
назначают виновника задержки. GPU-process CPU также не равен загрузке видеокарты.

Постоянный сбор раз в 2с не запускает `ps`, не читает аргументы команд и не
гоняет список процессов через renderer. Каждые 30с сохраняются средние/пики
всего окна наблюдения, а не один случайный снимок. У инцидента есть подробная
минута до сигнала, 20с после, PID/type/tab, состояние видимости и heartbeat.
Записи живут рядом с production.log в `perf-incidents/`, поэтому ротация лога
или очистка `/tmp` их не стирает. По прямому решению пользователя10.10 общий
бюджет —5GiB. Обычные записи, causal journal, метаданные и короткие native-стеки
живут до7суток; CPU-профили, browser trace и любой файл от8MiB —до24ч.
При заполнении бюджета сначала удаляются просроченные, затем тяжёлые и старые
артефакты. Журналы
пользователя и неизвестные файлы этой очистке не принадлежат.

Сигналы инцидента: UI EventTiming от120мс, остальные delayed input/LongTask от250мс, отсутствие heartbeat
(main 500мс, focused renderer 750мс, видимый нефокусный 1500мс), либо минимум
6с нагрузки Noted от 80% одного ядра / системы от 90%. Новый подробный пакет
для фонового CPU создаётся не чаще раза в10минут, для responsiveness —30с;
активное20с окно объединяет новые события и считает неуместившиеся. Обычные
CPU/native/UI-измерения продолжаются между пакетами.

Не более четырёх раз за скользящие сутки запускается тяжёлый
10-секундный профиль main/renderer JS плюс browser trace. Из четырёх слотов
фоновой sustained-CPU нагрузке доступны максимум два; два остаются для
responsiveness. Cooldown10минут считается по этой группе. Все причины
(`startup-warmup`, `reserved-for-responsiveness`, `capture-group-cooldown`,
`rolling-quota-exhausted`, merge/incident-window cooldown) и следующий доступный
wall time идут в `[Perf:CaptureDecision]`; повторный skip имеет счётчик.
Лимит переживает
перезапуск и восстанавливается со временем. До09.10 этот же отказ ошибочно
блокировал внешний native sample: у двух реальных Main stalls стек не сохранился.
Первая минута startup не
запускает тяжёлую запись. Trace ограничен буфером 8MiB, экспортом 16MiB;
потеря данных, занятый DevTools, ошибка/опоздание захвата записываются явно.
С30.09 JS sampling1мс; профиль пишет triggerStart/end, start-ACK metadata,
`triggerOverlap=trigger-already-finished|partial|unknown`, полноту экспорта и
peak buffer. Начатый после жеста профиль нельзя выдавать за стек этого жеста.
`rendererStartedAbs/mainStartedWallMs` нынешнего collector записаны ПОСЛЕ
await Profiler.start и не являются точным raw началом capture. Для coverage
сопоставлять raw profile startTime/endTime с native timestamp/query brackets
и UI *Abs; Date.now/печатный timestamp могут иметь иной offset. Первый большой
timeDelta до первого sample — слепой стартовый интервал, не доказательство
всей его работы под первым (program)/inspector frame. Полнота CPU profile не
означает полноту trace: при обрезанном JSON декодировать полный префикс и
сначала проверить его последний native interval относительно нужного action.
Занятый своим другим capture также оставляет явный profile status.
Профилировщик не поднимает окно и не отбирает существующий debugger/trace.
Он не собирает полный DOM, скриншоты, heap dump, тексты переписки или network
payload. Дополнение 14.09 сохраняет ограниченные метаданные элементов, описанные
ниже; это не постоянное сканирование страницы.

### Независимый стек и цепочка операций Main

Длительное отсутствие heartbeat не означает смерть Main. Watchdog принадлежит
fork IPC: при `disconnect` или явном shutdown-сигнале выполняет прежнюю очистку
и выходит; `bye` подавляет тревоги. Старый exit после180с тишины удалён:12.10 он
завершил наблюдение во время живого Main freeze, и последующие паузы остались без
наблюдателя. Пороги, частота tick, квоты профилей/стеков и per-stall admission не
расширены. Контроль `perf-watchdog.orphan.test.cjs` использует управляемые часы/
диагностические порты и отдельный настоящий IPC child; это не runtime-приёмка
первопричины зависания. Исчерпанные квоты по-прежнему сохраняются как отказ.

С09.10 внешний watchdog отдельно допускает односекундный `/usr/bin/sample`
при тишине Main от500мс либо focused renderer по его threshold. Квота тяжёлых
профилей на него не влияет. Один sample одновременно, cooldown30с на точную
identity PID, общие8/час и24/скользящие сутки; receipts переживают restart.
Начальные тревоги менее1с используют максимум6часовых/18суточных слотов;
остальные доступны продолжающейся паузе от1с. Если начальная заявка упёрлась в
этот резерв, прежний watchdog tick один раз повторяет её для того же stall/PID
после порога. Свежий heartbeat/hidden/observer-gap отменяет ожидание. Общие квоты,
process cooldown и запрет перехвата чужого процесса не ослаблены.
Перед spawn повторно проверяется принадлежность и поколение процесса. Отказ,
таймаут20с, неполный вывод и превышение8MiB сохраняются отдельно; убивается
только собственный дочерний sample. Видимый нефокусный renderer остаётся
в дешёвых измерениях и прежней heavy policy, без нового native capture.

`stall-*.sample.json` связывает heartbeat silence, spawn, окончание sampling,
выход процесса и наблюдённое возобновление. macOS sample v7 часто не сообщает
точный конец интервала: совпадение тогда доказуемо только если весь проверенный
capture envelope лежит внутри silence; `actualBoundsKnown=false`, `overlapMs=null`.
Начатый после возобновления стек не является стеком зависания; частичное или
неизвестное перекрытие не превращается в success по одному exit0.

Для native `.sample.txt` сохраняется защищённая доля64MiB ВНУТРИ общих5GiB.
Раньше старые incident JSON заполняли бюджет, а prune первым удалял каждый свежий
стек сразу после2минутной write-grace. Теперь старые metadata уступают место этой
доле. С10.10 она является минимальным защищённым запасом, а не отдельным
потолком: при свободном общем бюджете стеки не удаляются только из-за превышения
64MiB. Короткие стеки сохраняют7суток; файлы от8MiB —24ч. Quota receipts
сохраняются до конца их24ч окна. В `.sample.json` позднее удаление отмечается отдельно
`output.retained=false/removalReason/removedAt`; capture complete не означает
бессрочное наличие файла. У тяжёлых профилей соответствующая запись появляется
в `.profile.json.artifactRetention` без изменения результата capture.
`[Perf:ArtifactPrune]` различает weekExpired/heavyExpired/budgetEvicted.
Protected minimum проверяется по остатку ПОСЛЕ удаления целого файла: пул65MiB
с bucket4MiB не должен уменьшиться до61MiB, если есть обычный кандидат на удаление.
Возрастное истечение действует и для защищённых файлов. Повреждённый собственный
файл больше всего5GiB бюджета не получает эту защиту; нормальные native/bucket
producers имеют меньшие отдельные лимиты. Prune периодический и сохраняет2минутный
write-grace:5GiB не обещает отсутствие краткого превышения во время записи.

Тот же artifact store принимает ограниченный causal journal:до7суток внутри
общих5GiB, защищённая доля64MiB с использованием свободного общего бюджета,
hourly bucket до4MiB, запись до2KiB,60обычных+12критических записей
в минуту на источник. На Main/renderer нет файловой записи этого журнала.
`sourceBoot/sourceSeq/emittedAbs/watchdogReceivedAbs` отделяют время события
от поздней доставки; heartbeat учитывается в последовательности без записи
каждого heartbeat на диск. Лимиты очереди/байтов/rate, транспортные потери,
sequence gaps и flushLag видны явно. Heartbeat может подтвердить потерянный
settle уже известного span; отсутствие span в обрезанном snapshot означает unknown,
не завершение. Для завершённых именованных sync-work действует отдельный путь ниже.
Main gap от500мс идёт в существующий critical allowance: поток коротких GC
не должен занять его обычные60записей/мин и вытеснить thread CPU самого зависания.
Лимит12critical/мин остаётся; это приоритет событий, а не безлимитное логирование.

IPC wrapper разделяет `executing → sync-return/awaiting → settled`,
`syncMs` и `lifetimeMs`. Возраст ожидающего Promise не означает работу CPU.
Явные spans обрамляют Main raw JSONL consumer, loadSessionRecords, копирование
кэша, группировку и проекцию History/Timeline; caller и parent/action/read IDs
связывают операции. Full/append/memory-hit и размеры — metadata, без текста
переписки и полных путей. Generic wrapper не измеряет каждую continuation после
await; async CPU interval может содержать чужие задачи и не считается exclusive.

С Diagnostic25 `syncWork(siteId, metadata, callback)` измеряет конкретный синхронный
участок под прежним ALS-parent; после await caller открывает новый участок. Реально
сработавший HTTP/watch/timer root не наследует запрос регистрации. `sql(siteId,
prepare|get|all|run, callback)` считает только фактический вызов и его wall time на
ближайшем выполняющемся участке. Cached Statement выполняется под текущим caller;
lookup подготовленного statement не считается PREPARE. Callback вызывается один
раз с прежним value/Promise/error. Нет SQL text/bindings/row inspection/stack/пакета
на query. Thread CPU снимается на границе work, не на каждом SQL; parent/child
inclusive intervals и SQL wall не складываются как exclusive CPU.

Покрыты registry source SELECT, catalog usage/watch, availability manifest enumeration,
session-history DB readers и SQL/read/hash/diff linked-file context. Это перечисленные
sites, не вся native connection: iterator execution и startup до configure остаются
uncovered. Resource service отдельно помечает capture/group/publish одним `metrics:
<scannedAt>`; это не renderer commit. Git child spawn/exit/close — время наблюдения
callback, не kernel exit или child CPU; связываются `git-command:<pid>:<seq>`.

Source сохраняет до8 важных завершённых works (wall или SQL≥50ms либо≥128SQLops)
на5минут, отдельно от общего recent tail. В work до16 SQL cells и16числовых counters;
overflow, snapshot omission, actual eviction, unscoped SQL и unavailable timing
отмечаются отдельно. Main gap включает до2 реально пересекающихся works с полными
counts/times: частичное пересечение не разрешает пропорционально делить SQL cost.
Незавершившийся native call без доставленного prelude всё ещё может оставить caller
UNKNOWN. GC передаётся агрегатом, прежнее delivered-only ring64 не стало полной GC-историей.

Main transport сохраняет общий предел32: ordinary допускается до24,8мест оставлены
essential. Heartbeat строится после admission, переносит до2 due summaries; не более
3 metadata attempts каждого work, без нового timer и без повтора product callback.
`send(false)` означает принятый enqueue/backpressure, не разрешение второго send.
Journal принимает late completed summary даже без enter (`enteredRecordMissing`),
сохраняет исходный interval за пределами20s incident и ACK-ит exact PID/boot/id/revision
только после подтверждённого append+fsync. Callback transport не является disk ACK.
In-memory persisted dedupe ограничен512 и не восстанавливается после watchdog restart;
при анализе нескольких эпох нельзя суммировать metadata retry как новую работу.

В прежних60normal/min выделены32work/8health/20detail, critical12/min не расширены.
Queue64 вытесняет только lower-priority запись. В2KiB сначала убираются optional
cells/counters/context с явными omitted, а повреждённый aggregate/outcome не становится
успешным zero-SQL. Ordinary/health/details ограничены первыми2MiB общего hourly4MiB;
work/critical могут использовать оставшиеся bytes. Исчерпанный essential budget —
явный UNMET, не ACK. Full prune не выполняется при каждом append; append failure и
поздняя prune failure различены. Bounded retention ledger32entries/16KiB в тех же5GiB
фиксирует только подтверждённое удаление bucket с интервалом/bytes/reason; nofollow,
inode guards,7days/24h и независимые native/heavy quota receipts сохраняются.

Перед дописыванием causal bucket тот же проверенный `O_RDWR|O_APPEND|O_NOFOLLOW` fd
читает один последний byte непустого файла: требуется newline. Частичная запись вместе
с неудачным rollback иначе позволяла подтвердить новый JSON, приклеенный к оборванному
префиксу: ACK был, читаемых NDJSON records —0. `CAUSAL_TORN_BUCKET` оставляет bytes
нетронутыми, не даёт ACK и сохраняется как `incomplete-hour-tail`/`tornBucketRecords`
даже при ограничении частоты сообщений об ошибке. Новый store заново проверяет файл;
неизвестный хвост автоматически не обрезается. Здоровый следующий hourly bucket и
retry после успешного rollback работают прежним путём. Это один byte на batch append,
не чтение всего файла или новый query в Main. Контроль — real tempFS/fsync с адресно
инъецированными write/rollback errors, а не утверждение такого сбоя в production.

Main gap сохраняет прежний process CPU и отдельное время вызывающего thread.
В Electron28/Node18 нет `process.threadCpuUsage`: на macOS используется
`clock_gettime(CLOCK_THREAD_CPUTIME_ID)`, недоступность остаётся null+reason.
GC observer держит64события с абсолютным интервалом; late delivery сопоставляется
по startAbs. Ноль наблюдённых GC не доказывает отсутствие ещё не доставленного
события. Принудительный GC разрешён только в изолированном diagnostic canary.

После OOM11.10 `HistoryReadMemory` отмечает admission и окончание подготовки
turn-модели и Codex catalog query. В нём только readId/caller/provider/session,
счётчики, heapUsed/heapTotal/heapLimit текущего isolate и RSS всего процесса.
Начало остаётся в журнале, даже если fatal allocation не дало написать конец;
отсутствие конца означает unknown, не доказанный виновник. Это фазовые снимки,
не измеренный peak и не exclusive allocation. Нет heap dump, обхода графа,
сериализации тела или дополнительного чтения ради метрики. MainLoop также
пишет фактический heapLimit: startup `js-flags` не доказывает лимит уже живого
Main isolate. Worker получает readId из проверенного transport context после
удаления correlation-полей из authority-bearing payload. Его diagnostic-сообщение
приходит отдельно от результата RPC; приём результата не является ACK диагностики.

У outer Codex turn reader `prepared` означает готовый graph **до** final admission.
Раньше one-shot `end(success)` писал `complete` здесь и скрывал последующий отказ.
Теперь final rejection даёт один `error` с тем же readId, а успешный `complete`
испускается microtask после возврата синхронного wrapper frame. Scheduling
вооружается до последнего guard (даже async-hooks могут синхронно отозвать proof),
commit после guard не вызывает observer/console/memory sample. `decisionAbs` и
`decisionElapsedMs` относятся к решению, `emittedAbs/elapsedMs` — к записи и её
снимку памяти. Они не являются подтверждением доставки всего HTTP/IPC-ответа.
Остальные callers сохраняют прежний синхронный `end`.

Main `HistoryRead/call-complete` с `admission=pending-final-check` описывает
завершённую подготовку попытки до последней проверки допуска. Синхронный
diagnostic observer может отозвать её source/lineage: следующий `request-retry`
того же callId означает, что этот результат не выдан клиенту. Один success-log
без учёта attempt/retry поэтому не подтверждает публикацию результата.

## UI → native counters → запрос чтения

С30.09 дешёвая цепочка не зависит от доступности тяжёлого capture. На capture
click/pointer/key/wheel сохраняются `ui-…` ID и структурный адрес цели до её
удаления. `[Perf:UIAction]` объединяет EventTiming, callback первого/второго
кадра, render/layout-effect/after-effects, presentation, focus, activity и
scroll-writer phases. `frameAbs` — доставка callback, исходный rAF timestamp
сохранён отдельно: после длинного handler он бывает раньше самого клика.
Stylesheet identities показывают добавление/удаление даже вложенного `<style>`
без чтения cssRules, текста, computed style или обхода всех потомков.

С11.10 SOURCE frame probe запрашивает кадры только пока у допущенного действия
нет двух callback. Один scheduler объединяет действия и после drain останавливается;
постоянного idle rAF больше нет. Перед первым кадром и после простоя baseline
явно `unknown-idle-or-before-first-frame`: простой нельзя записать как rafGap.
Первый долгий handler после idle виден в action timestamps/LongTask/EventTiming
и независимых timer/heartbeat, но непрерывного idle-frame наблюдения уже нет.
Callback delivery и исходный RAF timestamp остаются разными часами.

Отменяемый `beforeunload` не завершает scheduler, heartbeat connection или очередь
clipboard outcomes. Cleanup выполняется на окончательном `pagehide` без persisted;
отменённое закрытие сохраняет наблюдение в продолжающем работать документе.
Persisted pagehide не уничтожает эти каналы; это не полная BFCache-приёмка.
Heartbeat регистрирует lifetime fence до запроса watchdog-info. Если final
pagehide пришёл, пока IPC pending, поздний ACK не создаёт socket/interval/reconnect.
Отменённый beforeunload и persisted pagehide сохраняют обычное подключение.

С09.10 клавиши пишутся безопасным классом Meta/Control/Alt/Shift/Arrow/Escape/
Enter/Space/Tab/Other и флагами modifiers/repeat, без печатной клавиши или input
value. Slow summary идёт тем же actionId напрямую watchdog, health/drop counters
попадают в heartbeat. Socket write означает enqueue, не подтверждение хранения.

С10.10 изменённые Copy/Cut/Paste/SelectAll/Undo/Redo/DeleteToStart различаются
allowlisted `shortcutClass`; физический code используется только для выбора
категории и не сохраняется. Это намерение клавиатурного жеста, не квитанция Copy.
Composer отдельно измеряет уже необходимые native read-text/write-text/read-formats
и read-snapshot: только время, число символов/форматов и failed/missing, без текста
и дополнительного чтения буфера для проверки. Медленная/ошибочная операция имеет
`[Perf:ComposerClipboard]` с прежним actionId. Выделенный текст History идёт
обычным DOM/native Copy и не обязан вызывать composer adapter.writeText. В самом
composer Copy может обработать CodeMirror; host-route/selectionChars относятся
к этому пути. Отсутствие adapter.writeText не доказывает отказ native History Copy.
Paste keymap может вставить текст через facade без native Paste event; связывать
нужно исходный жест, необходимое adapter-чтение и применение, не только события.
Fallback snapshot-read ловит исключение СНАРУЖИ измеренного вызова: иначе native
readHTML throw превращался в обычный null и измеритель ошибочно писал failed=false.
Публичный null fallback сохранён; в журнале безопасный код без текста исключения.

Существующий capture listener также принимает native `copy/cut/paste`.
`clipboardState` сохраняет owner/entry по anchor/focus, rangeCount/collapsed,
число выбранных символов только для одного текстового узла, trusted и
defaultPreventedAtCapture. finalDefaultPrevented первоначально unknown; один
MessageChannel task после dispatch дополняет тот же actionId через
`[Perf:ClipboardOutcome]`, даже если исходный UIAction уже записан. Microtask из
capture не гарантирует завершение target/bubble handlers и здесь не используется.
Очередь максимум32, native Event хранится только WeakRef до task; в журнал уходят
скаляры. Потерянный Event/accessor, overflow и невозможный task оставляют явный
unknown/reason, не false или success. Текст выделения, clipboardData и геометрия
не читаются. В нескольких узлах selectedChars остаётся unknown. Отмена default
не означает отказ Copy: CodeMirror может сам заполнить clipboardData и отменить
обычное действие. Факт native Copy также не является proof записи в OS clipboard;
его нужно связывать с последующим реальным read/paste, а не объявлять success.

Для контролируемого same-length сценария есть одноразовый oracle только с двумя
фиксированными синтетическими строками. Тест явно вооружает runId/step; на уже
необходимом adapter.readText пишутся matchesExpected/matchesPrevious/failed,
без значения/хеша и дополнительного OS read. Произвольный expected-text не
принимается, production hotkey/API/polling для включения нет. Private memory PASS
проверяет этот discriminator, но не подтверждает установленный физический
Cmd+C/menu→OS clipboard→Paste. Такой приёмочный контроль остаётся отдельным.

Meta dispatch получает один `[Perf:ModifierOwners]` с тем же actionId: число

Индикатор Cmd-вложенности добавляет в тот же action фазу

hit-test и всего собственного callback. Это отличает его работу от последующих

Focus manager использует ту же bounded фазу `pane-focus-boundaries` с source

`Perf:PaneFocusActivation outcome=reused` означает совпавшее состояние уже
выбранной панели: полная tab activation не повторялась, но прежний sidebar

`outcome=activate reason=...` отличает новую pane/project/selection/notification,

активации совпавшего состояния. Причина не требует DOM/History чтения.

Кольцо96действий,32phases (первые8 и последние24),24stylesheet changes каждого

предыдущий. Хранятся32окна, максимум6в одном action; время query — также ожидание
renderer, а не собственная CPU-цена наблюдателя. Интервал может содержать другую

доказывает Docker. Высокий собственный Script/style/layout требует ремонта
соответствующей работы даже при занятой системе.

payload перед service и не входят в cache/source identity, DTO и read proof.

Проверка диагностики — воспроизводимый известный CPU-блок + global restyle,
удаление нажатой кнопки, соседние periodic samples, ввод canary и wheel.

с private userData; рабочие вкладки, native cursor и provider input не нужны.

## Cold History: чтение, проекция и ожидания

`CodexHistoryRead` после большого чтения пишет startAbs/endAbs, bytes/chunks,
maxRecordBytes/maxBufferedBytes, framingMs/parseMs/feedMs/checkpointMs/yieldMs
и readWaitMs/consumeMs. Это позволяет отличить большие физические записи,
копирование незавершённой строки, JSON-разбор, сборку проекции и паузы между
порциями. Тексты, аргументы инструментов и raw records в лог не попадают.

Времена нельзя складывать вслепую: consumeMs включает feed/checkpoint/yield,
checkpointMs содержит await и не равен чистому CPU. readWaitMs включает доставку
read callback и ожидание event loop, поэтому не измеряет скорость SSD.
Следующие CodexHistoryMetadata и TranscriptService:HistoryPrepare отделяют
подготовку строк от этого чтения; HistoryHandoff — применение и paint.
Отсутствие совпадающего CPU trace не позволяет назначить конкретному соседнему
IPC всю задержку. Процент чтения показывает продвижение именно этих байтов,
не объясняет причину медленной обработки и не гарантирует готовность viewport.

С25.09 read/preparation Codex может выполняться в Node worker. Его сообщения
доходят до обычного журнала с `[HistoryReadWorker] emitAbs=...`: время источника
отделено от доставки main. CPU/RSS процесса включает worker, а main-loop gap
и обычный main JS-profile не равны его работе. `preparedCache` отделяет запись
готовых строк от `responseTiming`. В E2E heartbeat нужно дожидаться последнего
overdue tick после ответа; screenshot/readback измерять отдельно — иначе цена
тестового захвата кадра ошибочно становится «лагом History».

Шрам из isolated DEV27 (14.10): подключение NodeWorker и успешный Main profile
не доказывают сохранение worker CPU. Контроллер начал наблюдение, но закрыл Main
CDP без вызова worker stop/export; worker elapsed1680ms остался только wall time.
В private repair28 цепочка stop/export → detach/disable → закрытие соединения
проверена на fake CDP/tempFS; отдельный control с ответом через4.2s обнаружил,
что3s worker deadline короче искомой паузы, и сохранён общий15s CDP ceiling.
Actual28 затем сохранил два worker profiles с подтверждённым detach/pending0;
это покрытие этих фаз, не всех workers/production. При позднем start/detach/unsupported capability
сохранять UNMET; лимит считать по фактическому serialized artifact с metadata и
receipt, а не по размеру одного minified profile. Исходный прогон не переписывать.

Отказ system-wide AX point-owner до отправки событий — не измеренный медленный
клик: в DEV27 attempted/posted=0, а AX−25204 совпал с длинной Main task. Это ещё
не доказательство permission denial или её причины. Native latency и независимо
запланированную проверку редактора через trusted CDP учитывать отдельно; потеря
ACK/неизвестный ввод не разрешают повтор или смену канала доставки.

Следующая граница actual28: ACK `Input.insertText` не подтверждает полный CM
документ. Внутренний20s predicate под RPC15s потерял причину несовпадения, хотя
после ввода renderer уже мог простаивать. Сохранять первый полный CM snapshot
до ожидания; известный observer deadline должен завершиться раньше RPC и вернуть
последний снимок отдельно как mismatch/unavailable/read-error. Transport timeout
остаётся UNKNOWN и не разрешает повтор вставки или нормализацию различий.

Bulk CDP29686UTF16/405LF в actual28 дал3.919s renderer task с textInput3.830s,
680input events и1634Layout (union2.168s) в сохранённом trace prefix. Это native
редактирование DOM, не доказанный SQL/worker цикл; полного EOF нет. Shipped Soniox
и Global Dictation используют свои draft/editor-transaction/paste-receipt пути,
поэтому такой CDP стимул нельзя автоматически считать причиной пользовательской
диктовки или5s workspace switch. V8 `(program)` требует native trace, не догадки
по ближайшему JS frame; action-admission timestamp не заменяет отдельный ACK.

Actual29 различил прежний UNKNOWN: первый полный CM-read за85ms после ACK
показал весь canonical плюс один LF, а через8s тот же mismatch без ошибки.
Это functional FAIL, не8s CPU-пауза. Последующий hidden component control
воспроизвёл тот же hash только при соответствующем placeholder/focus пути;
generated hint исправляет точность этого ввода без trim/повтора операции.
Из этого не следует исправление production5s switch или ускорение вставки:
component timings не являются сопоставимым full-app измерением. Направление
selection также сравнивать отдельно от упорядоченного диапазона — одинаковые
`from/to` не доказывают сохранность anchor/head. SOURCE35 и пределы controls
сохранены в рабочем `docs/tmp/оптимизация-history.md`.

Счётчик количества cache updates не измеряет write amplification: одна
continuation может быть десятками MiB. Различать continuation read/write bytes,
serialize/write ms, metadata/row/payload write bytes и `baseCache`/`preparedCache`.
Это bytes SQLite bindings, не физические записи SSD/journal. Prefix verification
учитывается отдельно от source bytes; virtual имеет свои read/verification counters.
Эти счётчики относятся к projector lanes, не ко всем file I/O приложения.
Main heartbeat подтверждает доступность main, но не ограничивает ожидание
другого запроса в синхронной фазе worker. С30.09 `[HistoryRead]` различает
sessionQueueMs и coldAdmissionMs, execution, serialization/postMessage,
main delivery, revoke/retry/worker death. Cache phases ограничены16группами;
поздний exception вытесняет обычную группу, последний отказ и счётчики причин
сохраняются отдельно от truncation. Bytes structured clone или raw records-path,
который не отдаёт измерение, обозначаются unavailable, а не оценкой по stringify.

SSD причины разделены: no-file, disk-quota, version-mismatch, source identity/
size/truncate/rewrite, контекст/owner, checksum/index corruption, disabled,
permission/disk-full и write invalidation. Prune, RAM index eviction и source
invalidation — разные события. История удалений/версий ограничена256ключами и
не переживает restart; version hint берётся из уже существующего quota scan,
без нового сканирования на каждый read. Неизвестная ошибка сохраняет класс и
безопасную точку JS-source, без message/payload. Bootstrap cache outcomes тоже
передаются; hit после RAM eviction отдельно доказывает SSD, а не новый raw parse.

С06.10 split cache отдаёт `cacheTier=rows/state/timeline` и prune counts
`obsoleteEvictedCount/stateEvictedCount/rowsEvictedCount/timelineEvictedCount`.
20GiB — общий retention budget, не RAM/peak reservation. При повторном чтении
сверять конкретный tier: отсутствие graph не означает отсутствие готовой
Timeline или страниц. Полный raw fallback после настоящей дописи и отсутствия
checkpoint отличается от лишнего raw-read неизменной Timeline.

## Как читать доказательства

`[Perf:CpuWindow]` ведёт к серии CPU-окон; `[Perf:Incident]` — к конкретному
пакету, `.sample.txt`, `.cpuprofile`, `.main.cpuprofile`, `.trace.json` и
`.profile.json`. Сначала сравни время симптома и фактические границы записи.
`requestDelayMs` и времена начала важны: main может начать JS-профиль уже после
freeze. Это запись продолжения, не стек прошедшей паузы. `complete=false`,
`traceComplete=false`, `traceDataLoss`, `unavailable` и `coverage-gap` запрещают
вывод «ничего не было». Если уснул/не получил CPU сам watchdog, его тишина не
доказывает отдельное зависание всех наблюдаемых процессов.

Высокий CPU и совпадение по времени сужают расследование, но не называют
конкретную функцию. У native sample Electron часто нет точных символов:
ближайший экспорт с большим смещением может ошибочно выглядеть как font shaping.
`during=history-load(open)` тоже не CPU-профиль: запрос мог ждать очередь минутами.
Настоящий вклад функции устанавливается профилем/trace и при необходимости A/B.

Повтор после установки14.09 показал иной доказанный источник main-нагрузки:
`[CodexJsonlCache] full/evict` содержат `by=...` и связывают повторные полные
разборы с reconciliation результатов оркестрации. За минуту8 full reads/2228.9MiB
на двух больших активных сессиях: файлы взаимно вытесняются из raw-cache768MiB.
Это логические чтения/JSON-разборы, не замер физических байтов диска. Такой
путь устанавливается по caller и последовательности cache events даже без
свежего CPU-профиля; однако не объясняет автоматически каждую отдельную паузу
renderer. Соседняя Swift-компиляция также занимала несколько ядер. Детали и
source-ремонт общего result-reader — рабочая карта окон14.09,01:45МСК.

После ремонта `[CodexResultReader] mode/readBytes/verifyBytes/sourceVerifyBytes` различает
bootstrap, append и неизменный повтор. `readBytes` — цена нового JSONL-диапазона,
`verifyBytes` — SHA прочитанного диапазона, `sourceVerifyBytes` — дополнительная
проверка frozen ancestor/child-prefix у resolver; это не повторный JSON-разбор.
`authority=0` означает наблюдение без права окончательного commit, `authority=1`
— проверку для решения. Повтор после rewrite учитывает затраты обоих проходов;
ошибка проверки тоже не обнуляет её цену. На больших synthetic files проверены
unbound и ID-less пути: обычные busy-wakes, готовый A с append следующего B и
pending child с растущим parent не хэшируют прежний prefix при каждом событии.
Перед окончательным результатом и отказом digest по-прежнему проверяется.
Эти счётчики не измеряют
рендеринг History/hover и не заменяют общий CPU/paint профиль после установки.

### Первый scroll после возврата: вход, обработчик и движение не одно время

Прежний `SCROLL_GESTURE_BEGIN` находился внутри intent-handler после capture
и части подготовки. Поэтому его `inputDelayMs` нельзя целиком приписывать
доставке ОС, складывать с пересекающимся LongTask или считать началом handler.
В эпизоде4196 первый scroll наблюдался≈405мс после wheel, хотя высота/строки
не менялись; соседний тяжёлый projector начал работу только после этого scroll.
Повторный ремонт loader/anchors не следует из такого симптома.

`[HistoryHandoff] WHEEL_PIPELINE` теперь связывает по instance/owner/generation/
visit/id вход и выход tool-capture и intent, route `none/inner/edge`, cancelable/
defaultPrevented/propagationStopped, первый наблюдаемый scroll и ближайшие rAF.
`scrollHandlerEnterAbs` отделён от чтения позиции; `beforeObservationMs` включает
предшествующую работу scroll-handler. `afterIntentMs` — ожидание после выхода
из intent, не автоматически вина browser: там ещё могут выполняться другие JS
tasks. Scroll означает наблюдение после события, не доказательство его причины;
rAF также не гарантирует, что пиксели уже показаны.

Запись буферизуется в отдельный task; сравнивай исходные enter/exit/event/frame
Abs, а не время попадания строки в файл (`flushAbs/logLagMs` и RendererLogMeta).
Нет дополнительных geometry reads или scroll-writer. Первые3 packets после
quiet-gap250мс — только sampling, не управление жестом. Ещё ожидающий first
wheel не теряется при новом burst; owner/hide/remount не разрешают приписать ему
движение другой поверхности. Pending12, frames8 и очередь48 ограничены;
capacity/cancelled/dropped остаются явными, отсутствие sample не означает PASS.

`SCROLL_PROGRAMMATIC` закрывает другое недостающее звено: DOM scroll сам по
себе не называет писателя. В активном upward gesture обёртки только данного
History scroller наблюдают `scrollTo`, `scrollBy` и setter `scrollTop`; они не
отменяют, не повторяют и не меняют вызовы. Лог содержит вызванный метод/числа,
стек, owner/generation/visit/gid, intent/restore и последнее уже выполненное
измерение строки (включая1px). Дополнительных geometry reads нет. Числа из
options читаются по data descriptor: getters не исполняются диагностикой.
До8записей на gesture/24pending; limitReached запрещает считать охват полным.
Вывод отложен, сравнивать calledAbs с WHEEL/SCROLL, не timestamp flush.
Cleanup восстанавливает только собственные wrappers и не трогает поздние чужие.

`VIRTUOSO_MEASUREMENT_VIEWPORT_SYNC` обозначает раннюю публикацию уже изменённой
позиции после измерения карточки. Это synthetic scroll notification без записи
координат; он не является новым user input или измерением native browser ACK.
Позднейшее обычное scroll event остаётся допустимым. При анализе пустого кадра
сравнивать physical writer и native paint; rAF до RO может видеть промежуточную
геометрию даже в исправленном варианте. Механизм — fact-история-производительность.

Стек абсолютного scrollTo отличает повтор index/tail-команды от относительной
компенсации scrollBy. Если JS-записи нет, это ещё не доказательство browser
anchoring: сначала проверить полноту охвата/лога, затем native trace. Рост
scrollTop с равным ростом высоты и сохранённой видимой строкой может быть
корректной компенсацией. Проба `scripts/history-first-wheel-probe.mjs` снимает
именно writers/frames в private Electron; её MEASURED не является приёмкой
неповторившегося production-рывка.

Существующий incident trace дополнен `input`/`latencyInfo`: очередь и ACK
имеют отдельные события в [Chromium120](https://raw.githubusercontent.com/chromium/chromium/120.0.6099.0/content/browser/renderer_host/input/mouse_wheel_event_queue.cc).
JS-логи сами native ACK не измеряют. Категории сохранены в `.profile.json`;
privacy filter,8MiB buffer,16MiB export и capture quota прежние. Новая строка
WHEEL_PIPELINE не требует тяжёлого capture; профиль после события всё ещё не
восстанавливает прошедший ACK. Headless tests проверяют временную цепочку и
реальные callbacks History, не production pixel-latency.

`[TranscriptService:HistoryPrepare]` отделяет post-projection work от загрузки:
dehydrate, promptPresentation, responseTiming, revision, rowWindow, entryWindow,
digest и суммарные startAbs/endAbs/elapsedMs. Прежний путь без SSD-store также
отдаёт syncMs; worker с порционной записью отмечен yieldedCacheWork, его elapsed
включает уступки другим задачам и не равен CPU. Пишется только
при общей цене от24мс, без содержимого сообщений; refresh/delta/full возвращают
тот же результат. Async rewrite-baseline в эти времена не входит. На19.09
wheel171 ждал439/416мс до tool-capture при handler≤0.3мс; сопоставлять следует
эти main-фазы, а не чинить loader или складывать весь open IPC со временем input.

`[CodexAuditAddressRead]` отдельно пишет file, scanBytes/bodyBytes/
verificationBytes/cacheHit и elapsed ms адресного enrichment. Счётчики локальны
одному вызову, не разница общих totals параллельных readers. В нормальном
неизменном повторе scanBytes=0, bodyBytes — только exact user record; новая
ревизия может считать большой prefix, но не создаёт raw-массив. `outcome=address`
доказывает прочитанный physical locator; финальный audit hash/session/attempt
ещё проверяются общим publisher. После ремонта не должно быть
`CodexJsonlCache full by=resolveCodexAuditAddress`. Источник большого read —
отдельная проверка от его доли в задержке wheel: без совпадающего CPU/input
trace одно время завершения чтения такой доли не доказывает.

## Наблюдатель не должен тормозить жест

В исходном resize наблюдатель курсора читал hit-test/computed style из
MutationObserver после freeze/cursor writes, а rate-limit проверял уже после
чтения. Это принудительная синхронная граница layout на горячем пути. Фоновый
probe теперь пишет доставленную цель события (`targetEvidence=event`),
авторские стили и владельца курсора; `computed=not-sampled` намеренно не является
ни реальным computed cursor, ни системным NSCursor. Он не делает geometry reads
и не сканирует `:hover`. Владелец курсора теперь читается прямо из gesture-manager,
не по наличию временного style-элемента.

13.09 повторная production-жалоба на resize/workflow показала предел прежнего
ремонта: инвалидация от `:root * {cursor:...}` и `body.userSelect` оставалась
даже без probe geometry-read. Browser платил её до paint; release listener
workflow форсировал её чтением размеров и выглядел как `commitMs≈300` при
`committed=0`. Source переведён на cursor малого pointer-capture target;
новые `cleanupMs/storeCommitMs/releaseHookMs` разделяют отпускание и запись.
Изолированный Electron28/50k DOM доказал старую style-цену70–100мс против
0–0.2мс у нового пути, первый кадр~15–20мс. Это proof общего механизма, а не
замер всех History/layout costs production. Точная фикстура и остаток —
[рабочая карта окон](../tmp/окно-вкладок-и-переключатель-фичи.md).

Общий manager не доказывает, что все жесты используют его: sidebar `TabBar`
сохранял отдельный global stylesheet, а popup-resize — записи в body. При
повторении симптома проверяй фактический writer конкретного жеста. После их
ремонта отдельная fixture с actual outline/host hooks и 50k DOM дала снятие
старого правила91–92мс против0.6–0.7мс у локального пути. Это стоимость styles
в контроле, не полная задержка production. `[TabDnd:cursor] setupMs/cleanupMs`
тоже измеряют только JS-границы; общий input/paint delay остаётся в Perf-probe.
