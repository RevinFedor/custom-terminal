# Fact: панель потребления ресурсов (память/ЦП по вкладкам)

Плашка в правой части шапки, справа от кнопки инструментов Timeline. Показывает, сколько памяти
и процессора съедают вкладки проекта вместе со своими MCP-инструментами, само
приложение и брошенные остатки.

Компактный чип ресурсов остаётся одной строкой и не сжимает/не переносит число
памяти или процента. Если верхней шапке не хватает места, он остаётся доступен
в прокручиваемом toolbar, а не обрезается у правого края.

## Предупреждение о месте на диске

С06.10 SOURCE отдельная статичная иконка HardDrive стоит между ресурсами и MCP.
По уточнению пользователя это одна иконка без слова «Диск» и дополнительного
треугольника: состояние передаёт цвет. Она автоматически появляется янтарной, когда:

```text
оставшийся рост = max(0, лимит кэша − фактически занятый кэш)
прогноз остатка = свободное место − оставшийся рост
предупреждение = прогноз остатка < 6 ГиБ
```

Лимит хранения History —20ГиБ, один для всех вкладок/версий. Кэш14/20 и свободно10
дают остаток4 → warning; свободно12 дают ровно6 → чип скрыт. Уже занятые14 не
вычитаются второй раз. Если кэш временно выше лимита, дальнейший рост0; неизвестное
значение не превращается в0/healthy. Ошибка замера красит иконку красным,
отсутствующий/устаревший замер — серым. При восстановлении достаточного места
предупреждение исчезает.

Клик раскрывает все шесть чисел в трёх строках: `Кэш / лимит`,
`Свободно / рост кэша`, `После роста / минимум`; значения справа идут через `/`
с одной единицей ГиБ на пару. Предупреждающий заголовок и нижний поясняющий
абзац убраны по прямому запросу: они повторяли уже понятный сигнал и раздували
маленькое меню. Unknown/stale/error имеют только короткую строку состояния.
Повторный клик,
Escape и outside закрывают; само изменение состояния не открывает popup и
не перехватывает фокус. Inbox использует тот же чип. Это прогноз для ограниченного
сохраняемого кэша, не обещание максимального размера исходных сессий, сборок или
временных файлов.20ГиБ заранее не выделяются;6ГиБ не резервируются системой.

`disk-capacity-service.js` считает только async filesystem metadata под cache
root (все версии/families/sidecars) и доступные пользователю blocks через statfs
тома этого root. Нет SQLite/body reads, History worker start/RPC, полной storage
inventory или process scan. Один shared Main service, single-flight,30s при
подписчиках; renderer singleton обновляет все копии, через60s без нового результата
показывает stale. Destroy/navigation/unsubscribe снимают leases; поздний ACK
старой подписки не откатывает новую. Native/synthetic цифры различать в приёмке.
Ресурсный total/commands и его опрос остались прежними.
Пятисекундный/100000-entry scan-limit означает неизвестное измерение, не
превышение20ГиБ или заполненный диск. Новая диагностика различает elapsed и
entry предел, пишет только counters/elapsed без путей. При отказе cache inventory
statfs ещё мог не выполняться; freeBytes=null не доказывает его отказ. Следующий
успешный sample возвращает обычное состояние; лимиты и assurance не ослабляются.

## Почему не `ps`

`ps rss` — «страницы, физически лежащие в RAM сейчас». Он **не видит сжатую
память** (у macOS её обычно гигабайты) и **заново считает** библиотеки, общие
между процессами Electron. Замеры на живой машине:

| процесс | `ps rss` | `phys_footprint` (Activity Monitor) |
|---|---|---|
| главный процесс приложения | 832 МБ | **1485 МБ** |
| отрисовка окна | 815 МБ | 920 МБ |
| сессия Claude | 335 МБ | 313 МБ |

На главном процессе `ps` занижает почти вдвое. Для панели, которую открывают
именно чтобы узнать «кто жрёт», это не «немного врёт» — это неправда про
крупнейшего потребителя.

## Как берутся цифры

`src/main/process-metrics-source.js` зовёт ядро напрямую через koffi:

- `proc_listpids` — все номера процессов одним вызовом;
- `proc_pid_rusage(RUSAGE_INFO_V4)` — `ri_phys_footprint` (то же, что в
  Activity Monitor) и накопленное процессорное время;
- `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)` — родитель и владелец;
- `sysctl(KERN_PROCARGS2)` — командная строка.

**Цена одного полного прохода — 4–6 мс на ~900 процессов.** Поэтому стоимость
не зависит от числа вкладок: делается один снимок системы, а раскладка по
вкладкам считается уже в памяти. Что 5 вкладок, что 50, что 500 — одна цена.

Для сравнения: `vmmap --summary` даёт ту же цифру, но 0.8 сек **на один
процесс**; на 400 процессов это минуты. `ps` как внешняя команда — 56 мс;
его RSS не равен footprint. Накопленное CPU-время `ps -o time` пригодно
для независимой проверки единиц native-счётчика.

### Смещения структур брать только из компилятора

Угаданные смещения читаются **без ошибки** и возвращают мусор — снимок молча
выходит пустым при `ok: true`. Так и произошло при разработке: `pbsi_comm`
предполагался на 28, реально на 16; `pbsi_uid` — 36, а не 60.

Проверять через `offsetof` в C-программе, значения зафиксированы тестом
`process-metrics-source.test.js`:

```
rusage_info_v4:  user_time=16  system_time=24  phys_footprint=72   (sizeof 296)
proc_bsdshortinfo: ppid=4  pgid=8  comm=16  uid=36                 (sizeof 64)
```

### Инструмент опознаётся по аргументам, а не по файлу

У почти всех MCP исполняемый файл — просто `node`. Различает их путь к скрипту
в аргументах запуска, поэтому нужен `KERN_PROCARGS2`. Без него все инструменты
сваливаются в «прочее».

#### `uv` и `local` в каждой сессии — разные MCP, не одинаковая команда (05.10)

В живом дереве `uv tool uvx …` запускал Python entrypoint
`yandex-wiki-search-mcp`, а `local` был именем `local.js` из пакета
`figma-console-mcp`. Прежний поиск MCP по путям не опознавал uv-обёртку;
вся её ветка попадала в команды и завышала число справа от slash.
Figma уже была инструментом, но generic filename скрывал её назначение.

Роль дополнительных launchers uv/uvx/npx/npm exec/pnpm/yarn/python задаёт
исполняемый target-пакет/модуль MCP. Python SDK в `--with mcp` не превращает
`uv run worker.py` в MCP; `npm run dev`, установка пакета и поиск его имени
остаются командами. Встроенные dev-поддеревья сохраняют своего владельца.
Подписи `MCP · Yandex Wiki` / `MCP · Figma Console` и SVG Server различают
инструменты от SquareTerminal команд. Обычный uv/Python job получает имя
запускаемой команды/скрипта вместо одного имени runtime.

Проверка PID обнаружила разные экземпляры этих внешних stdio MCP у разных
Codex-процессов. Повторение имени не позволяет схлопывать их память: расход
реальный, `claimed` предотвращает только повторный учёт одного PID. В срезе
с30Yandex/20Figma общий расход сохранился побайтно, из команд убраны≈2.6ГиБ.
Это исправление роли/подписи, не освобождение RAM. Конфиги и процессы не
изменялись; эти два внешних MCP не являются шестью общими детьми хаба.

Путь и аргументы за жизнь процесса не меняются — кэшируются. Ключ кэша — пара
(номер процесса, родитель): номера система переиспользует, и запись с другим
родителем означает уже другой процесс.

#### Буфер под аргументы спрашивать у ядра, а не назначать (12.09)

Блок `KERN_PROCARGS2` содержит не только аргументы: за ними идёт всё окружение
процесса, поэтому у обычной AI-сессии он весит ~5–6 КБ. Ядро отдаёт его целиком
или **молча обрезает** по размеру буфера, причём `sysctl` в обоих случаях
возвращает 0 — обрезание выглядит как успех.

Буфер был 4 КБ, и разбор упирался в край до первого аргумента: строка запуска
выходила пустой **у 368 процессов из 902**. Видно это было не как ошибка, а как
плохие подписи в панели: команда называлась «node» вместо «npm run dev», а
сессия Claude — «2.1.269» (имя каталога версии в её пути; сама раскладка при
этом считала верно, `describeAgent` ловит Claude и по пути).

Размер теперь берётся из `kern.argmax` (на macOS 15 это 1 МБ) — назначать его
нельзя, лимит зависит от системы. Буфер один на все снимки и переиспользуется:
`Buffer.alloc` обнуляет мегабайт, и делать это каждые пару секунд незачем.
Читается только то, что ядро записало в этот раз, по возвращённому размеру,
поэтому остатки прошлого процесса наружу не попадают. Цена замера не изменилась
(3–4 мс на ~900 процессов), первый снимок на 20 мс дороже из-за прогрева кэша.

Тесты: собственная строка запуска содержит аргумент, а не только путь к node;
строка читается более чем у 90% процессов (единичная пустота законна — процесс
мог завершиться между перечислением и чтением, массовая означает обрезание);
прогретый снимок остаётся дешевле 50 мс.

## koffi: зачем и что важно при упаковке

Системные вызовы недоступны из Node напрямую. koffi выбран потому, что:

- **готовый бинарник, компиляции нет** — лежит в отдельном пакете
  `@koromix/koffi-darwin-arm64`, ставится как обычная зависимость;
- **работает под Electron 28 (ABI 119) без `electron-rebuild`** — проверено
  запуском; это снимает весь класс граблей из
  [`fix-electron-native-rebuild-trap.md`](fix-electron-native-rebuild-trap.md).

**Обязательно в `asarUnpack`:** `node_modules/@koromix/koffi-*/**`. Внутри
архива приложения нативная библиотека не загрузится, и панель молча откажет в
упакованной версии, работая в dev.

При недоступности koffi источник возвращает `{ ok: false, reason }`, а не
падает: панель показывает причину, остальное приложение не затронуто.

## Загрузка процессора: только из двух замеров

`ps %cpu` на macOS — сглаженная оценка за предшествующий интервал до минуты
(локальный `man ps`), а не `TIME / ELAPSED` и не среднее за всю жизнь процесса.
Для проверки короткого интервала сравниваются дельты накопленного `ps -o time`
и native-счётчика за один wall-time; сглаженное `%cpu` — только соседний ориентир.

Честное значение = прирост процессорного времени между двумя снимками,
делённый на реальный прошедший интервал (`computeCpuPercent`).

Следствия, зафиксированные тестами:

- **первый замер отдаёт `null`, а не `0`** — «ещё не измерено» и «простаивает»
  разные утверждения, рисовать их одинаково нельзя;
- **счётчик пошёл назад → процесс пропускается** — номер переиспользован
  системой, это уже другой процесс;
- **после паузы прошлый снимок сбрасывается** — прирост за время простоя
  размазался бы по всему интервалу и дал ложный ноль для занятого процесса.

**Исправление единиц 14.09.** `ri_user_time` и `ri_system_time` в этом API
содержат Mach ticks. До этой правки они ошибочно считались наносекундами:
на исследованном M1 Pro `mach_timebase_info=125/3`, поэтому CPU приложения,
вкладок и flight-recorder занижался в 41.67 раза. Смещения структуры были
правильными; footprint памяти этим дефектом не затронут. Реальные лаги ввода
сочетались с ложным впечатлением «CPU в норме».

Источник один раз получает системное отношение и преобразует сумму ticks
в наносекунды. Потребители используют уже нормализованный `cpuNs` и не умножают
снова; identity `startedAtTicks` остаётся исходной. Неизвестное/нулевое отношение
делает источник явно недоступным, а не подставляет 1:1. Снимок хранит происхождение
единиц в `cpuTimeNormalization`; такой же маркер есть в новых CPU-артефактах.
125/3 — измерение этой машины, не переносимая константа для всех Mac.

Проверка 14.09 00:12 МСК за 8.343с: main 105.85%, renderer 124.25%, GPU-process
79.74%; независимые дельты `ps time` дали 105.90/124.48/79.95%. `100%` означает
одно ядро, а CPU GPU-process не является загрузкой аппаратного GPU. Старые
округлённые per-process логи без этого преобразования не доказывают низкую
нагрузку; их поправка допустима лишь с известным timebase и оговоркой округления.

## Раскладка по владельцам

`process-metrics-grouping.js`. Вкладка = свой процесс + все потомки.

Порядок важен: **процессы приложения забираются первыми**, иначе вкладка, чей
shell порождён главным процессом, утащит в свой итог всё приложение.

Каждый процесс приписывается ровно одному владельцу (`claimed`), иначе итог
раздувается на величину общих поддеревьев. Если две вкладки смотрят на одну
сессию, вторая получает нулевой вес и пометку «учтено выше».

- **Инструмент через обёртку** (`npm exec …` → `node …`) — одна строка с
  суммарным весом, а не три одинаковых имени подряд.
- **Одноимённые процессы приложения** сливаются в строку с количеством
  («Отрисовка окна ×2»): две неразличимые строки читателю бесполезны.
- **Закрывшийся процесс вкладки** даёт нулевую строку, а не исчезает —
  пропавшая строка читается как «вкладки нет», хотя она открыта.
- **Обход итеративный и с защитой от повторов**: дерево приходит из системы и
  в теории может содержать цикл.

### Внутри вкладки: агент, команды, инструменты, оболочка (2026-09-12)

Корневой процесс PTY-вкладки — оболочка терминала (zsh) на ~3 МБ, а сам агент
запускается командой внутри неё и оказывается среди потомков. До 2026-09-12
раскрытая вкладка писала «сама сессия 3 МБ, прочее 944 МБ»: «сессией»
называлась оболочка, а весь реальный вес агента лежал в безымянном «прочем»
(юзер: «сама сессия 3 МБ, а прочие занимают 944… мне нужно разделение»).

09.10 реальная строка «сессия Codex» около10ГиБ оказалась суммой одного
Codex-бинаря≈8.7ГиБ, его `codex-code-mode-host`≈1.4ГиБ и лёгкой node-обёртки.
Независимый `vmmap -summary` подтвердил footprint бинаря; низкий RSS этого
процесса скрывал≈8.6ГиБ swapped pages. Число звеньев этой цепочки не является
числом внутренних агентов. Журнал сессии вырос до937142445bytes, преимущественно
записями MCP-results массового paged research, даже когда внешняя code-mode
команда возвращала только короткий счётчик. Это подтверждает объём и владельца,
но без heap-proof не доказывает конкретную утечку. После пользовательского
restart старый PID исчез; shell-only4МБ не подтверждает расход resumed Codex.
Диагностика: `/private/tmp/noted-career-memory-20261009.UeiqYv/HANDOFF.md`.

Поддерево вкладки раскладывается **одним обходом от корня**, не плоским
поиском по шаблонам. На каждом процессе, по приоритету:

- уже внутри открытой строки (инструмент/команда) → всё поддерево её;
- MCP-инструмент → строка инструмента (обёртки схлопнуты, как раньше);
- агент (`AGENT_PATTERNS`: Codex/Claude/Gemini) → строка «сессия X»; каждое
  звено цепочки запуска (node-обёртка → бинарь → `codex-code-mode-host`) само
  подходит под шаблон и складывается в ту же строку по совпадению ярлыка.
  Агент, запущенный другим агентом (claude из-под codex), — **отдельная**
  строка: приписать его вес родителю значило бы соврать о том, кто весит;
- прозрачная оболочка (`sh -c`, login-shell) → не строка: вес в «прочее»,
  потомки классифицируются сами;
- всё остальное → **команда, запущенная во вкладке**, строкой с её именем
  (`describeCommand`: «npm run dev», «vite», «serve-stand»), и её поддерево
  принадлежит ей ЦЕЛИКОМ. Это главный мотив обхода вместо плоского поиска:
  dev-запуск поднимает вложенный экземпляр приложения со своими
  agent-процессами и инструментами, и плоский поиск приписал бы их «сессии»
  вкладки, раздув её на чужой гигабайт (скриншот юзера: вкладка 1.8 ГБ, из
  них 1.8 ГБ безымянного «прочего» — это был вложенный dev-стенд).

Команды легче 12 МБ (`MIN_COMMAND_ROW_BYTES`) не получают индивидуальных
строк: короткоживущие git/ps мерцали бы в списке. С05.10.2026 их суммарный вес
виден как «мелкие команды» и входит в полный итог команд. В main прежний
`otherBytes` сохраняет этот вес для совместимости; UI вычитает
`smallCommandBytes` из «прочего», чтобы детали не считали его дважды.
Строка «оболочка терминала» (бывшая «сама сессия») приглушена; остаток
«прочее» показывается только если ненулевой.

Прямой запуск shell-скрипта (`bash ./deploy.sh`, в том числе с обычными
флагами) — отдельная команда с полным поддеревом и именем `deploy.sh`.
Служебная `sh -c …` остаётся прозрачной: командой будет её реальный потомок.

Имя команды `describeCommand` берёт из **командной строки**, а не из пути к
файлу: у части программ файл лежит в каталоге версии (у Claude это
`…/versions/2.1.269`), и basename пути дал бы номер версии вместо имени.
Порядок разбора: запускающая обёртка с задачей («npm run dev»), затем скрипт с
расширением, затем цель `node <файл>` без расширения («vite»), затем имя
бандла приложения («Electron»), и только в конце первое слово команды.

Расширение скрипта сохраняется в display label: `dist/main/main.js` показывается
как `main.js`, а не двусмысленное `main`. Каждая строка команды получает слева
SVG `SquareTerminal`; значок обозначает класс сущности «запущенная команда», а
полное имя — конкретный процесс. Изолированный E2E с настоящим `node ./main.js`
подтвердил одновременно текст `main.js`, `lucide-square-terminal` перед ним и
полный вес поддерева команды.

### Общий Process controls и обычные вкладки

При переносе процессного монитора с Home в нижнюю часть ресурсов добавлен
общий контрол AI/Electron Dev. Его полезное отличие — доступ к внешним агентам,
другим app instances и отдельным dev-приложениям; обычные наши Codex-вкладки
при этом повторяются в дереве памяти и в карточках контроля. Надпись
`this prod` означает текущий экземпляр Noted; `owner` — PID приложения,
время — время запуска, а число рядом с Codex — найденные процессы, не orphan
count и не число одновременно работающих ответов. Это не ошибка/cleanup signal.

Нижние CPU/MEM берутся из `ps` выбранного процесса. Для Codex это root
Node-wrapper, а основная память бывает в vendor child/code-mode-host.09.10
живые18919/11948/16384 имели≈13МБ wrapper и≈142–241МБ vendor child. Поэтому
MEM0.1% в карточке нельзя читать как общий расход чата или сравнивать с верхней
агрегированной footprint-строкой. Обычный idle CLI не должен автоматически
завершаться после ответа; Stop/close/shutdown — отдельные lifecycle-действия.

Fedor09.10 просит компактный понятный UX вместо второго списка карточек,
PID/owner/command и вложенных scroll. Предложено объединить управление своими
вкладками с существующими строками ресурсов, сохранив доступ к внешним/другим
процессам. Это ещё не реализованное продуктовое предложение, не снятие capability
и не разрешение на автоматическую остановку.

### Брошенное против служебного

«Брошенные инструменты» — найденные MCP-процессы под системным корнем
(`ppid === 1`), не приписанные живым вкладкам/процессам приложения и не
опознанные как общая служба. Такое бывает после завершения родителя, в том
числе при restart. Это диагностическая категория, а не доказательство
бесполезности процесса: один `ppid` не устанавливает прежнего владельца или
безопасность остановки. Нельзя считать такой процесс автоматически разрешённым
к убийству. Панель ресурсов показывает число/память и отсылает к меню MCP;
сама предупреждающая строка не останавливает процессы и не удаляет историю.

09.10 на screenshot было1шт/52МБ, но свежий native snapshot уже не нашёл
таких кандидатов; остался только исключённый общий browser bridge. Screenshot
без PID/имени и отсутствие старого процесса не позволяют достоверно назвать
этот конкретный инструмент. Предупреждение не означает потерю сессий или
необходимость их очистки. Fedor явно требует сохранять историю/результаты и
довести существующие research-задачи до конца, допуская прежний большой расход;
RAM-ограничение/auto-stop не является согласованным решением.

**`bridge.js` брошенным не считается.** Это общий шлюз к браузеру, один на все
сессии; он специально живёт отдельно, чтобы их переживать. Формально выглядит
как сирота, но им пользуются — предлагать его убить вредно.

**`mcp-hub.js` — тоже служебный** (в `SHARED_SERVICE_PATTERNS`): общий MCP-бэкенд
на все AI-вкладки, detached от приложения (см. [`fact-mcp-hub.md`](fact-mcp-hub.md)).
Его шесть детей имеют живого родителя-хаба (`ppid ≠ 1`), поэтому в «брошенные»
не попадают. Убийство хаба из панели уронило бы инструменты всех вкладок разом —
управление им в отдельном чипе McpHubButton (статус, рестарт per-server).

Исторический масштаб: браузерный MCP (`sc-desktop/mcp/browser/index.js`) не
реагировал на обрыв связи с сессией и копился — 164 копии, 0.68 ГБ, самой
старой 4 дня. Причина чинится в `sc-desktop`, панель лечит симптом.

## Два темпа: чип всегда, разбор — пока смотрят

До 2026-09-11 замер шёл только при открытой панели, и закрытая кнопка стояла с
прочерком: цифра появлялась ровно тогда, когда её и так открывали посмотреть.
Юзер: «при запуске он не отображается, мне нужно сначала на него кликнуть».

Теперь у цифры два адресата и два темпа. Панель — построчный разбор, шаг 2 с,
живёт пока есть подписчик. Чип в шапке — два итога, шаг 5 с, включается при
монтировании и живёт, пока виден.

**Цена прямого прохода измерена** (12 сентября, 612
процессов): снимок 3.0 мс (максимум 10.3), раскладка 1.1 мс, пути и аргументы
процессов кэшируются по номеру и читаются один раз. При шаге 5 с это ~0.08%
wall-time одного потока. A/B на живом dev дал **0.049% в обоих режимах по
тогдашнему счётчику**, footprint main — 127.1 МБ в обоих замерах. После обнаружения
ошибки единиц 14.09 эти 0.049% нельзя использовать как абсолютный CPU-бюджет:
точную цену фонового режима нужно повторно сравнить с нормализованным источником.
Замеры длительности прохода и footprint этой ошибкой не отменяются.

А вот **гонять при этом по IPC всю раскладку не нужно**: в историческом замере
12.09 это было5.4КБ против≈75байт прежнего итога. В фон теперь уходит только
`{ok, scannedAt, totalBytes, commandBytes, orphanCount}`, без строк процессов.

Замер **общий для обоих каналов**. Когда панель открыта, её быстрый тик
публикует и итог тоже, а медленный таймер на это время снимается. Два
независимых таймера сделали бы лишний проход по процессам и развели бы число в
чипе с подписью под открытой панелью — а это одно и то же число.

Сам итог считает раскладка (`totals.allBytes`), потребители его только
показывают. Полный итог команд также считает main (`totals.commandBytes`),
включая скрытые мелкие команды, все проекты и защиту от повторного владельца.
Раньше чип и подпись складывали четыре поля каждый у себя; две
копии формулы разъезжаются на первом же новом слагаемом.

Renderer может перезагрузиться, не отписавшись, поэтому и подписка панели, и
фоновый канал снимаются по событию `destroyed` его webContents. Чип теперь
находится в общей шапке и доступен также на Home: фон снимается при
размонтировании интерфейса, а не при смене содержимого рабочей области.

Сбой замера **не бросается наружу** ни в тике, ни при подписке: иначе одна
ошибка внутри ломает открытие панели целиком. В чип сбой приходит как
`{ok:false, reason}` и рисуется прочерком — ноль означал бы «ничего не
потребляется», а это другое утверждение.

## Весь ПК: общий снимок, другой охват

Переключатель `Noted Terminal / Весь ПК` меняет только охват открытой панели.
Чип в шапке сохраняет прежний итог Noted + вкладки/команды; нижний итог «Весь ПК»
называет свою сумму «приложения», чтобы не выдавать её за физически занятую ОЗУ.
Footprint учитывает также сжатые/выгруженные charges и может превышать объём RAM.
Системные ОЗУ, сжатие и swap показаны отдельно; цвет ОЗУ следует raw pressure
`1 / 2 / 4`, недоступный показатель остаётся неизвестным.

Collector уже получает все доступные процессы текущего пользователя. Новый
охват раскладывает этот же snapshot по внешнему app bundle и его потомкам;
один PID учитывается один раз. Процесс без доказанного приложения остаётся
в «Другие процессы пользователя». Это не полный баланс ядра/других UID и
не критерий бесполезности процесса. Раскрытие показывает суммы процессов,
а одинаковая подпись не означает один физический экземпляр.

`set-view` использует сохранённый panel snapshot и его CPU delta, не повторяет
capture, подписку или запуск таймера. App projection и короткие native
system-memory calls выполняются только при открытом «Весь ПК». Закрытие снимает
их cache/subscription; прежний ambient5s получает только старый компактный DTO.
Смена режима не сбрасывает первую/вторую CPU-точку и не будит History, Timeline,
parser/worker, DB или retention. Чтение system counters не запускает shell tools.
Late reply старого открытия/режима не заменяет текущие данные панели.

Escape принадлежит открытому popup. Search capture в History может быть
зарегистрирован раньше popup capture, поэтому `defaultPrevented` и порядок
listeners сами по себе не сохраняют поиск под ним. Его Escape-ветка проверяет
точный DOM ID popup через `getElementById`, без обхода большого retained tree;
обычный Escape после закрытия продолжает закрывать History search. Popup
снимает свой key listener вместе с открытым состоянием.

SOURCE10.10 проверен отдельным Electron-стендом с настоящими resource components,
service и kernel counters; stores, Tooltip/controls и search state заменены.
Full retained History и установленная версия этой проверкой не подтверждены.
Точный материал приёмки — рабочий [checkpoint](../tmp/хранилище-и-очистка-диска.md).

## Малиновый значок — известная подготовка истории

Пользователь допускает первоначальный прогрев, но хочет отличать временную
подготовку от постоянного лага. Поэтому тот же `Activity` становится статично
малиновым во время очереди прогрева сохранённых окон и известных больших чтений
истории/подготовки Resume. Число памяти, ширина кнопки и открытие панели прежние.
В существующей подсказке — «Подготовка историй» или «Загрузка истории: имя»;
при неизвестном имени показано просто «Загрузка истории».

Цвет не выводится из CPU, числа работающих агентов или отсутствия кадров.
Очередь прогрева владеет своим остатком, main — точными start/finally отдельных
операций. Короткие обычные append/unchanged не включают индикатор; для больших
файлов порог известен до чтения. Сбой/отмена заканчивает только свою операцию,
не соседнюю, и не оставляет обещание вечной загрузки. Уже существующая ошибка
операции остаётся в своём интерфейсе; цвет не означает успешное завершение.

Сигнал передаётся по событиям с начальным снимком и ревизией, отдельно от
5-секундного замера памяти. Тот же канал передаёт bounded byte-progress большому
History loader; ресурсный чип подписан на отдельный стабильный снимок состава
операций, поэтому каждый процент не перерисовывает открытую таблицу процессов.
У Codex операция охватывает чтение и последующую подготовку metadata.
Запоздавший снимок не оживляет окончившуюся операцию;
уход на Home/возврат заново читает текущий main-снимок. Второго опроса ресурсов, сканирования
DOM или нового владельца AI lifecycle нет. Холодная загрузка после открытия
старой вкладки тоже может окрасить значок; создание пустой вкладки и обычный
ответ агента сами по себе этого не делают.

## Ширина чипа: содержимое, а не резерв

Ширину задают обе подписи; `minWidth` держит только нижнюю границу, чтобы
прочерк до первого замера не сжал кнопку. Прежний резерв под «99.99 ГБ» был
виден не сам по себе, а той дырой, которую оставлял между значком и числом.

Знак после точки **один**: со вторым («6.46 ГБ») последняя цифра дрожала бы при
каждом тике, ничего не сообщая — десятки мегабайт в шестигигабайтном итоге не
решение пользователя, а шум. С одним знаком подпись меняет длину на смене
разряда любой из величин («9.9 ГБ» → «10.1 ГБ»), не на каждом тике.

## Всего / команды: одна кнопка и одна панель

Запрос05.10.2026 — отдельно видеть вес задач, запущенных нейронками:
dev-серверов, сборок и deploy. Первое число сохраняет прежний общий расход
приложения, вкладок и брошенных инструментов; справа через `/` стоит входящий
в него расход запущенных команд с серым SVG терминала. Два числа нельзя
складывать: второе уже учтено в первом. Это одна кнопка, оба числа открывают
прежнюю панель «Ресурсы».

Такая же пара стоит у проектов, вкладок и нижнего «всего». При известном
нулевом расходе команд весь дополнительный блок скрыт: ни slash, ни SVG,
ни «0 МБ» не занимают строку. Пользователь отдельно потребовал убрать эти
пустые показатели, поскольку они появлялись у каждой сессии без команд.
Это правило действует также в кнопке и CPU-строках без команд; общий расход
остаётся. Когда команда появляется, дополнительный блок возвращается.
В режиме ЦП
проект/вкладка показывают общий CPU и CPU команд; кнопка шапки и нижний итог
продолжают показывать память. Процессы самого Noted остаются своей группой,
а не объявляются пользовательскими сборками.

Обычный `commandBytes` внутри вкладки по-прежнему соответствует видимым
индивидуальным строкам; полный `commandTotalBytes` включает также маленькие
команды. Порог отображения не фильтрует итог. Весь dev-процесс с потомками
принадлежит своей команде, даже если внутри него запущен агент; отнимать
такого агента из задачи означало бы снова недооценить dev-стенд.

Оба числа приходят из одного замера, новый таймер не создан. Известное
отсутствие команд даёт0 в данных и скрытый блок в UI, неподдерживаемый старым main breakdown — прочерк,
сбой замера — прочерки. Первый/неизвестный CPU не превращается в0.

## Проекты: один список, текущий первым

Раздел «Другие проекты» был тупиковой строкой «вкладок: 77 · 2.1 ГБ» — чтобы
узнать, какие это вкладки, приходилось переключать проекты руками (юзер,
2026-09-12). Отдельного раздела больше нет: есть один список «Проекты», где
текущий проект и остальные различаются только подачей.

- **Текущий проект первым и выделен**, но при первом открытии панели он, как и
  остальные проекты, свёрнут. Подпись у него белая и полужирная; остальные
  проекты приглушены и отсортированы по убыванию веса. Раскрытие — только по
  клику на строку проекта; оно сохраняется при закрытии и повторном открытии
  панели, пока компонент жив, и не переключается автоматически при смене
  текущего проекта.
- **Значок проекта** берётся из каталога проектов (`useProjectsStore`) — тот
  же цветной значок, что в шапке. Резерв — серая иконка папки.
- **Имя** тоже из каталога; для проекта, которого там ещё нет, — папка из пути
  рабочей области, а в последнюю очередь декод из идентификатора (он же
  закодированный путь). Строка не должна остаться безымянной.
- **Текущий проект показывается всегда**, даже без вкладок: пустой список —
  это ответ «вкладок нет», а пропавшая строка читается как «проекта нет».

Подписи вкладок берутся из store подпиской на **все** проекты (упакованная
строка, та же схема дешёвой подписки), не только на активный.

Справа от заголовка «Проекты» показан итог **всех** проектов, включая свёрнутые
проекты и скрытые мелкие вкладки; отфильтрованные строки не уменьшают сумму.
Заголовок «Общее для приложения» показывает итог собственных процессов
приложения. В режиме «Память» это объём памяти, в режиме «ЦП» — сумма нагрузки
соответствующей группы (до второго замера — прочерк). Брошенные инструменты в
эти группы не входят, но остаются частью нижнего «всего» и числа на чипе.

## Из замера к вкладке: Cmd+клик

Пользователь открывает панель, чтобы найти тяжёлую сессию, но одного имени
недостаточно, чтобы отыскать её среди окон (05.10.2026). Поэтому обычный клик
по строке по-прежнему раскрывает процессы, а Cmd+клик открывает саму вкладку.
При зажатом Cmd строка под курсором получает голубой фон; после перехода
панель закрывается.

Уже размещённая вкладка открывается в своём окне, включая другое workflow.
Без размещения она добавляется последним чипом текущего окна: прежние чипы
сохраняются. Это та же сессия, а не создание/запуск нового агента. В отличие
от Cmd+клика в sidebar, здесь модификатор означает навигацию, не перенос.

Замер процессов не является источником размещения: вкладку и её владельца
проверяют в живом store при клике. Если она уже закрыта, старый замер не
создаёт призрачного чипа. Общая навигация продолжает вести боковой список
к проекту открытой вкладки; Inbox, ЦП и раскрытые мелкие вкладки используют
то же правило.

## Полоса прокрутки и значки сессий

Панель использует тот же 5px-призрак (`.resource-panel-scroll` в `globals.css`),
что списки вкладок и читающие поверхности: общая 8px-полоса приложения с
непрозрачной дорожкой в маленькой плавающей панели читается как вторая рамка
справа.

**Место под полосу зарезервировано** (`scrollbar-gutter: stable`). Содержимое
панели меняется на каждом замере, и без резерва строки дёргались бы по ширине
ровно в тот момент, когда список перерастает высоту.

Перед именем вкладки стоит значок её агента (Claude/Codex/Gemini) из общего
реестра `assets/icons/registry.tsx` — своя отрисовка означала бы, что одна и та
же сессия выглядит в панели не так, как в шапке и в дереве файлов. Место под
значок занято всегда, даже у обычной вкладки без агента: иначе колонка имён шла
бы лесенкой.

Значок Codex в реестре — **без белой подложки**. В файле-ассете
(`codex-color.svg`) под знаком лежит третьим слоем белый скруглённый квадрат:
картинке он нужен, чтобы читаться на любом фоне, но внутри тёмной панели
выглядит наклейкой поверх интерфейса (юзер, 2026-09-12).

## Мелкие вкладки свёрнуты

Неактивная вкладка — пустая оболочка на ~3 МБ. Их бывает несколько десятков
(на тестовой машине 38), и в общем списке они вытесняют то, ради чего панель
открывают. Всё легче 12 МБ уходит в одну свёрнутую строку с суммой.

В режиме ЦП порог не применяется: там простаивающая вкладка интересна ровно
тем, что простаивает.
