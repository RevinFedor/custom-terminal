# Fact: панель потребления ресурсов (память/ЦП по вкладкам)

Плашка в правой части шапки, справа от кнопки инструментов Timeline. Показывает, сколько памяти
и процессора съедают вкладки проекта вместе со своими MCP-инструментами, само
приложение и брошенные остатки.

## Почему не `ps`

`ps rss` — «страницы, физически лежащие в RAM сейчас». Он **не видит сжатую
память** (у macOS её обычно гигабайты) и **заново считает** библиотеки, общие
между процессами Electron. Замеры на живой машине:

| процесс | `ps rss` | `phys_footprint` (Activity Monitor) |
|---|---|---|
| главный процесс приложения | 832 МБ | **1485 МБ** |
| отрисовка окна | 815 МБ | 920 МБ |
| сессия Claude | 335 МБ | 313 МБ |

На главном процессе `ps` занижает почти вдвое. Для панели, которую открывают
именно чтобы узнать «кто жрёт», это не «немного врёт» — это неправда про
крупнейшего потребителя.

## Как берутся цифры

`src/main/process-metrics-source.js` зовёт ядро напрямую через koffi:

- `proc_listpids` — все номера процессов одним вызовом;
- `proc_pid_rusage(RUSAGE_INFO_V4)` — `ri_phys_footprint` (то же, что в
  Activity Monitor) и накопленное процессорное время;
- `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)` — родитель и владелец;
- `sysctl(KERN_PROCARGS2)` — командная строка.

**Цена одного полного прохода — 4–6 мс на ~900 процессов.** Поэтому стоимость
не зависит от числа вкладок: делается один снимок системы, а раскладка по
вкладкам считается уже в памяти. Что 5 вкладок, что 50, что 500 — одна цена.

Для сравнения: `vmmap --summary` даёт ту же цифру, но 0.8 сек **на один
процесс**; на 400 процессов это минуты. `ps` как внешняя команда — 56 мс и
неточные данные.

### Смещения структур брать только из компилятора

Угаданные смещения читаются **без ошибки** и возвращают мусор — снимок молча
выходит пустым при `ok: true`. Так и произошло при разработке: `pbsi_comm`
предполагался на 28, реально на 16; `pbsi_uid` — 36, а не 60.

Проверять через `offsetof` в C-программе, значения зафиксированы тестом
`process-metrics-source.test.js`:

```
rusage_info_v4:  user_time=16  system_time=24  phys_footprint=72   (sizeof 296)
proc_bsdshortinfo: ppid=4  pgid=8  comm=16  uid=36                 (sizeof 64)
```

### Инструмент опознаётся по аргументам, а не по файлу

У почти всех MCP исполняемый файл — просто `node`. Различает их путь к скрипту
в аргументах запуска, поэтому нужен `KERN_PROCARGS2`. Без него все инструменты
сваливаются в «прочее».

Путь и аргументы за жизнь процесса не меняются — кэшируются. Ключ кэша — пара
(номер процесса, родитель): номера система переиспользует, и запись с другим
родителем означает уже другой процесс.

#### Буфер под аргументы спрашивать у ядра, а не назначать (12.09)

Блок `KERN_PROCARGS2` содержит не только аргументы: за ними идёт всё окружение
процесса, поэтому у обычной AI-сессии он весит ~5–6 КБ. Ядро отдаёт его целиком
или **молча обрезает** по размеру буфера, причём `sysctl` в обоих случаях
возвращает 0 — обрезание выглядит как успех.

Буфер был 4 КБ, и разбор упирался в край до первого аргумента: строка запуска
выходила пустой **у 368 процессов из 902**. Видно это было не как ошибка, а как
плохие подписи в панели: команда называлась «node» вместо «npm run dev», а
сессия Claude — «2.1.269» (имя каталога версии в её пути; сама раскладка при
этом считала верно, `describeAgent` ловит Claude и по пути).

Размер теперь берётся из `kern.argmax` (на macOS 15 это 1 МБ) — назначать его
нельзя, лимит зависит от системы. Буфер один на все снимки и переиспользуется:
`Buffer.alloc` обнуляет мегабайт, и делать это каждые пару секунд незачем.
Читается только то, что ядро записало в этот раз, по возвращённому размеру,
поэтому остатки прошлого процесса наружу не попадают. Цена замера не изменилась
(3–4 мс на ~900 процессов), первый снимок на 20 мс дороже из-за прогрева кэша.

Тесты: собственная строка запуска содержит аргумент, а не только путь к node;
строка читается более чем у 90% процессов (единичная пустота законна — процесс
мог завершиться между перечислением и чтением, массовая означает обрезание);
прогретый снимок остаётся дешевле 50 мс.

## koffi: зачем и что важно при упаковке

Системные вызовы недоступны из Node напрямую. koffi выбран потому, что:

- **готовый бинарник, компиляции нет** — лежит в отдельном пакете
  `@koromix/koffi-darwin-arm64`, ставится как обычная зависимость;
- **работает под Electron 28 (ABI 119) без `electron-rebuild`** — проверено
  запуском; это снимает весь класс граблей из
  [`fix-electron-native-rebuild-trap.md`](fix-electron-native-rebuild-trap.md).

**Обязательно в `asarUnpack`:** `node_modules/@koromix/koffi-*/**`. Внутри
архива приложения нативная библиотека не загрузится, и панель молча откажет в
упакованной версии, работая в dev.

При недоступности koffi источник возвращает `{ ok: false, reason }`, а не
падает: панель показывает причину, остальное приложение не затронуто.

## Загрузка процессора: только из двух замеров

`ps` отдаёт **среднее за всю жизнь процесса**. Окно, проработавшее 21 час,
показывает 40%, хотя сию секунду может быть 5%. Проверка: `TIME / ELAPSED`
в точности равно `%CPU` — это и есть определение среднего.

Честное значение = прирост процессорного времени между двумя снимками,
делённый на реальный прошедший интервал (`computeCpuPercent`).

Следствия, зафиксированные тестами:

- **первый замер отдаёт `null`, а не `0`** — «ещё не измерено» и «простаивает»
  разные утверждения, рисовать их одинаково нельзя;
- **счётчик пошёл назад → процесс пропускается** — номер переиспользован
  системой, это уже другой процесс;
- **после паузы прошлый снимок сбрасывается** — прирост за время простоя
  размазался бы по всему интервалу и дал ложный ноль для занятого процесса.

## Раскладка по владельцам

`process-metrics-grouping.js`. Вкладка = свой процесс + все потомки.

Порядок важен: **процессы приложения забираются первыми**, иначе вкладка, чей
shell порождён главным процессом, утащит в свой итог всё приложение.

Каждый процесс приписывается ровно одному владельцу (`claimed`), иначе итог
раздувается на величину общих поддеревьев. Если две вкладки смотрят на одну
сессию, вторая получает нулевой вес и пометку «учтено выше».

- **Инструмент через обёртку** (`npm exec …` → `node …`) — одна строка с
  суммарным весом, а не три одинаковых имени подряд.
- **Одноимённые процессы приложения** сливаются в строку с количеством
  («Отрисовка окна ×2»): две неразличимые строки читателю бесполезны.
- **Закрывшийся процесс вкладки** даёт нулевую строку, а не исчезает —
  пропавшая строка читается как «вкладки нет», хотя она открыта.
- **Обход итеративный и с защитой от повторов**: дерево приходит из системы и
  в теории может содержать цикл.

### Внутри вкладки: агент, команды, инструменты, оболочка (2026-09-12)

Корневой процесс PTY-вкладки — оболочка терминала (zsh) на ~3 МБ, а сам агент
запускается командой внутри неё и оказывается среди потомков. До 2026-09-12
раскрытая вкладка писала «сама сессия 3 МБ, прочее 944 МБ»: «сессией»
называлась оболочка, а весь реальный вес агента лежал в безымянном «прочем»
(юзер: «сама сессия 3 МБ, а прочие занимают 944… мне нужно разделение»).

Поддерево вкладки раскладывается **одним обходом от корня**, не плоским
поиском по шаблонам. На каждом процессе, по приоритету:

- уже внутри открытой строки (инструмент/команда) → всё поддерево её;
- MCP-инструмент → строка инструмента (обёртки схлопнуты, как раньше);
- агент (`AGENT_PATTERNS`: Codex/Claude/Gemini) → строка «сессия X»; каждое
  звено цепочки запуска (node-обёртка → бинарь → `codex-code-mode-host`) само
  подходит под шаблон и складывается в ту же строку по совпадению ярлыка.
  Агент, запущенный другим агентом (claude из-под codex), — **отдельная**
  строка: приписать его вес родителю значило бы соврать о том, кто весит;
- прозрачная оболочка (`sh -c`, login-shell) → не строка: вес в «прочее»,
  потомки классифицируются сами;
- всё остальное → **команда, запущенная во вкладке**, строкой с её именем
  (`describeCommand`: «npm run dev», «vite», «serve-stand»), и её поддерево
  принадлежит ей ЦЕЛИКОМ. Это главный мотив обхода вместо плоского поиска:
  dev-запуск поднимает вложенный экземпляр приложения со своими
  agent-процессами и инструментами, и плоский поиск приписал бы их «сессии»
  вкладки, раздув её на чужой гигабайт (скриншот юзера: вкладка 1.8 ГБ, из
  них 1.8 ГБ безымянного «прочего» — это был вложенный dev-стенд).

Команды легче 12 МБ (`MIN_COMMAND_ROW_BYTES`) строку не получают — уходят в
«прочее»: короткоживущие git/ps мерцали бы в списке. Строка «оболочка
терминала» (бывшая «сама сессия») показывается приглушённой, «прочее» —
только если ненулевое.

Имя команды `describeCommand` берёт из **командной строки**, а не из пути к
файлу: у части программ файл лежит в каталоге версии (у Claude это
`…/versions/2.1.269`), и basename пути дал бы номер версии вместо имени.
Порядок разбора: запускающая обёртка с задачей («npm run dev»), затем скрипт с
расширением, затем цель `node <файл>` без расширения («vite»), затем имя
бандла приложения («Electron»), и только в конце первое слово команды.

### Брошенное против служебного

Брошенный инструмент — тот, чья сессия умерла, а он остался под системным
корнем (`ppid === 1`). Такие безопасно убирать одной кнопкой: родителей нет,
ломать нечего. Убийство идёт через существующий `system:kill-process`, где уже
есть защита процессов приложения.

**`bridge.js` брошенным не считается.** Это общий шлюз к браузеру, один на все
сессии; он специально живёт отдельно, чтобы их переживать. Формально выглядит
как сирота, но им пользуются — предлагать его убить вредно.

**`mcp-hub.js` — тоже служебный** (в `SHARED_SERVICE_PATTERNS`): общий MCP-бэкенд
на все AI-вкладки, detached от приложения (см. [`fact-mcp-hub.md`](fact-mcp-hub.md)).
Его шесть детей имеют живого родителя-хаба (`ppid ≠ 1`), поэтому в «брошенные»
не попадают. Убийство хаба из панели уронило бы инструменты всех вкладок разом —
управление им в отдельном чипе McpHubButton (статус, рестарт per-server).

Исторический масштаб: браузерный MCP (`sc-desktop/mcp/browser/index.js`) не
реагировал на обрыв связи с сессией и копился — 164 копии, 0.68 ГБ, самой
старой 4 дня. Причина чинится в `sc-desktop`, панель лечит симптом.

## Два темпа: чип всегда, разбор — пока смотрят

До 2026-09-11 замер шёл только при открытой панели, и закрытая кнопка стояла с
прочерком: цифра появлялась ровно тогда, когда её и так открывали посмотреть.
Юзер: «при запуске он не отображается, мне нужно сначала на него кликнуть».

Теперь у цифры два адресата и два темпа. Панель — построчный разбор, шаг 2 с,
живёт пока есть подписчик. Чип в шапке — одно число, шаг 5 с, включается при
монтировании и живёт, пока виден.

**Фоновый опрос безопасен, и это измерено, а не предположено** (12 сентября, 612
процессов): снимок 3.0 мс (максимум 10.3), раскладка 1.1 мс, пути и аргументы
процессов кэшируются по номеру и читаются один раз. При шаге 5 с это ~0.08%
одного ядра. A/B на живом dev с мгновенным замером (не `ps %cpu` — он
показывает среднее за всю жизнь процесса и для этого вопроса бесполезен) дал
**0.049% и там, и там**: разница фона не различима на фоне обычного простоя,
footprint main не изменился (127.1 МБ в обоих замерах).

А вот **гонять при этом по IPC всю раскладку не нужно**: 5.4 КБ против 75 байт
итога. В фон уходит только `{ok, scannedAt, totalBytes, orphanCount}`.

Замер **общий для обоих каналов**. Когда панель открыта, её быстрый тик
публикует и итог тоже, а медленный таймер на это время снимается. Два
независимых таймера сделали бы лишний проход по процессам и развели бы число в
чипе с подписью под открытой панелью — а это одно и то же число.

Сам итог считает раскладка (`totals.allBytes`), потребители его только
показывают. Раньше чип и подпись складывали четыре поля каждый у себя; две
копии формулы разъезжаются на первом же новом слагаемом.

Renderer может перезагрузиться, не отписавшись, поэтому и подписка панели, и
фоновый канал снимаются по событию `destroyed` его webContents. Чип живёт
только в рабочей области, поэтому при уходе на Home он гасит фон явно.

Сбой замера **не бросается наружу** ни в тике, ни при подписке: иначе одна
ошибка внутри ломает открытие панели целиком. В чип сбой приходит как
`{ok:false, reason}` и рисуется прочерком — ноль означал бы «ничего не
потребляется», а это другое утверждение.

## Ширина чипа: содержимое, а не резерв

Ширину задаёт само число; `minWidth` держит только нижнюю границу, чтобы
прочерк до первого замера не сжал кнопку. Прежний резерв под «99.99 ГБ» был
виден не сам по себе, а той дырой, которую оставлял между значком и числом.

Знак после точки **один**: со вторым («6.46 ГБ») последняя цифра дрожала бы при
каждом тике, ничего не сообщая — десятки мегабайт в шестигигабайтном итоге не
решение пользователя, а шум. Соседей по шапке это не двигает: с одним знаком
подпись меняет длину только на смене разряда («9.9 ГБ» → «10.1 ГБ»).

## Проекты: один список, текущий первым

Раздел «Другие проекты» был тупиковой строкой «вкладок: 77 · 2.1 ГБ» — чтобы
узнать, какие это вкладки, приходилось переключать проекты руками (юзер,
2026-09-12). Отдельного раздела больше нет: есть один список «Проекты», где
текущий проект и остальные различаются только подачей.

- **Текущий проект первым и раскрыт по умолчанию** — именно его вкладки
  открывают панель. Подпись у него белая и полужирная; остальные проекты
  приглушены и свёрнуты, отсортированы по убыванию веса.
- **Раскрытость хранится как отклонение от умолчания** (набор
  `collapsedProjects`), поэтому текущий проект снова раскрыт при следующем
  открытии панели, даже если его однажды свернули. Хранить «список
  раскрытых» значило бы, что после переключения проекта раскрытым остаётся
  прежний.
- **Значок проекта** берётся из каталога проектов (`useProjectsStore`) — тот
  же цветной значок, что в шапке. Резерв — серая иконка папки.
- **Имя** тоже из каталога; для проекта, которого там ещё нет, — папка из пути
  рабочей области, а в последнюю очередь декод из идентификатора (он же
  закодированный путь). Строка не должна остаться безымянной.
- **Текущий проект показывается всегда**, даже без вкладок: пустой список —
  это ответ «вкладок нет», а пропавшая строка читается как «проекта нет».

Подписи вкладок берутся из store подпиской на **все** проекты (упакованная
строка, та же схема дешёвой подписки), не только на активный.

## Мелкие вкладки свёрнуты

Неактивная вкладка — пустая оболочка на ~3 МБ. Их бывает несколько десятков
(на тестовой машине 38), и в общем списке они вытесняют то, ради чего панель
открывают. Всё легче 12 МБ уходит в одну свёрнутую строку с суммой.

В режиме ЦП порог не применяется: там простаивающая вкладка интересна ровно
тем, что простаивает.
