# Fact: панель потребления ресурсов (память/ЦП по вкладкам)

Плашка в правой части шапки, справа от кнопки инструментов Timeline. Показывает, сколько памяти
и процессора съедают вкладки проекта вместе со своими MCP-инструментами, само
приложение и брошенные остатки.

## Почему не `ps`

`ps rss` — «страницы, физически лежащие в RAM сейчас». Он **не видит сжатую
память** (у macOS её обычно гигабайты) и **заново считает** библиотеки, общие
между процессами Electron. Замеры на живой машине:

| процесс | `ps rss` | `phys_footprint` (Activity Monitor) |
|---|---|---|
| главный процесс приложения | 832 МБ | **1485 МБ** |
| отрисовка окна | 815 МБ | 920 МБ |
| сессия Claude | 335 МБ | 313 МБ |

На главном процессе `ps` занижает почти вдвое. Для панели, которую открывают
именно чтобы узнать «кто жрёт», это не «немного врёт» — это неправда про
крупнейшего потребителя.

## Как берутся цифры

`src/main/process-metrics-source.js` зовёт ядро напрямую через koffi:

- `proc_listpids` — все номера процессов одним вызовом;
- `proc_pid_rusage(RUSAGE_INFO_V4)` — `ri_phys_footprint` (то же, что в
  Activity Monitor) и накопленное процессорное время;
- `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)` — родитель и владелец;
- `sysctl(KERN_PROCARGS2)` — командная строка.

**Цена одного полного прохода — 4–6 мс на ~900 процессов.** Поэтому стоимость
не зависит от числа вкладок: делается один снимок системы, а раскладка по
вкладкам считается уже в памяти. Что 5 вкладок, что 50, что 500 — одна цена.

Для сравнения: `vmmap --summary` даёт ту же цифру, но 0.8 сек **на один
процесс**; на 400 процессов это минуты. `ps` как внешняя команда — 56 мс и
неточные данные.

### Смещения структур брать только из компилятора

Угаданные смещения читаются **без ошибки** и возвращают мусор — снимок молча
выходит пустым при `ok: true`. Так и произошло при разработке: `pbsi_comm`
предполагался на 28, реально на 16; `pbsi_uid` — 36, а не 60.

Проверять через `offsetof` в C-программе, значения зафиксированы тестом
`process-metrics-source.test.js`:

```
rusage_info_v4:  user_time=16  system_time=24  phys_footprint=72   (sizeof 296)
proc_bsdshortinfo: ppid=4  pgid=8  comm=16  uid=36                 (sizeof 64)
```

### Инструмент опознаётся по аргументам, а не по файлу

У почти всех MCP исполняемый файл — просто `node`. Различает их путь к скрипту
в аргументах запуска, поэтому нужен `KERN_PROCARGS2`. Без него все инструменты
сваливаются в «прочее».

Путь и аргументы за жизнь процесса не меняются — кэшируются. Ключ кэша — пара
(номер процесса, родитель): номера система переиспользует, и запись с другим
родителем означает уже другой процесс.

## koffi: зачем и что важно при упаковке

Системные вызовы недоступны из Node напрямую. koffi выбран потому, что:

- **готовый бинарник, компиляции нет** — лежит в отдельном пакете
  `@koromix/koffi-darwin-arm64`, ставится как обычная зависимость;
- **работает под Electron 28 (ABI 119) без `electron-rebuild`** — проверено
  запуском; это снимает весь класс граблей из
  [`fix-electron-native-rebuild-trap.md`](fix-electron-native-rebuild-trap.md).

**Обязательно в `asarUnpack`:** `node_modules/@koromix/koffi-*/**`. Внутри
архива приложения нативная библиотека не загрузится, и панель молча откажет в
упакованной версии, работая в dev.

При недоступности koffi источник возвращает `{ ok: false, reason }`, а не
падает: панель показывает причину, остальное приложение не затронуто.

## Загрузка процессора: только из двух замеров

`ps` отдаёт **среднее за всю жизнь процесса**. Окно, проработавшее 21 час,
показывает 40%, хотя сию секунду может быть 5%. Проверка: `TIME / ELAPSED`
в точности равно `%CPU` — это и есть определение среднего.

Честное значение = прирост процессорного времени между двумя снимками,
делённый на реальный прошедший интервал (`computeCpuPercent`).

Следствия, зафиксированные тестами:

- **первый замер отдаёт `null`, а не `0`** — «ещё не измерено» и «простаивает»
  разные утверждения, рисовать их одинаково нельзя;
- **счётчик пошёл назад → процесс пропускается** — номер переиспользован
  системой, это уже другой процесс;
- **после паузы прошлый снимок сбрасывается** — прирост за время простоя
  размазался бы по всему интервалу и дал ложный ноль для занятого процесса.

## Раскладка по владельцам

`process-metrics-grouping.js`. Вкладка = свой процесс + все потомки.

Порядок важен: **процессы приложения забираются первыми**, иначе вкладка, чей
shell порождён главным процессом, утащит в свой итог всё приложение.

Каждый процесс приписывается ровно одному владельцу (`claimed`), иначе итог
раздувается на величину общих поддеревьев. Если две вкладки смотрят на одну
сессию, вторая получает нулевой вес и пометку «учтено выше».

- **Инструмент через обёртку** (`npm exec …` → `node …`) — одна строка с
  суммарным весом, а не три одинаковых имени подряд.
- **Одноимённые процессы приложения** сливаются в строку с количеством
  («Отрисовка окна ×2»): две неразличимые строки читателю бесполезны.
- **Закрывшийся процесс вкладки** даёт нулевую строку, а не исчезает —
  пропавшая строка читается как «вкладки нет», хотя она открыта.
- **Обход итеративный и с защитой от повторов**: дерево приходит из системы и
  в теории может содержать цикл.

### Брошенное против служебного

Брошенный инструмент — тот, чья сессия умерла, а он остался под системным
корнем (`ppid === 1`). Такие безопасно убирать одной кнопкой: родителей нет,
ломать нечего. Убийство идёт через существующий `system:kill-process`, где уже
есть защита процессов приложения.

**`bridge.js` брошенным не считается.** Это общий шлюз к браузеру, один на все
сессии; он специально живёт отдельно, чтобы их переживать. Формально выглядит
как сирота, но им пользуются — предлагать его убить вредно.

Исторический масштаб: браузерный MCP (`sc-desktop/mcp/browser/index.js`) не
реагировал на обрыв связи с сессией и копился — 164 копии, 0.68 ГБ, самой
старой 4 дня. Причина чинится в `sc-desktop`, панель лечит симптом.

## Замер только при открытой панели

`process-metrics-service.js`: подписчик появился — начали, ушёл последний —
остановились. Фоновый опрос ради закрытой панели был бы тратой без адресата.

Renderer может перезагрузиться, не отписавшись, поэтому подписка снимается и по
событию `destroyed` его webContents.

Сбой замера **не бросается наружу** ни в тике, ни при подписке: иначе одна
ошибка внутри ломает открытие панели целиком.

## Мелкие вкладки свёрнуты

Неактивная вкладка — пустая оболочка на ~3 МБ. Их бывает несколько десятков
(на тестовой машине 38), и в общем списке они вытесняют то, ради чего панель
открывают. Всё легче 12 МБ уходит в одну свёрнутую строку с суммой.

В режиме ЦП порог не применяется: там простаивающая вкладка интересна ровно
тем, что простаивает.
