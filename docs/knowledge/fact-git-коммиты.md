# Fact: Git-коммиты проекта

Git-интеграция в workspace — это project-level control, а не tab-level инструмент. Постоянная поверхность в toolbar показывает только то, что нужно держать в поле зрения всегда: текущую ветку и количество незакоммиченных файлов. Всё остальное живёт в раскрытой панели по клику: список изменённых файлов, история, выбор ветки, генерация commit message, локальный commit и remote-действия.

## Toolbar contract

Git-кнопка стоит в самом правом краю project toolbar, после Docs/Copy Sessions/usage-чипов. Она не появляется вне Git-репозитория и не занимает toolbar в проектах без `.git`. Лицо кнопки — `branch + changed count`; clean-state остаётся коротким `branch · clean`. Это сделано по тому же принципу, что usage-чипы: постоянная полоса показывает статус, а не полный workflow. Подробный переносимый принцип — `methodology/переносимый-дизайн.md::Постоянная панель показывает статус, не workflow`.

Панель открывается рядом с кнопкой, а не из центра окна: Git-действия относятся к проекту и текущему рабочему дереву, поэтому пользователь должен воспринимать её как расширение toolbar. Панель закреплена к правому верхнему углу триггера и ресайзится влево/вниз; размер сохраняется, чтобы переключение Changes/History не меняло высоту и не дёргало layout. Центральный разделитель между левой навигационной колонкой и правым preview тоже ресайзится и сохраняется отдельно: пользователь может расширить список файлов/history без изменения общей высоты панели. Settings-шестерёнка находится в remote-status строке Git-панели, потому что настройки влияют только на этот commit workflow; в маленьком toolbar-чипе остаётся только статус.

Remote-status строка под header показывает provider (`GitHub`/`GitLab`/`Git remote`), host/path, способ доступа (`HTTPS · macOS Keychain`, `SSH key`, другой helper) и git-author. Push/fetch всё равно идут через обычный Git: Noted Terminal не хранит токены, а только объясняет куда привязан repo и даёт recovery-действия (`Open remote`, `Copy remote URL`, `GitHub Desktop` для GitHub). Это важно для self-hosted GitLab: OAuth в Noted Terminal не является обязательным условием push.

Открытие панели работает как stale-while-revalidate: если по проекту уже есть Git status, панель сразу показывает cached content и обновляет repository state в фоне. Общий loader `Checking Git repository` допустим только для первого открытия без данных и для явных действий пользователя (`Refresh`, `Commit`, `Push`, `Checkout`), где ожидание является самим действием. Иначе пользователь видит последовательность «актуальная информация → лоудер → та же актуальная информация» и считывает это как архитектурное мигание, хотя интерфейс уже доказал что данные доступны.

Фоновый refresh не должен инвалидировать правый diff-preview, если porcelain-signature файлов (`xy:path`) не изменилась. Иначе после открытия сначала виден cached preview, затем тот же файл remount'ится от фонового `git:status` и пользователь видит постфактум-мигание. Preview-version можно bump'ать на явных действиях, `fs:change` и реальном изменении списка файлов; обычный open/focus refresh обновляет только status-state. Переключение `History → Changes` тоже не очищает diff-preview: loader допустим только когда repo/file/signature key изменился, а не из-за смены вкладки.

Тот же cache-key нужен для левой колонки и dropdown'ов: History list и Branch menu помнят, для какого repo они загружены. При переключении `Changes ↔ History` или повторном раскрытии веток cached список текущего repo остаётся видимым, а фоновые `git:history` / `git:branches` не подменяют его пустым состоянием `No commits yet` / `No branches` или transient loader'ом. При смене repo/project cache-key сбрасывается, чтобы не показать список чужого репозитория.

## Repository selector

Git-панель привязана к текущему проекту, но выбранный Git-репозиторий внутри неё может быть другим: монорепозиторий и вложенные `.git`-папки живут в одном workspace. По умолчанию открывается репозиторий текущего проекта; если пользователь уже выбирал другой repo для этого проекта, выбор восстанавливается из project-scoped state. Это важно не оптимизировать в «всегда project path»: иначе пользователь в монорепе каждый раз будет заново искать нужный пакет.

Repo-select — один список с поиском, без вкладок: репозиторий текущего проекта всегда первым и отмечен home-иконкой слева, за ним идут favorites этого проекта со star-иконкой, затем тонкий разделитель и вложенные `.git`-репозитории внутри текущей папки проекта. Header `Current Repository` зеркалит этот же статус: home-иконка для repo проекта, star для favorite, отсутствие иконки для обычного выбранного repo. Он не сканирует весь компьютер и не подмешивает репозитории из других проектов приложения: такой список быстро становится шумным и даёт ложные home-иконки на чужих test/tmp repo. `Update` только пересканирует текущую папку проекта, когда пользователь добавил новый вложенный repo.

Favorites остаются project-scoped: добавление идёт через compact context-menu на строке repo или через выбор папки в `Add`, порядок меняется drag-handle'ом справа и сохраняется вместе с состоянием панели. Внешний repo, добавленный вручную, виден только в текущем проекте и не распространяется на другие workspace. Home не дублируется как favorite, потому что он уже является постоянной первой строкой.

## Commit workflow

Changes-tab показывает изменённые файлы слева и diff-preview выбранного файла справа, как source-control GUI, а не как простой checklist. Чекбокс меняет набор файлов для commit/generate; клик по строке открывает файл в правом preview. Эти жесты нельзя объединять: пользователь ожидает, что клик по файлу читает изменения, а не молча меняет состав commit'а.

Выделение файлов имеет два режима. До первого ручного клика по чекбоксу или строке `selected` панель считает выбор автоматическим: все текущие changed-файлы выбраны, и новые файлы, появившиеся после фонового refresh, тоже автоматически добавляются в выбор. После ручного клика выбор становится ручным: исчезнувшие файлы вычищаются из selection, но новые changed-файлы не добавляются сами. Иначе сценарий «утром был 1 файл, к вечеру стало 20» даёт ложное `1/20 selected`, хотя пользователь ещё не ограничивал commit руками.

В списке файлов статус показывается компактной иконкой справа: зелёный плюс для added/untracked, жёлтая точка для modified/renamed/other, красный минус для deleted. Сырые porcelain-коды (`M`, `??`) не выводятся в начале строки: они полезны для Git CLI, но в GUI читаются как мусор, особенно рядом с чекбоксом.

Локальный commit работает без GitHub auth: remote-доступ нужен только для push/fetch/publish. При commit выбранных файлов нельзя просто сделать `git add <paths>` и затем обычный `git commit`, потому что уже заранее staged-файлы из другого workflow тоже попали бы в commit. Commit должен фиксировать только выбранные пути; заранее staged unrelated-файлы остаются staged после операции.

History-tab показывает журнал последних commit'ов слева и diff выбранного commit'а справа. Unpushed commit'ы помечаются compact upload-иконкой в правой части строки: если upstream настроен, источник истины — `upstream..HEAD`; если upstream нет, но есть `origin/<branch>`, сравнение идёт с ним; если remote branch тоже нет, локальная ветка считается unpublished и видимые commit'ы получают marker. Это защищает UI от ложного «всё запушено» на локальных ветках без upstream.

Правый preview выбранного commit'а показывает subject и body commit message отдельно: subject остаётся плотным заголовком, body идёт ниже менее жирным текстом. Длинное описание режется по настройке Git-панели `Commit description lines` (1..6, default 3), потому что History preview должен оставаться scan-панелью перед diff, а не вытеснять список файлов и сам diff большим commit body.

History list хранит hash из `git log %h` как короткий SHA, а `git:commit-details` возвращает полный `hash` плюс `shortHash`. Preview-guard обязан быть repo-scoped и матчить full/short/валидный hex-prefix длиной не меньше `shortHash`, иначе успешный ответ details выглядит как stale для UI: заголовок остаётся `Select a commit`, а body висит на `Loading commit` без новых Git-логов.

`Undo Commit` доступен только через правый клик в History и только для верхнего commit'а, то есть текущего `HEAD`. Действие делает soft reset, чтобы изменения вернулись в Changes и пользователь мог поправить message/selection. Уже запушенный HEAD не откатывается из панели: это rewrite-history сценарий, его нельзя прятать за тем же жестом что локальный undo. Branch dropdown переключает локальные ветки из той же панели; push-кнопка сделана split-button'ом: основное действие — `Push` или `Publish` в зависимости от upstream, дополнительное меню содержит `Fetch origin`.

## AI commit message

Generate использует built-in prompt `Git Commit` (`git-commit`) из Settings → AI, а не Docs/API Claude settings. Пользователь может править текст prompt'а, model и thinking так же, как у `Tab Title` / `Prompt Summary`; default — `gemini-3.1-flash-lite` + `NONE`, потому что это короткая metadata-задача, а не reasoning-turn.

Вызов пишется в общий журнал AI prompt usage под тем же stable id `git-commit`. Это не billing-источник и не usage-chip: статистика нужна, чтобы видеть модель, токены, ошибки и источник utility-вызова рядом с другими metadata prompt'ами. Если после правки Git IPC/provider dev всё ещё показывает старую ошибку вроде `fetch failed`, сначала перезапусти Electron main process: renderer HMR не доказывает, что main handler уже обновился.

Prompt policy: если toggle `Docs-only AI context` включён и среди выбранных изменений есть `docs/`, AI получает только изменённые docs-файлы. Если toggle выключен или docs-изменений нет, AI получает выбранные изменения целиком с caps/truncation. Причина — commit message для документационного прохода должен описывать именно изменение документации, а не шум от параллельных файлов в рабочем дереве.

## Remote auth recovery

Push/fetch ошибки авторизации не запускают собственный login-flow в Noted Terminal. HTTPS token, SSH key, credential helper и GitHub account state слишком разные, чтобы воспроизводить GitHub Desktop внутри toolbar-панели. Правильная реакция — общий persistent toast «GitHub не принял доступ» с действием `GitHub Desktop`; клик открывает GitHub Desktop на текущем project path, где пользователь логинится штатным способом.

Локальные действия при этом не блокируются remote auth. Если GitHub не принимает push, пользователь всё равно может продолжать делать локальные commit'ы и вернуться к publish позже.
