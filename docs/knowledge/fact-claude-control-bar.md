# Feature: ClaudeControlBar (органы управления агентом)

## Где рисуется: строка композера, а не своя полоса (2026-08-16)

Компонент **не переехал** — он остался ровно там же в дереве, а переехал только
его вывод. Композер публикует пустое место внутри своей верхней строки, панель
рисуется туда порталом (`utils/composerControlsHost.mjs`). Пока место есть,
полосы под терминалом нет вообще; когда места нет (Gemini, обычный shell, или
композер ещё не показан) — панель рисуется по-старому отдельной полосой. Признак
в DOM: `data-agent-control-bar-placement="composer" | "strip"`.

**Почему портал, а не перенос кода.** Внутри компонента месяцы накопленных
фиксов: привязка занятости к вкладке, подтверждённые настройки из транскрипта,
кэш-канал, доказательства writer'а Codex. Плюс он монтируется ОДИН раз на проект
и перепривязывается сменой `tabId` — переписать его внутри истории значило бы и
воскресить старые баги, и потерять это свойство. Портал меняет место в DOM, не
место в дереве React: все эффекты, подписки и локальное состояние переживают
переключение нетронутыми.

**Ловушка порядка, из-за которой всё однажды сломалось.** При перестройке
раскладки (вход в разделённый режим, смена основной поверхности) React монтирует
новый композер ДО размонтирования старого. Уборка «по имени вкладки» стирала
место, которое новый композер только что опубликовал, и кнопки навсегда
оставались в полосе — публиковать второй раз некому. Поэтому снятие места идёт
через `releaseComposerControlsHost(tabId, node)`: освобождает, только если это
всё ещё ЕГО узел. Поймано живьём: место было на экране и пустое, а панель
рисовалась в старом месте.

**Место — это подписка, а не поиск по id.** Узел композера заменяется при смене
раскладки, и одноразовый `getElementById` в эффекте продолжил бы указывать на
отсоединённый — кнопки рисовались бы в невидимый узел.

**В композере нет переноса в две строки.** Вторая строка вернула бы ровно ту
высоту, ради которой панель туда и переезжала. При сужении показания занимают
собственную несжимаемую ширину, а соседние группы кнопок получают горизонтальную
прокрутку. Пользователь отдельно потребовал видеть процент всегда: наличие
второго показометра в Timeline не даёт права скрывать этот. Процент означает
использованную часть контекста и не меняет смысл/видимость от разрешения
автокомпакта; переключатель правила принадлежит Run After.

При проверке доступности кнопки сначала учитывать viewport её прокручиваемой
группы: `getBoundingClientRect()` содержит и обрезанную часть. Центр скрытой
части Send может попадать в правый model cluster без реального перекрытия внутри
левого viewport. Нужно штатно прокрутить свою группу, подтвердить изменение
scrollLeft и только затем проверять hit/действие; не возвращать ради теста вторую
строку и не скрывать показания контекста.

Исторически `shouldShedControlBarReadings` удалял кэш и процент вместе при
нехватке ширины; `[ControlBarReadings]` диагностировал именно это решение, а не
потерю bridge-события. Контракт скрытия отменён: старые логи не являются
описанием текущей компоновки. Отдельная standalone-полоса вне композера
по-прежнему умеет переносить группы в две строки (секция ниже).

## Что из панели удалено (не возвращать)

- **`⎘ copy-session-id`** и **`↻ refresh-timeline`** — удалены. ID сессии
  копируется правым кликом по вкладке (`ID | UUID/Path`), Timeline
  обновляется сам. Юзер: *«кнопку перезагрузки можно удалить, я её не
  использую»*, *«эту тоже удалить, я копирую через правый клик по вкладке»*.
- **`⑂→▭` и `⑂→SDK`** — форки ТЕКУЩЕЙ сессии переехали в контекстное меню
  вкладки: там теперь три части `Compact Fork | Fork | SDK`. Третья часть
  видна только для Claude — SDK не работает с Codex. Логика SDK-форка перенесена
  дословно (`handleContextForkToSDK` в TabBar): копия файла беседы создаётся ДО
  вкладки, потому что SDK-вкладке некому передать session id аргументом запуска.
  PTY Fork/Compact Fork с12.10, напротив, показывают новую вкладку до копирования,
  чтобы сразу разрешить ручное имя; её loading не заимствует SID источника.
  Подготовка идёт через общий Main launch, детали — `fact-tabs.md::Ранняя вкладка Fork и ручное имя`.
  Clipboard-варианты `*-F` остались в панели: это не форки текущей сессии, а
  запуски пустой вкладки из чужого id.
- **Пилюли `⌸→ ⎘ prompt` / `⌸→ + clear` и кнопка `⌸ → input`** — свёрнуты в один
  триггер меню черновика (`data-terminal-draft-trigger`). Все три читают одно и
  то же — живой composer TUI — и различаются только тем, куда попадает текст;
  три постоянные кнопки тратили три места на один предмет. Заглавное действие —
  «в поле ввода»: единственное, после которого текст оказывается там, куда
  смотрит пользователь.
- **Отдельный триггер провайдера** — стал первой секцией меню моделей: «где
  крутится» и «что крутится» это один выбор.
- **Инлайновый ряд усилий (до 6 пилюль) + `Think`** — свёрнуты в один триггер
  `effort`; `Think` стал последней строкой того же столбца, потому что решает,
  применяются ли уровни над ним вообще. **`Fast` в этот столбец не входит и был
  оттуда возвращён** отдельным квадратом справа — см. секцию про него ниже:
  одинаковое место для Think и Fast оказалось ложной симметрией, у них разные
  предметы.

Меню моделей стало вертикальным, поэтому совместимые усилия открываются **сбоку**
от наведённой строки (`components/UI/SideFlyout.tsx`), а не над триггером. Обёртка
начинается у самого края строки и несёт зазор внутренним отступом — иначе курсор
пересекал бы мёртвую полосу и подменю закрывалось бы по дороге (`сценарии-багов-design.md::1.2`).

## Кнопка состояния = запуск и остановка

Кнопка слева в строке композера больше не переключает терминал. Раньше на ней
висели две несвязанные работы: «что происходит» и «покажи другую панель».
Переключатель поверхностей уехал сначала в рейл Run after, а затем к полю ввода —
он теперь стоит парой со стрелкой вниз над правым краем поля
(`SideSurfaceToggleButton`, `data-side-surface-toggle`); в рейле осталась только
кнопка Timeline. Кнопка состояния взяла половину, которая
действительно принадлежит индикатору — действие над тем, чьё состояние он
показывает: `data-agent-status-action="stop" | "start" | "pending"`.

Двусмысленность снята видом: при наведении на живую сессию вся кнопка краснеет и
значок активности заменяется красным квадратом, при остановленной — зелёный ▶.
Это прямое требование правила «destructive ≠ status»: контрол, который прерывает
состояние, не должен выглядеть как индикатор этого состояния. Если действие ещё
не доказано (переход состояния, неизвестный владелец, временная блокировка),
левый клик остаётся бездействующим, а не меняет смысл на копирование. Детали
статуса копируются только правым кликом.

После main/app restart кнопка не полагается только на свежий Claude
bridge/statusline: живой процесс повторно доказывается внутри дерева точного PTY.
До доказательства состояние `unknown`, после process proof без composer proof —
`starting`; оба состояния запрещают Resume. Имя процесса берётся из effective
owner вкладки, поэтому старый `expectedProcess=codex` от общего status API не
может превратить живой Claude в ложный `inactive`.


**Ни свечение, ни рисунок этой кнопки не зависят от раскладки (2026-08-17).** Было два бага одной природы. Тень включалась, когда открыта боковая панель, — состояние менялось от действия, которое кнопке не принадлежит (выдвижением управляет своя кнопка у поля ввода). А рисунок иконки переключался при реверсе: та же кнопка после смены центральной поверхности выглядела другой, хотя про агента ничего не изменилось. Оба свойства (`active`, `surface`) удалены из `HistoryTerminalActivityIcon`, чтобы не вернулись: иконка всегда терминальная, потому что кнопка про процесс в терминале, а не про то, что сейчас в центре. Разница с кнопкой раскладки принципиальная: там иконка ОБЯЗАНА меняться при реверсе, потому что сам жест меняет смысл.

## Intro

Набор органов управления агентом: Provider/Model/Effort/Think, Start/Stop, черновик терминала, Mic/Enter/^C, кэш и % контекста. Историческое имя — «30px-полоса под Terminal-колонкой»: сначала всё это жило в правой `InfoPanel`-колонке (см. `fact-workspace.md::Two-Column Layout`), потом переехало в полосу под терминалом, а с 2026-08-16 рисуется в строке композера (см. секцию выше). Полоса осталась запасной поверхностью для вкладок без композера — Gemini и обычный shell.

Bar ложится **под** контентом Terminal-колонки, но не растягивается под Timeline'ом — `Timeline` отрисовывается соседом справа от vertical stack `[Terminal | ClaudeControlBar]`, не под ним.

После перехода Claude/Codex PTY на primary History историческое имя «Terminal-колонка» означает центральный structural slot workspace: bar остаётся под History/status/composer, а floating xterm содержит только raw terminal escape hatch. Переносить bar внутрь плавающего окна нельзя — lifecycle-controls должны оставаться доступны и при скрытом terminal.

## Операционная фаза ручного compact (2026-07-31)

Общий busy loader отвечает на вопрос «агент занят», но не объясняет почему.
Для точного ручного `/compact` main process публикует отдельную неперсистентную
фазу `COMPACTING`. History composer показывает текст фазы одновременно с
анимированным loader. Это не отдельный lock: ввод и background History сохраняют
свои прежние правила.

History поддерживает standalone slash-команды по принятому17.08 контракту;
старый `← Terminal only` больше не действует. Доставка команды и фактический
старт compact проверяются отдельно, через прежний общий scenario.

Codex native/automatic compaction также видна по typed provider request при
точном live writer/lifecycle, без чтения текста TUI. Она использует тот же
операционный индикатор и отдельное время Compacting в History, но не создаёт
ручной command receipt. Whole-turn timer/Worked не переписывается. См.
`fact-codex.md::Native compact виден в TUI, но History остаётся Working`.

Фаза начинается только после доказанного PTY submit точной команды в текущем
Claude owner (terminal + session + launch generation + input revision). Завершение
приходит от ручного `compact_boundary`/summary/stdout либо от точного
abort/failure lifecycle. Текст `Compacting conversation` в PTY сам по себе
не владеет операцией, потому что одинаков для ручного и автоматического compact.
History при remount запрашивает live snapshot у main; app restart ничего не
восстанавливает из старого JSONL. См. `fix-compact-logic.md::Живая фаза /compact`.

## Layout

Две зоны, разделённые `flex: 1` спейсером:

**Left cluster.** `SessionActionChip` (Start/Continue/Stop), триггер меню черновика терминала, live input actions (`mic | Enter | ^C`), и прижатые вправо показания — cache chip + context %-meter. Историческое содержимое (`⎘ session-id`, `↻ refresh-timeline`, форки `terminal→`/`terminal→SDK`, пилюли `⎘ prompt`/`+ clear`, `→ input`) удалено или свёрнуто — см. секцию «Что из панели удалено» вверху файла.

**Session-id copy `⎘`: Cmd-hover показывает полный id сверху.** Обычный клик по `⎘` копирует текущий `sessionId` и на короткое время меняет иконку на `✓`. При зажатом Cmd и наведении на эту же кнопку появляется read-only tooltip **над** кнопкой с полным UUID (`claudeSessionId` / `geminiSessionId` / `codexSessionId`). Это не action-menu и не поле ввода: цель — быстро проверить «какую именно сессию я сейчас скопирую» без клика и без засорения compact bar длинной UUID-строкой. Отличать от `CopySessionButton` в шапке приложения: там Cmd-hover открывает custom session-id input для копирования другой сессии, а здесь — только preview текущего id.

**Меню черновика: три пункта, три IPC.** Все три работают с живым TUI draft, а не с уже показанным prompt-блоком History, который копируется обычным выделением/Copy. Заглавный пункт «в поле ввода» шлёт событие `history-panel:pull-terminal-draft` (перенос + атомарная очистка). Пункт «скопировать» шлёт `<agent>:copy-input` — helper читает tempfile, отправляет text в socket, **не truncate'ит** input (юзер видит свой draft). Пункт «скопировать и очистить» шлёт `<agent>:grab-input` — тот же helper в `mode='grab'` truncate'ит tempfile **до** отправки text в socket (атомарно copy+clear в одном Ctrl+G round-trip). Сейчас `<agent>` = `claude` или `codex`; оба copy-пункта **приглушены** когда PTY-процесс не запущен, потому что без живого TUI composer'а Ctrl+G нечего читать. Сам триггер при этом остаётся на месте: он появлялся и исчезал бы под курсором на каждом Start/Stop, а это ровно та причина, по которой Mic/Enter тоже никуда не уезжают. Codex использует тот же UX, но main должен ставить helper-lock на vendor PID, а не только на direct child wrapper — см. `fact-codex.md::Stop и ввод`. См. `fact-prompt-queue.md::Focus terminal перед clear-input` про refocus terminal для немедленного re-read'а Claude'ом пустого tempfile.

**Graveyard: двухступенчатый copy + clear.** До переключения на `grab-input` "+ clear" шёл двумя последовательными IPC: `claude:copy-input` (Ctrl+G) → `claude:clear-input` (второй Ctrl+G ~5ms спустя). На быстрых turn'ах второй Ctrl+G падал в input как литерал `^G` потому что Claude ещё был в external-editor cycle от первого. Плюс `claude:clear-input` имел дополнительный guard `if (claudeTurnBusy === true) return claude_busy` которого нет у `copy-input` (см. `fix-claude-hook-silent-dropouts.md`) — асимметрия: copy успевал mid-turn, clear silently dropped. Симптом юзера: *«копирует, но не очищает окно промпта»*, в production-логе видно `[capture-input:copy]` без последующего `[clear-input]`. Atomic `grab-input` устраняет оба корня — один helper-run труncate'ит файл при отправке text в socket.

**Live input actions: mic + Enter + ^C.** Рядом с mic-кнопкой есть кнопка `Enter`, которая отправляет raw `\r` в текущий PTY input, и кнопка `^C`, которая отправляет raw `\x03`. Все три видимы только когда вкладка — живой Claude или Codex PTY (`isCommandRunning && !isSDKTab && sessionType in {'claude','codex'}`). Без живого TUI composer'а эти кнопки были бы ложным affordance'ом: SDK имеет React composer и свой submit/interrupt path, Gemini не имеет этой связки, обычный shell не должен получать случайный `\r` или `Ctrl+C` из AI-bar.

`Enter` намеренно не использует `safePasteAndSubmit`: он не вставляет новый текст и не делает программный paste+submit race, а только сабмитит уже видимое состояние TUI input. Исключение — активная диктовка: если mic сейчас `recording` или `stopping`, ControlBar переводит Enter в pending-state и ждёт `MicButton` stop-and-deliver, чтобы не отправить старый composer до того как распознанный текст вставлен. Детали — [`fact-dictation.md::Enter во время диктовки`](fact-dictation.md).

Dictation-state в этом keyless bar'е должен быть owner-scoped. `ClaudeControlBar` переиспользуется между табами, поэтому локальный `recording/stopping` без проверки `owner.tabId === tabId` протечёт на соседнюю вкладку: Enter начнёт ждать чужой delivery, а mic будет выглядеть активным там, где запись не принадлежит текущему PTY. Текущий контракт: owner-tab показывает обычный mic/Enter flow, non-owner live tabs получают disabled mic, а background owner раскрывается через status-row сверху справа. Детали — [`fact-dictation.md::Tab-owned background recording`](fact-dictation.md).

`^C` намеренно не проходит через `terminal:stop-ai-process`: это **input action**, а не Stop процесса. Claude/Codex сами решают, что значит одиночный Ctrl+C в текущем TUI-состоянии: очистить видимый input, отменить локальную команду, прервать turn или взвести danger-zone на пустом prompt'е. Если `Enter` уже висит в pending-state после `dictation:stop-and-deliver`, клик `^C` снимает pending Enter через `cancelPendingEnterRef` и не даёт автоматическому `\r` уйти после delivery. Это важно: пользователь передумал отправлять продиктованный текст, но сама доставка текста в composer может ещё завершиться.

**Right cluster.** Квадратная кнопка быстрого перехода, Model dropdown (провайдер — его первая секция, PTY-Claude only), Effort dropdown (модификатор сессии — его последняя строка). Popup'ы открываются **вверх**: обычное наведение лишь показывает выбор, а клик закрепляет его и даёт триггеру белую рамку; закреплённый выбор закрывается внешним кликом или `Esc`. Wrapper держит 4px hover-мост. Геометрия не должна возвращаться к фиксированному `right: 0`: popup измеряет фактическую ширину, центрируется над триггером и clamp'ится к реально доступной правой границе (включая Timeline только если он действительно справа от триггера). Иначе меню выглядело смещённым влево, хотя у центра было место.

У Model Claude и Codex одинаковый зависимый выбор: наведение на строку модели показывает только её совместимые effort отдельной плашкой, а клик по effort применяет пару. Для Claude PTY это не две независимые команды: сначала подтверждается `/model`, затем `/effort`; в SDK пара сохраняется для следующего `query()`. Список Claude берётся из сохранённых чекбоксов конкретной модели, поэтому у Haiku не появляется `max` или `ultra`.

Порядок строк Model наследуется от ручной сортировки в Settings → Системные.
Claude читает сохранённый список, Codex соединяет его с live-каталогом,
сохраняя пользовательские строки первыми. Фильтрация скрытых моделей не меняет
относительную позицию остальных; детали — `fact-settings.md::Настройки моделей`.

Startup Claude не считает synchronized render marker доказательством, что `/model` или `/effort` остался в composer. Перед Enter main заново читает текущий закрытый headless-кадр. Если paste исчез до Enter, точный Ctrl+G показывает пустоту и неизменны launch, terminal run, lifecycle и mirror generation, разрешён ровно один новый paste после следующего stable frame; Enter guard при этом не ослабляется. Неизвестная доставка или сменившийся owner остаются ошибкой без повтора. Такой отказ всегда сохраняет bounded raw PTY forensic JSON, даже когда headless и Ctrl+G согласны и обычный contradiction-trigger не срабатывает.

**Effort — dropdown, но набор уровней прежний.** Раньше уровни стояли инлайном (выбор виден без раскрытия, один клик переключает) — это стоило до восьми мест в строке и было самым широким элементом панели; в композере такой цены нет. Сам список не изменился: показываются только отмеченные в настройках уровни текущей модели, активный подсвечен `#DA7756`, а подпись свёрнутого триггера дословно повторяет отмеченную строку. Для Haiku это `low/med/high/xhi`; `max` и `ultra` не становятся ложными вариантами. Для остальных shipped Claude-строк полный набор остаётся доступен; `ultra` = ultracode (xhigh + dynamic-workflow на всю сессию), не обычный уровень модели, и отделён горизонтальным волоском с фиолетовым акцентом `#7c5cd6`. Сырой CLI может иметь более широкий menu, но выбор в Noted Terminal определяется явной продуктовой таблицей и сохранёнными чекбоксами, а не догадкой по одному metadata-полю. Принцип переносимый — см. `methodology/дизайн-принципы.md::Dropdown vs inline`.

Layout одинаковый для PTY и SDK, но набор контролов разный: для SDK секции провайдера в меню моделей нет (SDK гоняет напрямую в Anthropic), а effort использует тот же per-model список; DeepSeek-PTY сохраняет свою отдельную шкалу `DEEPSEEK_EFFORT_LEVELS` с `off`. Continue в SDK превращается в фокус на composer вместо `claude --resume` команды.

Быстрый переход — одна кнопка для Claude и Codex, а не две соседние. Сначала она ориентируется на тип текущего запущенного агента, подтверждённый process-promoted `commandType`; сохранённый ID старой истории служит только fallback'ом. Поэтому старый Claude transcript не может оставить оранжевую кнопку рядом с зелёной Codex-кнопкой в уже переключённом PTY. Для Claude preset в SDK меняет параметры следующего `query()`, в PTY последовательно применяет `/model`, затем `/effort`; успешная смена одной только модели не считается успешным переходом. Первый клик запоминает предыдущую пару и переключает на целевую, повторный возвращает её только пока текущая пара всё ещё совпадает с целью; ручное изменение или неудачное применение сбрасывает возврат, чтобы кнопка не обещала восстановить несуществующее состояние.

## Перенос в две строки при узкой ширине (2026-08-11)

Каждая кнопка в баре — pill фиксированного размера (`flexShrink: 0`), потому что её подпись обязана остаться читаемой. Значит при узкой ширине **ничего не сжимается**: два блока просто наезжают друг на друга, и подписи ложатся друг на друга нечитаемой кашей. Хуже всего в разделённом режиме, где два бара делят ширину окна (замерено: панель 573px при нужде 836px). Лечится переносом, а не сжатием.

Порядок обратный интуиции и в этом весь смысл: **правый блок остаётся на первой строке, левый уходит на вторую** (через `order`). Модель/усилие/think — то, к чему тянешься чаще, — сохраняют своё место относительно поля ввода сверху. Правый блок при переносе остаётся прижат к правому краю, иначе он бы «переехал» влево и выглядел как другой элемент.

Высота фиксирована `30px` только в одну строку; в две — по содержимому (58px). Бар — обычная строка раскладки в обоих местах монтирования, поэтому всё под ним просто сдвигается вниз; на измеренную высоту композера (`historyControlsHeight`) это не влияет — та меряет другое.

**Ширины измеряются, а не считаются.** Они зависят от живого текста подписи (`GPT-5.6-Sol` против `opus`), от размера шрифта в настройках и от набора необязательных чипов. Любой порог, выведенный формулой, был бы неверен для какой-то комбинации.

Три ловушки, каждая из которых давала «правка не работает»:

1. **`scrollWidth` — не нужда содержимого.** У левого блока в конце стоит распорка `flex:1`, прижимающая счётчик контекста к правому краю, поэтому `scrollWidth` всегда равен выданной ширине (замерено: 600 из 600 при реальной сумме детей 521). С таким числом сравнение самоссылочно: оно растёт вместе с доступной шириной, и бар никогда не «влезает» обратно. Нужно суммировать детей, пропуская распорку (`measureClusterContentWidth`).
2. **Наблюдатель за размером не срабатывает в скрытом окне** — ровно как не наступает кадр отрисовки. Замерено: ширина изменилась 1145 → 620, ни одного вызова. Поэтому источников три: наблюдатель, событие ресайза окна и безусловный расчёт на каждом рендере бара.
3. **`useLayoutEffect`, не `useEffect`.** Правый блок рендерится внутри вызова функции, его ссылка привязывается позже — обычный эффект успевал прочитать пустую ссылку, сбросить перенос и больше не пересчитаться, потому что зависимости не менялись.

Отдельно: у контейнера бара в панели разделения был `overflowX: auto` — он давал горизонтальный скролл вместо переноса, и бар оставался одной строкой со съехавшими кнопками. Убран.

Правило — `utils/controlBarWrap.mjs` (5 тестов). Проверено живьём в обе стороны: панель 573px → две строки, зазор между строками 2px; схлопывание разделения → 1145px, одна строка, 30px.

## Codex mode в том же bar

**2026-09-08 — уточнение model/effort:** сохранение выбора и его применение
разделены. После клика Model/Effort/Quick показывают ожидание и недоступны до
подтверждения применения либо явной ошибки; сами busy-turn/paste не запрещают
первый выбор. Ожидание читается из main и не сбрасывается переходом на другую
вкладку. Это заменяет прежнее требование принимать следующий UI-выбор во время
применения; внешняя API-очередь сохраняется. См.
`fix-codex-settings-history-rollback.md` — включая ошибочное возвращение Ultra
из старой History и ограничения проверки.

Компонент исторически называется `ClaudeControlBar`, но теперь держит общий lifecycle PTY-агентов. Codex использует тот же triplet session-id / Continue-Stop / refresh Timeline, но с отдельным `codexSessionId` и без Claude-only affordance'ов. На pristine табе рядом с Claude/SDK fork-кнопками видны `Codex` и `⑂ Codex-F`; как только в табе появился любой AI-process или session id, launch/fork-from-clipboard chips прячутся тем же `!hasAnySession && !isCommandRunning` guard'ом, иначе юзер видит fork-кнопки поверх занятого таба.

Codex не показывает секцию провайдера, Think и cache chip: у него нет provider proxy в нашем смысле и нет отдельного think toggle. Правая зона для Codex — квадратная кнопка быстрого перехода, Model и Effort, а `Fast` остаётся отдельным квадратом с молнией. Model/Effort идут через интерактивный `/model` picker Codex TUI; при наведении на строку модели совместимые effort показываются отдельной плашкой **сбоку** от этой строки (`SideFlyout`). Быстрая кнопка модели берёт сохранённую в настройках пару и умеет вернуться к прежней; Fast этой парой не управляет.

Fast показывает желаемый tab-scoped service tier и доступен при остановленном, запускающемся, готовом и busy Codex. Клик только сохраняет очередную ревизию intent, поэтому не блокируется общим session loader или другой настройкой; main применяет последнюю ревизию после exact TUI proof. В Codex 0.145 service tier не попадает в rollout JSONL, поэтому факт применения по-прежнему берётся только из verified footer (`model effort [fast]`) или ответа `Service tier set to priority/default`, привязанных к текущим PTY/run/launch/writer. `priority` означает Fast on, `default` — off. Пока proof отсутствует или отличается, кнопка показывает выбранное значение как pending; совпавший proof снимает pending без дополнительной команды. При busy-turn физический `/fast` допустим только с доказанно пустым composer; draft/unknown оставляют intent в очереди до следующего ready frame. Ручной `/fast` в terminal становится новым intent по точному feedback. Пользовательский симптом регрессии — кнопка disabled в stopped/starting, первый выбор теряется при готовности либо два быстрых клика выполняют два toggle не к последнему состоянию. Copy-пункты меню черновика остаются live-only. Детали — `fact-codex.md`.

Model/Effort picker для Codex использует общий main/headless xterm snapshot как основной ответ `hasDraft=true/false/null`. Свежий renderer-positive snapshot может консервативно доказать дополнительный draft и остановить действие, но renderer absence/negative не стирает более авторитетный main proof. После ожидания общей settings-очереди классификация повторяется у самой PTY write-boundary: между первым снимком и `Ctrl+C`/`/model` экран мог стать picker, Rewind или startup. `hasDraft=true` — не ошибка: main сохраняет draft через native stash и возвращает его после выбора; `hasDraft=null` fail-closed, dim-placeholder считается пустым. Детали — `fact-codex.md::Модели и effort`.

Codex Model/Effort хранятся на вкладке (`codexModel`, `codexEffort`), а не в локальном state ControlBar и не в глобальной настройке. Дефолт `xhigh` нужен для видимой пилюли на каждой Codex-вкладке, но при launch он не превращается в скрытый `-c model_reasoning_effort="xhigh"`: дефолтная пара должна приходить из `~/.codex/config.toml`, а ControlBar отправляет `model/effort` только если конкретная вкладка явно выбрана не-дефолтной. Симптом, который нельзя возвращать: пользователь видит `codexEffort` в одном табе и не понимает, «откуда он берётся» — это должен быть tab-scoped selection, а не глобальное эхо.

Codex Model/Effort controls могут сохранять tab-scoped выбор до materialized session id, но busy-режим разделён не по типу параметра, а по способу применения: Model и Effort остаются clickable при `task_started`, потому что оба идут через native `/model` picker и подтверждаются его success-result. Если probe даёт `hasDraft=null` или picker падает, ControlBar не сохраняет выбранное значение как будто оно применилось, а фокусирует терминал и пишет diagnostic log вместо пользовательского уведомления. Для этого ControlBar читает `tab.aiBusy` как Codex turn-busy отдельно от `isCommandRunning`: OSC-состояние отвечает «процесс жив», а rollout busy отвечает «идёт ответ; новая связка model/effort станет настройкой последующей работы». Диагностический минимум в логах правого кластера — `turnBusy`, `hasDraft` и `source`; если пользователь видит `Working...`, но model/effort не применяются live, сначала сверяй именно эти поля.

Runtime-настройки принадлежат доказанному writer, а не одному tab-state. Поэтому частичная смена только модели/effort и quick-toggle блокируются, если writer сменился или ещё неизвестен; явная полная пара остаётся доступным recovery-действием. После успеха proof owner сохраняется вместе с текущим writer. Если свежий Codex ещё не создал первый rollout, полная пара получает одноразовое доказательство для точного PTY/launch generation; его принимает только первый process-proven writer после durable binding. Для Codex 0.145 обычный `Max` меняет persistent default и сохраняет существующий Plan override, а `Ultra` действует только в текущем разговоре и требует отдельного точного acknowledgement.

## Empty PTY controls и launch order

На пустой PTY-вкладке правая зона Model/Effort/Think/Provider **не рендерится вообще**, а не показывается затемнённым Claude-набором. До запуска агента неизвестно, выберет ли пользователь Claude, SDK или Codex; disabled Claude-controls создают ложный сигнал «это Claude-вкладка, просто недоступна», а после запуска Codex этот же блок мгновенно меняет смысл. Пустое состояние без foreground-команды показывает только действия запуска, включая явный `Терминал`; пока разовая shell-команда выполняется, скрываются и launch, и model controls, а после её завершения выбор возвращается.

`isCommandRunning` доказывает только занятый PTY и больше не разрешает правый AI-кластер. Model/Provider/Effort показываются лишь когда единый execution-role resolver установил Claude/Codex/Gemini/SDK владельца. Явный `Терминал`, `devServer` и Restart after-зависимость закрепляют terminal-role и оставляют AI-кластер скрытым после завершения процесса. Прод-симптом прежнего fallback: `ControlBar type=claude, session=none, commandRunning=true` поверх `./deploy.sh`, хотя Claude не запускался.

Порядок launch-кнопок слева направо: `Claude`, `Claude-F`, `SDK`, `SDK-F`, `Codex`, `Codex-F`, `Терминал`. `Claude` и `Codex` используют один `SessionActionChip`-стиль: обычный вид — короткое имя агента, hover — `Start`, без отдельной рамки и без второго визуального языка. `*-F` берёт session id из clipboard и на pristine PTY-табе использует **текущую вкладку** как цель запуска/конвертации; новая соседняя вкладка создаётся только когда текущая уже занята сессией или живым процессом. `Терминал` ничего не перезапускает: он фиксирует `commandType='generic'` на существующем live shell и закрывает chooser.

## Focus contract после Start / Continue

Кнопки `Start`, `Continue`, `Claude-F`, `Codex`, `Codex-F` не просто запускают команду — они переводят следующий пользовательский ввод в PTY. Поэтому обработчик клика обязан сфокусировать терминал **до** отправки команды и повторить focus в `requestAnimationFrame` после React-layout. Без этого фокус остаётся на button'е: если Claude сразу показывает `Choose working directory to resume this session`, Enter не попадает в PTY и юзеру приходится кликать терминал вручную; если chooser'а нет, первый набор текста после Continue тоже уходит не туда. Для SDK-Continue тот же контракт, но target surface — composer, а не xterm.

Это не debounce и не ожидание готовности CLI: фокус — локальное UI-состояние, его можно и нужно выставлять синхронно. Детерминированный readiness (`prompt ready`, picker frame, session capture) остаётся отдельным слоем; focus не должен ждать этих событий, потому что интерактивный CLI может попросить пользователя нажать Enter ещё до первой session-записи.

Codex directory chooser при `codex-c`/`codex-f` дополнительно подтверждается main-side auto-Enter по фактическому PTY-фрейму (см. `fact-codex.md::Interrupted recovery и AutoResume`). Это не отменяет focus contract: ручной ввод после запуска, другие chooser'ы и fallback без auto-confirm всё равно должны попасть в терминал без отдельного клика пользователя. Main-side `term.write('\r')` не требует DOM-focus и не должен фокусировать окно сам, иначе background AutoResume начнёт красть фокус у пользователя.

## Busy-state tab binding — `useState` НЕ сбрасывается сам при смене таба

`ClaudeControlBar` монтируется в `Workspace.tsx` **без `key`** — React **переиспользует** один инстанс на все табы проекта, при переключении меняется только проп `tabId`, компонент **не ремаунтится**. Из этого следует ловушка для любого локального `useState`-флага (`isPasteBusy`, `isLocalBusy`, `effortLocal`, `thinkLocal`): он **не обнуляется** автоматически при смене `tabId`. Эффекты с `[tabId]` в deps пере-подписывают слушатели, но значение state остаётся от прошлого таба.

Два прод-бага вытекают ровно отсюда (сессия `ea2ae02c` / tab-283, 2026-06-03 ~22:07 MSK):

1. **LEAK across tabs.** `isPasteBusy=true` пойман для таба A → юзер переключился на таб B → shimmer-overlay правого кластера всё ещё горит, хотя B ничем не занят. Юзер: *«я на другую вкладку перешёл… но у меня почему-то loader от вот этого компонента всё равно сохранялся»*.
2. **STUCK FOREVER.** `safePasteAndSubmit` шлёт `emitBusy(false)` с `{tabId: A}` (см. `fact-claude-tui-control.md::paste-busy`). Но к моменту прихода этого события слушатель уже фильтрует по **новому** `tabId` (B): `if (data.tabId === tabId)` → `A !== B` → `false` **дропается**. Локальный `isPasteBusy` остаётся `true` навсегда — переживает reload вкладки и даже kill Claude-процесса. Это и есть «убил процесс клода, а loader не сбросился».

**Корень совпал с гипотезой юзера:** *«лоудер не имеет привязки к вкладке»*. Буквально: busy-флаг — это renderer-local state одного переиспользуемого инстанса, не per-tab persistent поле, и при ребинде он не чистится.

**Фикс (три слоя в одном `useEffect([tabId])`):**
- **Синхронный reset на ребинд:** в начале эффекта `setIsPasteBusy(false); setIsLocalBusy(false)` — свежепривязанный таб всегда стартует чистым, не наследует busy прошлого.
- **Clear на lifecycle-краях:** подписка на `claude:process-started` и `terminal:command-finished` (OSC 133 D) с фильтром по `tabId` → обнуляют оба флага. Когда Claude стартовал или умер — живого TUI mid-paste нет, любой висящий индикатор по определению stale. Это то, что чинит recovery после kill.
- **Manual escape hatch** (см. ниже) — на случай если оба автопути промахнулись.

Переносимый принцип: **любой `useState` в keyless-переиспользуемом компоненте, чьё значение семантически per-tab (или per-любой-prop-идентичность), обязан иметь explicit reset в `useEffect([thatProp])`.** Без `key` React не сделает это за тебя. Родственный антипаттерн — `fix-zustand-silent-mutation.md` (stale value при правильной подписке).

## Codex Fast — свой квадрат, а не строка в меню усилия (2026-08-17)

Fast вернулся отдельной кнопкой справа от блока усилия — квадрат с молнией, как было до переезда в меню. Внутри меню он оказался не на месте по смыслу: та колонка отвечает на вопрос «насколько глубоко думать», а Fast отвечает на другой — «как быстро обслужить запрос», и уровни не меняет вообще. Плюс он бинарный: у переключателя нет причин прятаться за раскрытие списка, из-за которого его нельзя было включить одним кликом.

Claude Think, наоборот, остался последней строкой меню усилия — он решает, ПРИМЕНЯЮТСЯ ли уровни выше, поэтому стоит с ними в одной колонке. Одинаковое место для Think и Fast было ложной симметрией: у них разные предметы.

Ширина кнопки равна высоте (22px): один глиф, без подписи — прямоугольник смотрелся бы как обрезанная кнопка с текстом. Кружок ожидания работает как у остальных: подпись остаётся в раскладке скрытой, ширина в момент клика не меняется.

## Значка раскрытия у Model и Effort нет

Треугольник `▴` у обеих кнопок удалён. Кнопка показывает ТЕКУЩЕЕ значение, и что по нему открывается список — понятно с первого раза; значок занимал место в самой узкой строке интерфейса. У кнопки черновика терминала он остался: там глиф не является значением, и без него кнопка не сообщает, что у неё есть меню.

## Ожидание рисуется на изменяемой кнопке, не на кластере (2026-08-17)

Когда значение записывается в агент (`/model`, `/effort`, переключение провайдера, Think, быстрый пресет), кружок-ожидание идёт **на той кнопке, которую меняют**. Соседи в это время просто недоступны, а занятая кнопка остаётся кликабельной — клик по кружку отменяет ожидание (наведение показывает красный ✕). В этом вся разница между «ждёт» и «недоступно», и она обязана быть видимой.

Какая именно кнопка занята, выводится из причины, с которой поднят флаг занятости (`utils/controlBarBusyTarget.mjs`): `claude-model:opus` → модель, `codex-effort:high` → усилие. Отдельно закреплено тестом: **пара «модель + усилие» показывает кружок на МОДЕЛИ** — это один жест, начатый на строке модели, и отметить усилие значило бы указать на кнопку, которую пользователь не трогал. Незнакомая причина → не крутится ничего, блокируется всё: честное «занято» лучше кружка на случайной кнопке.

Причина обязана лежать в **состоянии**, а не только в ref: ref не вызывает перерисовку, поэтому кружок оставался бы на кнопке, занятой в прошлый раз (`localBusyReason` синхронизируется во всех точках подъёма и сброса флага).

Три требования к самому кружку, все из-за жалоб на прошлый вариант: он не меняет ширину кнопки (подпись остаётся в раскладке скрытой, кружок рисуется поверх — иначе соседи уезжают в момент клика), он размером с глиф, а не на весь квадрат, и меню на занятой кнопке не открывается (предлагать выбор во время записи бессмысленно).

**Чего здесь больше нет.** Переливающаяся полоса по всему правому кластеру (`.control-bar-busy-overlay`) и красный оверлей «СБРОС» поверх неё (`.control-bar-busy-reset`) удалены вместе с CSS. Индикатор был на КЛАСТЕРЕ, а операция всегда над одной кнопкой: смена одного значения зажигала строку шириной почти в окно, а между проходами свечения не показывала ничего — *«я вообще не вижу, есть у нас loader или нет»*, *«примерно 5% окна»*. Не возвращать индикатор на группу.

Попутный шрам: отмена не снимала внутреннюю блокировку (`controlActionInFlightRef`) — визуально ожидание кончалось, а следующий клик молча отклонялся. `forceResetBusy` обязан чистить и её, и hover-состояние отмены.

## Подтверждённые model/effort: кэш в main + ожидание «подтверждение в полёте»

Кластер Model/Effort для PTY-Claude не принимает правдоподобный fallback за live-state. Model main реконструирует бэктрейсом активной JSONL-ветки (`claude:get-confirmed-settings`). Effort имеет более узкий контракт: Claude подтверждает его строкой `this session only`, поэтому JSONL старого процесса — только исторический факт. Текущим считается лишь `/effort` stdout, записанный после accepted launch-boundary нынешней живой process generation. Реконструкция полной ветки на 59MB-сессии стоила 480-1630мс main-времени, а вызывается она на каждый tab switch (session-change) и на каждое изменение транскрипта — это был один из слагаемых свап-фриза.

Кэш в main: ответ переиспользуется, пока каждый файл цепочки байт-в-байт тот же (свидетель identity+mtime+size, снятый ПОСЛЕ resolve по точному списку прочитанных файлов + mtime папки проекта — resume/fork-ребёнок появляется новым файлом и меняет latestSessionId, не трогая существующие). Живой ход инвалидирует кэш собственным append'ом. LRU 24 сессии, только в памяти — первый запрос после рестарта main снова полный. В логе `ConfirmedSettings ... cache=hit|miss`.

Пока подтверждение в полёте, клики НЕ блокируются (`data-settings-confirming="1"`, aria-busy): выбор модели во время чтения легален — выбор пользователя побеждает, устаревший ответ дропается по request seq. Смысл отметки здесь — «показанное значение ещё не доказано», не «занято», поэтому она не должна выглядеть как ожидание записи.

## Отмена залипшего ожидания

Escape hatch поверх автоматических сбросов, изначально запрошенный юзером как *«при наведении красное СТОП на весь loader, переклик сбрасывает состояние»*. Сейчас это тот же жест, но на одной кнопке: наведение на кружок даёт красный ✕, клик зовёт `forceResetBusy`.

**Что отмена НЕ делает:** не отменяет реально летящую запись в PTY — она только ре-синкает UI. Per-term mutex (`pasteInflight` WeakMap) в `safePasteAndSubmit` всё равно сериализует любую настоящую конкурентную запись на тот же PTY. То есть клик безопасен даже если main на самом деле занят: UI разблокируется, но байты не интерлевятся.

## Per-tab state и selectors

Tab-метаданные (`tabType`, `sdkModel`, `sdkEffort`, `sdkThinking`) читаются через **отдельные** primitive Zustand-селекторы на каждое поле. **НЕ** единый композитный селектор — он возвращал бы свежий объект `{}` на каждом рендере, Zustand видит новую ссылку и фурит компонент в бесконечный re-render. Это та же ловушка что в CLAUDE.md anti-pattern «Не подписывайся на Map целиком» (Zustand fingerprint pattern).

PTY-Claude Model/Effort в ControlBar — проекция доказанного состояния, но области жизни различаются. Model принадлежит **текущей сессии** и реконструируется по active `parentUuid`-ветке; effort — **текущему процессу этой сессии**. Claude пишет `/effort` как прямую wrapper→stdout пару, но следующий обычный ход может продолжить conversation branch мимо этой пары. Поэтому current effort ищется по точным физическим slash-записям той же session и принимается только при timestamp не раньше accepted boundary текущей live generation. Transcript watcher обновляет bar после ручной команды. Renderer seed хранит только model; переход process-status внутри той же session не обнуляет уже доказанные значения до ответа main, а новая generation снова требует свой effort proof.

Когда типизированная Claude/Codex PTY-вкладка остановлена, те же Model/Effort
становятся выбором **следующего запуска**. Для Claude сохраняется только полная
совместимая пара; при Start/Continue она имеет приоритет над подтверждёнными
настройками Resume и app defaults, применяется последовательно и исчезает из
pending-состояния только после proof обеих команд в точном launch generation.
Для Codex остановленный выбор также хранится полной парой без owner старой
сессии; Resume применяет её один раз и не объявляет готовность, пока composer
footer не подтвердит именно эту пару. Поэтому pending-выбор показывается выше
старого подтверждённого значения, но не выдаётся за уже применённое live-state.

StatusBar при этом остаётся настройкой **будущих** запусков. При Resume история выбирает желаемую model, но не закрывает model-step: новый процесс может открыть тот же JSONL на собственном default (production tab-3954: history=Fable, fresh bridge=Opus). Поэтому `/model` и process-local `/effort` применяются и доказываются заново для каждой launch generation; пропуск разрешён только claim'ом, полученным внутри этой generation. `_modelSentForTab` / `_effortSentForTab` лишь дедуплицируют команды внутри поколения и очищаются со смертью процесса. До нового proof ControlBar показывает выбранный fallback с жёлтым `!`, а не выдаёт его за подтверждённый live-state. `thinkLocal` остаётся отдельным TUI-mirror. См. `fact-claude-tui-control.md::Startup defaults /model + /effort при запуске Claude`.

## Context % bridge: три канала — PTY, SDK, Codex

PTY: `claude:bridge-update` IPC event с payload `{tabId, sessionId, model, contextPct}`. **Цифра — собственное число Claude, не наш расчёт.** Цепочка: Claude Code statusLine отдаёт `context_window.used_percentage` (уже посчитанный против `context_window_size` модели — 200k или 1M, знаменатель разрешает сам Claude) → `~/.claude/statusline-bridge.sh` сохраняет исходное дробное число в `~/.claude/bridge/<session>.json` (`null`, если поля действительно нет) → main `processFile()` закрепляет его за exact session, сохраняет для вкладки и форвардит как `claude:bridge-update` → ControlBar только показывает. Это **ровно то же значение что в TUI-statusLine** — никакого пересчёта `used/window` на нашей стороне (и не должно быть: своя формула разойдётся с источником на 1M-сессиях, см. `methodology/дизайн-принципы.md::Отображаемую метрику читай из числа источника`). НЕ «парсится из JSONL» — источник именно statusLine-хук, не транскрипт. Canonical build-install синхронизирует statusline-script вместе с turn-hook, поэтому старый `null → 0` bridge не остаётся жить отдельно от приложения.

Три guard'а на handler'е (`ClaudeControlBar.tsx`):
- **exact binding**: как только у таба есть долговечный `claudeSessionId`, bridge-кадр принимается только с тем же session ID. Это закрывает позднее событие старой сессии уже после завершившегося handoff; до первой привязки свежей сессии кадр ещё разрешён, чтобы bootstrap не закольцевался.
- **stale-session**: handler консультирует `isStaleAgainstPending(tabId, data.sessionId)` перед display+persist. Без этого во время resume-гонки (PID reuse) мёртвая сессия штамповала свой % на таб И писала его в SQLite (`tab:persist-context-pct`) — Terminal.tsx отвергал чужой sessionId-write, но meter всё равно врал. main шлёт `sessionId` в payload именно для этой сверки. См. `fix-bridge-stale-takeover.md`.
- **ноль отличается от отсутствия**: свежий `contextPct === 0` после compact/clear очищает старый seed; неизвестное значение приходит как `null` и ничего не доказывает. Нельзя снова кодировать оба состояния одним числом `0`: именно это оставляло 55% после Claude compact до 8k tokens.

Seed: на mount таба meter засевается из SQLite (`tab:get-context-pct` → `getTabContextPct`) — показывает last-known fill даже когда Claude не запущен (CLI вышел / ещё не стартовал). Но сохраняет число main, а не открытый ControlBar: compact/clear во фоновой вкладке не может потерять новый процент из-за отсутствующего listener. Renderer сохраняет только SDK-канал, потому что он действительно рождается в renderer.

SDK: нет IPC. `ClaudeSDKTab` хранит `lastContextUsedTokens` в локальном React-стейте и диспатчит `window.CustomEvent('sdk-context-update', {detail: {tabId, contextPct, model}})` на каждом ассистентском SSE. ControlBar слушает window-event. Мотивация: добавлять новый IPC channel + поле в Tab interface ради одного UI-меридиана — overkill. Window CustomEvent дешевле и не трогает SQLite-схему. Тот же паттерн уже использован для `history-panel:loading`. (SDK считает % сам — `lastContextUsedTokens / getModelContextWindow(...)` с детектом `[1m]`/Opus-4.8 — потому что у SDK нет statusLine-хука; это исключение из «бери число у источника», т.к. источника готового процента у SDK-канала нет.)

Codex: `codex:context-update` IPC `{tabId, sessionId, contextPct}`. **Цифра — собственное число Codex, не наш накопительный счётчик:** берётся из `event_msg.token_count.info`. Ключевое — **не заводить отдельный watcher и не поллить**: turn-watcher из main (`codexTurnWatchers`, тот что уже тайлит rollout ради busy-state `task_started/complete`) на каждой строке `token_count` считает `last_token_usage.total_tokens / model_context_window`, сразу закрепляет снимок за exact writer и сохраняет его в SQLite независимо от открытой панели; renderer и native/API получают ту же проекцию. Запись в БД дедуплицируется по целому отображаемому проценту, но main держит свежую дробную величину. **Ловушка знаменателя — `last`, не `total`:** `last_token_usage` = последний единичный запрос, а Codex каждый ход пере-отправляет всю историю, поэтому `last.total_tokens ≈ текущая занятость окна`. `info.total_token_usage` — кумулятив за всю сессию (десятки миллионов токенов за длинную сессию) → делится в тысячи процентов и вечно клампится в 100%; брать его в метр нельзя (та же ловушка живёт в `codex:get-timeline`, см. `fact-codex.md::Timeline и History`). При compact новый `token_count` является обычным причинным событием: например production tab-3314 дал `600432/828400=72.5%` до compact и `114208/828400=13.8%` сразу после. При первом подключении watcher'а (`catchUpCodexTurnState`) последний `token_count` из хвоста журнала засевает main-состояние без ожидания следующего хода.

## Cache cooldown chip — близнец контекст-метра

Слева от контекст-метра в LEFT-кластере. Главная цифра — **минуты до остывания** prompt-кэша, мелким рядом — % тарификации (доля от полной цены за последний ход). Два канала под ту же ось что у контекст-метра: PTY через `claude:cache-update` IPC (proxy парсит `message_start`, fires **только** в anthropic-режиме → для DeepSeek/Zen событие не приходит вообще), SDK через `sdk-cache-update` window-event (SDK ходит на Anthropic мимо proxy, ловит usage у себя и ре-эмитит). Оба несут `{cacheRead, cacheCreate, input, ts}`.

**Provider-gate, не просто «скрыть если нет данных»:** чип показывается при `(isSDKTab || isAnthropicPTY) && cacheData`. DeepSeek/Zen не имеют prompt-кэша — у них чип не появляется конструктивно (событие не приходит), плюс явный гейт по провайдеру на случай если канал что-то прислал. Codex — отдельно, см. секцию Codex выше («не показывает cache chip»).

**Почему у Codex такого чипа нет конструктивно, а не «пока не сделали».** Главная цифра чипа — обратный отсчёт, и он возможен только потому что у Anthropic TTL = фиксированный 1 час (захардкоженная константа-якорь) + `ts` последнего хода из источника. У OpenAI второго якоря не существует: официальные доки дают не фиксированный TTL, а плавающее окно — «typically 5–10 min of inactivity, up to 1 hour off-peak», extended-retention «up to 24h» для gpt-5.x, плюс eviction по memory-pressure (кэш умирает не по таймеру, а когда GPU-память переполнилась — подтверждено на разрывах в секунды). Codex вдобавок сам не шлёт `prompt_cache_retention`, то есть активен дефолт организации, невидимый клиенту. Значит любой «остынет через N мин» для Codex = выдуманный знаменатель, который систематически врёт (прямой случай `methodology/дизайн-принципы.md::Отображаемую метрику читай из числа источника`). Единственный честный кэш-сигнал у Codex — постфактумный `cached_input_tokens` per turn (был ли кэш-хит), и он живёт в detail-панели Timeline, не в этом чипе — см. `fact-codex.md::Per-turn usage в detail-панели Timeline`.

**Таймер замирает в busy — потому что TTL refresh-on-use.** Сервер продлевает 1h-TTL на каждом обращении (см. `fact-provider-proxy.md::TTL кэша = 1 час`), поэтому обратный отсчёт осмыслен только пока сессия простаивает; во время живого хода он бы прыгал обратно на 60 каждую секунду. Решение: при `busy` (для PTY — `isCommandRunning`, для SDK — `sdkBusy`) главная цифра заменяется на точку «●», `setInterval` на тик не заводится. ≤10 мин до сброса — жёлтый, >60 мин простоя — серый «❄ остыл». Чип — отдельный компонент со своим минутным интервалом, чтобы тик не ре-рендерил весь бар. `ts` не персистится: устаревший момент последнего хода врал бы про свежесть после рестарта, на cold-start чип пуст до первого ответа.

## sdkBusy mirror — отдельная подписка для SDK таб'ов

PTY-табы получают `isCommandRunning` от Workspace через OSC 133 D/B (см. `fact-terminal-core.md::OSC 133`). SDK-табы PTY не имеют — этот канал всегда возвращает `false`, и chip/right-cluster никогда не узнают что query сейчас идёт. Решение — ControlBar **локально** подписывается на `claude:busy-state` IPC (main forward'ит туда `claude-sdk:busy-state` через одну общую шину) с guard'ом `isSDKTab && data.tabId === tabId`. Полученный `sdkBusy` подаётся в `SessionActionChip` вместо `isCommandRunning` (только для SDK-режима); для PTY режима остаётся OSC-канал. Это единственный способ узнать busy-state для SDK таб'а на уровне ControlBar, не таская дополнительный prop из Workspace.

## Right cluster до запуска и после Stop

Model/Effort доступны в трёх случаях: SDK-вкладка, живой Claude/Codex PTY и
типизированная остановленная Claude/Codex PTY-вкладка. В stopped PTY клик не
шлёт slash-команду в shell, а сохраняет полную пару следующего запуска. Think
для stopped Claude остаётся live-only; Fast для Codex сохраняет desired state и
поэтому доступен также в stopped/starting. Conversation-only Codex Ultra нельзя
сохранить как future default. На pristine shell правый кластер по-прежнему скрыт
— до выбора типа агента неизвестно, к какому запуску относить настройки.

SDK-режим применяет параметры **аргументом** при следующем `query()` вызове
(см. `fact-claude-sdk-tab.md::Effort: продуктовая таблица по модели,
ultracode через settings`). Codex при `task_started` сохраняет отдельное узкое
исключение: Model/Effort остаются доступны для следующей работы текущей сессии.
Каждый клик сразу сохраняет полную desired-пару как новую revision; следующий
клик заменяет предыдущий. Если вкладка ещё `starting`, writer меняется или TUI
временно занят, main не теряет выбор по timeout, а применяет последнюю revision
после exact writer+composer proof. ControlBar показывает desired-пару как
pending, а session-owned live-поля обновляет только после подтверждённого
picker-result; replacement writer должен подтвердить ту же revision заново.

## Visibility guards для clipboard-fork chips

Кнопки `SDK` (`startNewSDKTab`), `Claude-F`, `SDK-F`, `Codex`, `Codex-F` показываются на pristine табах — `!hasAnySession && !isSDKTab`. К этому guard'у добавлен **третий**: `!isCommandRunning`. Без него существовал window между `claude:process-started` / `codex:process-started` (PTY запустил агент) и первой записью session id в Tab (1-3 сек) — в этом окне юзер видел fork/start-кнопки одновременно с живым процессом, *«у меня в этой вкладке запущен процесс клода, но одновременно отображаются Claude-F и SDK-F, какого хуя»*. С `!isCommandRunning` guard'ом кнопки прячутся как только OSC 133 D говорит «команда запущена».

## Fork: current-session всегда в новый объект, clipboard `*-F` может занять пустую вкладку

`⑂→▭` (`forkToTab`) и `⑂→SDK` (`forkToSDK`) — это кнопки форка **от текущей сессии**. Они рендерятся только когда у текущей вкладки уже есть `sessionId`, поэтому их действие всегда должно создавать новый объект рядом: PTY-tab для `⑂→▭`, SDK-tab для `⑂→SDK`. Даже если процесс уже остановлен и `isCommandRunning=false`, текущая вкладка всё равно содержит историю/identity исходной сессии; запуск fork'а в ней подменяет контекст, ломает ожидание от title `Fork в новую вкладку` и визуально выглядит как потеря родительской сессии.

Корневой симптом, который нельзя возвращать: юзер сделал Codex-fork, остановил процесс, нажал обычный `⑂→▭`, а fork запустился в той же вкладке, потому что guard смотрел только на `!isCommandRunning`. Это неверная ось. Для current-session fork состояние процесса не решает, свободна ли вкладка; решает наличие session identity. Если есть текущий `sessionId`, fork — всегда sibling.

Все async fork-действия показывают spinner внутри нажатой кнопки с первого синхронного state-update. Исходный label остаётся невидимым в layout и резервирует прежнюю ширину, поэтому соседние controls не сдвигаются в момент клика. In-flight identity включает `tabId + action + sequence`: повторный клик в той же вкладке блокируется, а `finally` старой вкладки не может снять loader более нового действия после tab switch. Таймер не является источником окончания — loader очищает completion самого action.

Clipboard-варианты (`Claude-F`, `SDK-F`, `Codex-F`) следуют той же идее, но источник session id — буфер обмена, а не текущая вкладка. Если юзер сначала открыл пустую вкладку и нажал `Codex-F`, это намерение «используй эту вкладку как target», а не «создай ещё одну пустую рядом». Поэтому pristine PTY → in-place (`claude-f` / `codex-f` в текущий PTY, `SDK-F` через `convertToSDKTab`), занятая PTY или SDK → соседняя вкладка.

Исключение строго одно: clipboard `*-F` на pristine PTY-табе, где нет `claudeSessionId`, `geminiSessionId`, `codexSessionId` и нет живого процесса. Там текущая вкладка действительно пустая и может быть target'ом. Переносимый принцип — `methodology/дизайн-принципы.md::Fork от живого/типизированного контекста = новый объект`.

## Карта visibility всех кнопок

В исходном коде `ClaudeControlBar.tsx` перед `return` JSX'а лежит ASCII-таблица состояний кнопок (`copy-session-id`, `SessionActionChip`, `refresh-timeline`, Claude/SDK/Codex fork chips, live-only `copy-prompt`, `mic`, `Enter`) по PTY/SDK/Codex состояниям. Источник правды для UI-state. **При любом изменении guard'а** — обновляй таблицу в коде синхронно (иначе следующий разработчик прочтёт устаревшую карту и сделает противоречивый guard). Юзер: *«можешь в этом компоненте как-то комментариями пометить, чтоб мы на будущее эту хуйню не сохраняли»* — карта нужна именно для предотвращения регресса.

## Ширина кнопки не меняется, пока идёт запись

Требование, из-за которого disabled-подход был отброшен ещё в первой версии и осталось в силе для кружка: триггеры с динамическим label'ом (Model, Effort) меняют ширину при изменении значения, а `disabled` + `opacity: 0.5` вдобавок читается как «функция сломана», не «занят, подожди». Юзер: *«сейчас он меняет ширину когда становится дизайблнутым; нужно сделать лоадер, при этом не менял ширину»*.

Поэтому подпись во время ожидания **остаётся в раскладке** (скрытой, не удалённой), а кружок рисуется поверх. Соседи при этом обычные `disabled` — они действительно недоступны, и это честнее любой анимации на них. Первая реализация решала ту же задачу полосой на весь кластер и провалилась по другой причине — см. секцию про кружок выше. Принцип переносимый — `methodology/дизайн-принципы.md::Busy-overlay вместо disabled`.

## Graveyard

**`setSdkModelCaps({})` в effect с `sdkModelCaps` в deps → infinite re-render loop.** Кэш model-caps загружается через `ipcRenderer.invoke('claude-sdk:get-model-caps')` один раз при mount'е SDK-таба. Изначально dep'ы effect'а были `[isSDKTab, sdkModelCaps]`. Когда main возвращал `{success:true, caps:{}}` (пустой кэш в первой версии endpoint'а), `setSdkModelCaps({})` создавал новую ссылку → effect re-fire → новый invoke → новый `{}` → бесконечно. Симптом — React error boundary с `Maximum update depth exceeded`, render-counter `[CB:R]` рос монотонно. Фикс: убрать `sdkModelCaps` из deps + добавить `Object.keys(r.caps).length > 0` guard (не записывать пустой объект). Принцип переносимый — *empty-object setState в effect deps создаёт ref-loop*, см. CLAUDE.md anti-pattern «Zustand: Не подписывайся на Map целиком» как родственный.

**`provider:get-state` IPC не существовал.** Правильный канал — `provider:get-status` с `{tabId}` payload. AI восстановит из grep по main/ipc — но если повторно столкнёшься с тем что provider state не читается — ищи имя канала, не реализацию.

## Брендирование Claude/Gemini

Два движка имеют закреплённые цвета: Claude — saffron orange `#DA7756`, Gemini — blue `#4E86F8`. Цвет активируется автоматически по типу сессии активной вкладки и распространяется на Timeline-точки, статус-сообщения, Stop-кнопку (`Stop Claude` / `Stop Gemini`). Resume/Continue chip подстраивается под тип активной сессии — оранжевый текст для Claude, синий для Gemini, чтобы пользователь без чтения лейбла видел, какой движок будет восстановлен. Тот же brand-tint в split-кнопке Stop при multi-select (см. `fact-tabs.md::Multi-select Stop с majority badge`), в Provider-row, в командных Status Styles (`<code>` тег, фон `#1a1a1a`, hover underline) — единая палитра по всему проекту, без локальных вариаций.

## Настройки копирования адаптируются под движок

Для Gemini-табов скрываются Claude-only опции в настройках копирования сессии (`CopySessionButton.tsx`, условие `showSettings && !isGemini`): переключатели «Include Reading», «Include Editing», «From Start». Эти концепты завязаны на структуру JSONL Claude (`type: 'user'` с `tool_result`, fork-сегменты, /compact branches) — Gemini-сессии устроены иначе, тогглы для них семантически пустые. Без скрытия юзер видел бы непонятные опции, не дающие эффекта.

Подзаголовок `Copy session` меняется на `Claude JSONL → clipboard` или `Gemini JSON → clipboard` в зависимости от активной вкладки. Юзер видит формат источника без раскрытия dropdown'а — disambiguation в один взгляд.
