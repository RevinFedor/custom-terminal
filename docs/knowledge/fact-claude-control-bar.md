# Feature: ClaudeControlBar (per-tab bottom strip под Terminal)

## Intro

30px-полоса под Terminal-колонкой, видимая когда активная вкладка — AI-tab: Claude/Gemini/Codex PTY или Claude SDK. Раньше Provider/Model/Effort/Think + Continue/Stop/Refresh/Fork + Copy-prompt + Ctx-meter жили в правой `InfoPanel`-колонке (см. `fact-workspace.md::Two-Column Layout`). Правая колонка удалена; контролы переехали в bar под терминалом, чтобы они были общим знаменателем для PTY и SDK табов, и чтобы Timeline (правее) сохранял полную высоту колонки.

Bar ложится **под** контентом Terminal-колонки, но не растягивается под Timeline'ом — `Timeline` отрисовывается соседом справа от vertical stack `[Terminal | ClaudeControlBar]`, не под ним.

После перехода Claude/Codex PTY на primary History историческое имя «Terminal-колонка» означает центральный structural slot workspace: bar остаётся под History/status/composer, а floating xterm содержит только raw terminal escape hatch. Переносить bar внутрь плавающего окна нельзя — lifecycle-controls должны оставаться доступны и при скрытом terminal.

## Layout

Две зоны, разделённые `flex: 1` спейсером:

**Left cluster.** Триплет `[⎘ session-id | Continue/Stop chip | ↻ refresh-timeline]`, форки (`terminal→` в новую PTY-вкладку, `terminal→SDK` в новый SDK-таб — только для Claude), Copy-prompt split-pill (`terminal→ ⎘ prompt | terminal→ + clear` — для живого Claude/Codex PTY), live input actions (`mic | Enter | ^C` — тоже только для живого Claude/Codex PTY), context %-meter.

**Session-id copy `⎘`: Cmd-hover показывает полный id сверху.** Обычный клик по `⎘` копирует текущий `sessionId` и на короткое время меняет иконку на `✓`. При зажатом Cmd и наведении на эту же кнопку появляется read-only tooltip **над** кнопкой с полным UUID (`claudeSessionId` / `geminiSessionId` / `codexSessionId`). Это не action-menu и не поле ввода: цель — быстро проверить «какую именно сессию я сейчас скопирую» без клика и без засорения compact bar длинной UUID-строкой. Отличать от `CopySessionButton` в ProjectToolbar: там Cmd-hover открывает custom session-id input для копирования другой сессии, а здесь — только preview текущего id.

**Copy-prompt split-pill: две кнопки, два IPC.** Обе начинаются знаком `terminal→`, потому что работают с живым TUI draft, а не с уже показанным prompt-блоком History, который копируется обычным выделением/Copy. Левая `⎘ prompt` шлёт `<agent>:copy-input` — helper читает tempfile, отправляет text в socket, **не truncate'ит** input (юзер видит свой draft). Правая `+ clear` шлёт `<agent>:grab-input` — тот же helper в `mode='grab'` truncate'ит tempfile **до** отправки text в socket (атомарно copy+clear в одном Ctrl+G round-trip). Сейчас `<agent>` = `claude` или `codex`; split-pill скрыт когда PTY-процесс не запущен, даже если старый session id сохранён, потому что без живого TUI composer'а Ctrl+G нечего читать. Codex использует тот же UX, но main должен ставить helper-lock на vendor PID, а не только на direct child wrapper — см. `fact-codex.md::Stop и ввод`. См. `fact-prompt-queue.md::Focus terminal перед clear-input` про refocus terminal для немедленного re-read'а Claude'ом пустого tempfile.

**Graveyard: двухступенчатый copy + clear.** До переключения на `grab-input` "+ clear" шёл двумя последовательными IPC: `claude:copy-input` (Ctrl+G) → `claude:clear-input` (второй Ctrl+G ~5ms спустя). На быстрых turn'ах второй Ctrl+G падал в input как литерал `^G` потому что Claude ещё был в external-editor cycle от первого. Плюс `claude:clear-input` имел дополнительный guard `if (claudeTurnBusy === true) return claude_busy` которого нет у `copy-input` (см. `fix-claude-hook-silent-dropouts.md`) — асимметрия: copy успевал mid-turn, clear silently dropped. Симптом юзера: *«копирует, но не очищает окно промпта»*, в production-логе видно `[capture-input:copy]` без последующего `[clear-input]`. Atomic `grab-input` устраняет оба корня — один helper-run труncate'ит файл при отправке text в socket.

**Live input actions: mic + Enter + ^C.** Рядом с mic-кнопкой есть кнопка `Enter`, которая отправляет raw `\r` в текущий PTY input, и кнопка `^C`, которая отправляет raw `\x03`. Все три видимы только когда вкладка — живой Claude или Codex PTY (`isCommandRunning && !isSDKTab && sessionType in {'claude','codex'}`). Без живого TUI composer'а эти кнопки были бы ложным affordance'ом: SDK имеет React composer и свой submit/interrupt path, Gemini не имеет этой связки, обычный shell не должен получать случайный `\r` или `Ctrl+C` из AI-bar.

`Enter` намеренно не использует `safePasteAndSubmit`: он не вставляет новый текст и не делает программный paste+submit race, а только сабмитит уже видимое состояние TUI input. Исключение — активная диктовка: если mic сейчас `recording` или `stopping`, ControlBar переводит Enter в pending-state и ждёт `MicButton` stop-and-deliver, чтобы не отправить старый composer до того как распознанный текст вставлен. Детали — [`fact-dictation.md::Enter во время диктовки`](fact-dictation.md).

Dictation-state в этом keyless bar'е должен быть owner-scoped. `ClaudeControlBar` переиспользуется между табами, поэтому локальный `recording/stopping` без проверки `owner.tabId === tabId` протечёт на соседнюю вкладку: Enter начнёт ждать чужой delivery, а mic будет выглядеть активным там, где запись не принадлежит текущему PTY. Текущий контракт: owner-tab показывает обычный mic/Enter flow, non-owner live tabs получают disabled mic, а background owner раскрывается через status-row сверху справа. Детали — [`fact-dictation.md::Tab-owned background recording`](fact-dictation.md).

`^C` намеренно не проходит через `terminal:stop-ai-process`: это **input action**, а не Stop процесса. Claude/Codex сами решают, что значит одиночный Ctrl+C в текущем TUI-состоянии: очистить видимый input, отменить локальную команду, прервать turn или взвести danger-zone на пустом prompt'е. Если `Enter` уже висит в pending-state после `dictation:stop-and-deliver`, клик `^C` снимает pending Enter через `cancelPendingEnterRef` и не даёт автоматическому `\r` уйти после delivery. Это важно: пользователь передумал отправлять продиктованный текст, но сама доставка текста в composer может ещё завершиться.

**Right cluster.** Provider (PTY only — SDK гоняет напрямую в Anthropic), квадратная кнопка быстрого перехода, Model dropdown, Effort **inline pill-row** (не dropdown), Think toggle. Popup'ы Provider/Model открываются **вверх**: обычное наведение лишь показывает выбор, а клик закрепляет его и даёт триггеру белую рамку; закреплённый выбор закрывается внешним кликом или `Esc`. Wrapper держит 4px hover-мост. Геометрия не должна возвращаться к фиксированному `right: 0`: popup измеряет фактическую ширину, центрируется над триггером и clamp'ится к реально доступной правой границе (включая Timeline только если он действительно справа от триггера). Иначе меню выглядело смещённым влево, хотя у центра было место.

**Effort inline, Provider только иконка — разные стратегии для разных триггеров.** Effort row показывает только отмеченные в настройках уровни текущей модели и подсвечивает активный `#DA7756`: выбор постоянно виден без раскрытия, один клик переключает. Для Haiku это `low/med/high/xhi`; `max` и `ultra` не становятся ложными вариантами. Для остальных shipped Claude-строк полный набор остаётся доступен; `ultra` = ultracode (xhigh + dynamic-workflow на всю сессию), не обычный уровень модели, и отделён вертикальной чертой с фиолетовым акцентом `#7c5cd6`. Сырой CLI может иметь более широкий menu, но выбор в Noted Terminal определяется явной продуктовой таблицей и сохранёнными чекбоксами, а не догадкой по одному metadata-полю. Provider trigger в свёрнутом виде показывает **только иконку** провайдера (без текстового имени Claude/Zen/DeepSeek), имя осталось в `title` и в раскрытом popup'е. Расхождение намеренное: Effort = близкие сравниваемые значения, Provider = сильные бренды, иконка уже различима. Принцип переносимый — см. `methodology/переносимый-дизайн.md::Dropdown vs inline`.

Layout одинаковый для PTY и SDK, но набор контролов разный: для SDK скрыт Provider (SDK гоняет напрямую в Anthropic), а effort использует тот же per-model список; DeepSeek-PTY сохраняет свою отдельную шкалу `DEEPSEEK_EFFORT_LEVELS` с `off`. Continue в SDK превращается в фокус на composer вместо `claude --resume` команды.

Быстрый переход Claude берёт пару из Settings. В SDK он меняет параметры следующего `query()`, в PTY последовательно применяет `/model`, затем `/effort`; успешная смена одной только модели не считается успешным быстрым переходом. Первый клик запоминает предыдущую пару и переключает на целевую, повторный возвращает её только пока текущая пара всё ещё совпадает с целью; ручное изменение или неудачное применение сбрасывает возврат, чтобы кнопка не обещала восстановить несуществующее состояние.

## Codex mode в том же bar

Компонент исторически называется `ClaudeControlBar`, но теперь держит общий lifecycle PTY-агентов. Codex использует тот же triplet session-id / Continue-Stop / refresh Timeline, но с отдельным `codexSessionId` и без Claude-only affordance'ов. На pristine табе рядом с Claude/SDK fork-кнопками видны `Codex` и `⑂ Codex-F`; как только в табе появился любой AI-process или session id, launch/fork-from-clipboard chips прячутся тем же `!hasAnySession && !isCommandRunning` guard'ом, иначе юзер видит fork-кнопки поверх занятого таба.

Codex не показывает Provider, Think и cache chip: у него нет provider proxy в нашем смысле и нет отдельного think toggle. Правая зона для Codex — квадратная кнопка быстрого перехода, Model, Effort и короткая `Fast`-кнопка после Effort. Model/Effort идут через интерактивный `/model` picker Codex TUI; при наведении на строку модели совместимые effort показываются отдельной content-width плашкой. Её правый край совпадает с правым краем наведённой модели: последний `max`/`ultra` остаётся над концом модели, а остальная шкала растёт влево. Название модели внутри не повторяется, потому что наведённая строка уже является видимым контекстом. Клик по effort применяет пару за один picker-flow. Быстрая кнопка берёт сохранённую в настройках пару: первый клик запоминает текущую пару вкладки и переключает на целевую, повторный возвращает её только пока текущая пара всё ещё целевая; ручная смена модели сбрасывает этот возврат, и следующий клик снова выбирает цель. Cmd-hover на кнопке показывает эту сохранённую пару, не меняя её. `Fast` — stateless one-shot affordance, который отправляет ровно `/fast` и не меняет `codexModel`/`codexEffort`. Поэтому availability у правого кластера не может быть одним общим `codexTurnBusy`: Model и Effort остаются доступны во время active turn для настройки последующей работы, а точный `/fast` Codex 0.145 принимает как live service-tier команду текущего turn. Живой лог подтвердил и `Service tier set to priority`, и обратное переключение `Service tier set to default` при `turnBusy=true`. Это узкое исключение не разрешает остальные slash-команды во время streaming: `Fast` доступен только при живом процессе и доказанно пустом terminal composer, а main повторяет current-frame guard у самой записи. Пользовательский симптом регрессии — красный `Codex /fast failed: codex_turn_busy`, отключённая кнопка во время ответа, `/fast` остаётся видимым в input или команда игнорирует набранный draft. Copy-prompt split-pill показывается для Codex только во время живого PTY-процесса и ходит в `codex:copy-input` / `codex:grab-input`; это не Claude-only flow, потому что EDITOR/VISUAL hook инжектится в shellEnv для PTY в целом. Busy-overlay должен очищаться теми же lifecycle-краями, что у Claude/Gemini (`tabId` rebind, process-started, command-finished, ручной reset): это один keyless React-компонент на разные табы, и отдельный Codex-loader легко застрянет при переключении вкладок. Детали Codex parser/picker — `fact-codex.md`.

Model/Effort picker для Codex использует общий main/headless xterm snapshot как основной ответ `hasDraft=true/false/null`. Свежий renderer-positive snapshot может консервативно доказать дополнительный draft и остановить действие, но renderer absence/negative не стирает более авторитетный main proof. После ожидания общей settings-очереди классификация повторяется у самой PTY write-boundary: между первым снимком и `Ctrl+C`/`/model` экран мог стать picker, Rewind или startup. `hasDraft=true` — не ошибка: main сохраняет draft через native stash и возвращает его после выбора; `hasDraft=null` fail-closed, dim-placeholder считается пустым. Детали — `fact-codex.md::Модели и effort`.

Codex Model/Effort хранятся на вкладке (`codexModel`, `codexEffort`), а не в локальном state ControlBar и не в глобальной настройке. Дефолт `xhigh` нужен для видимой пилюли на каждой Codex-вкладке, но при launch он не превращается в скрытый `-c model_reasoning_effort="xhigh"`: дефолтная пара должна приходить из `~/.codex/config.toml`, а ControlBar отправляет `model/effort` только если конкретная вкладка явно выбрана не-дефолтной. Симптом, который нельзя возвращать: пользователь видит `codexEffort` в одном табе и не понимает, «откуда он берётся» — это должен быть tab-scoped selection, а не глобальное эхо.

Codex Model/Effort controls могут сохранять tab-scoped выбор до materialized session id, но busy-режим разделён не по типу параметра, а по способу применения: Model и Effort остаются clickable при `task_started`, потому что оба идут через native `/model` picker и подтверждаются его success-result. Если probe даёт `hasDraft=null` или picker падает, ControlBar не сохраняет выбранное значение как будто оно применилось, а фокусирует терминал и пишет diagnostic log вместо пользовательского уведомления. Для этого ControlBar читает `tab.aiBusy` как Codex turn-busy отдельно от `isCommandRunning`: OSC-состояние отвечает «процесс жив», а rollout busy отвечает «идёт ответ; новая связка model/effort станет настройкой последующей работы». Диагностический минимум в логах правого кластера — `turnBusy`, `hasDraft` и `source`; если пользователь видит `Working...`, но model/effort не применяются live, сначала сверяй именно эти поля.

Runtime-настройки принадлежат доказанному writer, а не одному tab-state. Поэтому частичная смена только модели/effort и quick-toggle блокируются, если writer сменился или ещё неизвестен; явная полная пара остаётся доступным recovery-действием. После успеха proof owner сохраняется вместе с текущим writer. Если свежий Codex ещё не создал первый rollout, полная пара получает одноразовое доказательство для точного PTY/launch generation; его принимает только первый process-proven writer после durable binding. Для Codex 0.145 обычный `Max` меняет persistent default и сохраняет существующий Plan override, а `Ultra` действует только в текущем разговоре и требует отдельного точного acknowledgement.

## Empty PTY controls и launch order

На пустой PTY-вкладке правая зона Model/Effort/Think/Provider **не рендерится вообще**, а не показывается затемнённым Claude-набором. До запуска агента неизвестно, выберет ли пользователь Claude, SDK или Codex; disabled Claude-controls создают ложный сигнал «это Claude-вкладка, просто недоступна», а после запуска Codex этот же блок мгновенно меняет смысл. Пустое состояние должно показывать только действия запуска.

Порядок launch-кнопок слева направо: `Claude`, `Claude-F`, `SDK`, `SDK-F`, `Codex`, `Codex-F`. `Claude` и `Codex` используют один `SessionActionChip`-стиль: обычный вид — короткое имя агента, hover — `Start`, без отдельной рамки и без второго визуального языка. `*-F` берёт session id из clipboard и на pristine PTY-табе использует **текущую вкладку** как цель запуска/конвертации; новая соседняя вкладка создаётся только когда текущая уже занята сессией или живым процессом.

## Focus contract после Start / Continue

Кнопки `Start`, `Continue`, `Claude-F`, `Codex`, `Codex-F` не просто запускают команду — они переводят следующий пользовательский ввод в PTY. Поэтому обработчик клика обязан сфокусировать терминал **до** отправки команды и повторить focus в `requestAnimationFrame` после React-layout. Без этого фокус остаётся на button'е: если Claude сразу показывает `Choose working directory to resume this session`, Enter не попадает в PTY и юзеру приходится кликать терминал вручную; если chooser'а нет, первый набор текста после Continue тоже уходит не туда. Для SDK-Continue тот же контракт, но target surface — composer, а не xterm.

Это не debounce и не ожидание готовности CLI: фокус — локальное UI-состояние, его можно и нужно выставлять синхронно. Детерминированный readiness (`prompt ready`, picker frame, session capture) остаётся отдельным слоем; focus не должен ждать этих событий, потому что интерактивный CLI может попросить пользователя нажать Enter ещё до первой session-записи.

Codex directory chooser при `codex-c`/`codex-f` дополнительно подтверждается main-side auto-Enter по фактическому PTY-фрейму (см. `fact-codex.md::Interrupted recovery и AutoResume`). Это не отменяет focus contract: ручной ввод после запуска, другие chooser'ы и fallback без auto-confirm всё равно должны попасть в терминал без отдельного клика пользователя. Main-side `term.write('\r')` не требует DOM-focus и не должен фокусировать окно сам, иначе background AutoResume начнёт красть фокус у пользователя.

## Busy-state tab binding — `useState` НЕ сбрасывается сам при смене таба

`ClaudeControlBar` монтируется в `Workspace.tsx` **без `key`** — React **переиспользует** один инстанс на все табы проекта, при переключении меняется только проп `tabId`, компонент **не ремаунтится**. Из этого следует ловушка для любого локального `useState`-флага (`isPasteBusy`, `isLocalBusy`, `effortLocal`, `thinkLocal`): он **не обнуляется** автоматически при смене `tabId`. Эффекты с `[tabId]` в deps пере-подписывают слушатели, но значение state остаётся от прошлого таба.

Два прод-бага вытекают ровно отсюда (сессия `ea2ae02c` / tab-283, 2026-06-03 ~22:07 MSK):

1. **LEAK across tabs.** `isPasteBusy=true` пойман для таба A → юзер переключился на таб B → shimmer-overlay правого кластера всё ещё горит, хотя B ничем не занят. Юзер: *«я на другую вкладку перешёл… но у меня почему-то loader от вот этого компонента всё равно сохранялся»*.
2. **STUCK FOREVER.** `safePasteAndSubmit` шлёт `emitBusy(false)` с `{tabId: A}` (см. `fact-claude-tui-control.md::paste-busy`). Но к моменту прихода этого события слушатель уже фильтрует по **новому** `tabId` (B): `if (data.tabId === tabId)` → `A !== B` → `false` **дропается**. Локальный `isPasteBusy` остаётся `true` навсегда — переживает reload вкладки и даже kill Claude-процесса. Это и есть «убил процесс клода, а loader не сбросился».

**Корень совпал с гипотезой юзера:** *«лоудер не имеет привязки к вкладке»*. Буквально: busy-флаг — это renderer-local state одного переиспользуемого инстанса, не per-tab persistent поле, и при ребинде он не чистится.

**Фикс (три слоя в одном `useEffect([tabId])`):**
- **Синхронный reset на ребинд:** в начале эффекта `setIsPasteBusy(false); setIsLocalBusy(false)` — свежепривязанный таб всегда стартует чистым, не наследует busy прошлого.
- **Clear на lifecycle-краях:** подписка на `claude:process-started` и `terminal:command-finished` (OSC 133 D) с фильтром по `tabId` → обнуляют оба флага. Когда Claude стартовал или умер — живого TUI mid-paste нет, любой висящий индикатор по определению stale. Это то, что чинит recovery после kill.
- **Manual escape hatch** (см. ниже) — на случай если оба автопути промахнулись.

Переносимый принцип: **любой `useState` в keyless-переиспользуемом компоненте, чьё значение семантически per-tab (или per-любой-prop-идентичность), обязан иметь explicit reset в `useEffect([thatProp])`.** Без `key` React не сделает это за тебя. Родственный антипаттерн — `fix-zustand-silent-mutation.md` (stale value при правильной подписке).

## Click-to-reset overlay на залипшем busy-кластере

Юзер-запрошенный escape hatch поверх автоматических clear'ов: *«самое простое решение — сделать эту область кликабельной, при наведении красное СТОП на весь loader, переклик сбрасывает состояние»*.

Когда `isBusy` — поверх всего правого кластера (Provider/Model/Effort/Think) рендерится `.control-bar-busy-reset` (absolute, `inset:0`, `z-index:2` — выше shimmer-`::after` который `z-index:1`). Родитель в busy ставит `pointer-events:none`; overlay сам себе возвращает `pointer-events:auto` через CSS. Idle-вид overlay'я — прозрачный (label `color:transparent`), чтобы оранжевый shimmer просвечивал нетронутым. Hover — сплошная красная заливка + статичный белый **uppercase «СБРОС»** (destructive-intent + AI-OCR rule: статичный B/W uppercase, не opacity-анимация). Клик зовёт `forceResetBusy` → `setIsPasteBusy(false); setIsLocalBusy(false)` + refocus terminal.

**Что reset НЕ делает:** не отменяет реально летящий main-side paste — он только ре-синкает UI. Per-term mutex (`pasteInflight` WeakMap) в `safePasteAndSubmit` всё равно сериализует любую настоящую конкурентную запись на тот же PTY. То есть клик безопасен даже если main на самом деле занят: UI разблокируется, но байты не интерлевятся.

CSS — `globals.css::.control-bar-busy-reset` (рядом с `.control-bar-busy-overlay`). Красный тон `rgba(220,38,38,…)` = тот же `#dc2626` что в `glow-red` (единая палитра destructive).

## Per-tab state и selectors

Tab-метаданные (`tabType`, `sdkModel`, `sdkEffort`, `sdkThinking`) читаются через **отдельные** primitive Zustand-селекторы на каждое поле. **НЕ** единый композитный селектор — он возвращал бы свежий объект `{}` на каждом рендере, Zustand видит новую ссылку и фурит компонент в бесконечный re-render. Это та же ловушка что в CLAUDE.md anti-pattern «Не подписывайся на Map целиком» (Zustand fingerprint pattern).

PTY-Claude Model/Effort в ControlBar — проекция подтверждённого состояния **текущей сессии**, а не local mirror глобальных defaults. При привязке сессии bar читает её активную `parentUuid`-ветку и принимает только прямую пару `/<setting> value` → `<local-command-stdout>Set ...</local-command-stdout>`. Тот же transcript watcher обновляет bar после ручной команды в терминале; после Rewind физически более новые записи отброшенной ветки не выигрывают. Поэтому renderer/app restart восстанавливает фактические `model/effort`, а не сбрасывает их в `default`/`unset`.

StatusBar при этом остаётся настройкой **будущих** запусков. `_modelSentForTab` / `_effortSentForTab` лишь не дают двум startup-путям повторно отправить одну команду и очищаются со смертью процесса; они не являются источником отображаемого значения. Ошибка чтения JSONL не разрешает подменить состояние текущей сессии StatusBar-default'ом. `thinkLocal` остаётся отдельным TUI-mirror. См. `fact-claude-tui-control.md::Startup defaults /model + /effort при запуске Claude`.

## Context % bridge: три канала — PTY, SDK, Codex

PTY: `claude:bridge-update` IPC event с payload `{tabId, sessionId, model, contextPct}`. **Цифра — собственное число Claude, не наш расчёт.** Цепочка: Claude Code statusLine отдаёт `context_window.used_percentage` (уже посчитанный против `context_window_size` модели — 200k или 1M, знаменатель разрешает сам Claude) → `~/.claude/statusline-bridge.sh` читает это поле (`jq '.context_window.used_percentage'`, `cut -d. -f1` флорит в int) и пишет в `~/.claude/bridge/<session>.json` поле `context_pct` → main `processFile()` форвардит как `claude:bridge-update` → ControlBar показывает сырым. Это **ровно то же значение что в TUI-statusLine** — никакого пересчёта `used/window` на нашей стороне (и не должно быть: своя формула разойдётся с источником на 1M-сессиях, см. `methodology/переносимый-дизайн.md::Отображаемую метрику читай из числа источника`). НЕ «парсится из JSONL» — источник именно statusLine-хук, не транскрипт.

Три guard'а на handler'е (`ClaudeControlBar.tsx`):
- **exact binding**: как только у таба есть долговечный `claudeSessionId`, bridge-кадр принимается только с тем же session ID. Это закрывает позднее событие старой сессии уже после завершившегося handoff; до первой привязки свежей сессии кадр ещё разрешён, чтобы bootstrap не закольцевался.
- **stale-session**: handler консультирует `isStaleAgainstPending(tabId, data.sessionId)` перед display+persist. Без этого во время resume-гонки (PID reuse) мёртвая сессия штамповала свой % на таб И писала его в SQLite (`tab:persist-context-pct`) — Terminal.tsx отвергал чужой sessionId-write, но meter всё равно врал. main шлёт `sessionId` в payload именно для этой сверки. См. `fix-bridge-stale-takeover.md`.
- **live-0 не затирает seed**: live-кадр `contextPct === 0` (sub-1% зафлоренный `cut -d. -f1`, или отсутствующее `.used_percentage` → jq `// 0` fallback) больше НЕ вызывает `setContextPct(0)` — render-guard прячет meter при 0, и безусловный сброс гасил только что засиженное из SQLite значение. `setContextPct` теперь симметричен `persistContextPct`'s `pct <= 0` guard: применяется только положительное число, иначе держим last-known.

Seed: на mount таба meter засевается из SQLite (`tab:get-context-pct` → `getTabContextPct`) — показывает last-known fill даже когда Claude не запущен (CLI вышел / ещё не стартовал). Известная неточность которую НЕ чиним: после `/clear`/rewind реальный контекст падает, но seed/last-persisted держит старый % до следующего assistant-turn'а который перепишет bridge.json.

SDK: нет IPC. `ClaudeSDKTab` хранит `lastContextUsedTokens` в локальном React-стейте и диспатчит `window.CustomEvent('sdk-context-update', {detail: {tabId, contextPct, model}})` на каждом ассистентском SSE. ControlBar слушает window-event. Мотивация: добавлять новый IPC channel + поле в Tab interface ради одного UI-меридиана — overkill. Window CustomEvent дешевле и не трогает SQLite-схему. Тот же паттерн уже использован для `history-panel:loading`. (SDK считает % сам — `lastContextUsedTokens / getModelContextWindow(...)` с детектом `[1m]`/Opus-4.8 — потому что у SDK нет statusLine-хука; это исключение из «бери число у источника», т.к. источника готового процента у SDK-канала нет.)

Codex: `codex:context-update` IPC `{tabId, sessionId, contextPct}`. **Цифра — собственное число Codex, не наш пересчёт:** берётся из `event_msg.token_count.info` в rollout JSONL. Ключевое — **не заводить отдельный watcher и не поллить**: turn-watcher из main (`codexTurnWatchers`, тот что уже тайлит rollout ради busy-state `task_started/complete`) на каждой строке `token_count` считает `last_token_usage.total_tokens / model_context_window` и эмитит. Слушатель в ControlBar — зеркало SDK-обработчика (тот же stale-against-pending guard, тот же `setContextPct`/`persistContextPct` при `>0`), поэтому Codex-вкладка переиспользует ровно тот же `contextPct` state + SQLite seed (`tab:get-context-pct`) что Claude/SDK: чип, цвет и выживание после рестарта получаются бесплатно. **Ловушка знаменателя — `last`, не `total`:** `last_token_usage` = последний единичный запрос, а Codex каждый ход пере-отправляет всю историю, поэтому `last.total_tokens ≈ текущая занятость окна`. `info.total_token_usage` — кумулятив за всю сессию (десятки миллионов токенов за длинную сессию) → делится в тысячи процентов и вечно клампится в 100%; брать его в метр нельзя (та же ловушка живёт в `codex:get-timeline`, см. `fact-codex.md::Timeline и History`). Дополнительно: при первом подключении watcher'а к сессии (`catchUpCodexTurnState`) последний `token_count` из хвоста журнала эмитится сразу — resume'нутая вкладка засевает метр из транскрипта, не дожидаясь нового хода.

## Cache cooldown chip — близнец контекст-метра

Слева от контекст-метра в LEFT-кластере. Главная цифра — **минуты до остывания** prompt-кэша, мелким рядом — % тарификации (доля от полной цены за последний ход). Два канала под ту же ось что у контекст-метра: PTY через `claude:cache-update` IPC (proxy парсит `message_start`, fires **только** в anthropic-режиме → для DeepSeek/Zen событие не приходит вообще), SDK через `sdk-cache-update` window-event (SDK ходит на Anthropic мимо proxy, ловит usage у себя и ре-эмитит). Оба несут `{cacheRead, cacheCreate, input, ts}`.

**Provider-gate, не просто «скрыть если нет данных»:** чип показывается при `(isSDKTab || isAnthropicPTY) && cacheData`. DeepSeek/Zen не имеют prompt-кэша — у них чип не появляется конструктивно (событие не приходит), плюс явный гейт по провайдеру на случай если канал что-то прислал. Codex — отдельно, см. секцию Codex выше («не показывает cache chip»).

**Почему у Codex такого чипа нет конструктивно, а не «пока не сделали».** Главная цифра чипа — обратный отсчёт, и он возможен только потому что у Anthropic TTL = фиксированный 1 час (захардкоженная константа-якорь) + `ts` последнего хода из источника. У OpenAI второго якоря не существует: официальные доки дают не фиксированный TTL, а плавающее окно — «typically 5–10 min of inactivity, up to 1 hour off-peak», extended-retention «up to 24h» для gpt-5.x, плюс eviction по memory-pressure (кэш умирает не по таймеру, а когда GPU-память переполнилась — подтверждено на разрывах в секунды). Codex вдобавок сам не шлёт `prompt_cache_retention`, то есть активен дефолт организации, невидимый клиенту. Значит любой «остынет через N мин» для Codex = выдуманный знаменатель, который систематически врёт (прямой случай `methodology/переносимый-дизайн.md::Отображаемую метрику читай из числа источника`). Единственный честный кэш-сигнал у Codex — постфактумный `cached_input_tokens` per turn (был ли кэш-хит), и он живёт в detail-панели Timeline, не в этом чипе — см. `fact-codex.md::Per-turn usage в detail-панели Timeline`.

**Таймер замирает в busy — потому что TTL refresh-on-use.** Сервер продлевает 1h-TTL на каждом обращении (см. `fact-provider-proxy.md::TTL кэша = 1 час`), поэтому обратный отсчёт осмыслен только пока сессия простаивает; во время живого хода он бы прыгал обратно на 60 каждую секунду. Решение: при `busy` (для PTY — `isCommandRunning`, для SDK — `sdkBusy`) главная цифра заменяется на точку «●», `setInterval` на тик не заводится. ≤10 мин до сброса — жёлтый, >60 мин простоя — серый «❄ остыл». Чип — отдельный компонент со своим минутным интервалом, чтобы тик не ре-рендерил весь бар. `ts` не персистится: устаревший момент последнего хода врал бы про свежесть после рестарта, на cold-start чип пуст до первого ответа.

## sdkBusy mirror — отдельная подписка для SDK таб'ов

PTY-табы получают `isCommandRunning` от Workspace через OSC 133 D/B (см. `fact-terminal-core.md::OSC 133`). SDK-табы PTY не имеют — этот канал всегда возвращает `false`, и chip/right-cluster никогда не узнают что query сейчас идёт. Решение — ControlBar **локально** подписывается на `claude:busy-state` IPC (main forward'ит туда `claude-sdk:busy-state` через одну общую шину) с guard'ом `isSDKTab && data.tabId === tabId`. Полученный `sdkBusy` подаётся в `SessionActionChip` вместо `isCommandRunning` (только для SDK-режима); для PTY режима остаётся OSC-канал. Это единственный способ узнать busy-state для SDK таб'а на уровне ControlBar, не таская дополнительный prop из Workspace.

## Right cluster для SDK всегда enabled

PTY-режим: правый кластер (Provider/Model/Effort/Think) затемнён когда `!isCommandRunning` — без живого TUI slash-команды улетят в мёртвый shell и потеряются. SDK-режим: параметры применяются **аргументом** при следующем `query()` вызове (см. `fact-claude-sdk-tab.md::Effort: продуктовая таблица по модели, ultracode через settings`), не slash-командой в живой TUI. Юзер может выбрать модель/effort/think **до** первого сообщения, настройки персистятся в `Tab.sdk*` полях, в первый же submit пойдут.

Codex - узкое исключение внутри PTY: при `task_started` Model и Effort остаются доступны, потому что native `/model` явно разрешён во время task и меняет параметры будущей работы сессии. Effort не применяется «сырым» slash-command'ом; он проходит тем же picker-flow и меняет `tab.codexModel/codexEffort` только по success-result native picker, не по самому клику.

Гард в коде — `const canControl = isSDKTab ? true : isCommandRunning;`. Без этого SDK таб без session_id показывал кластер с `opacity: 0.4` + `pointer-events: none`, юзер видел disabled кнопки и не мог поменять модель до отправки первого prompt'а.

## Visibility guards для clipboard-fork chips

Кнопки `SDK` (`startNewSDKTab`), `Claude-F`, `SDK-F`, `Codex`, `Codex-F` показываются на pristine табах — `!hasAnySession && !isSDKTab`. К этому guard'у добавлен **третий**: `!isCommandRunning`. Без него существовал window между `claude:process-started` / `codex:process-started` (PTY запустил агент) и первой записью session id в Tab (1-3 сек) — в этом окне юзер видел fork/start-кнопки одновременно с живым процессом, *«у меня в этой вкладке запущен процесс клода, но одновременно отображаются Claude-F и SDK-F, какого хуя»*. С `!isCommandRunning` guard'ом кнопки прячутся как только OSC 133 D говорит «команда запущена».

## Fork: current-session всегда в новый объект, clipboard `*-F` может занять пустую вкладку

`⑂→▭` (`forkToTab`) и `⑂→SDK` (`forkToSDK`) — это кнопки форка **от текущей сессии**. Они рендерятся только когда у текущей вкладки уже есть `sessionId`, поэтому их действие всегда должно создавать новый объект рядом: PTY-tab для `⑂→▭`, SDK-tab для `⑂→SDK`. Даже если процесс уже остановлен и `isCommandRunning=false`, текущая вкладка всё равно содержит историю/identity исходной сессии; запуск fork'а в ней подменяет контекст, ломает ожидание от title `Fork в новую вкладку` и визуально выглядит как потеря родительской сессии.

Корневой симптом, который нельзя возвращать: юзер сделал Codex-fork, остановил процесс, нажал обычный `⑂→▭`, а fork запустился в той же вкладке, потому что guard смотрел только на `!isCommandRunning`. Это неверная ось. Для current-session fork состояние процесса не решает, свободна ли вкладка; решает наличие session identity. Если есть текущий `sessionId`, fork — всегда sibling.

Все async fork-действия показывают spinner внутри нажатой кнопки с первого синхронного state-update. Исходный label остаётся невидимым в layout и резервирует прежнюю ширину, поэтому соседние controls не сдвигаются в момент клика. In-flight identity включает `tabId + action + sequence`: повторный клик в той же вкладке блокируется, а `finally` старой вкладки не может снять loader более нового действия после tab switch. Таймер не является источником окончания — loader очищает completion самого action.

Clipboard-варианты (`Claude-F`, `SDK-F`, `Codex-F`) следуют той же идее, но источник session id — буфер обмена, а не текущая вкладка. Если юзер сначала открыл пустую вкладку и нажал `Codex-F`, это намерение «используй эту вкладку как target», а не «создай ещё одну пустую рядом». Поэтому pristine PTY → in-place (`claude-f` / `codex-f` в текущий PTY, `SDK-F` через `convertToSDKTab`), занятая PTY или SDK → соседняя вкладка.

Исключение строго одно: clipboard `*-F` на pristine PTY-табе, где нет `claudeSessionId`, `geminiSessionId`, `codexSessionId` и нет живого процесса. Там текущая вкладка действительно пустая и может быть target'ом. Переносимый принцип — `methodology/переносимый-дизайн.md::Fork от живого/типизированного контекста = новый объект`.

## Карта visibility всех кнопок

В исходном коде `ClaudeControlBar.tsx` перед `return` JSX'а лежит ASCII-таблица состояний кнопок (`copy-session-id`, `SessionActionChip`, `refresh-timeline`, Claude/SDK/Codex fork chips, live-only `copy-prompt`, `mic`, `Enter`) по PTY/SDK/Codex состояниям. Источник правды для UI-state. **При любом изменении guard'а** — обновляй таблицу в коде синхронно (иначе следующий разработчик прочтёт устаревшую карту и сделает противоречивый guard). Юзер: *«можешь в этом компоненте как-то комментариями пометить, чтоб мы на будущее эту хуйню не сохраняли»* — карта нужна именно для предотвращения регресса.

## Busy-overlay вместо disabled на правом кластере

Когда команда из правого кластера в полёте (`claude:send-command /model haiku`, `provider:switch`, `claude:toggle-thinking`), кластер визуально маркируется shimmer-полоской через CSS `::after` (`.control-bar-busy-overlay` + `@keyframes control-bar-busy-sweep` в `globals.css`) и блокирует клики через `pointer-events: none` на обёртке.

**Не делать так.** Раньше каждый триггер в кластере имел `disabled={isBusy}` + `opacity: 0.5` в style. Проблемы: (а) `disabled` с серой полупрозрачной заливкой выглядит как «функция сломана/недоступна», а не «занят, подожди»; (б) триггеры с динамическим label'ом (Model, Effort) меняют ширину при изменении значения, плюс disabled на soome платформах меняет padding/border визуально — суммарно блок «съёживается». Юзер: *«сейчас он меняет ширину когда становится дизайблнутым; нужно сделать лоадер, при этом не менял ширину; сделать и дизельблуд, и мигающим красиво»*. Принцип переносимый — см. `methodology/переносимый-дизайн.md::Busy-overlay вместо disabled`.

## Graveyard

**`setSdkModelCaps({})` в effect с `sdkModelCaps` в deps → infinite re-render loop.** Кэш model-caps загружается через `ipcRenderer.invoke('claude-sdk:get-model-caps')` один раз при mount'е SDK-таба. Изначально dep'ы effect'а были `[isSDKTab, sdkModelCaps]`. Когда main возвращал `{success:true, caps:{}}` (пустой кэш в первой версии endpoint'а), `setSdkModelCaps({})` создавал новую ссылку → effect re-fire → новый invoke → новый `{}` → бесконечно. Симптом — React error boundary с `Maximum update depth exceeded`, render-counter `[CB:R]` рос монотонно. Фикс: убрать `sdkModelCaps` из deps + добавить `Object.keys(r.caps).length > 0` guard (не записывать пустой объект). Принцип переносимый — *empty-object setState в effect deps создаёт ref-loop*, см. CLAUDE.md anti-pattern «Zustand: Не подписывайся на Map целиком» как родственный.

**`provider:get-state` IPC не существовал.** Правильный канал — `provider:get-status` с `{tabId}` payload. AI восстановит из grep по main/ipc — но если повторно столкнёшься с тем что provider state не читается — ищи имя канала, не реализацию.

## Брендирование Claude/Gemini

Два движка имеют закреплённые цвета: Claude — saffron orange `#DA7756`, Gemini — blue `#4E86F8`. Цвет активируется автоматически по типу сессии активной вкладки и распространяется на Timeline-точки, рамку и аксессуары `ActionsPanel`, статус-сообщения, Stop-кнопку (`Stop Claude` / `Stop Gemini`). Resume/Continue chip подстраивается под тип активной сессии — оранжевый текст для Claude, синий для Gemini, чтобы пользователь без чтения лейбла видел, какой движок будет восстановлен. Тот же brand-tint в split-кнопке Stop при multi-select (см. `fact-tabs.md::Multi-select Stop с majority badge`), в Provider-row, в `ApiSettingsModal`, в командных Status Styles (`<code>` тег, фон `#1a1a1a`, hover underline) — единая палитра по всему проекту, без локальных вариаций.

## ActionsPanel адаптируется под движок

Для Gemini-табов скрываются Claude-only опции в `ActionsPanel`: переключатели «Include Reading», «Include Editing», «From Start». Эти концепты завязаны на структуру JSONL Claude (`type: 'user'` с `tool_result`, fork-сегменты, /compact branches) — Gemini-сессии устроены иначе, тогглы для них семантически пустые. Без скрытия юзер видел бы непонятные опции, не дающие эффекта.

Подзаголовок `Copy session` меняется на `Claude JSONL → clipboard` или `Gemini JSON → clipboard` в зависимости от активной вкладки. Юзер видит формат источника без раскрытия dropdown'а — disambiguation в один взгляд.
