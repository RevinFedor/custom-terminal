# Оркестрация AI-вкладок

## Зачем нужен отдельный контур

Оркестрация вкладок — продуктовый сценарий Project API, а не цикл чтения чужой истории. Он нужен для запросов, которые могут работать десятки минут и запускаться с другого компьютера, где у клиента нет локальных MCP-серверов. Поэтому HTTP-запрос подтверждает только принятие задачи и быстро завершается; ожидание ответа принадлежит сохранённому run и SSE.

Terminal/History scenario layer остаётся единственной точкой живого управления Claude/Codex. Оркестрация не пишет в PTY напрямую и не читает TUI-output: создание фоновой вкладки, readiness, send during streaming, resume и очередь проходят через те же сценарии, что Project API и History. `delegate_to_session` / `get_delegation_result` единого Terminal MCP — тонкие typed-wrapper'ы над этим API; history-tools не участвуют в штатном ожидании run.

## Контракт run

Каждый запуск связывает исходную и целевую вкладки вместе с их проектами. Новая target-вкладка всегда создаётся в фоне: запуск исполнителя не меняет активный проект или вкладку пользователя. Связанная работа в том же проекте по умолчанию создаётся visual-child исходной вкладки; независимый run использует явный `placement: root`. Межпроектный запуск без явно выбранного parent остаётся root, а повторный вызов существующего `targetTabId` никогда не переподчиняет уже организованную вкладку.

Визуальная иерархия вкладок и причинная иерархия run — разные связи. Если исполнитель активного run сам вызывает `delegate_to_session`, новый run получает `parentRunId`: явно переданный ID имеет приоритет, автоматическое связывание допустимо только при одном однозначном входящем run исходной вкладки. Цикл, ссылка на завершённый run и неоднозначная автоматическая связь отклоняются. По умолчанию `waitForDescendants: true`: собственный ответ исполнителя сохраняется, но родитель не получает итог, пока не завершены дочерние ветки и доставленный дочерний результат не потреблён следующим ходом исполнителя. Этот ход обязан начаться отдельным app-owned completion user-message; чтение результата внутри исходного assistant-turn не считается ожиданием. `waitForDescendants: false` — явное разрешение раннего отчёта, а не скрытая эвристика по effort или длине ответа.

`202 Accepted` означает, что prompt принят общим send-сценарием, но не что ответ готов. Состояние дальше приходит как `orchestration-update` через SSE; статус и результат также адресуются стабильным `runId`. Клиент не держит исходный POST открытым и не опрашивает transcript. После completion-уведомления полный ответ читается одним `get_delegation_result` или HTTP GET.

Полный prompt и ответ не дублируются в orchestration-store. Store хранит размер prompt и fingerprint для сопоставления, а результат извлекается из канонического Claude/Codex transcript. Это одновременно не размножает историю, не раздувает служебный JSON и позволяет после restart доказать, какой именно turn принадлежал run.

Codex compact внутри долгого ответа не начинает новый продуктовый turn. History
может представить compact отдельной строкой, а дальнейшие assistant-блоки —
техническим продолжением без userUuid; result-reader использует чистую проекцию
того же реального пользовательского хода и возвращает блоки по обе стороны
compact. Следующее настоящее пользовательское сообщение остаётся жёсткой
границей и в чужой результат не попадает.

Для fresh Codex модель и effort принадлежат launch: новая вкладка получает их при старте, а первый send передаёт только prompt. Повторная попытка применить ту же пару вместе с `queue:true` уже после появления ready-composer корректно отклоняется idle-guard'ом и раньше оставляла target готовым, но без пользовательского сообщения (`codex_settings_change_requires_idle`). Для существующего idle target настройки можно применить перед send; busy target не должен маскировать смену настроек очередью.

## Авторитетный lifecycle

Готовность определяется структурными событиями агента: `task_started`/`task_complete`/`turn_aborted` для Codex и эквивалентным busy/done-контуром Claude. Стабильность текста, возврат prompt-глифа и terminal output не являются completion-proof.

`queue:true` означает только разрешение поставить сообщение за уже идущей работой. Это не доказательство, что предыдущий turn существует. Ожидание чужого completion включается только по реальному baseline `busy` или по сохранённому predecessor-run на том же target. Иначе собственный `task_complete` ошибочно поглощается как окончание несуществующей предыдущей задачи, а run навсегда остаётся `queued`.

У Codex post-Enter `user_message` audit может завершиться позже собственного `task_started`. Поэтому события до подтверждения доставки не объявляют run запущенным вслепую, а сразу после acceptance выполняется одна сверка transcript + live status. Она закрывает окно гонки; дальнейшее ожидание снова полностью event-driven. Это не polling.

Несколько run на одном target упорядочиваются predecessor-связью. Lifecycle применяется только к головному run; после его terminal-state следующий получает собственный busy→done. Один completion нельзя засчитать двум задачам.

Зависимости пересчитываются снизу вверх отдельно от predecessor-очереди. После собственного успешного ответа run с незавершёнными потомками остаётся активным в `waiting_descendants`; exact post-Enter audit уведомления ребёнка доказывает, какой именно follow-up начался, и только последующий authoritative done может закрыть ветку. Generic busy-turn того же исполнителя не устанавливает эту причинную связь. Поэтому короткий idle-разрыв между ребёнком и follow-up родителя не является окончанием всей работы.

После terminal-state дочернего run ветка ещё не считается свободной: отдельное durable-состояние source-handoff удерживает `inheritedBusy` во время result-proof, вставки/очереди completion-сообщения и до post-Enter доказательства именно этого уведомления. Доказательство несёт точный `runId` в handoff/source identity; generic `busy:true` источника не имеет права снимать oldest pending run. Prompt/Stop/Close After, Git Run After и Restart After используют общий completion-gate: они не стреляют на idle родителя, пока живы потомки или не завершён точный handoff. Фиксированная пятисекундная пауза запрещена: занятый input может законно держать notification в очереди дольше.

Fresh Claude требует отдельной причинной границы: до первого prompt у вкладки ещё нет JSONL-пути и `sessionId`, хотя процесс и composer уже готовы. Непосредственно перед Enter main доказывает Claude PID под точным PTY, чтобы `UserPromptSubmit` привязал появившуюся запись к staged send. Только для этого unresolved-transcript случая допустимо сравнение timestamp записи с моментом отправки; ошибка чтения уже известного JSONL не превращается в такое доказательство. Иначе одно физическое уведомление отображается в History дважды: как временная строка handoff и как durable user-запись.

## Завершение и уведомление источника

После успешного completion сервер сначала сопоставляет result-turn, затем отправляет в исходную вкладку короткое служебное сообщение через общий History/send-сценарий. В сообщение входят `runId`, исполнитель и адрес результата, но не полный ответ. Источник делает один структурный GET и продолжает исходную задачу без ANSI/TUI-парсинга. Result вместе с текстом возвращает точные `targetTabId` и `targetProjectId`: если исполнитель создавался только для разового теста или исследования, источник после чтения результата закрывает именно эту вкладку через Terminal MCP; постоянные сессии остаются открытыми.

Служебное уведомление не владеет текстом, уже набранным пользователем в source-composer. Видимый History-input живёт отдельно от PTY: реальный Electron-flow сохранил его текст, пока Claude получил и обработал completion отдельным turn. Нативный TUI composer защищён другим preflight того же send-сценария даже при `queue:true`: Codex использует headless draft-authority, Claude — актуальный headless terminal snapshot. Доказанный draft возвращает `terminal_draft_conflict`, уведомление переходит в `waiting-for-input`, а текст не меняется; неизвестность на активном materialized composer останавливает отправку вместо blind paste. Fresh source без materialized terminal-state остаётся разрешённым первым prompt, иначе уведомление само никогда не смогло бы создать его первую запись.

После authoritative освобождения input доставка пробуждается событием и повторяется. Для конфликта с уже набранным Claude/Codex TUI draft `busy:true` источника является безопасным wake-сигналом: source начал новый turn, после чего доставка заново выполняет авторитетный draft-preflight и продолжает только при пустом composer. Само событие не доказывает identity отправленного текста, не заменяет preflight и не подтверждает ни одно completion-уведомление. Успешный post-Enter audit освобождает только совпавший `runId`, поэтому два pending уведомления могут подтверждаться в обратном порядке без сдвига на один run. Idle/noise-событие retry не вызывает; `done` остаётся дополнительной границей для прежних waiting-состояний. Результат всё время доступен по `runId`, а повторная доставка не выводится из таймера или чтения transcript. Автоматическое пробуждение остаётся штатным для доказанного draft-conflict; явный Retry нужен для терминального состояния `unconfirmed`, где транспорт уже принял Enter, но после restart точное появление сообщения доказать не удалось. Такой Retry осознанно допускает повтор и потому не выполняется автоматически.

Уведомление — отдельный outcome. Run может быть успешно завершён, даже если source нельзя разбудить: например, fresh Claude был остановлен до первого materialized turn. Тогда сохраняется `notificationStatus: failed` с причиной `session_not_materialized`, а результат остаётся доступен по `runId`; ошибка уведомления не переписывает успешный target-result. Если source-вкладку удалили уже после target-result, ещё не доставленное уведомление терминально подавляется как `source-closed`, но сам результат остаётся завершённым и доступным.

Если fresh source-процесс всё ещё жив и input-ready, completion notification может стать его первым materialized prompt. Это нормальный путь: уведомление отправляется один раз, создаёт первую durable user-запись и гасит временный History handoff. Остановленный fresh source без готового composer остаётся предыдущим failure-case и не получает искусственную историю.

Abort/interrupt target-turn переводит run в failure, а не в completed. Явная отмена run может дополнительно interrupt’ить target, но обычное завершение не останавливает runtime: вкладка остаётся пригодной для следующего сообщения.

Явный Terminal MCP `complete_task` относится к готовности всей задачи source-вкладки, а не к исходу одного run. Поэтому вкладка с активными исходящими run получает отказ и не может погасить свой Loop или отчитаться как полностью готовая раньше дочерних исполнителей. Сам вызов ничего не завершает: он становится действительным только вместе с успешным authoritative done точного текущего provider-turn; ненормальный исход этот intent отменяет.

## Ошибка, восстановление и очистка

Ошибка провайдера, startup failure, выход процесса и закрытие target не должны выглядеть как успешный ответ или вечная очередь. Они нормализуются в отдельный outcome и переводят run в `waiting_recovery` с сохранённым deadline. Ручной interrupt/Escape участвует в этом flow только при включённой настройке; реальная ошибка и закрытие target учитываются всегда.

Во время grace-периода карточка предлагает три разных решения: восстановить слежение, передать ошибку родителю сейчас или закрыть вызов без сообщения. Новый подтверждённый busy-turn target автоматически восстанавливает тот же run; поздняя работа после dismiss или истёкшего deadline старый вызов не оживляет. Закрытие вкладки проходит через общий `closeTab` и сообщает store сразу, поэтому все связанные активные run получают исход вместо жёлтого `queued` навсегда.

Deadline и настройки хранятся вместе с run-store, а main ждёт ближайшую дату одним scheduler'ом. Renderer только показывает обратный отсчёт. По истечении recovery deadline ошибка становится конечной и доставляется source; после успешного одноразового run отдельный deadline может остановить созданный orchestration target. Старое намерение auto-stop навсегда теряет право на действие, если после завершения его run тот же target принял или начал более новую работу — даже когда новая работа уже успела завершиться к deadline. Проверять только текущие active run недостаточно: такой guard останавливал вкладку под уже выполненным следующим заданием. Вкладка не удаляется, а переиспользованный пользовательский target автоматически не останавливается.

## Persistence и восстановление

Run-метаданные, дерево зависимостей, recovery/auto-stop deadlines и настройки пишутся атомарно вне renderer-state и переживают Electron restart. При старте активные записи сверяются с transcript и текущим состоянием вкладки: найденный matching turn восстанавливает `running`, `waiting_descendants` или результат. Для уже доставленного completion-handoff отдельно ищется exact сохранённый prompt hash в transcript source-вкладки. Совпадение завершает handoff; отсутствие совпадения переводит старое `sent/queued` в `unconfirmed`, сохраняет возможность позднего exact proof, но убирает ложный spinner и требует Retry либо явного закрытия. Renderer нужен для отображения, countdown и переходов, но не является владельцем lifecycle.

История ограничена по числу и возрасту завершённых записей; активные run не удаляются этим лимитом. Idempotent client-supplied `runId` защищает повтор POST после сетевой ошибки от создания второго исполнителя.

## UI в History

Верхняя поверхность вплотную слева от `History` — live tracker: она показывает активные run и требующие решения recovery/delivery-состояния. Несколько одновременных вызовов объединяются в ограниченный по высоте прокручиваемый список; каждый ряд ведёт к связанной вкладке и раскрывает направление, проект и состояние. Верхняя строка popover принадлежит run, поэтому generic `закрыть / копировать` там не показываются: активный запрос получает отмену, recovery — восстановление, передачу ошибки и закрытие без сообщения, а неподтверждённая доставка — Retry и `×`. `×` сохраняет результат, подавляет только старое уведомление и освобождает completion-gate. Отмена `running` run передаёт soft-interrupt с доказанным `busy:true`; queued/sending run закрывается без терминальной клавиши, которая на idle Codex могла бы открыть Rewind. Отдельная settings-кнопка управляет grace, auto-stop и реакцией на ручной interrupt. При раскрытом Timeline rail сдвигается на его overlay-ширину: служебные controls не должны перекрывать semantic group и перехватывать клик её строк.

Успешно завершённый target исчезает из tracker только после точного подтверждения source-handoff; terminal failure остаётся до решения или deadline. Все конечные run доступны в компактном окне `History`, открывающемся вплотную слева от своей кнопки. Окно не блокирует History/terminal и прокручивается внутри. Переход из обеих поверхностей использует сохранённые `projectId + projectPath + tabId`, поэтому работает между проектами и не зависит от текущего `activeProjectId`.

Пока родитель ждёт потомков, его собственный runtime может быть idle, но работа, которой он владеет, ещё не завершена. TabBar и project aggregate получают отдельный `inheritedBusy`: он сохраняет process strip на вкладке и проекте с настраиваемым цветом, но не подменяет runtime busy, не запускает Run After и не рисует background-work loader над History input. Цвет полосы обозначает наследованного владельца, а общий контрастный shimmer — продолжающуюся работу; блик того же RGB, что фон, формально анимируется, но визуально выглядит статичным.

## Проекция в Timeline

Сообщение оркестрации распознаётся не по редактируемой строке `[Оркестрация]`, а по app-owned semantic tag в `history_prompt_presentations`. Tag сохраняется только после post-Enter audit рядом с точной durable identity пользовательской записи; Claude/Codex JSONL остаётся неизменным. Тот же sidecar переносит tag в доказанный Codex child при Resume/Fork вместе с presentation metadata.

Последовательные Terminal MCP request/completion/failure turns образуют отдельную фиолетовую группу и ромб-маркер. Счётчик группы — отдельная цифра без `×`: при наличии Pencil/Search верхний и нижний углы распределяются заранее, поэтому значки не перекрываются. Свёрнутая группа агрегирует работу с документацией всех своих turns в общем Cmd-hover, раскрытая показывает её у конкретных turns. Клик по свёрнутой группе сначала раскрывает Timeline и сам список, затем дочерние строки используют обычную UUID-навигацию History; обратное сворачивание панели немедленно схлопывает группу, чтобы дети не оставались в узком rail рядом с числом. Ромб всегда строится из квадратной геометрии до поворота — общий child-marker `8×3` превращал его в диагональную черту. Это не группа встроенных Claude subagents: внешняя полноценная вкладка имеет durable `runId`, а встроенный Agent/Task остаётся отдельным типом Timeline. Миграция старых записей допускает exact-prefix только в одноразовом backfill; runtime никогда не классифицирует сообщение по тексту.
