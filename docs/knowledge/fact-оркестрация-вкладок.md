# Оркестрация AI-вкладок

## Зачем нужен отдельный контур

Оркестрация вкладок — продуктовый сценарий Project API, а не цикл чтения чужой истории. Он нужен для запросов, которые могут работать десятки минут и запускаться с другого компьютера, где у клиента нет локальных MCP-серверов. Поэтому HTTP-запрос подтверждает только принятие задачи и быстро завершается; ожидание ответа принадлежит сохранённому run и SSE.

Terminal/History scenario layer остаётся единственной точкой живого управления Claude/Codex. Оркестрация не пишет в PTY напрямую и не читает TUI-output: создание фоновой вкладки, readiness, send during streaming, resume и очередь проходят через те же сценарии, что Project API и History. `delegate_to_session` / `get_delegation_result` единого Terminal MCP — тонкие typed-wrapper'ы над этим API; history-tools не участвуют в штатном ожидании run.

## Контракт run

Каждый запуск связывает исходную и целевую вкладки вместе с их проектами. Новая target-вкладка всегда создаётся в фоне: запуск исполнителя не меняет активный проект или вкладку пользователя. Связанная работа в том же проекте по умолчанию создаётся visual-child исходной вкладки; независимый run использует явный `placement: root`. Межпроектный запуск без явно выбранного parent остаётся root, а повторный вызов существующего `targetTabId` никогда не переподчиняет уже организованную вкладку.

`202 Accepted` означает, что prompt принят общим send-сценарием, но не что ответ готов. Состояние дальше приходит как `orchestration-update` через SSE; статус и результат также адресуются стабильным `runId`. Клиент не держит исходный POST открытым и не опрашивает transcript. После completion-уведомления полный ответ читается одним `get_delegation_result` или HTTP GET.

Полный prompt и ответ не дублируются в orchestration-store. Store хранит размер prompt и fingerprint для сопоставления, а результат извлекается из канонического Claude/Codex transcript. Это одновременно не размножает историю, не раздувает служебный JSON и позволяет после restart доказать, какой именно turn принадлежал run.

Codex compact внутри долгого ответа не начинает новый продуктовый turn. History
может представить compact отдельной строкой, а дальнейшие assistant-блоки —
техническим продолжением без userUuid; result-reader использует чистую проекцию
того же реального пользовательского хода и возвращает блоки по обе стороны
compact. Следующее настоящее пользовательское сообщение остаётся жёсткой
границей и в чужой результат не попадает.

Для fresh Codex модель и effort принадлежат launch: новая вкладка получает их при старте, а первый send передаёт только prompt. Повторная попытка применить ту же пару вместе с `queue:true` уже после появления ready-composer корректно отклоняется idle-guard'ом и раньше оставляла target готовым, но без пользовательского сообщения (`codex_settings_change_requires_idle`). Для существующего idle target настройки можно применить перед send; busy target не должен маскировать смену настроек очередью.

## Авторитетный lifecycle

Готовность определяется структурными событиями агента: `task_started`/`task_complete`/`turn_aborted` для Codex и эквивалентным busy/done-контуром Claude. Стабильность текста, возврат prompt-глифа и terminal output не являются completion-proof.

`queue:true` означает только разрешение поставить сообщение за уже идущей работой. Это не доказательство, что предыдущий turn существует. Ожидание чужого completion включается только по реальному baseline `busy` или по сохранённому predecessor-run на том же target. Иначе собственный `task_complete` ошибочно поглощается как окончание несуществующей предыдущей задачи, а run навсегда остаётся `queued`.

У Codex post-Enter `user_message` audit может завершиться позже собственного `task_started`. Поэтому события до подтверждения доставки не объявляют run запущенным вслепую, а сразу после acceptance выполняется одна сверка transcript + live status. Она закрывает окно гонки; дальнейшее ожидание снова полностью event-driven. Это не polling.

Несколько run на одном target упорядочиваются predecessor-связью. Lifecycle применяется только к головному run; после его terminal-state следующий получает собственный busy→done. Один completion нельзя засчитать двум задачам.

Fresh Claude требует отдельной причинной границы: до первого prompt у вкладки ещё нет JSONL-пути и `sessionId`, хотя процесс и composer уже готовы. Непосредственно перед Enter main доказывает Claude PID под точным PTY, чтобы `UserPromptSubmit` привязал появившуюся запись к staged send. Только для этого unresolved-transcript случая допустимо сравнение timestamp записи с моментом отправки; ошибка чтения уже известного JSONL не превращается в такое доказательство. Иначе одно физическое уведомление отображается в History дважды: как временная строка handoff и как durable user-запись.

## Завершение и уведомление источника

После успешного completion сервер сначала сопоставляет result-turn, затем отправляет в исходную вкладку короткое служебное сообщение через общий History/send-сценарий. В сообщение входят `runId`, исполнитель и адрес результата, но не полный ответ. Источник делает один структурный GET и продолжает исходную задачу без ANSI/TUI-парсинга. Result вместе с текстом возвращает точные `targetTabId` и `targetProjectId`: если исполнитель создавался только для разового теста или исследования, источник после чтения результата закрывает именно эту вкладку через Terminal MCP; постоянные сессии остаются открытыми.

Служебное уведомление не владеет текстом, уже набранным пользователем в source-composer. Оно только передаёт намерение общему send-сценарию: `queue:true` разрешает дождаться занятого turn, но не разрешает склеить уведомление с чужим draft. Codex уже имеет read-only proof состояния composer и может остановиться на конфликте; для queued completion notification в Claude эквивалентная проверка native TUI draft пока не доказана. Поэтому source Claude с непустым TUI input остаётся известным незакрытым edge: нельзя обещать безопасную доставку или повторять уведомление вслепую, а завершённый result должен оставаться доступным по `runId`.

Уведомление — отдельный outcome. Run может быть успешно завершён, даже если source нельзя разбудить: например, fresh Claude был остановлен до первого materialized turn. Тогда сохраняется `notificationStatus: failed` с причиной `session_not_materialized`, а результат остаётся доступен по `runId`; ошибка уведомления не переписывает успешный target-result.

Если fresh source-процесс всё ещё жив и input-ready, completion notification может стать его первым materialized prompt. Это нормальный путь: уведомление отправляется один раз, создаёт первую durable user-запись и гасит временный History handoff. Остановленный fresh source без готового composer остаётся предыдущим failure-case и не получает искусственную историю.

Abort/interrupt target-turn переводит run в failure, а не в completed. Явная отмена run может дополнительно interrupt’ить target, но обычное завершение не останавливает runtime: вкладка остаётся пригодной для следующего сообщения.

## Persistence и восстановление

Run-метаданные пишутся атомарно вне renderer-state и переживают Electron restart. При старте активные записи сверяются с transcript и текущим состоянием вкладки: найденный matching turn восстанавливает `running` или `completed`, после чего недоставленное уведомление можно отправить заново. Renderer нужен для отображения и переходов, но не является владельцем lifecycle.

История ограничена по числу и возрасту завершённых записей; активные run не удаляются этим лимитом. Idempotent client-supplied `runId` защищает повтор POST после сетевой ошибки от создания второго исполнителя.

## UI в History

Верхняя поверхность рядом с `Run After` — live tracker: она показывает только активные run. Несколько одновременных вызовов объединяются в ограниченный по высоте прокручиваемый список; каждый ряд ведёт к связанной вкладке и раскрывает направление, проект и состояние.

Завершённые, ошибочные и отменённые run сразу исчезают из tracker и остаются в компактном окне `History`, открывающемся вплотную слева от своей кнопки. Окно не блокирует History/terminal и прокручивается внутри. Переход из обеих поверхностей использует сохранённые `projectId + projectPath + tabId`, поэтому работает между проектами и не зависит от текущего `activeProjectId`.
