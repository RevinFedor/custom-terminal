# Переключатели вкладок и проектов (Ctrl+Tab / Cmd+P / Ctrl+Q)

## Зачем

Вкладок в проекте десятки, а работа идёт между двумя-тремя последними, часто из разных проектов. Боковой список отсортирован вручную и не отвечает на вопрос «куда я только что смотрел». Переключатель — отдельная поверхность поверх всего, которая отвечает именно на него.

`Ctrl+Tab` — быстрый возврат по свежести (удержание Ctrl листает, отпускание подтверждает). `Cmd+P` (и равноправный синоним `Ctrl+P` — рука после `Ctrl+Tab` не должна менять модификатор) — тот же список, но с поиском: по названиям вкладок либо, по переключателю в самом поле, по тексту промптов (см. «Поиск по промптам»). Обе поверхности — один компонент и одна модель строк; расходиться им нельзя, иначе одна и та же вкладка окажется в разных местах списка в зависимости от хоткея.

**Shift после открытия меняет commit на «добавить/открыть в сфокусированном окне».** Выбранная/наведённая строка получает ту же плашку, что в боковом списке: `add`, если чипа здесь нет, `open`, если он уже лежит в целевой полосе, ничего, если вкладка уже показана. Shift+Enter, Shift+клик и отпускание Ctrl при взведённом Shift используют `addTabToSplitPaneStrip`/`addTabToCenterStrip`; без Shift остаётся обычная единая активация.

Shift, которым **открыли** первый `Ctrl+Shift+Tab`, принадлежит обратному направлению перебора и сам по себе add-режим не взводит. Альтернативное действие включается только новым нажатием Shift уже при открытой панели (или явным Shift-кликом по строке). Поэтому reverse cycling не меняет смысл на «перенести вкладку». `Cmd+P`/`Ctrl+P` также открываются без Shift; порядок жеста тот же: сначала панель, затем модификатор действия.

## `Ctrl+Tab` всегда глобальный и ведёт только к невидимому

Одна история на всё приложение, и список — только то, чего сейчас не видно (подробнее ниже, в разделе про видимые вкладки). Подтверждение строки идёт через единую точку активации: выбранная вкладка заменяет вкладку в панели, которая сейчас в фокусе. Правило сплита «вкладка уже видна → фокус прыгает в её панель» в этом жесте не срабатывает по построению — таких вкладок в списке нет; оно остаётся для остальных входов (клик в боковом списке, `Cmd+P`).

**Своя история у каждой панели была и удалена (2026-08-17).** `Ctrl+Tab` открывал список конкретной панели, окном на месте этой панели. Пользователь: *«тема максимально сейчас бесполезная… там просто сплошной набор файлов»*. Причина — порядок: пане-список, как и глобальный, отсортирован по свежести, а выбирает пользователь глазами по КАРТЕ (иерархия бокового меню, которую он сам расставил). Журнальный порядок годится для слепого шага назад, а не для выбора; для выбора есть сайдбар и `Cmd+P` (поиск по имени).

Вместе с пане-скоупом удалены: `paneSwitcherScope.mjs`, «владелец клавиатуры» (`keyboardOwnerGesture.mjs`, `workspaceOwnsKeyboard`), третье состояние рамки панели («активна, но клавиатура в интерфейсе»), подсветка кнопки `⌘P` в тулбаре и `forgetPaneTabVisit`. Рамка панели снова отвечает на один вопрос: белая 75% — фокус здесь, боковые линии 8% — остальные.

Пане-история как ДАННЫЕ осталась (`splitPanesModel.mjs::paneHistory`, поле `history` на панели): она питает шаг назад по среднему клику на любом показанном чипе и показывает только то, что реально можно вернуть — вкладка жива и не открыта прямо сейчас в другой панели (`restorablePaneHistory`). Это обязательно после `MOVE HERE`: вытесненная обычная вкладка уже не лежит вторым чипом, но должна вернуться при отмене жеста.

Ловушка, из-за которой эта история молча обнулялась бы: объект панели пересобирается заново при каждой активации, и всё, что не перенесли явно, теряется. Поэтому единственный способ поменять вкладку в панели — `paneWithHistoryFrom`, он же переносит историю; собирать `{projectId, tabId}` руками нельзя.

## Средний клик по строке = забыть запись

В глобальном `Ctrl+Tab`/`Cmd+P` средний клик по живой строке зеркалит Shift: **MOVE HERE**, то есть снимает вкладку со старого placement и заменяет показанную в текущем фокусном окне. Это не удаление из MRU и не закрытие tab record. Строка исчезнувшего файла остаётся неактивной целью: переносить нечего, а скрытое удаление истории из навигационного жеста больше не выполняется.

Удаление из глобального списка обязано чистить **обе половины**: и сам порядок, и долговременную отметку на вкладке. Порядок после перезапуска выводится из отметок, а сохранённый массив используется только для вкладок без отметки — почистив что-то одно, получили бы запись, возвращающуюся на следующем запуске.

## Порядок строк — глобальная свежесть, проекты только разделяют

Список строится из ОДНОГО плоского пула всех вкладок всех открытых проектов, отсортированного по общей свежести (последняя активация — первой). Заголовок проекта вставляется как разделитель ровно там, где сменился владелец очередной вкладки, поэтому один и тот же проект может появиться в списке несколько раз — это не дубль и не баг.

Ранняя версия группировала строго по проектам (все вкладки проекта подряд), и пользователь сформулировал претензию точно: стоя на втором проекте и нажав `Ctrl+Tab` один раз, он ожидал попасть на предыдущую вкладку — а попадал на соседнюю вкладку того же проекта, потому что группировка ставила её выше. Проекты в этом списке — оглавление, а не уровень навигации.

Заголовок проекта **не является целью выбора**: он не кликается, не подсвечивается при наведении, пропускается стрелками и `Ctrl+Tab`. Визуально он меньше и тусклее строк вкладок (иконка 12px, приглушённая), потому что повторяется в списке часто и не должен спорить с содержимым. Строки вкладок сдвинуты вправо на несколько пикселей — этого достаточно, чтобы читалась принадлежность, без рамок и фонов у заголовка.

## Свежесть следует за фокусом; видимость решает только, что предлагать

Один и тот же клик отвечает на ДВА разных вопроса, и попытка ответить на оба одним признаком дважды дала баг — в противоположные стороны:

1. **насколько свежа вкладка** — обновляется на КАЖДОЙ активации, без исключений;
2. **можно ли предлагать её как возврат** — только пока её не видно на экране.

Первая версия отвечала только на (2) и использовала это для обоих: клик по соседней панели переписывал историю, и `Ctrl+Tab` предлагал вкладку, на которую человек и так смотрит. Тогдашняя починка — «переход засчитывается, только если вкладки не было на экране» — вылечила это и породила зеркальный дефект.

**Симптом (пользователь, 2026-08-17):** *«перехожу на другую вкладку, нажимаю Ctrl+Tab, ожидая увидеть ту вкладку, которая была до этого, но она вообще на десятом месте»*. Причина: вкладка, лежащая в панели, могла обрабатываться часами без единой записи — она не «появлялась», она уже там была. Уход с экрана событием тоже не является (никто не активирует вкладку, чтобы её спрятать). Позиция замирала на моменте последнего появления, а каждая чужая активация толкала её на шаг вниз. Пользователь назвал механизм точно: *«вкладка отходит всё назад и назад»*.

Поэтому вопросы разведены. Свежесть пишется по ФОКУСУ — это и значит «я только что здесь работал». Видимость больше не участвует в записи вообще: она фильтрует только строки переключателя (`TabSwitcherOverlay::computeRowsFromStores`). Правила встречаются ровно один раз: в момент, когда вкладка уходит с экрана, она автоматически оказывается самой свежей из невидимых, то есть встаёт сразу под якорем — без специального правила «предыдущая обязана быть второй», и весь список ниже упорядочен реальной работой, а не тем, какую вкладку случайно подменили последней.

Соблазн починить это правилом «ставить предыдущую второй» — заплатка: второе место стало бы верным, а третье и десятое остались бы мусором, и через два переключения упираешься в то же самое на шаг дальше.

**Цена, которую пришлось оплатить:** писать стало каждое переключение фокуса, а каждая отметка стоит полной записи списка вкладок проекта. Отметка пропускается, когда вкладка **уже самая свежая** (относительный порядок не изменится), но обязательна, если у неё **нет отметки вовсе** — после перезапуска порядок выводится из отметок, а такую вкладку может ранжировать лишь сохранённый запасной список; пропустив её, оставили бы её без отметки навсегда, и на следующем запуске она провалилась бы под все отмеченные.

Второй эффект развода: у `addTabToSplit` больше нет собственной отметки. Она существовала, потому что активация после записи панели видела вкладку уже видимой и правило её отбрасывало; теперь видимость ничего не решает, и единая точка активации записывает всё сама.

**В `Ctrl+Tab` видимых вкладок нет вообще, кроме текущей, в `Cmd+P` есть все.** Это два разных вопроса на одном компоненте:

- `Ctrl+Tab` = «я здесь → верни то, чего я не вижу». Список строится БЕЗ вкладок, лежащих сейчас в окнах (в одиночном режиме — без вкладки центра). Вкладка возвращается в список ровно тогда, когда перестаёт быть показанной: её панель опустела, раскладка схлопнулась, её слот занят другой вкладкой. Пользователь: *«она уже у нас отображается на главном окне, она нахуй нужна… появляется только в том случае, если я её закрываю»*;

  **Чип считается «на экране» (2026-08-18).** Окно теперь держит полосу вкладок и показывает одну из них. Строго говоря, содержимое непоказанного чипа не видно — но вопрос переключателя другой: «оно уже здесь, передо мной». Чип — здесь: он в одном клике, в месте, куда человек смотрит, и он там потому, что человек сам его туда положил. Предложить его в `Ctrl+Tab` значило бы назвать одну вкладку дважды и отодвинуть вниз то, чего действительно нет на экране, — тот же дефект, ради которого написан весь этот раздел, этажом выше. Пользователь: *«если она отображается в окне как вкладка, она не попадает в Ctrl+Tab. В Ctrl+P попадает»*;
- `Cmd+P` = поиск: существующая вкладка обязана находиться по имени, что бы ни было на экране, иначе поиск врёт о содержимом.

### Первая строка — «ты здесь», подсветка на второй

Единственное исключение из фильтра — **вкладка, на которой пользователь стоит сейчас**: она закреплена первой строкой, а подсветка стартует со второй. Так читаются `Alt+Tab` и `Ctrl+Tab` в VS Code: сверху точка отсчёта, под ней — куда попадёшь, отпустив Ctrl.

Симптом без якоря (пользователь, 2026-08-17): *«у меня почему-то та вкладка, на которую я буду переходить, отображается на первом месте, а текущая вкладка не отображается»*. Список открывался сразу на цели, и первая строка читалась как «текущая», указывая при этом на другую вкладку — жест терял точку отсчёта.

Закрепление нельзя отдавать свежести. Фокус на вкладке, которая и так на экране, переходом не считается (см. правило выше), поэтому текущая вкладка часто НЕ является головой истории — сортировка поставила бы её в середину списка. Отсюда отдельный вход `pinnedFirstTabId` в сборке строк: ранг `-1`, выше любой позиции истории и независимо от того, есть ли вкладка в истории вообще.

Три инварианта якоря:
- **освобождение от фильтра и закрепление — одно решение** (`anchorTabId = hideOnScreen ? currentTabId : null`). Разведи их — и первая строка начнёт означать разное в зависимости от того, что сейчас на экране. Освобождение касается только фильтра «видно на экране»: дочерние вкладки суб-агентов строками переключателя не становятся никогда;
- **в поиске якоря нет.** Текущая вкладка, всплывшая над совпадением, читалась бы как результат поиска;
- **подсветка его пропускает** (`initialCtrlIndex` пропускает активную вкладку). Когда, кроме якоря, в списке никого — не выбирается НИЧЕГО (`-1`), а не якорь: повторная активация текущей вкладки не безобидна, она переключает вид проекта на терминал и тащит боковой список к этой строке.

Якорь не выглядит целью: слева серая полоса, текст приглушён, кольца выбора нет — кольцо принадлежит строке, на которой клавиатура, и два кольца в одном списке спрашивали бы «так что из этого я выбираю?». Кликнуть по нему можно, это просто «остаться здесь, закрыть панель».

Фильтр стоит на уровне СПИСКА, а не на предвыборе. Пробовали иначе — «предвыбор пропускает видимые, но строки остаются»: тогда шаг клавишей, обход по кругу и быстрый тап всё равно приводили на вкладку, которая уже перед глазами. Фильтруя список, все три пути согласованы по построению; якорь — единственное исключение, и он же единственная строка, которую подсветка обходит.

Что «видно» — тот же ответ, которым пользуется правило истории (`tabVisitHistoryRule::onScreenTabIds`); два определения разошлись бы, и список с историей начали бы спорить, какие вкладки считаются видимыми. Состав панелей и текущая вкладка входят в СОДЕРЖИМОЕ списка, поэтому оверлей подписан на оба строками-отпечатками (массив панелей и объект рабочей области — новая ссылка на каждую запись в стор).

Список в `Ctrl+Tab` теперь пуст только когда открытых вкладок нет совсем; «всё открытое уже на экране» — отдельная подпись ПОД якорем, а не вместо списка: строка, на которой стоит пользователь, должна остаться на экране, пока он читает, почему панель на ней и заканчивается.

**Цена, принятая сознательно:** перевести фокус в соседнюю панель с клавиатуры больше нечем (мышью — клик по панели). Вкладка соседней панели не является ответом на «верни то, чего не видно», и держать её в списке ради этого значило бы ломать основной смысл жеста ради побочного. Если понадобится — это отдельный хоткей «фокус на следующую панель», а не строка в этом списке.

Исключением был короткий список недавних у чипа панели (он отвечал не «куда перейти», а «что положить в эту панель», поэтому вкладки, уже лежащие в панелях, из него исключались) — **удалён 2026-08-17** вместе с самой кнопкой.

## Поле поиска задаёт ДВА вопроса, а не один с фильтром

Справа в поле ввода стоит переключатель на две позиции: **Вкладки** и **Итерации**. Это не фильтр результатов, а смена самого вопроса, поэтому он и стоит внутри поля, а не над списком — он меняет смысл того, что человек прямо сейчас печатает.

- **Вкладки** — как называется вкладка. Мгновенно, локально, по именам того, что открыто. Ничего не стоит.
- **Итерации** — что в этой вкладке обсуждалось. Смысловой поиск по сохранённым ходам сессий; одна строка результата — один ход, а не вкладка целиком.

Один поиск не может ответить на оба вопроса: имя вкладки не знает, о чём в ней говорили, а ход не знает, как назвали вкладку.

**По умолчанию всегда «Вкладки», режим не запоминается между открытиями.** Переключатель чаще всего открывают, чтобы просто перейти; застать его в медленном режиме дороже, чем один клик. Переключить можно мышью или клавишей `Tab` — набранная строка при этом сохраняется, её же обычно и надо переспросить у другого поиска. Переключение мышью идёт на `mousedown` с возвратом фокуса в поле: человек печатает, и уехавший на кнопку курсор — это потерянный темп.

## Поиск по итерациям: тот же индекс, но по всем открытым проектам

Запрос уходит в `tab-iteration-search:semantic` — **тот же канал**, которым ищут «Итерации» на домашней странице проекта. Второй индекс тех же данных разошёлся бы с первым в первый же месяц, и разница вылезла бы как «на главной находит, а в переключателе нет».

Отличие от домашней страницы одно и принципиальное: там ищут по закрытым вкладкам ОДНОГО проекта, а переключатель обязан отвечать по всем открытым сразу — он и существует, чтобы переносить между ними. Поэтому запрос уходит в каждый открытый проект, а ответы сливаются в один список. **Порядок задаёт только совпадение**: делить на «сначала мой проект» значило бы прятать более точный ответ соседа. При равном совпадении выше идёт более свежий разговор — две одинаково подходящие формулировки чаще всего одна и та же мысль, и нужна её последняя версия. Один недоступный проект не обнуляет ответ остальных.

**Задержка перед запросом (280 мс) — не оптимизация, а условие.** Каждый заход считает эмбеддинг запроса, то есть платный внешний вызов; поиск на каждую букву превратил бы одно слово в шесть вызовов. Ответ помечается своим запросом (`iterationAnsweredQuery`), потому что к моменту его прихода строка уже другая: без метки список молча показывал бы ответ на позавчерашний вопрос. Пока идёт новый поиск, а на экране ещё старые строки, это сказано вслух прямо над списком.

Пустой экран называет ПРИЧИНУ, а не одно «ничего не найдено»: идёт поиск, допишите запрос, ошибка, ничего не нашлось — четыре разных факта, и одна строка на все четыре заставила бы гадать, ждать или переформулировать.

**Переход по найденному ходу** — три шага: найти вкладку по id сессии среди открытых (открытая всегда выигрывает у записи в истории — восстанавливать то, что и так на экране, значило бы создать вторую копию), иначе поднять её из истории закрытых **без запуска агента** (человек шёл читать разговор, а не продолжать его), затем перейти на неё, открыть переписку и прокрутить на этот ход. Прокрутка идёт тем же механизмом, что переход из Timeline (`historyScrollToUuid`) — второй путь к тому же месту разошёлся бы с ним.

Строки найденных ходов живут в ОБЩЕМ списке рядом с обычными строками: стрелки, выбор и Enter обязаны работать одинаково, а два списка со своими индексами разошлись бы на первом же шаге. Выглядят они при этом иначе — главное в строке сам текст хода (две строки), а вкладка, проект и номер хода уходят вниз мелким, как адрес найденного: карточка отвечает «вот вкладка», а эта строка — «вот место в разговоре».

## Строка вкладки повторяет боковой список, а не изобретает свой вид

Каждая строка показывает ровно то же состояние, что вкладка в сайдбаре: вертикальную полосу процесса с той же анимацией, квадратный/круглый маркер статуса, фон цвета вкладки, фиолетовую подсветку файловых вкладок. Общий источник цветов и геометрии вынесен в `tabChrome.ts` и импортируется и сайдбаром, и переключателем — расхождение оформления читалось бы как «это другая вкладка».

## Отсутствующий файл виден и не выбирается

Файловая вкладка ссылается на путь на диске, который могли переместить, переименовать или удалить. Такая вкладка **не удаляется** — пользователь мог сам увести файл и вернуть его обратно, и молчаливое исчезновение вкладки уничтожило бы привязку к сессии. Вместо этого она помечается красной иконкой (в переключателе, в боковом списке и в истории закрытых вкладок) и становится непроходимой: `Ctrl+Tab` её перепрыгивает, наведение не выделяет, клик не срабатывает.

Проверка существования общая (`missingFileTracker.ts`) — один кэш с коротким TTL и защитой от параллельных запросов на весь UI. Иначе три поверхности с одинаковым вопросом «этот файл ещё есть?» дали бы три независимых ответа и разную окраску одной вкладки.

## Автопрокрутка бокового списка: активная строка стремится в СЕРЕДИНУ

После активации вкладки боковой список подводит её строку к середине окна (`tabListRevealScroll.mjs`). Не «прижать к краю»: из середины видно соседей сверху и снизу — окрестность вкладки, в которой человек работает, — а прижатая к краю строка показывает соседей только с одной стороны. Прокрутка мгновенная, без анимации; анимация здесь превращает быстрый `Ctrl+Tab`-перебор в укачивание.

Два ограничения, без которых «в середину» превращается в дёрганье:
- **у краёв списка середина недостижима, и добиваться её нельзя.** Первая вкладка не может встать по центру, не открыв пустоту над собой: значение зажимается в `[0, максимум прокрутки]`, список просто упирается в начало или конец. Пользователь: *«если нет возможности, то скролл просто в самый низ, лишний скролл делать не нужно»*;
- **строка, которую и так видно целиком, не двигается вообще.** Иначе клик по видимой вкладке центрировал бы список и уводил строки из-под курсора.

Правило одно на обе точки, которые двигают список (автопрокрутка при смене активной вкладки и явный запрос «покажи строку»): две копии арифметики разъехались бы — одна прижимала бы к краю, другая вела к середине. Максимум прокрутки считается из `scrollHeight`, поэтому его обязаны передавать оба вызова — забыв его, уедешь в пустоту под последней строкой.

Позиция строки меряется относительно самого скроллера, никогда через `offsetTop`: карточка лежит в своей `position:relative` обёртке, поэтому `offsetTop ≈ 0` у ВСЕХ строк — наивная проверка читает любую строку как «выше видимой области» и слетает в начало списка на каждом клике.

Прокрутка-к-строке конфликтует с восстановлением сохранённого положения списка (у каждого проекта своё, переживает перезапуск), и приоритет у неё: запрос на показ строки отменяет отложенное восстановление и сам записывает новое положение. Без этого после перехода в другой проект список сначала показывал нужную строку, а через кадр отматывался обратно на сохранённую позицию.

**Запрос на показ строки одноразовый — по номеру (`seq`).** Поле живёт в сторе и после обработки не исчезает, поэтому без счётчика «уже обработано» ВОЗВРАТ в тот же проект переигрывал старый запрос: отменял восстановление сохранённой позиции и утаскивал список к вкладке из прошлого визита. Симптом: «позиция скролла не сохраняется при переключении проектов» — хотя сохранена она была правильно. Счётчик модульный, а не в `useRef`: список размонтируется на походе в Dashboard, и ref, сброшенный в ноль, дал бы тот же переигранный запрос при каждом возврате. Номер помечается обработанным только тем экземпляром, у которого реально есть скроллер, — скрытые списки-владельцы меню его не «съедают».

## Хоткеи слушаются в capture-фазе и не доходят до PTY

`Ctrl+Tab`, `Cmd+P` и `Ctrl+P` перехватываются на уровне окна в capture-фазе и дополнительно глушатся в **обоих** обработчиках xterm — иначе `Ctrl+Tab` уйдёт в TUI агента как управляющая последовательность, а `Ctrl+P` в оболочке означает «предыдущая команда» и отредактирует строку ввода в момент открытия панели. Буква определяется по физической клавише (`e.code === 'KeyP'`), а не по символу: на кириллической раскладке `Cmd+P` иначе не сработает вообще. Поиск внутри `Cmd+P` дополнительно сопоставляет русскую и латинскую раскладки, чтобы `ghbdtn` находил «привет».

Быстрое нажатие-отпускание `Ctrl+Tab` может завершиться до первого рендера списка; в этом случае строки пересобираются синхронно из сторов, и переход всё равно выполняется — пользователь не должен видеть разницу между быстрым и медленным нажатием.

## Выбор строки переключает и проект

Подтверждение строки идёт через единую точку активации центра (`activateCenterTab`), а она двигает ОБА указателя: центр и боковое меню. Выбрал вкладку чужого проекта — слева его список. Подробнее — `fact-рабочая-область.md::Один указатель`. (До 2026-08-17 было наоборот: боковое меню оставалось на прежнем проекте.)

## Поиск по промптам («Итерации») — второй вопрос к тому же списку

В строке ввода `Cmd+P` стоит переключатель из двух режимов, и это два РАЗНЫХ вопроса, а не фильтр одного результата:

- **«Вкладки»** — как называется вкладка. Мгновенно, локально, по именам открытого.
- **«Итерации»** — что в этих вкладках ПИСАЛИ. Одна строка результата = один промпт.

Переключить можно клавишей `Tab` прямо во время набора: строка при этом сохраняется — тот же текст обычно и надо переспросить у другого поиска. Режим не запоминается между открытиями: переключатель чаще всего открывают, чтобы просто перейти, и застать его в чужом режиме дороже одного клика.

**Поиск буквальный, не смысловой.** Пользователь: *«просто ищите наиболее точное слово»*. Смысловой поиск в проекте уже есть — на домашней странице проекта (`fact-semantic-search.md`), он отвечает на другой вопрос («о чём был разговор») и стоит внешнего вызова на каждую букву. Ранжирования здесь нет намеренно: у буквального поиска нет сигнала релевантности, кроме числа совпадений, и притворяться, что он есть, значило бы переставлять строки по причине, которую нельзя объяснить.

Если точной фразы нет **ни в одной** вкладке — повтор по отдельным словам, но с требованием ВСЕХ слов сразу. Режим один на весь ответ и подписывается вслух («Точной фразы нет — показаны промпты, где встречаются все слова»): строки в нём не содержат введённой фразы, и без подписи это читается как сломанный поиск. Решать режим для каждого промпта отдельно нельзя — список смешал бы точные совпадения с приблизительными без пометки, и подпись врала бы про половину строк.

**Ищем только по ОТКРЫТЫМ вкладкам, и это про то, куда ведёт результат.** Строка перехода активирует вкладку и прокручивает её переписку к найденному промпту; закрытую вкладку пришлось бы сначала восстанавливать — это уже не переход, а действие, и оно не должно происходить от `Enter` в списке. Для архива закрытых есть Home.

**Группировка по вкладке — это и есть ответ.** «В какой моей вкладке я это писал» — вопрос, за которым сюда приходят. Плоский список из десяти промптов одной вкладки читался бы как десять разных мест, поэтому найденное собирается под заголовком вкладки (невыбираемый разделитель, как заголовок проекта), а строки промптов сдвинуты и связаны с ним вертикальной линией: через десять строк уже не видно, к чему относится то, что читаешь.

**Свёрнутая строка — ровно ТРИ строки текста: строка с совпадением и по одной вокруг.** Не «сколько символов влезет»: у кусков разной высоты список перестаёт читаться как список — глаз не находит, где кончается один результат и начинается следующий. Соседние строки нужны, потому что промпт — это разговор, и одна строка без окружения часто не говорит ничего. Одна строка длиной в абзац режется по символам вокруг совпадения, иначе «три строки» превращаются в три экрана переноса. Многоточий по краям нет: обрезка очевидна и так (кусок начинается посреди фразы), а два лишних значка в каждой строке длинного списка читаются как часть текста.

Окно берётся вокруг совпадения, а не от начала промпта: длинные промпты часто начинаются одинаковой преамбулой, и три строки от их начала во всех результатах выглядели бы одним и тем же текстом без искомого.

**Служебные строки промпта:** сверху — сколько совпадений внутри ЭТОГО промпта (место зарезервировано под три цифры, поэтому появление «Свернуть» рядом не двигает текст под ним; из промпта видно три строки, и «здесь этих слов двенадцать» — единственный способ узнать, что за окном их больше). Снизу — адрес: `#7/214`, номер со знаменателем. Номер без знаменателя ничего не говорит: седьмой из десяти и седьмой из трёхсот — разный масштаб. «Раскрыть полностью (N строк)» стоит сверху; у раскрытого «Свернуть» появляется и снизу — конец длинного текста далеко от его начала.

**Результаты приходят ПОТОКОМ: вкладка разобрана — вкладка показана.** Не «ждём общего конца, потом рисуем»: обход десятка вкладок занимает секунды, и всё это время экран был бы пустым. Ждать незачем — порядок групп задаёт свежесть вкладок, она известна заранее, и ни одна поздняя вкладка не может переставить уже показанные. Куски встают НА МЕСТО своей вкладки, а не в конец, иначе первый показанный ответ уезжал бы вниз каждый раз, когда доразобралась более свежая вкладка.

Цена решения — второй проход. Запасной режим («не нашлось фразой — ищем словами») можно объявить только когда точно известно, что фразы нет ни в одной вкладке, а в потоке этот момент наступает в самом конце. Поэтому второй проход помечен как ЗАМЕНА: клиент выбрасывает показанное и рисует новое. Смешать два режима в одном списке значило бы соврать про половину строк.

**Лоадер, счётчик и предупреждение о режиме живут НА разделительной линии** — абсолютом, посередине рамки, поверх границы (тот же приём, что у подписи состояния на рамке композера в переписке). Строкой в списке они стоили бы места дважды: занимали бы ряд и сдвигали весь список вниз при каждом появлении — а появляются они на каждый запрос. Место одно, и важнейшее вытесняет остальное: пока идёт обход — говорим об этом; закончили по словам — предупреждаем; иначе показываем, сколько найдено.

**Счётчик в строке ввода — `7/135`: номер выделенного из всех найденных**, как в любом поиске. Считается ОТ СПИСКА, а не отдельным счётчиком: второй счётчик разошёлся бы с выделением на первом же обновлении, и стрелки двигали бы одно, а число показывало другое. Поэтому наведение мышью меняет его так же, как стрелки, — это одно и то же выделение.

**Состояние поиска переживает закрытие панели.** Набрать запрос, дождаться обхода, раскрыть найденное, проскроллить — это работа, а панель закрывают по десять раз за сеанс (сходить в найденную вкладку и вернуться). Если каждое открытие начинается с чистого листа, поиском перестают пользоваться. Хранится: запрос, результаты, режим совпадения, раскрытые промпты, выбор проектов, выделенная строка (по uuid — список к возвращению может быть другим) и положение прокрутки. Хранится в МОДУЛЕ, а не в сторе: панель — единственный читатель, а каждая буква запроса в глобальном сторе была бы обновлением для всего приложения. Повторный вход с тем же вопросом (запрос + набор проектов) не гоняет обход заново. Режим (`Вкладки`/`Итерации`) при этом НЕ хранится — открытие почти всегда «просто перейти на вкладку», — но память при возврате во вкладку «Итерации» цела.

**Наведение мышью не прокручивает список.** Подводить строку к видимой области нужно, когда её выбрали стрелками: она может быть за краем. Но наведённая строка по определению уже под курсором, то есть на экране, и любая прокрутка здесь — движение списка под неподвижной мышью. Дальше хуже: список уехал → курсор оказался над другой строкой → она выделилась → список уехал снова. Это и читается как «раскрыл промпт, скроллю вниз, а меня возвращает обратно». Поэтому источник выбора запоминается, и прокрутка разрешена только клавиатуре.

**Выбор проектов — иконками, а не названиями.** Проектов шесть-семь, они постоянные, и человек узнаёт их по картинке быстрее, чем читает слово: те же иконки он видит в сайдбаре и титлбаре каждый день. Названия в ряд занимали всю строку и переносились на вторую — управление стоило больше места, чем результаты. Название остаётся в подсказке; без иконки проект показывается словом, иначе его не отличить от соседа. В заголовке найденной вкладки — та же иконка, а без неё значок папки.

**Считает совпадения ТОЛЬКО main** (`iteration-search-match.js`), и он же отдаёт готовые смещения — и для куска, и для полного текста. Renderer их только рисует. Два matcher'а разошлись бы в первом же особом случае: промпт «подошёл» по одному правилу, а подсветить по другому нечего — верное совпадение выглядит ложным. Промпты читаются тем же `_loadSessionTurns`, что Timeline и History: свой парсер разошёлся бы с ними по uuid, и переход «к найденному» приводил бы не туда.

**Номер хода (`#7`) считается по ВСЕМ промптам вкладки, а не по найденным** — иначе он меняется от запроса к запросу и перестаёт быть адресом.

**Где искать — отдельная строка под полем ввода.** Иконки открытых проектов слева, «Все» справа. Это не фильтр результатов: выбор меняет объём работы ещё ДО запроса. По умолчанию выбран проект, из которого позвали (чаще всего искомое писали здесь же), дальше набор принадлежит человеку. Пустой набор — законное состояние «нигде», а не «везде»: подмена меняла бы объём ответа сама собой, без действия человека, поэтому вместо пустого списка панель прямо говорит «Выберите хотя бы один проект».

Запрос отложен на ~200 мс и помечен своим текстом: каждый заход читает и разбирает файлы сессий всех выбранных вкладок, а между вкладками main отдаёт событийный цикл — иначе десяток крупных сессий сложился бы в одну длинную остановку интерфейса. Ответ приходит, когда строка уже другая, поэтому устаревший список подписывается («ниже — ответ на …»), а не молчит.

**Высота панели — доля экрана, а не пиксели.** Половина 4K-монитора больше, чем весь экран ноутбука; на ноутбуке та же половина не вмещает и трёх промптов, а беречь там нечего. Поэтому чем меньше экран, тем большую его долю занимает панель (`iterationPanelMaxHeight`). Ширина в этом режиме тоже больше обычной: строка результата — текст в несколько строк, а не имя вкладки.

Мелочи, которые ломаются молча: текст промпта выделяемый (найденное часто копируют, не уходя из списка), поэтому переход идёт по КЛИКУ с проверкой на активное выделение, а закрытие по фону требует, чтобы на фоне произошли и нажатие, и отпускание — выделение часто дотягивают за край панели. Раскрытые промпты помнятся по uuid, а не по номеру строки: список перестраивается на каждый ответ, и по индексу раскрытие «прыгнуло» бы на соседний промпт.

Связанные факты: `fact-tabs.md`, `fact-рабочая-область.md`, `fact-workspace.md`, `fact-semantic-search.md`, `fact-timeline.md`.


## `Ctrl+Q` — тот же жест, но по проектам

Отдельная панель (`ProjectSwitcherOverlay` + чистая модель `projectSwitcherModel.mjs`), намеренно ПРОЩЕ переключателя вкладок, и все различия — следствие одного факта: проектов шесть-семь, а не десятки вкладок.

- **поиска нет** — список целиком помещается на экран, фильтру нечего делать;
- **скролла нет** — по той же причине;
- **ничего не прячется.** `Ctrl+Tab` убирает видимое, потому что список «всех вкладок» был бы бесполезен; здесь «все» и есть полезный список;
- **Home — такая же строка.** Это место, куда можно попасть из титлбара, значит, оно обязано быть и здесь: переключатель, молча пропускающий одно из мест, где ты бываешь, — карта с дырой. Inbox отдельного случая не требует: это обычный открытый проект, он приходит общим списком.

Что унаследовано от переключателя вкладок, потому что это свойства ЖЕСТА, а не того, что переключают: первая строка — где ты сейчас, подсветка стартует со второй, панель висит под верхней полосой, быстрый тап (Ctrl отпущен до первого кадра) всё равно приводит на предыдущее место. Порядок — по свежести (`projectHistory`), как у вкладок: это слепой шаг назад, а не место для поиска глазами; для поиска есть сайдбар и титлбар.

**`Ctrl+Q` обязателен к перехвату в xterm — оба обработчика.** Это XOFF: утёкший в терминал, он замораживает вывод до `Ctrl+S`. Пользователь увидел бы зависшее приложение без единой видимой причины. Клавиша читается через `event.code`, поэтому на русской раскладке (`Ctrl+Й`) жест работает так же.

Подтверждение строки, на которой ты уже стоишь, — no-op по построению: `showWorkspace` перетасовывает историю проектов, и «переход в себя» сдвинул бы порядок без всякого перехода.
