# Fix: Multi-instance MCP Isolation (PID-based Ports)

## Проблема
Изначально приложение использовало единый файл `~/.noted-terminal/mcp-port` для передачи номера порта HTTP-сервера MCP-клиентам. Это создавало критические гонки (race conditions) при параллельном запуске нескольких экземпляров приложения (например, dev-версия и prod-версия, или два окна разработки).

### Симптомы
- MCP-вызов из AI-агента в одном окне "приземляется" в main-процессе другого окна (например, `terminal` MCP перезапускает вкладку не в том instance).
- Ошибка "MCP port file not found", если один экземпляр закрылся и удалил общий файл, пока второй ещё работает.
- Непредсказуемое поведение кнопок статуса и вставки результатов.

## Root Cause: Race Condition
1. **`startMcpHttpServer()`** → записывал порт в фиксированный путь. Последний запустившийся инстанс "побеждал", перезаписывая порт предшественника.
2. **`stopMcpHttpServer()`** → вызывал `unlinkSync` на общем файле при выходе. Это лишало связи все остальные работающие инстансы.

## Решение: PID-based Port Files
Система переведена на использование именных файлов портов, привязанных к PID главного процесса Electron.

1. **Запись:** Каждый инстанс пишет в `~/.noted-terminal/mcp-port-<process.pid>`.
2. **Очистка (Cleanup):** При старте приложение сканирует папку портов и удаляет файлы, чьи PID больше не существуют в системе (проверка через `process.kill(pid, 0)`).
3. **Удаление:** При нормальном выходе удаляется только файл, соответствующий текущему PID.

## Алгоритм обнаружения (Process Tree Walking)
Поскольку Terminal MCP запускается самим AI-CLI (Claude / Gemini / Codex, который запущен в шелле, который запущен в `node-pty`), он не знает PID "своего" Electron напрямую.

Для поиска правильного порта реализован **Process Tree Walking**:
1. **Цепочка:** `MCP-сервер (node)` → `AI-CLI (Claude/Gemini/Codex)` → `zsh/bash` → `Electron (node-pty)`.
2. **Strategy 1 (Exact Match):** Сервер берет свой PPID (AI-CLI) и поднимается вверх по дереву процессов (до 4 уровней). Для каждого родительского PID проверяется наличие файла `mcp-port-<PID>`. Это гарантирует точное попадание в тот инстанс Electron, который породил текущую сессию AI-CLI.
3. **Strategy 2 (Liveness Fallback):** Если дерево процессов недоступно, сканируются все `mcp-port-*` файлы. Выбирается самый свежий по `mtime`, чей процесс еще жив.
4. **Strategy 3 (Backward Compat):** Попытка прочитать старый `mcp-port` (для плавного перехода).

## Dashboard ownership поверх port-файлов
Те же PID-based port files являются source of truth не только для MCP routing, но и для destructive UI в Dashboard. Если dev и production custom-terminal работают параллельно, проверка «процесс не принадлежит текущему renderer tabId» недостаточна: такой процесс может принадлежать соседнему живому instance и должен быть защищён.

Dashboard поэтому строит карту владельцев из живых `mcp-port-<pid>` файлов, валидирует main PID и поднимается по parent chain Claude/Gemini/Codex/MCP процесса. Термин `external` в UI значит «не принадлежит ни одному живому custom-terminal instance». Для batch kill это критично: кнопка `external only` не должна закрывать вкладки dev из production и вкладки production из dev. Симптом старой логики — пользователь нажимает крестик в одном окне, а пропадают AI-процессы, открытые в другом окне.

## Invisible Intent: Почему не `execSync` в Main
Согласно правилам `CLAUDE.md`, Main-процесс не должен блокироваться на системных вызовах. Поэтому тяжёлая работа по обходу дерева процессов (`ps -p PID -o ppid=`) вынесена в Terminal MCP, который является независимым процессом Node.js.

## Связанные файлы
- `src/main/main.js` — реализация записи и очистки портов (mcpHttpServer).
- `mcp/terminal-server.mjs` и установленная копия `~/.claude/mcp/terminal-server.mjs` — клиент, реализующий алгоритм поиска порта.
- [`fact-terminal-mcp.md`](fact-terminal-mcp.md) — единая публичная MCP-поверхность поверх раздельных live/history HTTP boundaries.

## External install: свежий Voice dev не является production owner

2026-09-08 реальный `build_install_noted_terminal` выбрал private Voice dev
17988 по самому свежему discovery-файлу, хотя installed Voice работал на7888.
Job был отменён владельцем до build/quit (`pid:null`, `installResult:null`);
production не заменялся. В том же каталоге оказались старые voice-файлы с
уже переиспользованными PID браузера/Finder: `kill(pid,0)` сам по себе не
доказывает ни приложение, ни владение портом.

Для destructive install MCP теперь отдельно определяет одного installed
Voice owner: точный executable `/Applications/Voice Record.app/Contents/MacOS/Voice Record`
и тот же PID, реально слушающий advertised TCP port. Проверки `ps/lsof`
асинхронные; свежесть файла не заменяет identity. Dev/stale/ambiguous кандидат
не становится fallback. После отправленного POST HTTP/network failure не
разрешает отправить тот же install другому экземпляру — сначала читается job
выбранного владельца. Остальной project/tab/dev-routing этим не меняется.

Регрессии исполняют фактический MCP handler: newer dev, reused PID, wrong
listener, ambiguity и ошибка после dispatch. До ремонта5FAIL, после5PASS;
live read-only selection выбрала PID41378/port7888 при одновременно живых dev.
Уже запущенный stdio MCP остаётся старым до reconnect/restart; для первого
deploy используется новый source MCP process либо явно проверенный внешний
Voice API, но не локальный `build:install` из погибающей host-вкладки.

## Global MCP hub: временный E2E-main не становится владельцем

Отдельная гонка проявилась на фиксированном порту `53133`: после shutdown
production-хаба няни нескольких одновременно живых Noted Terminal main'ов
пытались занять порт. Победил fixture из
`/private/tmp/noted-authenticated-fixture-*`, поэтому все настоящие AI-вкладки
получили глобальный хаб со старым кодом тестового снимка. Симптом обманчив:
шесть процессов зелёные, но `sc-desktop tools/list` висит и новые Codex-сессии
не видят ни одного `yougile_*` инструмента.

Граница владельца теперь определяется до spawn: экземпляр с
`NOTED_E2E_TEST=true` вправе подключиться к уже живому глобальному хабу, но при
пустом порте использует per-session stdio fallback и не запускает свою няню.
Обычные production/dev main сохраняют право поднять хаб. Это не изоляция данных
по PID, как у instance-local Project API выше: порт намеренно один для всех,
поэтому исправляется именно право владения, а не созданием шести новых флотов.

Deploy-граница расследования 14.09.2026: канонический живой хаб вручную заменён
на процесс из актуального repo source и уже использует recovery. Полный
`build:install` Noted Terminal не запускался, потому что рабочее дерево содержит
параллельные незавершённые изменения; уже запущенные production/E2E main'ы до
следующей штатной сборки всё ещё имеют старую nanny-логику. Пока новый detached
хаб жив, они только усыновляют его и не мешают; после следующего обычного
install запрет E2E-владения станет постоянным и для будущих запусков приложения.

19.09 добавлена вторая граница гонки: reaping выполняет только выигравший bind
хаб. Два запуска приложения могут оба увидеть пустой порт; проигравший теперь
получает EADDRINUSE до любых действий с детьми. Одновременно исправлено принятие
живого, но полностью неработоспособного legacy-хаба с `spawn node ENOENT` после
переоткрытия. Это другой дефект — окружение GUI-запуска, не владельцы вкладок;
подтверждение и восстановление описаны в [fact-mcp-hub.md](fact-mcp-hub.md).
