# Fix: привязка живой Codex-сессии

Этот шрам объединяет один пользовательский класс симптомов: после `Start`/`Continue` Codex уже работает, но loader исчезает и возвращается; Copy ID, Timeline или History показывают старую сессию; после перезапуска вкладка восстанавливает не тот разговор; готовый терминал через несколько секунд получает ошибку запуска; нажатие Enter доходит до Codex только через 6–15 секунд.

## Ошибочное предположение

Система считала одним значением три разных факта: какую сессию пользователь попросил продолжить, какая сессия сохранена у остановленной вкладки и какой rollout прямо сейчас меняет живой процесс. Обычно эти ID совпадают, поэтому ошибка долго выглядела как набор независимых багов loader, Resume, базы и Timeline. Codex 0.145 нарушил скрытое предположение явно: `resume A` может продолжить писать в A, а может создать связанную дочернюю сессию B.

Аргумент Resume доказывает только намерение. Запись в SQLite доказывает, куда можно вернуться после остановки. Live-действиям — Copy, Fork, Rewind, Timeline и внешнему API — нужен текущий writer, то есть сессия, rollout которой реально открыт работающим Codex на запись. Папка проекта, время изменения файла, старый ID в интерфейсе и готовый composer по отдельности writer не доказывают.

## Как причина была доказана

22 июля 2026 года вкладка продолжала source `019f3d1a…`, а новый живой ход записывался в child `019f8a92…`. Терминал показывал работающий Codex, но интерфейс и сохранённая вкладка продолжали смотреть на source. Это объяснило одновременно исчезающий loader и восстановление старой сессии после рестарта.

В ночь на 23 июля вкладка `tab-1871` уже имела готовый composer, но оставалась в provisional-состоянии без доказанного writer. Чтения runtime-состояния занимали 3–20 секунд и сериализовались с наблюдением процесса. Точный Enter этой вкладки не был залогирован, поэтому для него вывод остаётся корреляцией. Тот же механизм прямо доказан на соседней вкладке `tab-1800`: ручной Enter ждал 15.559 секунды до физической записи в PTY, а rollout `user_message` появился через 28 мс после записи. Значит, xterm и Codex были быстрыми; задержка возникла в нашем наблюдении до отправки.

Отдельный SQL-аудит production-БД нашёл одинаковый `tab_id` в двух разных проектах. Это доказало, что point-read/write только по ID вкладки может изменить обе строки или прочитать чужую. Совпадающее имя вкладки не было причиной: ошибочным было предположение о глобальной уникальности ID.

## Принятая модель

Живой writer принимается основной частью приложения только после свежей связи «процесс → открытый writable rollout → root user-TUI metadata». Проверяются все потомки Codex; subagent и `codex_exec` исключаются по metadata; два корневых writer дают неоднозначность; ошибка хотя бы одной части проверки даёт `unknown`, а не «процесса нет» или выбор самого свежего файла.

До этого proof Resume source остаётся provisional и не выходит наружу как текущая live-сессия. Чистый composer при этом завершает startup-loader и разрешает обычный ручной ввод: готовность терминала и доказательство writer — разные оси. Copy/Fork/Rewind и другие identity-зависимые действия продолжают ждать writer.

Ручной Enter не ждёт process/status/session-проверок: до физической записи допустима только локальная сериализация байтов одного PTY, а наблюдение writer запускается уже после неё. Автоматическая отправка имеет отдельный контракт: до paste она доказывает отсутствие чужого draft, затем пишет paste+Enter одним упорядоченным потоком и подтверждает доставку только по rollout `user_message`.

После writer proof основная часть приложения сохраняет новый ID точечно, а общий renderer-save не имеет права вернуть старый source поверх него. При закрытии сначала выбирается writer, затем сохранённая project-scoped сессия; входящий ID из интерфейса не является fallback. Loader стал компактной неблокирующей плашкой: он сообщает о lifecycle, но не закрывает терминал overlay'ем.

## Что не сработало и почему

- `mtime + cwd` выбирают похожий файл, но не владельца: соседний Codex или subagent может писать в той же папке позже.
- Немедленно сохранить аргумент `resume A` значит превратить намерение в доказательство и потерять handoff A→B.
- Брать fallback из renderer после authoritative `NULL` в main значит воскресить уже отвергнутый старый ID.
- Читать status, busy, readiness и session ID отдельными запросами значит склеить разные поколения состояния.
- Ждать дорогую проверку writer перед физическим Enter значит делать read-only наблюдение частью критического пути пользовательского ввода.
- Пятисекундная проверка процесса после записи launch-команды принимала ещё не обнаруженный процесс за провал запуска. Поэтому уже готовый Codex мог получить красную ошибку; ранний снимок процесса не является отрицательным подтверждением запуска.

## Статус аудита на 23 июля 2026

Причина классифицирована как `architecture issue`: система смешивала намерение Resume, сохранённую привязку, живого writer и ранний process-snapshot. Доказанные пути приведены к одному контракту: lifecycle/identity читаются одним main-owned snapshot; ручной Enter вынесен из read-only проверок; launch сначала публикуется как pending и завершается реальными событиями; `tab_id` стал глобально уникальным с детерминированной миграцией дублей; writer сохраняется точечно; межпроектный перенос атомарно меняет SQLite- и PTY-владельца; Close архивирует до kill, а Restore удаляет history-row только после строгого save ACK.

Остающийся process-discovery/reconciliation fallback периодически сканирует дерево процессов до появления первого rollout. На dev он занимал десятки миллисекунд, но ручной Enter при этом дошёл до PTY за 0,3 мс. Это отдельный статус `risk needs logs`: fallback больше не стоит перед вводом, а убирать его без доказательства нельзя — он страхует пропущенные filesystem-события.

После ремонта три ранее повреждённые production-привязки восстановлены через stopped-session compare-and-set и проверены одновременно в renderer и SQLite: `portfolio → 019f8a92…`, `sidebar → 019f8aa7…`, `реализация drag-and-drop… → 71044c52…`.
