# Факт: Codex CLI в Noted Terminal

Codex поддержан как третий PTY-agent рядом с Claude и Gemini. Это не SDK-интеграция: приложение запускает реальный `codex` в терминале, читает его JSONL из `~/.codex/sessions/`, а UI строит Timeline/History поверх этого файла. Главные пользовательские симптомы этой подсистемы: Codex запустился, но справа нет Timeline; кнопка копирования session id пуста; после Stop нет Continue; Codex-F стартует правильную сессию, но вкладка не подхватывает новый id; смена модели вводит `/model`, потом уходит в новую строку или показывает ошибку; loader правого кластера остаётся активным после неудачного picker-flow; `⎘ prompt` / `+ clear` открывает внешний редактор вместо копирования текущего composer'а.

Глобальные подключённые аккаунты в usage-popover не являются привязкой Codex-вкладок и не меняют launch-контракт ниже. Обычный запуск продолжает использовать основной `~/.codex`; дополнительные изолированные авторизации нужны для независимого чтения лимитов и управляются отдельно. Полный контракт — [`fact-claude-usage-chip.md`](fact-claude-usage-chip.md) секция «Подключённые профили Codex».

Сводный шрам про ложную привязку, production-доказательства и принятый lifecycle-контракт: [`fix-codex-привязка-сессии.md`](fix-codex-привязка-сессии.md).

## Источник session id

Авторитетный session id Codex берётся не из PTY-вывода, а из первой записи `session_meta.payload.id` в rollout JSONL. Файлы лежат по датам: `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`. Парсер обязан игнорировать битую последнюю строку: Codex пишет append-only JSONL во время работы, и в момент чтения хвост может быть неполным.

Новая Codex-вкладка больше не живёт без session id до первого prompt. Main
атомарно создаёт metadata-only rollout с одним `session_meta`, сразу закрепляет
его UUID за вкладкой и запускает обычный `codex resume <UUID>`. Реальный Codex
0.147 принимает такой файл без User-записи и без предварительной регистрации.
Model/effort остаются launch intent и подтверждаются готовым TUI, а не самим
фактом записи metadata. Процессная активность по-прежнему определяется
OSC/process-tree proof и не выводится из UUID.

History-режим «записать без ответа» использует тот же нативный rollout, без
app-server: после доказанного Stop и проверки revision одним append добавляются
`thread_settings_applied`, Responses `response_item(role=user)` и canonical
`event_msg.user_message`. Это model-visible контекст без `turn/start`; затем тот
же UUID открывается через Resume. Обычный Enter остаётся PTY-доставкой с
post-Enter rollout-аудитом.

Поиск сессии среди кандидатов не имеет права запускать full parser. Discovery читает ограниченный head до первой non-metadata записи (hard ceiling 512 KiB / 32 records) и не кладёт эти records в full-history cache. Шрам: до разделения discovery и parsing один boot разбирал 1.3–1.75 GB посторонних rollout-файлов лишь ради проверки `session_meta`. Exact filename suffix остаётся быстрым путём, content scan — bounded fallback. Ресурсный контракт: [`fact-transcript-сервис.md`](fact-transcript-сервис.md).

Аргумент `codex resume <sourceId>` задаёт источник истории, но не доказывает, что запущенный Codex пишет в rollout с тем же id. Codex 0.145 реально встречается в двух режимах: либо дописывает source-файл на месте, либо создаёт child rollout с новым `session_meta.payload.id` и `forked_from_id=<sourceId>`. Прод-симптом второго варианта: Codex TUI показывает `Working`, а фиолетовый loader исчезает, context и Timeline/History остаются на source-файле. 2026-07-22 source `019f3d1a…` был так принят за writer, хотя живой ход писался в child `019f8a92…`.

Поэтому resume использует двойное наблюдение: exact watcher source-файла от его текущего EOF и строгий discovery child-файла по metadata-ссылке. Новые байты source запускают проверку «этот PTY-процесс действительно держит rollout открытым на запись»; сам `task_started` без process-to-file proof ещё не даёт ownership. До proof source-дельты не публикуются. Для append-in-place все удержанные дельты затем replay'ятся до точного byte offset и дают один итоговый lifecycle-edge; для child watcher сначала переходит на его живую границу, затем атомарно меняет и сохраняет tab session id. В обоих путях handoff не публикует промежуточный `busy=false`. Renderer при mount/reload дополнительно запрашивает текущее turn-state, потому что IPC edge мог произойти до подписки UI.

У одной живой вкладки поэтому существуют разные роли идентификатора. `resume source` — намерение запуска; `saved session` в SQLite — durable цель остановленной вкладки; `read identity` — единственный ID, который сейчас безопасно читать/копировать; `active writer` — rollout, который текущий Codex-процесс реально держит открытым на запись. Только writer разрешает Fork/Rewind/Edit/Delete и заменяет durable binding. Read identity может быть stopped history, proven writer либо exact idle Resume-source: для последнего main одновременно сверяет persisted source, exclusive Resume lease, tab, terminal object, run, lifecycle/launch generation, source watcher и process-open rollout. Ни одно сохранённое поле renderer само этот verdict не выводит.

Готовый composer во время resume ещё не превращает source в writer, но завершает startup-loader и разрешает обычный ручной ввод. До первого submit обе copy-поверхности могут использовать exact idle read identity, не меняя writer-state. Перед первыми paste/Enter main ставит отдельный launch-scoped барьер read identity; неотправленная попытка снимает его, но после записанного Enter он переживает TTL временного prompt-сигнала и остаётся до causal source-vs-child resolution либо смены lifecycle. После durable adoption read identity становится точным writer child либо подтверждённым source-in-place. `inputReady`, read identity и `writerConfirmed` — независимые оси: mutation/API-команды всё ещё ждут writer, даже когда Copy уже безопасен.

Ручной Enter и автоматическая отправка используют общий локальный порядок PTY-байтов, но не общий status-preflight. Ручной Enter записывается сразу и запускает наблюдение writer после write. Автоматический путь до paste отдельно защищается от чужого draft, затем пишет paste+Enter без промежуточного render-ACK и ждёт rollout `user_message`; это не превращает ручной жест в «одно launch-scoped действие» и не ставит process/session lookup перед клавишей.

Standalone slash-команды Codex (`/status`, `/compact`, `/fast` и другие однострочные команды без attachments/chips) не являются conversation prompt: Codex может выполнить их, не записав `event_msg.user_message`. History поэтому отправляет их через отдельную TUI-транзакцию, которая сначала видит полную команду в текущем composer-фрейме, затем пишет Enter и помечает локальную строку `SENT` без обычного user-message audit. Во время активного ответа тот же History-путь может положить команду в нативную очередь; control-bar slash без queue остаётся запрещён, кроме собственного `/fast`-контракта. Многострочный текст или slash с вложениями остаётся обычным prompt и обязан получить transcript proof. `/compact` после submit дополнительно подтверждает operational lifecycle через `task_started` и terminal compact evidence; служебный `Conversation compacted` не является user-message carrier.

Programmatic `/compact` регистрирует exact pending operation до первой PTY
записи, чтобы `task_started` уже имел владельца. Эта собственная reservation не
является `turnBusy` для её же write-guard; игнорируется только совпадающий
`operationId`. Другой compact, настоящий turn, prompt audit или activity
interval остаются блокерами. Иначе операция сначала проходит `busy=false`,
сама создаёт pending и через миллисекунды отказывает себе `codex_turn_busy`.

Child rollout может скопировать сотни мегабайт source-истории и переписать её внешние timestamps так, будто все строки созданы сейчас. Поэтому `mtime`, внешний timestamp и последние 8 MiB не доказывают live-turn. Граница ищется по внутреннему `payload.started_at` относительно launch-time и хранится как физический byte offset.

Два одновременных `codex-c` одного source теперь имеют явную single-owner policy: первый запуск резервирует source до lifecycle-cleanup, второй получает структурированный отказ `codex_resume_source_in_use` и не пишет команду в PTY. Резервирование привязано к поколению запуска, поэтому опоздавший cleanup старой попытки не освобождает нового владельца; после writer proof принятие rollout дополнительно сериализовано, чтобы два таба не прошли проверку владельца одновременно. `codex-f` намеренно не занимает этот lease: fork создаёт независимый child и не должен блокироваться обычным Resume источника. Без этого контракта общий source JSONL не способен доказать, какой из двух PTY дописал его на месте.

Для свежего `codex` `mtime` и cwd разрешены только как bounded discovery кандидатов до появления process-to-file proof. Они не становятся live identity: финальный writer определяется по writable rollout, реально открытому потомком текущего PTY. Fresh-старт принимает только root/user TUI session: `thread_source` не `subagent`, нет `parent_thread_id` / `source.subagent`, и это не `codex_exec`. Exact cwd остаётся приоритетом среди кандидатов, но если совпадения нет, допускается related-cwd fallback: `session_meta.cwd` и launch cwd могут быть родителем/потомком друг друга. Реальный симптом: пользователь в табе проекта `uav` сделал `cd ..`, нажал Codex, отправил prompt; rollout записался с `cwd=/agrotech`, а UI искал `/agrotech/uav`, поэтому Timeline/copy-id оставались пустыми при живом Codex. Related fallback применяется только когда нет exact/source match и путь находится в той же filesystem-ветке; без writer proof найденный кандидат остаётся provisional.

Прод-шрам 2026-06-25: свежая вкладка `tab-1453` запустила обычный Codex и ждала первую root-сессию, но параллельный родительский Codex создал subagent rollout в том же `/custom-terminal`. Старый watcher выбрал более свежий subagent-файл по `mtime` + exact cwd, вкладка получила чужой `codexSessionId`, а loader отражал работу дочерней задачи, хотя пользователь в эту вкладку prompt не отправлял. Правильная модель — не «последний файл в cwd», а «последний файл нужного launch-типа».

Для `codex-f` cwd-фильтр тоже недостаточен: Codex может спросить «использовать текущую директорию или директорию исходной сессии», и если юзер выбирает директорию исходника, новый файл получает cwd исходного проекта, а вкладка была создана в другом. Поэтому watcher для fork принимает только файл, который реально ссылается на исходный session id (`forked_from_id` или дополнительный `session_meta` с source id); сам исходный id при этом надо пропустить, чтобы не привязать вкладку к старой сессии. Cwd без source-match для fork больше не является достаточным доказательством.

## Запуск и shell boundary

Команда запуска внутри приложения строится как `command codex --no-alt-screen --dangerously-bypass-approvals-and-sandbox ...`, а не просто `codex`. Это намеренная граница с пользовательским zsh: если в `~/.zshrc` уже есть функция `codex() { command codex --dangerously-bypass-approvals-and-sandbox "$@"; }`, прямой вызов `codex --dangerously-bypass-approvals-and-sandbox` даст ошибку Codex про дублирующийся флаг. `command codex` обходит shell-function/alias и делает приложение владельцем полного набора аргументов.

Стартовые параметры модели и effort можно передавать сразу: `--model <id>` и `-c 'model_reasoning_effort="<effort>"'`. Это отличается от Claude: у Codex нет отдельного Think-toggle, а reasoning effort меняется через тот же `/model` flow, что и модель.

Стартовые параметры Codex двухслойные. StatusBar хранит app-level defaults (`defaultCodexModel/defaultCodexEffort`); `none` означает «не добавлять CLI override, пусть Codex читает `~/.codex/config.toml`». На fresh-tab ControlBar может хранить per-tab `codexModel/codexEffort`, и tab-scoped значения выигрывают над StatusBar. Если итоговые значения не `none`, fresh `codex` получает `--model` и `-c 'model_reasoning_effort="..."'`.

Fresh и restore/fork нельзя склеивать. Обычный `codex` действительно потребляет выбранную tab/global пару и только после принятого запуска сохраняет её как fallback вкладки. `codex-c` и `codex-f` обязаны восстановить точную пару из source rollout; renderer launch payload не сохраняется как будто он уже стал состоянием нового writer. Иначе между кликом и writer proof UI показывает чужую пару, а crash в этом окне делает ложь durable. Общий launch helper всё ещё обязателен для всех путей, но main различает fresh defaults и source settings; AutoResume/Resume All/Continue/Fork не повышают локальный UI-кэш до истины.

Явная полная пара, выбранная пользователем на **остановленной** Codex-вкладке,
— отдельное исключение для следующего Resume. Она сохраняется без owner старого
writer, передаётся как `next-launch` intent и один раз перекрывает source-rollout
settings. Это ещё не proof: input остаётся закрыт, пока current composer footer
не подтвердит точные model+effort. Несовпадение/нечитаемый footer переводит
startup в явную ошибку; `Ultra` исключён, потому что он conversation-only.

Launch cwd для ControlBar — это `tab.cwd`, а не только `projectPath`. `projectPath` описывает корень workspace, но пользовательский shell может уйти `cd ..` / `cd subdir`, а Terminal уже обновляет текущий cwd через OSC 7 в Tab-записи. Если Start/Continue Codex из ControlBar снова передаёт project root, watcher и rollout расходятся ровно в момент, когда пользователь думает что запускает из текущего терминального контекста. Fallback в watcher страхует parent/child drift, но entrypoint всё равно обязан передавать самый свежий tab cwd.

Все app-controlled Codex launches передают этот cwd не только как shell working directory, но и явно через `codex -C <cwd>`. Это важно для restore/continue: если Codex показывает chooser между session directory и current directory, текущий рабочий root уже закреплён командой запуска, а не угадывается по shell. ProjectHome использует это как деградацию для удалённых папок: Codex history entry с отсутствующим `cwd` открывается в ближайшем существующем родителе и показывает toast, тогда как Claude/обычный terminal по-прежнему падают с `working_directory_missing`.

### Патченный бинарник Codex — это пара, а не один файл

Noted Terminal подставляет Codex-вкладкам собственную сборку CLI из
`~/.noted-terminal/bin/codex` (через `NOTED_CODEX_BIN_DIR` + префикс PATH,
восстанавливаемый в shell integration). Начиная с Codex 0.147 этого файла
недостаточно: CLI запускает вспомогательный процесс `codex-code-mode-host`,
который ищет **рядом с собой** — по пути собственного исполняемого файла
(`InstallContext::code_mode_host_program_from_exe`), а не по PATH. Наш bin —
голая папка без `codex-package.json`/`codex-resources`, поэтому «соседа» там не
окажется, если его туда явно не положить.

Отсюда невидимая ловушка: сборочный скрипт собирал только `codex`, вкладка
стартовала нормально, а падал каждый вызов инструмента:

```
failed to spawn code-mode host /Users/<user>/.noted-terminal/bin/codex-code-mode-host:
host executable was not found
```

Ключевое: **локальные feature-флаги это не лечат и не объясняют**. Режим
инструментов для модели задаёт сервер — `~/.codex/models_cache.json` присылает
`tool_mode = code_mode_only` для `gpt-5.6-sol/terra/luna` и `codex-auto-review`.
Серверное значение имеет приоритет над `[features]` (`core/src/tools/mod.rs`:
`model_info.tool_mode.unwrap_or_else(...)`), поэтому `code_mode = false` в
`~/.codex/config.toml` ничего не отключает. А `code_mode_only` — режим без
запасного варианта: обычные прямые инструменты не подставляются, и сессия
теряет всё, включая web-поиск.

Второй слой ловушки: попытка «выключить» проблему через `code_mode_host = false`
меняет симптом на `code-mode host is disabled` и делает хуже. Это Stable-фича с
`default_enabled = true`; она управляет не самим Code Mode, а только наличием
host'а, который Code Mode требует.

Host нельзя собрать локально: `codex-code-mode-runtime` зависит от крейта `v8`,
а prebuilt-архив для `aarch64-apple-darwin` не публикуется — build.rs падает с
HTTP 404. Поэтому единственный законный источник — vendor-payload официального
npm-пакета `@openai/codex-<platform>`, и версия обязана совпадать с версией
нашего патченного CLI: host говорит по версионированному framed-протоколу
(`ClientHello`/`SupportedProtocolVersions`), чужая сборка может не сойтись на
handshake. Копировать host из `ChatGPT.app` или `.plugin-appserver` нельзя —
это другая ветка сборки без гарантии совпадения версии.

Ремонт двухсторонний, оба слоя обязательны:

1. `scripts/build-install-noted-codex.sh` ставит host атомарно рядом с `codex`
   через `scripts/noted-codex-host-resolve.mjs` (резолв по точной версии, отказ
   при несовпадении). Host проверяется и на fast-path «codex уже актуален» —
   у него отдельный жизненный цикл, и codex-marker про него ничего не знает.
   При свежей сборке host ставится **до** публикации нового `codex`, иначе на
   диск попадёт заведомо нерабочая пара.
2. `decideCodexBinaryOverride` в `codex-semantic-channel.js`: если соседа нет,
   приложение вообще не подставляет свой бинарник и оставляет пользовательский
   Codex. Рабочая сессия важнее semantic side-channel — потеря обогащения
   Timeline обратима, мёртвая вкладка нет.

Launch failure — часть того же shell boundary, а не состояние Codex TUI. `terminal:create` обязан проверить `cwd` до spawn'а PTY: если папка проекта удалена/переименована, это `working_directory_missing`, а не shell, в который можно потом вставить первый prompt. Native/API launch (`/agent-tabs`, Inbox, History runtime) ждёт structured result от `codex:run-command`; при failed spawn/run нельзя слать `terminal:force-command-started`, иначе iOS увидит fake `starting` без процесса, обычный input на fresh tab и локальную user-row, которую rollout никогда не подтвердит. Прод-шрам: проект ссылался на отсутствующий `/Users/fedor/Desktop/cli-tools`, zsh сразу exit'нулся, web route ответил success, а первый mobile send зависал в `inactive/no session`.

## Готовность и переходные состояния

Готовность перед автоматическим первым prompt'ом определяется не таймером. `codex:run-command` подтверждает только, что main вооружил наблюдение и записал launch-команду в PTY; до lifecycle-proof результат остаётся `pending`, а ранний process lookup не имеет права превратить его в failure. Чистый composer/ready, ручной blocker, завершение команды, PTY exit или новое поколение закрывают pending по факту. Минутный watchdog — только защита от запуска без исхода, не источник истины «процесс отсутствует» и не gate ручного Enter. Для автоматической вставки scenario layer ждёт авторитетный TUI-ready; для Claude он может прийти по prompt-кадру `⏵`, для Codex — по живому composer без startup blocker.

Маркер composer'а — версионируемая деталь Codex TUI, а не один вечный символ: наблюдались `›`, `❯` и в Codex 0.145 новый `»`. Semantic-пути draft/readiness/active-prompt используют общий список и признают маркером только символ в начале логической строки после отступа. Иначе закрывающая русская кавычка `»` внутри текста обрезает draft до последних слов. ASCII `>` остаётся только слабым readiness-fallback и намеренно не участвует в извлечении draft, потому что часто встречается в shell/output.

Текст на экране сам по себе не является текущим состоянием. Visible-buffer проверяется только по актуальному интерактивному кадру — suffix от активного или последнего line-leading composer'а, — поэтому старая строка `Starting MCP servers` выше уже готового input не блокирует readiness и не разрешает restart. Headless xterm применяет байты синхронизированной перерисовки раньше, чем Codex завершает кадр, поэтому main хранит последний полностью закрытый кадр: пока следующий кадр открыт, readiness/watchdog читают закрытую версию, а не промежуточно стёртую строку. На 15-секундной границе destructive recovery заново подтверждает тот же launch, watchdog, PTY/mirror generation, user-input generation, текущий MCP-blocker и отсутствие готового composer'а/in-flight prompt; более новый закрытый кадр допустим только если он всё ещё семантически показывает тот же blocker. Недоступный proof означает повторную ограниченную проверку и сохранение процесса, а replacement запускается только после подтверждённого успешного Stop; внутренний retry не публикует промежуточный `inactive` как новый пользовательский lifecycle.

Поздний MCP-blocker может прийти уже после того, как Codex показал чистый composer и вкладка стала готовой. Первые сырые байты такого кадра временно закрывают только автоматические действия; они ещё не доказывают, что blocker действительно нарисован. Физическая клавиатура сильнее диагностического proof: любой user/unknown-origin input отменяет pending proof и прозрачно проходит в PTY, а terminal protocol reply не отменяет его. Решение по автоматике принимается после commit ровно этой записи в тот же main/headless terminal и только при совпадении terminal, lifecycle, run, input revision, launch, mirror и write sequence. Подтверждённый blocker снимает прежнюю готовность и запускает обычный watchdog; committed кадр без текущего MCP-blocker освобождает proof даже если app-owned `/model` временно держит slash help; устаревшее поколение отбрасывается. Во время этого ожидания нельзя сбрасывать process, writer/session ownership, модель, effort или FAST.

Если settings-picker уже вставил точный `/model`, но pending proof остановил Enter, транзакция сначала ждёт исход того же committed MCP-кадра. При отсутствии текущего blocker она повторно доказывает неизменный `/model` и продолжает ровно одним Enter. При blocker/failure cleanup разрешён только когда свежий draft proof всё ещё дословно равен app-owned `/model`, а terminal/run/lifecycle/mirror/input identity не менялись; тогда один Ctrl+C очищает строку и пустота подтверждается повторно. Изменённый пользователем draft, новая generation или unknown proof не трогаются. Любой исход освобождает pending proof и PTY-operation — диагностический watcher не может стать модальным терминалом.

Desktop-плашка является проекцией текущего lifecycle, а не накопителем старых диагнозов. Текущее `starting/active/inactive` Codex перезаписывает прежний timeout-error; красный вид разрешён только явному актуальному `startupFailed`. Сигнал ready/finished и завершение Claude startup-defaults gate инвалидируют уже запущенные presence-пробы, иначе поздний ответ старой проверки способен воскресить закрытый loader. Пользовательские симптомы нарушения одного класса: плашка исчезает и возвращается, готовый Codex внезапно получает `Terminal input did not become ready`, либо процесс визуально как будто запускается второй раз.

Lifecycle, read identity и writer authority читаются одним main-owned snapshot. Нельзя сначала получить `inactive/active`, затем отдельным IPC прочитать session id: между запросами writer может смениться, и один API-ответ склеит две генерации. Snapshot отдельно отдаёт `readSessionId/canCopySessionId` и `provenWriterSessionId/writerUsableForMutation`; renderer не строит первое из launch/SQLite/Zustand и не подаёт его во второе. Ошибка process lookup сохраняет последнее доказанное визуальное lifecycle-состояние, но не возвращает ID из SQLite/renderer; после failed Stop общий projection также не имеет права превращать один `tuiReady` в зелёный `active` без writer proof.

History, loader и API читают один main-owned lifecycle/identity snapshot одного поколения. Они не агрегируют command state, turn state, runtime session, stopping и readiness отдельными IPC-чтениями, поэтому handoff writer не может выдать `busy` вместе со старым ID или `isBusy=false`.

Desktop lifecycle-индикатор — общая для Codex и Claude компактная прямоугольная плашка слева сверху, а не полноэкранная модалка. Start/resume не забирает focus, не ставит backdrop и не перекрывает xterm, кроме собственного крестика. Это необходимо именно для startup-экранов Codex (`Update available`, trust и directory chooser): пользователь может взаимодействовать с видимым TUI, пока рядом честно показана текущая стадия. Чистый composer гасит startup-плашку даже если writer identity ещё уточняется; незавершённая identity-проверка сама по себе не должна выглядеть как загрузка терминала. Плашка переводит реальные blocker'ы в пользовательские этапы и при внешнем run сдвигается ниже уже занятого status badge. Stopping использует ту же геометрию без backdrop/focus с янтарным акцентом; просмотр, выделение и прокрутка остаются доступны, но main-side guard отбрасывает raw `terminal:input` и отклоняет `terminal:paste` до подтверждённого exit, чтобы поздний ввод не попал в появившийся shell.

Автоматизация startup-меню пишет стрелку/Enter прямо в PTY и не зависит от DOM focus или hit-test; ручная клавиатура идёт через xterm и требует одновременно доступного renderer-input и готового к вводу TUI. Поэтому сочетание «`down-enter-skip` уже есть в логе, ручные стрелки не действуют, а Skip всё ещё нарисован» не доказывает запоздалую автоматику: отдельно проверяются текущая startup-фаза и захват ввода интерфейсом. Неблокирующая плашка убирает собственную помеху, но не объявляет последний нарисованный кадр готовым composer'ом.

У `codex-f` появление нового rollout-файла ещё не означает, что текущая сессия готова: Codex сначала копирует в него историю исходной сессии, и на больших transcript это сотни мегабайт. Session id привязывается отдельно, а turn watcher заранее прикрепляется к новому файлу, но до настоящего composer-фрейма держит закрытый history barrier и не разбирает копируемый рост. Codex может повторно выпустить старые записи со свежими внешними timestamps, поэтому ни время записи, ни `mtime`, ни сам append не отличают историю от live-события. На первом подтверждённом composer-фрейме barrier переносит offset на текущий EOF; только последующие `user_message` / `task_started` / `task_complete` считаются живыми событиями новой вкладки. Иначе старый `task_complete` ложно снимает start/resume status, а чтение каждого append-куска создаёт main-process I/O storm. Barrier взводится только для fork с известной source session; fresh start, обычный `codex-c` и recovery pending paste audit сохраняют прежний catch-up путь. Диагностика: `[CodexTurn] fork history barrier armed/released`, где `copiedBytesIgnored` показывает объём исключённой копии.

## External Inbox runs

Внешний API Codex не является отдельным агентом и не пишет в rollout напрямую: `/api/inbox/runs` создаёт или переиспользует Codex PTY-вкладку в system Inbox, а дальше идёт тем же lifecycle, что обычный desktop-запуск. `conversationKey` связывает внешний чат с вкладкой, пока вкладка сохранена: повторный запрос с тем же ключом должен отменить pending auto-stop/auto-close и продолжить тот же Codex tab/session, а не плодить новую вкладку. Если auto-close уже закрыл вкладку, внешний клиент всё ещё владеет своим transcript/UI, но Noted Terminal начинает новый terminal run для того же `conversationKey`; старый live terminal context не восстанавливается из UI-чата сам собой. Поэтому внешний клиент владеет своим transcript/UI, но Noted Terminal остаётся владельцем Codex-процесса, rollout JSONL, session id, Timeline/History и stop-flow.

Claude startup defaults (`/model`, `/effort`) не применимы к Codex. Во внешнем API non-Claude PTY должен отдавать `startupDefaultsPending=false` и `startupDefaultsReady=true`: иначе native iOS держит fresh Codex в `Starting session`, хотя `/status` уже показывает `active inputReady=true`. Если Codex зависает на starting, сначала проверяй runtime/readiness, update/trust/directory/MCP blockers и rollout watcher; не добавляй ожидание Claude defaults как общий gate для всех agents.

SSE-клиент должен считать turn завершённым только по `done`. `busy:false` и отсутствие новых `message`-событий не являются completion: Codex может уже вернуть управление терминалу, но внешний consumer ещё не получил финальный `done` и не должен сохранять assistant-message как законченный. После `done` Noted Terminal планирует два независимых cleanup-таймера: auto-stop процесса по `autoStopMs` и auto-close визуальной Inbox-вкладки по `autoCloseMs` (default 15 минут). Ошибка в metadata/таймере должна логироваться, но не блокировать fan-out `done`, иначе внешний чат зависает при уже завершённом ответе.

Перед отправкой external prompt работает тот же terminal draft preflight, что в History, но endpoint'ы расходятся по ownership. `/api/terminal-tabs/:tabId/send` — project/tab API для iOS, History-like клиентов и прямого управления вкладкой: если в TUI composer найден draft, endpoint возвращает `409 terminal_draft_conflict` и **не очищает** terminal input. Старые клиенты должны увидеть конфликт, а пользовательский текст остаётся там, где был набран. `/api/inbox/runs` — внешний чат поверх system Inbox: при таком же конфликте Noted Terminal атомарно забирает draft из terminal composer, очищает TUI input и возвращает `draftText` + `originalPrompt` наружу. Внешний продукт обязан откатить свой just-sent user-turn и вернуть в composer `terminal draft` выше нового prompt'а; error bubble или assistant-message здесь ложные, потому что Codex ничего не получил.

После submit внешний API доказывает отправку через ближайший `event_msg.user_message`, но Codex canonicalizes leading whitespace: prompt, который в TUI начинался с пробелов, может попасть в rollout уже как `trimStart()` без того что отправка провалилась. Audit должен принимать этот узкий canonical match (`actual === expected.trimStart()`), но не ослаблять проверку середины/хвоста текста. Пользовательский симптом без этого исключения: `/api/terminal-tabs/:tabId/send` или `/api/inbox/runs` возвращает `409 codex_user_message_audit_mismatch`, хотя Codex уже получил prompt и начал отвечать; повтор клиента создаёт дубль. Шрам всплыл на Rewind/API-тесте с одинаковыми началами prompt'ов и ведущими пробелами.

Первый Inbox-turn имеет отдельный watcher edge. Prompt может быть вставлен уже после `tui-ready`, но до того как rollout watcher обнаружил `session_meta` и создал turn-watcher. Поэтому paste audit для `codex:append-input` / external run стадируется до turn-watcher'а; когда session detection наконец приходит, turn-watcher стартует с `offset=0` только при pending audit и сразу делает catch-up scan по уже записанному `event_msg.user_message`. Без этого первый `/api/inbox/runs` мог физически отправить prompt и получить ответ в терминале, но API падал как `codex_turn_watcher_unavailable` / не мог доказать `done`. Не переносить offset=0 на обычный polling: он нужен как recovery только для pending audit первого turn'а.

Metadata-only rollout существует до запуска TUI, поэтому app-created Fresh сразу
имеет точный watcher/read identity и может простоять без первого prompt сколько
угодно. Первый submit больше не занимается поиском session id: он только
подтверждает, пишет ли Resume в source на месте или в новый child. Старый
re-arm discovery остаётся только страховкой для вручную запущенного внешнего
`codex`, который обошёл app-created materialization. Renderer/xterm unmount не
закрывает main-side watcher — его lifecycle принадлежит PTY process exit/kill
или writer handoff.

## Инициализация Codex

Rollout не является произвольным внешним API. Разрешены только две узкие
операции Noted Terminal, закреплённые тестами текущего Codex: metadata-only
создание новой сессии и append user-context после доказанного Stop. UUID во
всех полях и имени файла совпадает; создание идёт exclusive-create, append —
по неизменной file revision и целой newline-границе. Копировать чужой rollout
как шаблон или дописывать живому writer запрещено.

Системные инструкции по-прежнему передаются через `AGENTS.md`/profile
`developer_instructions`; metadata-only rollout не содержит скрытого prompt и
не расходует контекст модели. После обновления Codex этот контракт обязательно
проверяется физическим `create → codex resume <UUID>` до изменения схемы.

## Timeline и History

`codex:get-timeline` строит точки из `event_msg.user_message`, дополняет их `turn_context` (model/effort) и `event_msg.token_count` (tokens/context%). `thread_rolled_back` откатывает последние turn'ы в уже построенном списке, compact-like события превращаются в compact marker. Это не Claude backtrace: у Codex нет нашего `parentUuid`-DAG и fork/plan markers, а token breakdown backend остаётся Claude-only. Timeline открывает общий middle-history popup: `codex:copy-range` копирует диапазон, `codex:edit-range` заменяет его compact/replacement entry, `codex:delete-range` удаляет выбранные turn'ы и compact markers. Обе мутации создают новый локальный rollout fork, после чего вкладка продолжает через `codex-c <newSessionId>`. Не возвращать Claude-only gate ни для `Редактировать`, ни для `Удалить выбранное`.

Codex compact marker в Timeline обязан принадлежать текущему user-turn'у, а не жить вне rollback. `thread_rolled_back` в rollout оставляет старые строки файла на месте, поэтому parser должен удалить и user-turn'ы, и compact markers, которые пришлись на откатанную ветку. Симптом регресса: HistoryPanel уже показывает усечённую историю, а правая Timeline-полоса после Rewind рисует несколько оранжевых compact markers подряд из сырого хвоста (`type:"compacted"`), хотя Codex-контекст уже восстановлен до более ранней ветки. Проверочный кейс: сессия с несколькими `type:"compacted"`, затем `thread_rolled_back { num_turns: N }`; `codex:get-timeline` и `codex:get-full-history` должны вернуть один и тот же набор compact uuid.

Codex middle-history edit не требует app-server. Текущая модель — локальная rewrite/fork поверх `~/.codex/sessions/**/rollout-*.jsonl` после проверки что turn idle; app-server `thread/rollback` сам умеет только tail rollback по `numTurns` и не решает замену диапазона в середине истории. Если нужна более богатая structured-интеграция, это отдельное архитектурное разрешение, не автоматический fallback.

Project Terminal API использует тот же core для `/api/terminal-tabs/:tabId/edit-range` и `/api/terminal-tabs/:tabId/delete-range`, но это не desktop Timeline flow. Внешний клиент должен сам остановить Codex через `/stop`, дождаться `inactive`, передать границы диапазона, а после успешного ответа сам вызвать `/resume`: routes намеренно режут только inactive rollout и возвращают конфликт для active/stopping, чтобы не закрепить неполный turn. Успешная Codex-мутация создаёт `newSessionId`; web-server просит renderer adopt'нуть его в tab state (`adoptedSessionId`), иначе следующий resume продолжит старый rollout и внешне будет выглядеть как «API изменил историю, но чат открылся прежний».

Delete Range использует тот же copy-on-write контракт, что Edit Range, но без replacement-записи. План строится по видимым Timeline-объектам: выбранный user-turn владеет зеркальной user-записью, assistant/reasoning/tool records и результатами инструментов до следующего turn; выбранный compact владеет своим compact record и companion marker. Из нового rollout исключаются все raw records этих владельцев, остальные сохраняют порядок. `compact` не является границей и не заставляет удалять префикс. Исходный файл остаётся неизменным даже для полного префикса или большого middle-range; результат всегда отдельная локальная сессия с `forked_from_id`. Новый rollout пишется последовательными порциями с exclusive-create, а не собирается целиком второй гигантской строкой в памяти; при ошибке недописанный файл удаляется, уже существующий файл не перезаписывается.

Автоматически приложенный `# AGENTS.md/CLAUDE.md instructions …` — не
отдельный пользовательский ход. В History он может оставаться видимым chip'ом,
но получает координату следующего реального prompt; в Timeline отдельной точки
нет, а Rewind/Delete на самом chip недоступны. При rewrite его raw
`developer + instructions + turn_context` preamble принадлежит следующему
canonical user-carrier. Иначе Timeline чеканит адресуемую точку без raw
`turnKey`, и любой диапазон через неё падает `no exact rollout identity`.
Аналогично paired image-carriers связываются общим точным image-aware matcher,
а `compacted` удаляет свой `context_compacted` companion по семантической паре,
не по расстоянию в строках: между ними законно стоят `world_state`,
`turn_context` и `token_count`.

`event_msg.token_count` питает **три** независимых потребителя, и каждый берёт своё поле — не путать: точки Timeline (выше), usage-чип лимитов (`payload.rate_limits`, см. `## Usage limits`) и живой контекст-метр в ControlBar (`info.last_token_usage.total_tokens / info.model_context_window`, канал `codex:context-update`, см. `fact-claude-control-bar.md::Context % bridge`). **Ловушка, заложенная в `contextPct` внутри самого `codex:get-timeline`:** он делит `total_token_usage.total_tokens` (кумулятив за всю сессию) на окно → на длинной сессии это десятки миллионов / 258k = тысячи процентов, клампится в вечные 100%. Это поле сейчас не рендерится в renderer (Timeline-метр контекста живёт в ControlBar по `last_token_usage`), поэтому баг латентный и не чинён — но при любом будущем выводе контекст-% из Timeline формулу `total_token_usage` копировать нельзя, правильный знаменатель-числитель — `last_token_usage` (последний запрос ≈ занятость окна, т.к. Codex каждый ход пере-отправляет всю историю).

`codex:get-full-history` строит HistoryPanel из `response_item`: reasoning summary идёт в thinking, assistant message — в обычный ответ, `function_call` + `function_call_output` превращаются в raw tool carrier для общего `claude-blocks` renderer. Новый Codex tool surface записывает реальные вызовы верхнеуровневым `exec`, а их имена и аргументы оставляет внутри JavaScript source (`tools.exec_command(...)`, `tools.apply_patch(...)`, `tools.mcp__...(...)`). History обязан снять эту transport-оболочку до renderer: shell становится Bash-карточкой, `apply_patch` раскладывается по файлам в Edit/Write/MultiEdit, image/read — в Read, MCP — в компактную MCP-карточку. Парсер читает только вызовы вне строк и комментариев и разбирает безопасный literal-subset без `eval`; иначе пример `"tools.exec_command(...)"` или строка внутри самого patch создаст ложное действие. Симптом нарушения этой границы — строки `EXEC const r = await tools...` в History; это потеря семантики в rollout adapter, а не проблема CSS-пакета.

### In-process субагенты (multi_agent_v1 / collaboration)

Codex-субагенты приходят в rollout **двумя поколениями инструментов**, и History рендерит оба одинаковыми Task-карточками (тот же вид, что субагенты Claude SDK), а не сырыми JSON-вызовами. v1 — namespace `multi_agent_v1`: `spawn_agent` output несёт `{agent_id, nickname}`, результат приходит в output `wait_agent`/`close_agent`. v2 — namespace `collaboration`: у `spawn_agent` в arguments вместо текста задачи лежит **зашифрованный** блоб (`gAAAA…`, та же Fernet-капсула, что compact) — его нельзя показывать как описание карточки; человекочитаемое имя берётся из `task_name` → `/root/<task_name>`. Привязка call→карточка в v2 идёт через `event_msg.sub_agent_activity` (`event_id` = call_id вызова, `agent_thread_id` = session id дочернего rollout), а финальный текст — через `agent_message` response_item с префиксом `FINAL_ANSWER` (эта запись НЕ обычный assistant-ответ и не должна попадать в transcript отдельной строкой).

Ловушка порядка: `sub_agent_activity` приезжает **между** `function_call` и его `function_call_output`, поэтому карточка регистрируется на моменте call'а, а не output'а — иначе activity некуда приклеить и child session id теряется. Статусы монотонны: `completed` не понижается поздним `interacted`; `interrupted` рисуется amber.

**Третий путь завершения — `<subagent_notification>` (E2E-зомби 2026-07-25).** Fire-and-forget агент (spawn без wait_agent) объявляет исход НЕ через `agent_message`/`wait`-output, а обычным `user_message` с телом `<subagent_notification>{"agent_path":"/root/…","status":{"completed":"…"}}</subagent_notification>`. Без обработки этого пути карточка/чип висели running вечно (подтверждено: 4м+ при уже завершённом агенте; спасал только kill процесса). Парсер: notification скармливается трекеру (`onSubagentNotification`) и фильтруется из transcript как service-noise (аналог Claude `<task-notification>`); Timeline тоже не чеканит для него точку. Non-JSON тело деградирует до mention-scan по известным агентам — дрейф формата даёт «совпало по упоминанию», не зомби.

**Отклонённый spawn — карточка терминальная, а не живая (прод-шрам 2026-07-26).** Запуск может быть отвергнут в момент вызова, и тогда агента НЕ существует: ни `wait_agent`-статуса, ни `close_agent`, ни notification для него уже не будет — карточка, зарегистрированная как `running` на call'е, висит вечно. Реальные отказы: `Full-history forked agents inherit the parent agent type; omit agent_type, or spawn without a full-history fork.` (прод-случай: `fork_context:true` + `agent_type` вместе), `collab spawn failed: agent thread limit reached`, `collab spawn failed: thread-store internal error: No space left on device`. Симптом у пользователя: два вечных чипа, рядом с которыми лежат их же успешные ретраи через 15 секунд.

Детектор — **структурный, по наличию identity в output**, не по фразам: успех v1 даёт `{agent_id, nickname}`, успех v2 — `{task_name:"/root/<name>"}` (обе формы проверены на 190 реальных spawn-output; отказ не даёт ни того, ни другого). Считать «нет `agent_id`» отказом нельзя — это убило бы все v2-карточки. Отклонённая карточка помечается `spawnRejected`, статусом `interrupted`, суффиксом ` · не запущен`, а текстом результата становится причина отказа (пользователь иначе вообще не видит, что попытка провалилась). Причина читается из СЫРОГО payload: отказ приходит plain text, и JSON-разбор превращает его в `null`. `spawnRejected` необратим: ни поздняя activity, ни resume не воскрешают несуществующего агента — повторный запуск это новый call и новая карточка.

**Родитель — ненадёжный свидетель завершения; агент авторитетен о себе.** `wait_agent` штатно вызывается БЕЗ цели («дождись хоть кого-нибудь»), и его вывод `{"message":"Wait completed."}` не называет никого. Агент реально закончил, а в родительском rollout терминального события для него нет вовсе — карточка висит `running` вечно и держит лоадер вкладки. Прод-шрам 2026-07-29 (вкладка `tab-1743`, 5465 записей): из 36 запусков 12 без единого терминального события, 11 из них при этом явно завершены в собственных файлах. Лечение — последний проход после разбора rollout: для каждой оставшейся `running`-карточки берётся её дочерний rollout по `agentSessionId` и проверяется хвост (64KB) на `task_complete` / `phase: final_answer`. Нечитаемый или отсутствующий файл НЕ закрывает карточку: отсутствие доказательства не равно доказательству завершения. Реализация — `src/main/subagent-transcript.js::isAgentFinishedByOwnTranscript`, потребитель — конец `buildCodexFullHistory`, лог `[CodexSubagents] closed by own transcript: N/M`.

**`close_agent` терминален в ОБЕИХ формах ответа.** Форма зависит от того, успел ли агент закончить сам: `{"previous_status":{"completed":"<текст>"}}` — успел, `{"previous_status":"running"}` — закрыт на ходу (обычно после `wait_agent` с `timed_out:true`). Вторая форма — простая строка, чтение `.completed` из неё даёт `undefined`, и карточка оставалась `running` навсегда: для закрытого агента никакое событие уже не придёт. В корпусе 4 закрытия из 32 приходят строкой; поймано на `explorer`-агентах (2 из 7 в одной сессии висели живыми). Закрытие без собственного результата → `interrupted` + суффикс ` · закрыт` + человекочитаемая причина; закрытие уже завершённого агента не понижает его статус.

**Типы агентов (`agent_type`) — не только `default`.** Каталог: `explorer` (быстрый read-oriented), `worker` (правки файлов), `luna_e2e` (ограниченный E2E с фиксированной моделью), `default`. По реальным вызовам за последние 60 сессий: без указания типа 97, `explorer` 67, `default` 24, `luna_e2e` 6 (`worker` есть в каталоге, но в проде не встретился) — то есть **дефолтный тип самый редкий**, а больше половины запусков идут либо безымянными, либо как `explorer`. Проверять поведение карточек только на `default` бессмысленно; в этой сессии именно так и потерялся баг с закрытием на ходу — он вылез только на `explorer`. Важно: счёт вести по реальным `function_call`, а не по вхождению слова в файл — каталог инструментов перечисляет все типы в каждом рollout и даёт кратно завышенную статистику. Отдельного namespace «мини-агентов» нет: роль задаётся типом, lifecycle-события у всех общие (`spawn_agent`/`wait_agent`/`resume_agent`/`send_input`/`close_agent` в `multi_agent_v1`). Параметра фонового запуска у `spawn_agent` нет — фоновость (`run_in_background`) относится к инструментам внутри вкладки, а не к субагентам Codex.

**Возобновление завершённого агента (`resume_agent`) возвращает карточку в работу.** Зеркало Claude-дыры с `SendMessage`, найдено в тот же день: `resume_agent {id}` → `{"status":"pending_init"}`, затем `send_input` даёт агенту следующую задачу, и следующий `wait_agent` снова его завершает. Имя было в списке control-вызовов, но не обрабатывалось — карточка оставалась `completed` весь возобновлённый прогон, чип не возвращался. Обработка стоит рядом с `wait_agent`/`close_agent` и намеренно обходит монотонность статусов (это единственный легальный переход `completed → running`); для неизвестного агента и для `spawnRejected` — no-op. Прод-последовательность 04:31:54→04:38:11 воспроизводится по срезам rollout: `completed → resume → running → wait → completed → send_input → running → финал completed`.

**Liveness чипа субагента — process-scoped, не turn-scoped.** Codex-агент законно переживает свой ход (spawn в N, wait в N+2): busy=false родителя чип НЕ гасит. Гейт — собственный `subagentStatus === 'running'` + живость хост-процесса (`historyComposerAvailability.status ∈ active/busy/starting`): мёртвый codex не может держать in-process агентов, и терминальное rollout-событие для них уже не придёт → fail-safe от вечного чипа. Скан идёт по ВСЕЙ ленте, а не по последнему ходу: last-turn-only скан молча гасил чип, как только пользователь отправлял следующий prompt (agent в N, новый ход N+1 → карточка агента уже не в последнем ходу). Contrast: Claude Task без явного статуса — turn-scoped (Escape гасит весь ход, E2E PASS ≤1 render tick); Claude background Bash — наоборот process-scoped, см. `fact-история-как-основная-поверхность.md`. Наследуемый лоадер вкладки: `history-panel:background-work {tabId,count}` → TabBar shimmer (display-only). Control-вызовы (`wait_agent`, `list_agents`, `close_agent`) при живых карточках подавляются как отдельные строки — их output абсорбируется в карточку соответствующего агента. Полная работа субагента лежит в отдельном rollout-файле (`thread_source: subagent`, `parent_thread_id` — связь с родителем); карточка несёт его session id для перехода. Реализация: `src/main/codex-subagent-cards.js` (+ unit-тесты рядом), потребитель — `buildCodexFullHistory`.

Orchestrated `exec` может вернуть `Script running with cell ID N`, а итог прийти следующим прямым `wait {cell_id:N}`. **Объявление ячейки — МАШИННАЯ строка, и распознавать её нужно как строку целиком, а не как подстроку.** Номер всегда цифровой и стоит на отдельной строке; вывод инструмента при этом на 99% состоит из прозы — содержимое файлов, диффы, цитаты документации. Прод-шрам 2026-07-31 (`tab-2634`): агент напечатал ЭТУ САМУЮ фразу из нашей документации, парсер по `[^\s]+` вытащил из markdown-цитаты «номер» ``N`,`` и увёл карточку в фон под идентификатором, который никакой `wait` назвать не может. Результат не приклеился уже никогда: 809 открытых живых карточек против 808 закрытых, единственная осиротевшая осталась с крутящимся индикатором на вкладке, где ход давно завершён (снаружи — «вкладка активна, хотя ничего не работает»). Асимметрия цены: пропущенное объявление стоит дёшево (карточка остаётся обычной и закрывается сама), ложное — стоит вечно висящей карточки, поэтому правило намеренно строгое. Full-history parser держит ссылки на уже созданные semantic-карточки и приклеивает поздний результат к ним; отдельную строку Wait в этом случае не создаёт. Если один exec содержит несколько вызовов, результаты распределяются по content-parts, когда их число совпадает; при слитом/truncated output весь доступный результат остаётся у последней карточки, а предыдущие всё равно помечаются завершёнными. Image content заменяется коротким маркером, base64 в History не материализуется. Прямые legacy tool-call записи сохраняются и проходят тот же semantic mapping. Это даёт тот же визуальный слой HistoryPanel, но без Claude-only действий. Timeline для Codex использует text-search anchoring как Gemini, а не Claude OSC markers; если Timeline пуст при живом Codex, сначала проверяй session capture (`codexSessionId`), а не scroll/search-часть Timeline.

Для rollback-safe привязки assistant-response к user-turn нельзя сначала выкидывать user rows из структурной проекции. `thread_rolled_back` может прийти после user-turn без assistant output; assistant-only список тогда удалял предыдущий представленный turn и сдвигал все ответы на один. User rows участвуют в indexing до применения rollback и фильтруются только из финального assistant-context. Иначе ручное `Обновить название` в Timeline может взять ответ следующей итерации.

Model/effort в Codex History — display-only строки из `turn_context`, а не реальные slash-команды в rollout. Codex получает модель и effort на старте через CLI args или через интерактивный `/model` picker; durable evidence для истории — ближайший user-turn с `turn_context`. History может вставить перед prompt'ом фиолетовые `/model <id>` и `/effort <level>` строки со стабильными display-id, если значения изменились относительно предыдущего turn'а. Эти строки не попадают в Timeline, не materialize conversation сами по себе и не должны различать manual/API/startup route: одна durable запись `turn_context` даёт одно отображение.

Новый общий путь для desktop Timeline/History и Project Terminal API — `agent-transcript:*` поверх `SessionTranscriptService` (см. `fact-transcript-сервис.md`). Старые `codex:get-timeline` / `codex:get-full-history` остаются совместимыми entrypoints, но добавлять новый per-surface polling reader нельзя: длинный rollout один, consumers много. Codex parser поэтому держит incremental cache по файлу: unchanged `size+mtimeMs` = cache hit, append читает только новые bytes и склеивает `leftover`, shrink/rewrite делает chunked full reread, concurrent callers делят один inflight promise. Full-record cache — LRU до трёх файлов и 768 MiB raw bytes, но один oversized active rollout намеренно остаётся: его eviction заставил бы повторно парсить 600+ MB на каждом клике. Логи `[CodexJsonlCache] full/append/evict` нужны для blame'а: если Timeline/History тормозит на большой сессии, сначала проверь что нет повторного `full reason=first-read/rewrite-or-shrink` на каждом refresh.

Codex compact надо читать из **top-level** записи `type: "compacted"`: именно там лежит `payload.replacement_history` — полный свёрнутый контекст. Соседний `event_msg.payload.type === "context_compacted"` полезен только как marker/telemetry и сам summary не содержит. Если парсер цепляется за `context_compacted`, HistoryPanel показывает пустую плашку `History Compacted`, а Timeline умеет только «здесь был compact», без содержимого. Для clean copy/export этот snapshot не разворачивается рекурсивно: иначе старые prompts дублируются при каждом новом compact. Исключение — явное одиночное `Копировать compact` из Timeline (`codex:copy-range` с `startUuid=endUuid` одного compact marker): пользователь выбрал сам compact как объект, поэтому backend разворачивает именно его `replacement_history`, а не оставляет заглушку `Conversation compacted`. См. [`fix-codex-дубли-после-сжатия.md`](fix-codex-дубли-после-сжатия.md). Последний предыдущий `token_count` даёт только `preTokens` — размер окна **до** сжатия. Он остаётся технической статистикой и не печатается как размер compact. Пока протокол не отдаёт явный `postTokens`, History/Timeline показывают `context compacted (encrypted)` без числа; если будущая версия добавит `post_tokens/postTokens/compacted_tokens`, число можно показать как размер результата.

Живая операция не восстанавливается из старого rollout. Для внешнего submit
точная текущая `event_msg.user_message` со значением `/compact` за byte-границей
активного process generation сохраняет прежний контракт старта. Для ручного
xterm `/compact` первый Enter создаёт только невидимое ожидание на текущих
terminal/session/process/prompt generation, EOF и event sequence: фазу
`COMPACTING` включает лишь новый причинный `task_started`. Это сохраняет второй
Enter, когда первый только выбрал slash suggestion, и не даёт ложный loader.
Top-level `compacted` того же writer/session/generation завершает уже
стартовавшую операцию успешно; `turn_aborted` завершает как прерванную, а
`task_complete` без предшествующего `compacted` — как не доказавшую compact.
`context_compacted` не является terminal proof.

**Fork от последнего compact — отдельный copy-on-write rollout.** После `session_meta` первой смысловой записью становится последний top-level `compacted`; более старые snapshots и самостоятельные ранние turns удаляются, а его companion `context_compacted` и весь поздний хвост сохраняются. В новом `session_meta` оба identity-alias обязаны одновременно указывать на child: `payload.id = child` и `payload.session_id = child`; происхождение хранится отдельно как `payload.forked_from_id = source`. Шрам 2026-07-27: writer переписал только `id`, оставил `session_id=source`, и корректно сокращённый файл не запускался с `session-meta-mismatch`. Source-settings resolver нельзя ослаблять: любое противоречие alias означает неизвестную identity и должно блокировать Resume; чинить нужно атомарную запись обоих полей. Source rollout остаётся byte-for-byte неизменным.

App-created compact-fork отличается от generic `codex resume <sourceId>` по силе доказательства чтения. Для compact-fork приложение само атомарно создаёт child rollout с новым точным id, поэтому новая вкладка обязана получить этот id сразу и показать уже перенесённую историю до первого prompt. Это не подтверждает runtime writer: launch всё ещё проходит обычный live-proof до того, как новые записи считаются принадлежащими вкладке. Прод-шрам 2026-07-28: child-файл tab-511 был создан заранее и содержал 380 записей, но id не передали вкладке; History оставался пустым до первого Enter, после writer-proof старая история появилась целиком, а новый prompt — ещё примерно через секунду после реальной записи в rollout.

В отличие от Claude, Codex compact **не создаёт Old History Zone**. Pre-compact записи остаются доступны через rollout JSONL и `codex:get-full-history`, поэтому Timeline не должен выставлять `lastBoundaryIdx`, красный background или click gate для Codex. Оранжевый compact marker у Codex означает только «здесь Codex свёл контекст», а не «всё выше недоступно».

`replacement_history` может быть очень большим и содержать вложенные content-parts. Regular `codex:get-timeline` отдаёт только короткий structural marker + token count, а Cmd-hover по Codex compact **не вызывает** `codex:get-full-history`: человекочитаемого summary там нет. ПКМ `Копировать compact` — отдельный explicit path через `codex:copy-range`: он разворачивает verbatim-часть одного выбранного compact и заменяет тяжёлые/нечитаемые parts (`input_image`, `image_url`, `data:image`, encrypted compaction state) короткими маркерами. Compatibility full History всё ещё eager материализует raw tool-output и compact snapshots; ленивый detail-endpoint по byte identity пока не реализован. См. [`fact-transcript-сервис.md`](fact-transcript-сервис.md).

Обрезка inline base64 внутри `compacted` действует только в parsed/UI-кэше.
Fork/Edit/Delete не имеют права сериализовать этот объект обратно: буквальный
`image_url: "[image omitted]"` делает новый rollout resumable, но первый же
model turn получает OpenAI `invalid_value`. Reader поэтому хранит рядом только
невидимые `{source file, byte range, sha256}` каждого удалённого data URL;
writer потоково возвращает exact raw value, проверяет hash и удаляет partial
child при сменившемся source. Сами base64 в JS-объекте не удерживаются.
`__line`/`__byteOffset` — такие же parser-only поля и в JSONL не записываются.
Уже повреждённый compact без raw proof fail-closed и не порождает следующий
fork. Production-класс 20.08: compact-fork `994dd484…`/`e949d096…` был создан
из memory-safe проекции и каждый Send падал на `input[N].content[1].image_url`.

**Внутри compact нет прозаического пересказа, и расшифровать его нельзя.** Вопреки названию «свёрнутый контекст», Codex не перефразирует историю в короткое summary как Claude. Запись `type:"compacted"` несёт `payload.message: ""` (пусто — заголовка/резюме компакта в открытом виде нет) и `payload.replacement_history` — массив из (а) **дословных** сообщений последних ходов (`role: user/assistant/developer`, вербатим, не пересказ) и (б) одного финального элемента `{type:"compaction", encrypted_content}`. Именно `encrypted_content` (~20–30 KB, префикс `gAAAAAB`) и есть настоящая модель-читаемая выжимка — но это **Fernet-токен**: открыты только version-байт + timestamp + IV, само тело это `AES-128-CBC` ciphertext + HMAC-SHA256. Расшифровать на стороне клиента **криптографически невозможно**: ключ держит только OpenAI, он привязан к конкретной модели и ротируется (TTL порядка часов/суток). Это by-design для ZDR / `store=false` (капсула транзитом проходит через клиент, лежит в `~/.codex/sessions/`, шлётся обратно — сервер расшифровывает у себя в памяти и выбрасывает) и как anti-prompt-injection (открытую summary можно было бы подменить). Поэтому форматтер заменяет блоб на `[encrypted compaction state]`, а «Копировать compact» по дизайну отдаёт вербатим-сообщения + этот маркер — **это не баг копирования и не «сломанный» компакт**. Те же ключи-капсулы дают `invalid_encrypted_content` при resume старой сессии или смене модели посреди диалога: к этому моменту даже сам OpenAI не может расшифровать свой блоб. Если нужен человеко-читаемый пересказ Codex-сессии — его придётся **генерировать самим** (прогнать `replacement_history` + ходы через модель), а не пытаться достать из компакта.

**Remote v2 compact не очищает большой импорт целиком.** В OpenAI-пути Codex (`responses_compaction_v2`) `replacement_history` собирается как retained raw-сообщения `user/developer/system` плюс compaction output; клиентский код зеркалит server default `RETAINED_MESSAGE_TOKEN_BUDGET = 64_000` в `codex-rs/core/src/compact_remote_v2.rs`. Бюджет общий на все retained-сообщения, не на каждое: Codex идёт с конца истории к началу, новые сообщения оставляет целиком пока они влезают, граничное старое сообщение режет по середине через `…N tokens truncated…`, всё ещё более старое выкидывает из raw retained. Пример: первый prompt 200k токенов, потом 20k, потом пять сообщений суммарно 7k → после `/compact` последние 27k остаются целиком, от первого prompt остаётся примерно 37k, остальная середина заменена truncate-маркером; сверху всё равно есть encrypted compaction state. Поэтому `/compact` снижает налог на окно, но не является clean-room summary. Если пользователь импортировал Claude-export на сотни тысяч токенов и хочет гарантированно убрать сырой дамп из будущего контекста, рабочий flow: попросить Codex написать человеко-читаемый handoff-summary → `/clear` или новый thread → продолжать с этим summary.

## Per-turn usage в detail-панели Timeline

Detail-панель (плашка по hover на точке Timeline) показывает для Codex-entry разбивку из `last_token_usage` того же `token_count`: вход `uncached` (`input_tokens − cached_input_tokens`) / `из кэша` (`cached_input_tokens`), выход `ответ` (`output_tokens − reasoning_output_tokens`) / `размышление` (`reasoning_output_tokens`). Две вещи специфичны для Codex и не повторяют Claude API-разбивку: кэш у Codex — **только** `cached_input_tokens` (аналог Claude `cache_read`); `cache_creation` Codex наружу не отдаёт, поэтому строки «записано в кэш» быть не может. И наоборот, `reasoning_output_tokens` даёт split выхода на ответ vs размышление, которого у Claude в этой панели нет — это и есть «сколько Codex думал» числом, а не флажком `· think`.

Числа честны **только per-entry**: `last_token_usage` — это последний единичный запрос, ровно этот ход. Суммировать по range нельзя — Codex каждый ход пере-отправляет всю историю, счётчики перекрываются, и сумма по диапазону превратится в число-ложь. Поэтому usage цепляется к одиночной точке, отдельного range-эстимейта (как Claude `claude:estimate-range-tokens`) для Codex нет и заводить его на этих полях нельзя.

**Слой имеет значение: per-turn числа цепляются в источнике, не в отображении.** `codexUsage`/`codexLimits` навешиваются на `currentUser`-entry внутри `buildCodexTimeline` — это **слой-источник**, где per-turn данные собираются из rollout. Detail-панель только читает готовые поля entry, ничего не пересчитывает. Reasoning при этом живёт в двух слоях разными сущностями: как **число** (`reasoning_output_tokens`) — здесь, в источнике Timeline; как **текст** (summary размышления) — в `buildCodexFullHistory`, слой отображения History (второй уровень). Их нельзя путать: добавляя reasoning-число, цепляй его к timeline-builder'у, а не к history-builder'у — иначе оно окажется в слое, который про текст, а не про метрики. Та же `last_token_usage`-ловушка `last` vs `total`, что для context% (см. секцию Timeline и History выше), применима и тут: брать `last`, не кумулятивный `total`.

History-методы Terminal MCP для Codex — read-only слой поверх того же rollout JSONL: stats, `list_turns` и точечный pull истории допустимы. `fork_session` / `propose_edit` / `apply_edit` намеренно unsupported, потому что Codex не имеет Claude `parentUuid`-DAG и edit-range pipeline. Живое управление Codex (`start`, `codex-c`, `codex-f`, prompt, stop) идёт через live-методы того же Terminal MCP, то есть через владельца PTY-процесса, а не через попытку переписать transcript.

Docs-индикаторы для Codex собираются в `codex:get-timeline` из `response_item`, пока парсер стоит на текущем user-turn. `function_call` с `namespace: "mcp__knowledge"` и `name: "docs_search"` добавляет query в `docsSearchQueries`; `custom_tool_call` / `function_call` с `name: "apply_patch"` извлекает только patch headers `*** Add/Update/Delete File:` для `docs`/`Docs` и `CLAUDE.md` в `docsEdited`. Для absolute-путей чужих проектов docs-директория считается knowledge docs, если рядом с ней на том же уровне лежит `.semantic-index.json`; lower-case `/docs/` оставлен как legacy fallback. Не искать docs-события в `function_call_output` или stdout: там могут лежать большие Read-результаты, pasted docs-rules и diff'ы, что даёт ложные «документация обновлена» на Timeline. Цвета и precedence этих атрибутов описаны в `fact-timeline.md::Docs-индикаторы`.

Copy Session для Codex использует тот же rollout JSONL, но не тот же shape что HistoryPanel: clean export строит user/answer/thinking/tool blocks и отдельно классифицирует `apply_patch`, shell, MCP, `web_search`, `tool_search`, subagents и other tools. Не переносить Claude `formatToolAction` напрямую: Codex `tool_search_output` должен ужиматься до списка namespace/function, а result берётся из `response_item.*_output`, не из `event_msg.mcp_tool_call_end`. Детали — `fact-clipboard-tools.md::Codex Copy Session export`.

Cmd+] History controls для Codex идут через agent-runtime adapter, а не через Claude-specific ветки внутри HistoryPanel. Правая панель только рендерит оболочку: статус, textarea, Resume/Stop/Pull/Send/Interrupt; Codex-runtime владеет resume, stop, send и draft-grab, а presence получает готовым main-owned snapshot вместо склейки нескольких runtime-чтений. Это нужно, чтобы следующий PTY-agent (Gemini или другой CLI) добавлялся новым runtime, а не ростом условных веток в HistoryPanel.

History send preflight для Codex сначала читает общий draft-state proof: main-side headless xterm mirror первым, renderer `terminalRegistry.getCodexDraftState` только fallback когда tab реально mounted. `hasDraft=false` с `source=*:dim-hint` означает пустой composer и **не должен** вызывать `codex:grab-input`: Ctrl+G/external-editor cycle на пустом prompt'е меняет TUI-состояние и может проглотить следующий immediate `codex:send-command`. `hasDraft=true` → вызвать `codex:grab-input`, атомарно забрать и очистить composer, prepend'нуть текст в History textarea, показать `Send stopped · draft moved` и не отправлять History prompt. `hasDraft=null` → fail closed, потому что speculative send может склеить пользовательский draft с новым prompt'ом. Старый shortcut «renderer no-terminal, значит пропускаем guard» для History/Rewind/API больше невалиден: background flow должен получить main proof или явную ошибку.

Обычный пользовательский Enter не проходит этот внешний preflight и не ждёт process/status/session proof: адресат уже выбран самим активным терминалом. Перед write остаётся только локальная очередь байтов PTY; после write main обновляет наблюдение writer и логирует реальную задержку до физической записи.

Любой внешний Codex submit (`History Send`, `Run after`, Replay с Cmd+click, MCP `ai-prompt`) имеет только один честный guard до paste: если composer уже содержит ручной draft, новый prompt нельзя смешивать с ним или перетирать его. Этот guard читает xterm visual state через общий main/headless-first proof (renderer только fallback), поэтому он защищает ownership input, но не является доказательством будущей доставки.

После bracketed paste у Codex нет детерминированного события «composer принял вставку до Enter». Hidden/background renderer может не ответить или увидеть stale `source=*:dim-hint`, а PTY render/sync marker может быть stale или не прийти, хотя текст уже физически лежит в composer. Поэтому внешний Codex submit не строится на post-paste UI/render ACK: handler пишет paste и Enter в один упорядоченный PTY-поток (`skipRenderWait:true`) и считает доставку доказанной только после ближайшего rollout `event_msg.user_message` с тем же length/hash. Если audit после Enter не прошёл, это `submitted_unverified`/failure после submit, а не разрешение слепо повторить Enter: prompt мог уже уйти, а подтверждение могло отстать.

Шрам 2026-06-18: History уже работал, а Run after вставлял текст и не отправлял, потому что мгновенный snapshot после paste видел старый dim-placeholder. Шрам 2026-06-20: переход на render marker тоже оказался недетерминированным — в hidden/background окне Codex принял текст, но fresh marker не пришёл и `paste_render_timeout` остановил Enter. Итоговая граница: до paste только draft-conflict guard; после paste — ordered PTY submit; точное совпадение текста — только rollout audit. Если первая строка composer после `›` пустая, pre-paste guard всё равно должен просканировать следующие visual rows и вернуть `*:multiline-draft-row-N`: пустая первая строка означает blank line/отступ, а не пустой draft.

History разделяет намерение, факт записи в PTY и durable delivery. Локальная пользовательская строка появляется сразу, но получает source identity только после `user_message` за точной pre-Enter byte-границей. На вкладке может одновременно ждать несколько таких audit-владений: один pending-slot опасен, потому что B затирает A, а запоздавшее после compact подтверждение A ошибочно сравнивается с B. `task_complete`, timeout и закрытие watcher не доказывают отказ доставки; перед закрытием нужен финальный scan уже записанного хвоста, а неподтверждённая строка остаётся unknown без красного `SEND FAILED` и без автоматического повтора. Failed/cancelled presentation удаляется из самого bounded store после TTL, иначе remount присваивает ей свежий timestamp и снова переносит в конец History.

Остаётся известный разрыв входов, который не исправлялся вместе с Direct Send: Enter на inactive Codex сам запускает/возобновляет процесс, ждёт readiness и отправляет snapshot один раз, а Run after сначала требует уже готовый input и сам этот запуск не инициирует. Это не ограничение PTY и не баг одной кнопки, а неполная унификация scenario layer; исправлять нужно общим `launch-if-needed → readiness → submit/queue` владельцем, сохраняя разную политику ownership draft у History, Project API и Inbox.

Manual Pull из History использует тот же visual-state guard. При `hasDraft=false` это no-op: не трогать external-editor helper, не показывать жёлтое `Send stopped`, а дать короткий нейтральный `Terminal input empty`. Это защищает от ложного пользовательского вывода «отправка была остановлена», когда на самом деле переноса не было.

Порядок prepend общий с Claude: текст, уже набранный в TUI composer, является первичным draft'ом пользователя и должен оказаться перед текстом из History textarea. Append ломает намерение в сценарии «сначала написал в terminal, потом открыл History и решил отправить другое»: пользователь получает обратный порядок причин, хотя приложение формально ничего не потеряло.

Если prompt ушёл из History и пользователь быстро нажал Stop, Codex может сначала вернуть draft в terminal composer и только затем записать `turn_aborted` в rollout JSONL. History runtime слушает именно `turn_aborted`, держит `Stopping`-state до подтверждения и после него делает короткую серию probes terminal draft (первый probe может быть пустым). Найденный terminal draft prepend'ится обратно в textarea с `Prompt restored`. Когда Codex уже прислал `task_complete`/`turn_aborted`, но History ещё перечитывает rollout, панель показывает `UPDATING`: thinking уже закончился, но durable JSONL-история ещё не догнала UI.

History Cancel/Interrupt для Codex должен нажимать native `Escape`, а не raw `Ctrl+C`. В upstream Codex именно `Escape` из running-status вызывает restore-aware ветку `interrupt_and_restore_prompt_if_no_output`; при pending steer эта же клавиша может прервать текущий turn и применить ожидающий ввод по правилам самого TUI. Внутренний `AppEvent::RestoreCancelledTurn` не выходит наружу через rollout/app-server, поэтому внешний слой Noted Terminal не может ждать события «composer restored»: контракт остаётся `turn_aborted` как авторитетный edge, затем terminal draft probe/grab.

Если terminal draft не читается, History НЕ возвращает последний отправленный prompt из памяти. Last-sent fallback создаёт ложный рассинхрон: textarea показывает текст, которого terminal input фактически не вернул; пользователь видит это как prompt, появившийся "в какой-то рандомный момент". В этом случае показывается нейтральное `Cancel confirmed` / `prompt was not returned`, textarea остаётся пустой.

History textarea draft хранится per-tab вне mount-cycle панели. Закрытие/открытие `Cmd+]` не очищает input; clear происходит после успешного send или явного действия пользователя. Симптом регресса: юзер закрыл History на время проверки терминала, открыл снова, а недоотправленный prompt исчез.

Отправка из History/iOS/API во время streaming для Codex теперь физически остаётся Enter-submit, а не native `Tab` queue-key. `statusAtSend=busy`/`queue:true` в `codex:send-command` означает только local handoff-state: клиент уже показал строку `SENDING/QUEUED` и ждёт, пока rollout догонит её `event_msg.user_message`. Handler всё равно пишет bracketed paste + `Enter` в ordered PTY stream; `Tab` использовать нельзя, потому что это «ожидать конец ответа и поставить follow-up в native queue», а пользовательский контракт здесь — Enter во время streaming. Фактический JSONL для Enter-busy может появиться не сразу: в тесте 2026-06-26 второй `event_msg.user_message` был записан после завершения текущего shell tool и затем текущий Codex turn завершился ответом на этот ввод. Поэтому HTTP/API может вернуть `queued:true` / `status:"queued"` как pending marker и даже `userMessageAuditPending:true`, но это не доказательство native queue и не повод дожимать `Tab` или повторный `Enter`. Симптом регресса 2026-06-20 остаётся тем же: marker под сообщением исчезал раньше durable `event_msg.user_message`, а затем сообщение «телепортировалось» вниз после перечитывания JSONL. Такой handoff нельзя считать успешным по tool/MCP/thinking row: локальный marker держится до matching user-message, явного cancel/turn edge или проверенного consumed-state.

### Native backtrack / Timeline Rewind

У Codex нет Claude-style `/rewind`. Обычный Timeline `Откатиться` идёт через родной backtrack TUI: первый `Escape` должен показать hint `esc again to edit previous message`, второй `Escape` открывает transcript overlay на последнем user prompt, к более старым prompt'ам автоматика двигается `←`, а `Enter` отправляет `ThreadRollback { num_turns }`. Footer Codex показывает `esc/← to edit prev`, но для нашего cleanup это не значит что `Escape` безопасно закрывает overlay: отмена открытого overlay идёт через `q`. В rollout JSONL rollback появляется как `event_msg.payload.type === "thread_rolled_back"`, и парсеры `codex:get-timeline` / `codex:get-full-history` физически откатывают уже построенный список на `num_turns`.

`Escape` не является универсальной «очисткой» Codex: на готовом composer он открывает native backtrack. Перед cleanup или History Send общий main/headless screen proof сначала различает composer, model picker, transcript/Rewind overlay и startup blocker. Доказанный picker можно закрыть `Escape`, доказанный Rewind overlay — только `q`; неизвестный экран остаётся нетронутым. Обычный физический Enter при этом не ждёт lifecycle/session-проверок и сразу пишется в PTY, но History Send отказывается отправлять, если текущий кадр доказывает picker, Rewind или startup вместо composer.

Если Codex process остановлен, Timeline Rewind сначала делает resume той же session id и ждёт `codex:tui-ready`. Это не просто «процесс жив»: readiness отвергает update/trust/directory prompts и `MCP startup interrupted`, затем сверяет точный текущий composer, model/effort footer и живой Codex descendant process. `Starting MCP servers` не блокирует эту связку: composer уже принимает prompt, а Codex сам дожидается MCP. Пока composer-proof нет, `codex:open-history-menu` по-прежнему fail-closed (`codex_not_input_ready`).

Главное отличие от Claude: successful Codex rollback **сразу durable**. Это не preview-режим и не локальная ветка до следующего submit. После `thread_rolled_back` History/Timeline должны показывать уже усечённую историю из rollout, без постоянного `I REWOUND` marker'а и без дублирования target user-row. UI не должен снимать `REWINDING` в момент ответа IPC: он держит `Updating history...`, пока refresh `codex:get-full-history` не докажет что target/future rows исчезли из server entries. Выбранный prompt всё равно переносится в History textarea как draft, чтобы пользователь мог отредактировать и отправить новую ветку; terminal composer после этого должен быть пустым. Этот draft возвращается как часть результата Rewind и хранится per-tab, поэтому Rewind при закрытой History должен дать тот же input после последующего открытия панели. Если закрыть и открыть Codex заново сразу после rollback, откат уже сохранён, в отличие от Claude native `/rewind`, где preview до нового send не меняет JSONL.

`thread_rolled_back` доказывает сам rollback, но не новый writer. Codex 0.145 после подтверждения native Rewind может продолжить source rollout либо создать linked child. Поэтому перед необратимым `Enter` приложение сохраняет durable операцию с точным target proof, source ID и поколением PTY. После Enter оно принимает только единственного child-кандидата с точным префиксом откатившейся source-истории, затем одной SQLite compare-and-set транзакцией меняет binding source→child и удаляет журнал. При рестарте незавершённая операция восстанавливается до AutoResume тем же proof; неоднозначный или неполный scan не угадывает writer и сохраняет операцию для диагностики.

Удаление pre-Enter журнала после успешного source→child commit не удаляет доказательство уже совершённой операции. В той же SQLite-транзакции создаётся точная commit-квитанция: operation/request token, action generation, исходный проект операции, текущие project+tab, source+child, PTY lifecycle/run, target/hash/depth. Поздний post-grab callback читает её без живого watcher/intent и принимает только при полном совпадении плюс всё ещё сохранённой привязке вкладки к exact child. После успешного ответа квитанция переводится в закрытое состояние; точный повтор остаётся идемпотентным, а новая операция вытесняет старую запись. При переносе вкладки меняется только текущий project квитанции и журнала, исходный project операции остаётся неизменным. Таймеры, recency и произвольный новый writer не являются proof.

После успешного source→child handoff source и child могут оба оставаться открытыми writable в том же PTY. Одноразовый журнал к этому моменту уже правильно удалён, поэтому следующий Rewind не должен снова требовать его и объявлять writer ambiguous. На срок текущего PTY/run generation сохраняется settled proof: точный child, source, action generation и SQLite binding. Он разрешает конкурентами только доказанных предков child; sibling, descendant, чужой rollout, новый append в source, Stop/relaunch или смена generation немедленно делают состояние неоднозначным. Параллельный observer того же commit принимается только как точный replay всех этих полей, а не по условию «binding уже равен child».

Success path проверяется по детерминированным кадрам, а не по таймауту: `prime initial ... hint=true`, `open Esc` с transcript overlay, frame после стрелок содержит target prompt (с учётом `skipDuplicates` для одинаковых prompt'ов), xterm visible-snapshot доказывает что именно этот prompt сейчас активен, затем `thread_rolled_back` появляется при следующем чтении rollout. Символ `›` в Codex overlay — prompt/cursor marker и может стоять у нескольких prompt-строк; он сам по себе не означает «выбранная строка». Шрам 2026-06-18: dev session `019edc60` падала `codex_rewind_target_not_selected_before_enter` или откатывалась не туда на 3-message flow, потому что target уже был виден в overlay, но текстовый frame не доказывал активную строку.

Текущий safety contract для Codex Rewind: `inputReady=true` означает только готовность к обычному вводу, но не готовность к native backtrack. Перед первым `Escape` Rewind проверяет текущий visible-state; если виден старый transcript/protocol UI, закрывает его через `q`, а если чистый старт не доказан — падает до rollback. Число стрелок выводится из target index только как план навигации, а `Enter` разрешает renderer xterm snapshot. Snapshot возвращает prompt rows вместе с cell-style (`fg/bg`, `inverse`, `bold`, `dim`); активным считается prompt, который Codex подсветил фоном/inverse-стилем. Если style-parser не доказывает что активная строка совпала с target, overlay закрывается через `q` и возвращается `codex_rewind_target_not_selected_before_enter` без rollback. Text-frame остаётся вспомогательным anchor'ом и логом, но не fallback-коммитом; если видимый префикс активной строки противоречит началу target, общий anchor в середине текста не считается match. После `Enter` всё равно нужна post-grab сверка normalized text с target: активная подсветка доказывает выбранный prompt, а grab доказывает что Codex реально префиллил и очистил composer. Таймауты в этом flow только failure bounds. Если Codex сейчас busy (`task_started` без `task_complete/turn_aborted`), rewind должен отказаться с `codex_busy`: backtrack посреди активного turn'а не является безопасной операцией.

Для коротких/одноходовых Codex-сессий target может быть multiline, а active xterm snapshot иногда показывает только первую visual row (`› Dev lifecycle final API self-test.`) вместо всего `targetFullText`. Это не разрешает возвращать text-frame fallback: style snapshot всё равно должен доказать активную строку. Но если normalized active text без prompt glyph является достаточно длинным префиксом полного normalized target (минимум 16 символов и 3 слова), Rewind принимает `anchorMode=active-visible-prefix`. Короткие или общие префиксы остаются недоказанными, иначе одинаковые первые слова снова дадут silent rollback не туда.

После confirm Codex временно префиллит target prompt в своём composer'е. Приложение забирает его через тот же `codex:grab-input` / Ctrl+G helper, что и ручной `+ clear`, и сверяет restored draft с target. Для обычного текста это normalized text match, но prompt с картинками сравнивается как текст + image slots: `[Image #1]`, `[imagePath: ...]` и image placeholder являются одним вложением, если текстовая часть и позиция слота совпали. Сам draft для History собирается из rollout user-message metadata (`local_images` / `text_elements`): если путь картинки ещё доступен, textarea получает `[imagePath: ...]`, а общий Codex send-path перед paste превращает этот marker обратно в путь, который Codex поднимает как image chip. `codex_rewind_restored_input_mismatch` или `codex_rewind_restored_input_empty` нельзя превращать в успешный UI-state: rollback мог уже примениться (`rollbackMayHaveApplied: true`), но terminal input не доказанно очищен или содержит не тот prompt. Если отличается только представление картинки и rollout даёт recoverable path, это успешный Rewind с restored draft; если путь недоступен, draft содержит явный `imageError`, а UI показывает warning вместо ложного «выбран другой prompt».

AI Rewind поверх Codex backtrack — отдельный post-action, а не вариант обычного preview. Сначала применяется native `thread_rolled_back`, потом диапазон user prompt + ответ до следующего user prompt или конца сессии отправляется в Gemini/Rewind prompt, и результат становится новым prompt'ом для Codex. Поэтому источник для Gemini должен быть durable History/rollout после rollback, а не terminal buffer: у Codex откат уже сохранён к моменту compact-запроса.

Для вставки результата Gemini в Codex нельзя использовать fast paste path. Codex — crossterm TUI с explicit bracketed paste: large paste может визуально свернуться в `[Pasted Content N chars]`, но rollout должен получить полный `event_msg.user_message`. Прод-шрам: Gemini вернул полный markdown на ~1k+ символов, Claude принял его целиком, а Codex при fast multi-write записал в JSONL только хвост (prompt начинался с пунктов 4-5 списка). Byte-safe UTF-8 chunking сам по себе не чинит этот класс: проблема не в JSONL writer и не в разрыве кириллицы, а в submit до того как composer принял весь logical paste. `codex-rewind-ai` обязан идти TUI-safe путём: одна logical bracketed paste, sync/render marker, потом отдельный Enter. `CodexPasteAudit` сравнивает ожидаемый Gemini-текст с ближайшим rollout `user_message`; mismatch означает paste/composer regression, не ошибку Gemini.

`codex app-server` (`thread/start|resume`, `thread/rollback`, `turn/start|steer`) существует как structured control-plane внутри Codex CLI, но для текущей архитектуры Noted Terminal это **не целевой путь**: это внешний для приложения experimental API/protocol, не наша локальная JSONL-архитектура. Новые rich Codex-действия, включая future middle-history replace, делать без app-server, пока пользователь явно не разрешит переход на этот dependency. Важно: даже app-server rollback по текущему протоколу удаляет только `numTurns` с конца thread'а, поэтому он сам по себе не решает замену диапазона в середине истории.

## Usage limits

Внутри rollout JSONL авторитетный snapshot лимитов — `event_msg.payload.type === "token_count"` с `payload.rate_limits`. В текущем формате `primary` обычно 5-hour, `secondary` — weekly, но UI классифицирует их по `window_minutes`, а не по позиции; `resets_at` приходит epoch seconds и перед показом переводится в ISO/local time. Этот snapshot нужен Timeline/detail-панели: он отвечает «какой budget-state был у конкретного хода».

Toolbar usage-chip отвечает на другой вопрос — «какой budget сейчас у выбранного Codex аккаунта». Для текущего Codex login `codex:get-usage` читает тот же `GET https://chatgpt.com/backend-api/wham/usage`, что web dashboard, с OAuth и `ChatGPT-Account-Id`. Active rollout и `logs_2.sqlite` остаются только account-bound discovery/fallback, когда для запрошенного аккаунта ещё нет verified OpenAI snapshot; уже сохранённый server snapshot не подменяется локальными данными из-за возраста или временной сетевой ошибки. Не возвращать старую модель «чип = последний rollout активной вкладки»: при мультиаккаунтинге пользователь может смотреть бюджет второго аккаунта, пока активная вкладка принадлежит первому. Полная UX/логика чипа — `fact-claude-usage-chip.md::Источник данных Codex`.

`account_id` в ответе `wham/usage` — user identity и не равен workspace/account id из request header. Сверять ответный `account_id`/`user_id` нужно с JWT claim `https://api.openai.com/auth.user_id`; сравнение с `ChatGPT-Account-Id` ложно отклоняет реальный текущий аккаунт.

HTTP 200 от `wham/usage` сам по себе не доказывает свежую ветку лимита: один account уже давал краткий флап `обычный used → почти нулевой used со сдвинутым reset → обычный used`. Подозрительный reset/regression не заменяет last verified snapshot до второго совпавшего ответа той же ветки с интервалом минимум 30s; после наступления прежнего reset новая ветка принимается сразу. Force refresh не обходит этот guard. До восьми verified snapshots с маскированной identity сохраняются через `app_state` без OAuth-секретов, поэтому список аккаунтов не исчезает после рестарта.

В UI только текущий Codex login имеет зелёную точку; historical аккаунты серые и stale независимо от выбора. Заполнение progress bar показывает remaining, а его цвет — степень исчерпания по used. Не возвращать старую семантику, где подпись говорила `left`, а длина полосы изображала `used`.

Account-log freshness сортируется по **поколению reset**, не по времени строки лога. После недельного reset старая сессия может позже дописать старый `rate_limits` snapshot с большим `ts`, и если выбрать просто latest row, toolbar откатится с новых `0/1%` обратно на старые `77/81%`. Правильный порядок: `secondary.reset_at` (weekly) → `primary.reset_at` (5-hour) → `ts`/`ts_nanos`. В логах должны быть `wReset/5hReset/thread`, иначе такой флап нельзя доказать.

`active-session-rollout` fallback требует `opts.sessionId` и `opts.cwd`, запускается только когда для запрошенного account key нет verified OpenAI snapshot, и читает bounded tail файла, а не весь rollout. Он применим только к совпавшему account key. Если identity активной сессии уже известна и отличается от selected account, совпавший старый `sourceThreadId` не даёт права перетирать selected snapshot; неизвестную identity нельзя выводить из текущего глобального auth по одному времени записи. Global `latest-rollout` допускается только как unverified fallback, когда вообще нет доказанных аккаунтов и пользователь не выбрал account key.

Это отличается от Timeline/context%: тот же `token_count` уже используется для точек Timeline, но лимитам нужен именно server `rate_limit` / rollout `rate_limits`, а не `last_token_usage.total_tokens`. Если Timeline есть, а Codex usage пустой, сначала проверь source/account/error в `[CodexData] get-usage ...`; session id и parser могут быть исправны, а OAuth мог истечь или выбранный non-current аккаунт ещё не дал account-bound sample.

Тот же `rate_limits`-снимок цепляется и к timeline-entry (`codexLimits`) для показа в detail-панели — это не дубль usage-чипа тулбара, а **другой вопрос**: тулбар-чип отвечает «сколько бюджета осталось сейчас», а снимок на entry — «где этот конкретный ход оставил бюджет» (per-turn состояние на момент хода). Поэтому он нейтрально-серый рядом с usage-числами хода, без severity-порогов чипа.

## Loader и App Server

Для текущего продукта Codex App Server **не обязателен**: loader'у не нужны дробные состояния «пишет ответ», «ждёт approval», «выполняет команду». Нужен один high-level факт — turn ещё продолжается или уже завершён/прерван. Rollout JSONL уже даёт этот уровень через `task_started`, `task_complete` и `turn_aborted`; задержка до первой записи меньше секунды допустима, потому что пользовательские Codex-turn'ы обычно длятся минуты, а критичный риск — не поздний старт loader'а, а ложный обрыв посреди работы.

Main-owned turn state и его доставка — разные части контракта. Primary History может увидеть правильный `busy` через pull-snapshot, но это не заменяет общий fan-out для вкладки, проекта, очередей, уведомлений, Dock и SSE. При resume catch-up исторические переходы остаются подавленными до writer proof и полного чтения удержанного диапазона, после чего наружу выходит одно текущее состояние; `pasteBusy` остаётся только коротким подтверждением доставки prompt и не продлевается на весь turn.

Этого достаточно для loader'а, но не для доказательства успешного результата. `task_complete` означает только «ход больше не выполняется». Результат подтверждается одним из двух rollout-фактов: (1) непустым `task_complete.last_agent_message`; либо (2) непустым корневым `response_item.message` с `role:'assistant'`, `phase:'final_answer'` и тем же точным `turn_id`, что у завершающего `task_complete`. Commentary, `final_answer` без `turn_id` или ответ от другого turn доказательством не являются. Если ни одного доказательства нет, main публикует `busy:false` с причиной `codex-no-final-result`: composer снова доступен, но автоматика не получает права на побочное действие.

Прод-шрам 2026-07-15: Codex показал в TUI `unexpected status 403 Forbidden`; в проверенном rollout не было ни непустого `last_agent_message`, ни matching same-turn `final_answer`. Это доказывает только завершение без подтверждённого результата, но не кодирует `403` и даже не определяет класс ошибки. Текст TUI остаётся диагностическим свидетельством, а не lifecycle-контрактом автоматики. Для точного машинного класса нужен отдельный структурированный источник, например Codex App Server.

App Server остаётся только explicit future-path, если пользователь отдельно согласится на зависимость от experimental Codex protocol ради точного статуса `completed/failed`, нативного approval/question UI, item-level tool lifecycle или официального `turn/interrupt`. Не переносить Codex на App Server только ради loader'а, rewind/edit-range или удобства RPC, пока JSONL watcher стабильно держит busy=true на всём turn'е, а автоматика безопасно трактует отсутствие финального результата как неизвестный исход.

### Native iOS live stream

Native iOS получает Codex через тот же `/api/events` SSE, что mobile-web. `task_started/task_complete/turn_aborted` достаточны для loader'а, но не доставляют текст ответа: для live-чата tail watcher должен превращать новые rollout JSONL `response_item` записи в тот же raw message envelope, который уже понимает мобильный renderer. Маппинг: `event_msg.user_message` → user text, `response_item.reasoning` → assistant thinking, `response_item.message` с `role=assistant` → assistant text, `function_call`/`custom_tool_call` → `tool_use`, outputs → `tool_result`.

Пользовательский симптом, когда этот fan-out пропущен: вкладка на iOS показывает `busy`, после выхода/входа история становится длиннее, но пока пользователь остаётся внутри вкладки новый assistant-текст не появляется. Диагностический canary: `[CodexTurn:Delta] ... responseItems=1 ... lastResponseItem=message` доказывает, что JSONL delta прочитан; если рядом нет `[WebBcast:SEND] type=message`, сломан именно broadcast в mobile SSE. `[WebBcast:DROP] type=message ... noSubscribers` означает уже другую проблему — iOS не подписан на этот `tabId`.

Контекст-% для native/web идёт тем же `bridge-update` envelope, что у Claude. `emitCodexContextPct` исторически слал процент только в desktop renderer (`codex:context-update` через `mainWindow.webContents.send`); для телефона добавлен параллельный `_webBroadcast(tabId, {type:'bridge-update', contextPct})`. Без него Codex-вкладка на iOS никогда не получала процент — у Codex нет StatusLine bridge, который у Claude эмитит этот кадр. Плюс last-known процент сидится из SQLite в `/params` и в списке вкладок (см. `fact-mobile-claude-pty.md::Контекст-% и список моделей`), чтобы значение было на открытии вкладки до первого живого `token_count`.

Prompt Queue / Run after использует тот же high-level слой, но различает окончание работы и наличие результата. `task_complete`, подтверждённый непустым `last_agent_message` либо matching same-turn root `final_answer`, — штатный конец, после которого можно отправлять следующий queued prompt. `codex-no-final-result` снимает loader и disarm'ит как собственную очередь trigger-tab, так и cross-project owner-очереди, которые выбрали его через `runAfterTabId`. `turn_aborted` выключает собственную автоматику Codex-tab'а, но сохраняет внешнюю подписку: после продолжения она ждёт следующего доказанного `task_complete`, а не принимает abort за успех и не исчезает навсегда. Тексты queued items при disarm сохраняются для явного повторного arm. Дробные состояния «ждёт approval», «печатает ответ», «выполняет команду» для этой фичи не нужны — пользовательский инвариант один: пока Codex-turn не дал подтверждённый результат, следующий prompt не уходит. После отправки граница ownership проходит по `submitted`: audit timeout после уже записанного Enter не возвращает item очереди, иначе повторный arm создаст дубль.

Граница `Escape`: приложение не считает raw `Escape`/`Ctrl+C` Codex-сигналом само по себе. Для Codex авторитетен только rollout JSONL: если после вмешательства появился `turn_aborted`, loader гасится, собственный Run after disarm'ится, а чужая подписка остаётся ждать будущего success после продолжения. Claude-style fallback «нажали Escape → через короткую idle-проверку принудительно busy=false» пока не переносить на Codex без реального симптома, иначе можно получить ложный обрыв long-running turn'а.

То же правило действует в Cmd+] History controls: успешный `codex:send-command` и `PasteBusy` не переводят Codex в долгоживущий `BUSY`, а только `task_started` из rollout JSONL. После Ctrl+C/interrupt HistoryPanel не ставит `READY` оптимистически; он ждёт `turn_aborted` или `task_complete`, затем обновляет presence через `codex:get-turn-state`. Пользовательский симптом нарушения — справа залипает `BUSY` после пустой отправки, или наоборот панель показывает `READY` сразу после Escape, пока turn ещё жив.

### OSC 133 D→B debounce внутри Codex TUI

У Codex есть дополнительный shell-layer шум: PTY shell может эмитить OSC 133 `D` (`terminal:command-finished`) на короткой внутренней границе, а затем почти сразу приходит `B` и Codex продолжает тот же TUI lifecycle. Если на первый `D` сразу делать общий command-finished cleanup, приложение преждевременно чистит `codexKnownSessions`, закрывает turn watcher и гасит process state; пользователь видит микрофлап loader'а или Continue-state при живом Codex.

Для Codex-tab `parseOSC133AndEmit` задерживает `terminal:command-finished` на 250ms. Если за это окно приходит `B`, timer отменяется и логируется `[CodexTurn] suppress command-finished ... reason=osc-d-followed-by-b`. Если `B` не пришёл и `terminalCommandState` всё ещё idle — delayed cleanup выполняется. Это не заменяет rollout JSONL busy: `task_started/task_complete/turn_aborted` остаются источником turn-loader'а; debounce защищает только shell lifecycle cleanup.

После задержки `D` недостаточно проверить только `terminalCommandState`: Codex может продолжать жить как descendant под shell, даже если shell-level OSC уже сказал idle. Перед финальным `command-finished` main делает descendant-lookup по tab и engine=`codex`; если найден живой Codex PID, state возвращается в running, renderer получает `terminal:command-started`, а turn watcher переармится по известному session id. Пользовательский симптом без этого guard'а — loader/Continue флапает или гаснет на живом Codex TUI после короткой shell-границы.

Эта alive-ветка обязана иметь собственный финализатор. Когда delayed `D` увидел Codex descendants и заново эмитнул `command-started`, shell-level `D` уже потрачен: когда wrapper/vendor binary исчезнут через секунду после Ctrl+C, нового OSC `D` не будет. Поэтому вместе с `reason=codex-descendant-alive` запускается process-tree recheck; пока `matches>0` вкладка может оставаться live, а первый `matches=0` делает тот же Codex cleanup, что обычный `command-finished`, и публикует `inactive`. Recheck чистится на новом `B`/force-start/PTY exit/terminal kill, чтобы старый финализатор не погасил новый запуск. Прод-шрам 2026-06-24: session `019ef4ec-0e93-7e70-a35a-ccb3289dc1e6` после Ctrl+C дала `D exitCode=130`, delayed branch увидел `matches=2`, но без recheck UI через несколько минут всё ещё показывал `Resuming Codex`. Диагностические логи: `[CodexExitRecheck] arm/still-alive/finalized/clear/stop`.

Process-tree — отказоустойчивый наблюдатель, а не самостоятельный источник истины. Его контракт трёхсоставный: найденные descendants = `found`, успешно прочитанное пустое дерево = `absent`, timeout/ошибка `ps` = `unknown`. Только `absent` разрешает очистить known session, TUI readiness и turn watcher; `unknown` не кэшируется как пустой результат, сохраняет последнее подтверждённое lifecycle-состояние и запускает повторную проверку. Следующее положительное доказательство жизни возвращает running-проекцию и переармляет отсутствующий watcher по известному session id. Номер запуска защищает от обратной гонки: поздний результат delayed `D` или recheck старой команды не может погасить новый `B`/explicit launch.

Прод-шрам 2026-07-15: пять одновременных снимков `ps -eo pid,ppid,command` завершились timeout, прежний helper превратил ошибку в `[]`, а exit-recheck принял это за доказанный exit. Loader исчез, вкладка кратко показывала зелёный `active`, затем новый rollout-edge вернул loader, но уже закрытый watcher не восстановился. Поэтому в диагностике важна пара `process lookup unknown action=preserve-and-retry` → последующий `found/absent`, а не один визуальный флап.

## Модели и effort

Список моделей нужно брать из live `codex debug models`. Bundled catalog используется только fallback'ом: он может содержать hidden/internal/upgrade-only rows, которые интерактивный `/model` picker не примет. UI синхронизирует свои варианты обратно из реально распарсенного picker'а, потому что именно TUI является финальным источником «какие строки доступны этому аккаунту сейчас».

На Codex CLI 0.145.0 серверная видимость `codex-auto-review` менялась между `hide` и `list` без смены локальной версии, а каждый уже запущенный TUI сохранял снимок каталога с момента своего старта. Поэтому две одновременные вкладки могут законно показывать разные первые экраны `/model`: quick-auto слой с `codex-auto-review` и `All models` либо сразу полный список. Видимый `codex-auto-review` поддерживает обычный следующий экран effort (`low..ultra`), а не применяется как готовая пара без выбора reasoning. У Sol/Terra допустимы `low..ultra`, у Luna `low..max`, у 5.5/5.4/mini/spark — только `low..xhigh`; весь перечень остаётся live-фактом, а не вечной константой.

Renderer-side fallback и ручные display/ordering overrides живут в `constants/codexSettings.ts` + `UIStore.codexSettings`; SettingsModal показывает их рядом с Claude Code, по одной модели и её effort-list в строке. У модели есть отдельная галочка видимости: снятая галочка убирает её из обычных списков ControlBar и StatusBar, но не отменяет доступность в TUI. Если скрыты все, текущая выбранная модель остаётся единственной строкой, чтобы пользователь мог выйти из этого состояния. Новый порядок ставит GPT-5.5 после 5.6 Luna и перед GPT-5.4; нетронутая старая конфигурация мигрируется на этот порядок, а индивидуально отсортированная сохраняется. В той же настройке хранится пара для быстрого перехода; effort в ней всегда приводится к списку выбранной модели, а не берётся из общей шкалы.

Выбранные пользователем effort и реальные возможности модели хранятся раздельно: снятый checkbox не расширяет и не сужает live-capability, а merge пересекает настройки с подтверждённым каталогом. Удаление модели — тоже постоянное намерение, не временная фильтрация: её id попадает в отдельный список удалённых и отбрасывается как из fallback, так и из следующего `codex debug models`. Иначе пользователь удалил бы строку в Settings, а она вернулась бы при первом же обновлении каталога. Финальное подтверждение конкретной пары всё равно приходит из native picker.

Строка auto-пресета в session-local picker доказывает только его видимость в этой вкладке. Она не доказывает default effort и полный набор уровней: неизвестный пресет можно временно добавить в UI лишь после подтверждения точной пары model+effort, а затем заменить данными live-каталога. Иначе короткий первый экран заставляет приложение выдумать пресету всю общую шкалу reasoning, которой upstream мог не разрешать.

Main-side effort parser не держит закрытый список имён. Capture может содержать остаток model menu над следующим экраном, поэтому parser сначала отрезает всё до последнего `Select Reasoning Level`, затем читает все numbered rows реального TUI и нормализует только известные aliases (`Extra high` → `xhigh`). Шрам: live `/api/agent-models` уже показывал `max/ultra`, а установленный Mac parser распознавал только `low..xhigh`; модель с телефона применялась, effort возвращал `option not found`, хотя строка `Ultra` была видна в captured frame. Добавление очередного имени в whitelist лечит один релиз, но сохраняет тот же класс рассинхрона.

Model picker на узком/частично перерисованном TUI может потерять заголовок и clipping hint, оставив только numbered model rows и общий footer. Headerless frame принимается только как цельный последний блок непосредственно над footer: минимум две конкретные model-id, наблюдаемая физическая selection и отсутствие более нового несовместимого header. Одна строка или generic numbered confirmation остаются неизвестным экраном. Это сохраняет fail-closed commit, но не делает наличие заголовка обязательной частью протокола, которой реальный Codex не гарантирует.

Каталог и способность установленного контроллера применять его — разные факты. `/api/agent-models` поэтому отдаёт `controlCapabilities.codexEffortPicker = "tui-numbered-v2"`. Новый iOS-клиент при отсутствии capability (старый Mac build) сохраняет новые модели, но ограничивает effort исторически безопасными `minimal/low/medium/high/xhigh`; после обновления Mac `max/ultra` появляются автоматически. TUI остаётся финальным подтверждением конкретного выбора.

External `/api/inbox/runs` тоже может принести model/effort от клиента (например Voice Record). Эти значения применяются перед отправкой prompt'а и только когда Codex idle: если текущий turn busy, нельзя открывать `/model` посреди ответа ради внешнего запроса. Внешний bridge должен либо отправить/очередить prompt с уже активными runtime-настройками, либо явно вернуть ошибку применения, но не менять renderer-state так, будто Codex TUI принял новую модель.

Codex 0.145 использует ветвящийся `/model` flow. Quick-auto top picker существует только когда в снимке текущей сессии есть видимый `codex-auto-*`; при его отсутствии CLI сразу открывает полный список. Если top picker появился, `All models` тоже является семантическим переходом, а не фиксированной строкой №2; при отсутствии non-auto моделей его может не быть. Top picker может быть обрезан по высоте и показан без заголовка. После конкретной модели, включая `codex-auto-review`, обычные уровни находятся в `Select Reasoning Level`, а `max`/`ultra` выбираются через `More reasoning` → `Advanced Reasoning`. Парсер обязан:
- раскрывать `\x1b[<N>C` в реальные пробелы до `stripVTControlCharacters`, иначе строки слипаются;
- поддерживать узкий layout, где строка приходит как `2.` на одной строке, а `gpt-5.4` на следующей;
- считать ordinal только формой `N.` или `N. <label>`, но не `N.<text>`: перенос `(current: gpt-5.6-sol)` может оставить строку `5.6-sol)`, которая иначе превращается в фальшивую модель `6-sol`;
- сохранять физические индексы всех numbered rows, включая неизвестные строки: навигация идёт по расстоянию стрелок, а не по отфильтрованному массиву;
- различать `Select Reasoning Level`, `Advanced Reasoning` и появляющийся только по инициативе upstream Plan-scope dialog; новые имена не должны требовать изменения parser whitelist.

Первый распознанный numbered row не является доказательством готовности кадра: Ink может прислать частичную перерисовку, где нужная модель, `All models`, effort или `More reasoning` появятся следующим PTY frame. Каждый шаг ждёт именно свою семантическую цель. Исключение — доказанно обрезанный полный список с подсказкой `Ctrl+A view all`: такой кадр разрешает только переход к верхней части того же списка, а не выбор отсутствующей строки.

Обычный/default `Max` означает persistent `model_reasoning_effort=max` и не имеет права переписывать уже существующий `plan_mode_reasoning_effort`. Только если сам Codex в активном Plan mode показывает вопрос об области применения, приложение выбирает нужную строку и после подтверждения проверяет оба top-level значения. `Ultra` — conversation-only режим: он никогда не идёт через Plan-scope и считается применённым только после точного acknowledgement `Model changed ... ultra for this conversation`. Acknowledgement и восстановленный composer могут прийти в разных синхронизированных кадрах; требовать оба в одном render — ложный timeout уже успешного выбора.

Изменение picker'а затрагивает глобальный `~/.codex/config.toml`, поэтому операции разных вкладок сериализуются общей очередью, а перед физической записью повторно проверяются владелец writer и текущий screen mode. Частичная смена только модели/effort и quick-toggle разрешены лишь той сессии, которая уже владеет доказанными runtime-настройками; явная полная пара остаётся recovery-path. На свежей вкладке до первого rollout успешная полная пара хранится как одноразовое доказательство ровно для текущего PTY, launch и поколения. Его может принять только первый process-proven writer после durable SQLite binding; смена запуска/поколения удаляет proof, а `Ultra` никогда не восстанавливается догадкой из config.

Открытие `/model` нельзя делать через фиксированную задержку. Проваленные варианты из этой сессии:
- `safePasteAndSubmit('/model', fast:true)` работал, но оставлял `/model` видимым в input около секунды из-за встроенного ожидания перед Enter;
- raw write `/model\r` мог трактовать Enter как перенос строки в composer;
- ожидание только sync marker давало ложную ошибку, когда Codex уже эхо-отрендерил `/model`, но маркер не пришёл в нужном окне.

Финальный сигнал для Enter: после bracketed paste `/model` ждать кадр, где либо чистый текст содержит `/model`, либо raw содержит sync marker `\x1b[?2026l`; только после этого слать отдельный `\r`. Таймаут здесь только error-path. Та же логика применяется к стрелкам: каждое движение по picker'у ждёт новый PTY frame, а не «спит N миллисекунд».

`/fast` использует тот же live slash-command контракт, а не старый `safePasteAndSubmit(..., fast:true)`. Симптом регресса был пользовательский: кнопка выглядела как аналог смены модели, но работала медленнее и ошибочно блокировалась во время ответа. Production-отказ `codex_turn_busy` оказался нашим pre-write guard, а не ответом Codex: установленный Codex 0.145 принимает точный `/fast` как service-tier команду активного turn. Живые прогоны при `turnBusy=true` подтвердили оба acknowledgement — `Service tier set to priority` и `Service tier set to default`.

Разрешение узкое: во время streaming composer обязан быть доказанно пустым; реальный draft блокирует Fast, потому что `Ctrl+C` ради временного stash остановит текущий ответ. `hasDraft=null` также fail-closed. На idle live-процессе `hasDraft=true` по-прежнему можно stash'ить через native `Ctrl+C` и восстановить `ArrowUp`. Main повторяет current-frame и turn-state прямо у write-boundary, поэтому разрешение `/fast` нельзя обобщать на остальные slash-команды. После bracketed paste `/fast` main ждёт frame с echo/sync marker и только затем Enter; затем ждёт submit-frame с `Service tier set to priority/default` и возвращает `notice` из этого TUI-факта. В текущем rollout `019efacc-3dab-7883-9e3d-5736e26fba46` эта строка не сохранялась как отдельный Codex JSONL event, поэтому JSONL/history нельзя использовать как источник Fast feedback. Таймер здесь только ошибка, не «подождать 500ms и нажать Enter».

Сохранение draft'а при смене модели не должно идти через `Ctrl+G` external-editor. Этот путь правильный для явного `⎘ prompt | + clear`, но для picker'а он видимо меняет composer: пользователь видит `Save and Close`/очистку input'а, затем 5-секундный timeout и поздний restore. У Codex есть native stash: `Ctrl+C` на непустом composer'е очищает строку и кладёт draft в history, после picker'а его можно вернуть стрелкой вверх.

Перед любым `Ctrl+C` общий main/headless snapshot классифицирует текущий экран и composer как `hasDraft=true/false/null`; проверка повторяется после ожидания глобальной settings-очереди прямо у границы записи. `hasDraft=true` → `Ctrl+C`, затем `/model`; после успешной отправки `/model` восстановление делает `ArrowUp` два раза: первый элемент history — только что отправленный `/model`, второй — draft из `Ctrl+C`. Если `/model` не был отправлен, достаточно одного `ArrowUp`. `hasDraft=false` → не слать `Ctrl+C`, а открыть `/model` после очистки строки: на пустом Codex prompt raw Ctrl+C завершает TUI (`Shutting down...`), и следующий `/model` уходит уже в shell. `hasDraft=null` или доказанный picker/Rewind/startup → fail closed; speculative `Ctrl+C`, `Escape` и Enter запрещены.

Fail-closed live picker не должен означать «клик потерян», но и не должен лгать UI. Пользовательский выбор модели/effort — tab-scoped намерение для будущего launch, а live `/model` — попытка применить его к уже запущенному TUI. Native Codex разрешает `/model` во время active turn: Model и Effort в ControlBar остаются доступны, выбранная связка становится настройкой последующей работы сессии, а уже стримящийся ответ продолжает на прежней связке. Если composer-state неизвестен (`hasDraft=null`) или live `/model` flow вернул ошибку, ControlBar не меняет `codexModel`/`codexEffort` на вкладке: иначе toolbar покажет новую модель, хотя Codex TUI её не получил. В этом path только фокусировать терминал и писать diagnostic log `[CodexControlBar] live picker skipped ... reason=...`; следующий launch/non-default apply должен использовать только реально сохранённый tab-state. Прод-шрам: в 15:43 MSK сессия уже была определена, но Codex был в активном turn; прежний код видел только живой процесс, не `task_started`, и клик по effort выглядел как неработающий.

Пустой Codex composer может показывать dim-placeholder (`Find and fix a bug in @filename`, `Explain this codebase`). Plain-text парсинг видит это как обычный текст, но xterm cell-style помечает подсказку как dim; такой кадр обязан классифицироваться как `hasDraft=false` с source вроде `cursor:*:dim-hint`. Не хардкодить конкретные фразы подсказок: они меняются версией Codex, а стиль остаётся единственным смысловым признаком «это hint, не draft». Реальный пользовательский draft содержит non-dim cells и идёт по `hasDraft=true` stash-path.

Если первая строка после `›` пустая, это ещё не пустой draft. Многострочный Codex composer может начинаться со blank line или отступа, а полезный текст будет на следующей visual row; `getCodexDraftState` обязан сканировать продолжение и возвращать source вида `*:multiline-draft-row-N`. Не расширять это в «полный парсер prompt'а»: xterm-buffer подходит для yes/no перед Enter и короткого preview, но 500 строк с wrap'ами, prompt-like символами и copied Codex output проверяются только после отправки через rollout.

`Ctrl+G` / `codex:copy-input` нельзя использовать как preflight-истину перед `/model`. Этот путь нужен только для явного `⎘ prompt | + clear`: external-editor helper может вернуть пусто, пока xterm показывает dim-placeholder или draft, и сам заход в external-editor визуально меняет composer. Picker preflight читает только xterm-buffer; `Ctrl+G` остаётся пользовательской командой копирования/очистки, не диагностикой безопасности.

В dev-режиме Vite hot reload может перезагрузить модуль renderer-parser'а посреди живого терминала. Если реестр терминалов хранится в module-scope `Map`, ControlBar начинает видеть `no-terminal` при видимом Codex TUI и fail-closed пропускает live picker. Реестр xterm refs должен жить в process-wide singleton на `globalThis`; production reload стартует чисто, но dev/HMR иначе маскирует реальные picker-регрессии ложным `no-terminal`.

Диагностический контракт picker'а: пустой composer в логах выглядит как `hasDraft=false ... :dim-hint`; реальный draft — `draft-stash start` перед открытием `/model`, затем `draft-restore start arrowUp=2` после отправленной slash-команды (`arrowUp=1`, если `/model` не успел отправиться). При регрессе «с пустым input работает, с текстом не работает» сначала grep'ить эти маркеры, а не внешний editor-helper.

Generic Codex send paths не имеют права возвращаться на `fast:true`: `codex:send-command`, `codex:append-input` и MCP `/terminal/ai-prompt` для engine=`codex` должны писать один logical bracketed paste, а не дробить prompt на независимые paste-события. Но для внешнего submit `skipRenderWait:true` — намеренная граница, потому что render/sync marker не является надёжным pre-Enter ACK Codex composer'а. Source в логах нормализуется с префиксом `codex-*` (`codex-history-send`, `codex-history-queue`, `codex-mcp-ai-prompt`, `codex-append-input`), чтобы при следующем paste/composer-регрессе audit сразу показывал caller, а не общий `safePasteAndSubmit`. `codex-history-queue` — legacy diagnostic source для busy-handoff; он не означает физический `Tab(queue)`.

Windows-переносы внутри logical paste имеют отдельную доказанную границу: Codex PTY может материализовать каждый `CRLF` как два `LF` в rollout `event_msg.user_message`. Длина текста при этом совпадает, а fingerprint — нет. Post-Enter audit принимает только точную именованную трансформацию `expected.replace(/\r\n/g, '\n\n')`; обычный `CRLF → LF`, схлопывание пробелов/табов и любые другие изменения остаются mismatch. Симптом отсутствующего правила — одна реальная отправка уже видна канонической user-строкой, но рядом остаётся второй optimistic `CONFIRMING`.

Физический Enter в доказанном `Select Model` / effort picker подтверждает управляющий выбор, а не пользовательский prompt. Он не вооружает generic `CodexPromptInFlight`, не резервирует writer identity и не может оставить следующий History/Run after send в `codex_writer_identity_pending`. Классификация делается по свежему текущему frame у самой PTY write-boundary; migration chooser и native Rewind остаются у своих специализированных контрактов, а обычный composer без такого proof считается prompt submit.

`/terminal/ai-prompt` — такой же внешний Codex submit, как History/Run after, но он часто
приходит сразу после app restart. Поэтому перед paste он обязан пройти тот же startup/readiness
gate: `Update available`, trust prompt, directory chooser и `Starting MCP servers...` не являются
composer'ом. Если prompt уже дошёл до Enter, но audit не смог доказать ближайший
`event_msg.user_message`, статус должен быть `submitted_unverified`, а внешний caller не должен
слепо ретраить тот же текст. Практический шрам: build-install callback с коротким HTTP timeout'ом
повторял `Build install completed...` много раз, пока Codex стоял на update prompt; правильная
модель — дождаться input-ready внутри terminal layer и различать "не отправлено" от "отправлено,
но не доказано".

Прод-форензика 2026-06-15: если в логах есть `draft visual-probe ... hasDraft=false` и затем `skip Ctrl+C draft clear`, stash/restore pipeline не провалился — он вообще не запускался. В таком случае пропавший пользовательский prompt объясняется false-negative классификацией xterm visual-probe, а не тем что `Ctrl+C`, вставка `/model` или `ArrowUp` сломались. Для следующего repro нужны source-маркеры `cursor-empty-false` / `viewport-empty-false` с sampled rows: без них нельзя доказательно ответить, почему renderer решил что composer пустой.

## Stop и ввод

Stop для Codex идёт через общий `terminal:stop-ai-process`: сначала ищется прямой child-процесс `codex` под shell PID, затем Codex-specific fallback обходит descendants под shell, потому что реальное дерево может быть `shell → node /opt/homebrew/bin/codex → vendor codex binary`. Останавливать надо верхний найденный Codex-процесс через controlled kill-ladder. Важно не путать это с «просто нажать Ctrl+C в UI»: raw Ctrl+C в Codex зависит от состояния input'а и может очистить строку, открыть danger-zone или выйти не тем путём. `terminal:stop-ai-process` сам владеет последовательностью graceful `\x03` → проверка живости → SIGTERM → SIGKILL fallback; если stop-кнопка «вводит codex» или не меняет Continue-state, значит commandType/session lifecycle разъехались, а не надо добавлять ещё один keystroke.

Stop для Codex тоже публикует runtime `stopping` сразу после принятия stop intent. Это не `turn_aborted` и не `task_complete`: rollout может ещё не дописать хвост, process-tree lookup может ещё видеть descendant, а UI/API уже обязаны заблокировать send, rewind, edit-range и новый Continue. Финальный переход в `inactive` происходит только после доказанного exit/cleanup watcher'ов; до этого `busy:false` не означает input-ready.

Если Stop не нашёл Codex-процесс (`matches=0`), это всё равно финальный runtime edge, а не no-op для UI. Здесь `matches=0` означает только успешный снимок process-tree: при `unknown` Stop возвращает `process_lookup_failed`, снимает лишь временный `stopping` и заново публикует последнее подтверждённое `starting` / `active` / `busy`, не очищая session/readiness/watcher. Ветка доказанного no-process обязана форсить `terminal:command-finished`, сбрасывать `terminalCommandState`, инвалидировать process cache и публиковать `inactive`; иначе stale `commandRunning=true` делает вкладку «живой» без процесса и рисует ложный `Resuming Codex` после возврата на вкладку или клика Continue. Это не чинится startup timeout'ом: без fresh launch payload watchdog не заведён. Подробный шрам — `fix-interrupted-session-lifecycle.md::Runtime Stop без процесса`.

Codex Edit Range перед локальной rewrite/fork обязан проверить `codex:get-turn-state`. Если watcher видит активный turn (`task_started` без `task_complete` / `turn_aborted`), операция должна fail-closed и попросить дождаться завершения. Редактировать rollout во время активной генерации нельзя: Ctrl+C может показать уже выведенный в терминал хвост, который ещё не попал в JSONL, а последующая materialized rewrite закрепит неполную историю. Когда Codex-процесс жив, но turn idle, Edit Range использует тот же `terminal:stop-ai-process` graceful path и только потом пишет новый локальный rollout fork.

Close tab использует тот же stop-flow перед `terminal:kill`, даже когда confirmation dialog не показывается. Диалог завязан на busy/streaming loader, а не на `codexSessionId`: idle Codex с историей закрывается тихо, но live Codex foreground всё равно получает controlled stop, чтобы rollout JSONL успел дописать хвост. Cleanup `terminal:kill` обязан закрывать и session watcher, и turn watcher (`codexWatchers` + `codexTurnWatchers`); иначе после Esc/Stop/close вкладка может исчезнуть, а busy loader продолжит жить по старому watcher'у.

Close → `tab_history` — отдельная durable identity boundary. Архивирование выполняется до kill/удаления строки вкладки и игнорирует входящий `tab.codexSessionId` renderer'а: при живом процессе выигрывает текущий writer proof, иначе project-scoped `tabs.codex_session_id`, а отсутствующая/`NULL` строка остаётся `NULL`. Поэтому поздний renderer-кэш source A не может записаться в History после принятого writer B, и Shift+Cmd+T восстанавливает именно main-owned binding.

**Отказ архива без доказанного writer'а закрытие не отменяет — сначала стоп, потом повторная запись.** Условие отказа (`codex_archive_live_writer_unproven`) — процесс ЖИВ, в строке вкладки есть сессия, текущий writer не доказан; «жив» здесь не равно «отвечает», поэтому под него попадал и просто открытый простаивающий Codex. Симптом был именно молчаливым: закрытие обрывалось до того, как выставлялся loader, и средний клик по вкладке выглядел как несработавший — ни лоадера, ни диалога, ни ошибки, при том что ручная последовательность «ПКМ → Стоп → закрыть» работала.

Правило (`tabPersistenceTransactions.mjs::commitArchiveWithStopRetry`) автоматизирует ровно эту ручную последовательность: на ЭТОТ и только этот отказ выполняется `terminal:stop-ai-process`, затем архив повторяется. Остановленный процесс не может передать эстафету A → B, вопрос о доказательстве исчезает, и в историю пишется сессия из строки вкладки. Остальные отказы (`binding_read_failed`, `runtime_unknown`, `generation_changed`, `project_mismatch`) остаются жёстким стопом: там состояние действительно неизвестно, и остановка процесса его не прояснит. Провалившийся стоп сохраняет исходный отказ — вкладка и процесс остаются, как и раньше.

Два сопутствующих правила, без которых фикс неполон: loader закрытия поднимается ДО архива (Codex-путь может тратить на writer proof и повторную попытку заметное время, и клик без реакции читается как несработавший), а уцелевший после повтора отказ показывается тостом — молчаливый no-op и был исходным багом.

Codex не требует Claude-style `bridgeKnownSessions` / stale `~/.claude/bridge/*.json` guard'ов: у него нет statusline bridge, который может через секунду перезаписать вкладку древним sessionId. Это не означает, что любой локальный ID авторитетен: renderer snapshot, CLI resume-аргумент и SQLite имеют разные роли из секции «Источник session id» и не могут подменять live writer. Его durable transcript — rollout JSONL в `~/.codex/sessions/`; `resume`/`fork` восстанавливаются из него, не из RAM процесса. Поэтому второй риск при резком убийстве — in-flight кусок ответа мог быть виден в терминале, но не успеть попасть в JSONL. Парсер уже игнорирует битый хвост, а UI должен считать историей только то, что записано в rollout. Не переносить на Codex весь Claude bridge/pendingResume слой: нужная защита здесь — writer ownership + main-owned persistence и graceful-stop, а не Claude bridge-модель.

## Interrupted recovery и AutoResume

> Актуальный input-ready контракт: `Starting MCP servers` не блокирует
> точный composer+model/effort footer того же закрытого кадра и не
> разрешает watchdog Stop/restart. Старые абзацы ниже о controlled
> recovery относятся только к banner без composer-proof; `MCP startup
> interrupted` остаётся blocker.

Codex участвует в том же interrupted-overlay / AutoResume flow, что Claude, но источник live-сессии другой. У Claude main берёт `bridgeKnownSessions`; у Codex нет bridge-файлов, поэтому `codexKnownSessions` содержит только принятого writer из rollout/process proof. Ручной `codex-c` кладёт source в launch intent и публикует `starting`, но не заполняет live-map и не эмитит окончательный `session-detected` до writer proof. Для остановленной вкладки overlay Continue, AutoResume и Resume All берут durable ID из SQLite и запускают `codex:run-command {command:'codex-c', sessionId, cwd}`; после запуска этот ID снова становится только provisional source. Shutdown обязан сохранить отдельно доказанного live writer и durable binding, не повышая resume-аргумент до текущей сессии.

Codex startup может показать update prompt (`Update available`, `1. Update now`, `2. Skip`, `3. Skip until next version`). В Noted Terminal это тоже startup prompt, не input-ready: guard выбирает `2. Skip` (если выделен первый пункт — `↓` + Enter, если второй уже выделен — Enter) и заново сбрасывает readiness detection. `Skip until next version` не выбирается автоматически, потому что это меняет будущую политику обновлений, а не только разблокирует текущий запуск. Guard не должен зависеть только от caller'а запуска: `codex:run-command` и terminal MCP вооружают его до записи команды, а ручной повтор через shell history вообще обходит эти handlers. Для такого запуска разрешение на auto-skip восстанавливается лишь когда **последний синхронизированный PTY-кадр** содержит полный безопасный update picker и process tree одновременно подтверждает живого Codex descendant; произвольный текст `Update available` из scrollback не даёт права писать стрелки/Enter. Прод-шрам 2026-07-14: loader правильно видел `blocked:update-prompt`, но guard оставался `startupArmed=false`, потому что после Ctrl+C Codex был перезапущен через `↑ + Enter` в zsh.

Codex 0.145 добавил ещё один startup blocker — замену устаревающей модели: `Choose how you'd like Codex to proceed`, затем `1. Try new model` / `2. Use existing model`. Объясняющий текст и названия моделей уже менялись между Luna/Terra и формулировками `will be deprecated soon` / `is no longer available`, поэтому они не являются контрактом детектора. Auto-confirm разрешён только по свежему текущему экрану со стабильными заголовком, обеими строками выбора, footer'ом подтверждения и выделенным `1. Try new model`; выделенный второй пункт остаётся ручным решением. Непосредственно перед одним `Enter` main заново flush'ит headless-экран и проверяет тот же PTY, поколение команды и ревизию input. Любая пользовательская стрелка отменяет автоматику, а `Escape` здесь запрещён как cleanup: upstream тоже подтверждает им текущий выбор. Принятие миграции меняет не только модель, но и effort на default новой модели (`gpt-5.6-luna medium` в живом прогоне), поэтому исходные launch args после этого не являются доказательством effective settings; durable truth даёт первый rollout `turn_context`, который затем проецируется в состояние вкладки.

`terminal:input` от xterm — смешанный канал: публичный `onData` несёт и клавиатуру/paste, и автоматические ответы терминального протокола на запросы TUI (focus report, cursor position, цвета, device attributes). Последние нельзя считать доказательством, что пользователь взял управление startup picker'ом. Renderer переносит авторитетный origin из xterm `coreService.onUserInput`: только `user` отменяет ожидающий auto-skip, `terminal-response` продолжает guard, а отсутствующий/неизвестный origin остаётся fail-safe ручным. Не заменять это regex по escape-последовательностям: пользователь может вставить те же байты, а некоторые terminal replies пересекаются с клавишными CSI. Прод-шрам: на активных restored-вкладках protocol replies очищали guard за 158 мс до полного update frame, поэтому background-вкладки проходили автоматически, а видимая застревала в одном и том же меню.

Codex startup может показать trust prompt при первом запуске в директории: `Do you trust the contents of this directory?`, `Working with untrusted contents...`, затем `1. Yes, continue` / `2. No, quit`. В Noted Terminal это подтверждается тем же main-side PTY-frame guard'ом: main копит короткий startup-фрейм, нормализует ANSI cursor-forward в пробелы и пишет `\r` только когда увидел весь prompt и default highlight стоит на `1. Yes, continue`. Если выделен `2. No, quit`, auto-enter не срабатывает; пользовательское намерение не перетаптывается.

Первый запуск Codex без авторизации может показать меню `Welcome to Codex` с вариантами `Sign in with ChatGPT`, `Sign in with Device Code`, `Provide your own API key`. Это **не** startup prompt для автопрожатия: выбор меняет способ авторизации/биллинга, поэтому Noted Terminal не нажимает Enter и не делает MCP-restart. Такой экран классифицируется как `auth-required`: launch/readiness lifecycle завершается как ручной блокер, `Resuming Codex`/`starting` снимается через `command-finished`/`inactive`, но `codex:tui-ready` не эмитится и внешний API получает быстрый `codex_auth_required` вместо долгого ожидания input-ready. Пользователь остаётся в терминале и сам выбирает способ входа.

`codex-c` и `codex-f` могут показать directory chooser: `directory to resume this session`, `Session = latest cwd recorded in the resumed session`, `Current = your current working directory`, затем `1. Use session directory` / `2. Use current directory`. Это подтверждается тем же one-shot guard'ом, только для resume/fork окно длиннее. Если trust prompt был прожат первым, guard остаётся коротко вооружённым под следующий CWD chooser; после второго подтверждения очищается. Это не старый rejected Double Tap: fixed delay запрещён, потому что лишний Enter без меню уйдёт в Codex composer как пользовательский submit. Если выбран второй пункт, auto-enter не срабатывает.

После chained prompt'ов (`Update available` → directory chooser) raw PTY frame может прийти рваным: в логах видны обрезанные слова вроде `S ssion` / `Use c rrent`, detector честно отказывается нажимать Enter, а новых raw-байт уже может не быть. Поэтому startup auto-enter должен прогонять через тот же detector quiet-snapshot xterm buffer'а (main/headless first, renderer visible-buffer только fallback), где экран уже дорисован целиком. Это не fallback к “нажми Enter потому что похоже”: выбранный `Current`, третий пункт update, неполный chooser, MCP startup banner и `MCP startup interrupted` всё ещё fail-closed.

После любого startup prompt (`update`, model migration, trust, directory chooser) прежний `codex:tui-ready` считается недействительным. Следующий readiness должен прийти заново уже из чистого composer'а; иначе Rewind/History send могут начать ввод в промежуточный экран.

`Starting MCP servers ... esc to interrupt` — фоновый прогресс после того, как в том же закрытом кадре доказаны composer и model/effort footer. В этом состоянии `inputReady=true`, а любой ранее взведённый MCP-watchdog очищается. Banner без composer-proof ещё может быть startup blocker и проходить ограниченный recovery; `MCP startup interrupted` всегда остаётся отдельным blocker. Esc не используется как recovery.

Но сам текст `Starting MCP servers` не является разрешением на restart. Codex может показать такой же banner уже после отправки prompt'а, когда turn реально стартует и загружает tools. Перед watchdog restart нужно доказать именно startup-фазу: нет `task_started`/busy turn, нет pending paste audit, нет `CodexPromptInFlight` окна после safePaste/Enter до первого rollout edge, нет ожидания matching `user_message`, нет queue handoff и нет activity-open interval. `CodexPromptInFlight` начинается перед PTY submit, помечается `submitted` после Enter и чистится по watcher close, TTL или `submit-not-sent`; это закрывает узкий промежуток, где `task_started` ещё не записан, но prompt уже физически ушёл. Если любой prompt/turn уже in-flight, watchdog должен skip/clear и ждать rollout edge (`task_complete`/`turn_aborted`/matching `user_message`), иначе он убьёт живую сессию посреди пользовательской отправки. В логах искать `[CodexPromptInFlight] begin/submitted/clear` и `[CodexTuiReady] ignore mcp-startup blocker ... reason=prompt-or-turn-in-flight|already-ready|not-startup-lifecycle`.

Тот же принцип действует внутри успешного Rewind. После `Enter` в transcript overlay Codex может на один кадр показать recoverable startup-like interstitial (`Update available`, chooser, MCP text), а затем всё равно успешно префиллить target prompt и пройти `grab`. Такой confirm-frame нельзя сразу превращать в `codexTuiReadyTabs.delete()` и SSE `status=starting`: это рисует ложный `starting` на iOS/desktop посреди успешного Rewind. Правильный контракт — логировать frame и отложить clear/publish до исхода grab: successful grab возвращает/сохраняет `active`, unrecovered grab/failure уже может surface'ить not-ready/error.

Watchdog MCP-startup не должен жить внутри guard'а startup prompt'ов (`Update available`, trust, directory chooser). Прод-шрам 2026-06-20: `Update available` был auto-skipped, guard сократил TTL до 15 секунд, MCP banner появился через ~2 секунды, и на 13-й секунде watchdog ещё писал `still waiting`; затем prompt guard сделал `clear reason=ttl` и снял restart до порога 15 секунд. Симптом: вкладка часами остаётся в `starting/resuming`, но после клика по вкладке visible-buffer распознаёт уже готовый Codex prompt и статус становится active. Поэтому MCP watchdog — отдельное main-side состояние на tab, очищается только при реальном `tui-ready`, новом launch/stop/kill или явном restart-limit; для `codex-f`, если watcher уже нашёл новую fork-сессию, retry запускает `codex-c` этой новой session id, а не создаёт второй fork.

Важно, что watchdog находится в main-side readiness/launch слое, а не в iOS, History или отдельной кнопке Continue. Тогда stopped-session Rewind, `/api/terminal-tabs/:id/send`, Inbox run, AutoResume и ручный Continue получают одинаковое поведение: перед вводом prompt'а они либо видят чистый Codex composer, либо fail/restart по одному и тому же доказанному состоянию. Логи искать по `[CodexMcpStartupWatchdog] seen/still waiting/restart begin`.

Stop зависшего MCP-startup и replacement — одна main-owned lifecycle-транзакция. Между ними нельзя отпускать per-tab очереди: Stop намеренно сохраняет публичный `starting` без серого промежутка, поэтому отдельный следующий launch примет этот же сохранённый статус за чужую foreground-команду и заблокирует сам себя как `shell_not_idle`. Успешный Stop выдаёт одноразовый handoff только точной комбинации watchdog/PTY/terminal generation/run sequence/input revision/старого launch id и доказанного отсутствия процесса. Replacement получает новый launch id, удерживает input-barrier до синхронной записи команды и перед записью повторно проверяет отсутствие процесса. Любой новый ввод, другая команда, новый процесс, смена PTY или поколения отменяют handoff. Если повторный proof временно недоступен, запуск не выполняется, но точное старое поколение всё равно завершается по уже полученному Stop-proof: вечный loader не сохраняется. Это правило относится и к Run After на остановленной вкладке: Run After уже умеет `Start/Continue → input-ready → один submit`; он не должен реализовывать отдельный restart или обход shell-admission.

Для hidden/background Codex-вкладок visible xterm buffer — диагностический канал, а не обязательный источник ready. Если renderer не mounted (`no-terminal`) или отдаёт старый кадр, main всё равно может признать composer готовым по raw PTY buffer + живому Codex descendant process, но только когда raw-frame не содержит startup blockers. Обратная ошибка тоже опасна: если visible-buffer доступен и доказывает update/trust/directory/MCP blocker, raw-ready не должен его перетаптывать. Пользовательский симптом рассинхрона: вкладка остаётся `starting/resuming` до клика по ней, потому что only-visible проверка просыпается только после mount, или наоборот Rewind/API начинают ввод во время `Starting MCP servers`. Raw/visible tail также может содержать строки из transcript'а или старого preview; readiness/restart нельзя выводить из произвольного текста в хвосте, только из текущего TUI frame и фазы запуска.

С 2026-06-20 общий screen/draft proof для фонового Codex сначала идёт через main-side `@xterm/headless` mirror: main пишет в него тот же PTY stream и может читать logical rows/cell-style без mounted React terminal. Renderer snapshot остаётся UI/fallback/debug каналом, а не владельцем истины для Rewind, History Send, mobile/iOS params и Terminal API. При аудите похожих багов сначала grep'ать прямые renderer-зависимости (`terminalRegistry.getVisibleSnapshot`, `getCodexDraftState`, `waitForCodexDraftState`) и спрашивать: может ли этот path запускаться из hidden tab/API/History? Если да, renderer-only proof снова вернёт симптом «заработало только после клика по вкладке» или «отправка/rewind пропустили чужой draft».

Launch payload (`codexLastRunCommandPayload`) — одноразовый retry-token текущего запуска, не durable признак live-сессии. Его нужно очищать на `command-finished`, PTY exit, terminal kill и manual stop; MCP-watchdog internal stop сохраняет payload только на время controlled restart и перед повторным запуском сверяет `launchId`. Если пользователь остановил/закрыл вкладку между stop и restart, watchdog обязан отмениться. Симптом старого шрама: manual Stop гасит Codex, но старый watchdog через мгновение снова запускает процесс или продолжает слать `starting` в API/iOS.

Process-tree lookup для Codex дорогой, особенно когда список проектов/iOS часто опрашивает много hidden tabs. Прод-диагностика 2026-06-20 показала десятки `ProcessTreeLookup` по 50-90ms на фоне; это читалось как лаги всего Mac при открытом проде. Допустим короткий main-side cache (порядка 2s), но он должен инвалидироваться на launch/exit/kill/ready, иначе stale process-state начнёт врать тем же `starting`/process-bar каналам.

Тонкий teardown-шрам: во время graceful quit `before-quit` сначала early-mark'ит активные AI, потом шлёт Ctrl+C живым CLI. Codex может успеть чисто выйти и сгенерировать OSC 133 D **до** `will-quit`. Если в этот момент `command-finished` очистит `codexKnownSessions`, финальный `will-quit` сделает clear stale `was_interrupted=1` и уже не re-mark'нет вкладку — после рестарта overlay пропадёт, хотя session была активна при закрытии. Поэтому `clearCodexKnownSession(tabId, 'command-finished')` запрещён пока `_gracefulShutdownInProgress=true`; map держится до финального clear+mark pass. Это Codex-аналог bridge lifecycle, но без stale-bridge takeover риска.

Микрофонная диктовка для Codex использует тот же PTY-путь, что Claude PTY: `terminal:paste` с `submit:false`, чтобы текст оказался в composer и юзер мог его отредактировать перед Enter. SDK-путь сюда не подходит: у Codex нет отдельного React composer'а внутри приложения.

`⎘ prompt | + clear` для Codex использует тот же external-editor flow, что Claude: UI триггерит Ctrl+G, helper `noted-code-grab.js` читает tempfile и либо копирует текст без очистки, либо атомарно копирует+truncates input в `grab` mode. Split-pill показывается только когда Codex PTY сейчас жив: старый `codexSessionId` означает историю/Continue, но без запущенного TUI composer'а нечего копировать или очищать.

Codex запускается двухслойным деревом процессов: shell → `node /opt/homebrew/bin/codex ...` wrapper → vendor binary `.../@openai/codex-*/bin/codex`. External-editor helper наследует `ppid` именно vendor binary, а не direct child wrapper. Поэтому main-side lock/socket registration должен обходить descendants под PTY shell и ставить `/tmp/noted-grab-<pid>.json` для всех Codex PID'ов, начиная с самого глубокого. Симптом неправильного lock'а: клик `⎘ prompt` или `+ clear` открывает пользовательский редактор (например Sublime), input не копируется и не чистится, а helper-log показывает `LOOK lockPath=/tmp/noted-grab-<vendorPid>.json existsBeforeRead=false` и `PASSTHROUGH mode=null`.

Та же wrapper-деталь важна для tab close warnings: `terminal:hasRunningProcess` должен отдавать full command-line, не только short `comm`, иначе direct child `node` будет выглядеть как обычный Node/script-процесс. Пользовательский симптом — Codex-tab с живым CLI получает warning как обычный процесс или, наоборот, обычный `node` внутри AI-typed tab закрывается без предупреждения.
