# Область ответственности и отложенное состояние вкладки

## Контракт

Вкладка имеет отдельно сохраняемую область ответственности (`responsibility`),
связанные рабочие Markdown-файлы и последовательность обновлений контекста.
Обновление не запускает агент, не отправляет новый turn и не создаёт orchestration-run.
Открытие вкладки только показывает чипы обновлений. Следующее настоящее сообщение
забирает их независимо от источника: History Enter, Run after, Terminal MCP,
Project API, Inbox или служебный follow-up оркестрации.

Responsibility — одно заменяемое описание, а не накапливаемая лента. Оно
доступно через API/UI, но `prepare` не добавляет его автоматически в каждый
prompt. Рабочий файл сам не заполняет responsibility. Очередь обновлений
сохраняется отдельно по tabId: переименование или изменение описания не
пересматривает её смысл и не очищает старые уведомления. Подтверждённая
доставка доказывает получение текста, а не применение каждого факта моделью.

Исключение для standalone slash-команды использует общую grammar с History
и delivery audit. Абсолютный путь в начале (`/Users/...`) и многострочный
prompt не являются этим исключением и получают pending context. Старый
`startsWith('/')` молча пропускал подготовку таких обновлений; нельзя
восстанавливать его ради «быстрой проверки команды».

В подготовленном сообщении обновление занимает самостоятельную обёртку
`<saved_prompt name="..." context-update-id="...">`. History восстанавливает
чип обновления по этой обёртке, даже если отдельной presentation metadata нет.
Копирование и Rewind сохраняют идентификатор обновления вместе с текстом.
Обычные библиотечные промпты сохраняют своё оформление.

Связь рабочего файла используется также в Timeline: редактирование текущего
связанного пути даёт существующий карандаш на породившей итерации, даже вне
`docs`. Вложение само по себе и получение файлового context-update карандашом
редактирования не являются. Отметка не запускает агент и не потребляет pending
update; механизм и границы — `fact-timeline.md::Docs-индикаторы`.

При вставке копии сообщения учитывается уже ожидающий pending update по его
ID/member ID и точному содержимому. Совпавший чип второй раз не добавляется;
изменённая версия остаётся отдельным вложением, а dismissed update не считается
присутствующим в composer. Paste не подтверждает доставку и не потребляет pending
update. Асинхронный импорт изображения сверяет актуальный контекст исходной вкладки
в момент завершения, а не snapshot до начала копирования. См.
`fact-clipboard-tools.md::Копия сообщения обратно в History composer`.

Явный `publish_context_update` предназначен для другой вкладки. При совпадении
получателя с известным отправителем MCP отклоняет вызов до HTTP; main также
возвращает `context_update_self_target` (400), не создавая update и не меняя
revision. Внешние клиенты без собственной tab identity по-прежнему могут
публиковать в явно выбранную вкладку. Собственные get/set responsibility
остаются доступны. Отсутствие своего рабочего Markdown не требует self-chip.

признаком типа. Действие «вернуть обновление в текст» тоже сохраняет полную
обёртку с ID, как у исходного pending-чипа; у обычного prompt остаётся прежнее
разворачивание тела. Возврат в draft сам по себе не переоткрывает старую
delivery-квитанцию и не создаёт новое main pending-update.

## Хранение и доставка

Main-owned `TabWorkContext` использует отдельные таблицы в существующей SQLite:

- `tab_work_context`: описание и ревизия;
- `tab_context_files`: последняя наблюдавшаяся версия связанного Markdown;
- `tab_context_updates`: отдельные сообщения/изменения файла в исходном порядке;
- `tab_context_handoffs`: неизменный набор обновлений, подготовленный полный текст и его хеш для конкретной отправки.

Полное сохранение вкладок не пишет в эти таблицы и не может затереть более свежее
обновление. Закрытие/reopen сохраняет состояние по прежнему tabId. Явное
обновление однозначно архивированной вкладки не восстанавливает её процесс.

Подготовка убирает выбранные чипы из composer band (`pending -> sending`).
Точное подтверждение получения user-message делает их `delivered`.
Доказанный отказ до отправки или точный provider-not-accepted возвращает их в
`pending`. Неопределённая доставка остаётся привязана к прежней квитанции;
новый запрос не получает права повторно отправить эти же скрытые обновления.
Обновления, пришедшие позже подготовки, остаются для следующего запроса.

HTTP готовит контекст до подсчёта identity/хеша отправки и передаёт признак
`workContextPrepared` renderer. Он не дописывает чипы к уже подготовленному
сообщению. History/Run after готовят текст до создания временной строки History.
Старая очередь, существовавшая до введения функции, сохраняет свой исходный текст.
Slash-команды не забирают рабочий контекст: добавление префикса изменило бы их смысл.
History также исключает обычные prompt-чипы из transport такой команды и после
отправки оставляет их над пустым input. Поэтому `/compact` доходит как отдельная
системная команда, а все отложенные материалы ждут следующего обычного сообщения.

Отдельный source14.09 completion fact использует ту же подготовку/неизменный
handoff, но не является file-update или новым orange chip. Причина: скрытие
неподтверждённого уведомления не сообщает модели, что её задача уже завершена.
Run-store проецирует только terminal facts её текущей подтверждённой session;
подготовка обычного prompt резервирует до8 ID в `continuation_facts`. Старый
payload остаётся byte-stable после restart/поздних completion. Unknown не
разрешает новую подготовку тех же фактов, proven failure освобождает
резервацию. Явный Retry другого proven-unsent frozen prompt может повторять
его read-only справку — это разрешённое пользователем15.09 исключение, не
новый запрос результата. Ответ не читается, UI не пробуждается; notification/slash исключены.
Полная граница — fact-оркестрация-вкладок::Скрытое уведомление.

Неизменность prepared prompt не является разрешением отправить его в другую
сессию. `prepare` возвращает старый текст также для чтения/replay receipt, а
исполнение повторяет source guard до действия и у physical chunk/Enter. Не
«лечить» stale context удалением префикса из старого handoff: это изменит хеш
неизвестной попытки. Новая отправка другого владельца получает новый handoff.

## Markdown

Рабочим Markdown считается существующая дочерняя file-вкладка с расширением
`.md`/`.markdown` и `visualParentTabId`, указывающим на AI-вкладку. Новая связь
устанавливает исходный снимок; последующие изменения сравниваются по содержимому.
Наблюдение за каталогом переживает атомарную замену файла. Повторное чтение при
подготовке отправки закрывает пропущенные filesystem-события, а сохранённый
снимок позволяет заметить изменения между перезапусками.

Уведомление содержит путь, хеши старой/новой версии и отдельные изменённые
участки с двумя строками контекста, включая удалённый текст. Сдвиг строк после
вставки не считается их изменением. Bounded Myers diff ограничен по edit-distance
и числу операций; для действительно большой переписи безопасный fallback
остаётся одним полным диапазоном и не отбрасывает байты. Недоступный файл или
размер больше 2 MB дают видимый отдельный context notice, а не пустой успех.

Число чипов/изменённых строк не является лимитом объёма следующего prompt:
в него входят добавленный и удалённый текст. Live-проверка27.09 у tab171
показала один пакет `пхукет-база.md` на279615символов; известный source2800 —
другая вкладка с тем же названием. Совпадение имени не доказывает self-update.
Сейчас такой пакет передаётся полностью; `get_tab_context` после delivered
его не возвращает. Переход на краткую ссылку без отдельного чтения сохранённой
версии нарушил бы доступ к данным и не является действующим контрактом.

Все ожидающие автоматические изменения Markdown одной вкладки объединяются в
один логический файловый пакет. Свободные DB-записи физически объединяют версии:
следующее изменение того же пути обновляет конечную версию, новый путь добавляет
файл. Запись, уже участвовавшая в handoff, физически остаётся неизменяемым member:
старый retry обязан получить прежний подготовленный payload. Это внутреннее
ограничение больше не просачивается в UI. Main группирует все pending file-members
одного статуса под стабильным логическим ID, а API отдаёт реальные `memberIds` и
упорядоченные `sections`. При одном уникальном пути заголовок называет файл, при
нескольких — их количество; участки и строки суммируются. Ручные
`publish_context_update` в эту группу не входят.

Каждая секция сохраняет собственные версии и собственные source-вкладки. Её
текст не дублируется в JSON: `textStart/textEnd` адресуют единственную общую
строку `text`. Поэтому подробный `get_tab_context` не платит двойной объём за
UI-структуру. Поздний member того же или другого файла меняет состав группы, но
не её логический ID.

Если пользователь перенёс update-chip в input, последующие изменения могут
обновить группу до Enter. При подготовке отправки main узнаёт как логический ID,
так и любой прежний member ID: все найденные старые обёртки заменяются одной
актуальной, а не дублируются рядом. Новый handoff сохраняет один grouped wrapper,
но перечисляет все реальные member IDs для точного confirm/release. Уже
существующий handoff продолжает возвращать свой прежний prepared prompt.

Собственные успешные структурированные Edit/MultiEdit/Write/apply_patch
читаются через существующие Claude/Codex projectors. Подавление уведомления требует точного
совпадения перехода содержимого. Для Codex `patch_apply_end` передаёт исходные
координаты unified diff: они применяются к конкретной версии файла, поэтому
повторяющийся `old_string` не превращает собственный edit в ложное внешнее
обновление. Короткая цепочка ожидаемых версий сохраняет порядок нескольких
собственных edit, даже если filesystem watcher объединил их в одно чтение. Если
после доказанного собственного A→B уже появился внешний B→C, из пакета убирается
только A→B, а B→C остаётся видимым.

Явные файловые записи внутри `Bash` проходят тот же projector. Общая History
grammar распознаёт, в частности, `Path(...).write_text/write_bytes`, write-mode
`open(...)`, `sed -i`, `cp/mv/rm/touch/truncate`, `tee` и вывод в файл, но простой
запуск Python или `read_text` записью не считается. Для shell нельзя безопасно
вычислить итоговый текст из команды, поэтому доказательство другое: на записи
вызова запоминается точная исходная версия связанного пути, успешный result
ограничивает интервал операции, а filesystem watcher даёт физический переход
этого же пути. Переход принимается только при одном возможном operation и одной
версии с совпавшими source hash, path и mtime внутри интервала. Своя версия
вычитается, чужая получает source-вкладку. Если перед собственной shell-правкой
уже был внешний A→B, из суммарного A→C снимается только доказанный хвост B→C.
Failed result, запоздалый replay, несколько возможных вызовов, неразрешимый путь
или конфликт с уже доказанным автором ничего не списывают.

Вычисляемый `tools.apply_patch` внутри Codex `exec` использует тот же owner
физического перехода, если JavaScript AST доказывает неизменный абсолютный
target. Поддерживается верхнеуровневый awaited-вызов с literal `const` path;
само тело патча может строиться из прочитанного текста. Скрипт не исполняется
для анализа. Условный вызов или вызов без await, shadow/reassignment, неизвестный путь,
ошибка или yielded exec не получают такого proof. Вызов закрепляет исходный
hash, завершение — временную границу; только единственный подходящий переход
снимает собственный diff. Ранний внешний prefix остаётся по прежним правилам.

исторические операции автоматически заново не исполняются и не присваиваются.

writer в одном интервале делают доказательство неоднозначным. Result всё ещё
требует успешный однозначный operation↔transition match. Допуск назад только
2 мс на точность mtime: внешняя версия непосредственно перед call не
присваивается агенту.

Для авторства TabWorkContext подписывается не на все сохранённые истории, а
только на точных живых writer Claude/Codex, пока существует связанный Markdown.
Появление, смена и исчезновение writer обновляют подписки event-driven. Успешная
структурированная правка другой вкладки не скрывается: её exact before/after edge
добавляет вкладку, session и operation к файловому пакету. Цепочка таких edges
отделяет полностью объяснённый переход от остатка неизвестного происхождения.

доказанно дописала файл в 01:40 UTC, затем tab3314 сама изменила другие места
в 01:43 и 01:45. Раньше эти собственные Edit накладывались на общий диапазон
версий, и уже доказанный источник переставал покрывать новый hash: чип показывал
имя tab4875 вместе с ложным `Внешнее изменение`. Теперь структурированная
собственная правка переносится на обе версии ожидающего изменения только при
точной версии «до» из вызова, успешном результате и совпадении вычисленного
конца с наблюдаемым файлом. Для одного доказанного source-владельца его переход
переносится на новые версии, поэтому несколько последовательных собственных
правок не добавляют ложный неизвестный остаток. Перекрытие чужого фрагмента
или недостаточное доказательство по-прежнему оставляет неопределённость.
В раскрытии grouped update каждая неизменяемая версия показана отдельной секцией
`участки · строки`; карточки рядом принадлежат именно этой секции, а не всему
суммарному файлу. Известные вкладки остаются структурированными в API
(`sections[].sourceTabs`); клик использует обычную активацию вкладки, поэтому
переходит и в её workflow, и в её окно. Ручной
`publish_context_update` использует тот же source-контракт. Shell без явного
файлового target или однозначной пары call/result↔version, ручной редактор и
другой filesystem writer остаются `Внешнее изменение`.

Открытый отложенный чип показывает структурированные source-вкладки. После
отправки прежний History popover показывал только буквальный `Sources:` внутри
`<saved_prompt>`, без кликабельной карточки. Теперь при открытии отправленного
context-chip main сопоставляет полный текст сообщения с сохранённым exact
handoff hash и его неизменяемыми member IDs, восстанавливает source-вкладки и
секции, а History использует ту же карточку и навигацию. При несовпадении
текста или неоднозначном handoff остаётся буквальный просмотр; копирование и
текст, полученный моделью, не меняются. Уже отправленная версия на скриншоте
сохраняет старую строку `Внешнее изменение` как исторический снимок, но её
известная вкладка-источник получит кликабельную карточку после установки новой
сборки.

Успешное чтение связанного файла самой вкладкой означает, что повторно отправлять
ей уже увиденный фрагмент не нужно. Система принимает только доказанный `Read`:
результат должен быть новее pending-пакета, относиться к точному пути, содержать
текущие строки без преобразования и завершиться без ошибки. Прочитанный диапазон
встраивается в отдельную «уже известную» базовую версию; следующий diff содержит
только оставшиеся участки. Полное точное чтение убирает файл из чипа, а если он
был единственным — весь чип. Чтение во вкладке-авторе, старый transcript record,
ошибка, `awk/jq`-преобразование или неоднозначный shell-output ничего не списывают.
Поздняя внешняя правка сравнивается с уже известной базой, поэтому прочитанные
строки не появляются снова. То же монотонное сокращение разрешено member-записи,
закреплённой за старым handoff: старый prepared payload не меняется и содержит
не меньше информации, чем оставшийся pending residue.

Шрам 10.09: один пакет содержал удаление 10 строк и две однострочные замены на
удалённых позициях. Прежний prefix/suffix envelope показал `399 строк` и отправил
модели 399 старых + 389 новых строк, хотя логически были изменены 3 участка и
12 строк. Multi-hunk presentation теперь отправляет только эти участки с малым
контекстом; legacy pending-пакет пересчитывается при startup-консолидации.

Один путь, mtime или близкий момент времени не доказывают авторство. Неуспешный
tool, ручная правка и shell-команда без явного target, исходной версии и точного
результата остаются видимыми. Размер старой истории не влияет на работу: main подписан на общий
incremental transcript service и обрабатывает только новые записи, а файл читает
по filesystem-событию и контрольной проверке перед отправкой.

## UI и MCP

Описание находится первой строкой над планом задач. Оно использует установленный
предел ширины панели; первый клик раскрывает абзацы вниз, повторный сворачивает
до одной строки с ellipsis. Изменение ширины остаётся общей существующей ручкой.

Неподвижный светло-фиолетовый `RefreshCw` у нижнего левого края карточки
показывает наличие pending updates и в sidebar, и в окне. Context-percent и
Fast остаются сверху слева; квадратики задач начинаются правее отдельного
нижнего слота обновления. Выступ ограничен зазором между карточками.
Жёлто-оранжевый убран29.09 по просьбе пользователя: рядом с процентами он
читался как предупреждение о заполнении контекста. Полностью фиолетовый чип
тоже не выбран: он сливался бы с обычными сохранёнными промптами.

Чип обновления имеет нейтральный тёмный корпус, светлый текст и отдельный
фиолетовый сегмент под иконку. Этот профиль общий для pending, восстановленного
draft и отправленного History; иконка не вращается, потому что обозначает
наличие информации, а не выполняемую синхронизацию. Чипы находятся в общей
полосе над input перед обычными prompt-чипами; взаимный порядок обновлений
сохраняется, включая пришедшие позже. Они используют тот же `ComposerChip`,
потолок 168px и высоту; сегмент под иконкой не увеличивает габариты. Полоса
сохраняет отступы рамки и место справа для кнопок History, переносится вверх максимум на три строки и
после этого сжимает подписи с ellipsis без horizontal scroll или скрытых
элементов. Полный заголовок также находится в native tooltip. По клику первая
строка показывает суммарные файл/участки/строки, ниже каждая секция показывает
свой объём, карточки известных вкладок и отдельную некликабельную метку внешнего
остатка. Обновления и обычные prompt-preview входят в один видимый порядок. Navbar
показывает icon-only `←/→`, перенос в input, копирование и закрытие; смысл
доступен через `title`/`aria-label`. Только у context update рядом с `X`
есть корзина: она переводит все `memberIds` логической группы в необратимый
статус `deleted`, убирает их из очереди и не участвует в Undo. Tombstone остаётся
для idempotency: повтор того же `requestId` не воскресит удалённый чип. На
свёрнутом чипе нет крестика и переноса; средняя кнопка
лишь скрывает update без `Sure?`. Это скрытие записывается в общую CodeMirror Undo-историю:
`Cmd+Z` возвращает update через main API, `Redo` снова скрывает. Обычные
prompt/paste-чипы уже используют ту же историю, поэтому порядок общий с
последующим редактированием текста, а не отдельный глобальный undo-стек. Undo
хранит точный список members удалённой группы: если в паузе пришёл новый member,
Redo не имеет права удалить невиденное пользователем обновление.

В History ведущая chip-band использует `fit-content` и `align-self:flex-end`.
Она не задаёт циклическую процентную ширину shrink-to-fit user-column, поэтому
заканчивается на правом краю текстового бабла и не меняет позицию Copy/Rewind у
коротких сообщений.

Terminal MCP:

- `list_tab_contexts`: описания и связанные файлы текущего/выбранного workflow;
- `get_tab_context`: одна вкладка, её файлы и обновления;
- `set_tab_responsibility`: согласованное с пользователем описание;
- `publish_context_update`: отложенное уведомление без отправки и запуска агента.

HTTP: `GET /api/tab-contexts`, `GET /api/terminal-tabs/:id/work-context`,
`POST .../work-context/responsibility`, `POST .../work-context/updates`.
Для native карточек есть отдельная read-проекция того же owner: `summaries`
возвращает revision/count без texts, file reads и syncLinks. Она сохраняет
grouped-file семантику `presentUpdates`: несколько валидных pending file members
дают один count, sending не участвует. SOURCE05.10 передаёт это внутри общего
`cardSignals` у `/api/projects/:id/tabs`; прежний onChanged будит coalesced
project-activity metadata, а не запускает агент. Полный work-context API и
delivery membership не меняются. Wire/ordering — `fact-mobile-web.md`.
Skill `terminal` и общий `claude-dev/02-instructions.md`, step 6, задают
порядок работы агента. При начале/возобновлении он получает собственную
актуальную ответственность и список рабочих файлов, если их ещё нет в
контексте; `workingContext` из `current_context` заменяет повторный
`get_tab_context`. Поле ответственности само в каждый prompt не вставляется.
Явное решение пользователя о постоянной зоне сохраняется в том же ходе;
разовый баг, название и чужая файловая правка зону не расширяют.

После проверенного этапа агент передаёт только новую информацию, важную
другому владельцу. Известный tabId читается адресно; каталог своего/явно
выбранного workflow и затем allWorkflows нужны по мере расширения поиска,
не после каждой реплики. В каталоге нет семантического query и тел файлов;
подробный get_tab_context включает полный pending/sending-текст.

Связанную подтверждённую дельту может внести другая сессия: прочитать текущий
участок подходящего linked Markdown и точечно изменить его, сохранив чужие
правки. Это не передаёт ей владение темой. Если подходящего файла нет,
используется одно ручное уведомление другому владельцу; недоступный файл
или неизвестный исход записи не являются разрешением продублировать факт.
Получатель сверяет контекст с текущим поручением и актуальным состоянием,
не применяет уже записанный diff повторно и не принимает чип за новое задание.
Это инструкция агенту, не автоматический обход вкладок приложением.
