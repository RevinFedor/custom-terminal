# ОПЫТ: Решение конфликта гидратации Markdown (pre inside p)

### Симптомы
В консоли разработчика (DevTools) появляются красные ошибки `Hydration failed`, а при получении ответов от нейросети с блоками кода текст может "прыгать", мерцать или отрисовываться некорректно (например, код оказывается внутри текстовой строки).

## Суть проблемы
Библиотека `react-markdown` по умолчанию оборачивает текстовые блоки в теги `<p>`. Однако, если AI возвращает блок кода (который рендерится как `<pre>`), React выбрасывает ошибку валидации DOM: 
`In HTML, <pre> cannot be a descendant of <p>.`
Это приводит к нарушению гидратации и потенциальным багам отрисовки в Electron/React 19.

## Решение
В компоненте `MarkdownRenderer.tsx` переопределен рендерер для параграфа (`p`). Система проверяет наличие блочных элементов (`pre`, `div`) среди дочерних узлов.

### Логика проверки:
Если внутри параграфа обнаружен `pre` или `div`, вместо тега `<p>` используется `<div>`. Это сохраняет валидность HTML-дерева.

```tsx
p({ children, node }) {
  const hasBlockChild = node?.children?.some((child: any) =>
    child.tagName === 'pre' || child.tagName === 'div'
  );

  if (hasBlockChild) {
    return <div className="mb-3 last:mb-0">{children}</div>;
  }
  return <p className="mb-3 last:mb-0">{children}</p>;
}
```

## Результат
- Исчезли ошибки в консоли DevTools.
- Корректная отрисовка смешанного контента (текст + код).
- Стабильная работа `react-virtuoso` при прокрутке длинных ответов.

# ОПЫТ: Рендеринг Inline-кода (react-markdown v9)

## Проблема
После обновления до `react-markdown` v9+, фрагменты inline-кода (одиночные обратные кавычки `` `code` ``) стали отображаться некорректно: они переносились на новую строку или ломали верстку параграфа.

## Причина
В предыдущих версиях `react-markdown` передавал проп `inline` в компонент `code`. В версии 9 этот проп был удален. Теперь компонент `code` используется как для inline-вставок, так и для больших блоков внутри `<pre>`.

## Решение
В компоненте `MarkdownRenderer.tsx` внедрена проверка родительского элемента. Если `code` находится внутри `pre`, он считается блочным. В противном случае — inline.

### Логика:
```tsx
code(props) {
  const { children, className, node, ...rest } = props;
  const match = /language-(\w+)/.exec(className || '');
  
  // Если нет родителя 'pre' — это inline код
  if (node?.parent?.tagName !== 'pre') {
    return (
      <code className="bg-white/10 px-1 py-0.5 rounded text-sm font-mono" {...rest}>
        {children}
      </code>
    );
  }

  // Блочный код с подсветкой...
  return <SyntaxHighlighter ... />;
}
```

## Результат
Inline-код корректно вписывается в поток текста, имеет аккуратный фон и не вызывает ошибок гидратации.

# Experience: Markdown Editor Recreation Fix

### Симптомы
При вводе текста в редакторе заметок (Notes) или InfoPanel курсор постоянно "прыгает" в начало строки или в конец текста, фокус ввода теряется после каждого нажатого символа, и редактор визуально мерцает при каждом изменении.

## Проблема (The Bug)
В `gt-editor` (Markdown редактор) наблюдался эффект "сброса" курсора и потери фокуса при вводе каждого символа. Редактор визуально мерцал, а введённый символ мог оказаться не в том месте.

## Причина
Компонент `MarkdownEditor` использовал дефолтное значение для пропса в виде литерала массива:
```typescript
export function MarkdownEditor({ includeOffsets = [] }: Props) { ... }
```
В React при каждом рендере родителя `{ includeOffsets = [] }` создавал **новую ссылку** на пустой массив (`[] !== []`). Этот пропс был в зависимостях `useEffect`, который инициализировал CodeMirror. В итоге при каждом нажатии клавиши (которое вызывало `setState` в родителе) весь инстанс редактора уничтожался и создавался заново.

## Решение
Вынос пустого массива в стабильную константу на уровне модуля:
```typescript
const EMPTY_OFFSETS: any[] = [];

export function MarkdownEditor({ includeOffsets }: Props) {
  const stableIncludeOffsets = includeOffsets ?? EMPTY_OFFSETS;
  
  useEffect(() => {
    // Инициализация...
  }, [..., stableIncludeOffsets]); // Ссылка теперь стабильна
}
```

## Урок для проекта
Никогда не использовать литералы объектов или массивов в качестве дефолтных значений пропсов внутри деструктуризации параметров компонента, если они попадают в `useEffect` или `useMemo`.

# ОПЫТ: Сборка Tailwind v4 в Electron (директива @source)

## Проблема
При использовании Tailwind CSS v4 в связке с Vite и Electron, динамические классы (arbitrary values типа `text-[#a8c7fa]`) не попадали в итоговый билд `output.css`. Интерфейс выглядел "сырым", стили не применялись.

## Причина
В Tailwind v4 механизм сканирования файлов изменился. По умолчанию JIT-движок может не подхватывать `.tsx` файлы в глубоких подпапках Electron-проекта, если они не указаны явно или если структура проекта сбивает стандартный поиск.

## Решение: Vite plugin и явные источники классов
Отдельную CSS-сборку заменил официальный плагин `@tailwindcss/vite`.

1. **Интеграция:** Плагин подключается в `electron.vite.config.js`.
2. **Преимущества:**
   - **Мгновенный HMR:** Стили обновляются сразу при сохранении файла без перезагрузки страницы.
   - **Явные входы:** `globals.css` использует `source(none)` и `@source` для
     `index.html`, всего `src` и source-каталогов bundled conversation/editor/DnD/file-explorer.
     Общий `src` сохраняет также shared и generated compatibility ветки.
     Исключены generated `src/pty-proxy/target` и файлы `.test`/`.spec`; runtime
     templates/examples/fixtures не объявляются тестами только по имени каталога.
   - **Отсутствие артефактов:** Исчезла проблема с `output.css`, который мог "отставать" от изменений в коде.

Прежнее утверждение, что автоматический scanner ограничен графом Vite, было
неверным: обычный checkout подтягивал классы из посторонних пакетов, которых не
было в frozen source. Менялись не только unused utilities, но и универсальные
инициализаторы CSS-переменных. Поэтому совпадение JS/source pins само по себе
не доказывает одинаковые стили. Проверка использует реальные compiler/scanner,
физические входы и итоговый CSS; для новой runtime source-root требуется
добавить её в декларации. Полные имена условных классов сканируются, динамическое
конструирование части имени Tailwind по-прежнему не выводит автоматически.
Это контракт воспроизводимой сборки, а не доказательство причины UI-задержки.

## Пульс точек фоновых задач

History и SDK BackgroundTasksBar используют общий `animate-glow-yellow` с
профилем `noted-background-task-dot`: размер6px, период1.4s, прежние amber/yellow
цвета и конечные ореолы. Два заранее нарисованных слоя меняют взаимную opacity;
сама точка остаётся непрозрачной и меняет цвет. Это не затухание всего элемента.
`noted-infinite-animation` и общий hidden-owner selector приостанавливают host,
а обе псевдочасти наследуют `animation-play-state`.

Прежняя анимация `sdk-bg-task-pulse` меняла background-color/box-shadow каждый
кадр. Тень не была «GPU-cheap»: в отдельной packaged E28 копии три таких слота
тратили462/522ms времени renderer-потока за4s против43/39ms с общим glow в A/B/A/B.
Это контроль одного CSS-механизма, не причинность всей установленной нагрузки.
Геометрия совпала; конечные compositor PNG отличались максимум на1/255 канала.
Полная побитовая эквивалентность промежуточных форм размытия не заявляется.
При изменении проверять оба caller, видимую смену цвета, hidden pause/resume,
геометрию и стоимость кадров; один JS-профиль не покрывает native paint.

## Вращение статуса инструмента

`ColoredToolIcon` в общем пакете claude-blocks вращает HTML `span.cb-spin`,
внутри которого остаётся прежний статичный `Loader2Icon`. Размер14px,
stroke2.75, currentColor, цикл1s, `.cb-tool-ic`/`.cb-c-running` и скрытая
пауза сохранены. Классы статуса/отступа остаются на внешнем элементе; waiting,
done, error и переданный пользователем glyph не меняются. Это тот же принцип,
что у HistorySpinner, без зависимости shared-пакета от desktop-компонента.

В packaged E28 контроле29Oct три исходных SVG дали376/519ms renderer-thread
за4s против34/155ms у HTML-carrier; один `will-change` на SVG не помог.
Четыре compositor PNG (0/250/500/750ms) совпали побайтово по пикселям,
hidden pause проверена. Это проверка конкретного механизма; она сама по себе
не доказывает устранение всех installed задержек или других native затрат.
