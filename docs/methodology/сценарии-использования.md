*Пошаговые пути юзера через несколько фич custom-terminal'а — там где успешный исход зависит от последовательности состояний (background↔foreground, killed→cold-launch, idle→busy→idle, AI-engine выбран → запущен → context preserved). Один сценарий = одна цепочка, которая в любом отдельном `fact-*.md` целиком не помещается. Активируется явно («проверь основной флоу X», «не сломали ли мы Unified AI Launch») или через `docs_search` по запросам про user-journey. Каждый сценарий ссылается в конце на participating fact-файлы, где живёт механика конкретных подсистем.*

## Сценарий: MCP после закрытия и повторного открытия приложения

1. Пользователь открывает Noted Terminal обычным способом macOS, затем закрывает
   и снова открывает. Общий detached-хаб сохраняется; новый main принимает его,
   не создавая второй комплект серверов. Запуск не зависит от PATH интерактивного shell.
2. Если HTTP хаба жив, но старые дети все падают с ENOENT/code127, это состояние
   не считается готовностью: штатная замена восстанавливает окружение запуска.
3. В панели пользователь перезапускает один сервер или нажимает «Перезапустить
   все MCP». Кнопки показывают процесс и доступны снова после ответа; зелёный
   означает завершённый initialize. Ошибка остаётся видимой, включая частичный сбой.
4. После отдельного restart PID соседнего сервера сохраняется, запрос инструмента
   проходит через прежний адрес хаба. При недоступном хабе общая кнопка сначала
   поднимает его. Быстрый повтор клика/конкурирующий launch не создаёт дубли.

Проверено на приватных портах с настоящими Electron/IPC и управляемыми MCP-детьми;
отдельный live smoke проверяет tools/list каждого из шести production-серверов.
См. [MCP-хаб](../knowledge/fact-mcp-hub.md).

## Сценарий: Первый клик из другого приложения

Noted Terminal виден, но фокус находится в другом macOS-приложении.

### Основной путь

1. В Noted Terminal выбраны вкладка и workflow; пользователь работает в другом приложении.
2. Пользователь наводит мышь на нужную sidebar-вкладку, чип в шапке окна, project-card или workflow. Элемент подсвечивается, но фокус остаётся в другом приложении, выбранные вкладка/проект/workflow не меняются. При уходе мыши подсветка снимается.
3. Пользователь один раз нажимает левую кнопку, в том числе после неподвижного наведения. Приложение получает фокус, тот же физический клик доходит до выбранной поверхности ровно один раз.
4. Tab выбирается по обычным правилам размещения; project-card меняет проект бокового списка, сохраняя окна; workflow восстанавливает свою раскладку. Второй клик для выполнения действия не нужен.

### Edge: возврат через Cmd+Tab без клика

Курсор остаётся над другой карточкой, пока пользователь возвращается в приложение
через Cmd+Tab. Фокус ввода восстанавливается в прежней вкладке; выбранные tab,
project и workflow сохраняются. Hover может обновляться, но событий нажатия,
отпускания и click без физического клика нет; объект под курсором не открывается.
Следующий настоящий клик выполняет обычную навигацию.

См. [системный фокус](../knowledge/fact-cmd-tab-refocus.md#первый-клик-по-неактивному-приложению) и [правила панели](../knowledge/fact-рабочая-область.md#клик-по-невыбранной-панели-фокусирует-и-проходит).

## Сценарий: Unified AI Launch (Claude | Gemini | Codex)

Юзер заходит на pristine таб без сессии и хочет начать работу с AI-агентом. Раньше выбор движка жил в правой `InfoPanel`-колонке как split-button. После удаления правой колонки lifecycle-affordance (запуск + Continue/Stop + fork + copy session-id + force-refresh timeline) переехала в `ClaudeControlBar` под Terminal. Стартовая точка одна, дальше пути расходятся по engine'у.

### Основной путь
1. Состояние: уже существующий Blank с живым shell, без закреплённой Terminal/AI-роли и без foreground-команды. В `ClaudeControlBar` видны launch/fork-чипы. Это legacy/durable вход; оконная «Новая вкладка» до выбора ещё не имеет рабочей записи и описана отдельным сценарием ниже.
2. Юзер выбирает Claude, Gemini или Codex кликом по соответствующему launch affordance.
3. Фокус переносится в основную поверхность выбранной вкладки по её режиму: History composer, terminal или SDK composer. Это часть launch/continue gesture, а не отдельный клик пользователя.
4. Общий сценарий запуска доводит процесс до готовности. После закрепления AI-роли первоначальный выбор движка не возвращается от Stop или отсутствия первой записи; у принятого AI остаются его настройки. Current-session fork-кнопки требуют подходящего session proof и открывают соседнюю вкладку.
5. ControlBar адаптируется под движок: для Claude доступен Provider + Effort inline-row + Think + Copy-prompt split-pill + `⑂→SDK` fork-чип; для Codex — Model + Effort через `/model` picker, Copy-prompt split-pill только пока PTY жив, без Provider/Think; для Gemini — этих контролов нет (объяснение асимметрии ниже).
6. После session capture в Tab пишется `claudeSessionId` / `geminiSessionId` / `codexSessionId`. Триплет `[⎘ session-id | Continue/Stop | ↻ refresh-timeline]` становится постоянно видимым, Timeline и HistoryPanel получают правильный parser по engine'у.

### Edge: во время Start/Resume уже появился другой запуск

Начатый запрос ждёт свой launch, включая его собственную первую OSC-B и позднее
появление writer. Если пользователь остановил его и открыл новый, поздний ответ
старому запросу не объявляет новый процесс своим успехом и не закрывает его при
cleanup. HTTP/Inbox сохраняют admission identity до последнего main snapshot.
Чтение неизвестного состояния повторяет один согласованный catch-up; если owner
продолжает меняться, возвращает typed unknown вместо смешанного ready/PID.
Проверять cold/background вкладку, передачу App→main→HTTP, новый same-SID launch
и delayed response после SSE, а не только исчезновение Starting.

### Edge: пустой Claude переживает перезапуск приложения

Пользователь запускает Claude, не отправляет ни одного сообщения и закрывает
приложение. При следующем запуске та же вкладка открывает пустой Claude,
сохраняя History draft; попытки `--resume` по одному служебному UUID нет.
Если в истории есть реальный prompt, compact или запись без ответа, остаётся
обычный Resume. Недоступный файл не позволяет заменить разговор новым.
Во время запуска показывается ожидание; готовность нового процесса завершает
его, а реальный выход процесса завершает его отказом, не минутным таймаутом.
Проверяется также порядок «новый UUID/statusLine → первая запись JSONL»:
при появлении файла приложение связывает именно живой новый процесс с его
историей и читает уже записанный результат startup-команды. Старый пустой UUID
не удерживает Configuring; второго `/model` ради смены привязки не отправляется.
См. `fact-claude-sessions.md::Автовосстановление до первого сообщения`.

### Edge: Resume не создаёт скрытый вариант модели из короткой подписи

Пользователь выбирает в Settings единственную Fable-команду
`claude-fable-5[1m]`, работает в сессии и перезапускает приложение. JSONL может
сохранить точный аргумент wrapper, но stdout/ControlBar показать только
`Fable 5`. AutoResume связывает оба значения с текущим каталогом и снова
отправляет `[1m]`; короткого `claude-fable-5`, отсутствующего в Settings, не
появляется. Если строка была удалена или двум строкам соответствует одна
подпись, применяется global default. До JSONL proof новой команды интерфейс не
выдаёт historical label за live-state. Проверка включает context meter: он не
должен прыгать к100% из-за скрытого перехода на меньший context и возвращаться
после повторного ручного выбора.

### Edge: большой первый prompt и непрерывная работа Claude

Пользователь отправляет большой многострочный prompt в новой Claude-вкладке.
Подтверждение доставки завершает ожидание отправки, а принятое UserPromptSubmit
держит индикатор работы через thinking/tool-фазы до Stop того же основного хода.
Если параллельный subagent падает или приходит конец предыдущего prompt на том
же SID/PID, индикатор текущего ответа не гаснет и Run After не продолжается.
Точный повтор start не начинает второй интервал работы. Наличие полного
prompt в JSONL не гарантирует, что отдельное событие начала работы дошло:
проверять также большой hook-пакет при занятом main и последующий Stop, а не
чинить такую потерю CSS-анимацией. См. `fact-claude-stop-hook.md::Hook script`.

После подтверждения обычный текст из поля ввода остаётся текстом в History,
даже если сохранённая provider-запись получила внешнюю paste-оболочку. Явная
вставка внутри сообщения остаётся ровно одним чипом на прежнем месте. Reopen
не меняет этот вид: его восстанавливает exact main presentation, не новая
отправка и не похожий текст соседнего хода.

### Edge: первый prompt задаёт название вкладки
Если pristine Claude/Codex таб назывался `tab-N` и пользователь не менял имя вручную, первый реальный user prompt после fresh launch становится источником AI-названия вкладки. Последовательность важна: launch affordance взводит tab как eligible, первый materialized session id создаёт одноразовый pending, а App-global coordinator подписывается на durable transcript и headless выбирает первую user-entry для Gemini prompt `tab-title`. Visual Timeline здесь только показывает историю: её hidden/busy refresh-gating не владеет именованием. Restore, Continue и повторное чтение старого transcript не проходят этот путь.

Pending не истекает по времени до первого prompt/конца длинного первого ответа. Он живёт до rename, ручного имени, смены сессии, закрытия/отклонённого launch или app restart. Это покрывает фоновую вкладку и первый turn дольше десяти минут, не снимая полезную busy-защиту с визуального Timeline.

Fresh launch здесь означает не только кнопку в ControlBar. Если новая Claude/Codex-сессия создаётся через MCP/API, `pendingAction`, History runtime или старый no-session chip в InfoPanel, это тот же user-flow: пользователь видит новую AI-вкладку и ожидает название от первого prompt'а. Если путь восстанавливает уже известный session id (`Continue`, AutoResume, edit-range), это не fresh launch и auto-title не взводится.

Для native iOS этот же сценарий начинается из списка проекта: пользователь создаёт новый Claude/Codex terminal, попадает в чат и ждёт запуска процесса. `/agent-tabs` должен довести вкладку минимум до принятого runtime launch; пока нет `active/inputReady`, composer не является готовым input'ом и не создаёт локальную user-row. Если launch падает раньше runtime (например, missing cwd), путь завершается ошибкой запуска, а не бесконечным `starting` и не первым prompt'ом, который потом нечем подтвердить в JSONL/rollout.

Fork — исключение из restore-логики: это новая ветка работы, поэтому staging-name источника (`<name>_fork` или session-prefix) не считается финальным названием. После materialized fork session id pending работает в `fork` mode и ждёт первый eligible user prompt **после** fork boundary: у Claude после синей fork-границы, у Codex после `forked_from_id`/timestamp в session meta. Старые copied entries в fork-файле не должны участвовать, иначе новый tab называется по задаче родителя, а не по тому что пользователь первым спросил уже в fork.

Fresh tab может ещё стоять в inline rename, когда пользователь сразу кликает Claude/Codex launch. Blur или Enter с неизменённым `tab-N` не считается ручным переименованием и не блокирует auto-title; блокирует только реальная правка текста имени до запуска. Иначе пользователь видит свежую вкладку `tab-1`, отправляет первый prompt, но название не появляется, хотя явный ПКМ-refresh потом работает.

Если пользователь уже переименовал вкладку, автоназвание silently skip'ается. Явный ПКМ → `Обновить название` остаётся ручным действием и может обновить имя в любой Claude/Codex вкладке; во время запроса пункт меню показывает loader, чтобы повторный клик не создавал параллельные Gemini-вызовы. Механика и prod-шрамы `startCodexTab` / false inline-rename ownership описаны в `fact-tabs.md::AI auto-title по первому пользовательскому prompt`.

### Edge: Engine asymmetry (Claude-only vs Gemini-only)
Часть affordance'ов в баре существует только для Claude и **сознательно отсутствует** для Gemini/Codex. `⑂→SDK` (fork в SDK-таб) — SDK не запускает Gemini или Codex, у `@anthropic-ai/claude-agent-sdk` нет аналога. Provider switcher — Anthropic proxy-концепт. Copy-prompt split-pill (`⎘ prompt | + clear`) есть у Claude и Codex, но только у живого PTY-процесса: оба используют external-editor hijack (Ctrl+G → `EDITOR=noted-code-grab.js`), а у Gemini CLI такого reliable hook'а в проекте нет. Codex отдельно поддерживает Model/Effort, но оба применяются через его интерактивный `/model` picker, а не через Claude `/model <alias>` slash-команду. Скрытие кнопок для других движков — не bug, а контракт engine'а; визуально юзер сразу понимает тип таба по набору контролов в баре.

### Edge: `*-F` из заранее открытой пустой вкладки
Юзер может сначала создать новую пустую вкладку как target, скопировать session id из другого места и нажать `Claude-F`, `SDK-F` или `Codex-F`. В этом состоянии не должна появляться ещё одна вкладка: пустой PTY-таб уже и есть выбранная цель. `Claude-F`/`Codex-F` запускают fork-команду в текущий PTY, `SDK-F` конвертирует текущий PTY в SDK и цепляет форкнутый session id. Если текущая вкладка уже занята процессом или session id, тогда fork уходит в соседнюю вкладку, чтобы не разрушить живой контекст.

### Edge: большой Codex-F копирует историю до готового composer

1. Состояние: целевая PTY-вкладка пуста, а выбранная исходная Codex-сессия содержит большую историю. Юзер запускает `Codex-F`. При запуске из контекстного меню source сразу показывает «делается форк…», до ожидания проверки сессии. Повторный клик, пока эта подготовка не закончена, не создаёт вторую операцию; после её завершения независимый новый Fork доступен.
2. Codex может показать `Update available`; автоматика выбирает `Skip` только после распознанного полного кадра. Компактная lifecycle-плашка уже объясняет startup-фазу, но не перекрывает терминал.
3. После отправленного Down+Enter меню может ещё несколько секунд оставаться последним нарисованным кадром, а ручные стрелки — не приниматься: в это время Codex копирует rollout и поднимает инструменты. Плашка продолжает показывать реальную фазу, а не объявляет видимое меню готовым input.
4. Новый rollout повторно выпускает старые события, иногда со свежими внешними timestamps. Turn watcher держит history barrier и игнорирует весь рост до текущего EOF, поэтому старые `task_started/task_complete` не меняют busy/readiness новой вкладки.
5. Только чистый composer освобождает barrier и завершает startup status. С этого момента новые append-события считаются живыми; manual-action/error вместо composer остаётся видимым состоянием, а не ложным успехом.
6. Принятие копии остаётся отдельным proof: full rollout со старыми compact и serializer-default null должен сохранить History/Timeline. Настоящее изменение текста, вложения или compact не принимается по одному числу сообщений. Ошибка source lookup/compact до создания вкладки снимает её pending-label, не оставляет вечный loader.
7. Та же операция из остановленной source не требует сначала Resume. Если быстрый probe не дочитал большую первую запись, Fork уточняет сохранённую историю сам; пустой metadata-only файл по-прежнему не считается беседой. Смена source/input во время чтения отменяет именно старую попытку. Проверять nullable reasoning как отдельную запись и внутри обоих compact checkpoints, не только верхние compact-поля.

### Edge: проверка процесса недоступна во время живого Codex-turn

1. После Start/Continue Codex пишет `task_started`; вкладка переходит в `busy`, loader виден, turn watcher и session id уже подтверждены rollout'ом.
2. Shell выпускает промежуточный `D`, но проверка process-tree завершается timeout/ошибкой. Это состояние `unknown`: loader, session, readiness и watcher остаются прежними; UI не показывает `active` или `inactive` как будто turn закончился.
3. Следующая успешная проверка находит живого descendant и при необходимости восстанавливает watcher. Для пользователя это тот же непрерывный turn без исчезновения и повторного появления плашки.
4. Переключение вкладки или проекта может скрыть локальную плашку, но не меняет lifecycle фоновой вкладки. При возврате она всё ещё `busy`, если rollout не записал финальный edge.
5. `task_complete` / `turn_aborted` завершает сам turn; успешный пустой снимок после реального exit переводит процесс в `inactive`. Ошибка наблюдателя не подменяет ни одно из этих событий.

### Edge: Continue при возврате после kill
Если процесс был убит (Stop через UI, manual stop, kill из шапки), таб сохраняет `claudeSessionId`/`geminiSessionId`/`codexSessionId`. В ControlBar триплет показывает `Continue` (не Stop) — клик восстанавливает контекст: для PTY-Claude через `claude --resume <sid>`, для Gemini через `gemini -r <sid>`, для Codex через `codex resume <sid>`, для SDK через возврат фокуса в composer + следующий submit с `query()` использующий тот же sid. Если Claude/Codex показывает интерактивный chooser (`Choose working directory`, model picker, подтверждение resume), Enter должен работать сразу после клика Continue, без предварительного клика по терминалу. Codex directory chooser (`Use session directory` / `Use current directory`) дополнительно auto-confirm'ится только когда main реально увидел этот PTY-фрейм; пользовательский fallback остаётся тем же — терминал уже в фокусе.

### Edge: Claude Resume сохраняет настройки разговора

1. Состояние: приложение перезапущено, Claude-процесс остановлен, а вкладка хранит session id; глобальные StatusBar defaults уже могут отличаться от того, с чем шёл этот разговор.
2. До запуска ControlBar читает активную ветку истории и показывает последние подтверждённые Model/Effort этой сессии. Отменённая команда и setting из будущего, отброшенного Rewind, не участвуют.
3. Пользователь нажимает Continue. После готового Claude composer приложение последовательно возвращает session Model и Effort; global defaults заполняют только отсутствующее поле, а ошибка чтения не разрешает переопределять разговор догадкой.
4. После подтверждения Claude снова показывает READY, и обычный Send проходит без дополнительного клика по терминалу.
5. Если пользователь вручную вводит `/model` или `/effort` в терминале, ControlBar меняется только после stdout-подтверждения в активной ветке; StatusBar defaults для будущих сессий остаются прежними.

### Edge: Codex применяет выбор во время запуска до первого prompt

1. Состояние: пользователь запускает новую или остановленную Codex-вкладку;
   процесс ещё `starting`, поле ввода не подтверждено, а в TUI может быть видна
   прежняя пара model/effort.
2. Первый выбор Model/Effort/Quick доступен и до готовности. Пользователь
   выбирает, например, `gpt-5.6-sol/max`; после этого UI ждёт применения и
   блокирует повторный settings-клик. Внешние запросы по-прежнему сохраняют
   revisioned intent, и main не применяет старую ревизию поверх новой.
3. Main не пишет команду в shell или startup blocker. Он ждёт чистый composer
   именно текущего launch и только тогда выполняет нативный picker.
4. Footer подтверждает `gpt-5.6-sol/max` ещё при пустой History/Timeline и до
   появления первого rollout writer. Launch в этот момент владеет только
   настройкой, поэтому Fork/Rewind не получают выдуманный session owner.
5. Пользователь отправляет первый prompt. Созданный или продолженный rollout
   становится writer; если его model/effort proof совпадает, уже применённая
   ревизия просто передаётся с launch на session без второго picker.
6. При отказе picker сохранённое намерение не выдаётся за применённую пару:
   ожидание завершается явной пометкой ошибки, контролы снова доступны.
   Допустимое фоновое продолжение intent на readiness/turn-end вновь показывает
   ожидание и заканчивается собственным подтверждением.

См. `fact-claude-control-bar.md`, `fact-claude-sessions.md`, `fact-gemini-sessions.md`, `fact-codex.md`, `fact-claude-sdk-tab.md`.

### Edge: выбор настройки, ожидание и возврат на вкладку

Пользователь выбирает model/effort → выбранный контрол показывает loader,
Model/Effort/Quick недоступны → main подтверждает фактическое применение либо
отказ → показывается подтверждённая пара либо явная ошибка, контролы доступны.
Сохранение выбора не завершает ожидание. Если во время этого перейти в другую
вкладку и вернуться, операция и её результат не теряются. Старая History с
Ultra не перезаписывает уже подтверждённый Max; фоновое чтение каталога вообще
не меняет выбор. Для stopped-вкладки сохраняется следующая launch-пара без
ожидания выключенного CLI. Фоновый ответ/paste сам по себе не запрещает первый
выбор настройки; повторный UI-клик ждёт завершения именно настройки. Если
running Codex уже записал подтверждение, видимая History показывает короткую
`/model`/`/effort` строку без ожидания, пока пользователь перестанет печатать,
двигать мышь или скроллить. Hidden и тяжёлые refresh продолжают применяться в
фоновой очереди и не отнимают ввод у текущей поверхности.

Если новая Claude-модель требует другого effort, это всё ещё один выбор:
Model→подтверждение модели→совместимый Effort→подтверждение effort. Запрос
другого клиента ждёт всю эту операцию, не вклинивается между её командами.
Если второй шаг отказал, показывается уже применённая модель и явная ошибка
effort; вся пара не объявляется применённой и пользовательский prompt не
отправляется автоматически.

После failed startup пользователь выбирает новую модель B и effort; B применяется,
effort получает429. На возврате показываются B и НОВАЯ ошибка effort, не старая
ошибка модели и не Starting. Закрытие старой карточки не скрывает новый отказ;
приложение не повторяет effort из catch. Если вместо отказа пропал ответ HTTP,
native-клиент с capability agentParams сохраняет requestId и читает ту же
квитанцию. Late proof обновляет её даже после ухода с экрана; другой новый выбор
не отменяется этим старым результатом. Неисполненный суффикс не отправляется
одним фактом позднего чтения. Codex по-прежнему использует свой pending intent.

Для связанного Codex settings+prompt provider может перейти с A на B, пока
приложение ещё ждёт подтверждения сохранённой конфигурации A. В таком случае
старый результат не возвращает label A и не отправляет explicit-A сообщение при
наблюдённой B. Отказ до Enter не скрывает уже записанный paste; повтор сообщения
определяется его собственной квитанцией, не лоадером выбора модели.

## Сценарий: native iOS создаёт Codex и догоняет busy после foreground

Пользователь находится в нативном Terminal mode на iPhone, создаёт Codex-вкладку в проекте и может уйти в другое приложение прямо во время ответа. Успех сценария зависит от связки SwiftUI navigation, `/agent-tabs`, runtime status, SSE/history catch-up и Codex rollout; ни один из этих слоёв отдельно не доказывает весь путь.

### Основной путь

1. Состояние: открыт список проектов или список вкладок проекта в native iOS. Пользователь выбирает проект и нажимает `New → Codex`.
2. Сервер создаёт agent tab через `/api/projects/:id/agent-tabs {toolType:"codex"}` и запускает runtime. Клиент показывает `starting`, но composer остаётся поверхностью намерения: Send может быть передан общему scenario и дождаться ready/queue без второго запуска.
3. Первый Send создаёт локальную user-row с handoff identity. Только серверный runtime переводит вкладку в `busy`; новый Send во время ответа остаётся допустимым и проходит через provider queue, тогда как Stop управляет текущим turn.
4. Пользователь уходит в другое iOS app во время длинного turn'а. Noted Terminal не обязан держать SwiftUI screen actively rendered in background, но серверный runtime и rollout продолжают быть source of truth.
5. При foreground native немедленно делает catch-up: заново открывает SSE, один раз перечитывает status/history/queue/question и сначала сверяет незавершённый handoff через read-only receipt. `busy` сохраняет loader/Stop, но не отнимает право поставить следующий prompt в очередь.
6. Когда Codex пишет `task_complete`, visible state возвращается в `active` и composer снова доступен. При непустом `last_agent_message` либо корневом assistant `final_answer`, явно привязанном к тому же turn, history содержит один assistant-result. Если нет обоих доказательств, ход закончен только по liveness: assistant-result не выдумывается, а автоматические действия не считают это успехом.

### Edge: первый prompt после долгого idle

1. Native iOS создаёт fresh Codex tab и дожидается `active/inputReady`, но durable session ещё не существует: до первого обычного prompt нет rollout и `sessionId`.
2. Пользователь оставляет готовый composer без действий дольше TTL launch-watcher'а.
3. При позднем Send main переармирует session discovery по сохранённой launch identity до вставки и Enter; отсутствие текущего watcher'а не превращается в `codex_turn_watcher_unavailable`.
4. Первый `session_meta` привязывает rollout к той же вкладке, catch-up видит уже записанный `task_started`, поэтому desktop и iOS получают один busy-state и одну History.

### Edge: Resume создаёт нового writer и вкладка переживает Close/Restore

1. Состояние: остановленная вкладка хранит session A. Пользователь нажимает Continue; A становится только источником Resume, а компактная плашка показывает `starting`.
2. Codex может дописать A или подготовить child B. Чистый composer гасит startup-плашку и разрешает обычный ручной ввод, но до доказательства writable rollout UI не называет A текущей live-сессией и не разрешает identity-зависимые действия.
3. Пользовательский Enter сразу записывается в выбранный PTY без status/session/process preflight. Внешний клиент проходит отдельную цепочку: доказать отсутствие чужого draft → упорядоченно записать paste+Enter → подтвердить доставку по rollout `user_message`.
4. Writable rollout + metadata или первый append source доказывают writer. При child-варианте вкладка атомарно принимает B, сохраняет B и продолжает loader по `task_started`, не показывая промежуточный idle.
5. Copy ID, Timeline, History, Rewind и Project API теперь видят B из того же runtime snapshot. Ошибка process lookup сохраняет lifecycle, но временно не выдаёт мутационный ID.
6. Пользователь закрывает вкладку. Main архивирует B до kill; Shift+Cmd+T восстанавливает B из `tab_history`, даже если renderer ещё держал A. Если archive не сохранился, Close останавливается и оставляет вкладку с процессом живыми.

### Edge: короткий prompt завершился до foreground

Если ответ закончился пока приложение было в фоне, foreground может сразу показать `active`. Это не проверяет busy catch-up; для smoke нужен искусственно длинный command (`sleep 20`), чтобы возврат произошёл до `task_complete`.

### Edge: служебный Codex event похож на дубль

Rollout содержит `event_msg.user_message` и conversation `response_item message role=user`. Visible history должна считать второе, а первое использовать как audit/event. Если тест считает оба как user bubble, он найдёт ложный дубль, которого пользователь не видит.

### Edge: Stop/Resume после первого prompt

После первого materialized prompt Codex уже имеет rollout session id и полезную visible history. Если пользователь жмёт Stop на iOS или desktop, клиент видит `stopping → inactive` и блокирует send/rewind до финального exit; следующий Continue/Resume запускает `codex-c` той же сессии, а history после reload сохраняет user/assistant строки. `/model <id>` и `/effort <level>` в этой истории приходят из `turn_context` как служебные display rows: они не должны появляться слитно, исчезать после reload или считаться отдельными Timeline turn'ами.

См. `fact-mobile-web.md::Native iOS validation via Simulator/WDA`, `fact-codex.md`, `fact-test-infrastructure.md::Native iOS через ios-mcp`.

## Сценарий: внешний чат запускает Codex через Inbox

Юзер пишет в другом приложении, но ожидает, что Codex будет жить в Noted Terminal как обычный терминальный агент: с видимой вкладкой Inbox, Timeline/History, Stop/Continue и тем же session id. Путь пересекает внешний HTTP-клиент, system Inbox, PTY readiness, SSE, auto-stop процесса и auto-close вкладки.

### Основной путь
1. Состояние: внешний desktop-клиент открыл чат и выбрал Codex provider. Пользователь отправляет prompt, а клиент уже знает `conversationKey` этого чата.
2. Клиент делает `POST /api/inbox/runs` с prompt, `source`, `conversationKey`, optional model/effort/system prompt/auto-stop/auto-close. Noted Terminal создаёт system Inbox при необходимости и создаёт или переиспользует Codex tab.
3. Если tab новый или процесс остановлен, Noted Terminal запускает Codex с profile/developer instructions и ждёт `agent:tui-ready-internal` + `inputReady`. Prompt не вставляется по «прошло N секунд».
4. После readiness prompt отправляется в тот же PTY-path, что desktop History/ControlBar send. Клиент открывает `/api/events?tabId=...` и читает `message`/`busy`/`done`.
5. Codex стримит в терминал и rollout; Noted Terminal транслирует состояние во внешний SSE. `done` будит exact `GET /api/inbox/runs/:runId/result`; assistant-turn сохраняется только после подтверждения своего provider turn, не по `busy:false` или чужому tab-level done.
6. После exact completion стартуют два countdown'а: auto-stop процесса и auto-close вкладки. Бейдж/metadata внешнего run показывает оставшееся время и источник запроса; Stop идёт через тот же controlled stop-flow, что ручная остановка Codex.

### Edge: создание дольше HTTP observation, клиент ушёл в Subtitles

Один POST с durable client/run intention; creation observation8s возвращает202,
но исходный SAME await/bridge rid живёт дальше. Поздний exact owned reply сначала
сохраняется, затем отправка продолжается один раз. Никакой foreground/Check/
повторный POST не создаёт вторую вкладку или Send. GET run показывает setupOutcome:
created не означает submitted, pending/unknown не означают отказ. Точный отказ
ДО Send публикует no-write proof + finite setup error без provider Worked.
После restart original GET доступен без запуска; legacy потерянный reply не
восстанавливается по готовой вкладке или совпадению текста. Original D02 не replay.

### Edge: finished Inbox Rewind после auto-close/archive

Клиент явно выбирает подтверждённую user-точку своего run. Обычный exact restore
поднимает ТУ ЖЕ архивированную вкладку с resumePolicy:never; owner/policy из main
archive commit переносятся вместе с ней. Старый closing/stopping из этого carrier
не означает текущий control in-flight. Активный Close/Stop и чужой run/fingerprint
по-прежнему отказывают. Origin A и cleanup B проверяются раздельно, не по SID.
После этого один прежний saved-history executor; не native/AI fallback и не
отдельный клиент Stop/Resume/Enter. Failed pre-executor A8 остаётся отказом:
исправление source не повторяет его, сохранённый ввод/два сообщения не меняются.

### Edge: isolated Inbox retake with an existing authenticated Codex profile

Для native Rewind/Delete-приёмки можно подготовить отдельный Inbox fixture с
новым `CODEX_HOME` и пустой историей, не копируя credential. Main привязывает
launch к уже авторизованному profile source через локальный proxy capability;
credential не попадает в PTY, renderer, handoff или public API. Admission включает
exact tab/launch/cwd/account, поэтому старый websocket не использует successor.
Пустой tab сначала должен дать `active + inputReady`; только после этого native
owner выполняет один Send и saved-History Rewind/Delete. Если auth proof не
получен, fixture блокируется до provider action и не предлагает повторный login
рабочего аккаунта.

### Edge: повторный prompt в тот же чат
Если новый запрос пришёл с тем же `conversationKey` до закрытия вкладки, pending auto-stop/auto-close отменяются, а существующая Codex-вкладка переиспользуется. После auto-close внешний чат передаёт сохранённый `resumeSessionId`: Noted Terminal создаёт новую видимую Inbox-вкладку, но продолжает тот же Codex context. Model/effort не переигрываются как ambient настройка каждого prompt.

### Edge: в Codex composer уже есть terminal draft
1. Состояние: внешний чат с тем же `conversationKey` отправляет новый prompt, но в соответствующей Inbox Codex-вкладке пользователь или тест уже набрал текст в TUI composer.
2. Noted Terminal не склеивает два текста и не нажимает Enter. Перед send он забирает terminal draft, очищает composer и возвращает наружу `terminal_draft_conflict` с `draftText` и `originalPrompt`.
3. Внешний клиент откатывает только что добавленный user-turn, не пишет assistant error и возвращает в свой input два блока: сначала terminal draft, затем новый prompt. Пользователь сам решает, отправлять объединённый текст или поправить его.
4. В Timeline/History Noted Terminal не появляется ghost-turn, потому что Codex фактически не получил prompt. Это отличается от project/tab API: там конфликт оставляет draft в терминале и возвращает `409`, потому что клиент управляет самой вкладкой.

### Edge: readiness не наступила
Если `agent:tui-ready-internal` не пришёл до failure guard, prompt не отправляется вслепую. Клиент получает ошибку запуска/готовности; это лучше, чем вставить user prompt в shell, chooser или ещё не отрисованный composer.

### Edge: пользователь остановил Inbox Codex и вернулся на вкладку
1. Состояние: внешний чат через Inbox уже запускал Codex, пользователь вручную нажал Stop или клиент вызвал stop endpoint, затем ушёл на другую вкладку.
2. Если к моменту Stop OS-процесс Codex уже умер и process lookup возвращает `matches=0`, Noted Terminal всё равно публикует финальный `inactive` и сбрасывает command-running projection. Это успешный stop, а не «ничего не случилось».
3. При возврате на вкладку пользователь не должен видеть `Resuming Codex`, пока не было нового Continue/Inbox run. Active stripe без команды в терминале — баг stale status, не hidden startup.
4. Если пользователь потом нажимает Continue, начинается новый resume lifecycle: видно реальную команду/PTY-start или явную startup error. Старый stop-loader не имеет права возвращаться через секунду сам по себе.

### Edge: возврат на вкладку после Ctrl+C Codex
1. Состояние: Codex запущен в обычной PTY-вкладке, пользователь вручную жмёт Ctrl+C или Stop, затем уходит на другую вкладку до полного исчезновения процесса.
2. Shell может уже прислать финальный `D`, пока под ним ещё коротко живут wrapper/vendor descendants. В этот момент Noted Terminal может оставить вкладку live только как временное состояние, привязанное к реальному process-tree.
3. Когда descendants исчезли, состояние обязано перейти в `inactive` без нового действия пользователя. Возврат через несколько минут не должен показывать `Resuming Codex`, active stripe или Continue-click без видимой команды запуска.

### Edge: Project API управляет тем же агентом напрямую
History, native iOS и другие project/tab-клиенты идут через `/api/terminal-tabs/:tabId/*`, а не через Inbox. Они видят тот же агентский таб, тот же JSONL/rollout и тот же scenario layer, но владеют конкретной вкладкой, поэтому draft conflict не очищает terminal composer. Если во время будущей переделки меняется внутренний парсинг xterm/PTY или момент JSONL-audit, внешний клиент не должен переписывать свой flow: меняется только поведение сценарного слоя под теми же API-статусами.

### Edge: native iOS после Rewind отправляет новый prompt
1. Состояние: пользователь на iPhone открыл Terminal tab, сделал Rewind и видит `REWINDING` над input.
2. Пока canonical history reload не подтвердил новый хвост истории, iOS не публикует восстановленный prompt в input и не убирает pending-state. Пользователь не должен видеть обычный composer в промежутке между rollback и перестроенной историей.
3. После reload prompt появляется в input как draft новой ветки. Следующий Send идёт сразу в `/send`; iOS не вызывает `/draft` как жёсткую проверку, потому что это может вернуть ложный `claude_busy`.
4. Если во время ответа пользователь отправляет второй prompt или `стоп`, локальная строка получает `queued/sending` и остаётся с этим маркером до durable row / consumed-state. Queue-ack или tool/thinking следующего turn'а не снимает маркер.
5. Когда canonical reload догоняет JSONL/rollout, локальная строка adopt'ится или исчезает как отменённая. В ленте не остаётся дубля `sending` рядом с реальной user-записью.

Для composite Codex history выбранная точка несёт полный `entryRef + contentRevision`. Main повторно разрешает физическую строку непосредственно перед destructive write; stale revision, partial tuple или совпавший текст другой строки отклоняются до Enter.

### Edge: send во время streaming и Stop второго prompt'а
1. Состояние: Codex/Claude уже отвечает на первый prompt, внешний клиент отправляет второй prompt через Project API или Inbox API с разрешённой очередью.
2. Scenario layer не нажимает Enter в занятом composer вслепую. Он ждёт runtime-сигнал, что prompt попал в очередь/JSONL или что отправка должна быть отложена, а клиент продолжает показывать `sending/loading` до авторитетного события.
3. Если пользователь нажимает Stop по второму prompt'у, UI возвращает только тот draft, который реально восстановился в terminal input после `turn_aborted`/interrupt. Last-sent prompt из памяти клиента не считается доказательством.

### Edge: Rewind и AskUserQuestion через API
Если `/api/terminal-tabs/:tabId/rewind` приходит в остановленную Claude/Codex-сессию, сценарий сначала запускает resume, ждёт чистый input-ready/defaults/MCP-ready и только потом открывает native rewind/backtrack. Для AskUserQuestion внешний клиент может подключиться уже посреди вопроса через `pending-question`; `answer-question` отвечает или останавливает тот же живой вопрос, который видит desktop/History, а не создаёт отдельную модель вопроса в клиенте.

См. `fact-codex.md::External Inbox runs`, `fact-mobile-web.md::Endpoint map`.

## Сценарий: ручной Codex Rewind через терминал

Пользователь работает в живой Codex-вкладке, хочет вернуться к предыдущему
запросу и продолжить его как редактируемый draft. Путь проходит через native
TUI, main-owned target proof, смену writer и History одной вкладки.

### Основной путь

1. Состояние: Codex idle, текущий writer доказан, composer доступен. Пользователь
   открывает тот же единственный терминал вкладки и нажимает `Escape` дважды.
2. Native transcript открывается на последнем user prompt. Пользователь может
   сразу подтвердить его Enter либо уйти левее и выбрать более старый prompt.
3. Перед destructive Enter приложение связывает native selection с source по
   причинной позиции: последний user item минус принятые `Escape/←` (и плюс
   `→`). Экранный текст не выбирает target и не блокирует Enter; он лишь
   объясняет presentation drift в логе. Exact native title/footer, writer,
   PTY/lifecycle/run и durable journal по-прежнему обязательны, поэтому обычный
   Enter не превращается в blind rollback.
4. После Enter выбранный текст возвращается в composer как draft. Это ещё не
   proof rollback. Exact child принимается сразу; `thread_rolled_back`
   подтверждает source-in-place; `Failed to branch…` завершает операцию без
   изменения истории; `You’re continuing from this point…` создаёт
   `branch-draft-restored`, и ровно следующий подтверждённый Enter материализует
   child. После принятия child вкладка и History атомарно переходят на него.
5. Пользователь редактирует draft или отправляет его. Следующий ход принадлежит
   принятому writer, а restart восстанавливает ту же durable binding.

### Edge: длинный prompt и авторские marker-ы

Обычный multiline, paste-chip и Opt+V saved-prompt выглядят в TUI как несколько
физических строк. Их кавычки, переносы, `<pasted_content>`,
`<saved_prompt name="…">`, image markup и tool-like строки не участвуют в
identity. Если начало длинной выбранной карточки прокрутилось выше viewport,
exact `TRANSCRIPT` title + adjacent selection footer сохраняют Enter. Точная
проверка восстановленного composer после Enter не очищает draft и уступает,
если пользователь уже начал его менять.

### Edge: Resume простаивал дольше watcher TTL

1. Состояние: приложение перезапустилось, Codex Resume показал чистый composer,
   но пользователь не отправлял новых сообщений дольше десяти минут.
2. Файловый watcher уже завершён, однако тот же PTY/process generation и
   сохранённый source всё ещё доказаны. `Escape → Escape → Enter` работает как
   обычный ручной Rewind; Timeline не блокирует его ложным статусом отправки.
3. Если между открытием меню и Enter процесс, lifecycle, run или persisted
   source изменился, старое доказательство отзывается и операция останавливается
   до мутации. Безопасность сохраняется без временного ограничения capability.

### Edge: сообщение отправлено внутри уже идущего хода

1. History и native transcript могут показывать дополнительный user-message,
   отправленный пока предыдущий provider turn ещё работал.
2. Если перед ним нет собственного `task_started`, это steering/queued input,
   а не отдельная точка ветвления. Enter не отправляется, overlay остаётся
   открытым, пользователь получает предупреждение и выбирает предыдущий turn.
3. Если отказ произошёл на старом билде уже после Enter, Stop/Resume проверяет
   durable результат. При полном отсутствии child/rollback/new task/new user и
   неизменном source журнал снимается без переписывания истории; неизвестный
   результат остаётся заблокированным.

См. `knowledge/fix-rewind-navigation.md::Codex native backtrack` и исполняемый
`electron-mcp/scenarios/13-native-rewind-receipt.md`.

## Сценарий: AI-hop build install возвращает агента в ту же вкладку

Юзер просит агента внутри Noted Terminal установить новый билд самого Noted Terminal. Важное ожидание: build может убить приложение, но после перезапуска тот же агент получает один completion prompt в исходную вкладку и продолжает работу; соседние живые turn'ы при этом не обрываются.

### Основной путь
1. Состояние: Codex/Claude уже работает в terminal tab и через Terminal MCP вызывает `build_install_noted_terminal`.
2. MCP не запускает `npm run build:install` в текущей PTY. Он отдаёт задачу Voice Record вместе с `returnTo` (`tabId`, `sessionId`, project metadata), потому что текущий Noted Terminal будет закрыт install-процессом.
3. Voice Record наблюдает `/api/active-loaders` у установленного Noted Terminal и ждёт, пока соседние AI-turn'ы и shell-команды, запущенные через `Restart after`, уйдут в idle. Вызвавшая вкладка исключена из блокеров, иначе агент ждал бы сам себя.
4. После `build:install` Voice Record ищет новый packaged-инстанс через fresh MCP/web-server files, дожидается что исходная вкладка снова существует, PTY жив, а session id совпадает.
5. Только после этого Voice Record отправляет completion prompt через `/terminal/ai-prompt`; terminal layer сам ждёт Claude/Codex input-ready и проходит startup prompts.
6. Исходный агент получает один prompt `Build install completed...` и проверяет финальный статус уже в новой установленной версии.

### Edge: prompt отправлен, но не доказан
Если `/terminal/ai-prompt` вернул `submitted_unverified` или HTTP timeout после начала handoff'а, Voice Record считает callback доставленным непроверенно и не ретраит тот же текст. Пользовательский риск обратный: повтор хуже ошибки статуса, потому что в живой AI-сессии появляются дубли completion prompt'а. Если target ещё не найден или tab/session не восстановились, это другой класс состояния — там retry допустим, потому что terminal input ещё не трогался.

См. `fact-build-when-idle.md::AI-hop изнутри Noted Terminal`, `fact-terminal-mcp.md::AI live control`, `fact-codex.md::Stop и ввод`.

## Сценарий: Диктовка → Enter в живом Claude/Codex

Юзер диктует prompt в live Claude или Codex PTY и хочет отправить его тем же жестом Enter, не дожидаясь ручного появления текста в TUI. Сценарий связывает mic state-machine, delivery в PTY composer и raw Enter submit из `ClaudeControlBar`.

### Основной путь

1. Состояние: активная вкладка — живой Claude/Codex PTY (`isCommandRunning=true`), в ControlBar видны `mic` и `Enter`.
2. Юзер нажимает mic и говорит prompt. Floating window показывает real-time transcript, MicButton в state `recording`.
3. Пока запись ещё идёт, юзер нажимает `Enter` рядом с mic.
4. ControlBar не шлёт `\r` сразу, а переводит Enter в pending-state и отправляет `dictation:stop-and-deliver`.
5. MicButton переходит `recording → stopping`, финализирует Soniox stream, доставляет финальный текст в PTY через `terminal:paste {submit:false}` и публикует `dictation:delivered`.
6. Только после delivery ControlBar отправляет raw `\r` в тот же PTY. Claude/Codex получает уже вставленный текст как обычный submit.

### Edge: Enter на фазе stopping

Если юзер нажал Enter когда mic уже останавливается, повторный stop не запускается. Enter просто становится pending и ждёт тот же `dictation:delivered`. Это защищает от двойной финализации WebSocket и от двух `\r` подряд.

### Edge: `^C` пока Enter pending

Если после шага 4 пользователь передумал отправлять и нажал `^C` в том же ControlBar, pending Enter отменяется. Текст диктовки может всё равно доехать в PTY composer после stop-and-deliver, но ControlBar уже не отправляет raw `\r`; в PTY уходит только raw Ctrl+C, и Claude/Codex применяют свою текущую TUI-семантику (clear input / cancel local command / interrupt turn). Это сохраняет обратимость жеста: Enter = «доставь и отправь», `^C` в pending-фазе = «не отправляй автоматически».

См. `fact-dictation.md`, `fact-claude-control-bar.md`, `fact-codex.md`, `fact-terminal-core.md::Terminal Paste Pipeline`.

### Edge: Voice Record завершён над обычным терминальным вводом

Если каретка уже стоит в TUI/xterm, SDK или другом поле вне History, готовая речь
идёт обычной вставкой без шестисекундного ожидания History-чипа. Если поле ещё
не выбрано, Stop → последующий клик в History ставит чип, а клик в обычный input
сразу выбирает обычную вставку. После выбора одного поля последующий focus уже
не создаёт второй чип. Подтверждённый текст не должен ждать неиспользуемую поверхность.

## Сценарий: Primary History и живой TUI composer

Edge: пользователь прикрепляет библиотечный prompt/file-chip и пишет текст,
начинающийся с абсолютного пути, затем отправляет из History. Чипы и pending
context входят в payload; создаётся audit той же попытки. Escape после этого
завершает turn/возвращает draft по своим доказательствам, но не оставляет
вечный loader из-за audit, который вообще не запускался. `/compact` без
другого текста остаётся самостоятельной local-командой и сохраняет chips для
следующего сообщения. См. `fact-claude-tui-control.md` и
`fact-история-как-основная-поверхность.md`.

Юзер работает в primary History Claude/Codex PTY, а тот же живой TUI остаётся скрытым или открыт floating-окном. Успешный путь здесь не «отправить любой текст любой ценой», а сохранить границу между уже набранным terminal draft, новым текстом в видимом History input и состоянием turn'а.

### Основной путь: Enter в остановленной вкладке

1. Состояние: primary History открыта, Claude/Codex process остановлен; у вкладки может быть сохранённая session id либо это новая вкладка без сессии.
2. Юзер набирает prompt и один раз нажимает Enter. History атомарно фиксирует `text + chips + images`, очищает только этот неизменившийся snapshot и показывает `STARTING`; отдельный клик Resume не требуется.
3. Общий scenario layer запускает fresh process либо resume сохранённой сессии и ждёт реальный input-ready/startup-defaults signal. Наличие PTY или принятие launch-команды ещё не разрешают отправку.
   Если Claude показывает folder trust, управляемый запуск сам выбирает semantic
   `Yes, I trust this folder`, в том числе когда первым выделен No. После выбора
   подтверждаются текущий Yes и исчезновение меню; лишь затем идут настройки и prompt.
4. После ready тот же snapshot отправляется ровно один раз через обычную History delivery boundary. Локальная строка проходит `SENDING → sent/queued → durable`, а lifecycle отдельно становится `busy`.
5. Ошибка до реального submit возвращает исходный snapshot, не стирая более новый draft. Ошибка после `{submitted:true}` не повторяет prompt автоматически: ownership уже у терминала, даже если подтверждение задержалось.

На всём этом пути общий loader Workflow/вкладки/Dock остаётся включён: конец
Start или paste не гасит принятую отправку. После Enter отсутствие exact записи
означает «Подтверждаем», а не паузу работы. Пришедший turn-busy продолжает тот же
индикатор, но остаётся отдельным фактом для управления вводом и Stop. Отказ/отмена
завершают отправку с её собственным результатом; визуальный loader не скрывает их.

### Edge: Option+1 в History — то же намерение, что Enter

Если в composer уже обычный готовый текст, Option+1 запускает тот же
canonical send, что Enter. Если в тексте ещё стоит pending-чип Voice Record,
жест не отправляет сырой `[Dictating …]`, а взводит одноразовую отправку на
момент раскрытия последнего чипа. В ярлыке сразу появляется фиолетовый ⏎; символ `¡`
в черновик не вставляется. Ручная печать после взвода по-прежнему отменяет автоотправку.
Завершение в открытом input сразу проходит обычную отправку и очищает принятый
черновик; переключать вкладку для этого не требуется. Повторённое в финале старое
значение Voice Record не отменяет поздний Option+1 и не возвращает взвод после печати.

### Edge: дописать текст или вставить картинку после чипа диктовки

При выключенной автоотправке пользователь завершает запись и оставляет каретку
после чипа. После раскрытия следующий набранный символ должен появиться сразу
после распознанного текста. Если до раскрытия после чипа вставлено изображение,
каретка остаётся после изображения; если перенесена вручную в начало — в начале.
Отсутствие движения каретки не должно оставлять её внутри выросшей фразы, а
готовность диктовки не должна отменять осознанный перенос пользователя.

### Edge: Cmd+Enter записывает контекст без ответа

1. Пользователь набирает prompt в primary History, удерживает Cmd и наводит
   курсор на нижний `Enter`: кнопка становится фиолетовой. Левый клик с реально
   зажатым Cmd фиксирует exact `text + chips + images` и показывает
   `PREPARING`; ПКМ ничего специального не делает.
2. Действие допускается только при idle/inactive provider. Живой idle process
   проходит доказанный Stop; busy/starting, неизвестный owner/draft и failed
   Stop оставляют процесс и authoring нетронутыми.
3. Claude записывает обычный user-record в свободный JSONL; Codex дописывает
   settings proof и парные user-carriers в свой остановленный native rollout.
   Это durable model-visible история, но не model turn:
   нет submit/ответа/инструментов.
4. Exact provider identity сразу заменяет optimistic строку, затем эта же
   сессия открывается через Resume и ждёт input. Ошибка Resume не откатывает уже
   записанный context и не создаёт повтор.
5. Если через 500 мс пользователь набрал второй prompt и нажал обычный Enter,
   вторая карточка сразу получает `PREPARING` и встаёт FIFO. После ready только
   она проходит обычный audited submit; первый context физически находится в
   истории перед ней и доступен модели. Один process launch, один model turn,
   один assistant response.

### Основной путь: terminal draft конфликтует с History send

1. Состояние: живой Claude или Codex PTY, primary History уже видима, а в hidden/floating terminal composer есть ручной draft.
2. Юзер пишет другой prompt в History textarea и нажимает Send. В legacy surface тот же путь начинается с открытия боковой History через `Cmd+]`.
3. Preflight сначала читает текущий authoritative TUI screen. Если Codex находится в model picker, native Rewind overlay или startup blocker, History сохраняет свой текст, показывает причину блокировки и не отправляет Enter в невидимую поверхность.
4. Если доказан composer и найден реальный draft, приложение атомарно забирает и очищает TUI input, переносит этот draft в начало History textarea, показывает `Send stopped · draft moved` и **ничего не отправляет**.
5. Юзер видит оба текста в одном input в правильном порядке: сначала то, что уже было набрано в терминале, затем текст из History. Дальше он сам редактирует/удаляет лишнее и нажимает Send повторно.

После Resume готовность процесса сама по себе не доказывает пустой composer.
Пока текущий кадр открыт/не применён/не перерисован после resize, preflight ждёт
его событие. Подтверждённый кадр завершает то же ожидание; неразрешённая проверка
возвращает текст без paste/Enter и сохраняет точную причину с replay. Диагностика
не создаёт второй Send и не объявляет сообщение доставленным или работающим.
Это действует и когда первая проверка уже увидела empty, а новая перерисовка
началась во время ответа окна: после ответа читается новый кадр в остатке того
же ожидания. Возвращаться к старому empty или заново отправлять сообщение нельзя.

Для Claude и Codex это одна read-транзакция основного процесса: отсутствие
открытого терминального окна не меняет путь. Если пользователь за время чтения
ввёл новый текст или нажал Stop и уже успел дождаться его завершения, поздний
ответ старой проверки не переносится на новый input. Новая явная отправка
получает свежую проверку; неизвестность старой не разрешает автоматический повтор.

### Edge: process Stop во время предварительной подготовки History Send

Пользователь нажал Send, затем Stop до передачи handoff в общий PTY-сценарий.
Stop сразу запускает прежнюю остановку процесса; input и вложения остаются,
поздний ответ materialize/context не запускает отправку. Пока Stop не подтвердил
исход, статус stopping; после успешного exit — inactive, после неизвестного
результата — честная ошибка/актуальная presence. При пустом prompt или раннем
отказе без Stop временный send token освобождается сразу, следующий клик доступен.

То же действует после передачи в PTY-очередь: Stop→clear до головы очереди
или до paste оставляет ноль записей; после paste до Enter сохраняет факт
вставки, но не отправляет сообщение. После уже записанного Enter Stop не
превращает попытку в «не отправляли»: её квитанция и exact audit остаются теми же.

### Edge: Checking после ошибки наблюдения процессов

При открытии History первая проверка может завершиться ошибкой OS lookup.
Проверка перестаёт крутиться, состояние остаётся неизвестным. Следующий успешный
общий снимок процессов будит exact текущую вкладку, и History перечитывает
presence; возврат в окно также разрешает catch-up. Ни это чтение, ни скрытие
плашки не отправляют prompt и не выводят готовность из сохранённого SID.
Если во время чтения уже пришёл новый start/ready/finish, поздний старый ответ
не возвращает прежний статус: тот же flight перечитывает текущего владельца.

### Edge: отправка записана, но квитанция завершилась ошибкой

Claude может сохранить короткий отправленный текст в native pasted-content
обёртке. Когда ответ уже завершился, приложение всё равно завершает именно
квитанцию исходного Send: отображает содержимое без служебных тегов, заменяет
CONFIRMING точной History-записью и снимает send-loader. После restart это делает
чтение прежней causal boundary; нового Send/Enter не требуется. Неподтверждённый
иной текст не объявляется доставленным только из-за idle процесса.

Пользователь нажал Send, Enter мог уйти в CLI, а запись receipt/наблюдение упало.
History сохраняет ту же неизвестную отправку; не возвращает её как новый prompt
для повторного клика. Same-handoff read/replay не пишет второй Enter, поздний
exact audit уточняет исход. Уже queued ручной Enter также не дублирует эту
попытку; новый текст после освобождения ввода остаётся доступным. Если отказ
доказан ДО Enter, текст по-прежнему остаётся редактируемым и допускает новый Send.

### Edge: Escape сразу после отправки из History

1. Состояние: History textarea отправила prompt, Claude/Codex перешёл в busy.
2. Юзер быстро нажимает Escape/Interrupt, в том числе пока новый prompt ещё SENDING/CONFIRMING. Обычный send-lock не поглощает это действие; main адресует текущий ход и проверяет его ещё раз на PTY-границе. Hard Stop процесса остаётся отдельным действием.
3. Фактическая запись Escape коротко подсвечивает рамку; она не переводит процесс в stopped и не подтверждает prompt. Если CLI начал следующий queued ход, сохраняется рабочий статус, даже когда старый interrupt-event или результат IPC приходят позже.
4. При пустой очереди authoritative interrupt завершает ход. Если CLI действительно вернул draft, recovery переносит его в History с сохранением нового параллельного ввода. Если следующий ход уже работает, автоматическое recovery не забирает его composer; явный Pull остаётся доступен.
5. Повторить с одним и несколькими queued prompt, до и после queue ACK. Каждый сохраняет собственную квитанцию; неизвестная доставка не становится success от одного `task_started`. Медленный History refresh не держит STOPPING и не блокирует следующий Escape. Недоступный draft не восстанавливается из копии отправленного prompt вслепую.

### Edge: отправка во время streaming и JSONL появляется позже

1. Состояние: Claude/Codex уже отвечает на предыдущий turn, History textarea принимает новый prompt и пользователь жмёт Send.
2. Сразу после Enter в History появляется локальная user-row со статусом `SENDING`; prompt не исчезает на 1-2 секунды в ожидании scenario/audit. Первый feedback пользователю — его собственное сообщение, а не tool/MCP/thinking row следующего agent turn'а.
3. После Enter local marker остаётся pending, пока provider не дал точный receipt. Для Codex committed `Messages to be submitted after next tool call` с новым matching prompt переводит эту же строку в `QUEUED`; это provider acceptance, но ещё не durable History. После matching `event_msg.user_message` тот же handoff становится `SENT`. Для Claude PTY exact queue-operation играет ту же промежуточную роль, а `queue-operation remove` без последующей `type:user` записи может быть финальным consumed-state, например `стоп` во время `AskUserQuestion`; тогда synthetic row остаётся `SENT`, а не spinner. Timeout не понижает доказанный `QUEUED`, tool/MCP/thinking row сам по себе ничего не доказывает.
4. Когда agent уже закончил thinking/streaming (`task_complete`, `turn_aborted`, command-finished), но History ещё перечитывает JSONL/rollout, над input появляется `UPDATING`: это отдельная стадия «история догоняет», а не продолжение thinking.
5. Если пользователь прервал turn до durable materialization, History показывает отменённый/служебный marker, но не рисует второй user bubble. Если Claude позже дописал такую же user entry в abandoned tail, History suppression скрывает её до тех пор, пока активная ветка не подтвердит этот prompt как реальный.

### Edge: длинный ответ, старая ошибка отправки и новые уведомления

1. Codex остаётся busy, History хранит старую failed/cancelled карточку, а
   пользователь или оркестрация отправляет следующий prompt. После точного
   принятия он появляется перед относящимся к нему живым ответом; старая
   ошибка не собирает все последующие prompts отдельной полосой внизу.
2. При позднем подтверждении старой отправки меняется только её карточка по
   exact operation+attempt+provider+session+canonical identity. Чужой audit,
   queue-only proof и старый timeout ничего не подтверждают. Новый ещё
   ожидающий ввод остаётся после текущего ответа.
3. После turn-end сохранённые строки заменяют живые без дублей. Повторное
   чтение квитанции не возвращает старую попытку поверх начатого retry.
   Source14.09 и isolated HistoryPanel проверены; production не обновлялся.

### Edge: живой assistant-ответ появляется до JSONL

1. Состояние: Claude/Codex принял prompt и начал отвечать, но цельная assistant-запись ещё не появилась в JSONL/rollout.
2. History показывает растущий левый блок с пометкой `Live response · not yet saved to history`. User prompt, thinking, `Read/Edit/Bash`, progress/footer и служебные side requests в этот блок не входят.
3. Пользователь остаётся у хвоста — новые строки продолжают follow-bottom. Если он прокрутил вверх, рост preview не двигает читаемую строку; искусственный пустой резерв снизу не создаётся.
4. Когда exact assistant item материализовался, preview остаётся видимым, пока соответствующая physical row не появилась в projection и DOM. Затем временная пометка исчезает до paint под тем же semantic anchor: нет промежуточного пустого кадра/skeleton, геометрия и место чтения не пересоздаются.
5. Поздний completion уже сохранённого item, повторный refresh или close старого semantic connection не возвращают preview. Если Claude Stop отозвал последние сетевые символы раньше `content_block_stop`, полный canonical-блок всё равно заменяет settled prefix по exact `message.id`; похожий текст другого сообщения не подходит. При gap/неизвестном ownership History сохраняет последнюю доказанную версию либо молчит, но не публикует экранный хвост как prose.

### Edge: AskUserQuestion в History управляет PTY-курсором

1. Состояние: живой Claude PTY задал `AskUserQuestion`; hook прислал pending-вопрос, hidden/floating terminal ждёт в Ink TUI, а primary History показывает карточку вопроса.
2. Юзер кликает question-chip. Ожидание: меняется только активный вопрос (`←`/`→` в PTY); ответ не выбирается.
3. Юзер кликает option-card. Ожидание: курсор Claude Code в терминале двигается на эту строку (`↑`/`↓`), но `Enter` не отправляется.
4. Юзер кликает radio/checkbox слева от варианта. Ожидание: single-select подтверждается `Enter`; multiSelect toggl'ится `Space` и остаётся на текущем вопросе.
5. Если single-select был не последним вопросом, Claude Ink автоматически переводит focus на следующий вопрос, и HistoryPanel повторяет этот переход. Если вопросы закончились или форма multiSelect, юзер жмёт Submit; History переводит PTY на submit-view и подтверждает `Enter`.
6. Awaiting-state очищается только после реального завершения вопроса (`PostToolUse`/`question-cancelled`/busy:false safety-net), а answered/checked marker не подменяет focused-state: полный фон/рамка остаются у текущего PTY-курсора.

### Edge: native Rewind возвращает prompt в History input

1. Состояние: primary History видима, живой Claude terminal скрыт или открыт floating-окном. Юзер нажимает Rewind под старым prompt либо выбирает обычное `Откатиться` в Timeline.
2. Если Claude process остановлен, действие сначала запускает `claude --resume` для той же session id. Пока Claude не показал input-ready и startup defaults не прошли (`/model` then `/effort`), `/rewind` не отправляется. Timeout readiness/defaults показывает ошибку, а не «тихо ждём/продолжаем».
3. `/rewind` выбирает target в родном Claude picker'е. Открытие picker'а доказывается visible frame: если после первого Enter виден slash-help, приложение делает один confirm Enter и снова требует menu-proof; без proof операция падает до навигации. Claude временно восстанавливает target prompt в terminal composer.
4. Приложение сразу забирает этот prompt тем же `grab-input` path, что и ручная кнопка `+ clear`, кладёт текст в History textarea и очищает terminal composer.
5. History показывает preview-срез до выбранной точки и жёлтый marker `I REWOUND`; target user-row не дублируется как отдельное новое сообщение. Пользователь видит текст в основном input и сам решает, отправлять ли новую ветку.
6. Если закрыть Claude/терминал до отправки, preview не считается сохранённым откатом: при следующем открытии History снова строится из полного JSONL до последнего durable turn.

### Edge: Codex Rewind — сохранённая ветка или честный pending draft

1. Состояние: primary History видима, Codex terminal idle/hidden/floating либо process уже остановлен. Юзер нажимает Rewind под старым prompt или выбирает обычное `Откатиться` в Timeline.
2. Если Codex process остановлен, действие сначала запускает resume той же session id. Пока Codex показывает update/trust/directory prompt или startup-фазу `Starting MCP servers ... esc to interrupt`, backtrack не начинается: readiness ждёт чистый composer, иначе первый `Escape` станет отменой startup, а не Rewind-жестом. Если похожий MCP banner появился уже после отправки prompt'а/live turn, это не повод для Rewind/restart: сценарий должен дождаться окончания turn или вернуть busy-error, а не интерпретировать live tool-startup как готовность к backtrack.
3. Codex проходит native backtrack: первый `Escape` prime'ит hint, второй открывает transcript overlay уже на последнем prompt. Если последний prompt и есть target, стрелки не нужны; иначе после каждой стрелки приложение ждёт стабильную подсвеченную строку, читает overlay frame и отдельно запрашивает xterm visible-snapshot. Target prompt должен быть не просто виден в overlay, а совпасть с prompt-строкой, которую Codex сейчас подсветил фоном/inverse-стилем. Если активная строка не доказана или target frame не найден, overlay закрывается `q`, rollout не меняется, History не показывает успешный откат. Перед подтверждающим `Enter` main сохраняет durable операцию с точным target, source session и поколением PTY.
4. После `Enter` возможны три точных исхода: один linked child с префиксом до target; физический `thread_rolled_back` в source; либо только восстановленный target-draft без записи истории. Возвращённый текст сам по себе не доказывает первые два исхода.
5. При child-path SQLite binding меняется source→child compare-and-set транзакцией вместе с commit receipt и удалением journal. При `thread_rolled_back` source остаётся writer, но success разрешён только с точной depth события. Несколько кандидатов, неполный scan или неожиданная третья binding остаются unresolved.
6. Если provider пока вернул только draft, History показывает `REWIND DRAFT · N old turns still saved`: старое будущее физически остаётся в source и лишь временно скрыто из основной ленты. Следующий exact audited Enter создаёт/подтверждает новую ветку; Stop/restart до него возвращает полную source-историю как no-mutation.
7. После durable child/rollback History/Timeline перечитывают канонический rollout; target переносится в History textarea один раз. В xterm scrollback могут оставаться старые уже нарисованные строки source — они не являются current transcript. Текущую ветку определяют bottom/current TUI frame и принятый writer.
8. Если приложение закрыть между `Enter` и writer handoff, startup recovery либо принимает exact child/rollback, либо при доказанном отсутствии любого durable изменения очищает journal и разрешает Resume. Неоднозначность остаётся видимой и не выбирает ветку по времени файла.

### Edge: вторая кнопка Rewind редактирует сохранённую историю

1. У обычного user-message в History основная violet Rewind обрезает сохранённый JSONL/rollout; native picker остаётся отдельным действием через ПКМ.
2. Violet-кнопка использует тот же saved-history сценарий, что `Rewind` в Timeline и meta-action Queue: перечитывает актуальный хвост, останавливает writer, удаляет target+future, принимает copy-on-write child для Codex или изменённую Claude session и запускает её снова.
3. После Stop Codex сначала завершает старую native-Rewind транзакцию той же вкладки. Если точный исход ещё неизвестен, JSONL не трогается. Если прежняя попытка доказанно ничего не записала либо уже существует exact app-owned child того же target, journal закрывается и только затем начинается saved-history mutation.
4. До мутации target превращается обратно в authoring snapshot. Saved prompt возвращается prompt-chip, `<pasted_content>` — paste-chip в прежней позиции, доступная картинка — image-chip, остальной текст остаётся редактируемым. Маркер без точного image-ref не угадывается и остаётся явной ошибкой вложения.
   Context-update из той же записи сохраняет свой ID и оранжевый RefreshCw в composer; совпадение названия с обычным prompt не меняет тип. Перенос восстановленного обновления в текст оставляет его wrapper/ID, а не только тело.
5. Если во время stop/delete пользователь уже набрал другой draft, восстановленный target добавляется перед ним с перенумерацией image ids и свежими chip ids; существующий input не перезаписывается.
6. Успех проверяется не исчезновением строки в UI, а новым каноническим owner: target отсутствует в child/current Timeline, исходный файл не изменён для Codex copy-on-write, вкладка возобновлена на принятой сессии. `history_delete/edit` остаётся lineage-записью, но не выглядит синей точкой обычного Fork. Уведомление появляется в углу этой вкладки, а успешный Resume убирает прежнюю inline start-error card.

### Edge: фоновые мобильные чаты, Working/Worked и возврат к History

Проверка вложений: явный Send typed image → exact confirmed → в user-row
thumbnail/marker в исходной позиции без transport-пути. Тот же путь, вручную
введённый отдельным text-part, остаётся текстом. Commentary→tools→final получает
Worked только на final; после reopen и очистки старой send-квитанции показ не
меняется, потому что authoring/timing принадлежат постоянным History sidecars.

1. Клиент удерживает прочитанные окна нескольких активных чатов и один SSE с
   явным `tabIds`. Initial каждой вкладки предшествует её live-событиям; чужой
   tab/session не обновляет открытый чат.
2. Main preflight/activity задаёт start текущего Working. Completion даёт короткий
   pending, затем exact sidecar у своего ответа; Worked раскрывает finish time по
   tap. Mount, turnStartedAt и длительность соседнего ответа не являются proof.
3. На transcript/timing change клиент делает один conditional History read.
   Unchanged оставляет rows; Codex delta заменяет только названные UUID и порядок;
   полный bounded ответ заменяет соответствующее окно, не весь локальный архив.
4. На reopen/foreground/reconnect строки остаются видимыми до проверки ревизии.
   Read owner изменился после Rewind — старый token не подтверждает новое окно;
   loader/writer readiness читаются независимо. Закрытие последней подписки
   освобождает consumer даже при незавершённом async subscribe.

### Edge: saved-history Rewind/Delete из мобильного Timeline

Поздний receipt сначала сверяется через main applicability: O→свой Resume
остаётся applicable, O→новый B при том же SID/process — superseded. Старый O
не заменяет новый composer. Snapshot/History/SSE несут общий ownerOrder; поздний
applicable ниже уже увиденного порядка не применяется, смена epoch требует сверки.
После exact Claude clear первый structured Send использует expectedBinding:none
и текущий ownerToken: свой первый launch разрешён, чужой — отказ до записи.
Legacy null SID и отсутствие процесса не являются proof пустоты. Кодекс после
удаления единственного хода сохраняет bound child, не получает выдуманный null.
Старый receipt без checkpoint остаётся историческим фактом с unknown применимостью.

Benign Stop/auto-close после O сохраняет applicable через exact единственный
archive и прежний checkpoint; process absent/read-writer null не понижают logical
разговор и не повышают ready. Сохранённый observation-unknown проверяется SAME-ID
GET/Check после install, без второго History POST/Resume. Missing/ambiguous proof
остаётся unknown, новый ввод того же SID — superseded.

Claude source prerequisite14.09 проверяется отдельно от текущей Codex capability:
изменить input/terminal/run/session во время подготовки Resume — ни одного байта
команды; при неизменном owner один launch и один run++ даже после OSC B. Между
чтением source и commit изменить child или linked parent — операция отказывает,
не стирая позднюю запись; полное удаление тоже проверяет guard. Private fixtures
с одинаковым UUID в двух roots должны читать/копировать только выбранный root.
Source Claude adapter включён отдельно от physical iOS parity. Общий стенд
не изменяется без handoff владельца; auth isolation доказывается до provider turn.
После Rewind с остатком истории Claude возвращает тот же SID; удаление всей
истории очищает binding и НЕ запускает --resume удалённого файла. Оригинальный
prompt/files/images возвращаются вместе с отдельно набранным новым draft; только
следующий явный Send создаёт новый разговор после cleared binding. Source/API
и real CLI/Simulator проверяются как разные границы, не общий fake PASS.

Контроль нулевого результата: один настоящий Send → Rewind его единственной
user-точки → исходный текст возвращён в composer с сохранением нового ввода →
Timeline0, History содержит максимум сохранённые служебные settings. Нужная
ветка остаётся читаемой сразу после появления read proof; unknown writer не
разрешает мутации, но не превращает законную пустоту в потерянный native prefix.

1. На телефоне открыта текущая Codex Timeline; процесс на Mac idle/busy/stopped,
   сама вкладка может быть в фоне. Клиент сохраняет session/UUID и composite
   entryRef/revision выбранной user-точки, отправляет один `history-operations` intent.
2. 202 означает лишь принятие. Пока Mac выполняет общий Stop/rewrite/adopt/Resume,
   повторное подключение телефона читает тот же operationId, не повторяет Rewind.
   Чужой terminal draft остаётся на месте и даёт явный conflict до Stop.
3. Подтверждённый Rewind убирает выбранную итерацию и будущее, возвращает полный
   structured draft в мобильный composer. Delete убирает только эту итерацию с
   ответом; следующие итерации остаются, draft не вставляется. Desktop input не меняется.
4. Клиент принимает новый binding, читает текущую History/Timeline и отдельно
   слушает готовность CLI. `launchWritten` не заменяет `inputReady` и не разрешает
   дополнительный Resume/Enter. Если запуск отказал после adoption, уже изменённая
   история и восстановленный draft не откатываются локально.
5. После потери HTTP результат читается GET. При app crash и `outcome-unknown`
   нельзя повторять мутацию или угадывать локальный tail; нужна сверка того же receipt.
   Inbox/Voice дополнительно сохраняет связь conversation/run. Новый run-scoped
   Noted ingress удерживает cleanup timers, восстанавливает только exact archived
   tab без отдельного Resume и возвращает тот же executor receipt. Смена владельца
   не разрешает старой операции Stop/launch; после terminal receipt новый владелец
   не получает старую cleanup-политику. Voice применяет binding и draft один раз,
   не вычисляет локальный tail и не вызывает native fallback.
6. После Rewind пользователь редактирует draft.authoring: текст, paste body или
   порядок image parts. Только отдельный явный Send передаёт этот DTO в обычный
   `/send`; native не пересчитывает desktop labels, не склеивает prompt bodies и
   не добавляет второй список attachments. После exact sent и следующего Rewind
   возвращаются те же prompt/file metadata и изображения в новом порядке.
   Потеря reply читает прежний send receipt; изменение DTO требует нового Send intent.

### Edge: Rewind при закрытой legacy History

1. Состояние: пользователь находится на legacy surface, где History ещё является закрываемой side-panel; Timeline виден рядом с живым или остановленным Claude/Codex terminal.
2. Юзер запускает обычный `Откатиться` из Timeline. Rewind проходит тот же native picker/backtrack flow, как если бы History была открыта.
3. После успеха приложение сохраняет локальный draft и preview-состояние для этой вкладки, а не пытается сразу писать в отсутствующую textarea. Terminal composer при этом уже очищен через тот же grab/clear path.
4. Юзер открывает `Cmd+]`. History показывает восстановленный prompt в input и тот же preview/rollback-state, который был бы виден при открытой панели. Очистка draft происходит только после успешного Send или явного clear, не от факта закрытой панели.

### Edge: новая готовая Codex-вкладка без первого prompt

1. Native создаёт новую вкладку; metadata-only UUID и pending startup ещё не
   дают loaded-empty. Без main read proof History может вернуть409.
2. Exact main ready edge на том же idle lease публикует read SID для отдельно
   проверенного полного standalone empty source. Bounded History GET возвращает
   обычный200/entries[]/total0/revision, без writer promotion/пробного Send.
3. Reopen/background остаются catch-up reads, не новым Start/Resume. Unknown/
   partial/thin fork не превращаются в empty. Начало настоящего Send/изменение
   source снимают old empty proof; поздний zero на SAME SID не стирает новый turn.

### Edge: Codex Rewind на prompt с картинкой

1. Состояние: target user-turn в Codex содержит image attachment, а в rollout text виден placeholder вроде `[Image #1]`.
2. После rollback Codex может вернуть в composer не тот же буквальный текст: placeholder, путь к локальному файлу или image-chip являются разными представлениями одного вложения.
3. History input получает восстановимый draft с `[imagePath: ...]`, если путь из rollout metadata ещё доступен; следующий Send снова отдаёт Codex путь так, чтобы он поднял image chip.
4. Если файл картинки уже недоступен, History показывает явный `imageError` в draft и warning-toast. Это не красная ошибка «выбран другой prompt», потому что rollback мог быть правильным, но вложение нельзя восстановить без файла.

Native image Send16.09: после confirmed audit History ref использует original
upload path и exact staged transport annotation. Native footer и ref должны
слиться как две representations одной ordered occurrence; следующий намеренный
повтор того же path остаётся второй occurrence. Проверить same user UUID read,
reopen/receipt TTL/child copy; не повторять Send ради устранения двойного preview.

### Edge: открыть terminal и вернуться к History

1. Состояние: в History textarea есть недоотправленный prompt или восстановленный после Stop текст.
2. Юзер открывает floating terminal через status-control, проверяет TUI и сворачивает окно повторным кликом.
3. Primary History всё время сохраняет тот же draft. Видимость terminal — не clear; то же правило действует при закрытии и повторном открытии legacy side-panel.

### Edge: открыть terminal после долгой фоновой работы

1. Состояние: Claude/Codex PTY запущен в фоне, History остаётся основной поверхностью, а renderer xterm этой вкладки ещё не создавался. За это время TUI успевает вывести много дифференциальных кадров либо процесс естественно завершается.
2. Юзер открывает floating terminal через status-control. Первый видимый кадр показывает текущее либо последнее завершённое состояние TUI, а не shell prompt и не строку запуска; History draft и lifecycle не меняются.
3. Пока полный main/headless snapshot переносится, более новый PTY-output догоняет его в том же поколении. Timeline продолжает адресовать восстановленные prompt boundaries.
4. Юзер закрывает и снова открывает terminal. Экран не пересобирается из случайного raw-хвоста, не смешивается с новым PTY того же tab и остаётся функциональным для ввода, поиска и scroll-to-bottom.

### Edge: вернуться в большую History без Loading

1. Состояние: вкладка A уже показала большую History и сохранила последний ограниченный snapshot; пользователь переключается на вкладку B.
2. Пока B активна, transcript A может измениться или остаться прежним. Локальные queued/sent/rewind-строки A остаются отдельным слоем и не превращаются в durable cache.
3. Пользователь возвращается A. В первом кадре он видит известные строки, а не экран `Loading`; один последний exact snapshot сохраняется даже если лишь немного превышает обычный byte-budget. Фоновая проверка revision решает, нужен ли новый parse.
4. Если transcript изменился, owner, rows и loading нового поколения применяются одной фазой. Между loader и данными нет кадра с пустой History; поздний ответ первого открытия A после цепочки A → B → A отбрасывается, а локальный draft и handoff-строки сохраняются.

См. `fact-история-как-основная-поверхность.md`, `fact-claude-tui-control.md::Cmd+] History send preflight`, `fact-claude-tui-control.md::Rewind Automation`, `fact-timeline.md::Rewind (Откатиться)`, `fact-codex.md::Timeline и History`, `fact-claude-control-bar.md::Codex mode в том же bar`, `fact-claude-awaiting-input.md::HistoryPanel: AskUserQuestion как пульт для Ink TUI`.

## Сценарий: Run after отправляет Codex без фокуса окна

Юзер ставит следующий prompt в очередь и уходит из окна Noted Terminal. Ожидание: выбранная Codex-вкладка остаётся целью автоматизации, но приложение не должно вытаскивать окно на передний план и не должно требовать живой renderer-отрисовки для отправки.

### Основной путь

1. Состояние: вкладка A — Codex PTY с активным turn'ом, в Prompt Queue лежит следующий prompt и включён Run after.
2. Юзер переключается в другое приложение или сворачивает/прячет окно Noted Terminal. Вкладка A остаётся target'ом очереди, но её terminal surface может не перерисовываться в renderer.
3. Codex штатно заканчивает turn: rollout пишет `task_complete` с непустым `last_agent_message` либо корневым assistant `final_answer`, чей явный `turn_id` совпадает с завершившимся turn. Runner видит подтверждённый натуральный busy→idle edge и забирает head очереди.
   Если текущая работа — explicit `/compact`, его итог доказывает `compacted`
   между началом и завершением того же operation. Отсутствие assistant final
   не disarm'ит ни собственную очередь, ни другую вкладку, ожидающую этот compact.
4. До IPC History фиксирует immutable handoff: prompt сразу появляется справа как `SENDING`, а его prompt/paste-чипы сохраняют presentation. Тяжёлый durable snapshot и видимость raw terminal не являются условием первого показа.
5. Перед paste приложение проверяет, что в Codex composer нет чужого draft'а. Если draft есть или состояние неизвестно, prompt остаётся в очереди и Enter не нажимается.
6. Prompt отправляется ordered PTY paste+Enter. Для Codex нет pre-Enter ACK: renderer draft и PTY render/sync marker не доказывают, что composer принял весь текст, особенно когда вкладка hidden/background. Перед Enter допустим только guard от чужого draft'а и startup blockers. Физический Enter пользователя сериализуется с этим же PTY-потоком и не может отправить тот же paste второй раз.
7. После записи Enter в ordered PTY stream main возвращает `submitted:true`: в этот момент ownership prompt'а переходит от очереди к агенту, поэтому карточка удаляется, а History-handoff остаётся до exact durable adoption. Rollout audit ближайшего `user_message` подтверждает точность доставки, но поздний timeout аудита не возвращает уже отправленную карточку — иначе повторный Run after создаст дубль.
8. Пока durable snapshot ещё тяжёлый или stale, canonical live-поток дополняет History assistant/tool-событиями. Финальный refresh удаляет только совпавшие live identity; закрытие и повторное открытие вкладки не должно быть способом «разбудить» историю.

Если Codex audit уже знает physical byte offset, но ещё не canonical UUID,
main получает номер строки без загрузки всех raw records и дополняет прежнее
подтверждение. Timeline получает адресуемую точку до тяжёлого refresh, затем
canonical snapshot забирает её без дубля. Ошибка адресного чтения сохраняет
подтверждённую отправку; повторно нажимать Send из-за отсутствия UUID не нужно.

### Edge: Claude compact → настройки → сообщение очереди

1. В Run after у следующей карточки задана пара Model/Effort. Compact завершается,
   main подтверждает модель, затем effort, и только потом runner отправляет prompt.
2. History получает отдельные сохранённые JSONL-строки настроек по live-каналу;
   они видны перед следующим user-message даже если полный refresh ещё ждёт
   окончания работы/освобождения input priority. Timeline не считает настройки
   отдельными пользовательскими итерациями.
3. Полный snapshot позже заменяет эти строки по тем же UUID без дубля/перестановки.
   Ошибка настройки по-прежнему останавливает отправку; строка команды в History
   не является самостоятельным подтверждением успеха. См. [live History](../knowledge/fact-живой-ответ-в-history.md).
4. Пользователь несколько раз прокручивает вверх/вниз, пока ответ продолжает
   обновляться, либо возвращается из другой панели: остаётся по одной строке
   на реально выполненную команду. При чтении выше текст не уезжает; у низа
   история продолжает следовать за ответом. Новый настоящий выбор тех же
   настроек даёт новые строки, а не скрывается сравнением одинакового текста.

### Edge: Run after подготовлен до запуска агента

1. Состояние: fresh или остановленная Codex PTY-вкладка уже показывает primary History, но живой агент ещё не запущен. Юзер добавляет prompt и включает Run after.
2. Очередь сохраняет это как обещание, но не вставляет текст в shell и не запускает delay: отсутствие процесса не считается idle-сигналом готового агента.
3. Юзер нажимает Start/Resume. Runner ждёт авторитетную связку process active + input-ready + turn idle; update/trust/directory/startup blocker не разрешает paste.
4. Только после readiness начинается настроенная задержка и обычный ordered paste+Enter. Если готовность неизвестна или запуск сорвался, карточка и arm остаются видимыми, а Enter не отправляется.

### Edge: hidden renderer не ответил после paste

Если renderer в фоне не успел доказать `hasDraft=true`, это не должно само по себе блокировать отправку. `submitted:false` означает, что Enter не был записан: карточка остаётся, автоматика выключается. `submitted:true` означает, что Enter уже ушёл: карточка удаляется даже при позднем или неподтверждённом rollout audit, чтобы повтор не отправил дубль. Возвращать обязательный post-paste UI/render ACK как pre-Enter gate нельзя.

### Edge: Codex закончил ход без результата

Если terminal completion содержит typed error, это отдельный сохранённый отказ,
а не отсутствие данных: History/messages показывают один error carrier с причиной.
Reload возвращает ту же строку по identity; исходный Send остаётся confirmed,
живой свободный CLI — active. При ошибке отозванного токена нужен отдельный вход
в соответствующий аккаунт, не автоматический повтор уже принятого prompt.

1. В активном turn Codex получает upstream-ошибку; TUI может показать `403` или другой error, но rollout заканчивается `task_complete` с пустым/null `last_agent_message` и без корневого assistant `final_answer`, явно привязанного к тому же turn. Rollout доказывает отсутствие подтверждённого результата, но не обязательно точный класс upstream-ошибки.
2. Loader снимается и composer снова становится доступен, потому что ход действительно закончился. Это ещё не означает, что пользователь получил результат.
3. Main публикует исход `codex-no-final-result`. Связанный Run after выключается, queued prompt остаётся в панели и Enter не нажимается; Git Run after отменяет текущую задачу; one-shot completion notification гасится без звонка, но persistent-настройка сохраняется; Restart after пропускает текущий edge, сохраняя постоянную подписку.

### Edge: приложение восстановилось между постановкой и результатом

До завершения hydrate очереди и workspace restore runner только собирает live-события и snapshot Codex. После барьера он сначала применяет все ошибки, затем только самый новый штатный исход каждого trigger'а. Исход действует лишь на обещание, поставленное не позже него: старая ошибка не снимает новый ручной retry, а неизвестное время постановки или результата не даёт права отправить prompt.

### Edge: цепочка из нескольких Run after

1. Вкладка B содержит prompt и ждёт завершения вкладки C; вкладка A содержит следующий prompt и ждёт B. Пока C работает или ещё не запускалась, B отмечена hourglass и не считается завершённой только из-за отсутствия собственного loader'а.
2. После штатного завершения C runner отправляет prompt в B. Промежуток до появления loader'а B остаётся частью той же цепочки, поэтому A не запускается.
3. Только после реального запуска и штатного завершения B prompt отправляется в A. Связь, создающая цикл вроде `A → B → A`, не сохраняется и сопровождается предупреждением.

См. `fact-prompt-queue.md::Auto-run стреляет ТОЛЬКО на штатный конец turn'а`, `fact-codex.md::Timeline и History`, `fact-terminal-core.md::safePasteAndSubmit`.

## Сценарий: Пауза связи с дочерним исполнителем

Юзер хочет временно обсудить что-то с дочерним Claude/Codex, не завершая его процесс и не возвращая промежуточный ответ оркестратору.

### Основной путь

1. Состояние: вкладка A ждёт результат дочерней вкладки B; A показывает фиолетовую наследованную активность.
2. Юзер останавливает текущий ход B через Escape. Связь переходит в жёлтое ожидание с loader и предупреждением; Run after и Build Install по-прежнему ждут, но фиолетовая анимация A гаснет.
3. Юзер нажимает Pause на карточке связи. Процесс B не останавливается: юзер отправляет ему уточняющие сообщения и читает ответы локально.
4. Ответы и вложенные вызовы, начатые во время паузы, не снимают ожидание A и не передаются ему как итог исходной задачи.
5. Юзер нажимает Resume. Карточка остаётся жёлтой и блокирующей, пока в B не начнётся новый ход; старый ответ из паузы не воспроизводится.
6. Юзер пишет B «продолжай». Точный новый старт возвращает фиолетовую активность A. После штатного завершения этого хода его результат возвращается A один раз.

### Edge: отвязать вместо Resume

Крестик закрывает только связь: A больше не ждёт и не получит результат, а B продолжает жить. Пауза и ожидание нового хода переживают restart; после начала передачи результа Pause уже недоступна.

См. `fact-оркестрация-вкладок.md::Ошибка, восстановление и очистка`, `fact-prompt-queue.md::Auto-run стреляет ТОЛЬКО на штатный конец turn'а`.

## Сценарий: очередь с изображениями переживает закрытие приложения

Юзер собирает в Codex/Claude draft промпт с несколькими картинками, переносит его в Run after и закрывает Noted Terminal. Ожидание: после cold launch в очереди остаются и текст, и сами изображения, даже если исходный cache/temp агента уже очищен.

### Основной путь

1. Состояние: в live composer есть текст и два или больше image chips; у каждого есть конкретная slot-привязка.
2. Юзер нажимает `+Grab`. Карточка появляется сразу со статусом сохранения вложений, а байты каждого файла переходят в хранилище, которым владеет Noted Terminal. До завершения этого шага карточку нельзя отправить через Replay или Run after.
3. После успешного копирования карточка получает стабильные идентификаторы обоих файлов и становится готовой. При штатном закрытии приложения shutdown-flush синхронно сохраняет актуальное состояние очереди в SQLite.
4. На cold launch данные карточек сразу возвращаются в store, а файлы повторно проверяются. Пока проверка не закончена, вложение не притворяется готовым.
5. Replay или Run after ещё раз проверяет оба файла перед передачей prompt агенту. В Codex сохранённый файл подставляется через короткий служебный путь без пробелов и снова становится нативным image chip; только после успешной отправки очередь удаляет карточку.

### Edge: действие до окончания hydrate

Если сразу после запуска юзер успел добавить ещё один prompt, ответ SQLite объединяет persisted и новые items по id. Появление in-memory очереди не даёт права пропустить всю сохранённую очередь этой вкладки.

### Edge: managed-файл утрачен

Если один из файлов реально пропал уже из хранилища Noted Terminal, карточка остаётся в очереди с missing-state, а автоматика disarm'ится. Нельзя молча отправить только текст и удалить item как будто вложение было доставлено.

### Edge: marker изображения отредактирован

Точная `[Image #N]` в редакторе подсвечена синим. Если юзер обрезал скобку, экранировал marker или изменил номер на неизвестный, синяя подсветка исчезает, карточка показывает повреждение и не отправляется через Replay/Run after; файл при этом не теряется. Полное удаление marker'а считается осознанным удалением соответствующего вложения, остальные изображения остаются готовыми.

Сценарий гарантируется для штатного закрытия; `kill -9`/потеря питания не дают renderer'у выполнить синхронный shutdown-flush. См. `fact-prompt-queue.md::Image-paths resolution из grabbed [Image #N]` и `fact-prompt-queue.md::Store (usePromptQueueStore.ts)`.

## Сценарий: Restart after AI completion

Юзер держит обычную terminal/dev-вкладку с локальным процессом и хочет перезапускать её только после завершения работы AI-вкладки. Это не очередь prompt'ов: AI-таб является триггером, а целевая вкладка остаётся обычным терминалом или dev-server.

### Основной путь

1. Состояние: вкладка A — обычный terminal/devServer, вкладка B — Claude/Gemini/Codex/SDK с активной или будущей работой.
2. Юзер открывает ПКМ по вкладке A, выбирает `Restart after` и указывает одну или несколько AI-вкладок через тот же picker AI-вкладок, что используется для Run after. В этом сценарии picker работает как multi-select: клик по вкладке toggl'ит её и меню не закрывается.
3. Если нужно не повторять последнюю команду, а запустить конкретный script, юзер выбирает `Script` из npm/sh списка этой вкладки.
4. Непустой список выбранных trigger-вкладок сам является включённой подпиской, пока `Restart after` не поставлен на pause. Отдельного шага с one-shot/persistent bell нет. Вкладка A получает фиолетовый restart-marker даже если dev-процесс сейчас остановлен; paused-состояние серит marker/строки меню, но сохраняет выбранные вкладки и script.
5. Когда вкладка B завершает AI-turn штатным busy-end, вкладка A сначала получает controlled stop старого процесса. Если выбран script — после stop в терминал A отправляется этот script; если процесса нет, script стартует с нуля. Если script не выбран — запускается обычный restart-путь текущей команды.
6. Если выбранный конечный script ещё выполняется после предыдущего trigger'а, новые завершения любой выбранной trigger-вкладки не прерывают его и не запускают второй экземпляр. Вкладка A получает один pending rerun; когда текущий script завершится через `terminal:command-finished`, script стартует ещё раз. Несколько завершений разных trigger'ов за время одного долгого script'а схлопываются в один повтор. Для `dev`/`start`/`serve`/`watch` сохраняется restart-поведение, потому что такие команды обычно не завершаются сами.

### Edge: очистить подписку

Юзер может временно выключить `Restart after` без потери выбора: кликом по строке `Restart after` в ПКМ-меню или pause-кнопкой слева от restart-кнопки в vertical sidebar. Это ставит `restartAfterPaused`, серит trigger/script UI и не даёт natural completion запускать side effect. В paused-state pause-иконка остаётся pause-иконкой, но перечёркивается диагональю. Полный сброс остаётся отдельным действием: крестик справа от выбранного trigger'а в ПКМ-меню или `Cmd+click` по restart-after кнопке в vertical sidebar. При `Cmd+hover` эта кнопка показывает X; clear не останавливает живой devServer. Красный square-stop на Cmd-hover относится только к обычному зелёному devServer без restart-after.

### Edge: ненатуральный конец AI-триггера

Manual Stop, interrupt/error/watchdog и Codex `turn_aborted` / `codex-no-final-result` не запускают Restart after и не делают side effect в целевой вкладке: пользователь остановил или сломал ожидание результата, значит перезапуск dev-процесса был бы ложным следствием. Сама подписка при этом остаётся пользовательской настройкой до явного clear, потому что она описывает будущий trigger-source, а не одноразовый bell-arm.

См. `fact-scripts.md::Restart after AI completion`, `fact-prompt-queue.md::Auto-run стреляет ТОЛЬКО на штатный конец turn'а`, `fact-tabs.md::Уведомление о завершении вкладки`.

## Сценарий: Диктовка продолжается после ухода с вкладки

Юзер начал диктовать prompt в live Claude/Codex табе, но во время записи переключился на другую вкладку, другой проект или Home. Запись должна продолжаться в фоне и оставаться привязанной к вкладке старта; новый экран не становится владельцем микрофона только потому что он сейчас видим.

### Основной путь

1. Состояние: вкладка A — live Claude/Codex PTY, в ControlBar видны `mic` и `Enter`. Юзер нажимает mic, owner фиксируется как `{projectId, tabId, tabName, mode}` вкладки A.
2. Юзер уходит на вкладку B, другой проект, Home или Dashboard. Soniox stream продолжает идти в фоне; floating transcript вкладки A не переносится на новый экран.
3. Если текущая поверхность тоже live Claude/Codex, её mic показывается disabled: запись уже принадлежит вкладке A, второй старт не должен менять owner.
4. Справа сверху под transient-toasts появляется постоянная строка `RECORDING` с коротким именем вкладки A. Это статус фоновой операции, не warning и не одноразовое уведомление.
5. Юзер кликает имя вкладки в status-row. UI возвращает проект и вкладку A, включает terminal view и сбрасывает subagent viewport, если пользователь был в дочернем просмотре.
6. На вкладке A mic/floating transcript показывают текущую фазу записи. STOP или `Enter` доставляет финальный текст в composer вкладки A, а не в вкладку/проект, где пользователь находился до возврата.

### Edge: Enter на другой live-вкладке

Если пользователь находится на вкладке B, пока запись идёт во вкладке A, `Enter` в B не ждёт чужой `dictation:delivered`. Owner-scoped ожидание нужно только там, где Enter семантически означает «заверши мою диктовку и отправь мой prompt». Mic disabled на B предотвращает второй concurrent-start, но не превращает весь ControlBar B в pending-state.

См. `fact-dictation.md`, `fact-claude-control-bar.md`, `fact-workspace.md`.

## Сценарий: Уведомление о завершении фоновой вкладки

Юзер запускает долгий AI-ход во вкладке, но хочет уйти заниматься другим проектом и получить явный сигнал, когда ход завершится. Сценарий связывает ПКМ-меню вкладки, busy-state reasons, project-tab aggregation, системный звук и acknowledgement при возврате.

### Основной путь
1. Состояние: вкладка A — Claude/Gemini/Codex/SDK tab, ход ещё не завершён или будет запущен следующим prompt'ом. Юзер открывает ПКМ по вкладке и нажимает «Активировать уведомления» в широкой части split-row.
2. One-shot notification armed. Если включена правая компактная часть split-row, persistent-режим сохранится и каждый следующий busy-edge будет сам заново армить уведомление.
3. Юзер отправляет prompt и уходит на другую вкладку, другой проект, Home или Dashboard. Вкладка A может показывать обычный process/busy shimmer, но completion notification пока не считается сработавшим.
4. AI-ход завершается natural completion edge'ом. Если включён звук, проигрывается разовый системный звук; native notification создаётся silent. Так как target сейчас не виден, сама вкладка A получает красную traveling-border рамку, а project tab получает красный count-badge и красную рамку.
5. Юзер кликает project tab или саму вкладку A. Notification state очищается сразу: count и fired-state больше не кормят store. Красная рамка может плавно затухнуть на месте как exit-анимация, но это уже presentation-layer, не pending-состояние.

### Edge: завершение пока вкладка активна
Если пользователь включил уведомление и остался на той же terminal-вкладке до natural completion, звук всё равно срабатывает: он явно попросил разовый audible signal. Но unread-красная рамка не взводится, потому что пользователь уже видит owner surface и acknowledgement фактически произошло.

### Edge: native iOS открывает уведомление

На iPhone completion notification не считается прочитанным от одного входа в проект. Root badge на AI Chat и project-chip подсветка только приводят пользователя к области, где лежит target; acknowledgement происходит, когда native Terminal mode открыл именно вкладку A. Если тап по системному уведомлению догнал desktop clear или вкладку уже закрыли, clear endpoint всё равно успешен и локальный badge должен погаснуть по следующему full `project-activity` snapshot'у.

### Edge: iPhone свернут или заблокирован

Если iOS app уже suspended/locked, `project-activity` SSE не является delivery-каналом.
Natural completion edge должен породить remote APNs alert с тем же `projectId/tabId/firedAt`,
а foreground/local notification остаётся только fallback'ом для открытого app. После тапа по
APNs iOS сначала применяет payload в local unread-state, затем открывает AI Chat → Terminal
mode → target tab и только там вызывает clear. Без APNs entitlement, device token и provider
credentials этот edge считается не настроенным, даже если badge корректно появится после
ручного foreground catch-up.

### Edge: ручная остановка или Escape
Escape, Stop, interrupt, close, `turn_aborted`, `codex-no-final-result`, watchdog/error cleanup и локальные slash-command cancel edges не являются завершением результата. Они гасят busy/liveness UI, но не звонят, не создают native notification и не зажигают красный fired-state. Иначе пользователь, который сам отменил ожидание результата, получит ложный сигнал «готово».

См. `fact-tabs.md::Уведомление о завершении вкладки`, `fact-settings.md::Уведомления вкладки / Системный звук`, `fix-claude-busy-detection.md::reason:'manual-stop' payload`.

## Сценарий: Multi-select Persistence при работе с боковой панелью

Юзер выделил несколько вкладок (Shift+Click диапазон или Cmd+Click по одной), хочет применить к ним массовое действие из боковой панели (batch-copy session, групповая Stop). Раньше любой клик в панели сбрасывал выделение — пока юзер кликал в поле ввода, multi-select исчезал, и батч-операция отрабатывала только по последнему clicked-табу.

> Панель действий с кнопкой Docs, на которой этот сценарий возник, удалена
> 2026-08-18. Механизм `data-keep-selection` остаётся обязательным для любой
> новой панели, переживающей multi-select.

### Основной путь
1. Юзер удерживает Shift: активная вкладка становится anchor, hover другой видимой строки сразу показывает будущий диапазон; один Shift+Click фиксирует его в `useWorkspaceStore`. `Cmd+Click` добавляет/снимает отдельные строки. Выделение визуально маркировано (dashed-white border на вкладках).
2. Юзер перемещает курсор в боковую панель справа, кликает по полю ввода или по toggle'у настроек.
3. Click bubble'ит до document-level `mousedown` handler'а в `TabBar.tsx`, который раньше всегда вызывал `clearSelection`. Сейчас handler сначала проверяет `e.target` и всех его родителей на атрибут `data-keep-selection` — контейнер такой панели этим атрибутом помечен.
4. Выделение **сохраняется**. Юзер свободно вводит текст промпта, переключает toggle'ы.
5. Юзер кликает action-кнопку (Copy / Stop N) — операция отрабатывает по всему выделенному набору.

### Edge: клик вне `TabBar` и вне `data-keep-selection`-зоны
Клик в терминал, в Timeline, в любую другую панель без атрибута → `clearSelection` срабатывает как раньше. Это сознательно: multi-select имеет смысл только пока юзер работает с инструментами над табами; уход в терминал = намерение работать с одним конкретным.

См. `fact-tabs.md::Multi-Select`, `fact-clipboard-tools.md`.

## Сценарий: очистка AI-сессий на глобальном Home

Пользователь открывает Home и хочет увидеть, почему диск занят, не смешивая
закрытые разговоры, живые процессы и build cache. Путь проходит через Home UI,
main inventory, Noted DB, provider storage и повторную защиту перед delete.

### Основной путь
1. Home показывает `MCP servers → Storage → AI processes`; Storage закрыт и не
   участвует в initial Dashboard scan.
2. Пользователь раскрывает Storage. Main одним bounded scan читает metadata
   Claude/Codex, связи Noted Terminal и build/app directories; полный transcript
   не парсится.
3. В `Sessions` пользователь выбирает `All / Codex / Claude`, группу, date
   range и сортировку. Cmd-hover объясняет группу; выбранная detail-строка
   лениво получает iteration count.
4. Открытая session и нужные ей physical sources показывают `Protected`.
   Закрытая session получает countdown из group retention.
5. Checkbox выбирает строку; Shift+Click после любого scroll выбирает диапазон
   по полному virtual array. Header checkbox/`Select all N` выбирает все
   deletable filtered rows. `Delete selected`, `Delete now` либо `Clean ready`
   сначала показывает inline count+bytes, затем item-progress. После
   подтверждения renderer передаёт opaque IDs и scan generation.
6. Main повторно читает inventory/runtime/DB. Изменившаяся или открывшаяся
   session остаётся; Claude удаляется exact file contract, Codex — provider
   thread-delete. UI убирает строки только после ACK и делает fresh scan.

### Edge: возврат на Home

Пользователь раскрывает Storage, уходит в Project Home/Workspace и возвращается
на глобальный Home. `SpaceStrip` остаётся тем же экземпляром; Storage сразу
показывает cached metadata и прежнее раскрытие, без initial scan loader и без
фонового disk revalidate. History/Timeline/transcript ради Dashboard не
монтируются и не читаются; обновление списка — явный Refresh либо mutation.

Пока Home открыт, Tab и программный focus не попадают в скрытый composer,
а оставшийся workspace popup не перехватывает клик по Dashboard. Обратный
переход возвращает те же scrollers, draft и порядок клавиатурной навигации;
добавленные во время скрытия controls тоже получают правильный tabindex.
См. [presentation и focus](../knowledge/fact-рабочая-область.md).

### Edge: Home History остаётся без физического transcript

Закрытая Noted session может быть удалена по принятой политике одного дня, но
`tab_history` row остаётся. Project Home сохраняет title/project/date и явно
получает missing transcript при Preview/Resume; cleanup не перепривязывает
карточку к похожему файлу и не удаляет её молча.

См. `fact-хранилище-сессий.md`, `fact-project-home.md`,
`fix-interrupted-session-lifecycle.md`.

## Сценарий: автоматическое восстановление AI-сессий после неожиданного выхода

При проверке source14.09 включать отдельные Codex Goal/usage ветви: один Resume,
configured Resume/Leave paused, текущий committed result после выбора; потеря
HTTP ответа не вызывает новый Resume или Enter. Известный оставшийся dialog
даёт статический manual warning при живом процессе. Для usage default выбирает
только Luna Reserve; альтернативная политика останавливает exact Codex jobs
через общий process Stop, не через composer interrupt. После fallback и возврата
на Sol/Astra проверить одинаковую фактическую модель в params/status/activity/UI,
не меняя намерение пользователя. Новый native retake этих ветвей пока открыт.

Приложение сохраняет точный shutdown-набор живых Claude/Codex вкладок и после
cold-launch восстанавливает их без общей модалки и ручного Continue. Recovery не
блокирует workspace: каждая вкладка показывает собственное состояние, а
launch-команды идут последовательно, чтобы несколько process lookup и startup
не образовали storm.

### Основной путь
1. Состояние: в одной или нескольких вкладках живы idle либо busy Claude/Codex.
2. Пользователь закрывает приложение, запускает Build Install или приложение
   аварийно завершается. До остановки PTY main замораживает точные
   `{tabId, provider, sessionId}`; сохранённый `commandType` и просто наличие
   старой истории не добавляют вкладку в набор.
3. После cold-launch renderer сначала восстанавливает workspace и вкладки, затем
   получает этот неизменный набор. Ожидающая цель никак не выделяется визуально
   (с 2026-09-11 плашки `SESSION INTERRUPTED` и синей пунктирной рамки нет —
   вкладка выглядит просто неактивной); Home, другие окна и History доступны.
4. AutoResume запускает цели по одной. После принятой команды очередь ждёт
   main-owned ready, ручной blocker либо окончательную ошибку и только затем
   переходит к следующей вкладке.
5. `wasInterrupted` очищается после input-ready proof либо после доказательства,
   что именно эта session уже запущена другим допустимым действием. Ранний
   `inactive` сразу после записи launch-команды не завершает шаг.
6. Ошибка одной ещё не принятой цели сохраняет её recovery intent, показывает
   постоянный жёлтый (warning) tab-scoped toast «Ошибка запуска …» с копируемыми
   tab/session/time/reason и разрешает очереди продолжить остальные цели.
   Жёлтый, не красный: сессия не потеряна, она на паузе и возобновляется
   вручную. Accepted startup с неизвестным исходом останавливает проход: второй
   launch поверх него запрещён.

### Edge: пользователь отправляет сообщение, пока вкладка ждёт своей очереди
1. Поздняя вкладка ещё помечена interrupted, но AutoResume восстанавливает более
   ранние цели. Пользователь открывает её и отправляет prompt через History.
2. Общий send-сценарий видит остановленный runtime, запускает или возобновляет
   точную session и после готовности отправляет prompt один раз.
3. Когда AutoResume позже доходит до этой цели, он непосредственно перед launch
   перечитывает main-owned runtime. Точный live writer либо точный запускающийся
   Resume той же пары tab+provider+session означает «уже восстановлено»:
   очередь присоединяется к существующему lifecycle, очищает marker и не пишет
   вторую команду.
4. Если ручной запуск попал в узкое окно уже после этой проверки, main отклоняет
   второй Resume как `foreground_command_running`; AutoResume повторно читает
   runtime и превращает отказ в успех только для той же точной session.
5. Чужой writer, другая session и unresolved owner остаются ошибкой. Совпадение
   только с сохранённой History session не даёт права скрыть конфликт.

### Edge: Codex Resume дописывает исходную сессию

При холодном открытии большой сохранённой сессии resource-icon в общей шапке
становится малиновым на время известной подготовки. Пользователь может открыть
ресурсы или перейти в другое окно; число памяти и размеры кнопки сохраняются.
Окончание одной загрузки не снимает цвет, пока готовится другая. После подготовки
цвет обычный; дальнейший ответ агента сам по себе его не включает. В невидимых
окнах обновляются данные и сохраняется draft/scroll, но не крутятся бесконечные
визуальные индикаторы. Возврат показывает прежнюю поверхность с актуальным
статусом, без повторного запуска агента ради показа.

1. После Continue Codex показывает готовый composer, но source ещё provisional: History доступна, обычный ввод разрешён, identity-зависимые действия ждут writer proof.
   Fork/Compact Fork — отдельное исключение: он не меняет source и может снять
   точный snapshot с idle Resume read identity. Это не делает source writer’ом
   и не разрешает Edit/Delete.
2. Юзер отправляет prompt. Короткий delivery-loader заканчивается после передачи Enter, но это не завершает turn.
3. Source rollout получает `task_started`; после process-to-file proof main replay'ит удержанный диапазон и публикует один общий `busy=true`. Primary History, вкладка, проект и публичные потребители показывают один продолжающийся ход, даже если terminal скрыт.
4. Rollout дописывает `task_complete` или `turn_aborted`. Тот же общий lifecycle публикует `busy=false`; только подтверждённый успешный результат разрешает Run after, Restart after и completion-уведомления.

### Edge: AutoResume восстанавливает вкладки независимо
После cold-launch каждая Claude/Codex-вкладка получает runtime `starting` и
собственную неблокирующую status-плашку: terminal surface, History, список
проектов и другие вкладки остаются доступны, а Send/Resume/Rewind читают тот же
runtime gate. iOS и внешние клиенты видят тот же `starting` через API.

Для Claude отказ `/model` после запуска заканчивает настройку явной ошибкой,
не означает смерть CLI. Пользователь видит короткую причину по-русски и может
скопировать полный отчёт. После закрытия сообщения и повторного открытия вкладки
та же ошибка не воскресает и не превращается в Starting: состояние процесса
читается независимо. Выбор другой модели остаётся доступен; закрытие ошибки само
не отправляет pending prompt. Повтор уже идущей настройки присоединяется к ней,
а новая ошибка другой попытки показывается заново. Source14.09 проверен на
actual main/reducer/Copy; packaged UI/CLI-повтор ещё не выполнялся.

После установки версии с отключённым Astra sparkle новый управляемый Codex
получает `tui.whimsy=false` при AutoResume так же, как при Start/Continue/Fork.
Пустая подсказка не должна содержать звёзды, а обычные анимации и настоящий
braille-ввод сохраняются. Установка исходников сама по себе не меняет настройки
уже работающего CLI: для проверки нужен его следующий запуск, не reload History.

Для Codex отдельный edge — зависание на `Starting MCP servers ... esc to interrupt`. Это не состояние composer'а: AutoResume ждёт readiness/watchdog в том же общем Codex startup layer, что History/Rewind/API. Один скрытый Codex-tab не должен держать весь экран или следующий batch; он держит только свой per-tab `starting`/diagnostic state. Первый `inactive` сразу после отправки `codex-c` не считается завершением восстановления, потому что runtime-start мог ещё не дойти до presence; иначе статус исчезает до первого paint, а пользователь видит обычный терминал при продолжающемся фоне.

### Edge: закрытие последнего окна с живыми AI-вкладками
1. Состояние: в нескольких вкладках живы idle или busy Claude/Codex-процессы.
2. Юзер закрывает последнее окно. Приложение переводит это действие в штатный quit до уничтожения PTY, помечает только реально живые AI-сессии и завершается; ждать окончания их turn'ов не нужно.
3. Юзер снова открывает Noted Terminal. Сохранённые вкладки появляются с прежними session id.
4. AutoResume последовательно запускает агент в каждой ранее живой вкладке.
   Одна отклонённая цель не блокирует остальные, но принятый запуск с
   неизвестным исходом удерживает очередь от второго процесса.

### Edge: юзер останавливает восстановленный агент
Stop после Continue/AutoResume проходит через `active|busy|starting → stopping → inactive`. В `stopping` пользователь уже сделал destructive action, но shell/rollout/bridge ещё не доказали, что агент умер. Desktop показывает неблокирующую status-плашку и оставляет scroll/selection/inspection, но main отбрасывает raw keyboard input и отклоняет paste до exit; History, Project API и iOS не дают send/resume/rewind. Это защищает от двойного действия «нажал Stop → сразу нажал Continue/Rewind», когда второй action попадает в процесс, который ещё teardown'ится.

### Edge: множественные сессии помечены wasInterrupted
Подводный камень в lifecycle — writer'ы shutdown/restart могут гонкой перетереть
друг друга. С точки зрения сценария AutoResume получает только те вкладки, где
при shutdown был доказан живой AI-процесс, а не все вкладки с сохранённым
session id. Полный разбор отброшенных подходов —
`fix-interrupted-session-lifecycle.md`.

См. `fact-claude-sessions.md::Interrupted Recovery`, `fact-codex.md::Interrupted recovery и AutoResume`, `fix-interrupted-session-lifecycle.md`, `fact-data-persistence.md`.

## Сценарий: Resume Inactive CLAUDE с мобилы

Когда юзер на мобильном открывает CLAUDE-PTY-таб, в котором Claude-процесс умер (Ctrl+C в десктоп-сессии, crash, app restart) — он должен иметь возможность «вернуть Claude к жизни» в тот же таб, чтобы продолжить сессию по тому же `sessionId` без потери истории и без открытия новой вкладки. Сценарий проходит через состояния `inactive → starting/resuming → active` и `active/busy → stopping → inactive`, координирует mobile-web UI, web-server bridge, main session-detector и PTY/Claude TUI.

Отдельная ветка этого же сценария — fresh Claude, остановленный до первого содержательного prompt'а. Вкладка может иметь технический UUID/JSONL, но пока transcript не materialized, это не сохранённый разговор: iPhone показывает Start, а не Resume, и copy-id не выглядит полезным действием.

### Основной путь

1. Юзер тапает CLAUDE-таб в project list мобильного — таб в state `inactive` (серая dot слева от имени). История JSONL уже видна в чате (загружена через `/history` REST, читается напрямую из `~/.claude/projects/...jsonl`).
2. Вместо composer внизу — оранжевый баннер «▶ Resume Claude session / session stopped · JSONL preserved».
3. Юзер тапает Resume. Mobile UI меняет состояние кнопки на loader. POST `/api/terminal-tabs/:id/resume` → bridge `resumeClaudeTab` action в renderer.
4. Renderer проверяет presence через `claude:get-presence` — status уже `inactive` (PTY жив, Claude процесса нет), значит можно слать. Зовёт `markPendingResume(tabId, sid)` (защита от stale bridge.json) и после доказанного запуска снимает durable interrupted-marker; отдельной desktop Continue-модалки больше нет. Шлёт `\x15claude --dangerously-skip-permissions --resume <sid>\r` в PTY.
5. PTY проглатывает команду, shell спавнит Claude process. Через 1-3 секунды Claude инициализируется и пишет `~/.claude/bridge/<sid>.json` → main Bridge detector ловит → `_notifyClaudeSession(tabId, sid)` → web-server promote pending watcher + `_webBroadcast({type:'snapshot', sessionStatus:'active'})`. Mobile получает snapshot — UI знает что Claude запустился (но prompt ещё не отрендерён).
6. Mobile отображает «Starting Claude…» strip (вместо composer и вместо Resume-баннера). Через ещё 1-3 секунды Claude Ink TUI рисует `⏵` в PTY-выводе → main глобальный детектор `⏵` → `claudePromptReady.add(tabId)` → `_webBroadcast({inputReady:true, sessionStatus:'active'})`. Mobile flip'нул UI на composer.
7. Юзер пишет промпт, тапает Send. POST `/api/terminal-tabs/:id/send` → bridge `sendMessageAuto` → routes to `terminal:paste {fast:false}` (single-bracket-pair, waitForRender). Claude получает paste через atomic bracketed paste, обрабатывает как обычный prompt.

Если пользователь вместо Send нажимает Stop до готового composer'а или во время turn'а, клиент не ждёт только финального `inactive`: он сразу видит `stopping` snapshot и держит stop-loader до exit. Локальный mobile `setStopping(true)` — только мгновенный feedback для собственного клика; source of truth для всех клиентов — серверный `sessionStatus:'stopping'`.

### Edge: Stop до первого prompt

1. Состояние: пользователь создал Claude через native iOS `New → Claude`; Mac уже доказал runtime `active/inputReady`, startup defaults прошли или дали явную ошибку, но `conversationMaterialized=false`.
2. Пользователь ничего не отправляет и останавливает процесс с desktop или iPhone. Клиент получает `stopping`, затем `inactive`, но не включает Resume: продолжать пока нечего.
3. Нижняя панель показывает Start Claude в том же визуальном классе, что Resume. Клик Start запускает fresh runtime в той же PTY-вкладке; только первый содержательный user/assistant turn включает Timeline, copy-id и будущий Resume.

### Edge: Claude уже живёт в табе на момент Resume

В очень узком окне (~1-2 сек) mobile status может показывать `inactive` тогда как Claude фактически уже поднялся (например, юзер тапает Resume в момент когда desktop AutoResume только что отработал). Если просто послать `\x15claude --resume`, Ctrl+U стёр бы typed text desktop-пользователя И выкинул бы его из Claude TUI обратно в shell.

`resumeClaudeTab` делает pre-check через `claude:get-presence` сразу перед отправкой команды. Если status вернулся `active` или `busy` — возвращает `{alreadyRunning: true}`, никакой команды в PTY не уходит, mobile сразу видит composer, а stale interrupted-marker снимается по точной session identity.

### Edge: composer залип на Stop сразу после Resume (stale glyph на `⏵`)

После успешного Resume Claude поднимается, и в шаге 6 основного пути PTY **реплеит старый скроллбэк** — а в нём висит протухший кадр спиннера от давно завершённого turn'а (`✻ Brewed for 4s`). В момент когда Claude рисует prompt-символ `⏵`, глобальный детектор шлёт телефону snapshot — и если он считает busy по глифу (`claudeSpinnerBusy`), протухший кадр ложно даёт `busy:true` → composer лочится на Stop. Юзер не может отправить сообщение; помогает **только refresh** страницы (свежая загрузка идёт через уже-починенный `get-presence`, не через `⏵`-snapshot).

Это второй busy-эмиттер на телефон, мимо presence-маппинга. Лечится тем же каноном что get-presence: snapshot при `⏵` обязан читать `claudeTurnBusy` (authoritative Stop-hook), не глиф. После фикса composer показывает Send сразу как `⏵` отрендерился, без refresh. Полная механика — `fact-mobile-claude-pty.md::Второй busy-эмиттер: ⏵-детектор`.

### Edge: ловля sessionId до того как WS subscribe'нулся

Если юзер быстро тапает по табу сразу после создания, mobile WS subscribe'тся, но `getClaudeTabStatus` ещё не вернёт sessionId (Bridge:Fresh не выстрелил). Web-server паркует tabId в `claudeTabWatcherPending: Set` без таймеров. Когда main позже звонит `_notifyClaudeSession(tabId, sid)` — promotion срабатывает: pending удаляется, fs.watch стартует, mobile получает `snapshot` с sessionId.

Если subscriber отвалился (юзер быстро навигировался прочь) — `releaseClaudeWatchersIfOrphan` срабатывает на WS close и чистит pending Set. Никаких orphan timers, всё event-driven.

### Edge: JSONL ещё не на диске

SessionId известен (bridge.json есть), но `findSessionFile` возвращает null — Claude батчит первые писания, JSONL появится через 100-500ms. Web-server ставит **одноразовый** `fs.watch` на `~/.claude/projects/` root: первое появление файла с этим UUID в имени → tryPromote → реальный fs.watch на сам файл. Один-выстрел event-driven, не polling.

См. `fact-mobile-claude-pty.md` для полной механики, `methodology/дизайн-принципы.md::Event-driven promotion вместо retry-polling` для переносимого принципа.

## Сценарий: Стоп ответа и фоновые агенты в SDK-табе

Юзер запустил в SDK-табе тяжёлую задачу — Claude отвечает и параллельно держит фоновых агентов (workflow / Agent-tool subagent). Хочет прервать **текущий ответ**, но не убить фон, и при этом детерминированно понимать, жив ли процесс. Сценарий проходит через три состояния процесса (стримит → припаркован-жив → убит) и две подсистемы (foreground-ход + background-агенты), поэтому в один `fact-*` целиком не ложится.

### Основной путь (soft → hard)
1. Состояние: процесс жив, идёт стриминг. Индикатор в строке управления — `работает` (пульсирующий янтарный); плашка активности вкладки пульсирует. Тот же сигнал (`tab.sdkProcessAlive` + busy) кормит оба места.
2. Юзер жмёт Escape (или точку вкладки / двойной Ctrl+C) — **soft-interrupt**: текущий ответ обрывается, на нём снизу встаёт плашка `⊘ stopped`. Процесс, сессия и фоновые агенты **остаются жить**. Индикатор → `активен` (ровный янтарный). Жать Escape хоть десять раз — ничего больше не закрывается.
3. Фоновый агент дорабатывает; когда закончит — его `task_notification` долетает по живому stream-loop'у, чип агента гаснет сам. (Это нативный «обратный callback» — работает именно потому, что сессию мы не убили.)
4. Юзер либо пишет новое сообщение — оно продолжает **ту же** сессию (mid-stream push), индикатор снова `работает`; либо кликает индикатор в состоянии `активен` → **hard-kill**: процесс и все агенты гаснут разом, индикатор → `остановлен` (серый). Поле ввода и история остаются доступны.

### Edge: warm-start из «остановлен»
Процесс мёртв (`остановлен`). Клик по индикатору поднимает процесс **вхолостую** (`claude-sdk:warm-start`, `prompt:null`) — индикатор сразу `активен`, без отправки сообщения, курсор в инпуте. Запуск идёт с `resume:<sessionId>`, поэтому первый же ход помнит прошлый диалог; пока процесс просто припаркован, в JSONL ничего не пишется (sessionId создастся только с первым реальным сообщением).

### Edge: Правка/Повтор при живом агенте
Кнопки ↻/✎ переписывают JSONL — под живым процессом это рвёт цепочку. Поэтому пока идёт стрим ИЛИ жив фоновый агент они **серые** (курсор `not-allowed`, tooltip объясняет). Когда юзер всё же жмёт Повтор на завершённом ходе: перед переписыванием истории процесс жёстко гасится с видимым «останавливаю процесс…» (и в индикаторе, и в статус-строке композера ~1.2с), потом truncate + новый ход.

### Edge: закрытие вкладки
Закрытие SDK-вкладки — всегда **hard** (нельзя оставлять осиротевший процесс + фон без UI, которым их остановить). При soft-стопах процесс жив намеренно; единственные жёсткие пути — кнопка-индикатор, Правка/Повтор и закрытие вкладки.

### Ловушка (была): зависший workflow-чип
Юзер: *«нажимаю на Warflow, потом X — не заканчивается, как мне его остановить?»*. Оказалось: процесс уже был мёртв (тогда Escape рубил всю сессию hard'ом), workflow на диске `status:"killed"`, живых процессов ноль — а чип в UI никто не погасил после teardown. Это был UI-труп + no-op кнопки X на мёртвой сессии, не runaway-агент. После перевода Escape на soft (сессия живёт → X работает) и реконсиляции чипов на teardown — закрыто.

См. `fact-claude-sdk-tab.md::Soft interrupt vs hard kill`, `::Процесс-индикатор`, `::«⊘ stopped» badge`, `fact-claude-sdk-workflows.md::WorkflowPanel`.

## Сценарий: Фоновая оркестрация AI-вкладки

Юзер поручает текущей Claude/Codex-вкладке запустить исполнителя в этом или другом проекте, не отдавая ему фокус и не удерживая сетевой запрос на всё время работы. Путь проходит через source History, background target, Project API, SSE и transcript-result.

### Основной путь

1. Состояние: source-вкладка открыта в History и содержит materialized сессию. Клиент выбирает существующий target либо проект и тип нового агента.
2. Клиент создаёт orchestration run через Project API или `Terminal MCP::delegate_to_session`. Связанная новая target-вкладка в том же проекте открывается в фоне как visual-child source; для независимой работы клиент передаёт `placement: root`. Активный проект и source не меняются. Вызов возвращает после подтверждения доставки, даже если задача будет идти 30 минут.
3. В source и target рядом с `Run After` появляется один и тот же live run с противоположным направлением. Hover показывает проект и вкладку, клик переводит на связанную History-поверхность, включая cross-project переход.
4. Target пишет структурный busy/start, выполняет задачу и завершает её terminal-event’ом. Если он создал дочерние Terminal MCP run, собственный ответ переводит его в `waiting_descendants`, а inherited-loader source/project остаётся непрерывным до обработки последнего потомка. Terminal output для этого не читается.
5. Сервер сопоставляет target-turn по сохранённым provider/session/turn и адресу prompt; совместимый fingerprint-путь сохраняется для старых записей. Только после завершения всей ветки и доказанного собственного результата он отправляет source короткое уведомление с `runId`; полный ответ остаётся в transcript target.
6. Source получает результат одним `get_delegation_result({runId})` или HTTP GET и продолжает свою задачу. Если target был одноразовым тестовым исполнителем и больше не нужен, source после чтения результата вызывает `close_tab`; переиспользуемая полноценная сессия остаётся открытой. Завершённый run исчезает из live tracker и остаётся в компактном окне `History` слева от одноимённой кнопки.

### Edge: fresh Claude target получает длинный prompt с изображениями

1. Оркестратор создаёт target и сохраняет intent до запуска. Trust/auth/startup
   blocker удерживает отправку; его снятие не требует повторного запроса source.
2. После exact `active + inputReady` общий writer вставляет один immutable
   snapshot текста и изображений. Первый закрытый Ink-frame может показывать
   `Pasting…` или временно пустой input и не разрешает Enter.
3. Enter пишется только когда current committed composer показывает все
   ожидаемые image chips и законченную inline/collapsed форму текста. Unknown
   форма сохраняет input и оставляет run в восстановимом состоянии.
4. `UserPromptSubmit` связывает provider-преобразование с той же operation, а
   causal JSONL user-record заменяет optimistic History-row. Source видит одну
   отправку даже если локальные пути превратились в image blocks с другим hash.
5. После canonical assistant-row хвостовой live preview исчезает в том же
   presentation commit. Пользователь не должен вручную нажимать Enter и не
   должен видеть ниже сохранённого ответа его фиолетовый дубль.

### Edge: Claude/Fable исчерпал лимит

1. Отправить через общий scenario prompt с TAB/CRLF (в том числе context-file):
   квитанция подтверждает исходный запрос через точное преобразование transport,
   а не ждёт совпадения двух заведомо разных hashes.
2. При точном StopFailure run завершается ошибкой, основной и orchestration
   loader не изображают работу. Источник получает обычное completion-уведомление
   и одним GET читает понятную причину, не частичный ответ. Процесс не убивается.
3. Та же synthetic API-error запись History показывается малиновой служебной
   строкой с иконкой, как Codex. Цитата ошибки не перекрашивается.
4. Повторная сверка/перезапуск клиента дают тот же failed result без нового Send;
   ошибка соседнего turn и поздний callback после detach ничего не завершают заново.
5. Если `/model` после Resume сам получил429, это отказ настройки в живом Claude,
   не failed launch. Явный stdout освобождает очередь без timeout/Enter retry;
   можно выбрать другую модель, но успех показывается только по её собственному proof.
   Успешная замена продолжает оставшиеся startup settings той же generation,
   не применяя прежнюю модель повторно и не требуя перезапуска процесса.
6. Если в ручной паре модель применилась, а effort отказал, следующий model-only
   выбор не стирает ошибку effort. Кнопка Retry повторяет именно отказавший ручной
   effort; подтверждённая модель и не затронутые настройки не отправляются снова.

### Edge: Electron или клиент перезапустился

POST уже завершён, поэтому разрыв клиента не отменяет target. После старта сохранённый run сверяется с transcript: если matching turn завершён, статус и result восстанавливаются, а недоставленное source-уведомление повторяется. Верхний tracker и окно истории гидратируются из того же store.

### Edge: несколько запросов к одной вкладке

У каждого run свой `runId`, а target строит predecessor-цепочку. Первый busy→done закрывает только головной run; следующий начинает считаться работающим по собственному start. В UI все активные вызовы живут в одном прокручиваемом блоке.

### Edge: пользователь дополняет задачу в дочерней вкладке

1. Состояние: target уже выполняет orchestration-run, его loader продолжается, а source ждёт финальный ответ.
2. Пользователь открывает target и отправляет одно или несколько уточнений. Они отображаются отдельными History-сообщениями, но связь с source не прерывается.
3. Target обрабатывает всю очередь, может запустить своих дочерних исполнителей и продолжает тот же физический ход, пока loader не завершился.
4. После точного завершения source получает один итог, включающий финальный ответ после последнего уточнения. Промежуточный ответ до более позднего queued-сообщения не закрывает run.
5. Если target завершился ошибкой или был прерван, source получает этот исход вместо ложного success.
6. Новое обычное сообщение, отправленное уже после остановки loader, начинает независимый ход и не добавляется к старому result.

### Edge: исполнитель делегировал E2E третьему уровню

Исполнитель второго уровня вызывает `delegate_to_session` из target активного run. Новый вызов получает `parentRunId`, а первый run по умолчанию ждёт: собственный вводный/финальный ответ не становится отчётом архитектору, пока E2E-run не завершён и его notification не породил следующий обработанный turn исполнителя. Вкладка исполнителя может быть runtime-idle, но её вкладка и проект продолжают показывать отдельный inherited-loader. Если задача действительно допускает ранний отчёт, caller передаёт `waitForDescendants:false`; effort модели и текст ответа эту политику не угадывают.

### Edge: Codex уже ответил, а вкладка начала другую задачу

1. Ответ A сохранён; если у него есть дочерняя работа, source продолжает ждать её.
2. Пользователь отправляет в ту же вкладку независимый B. Его busy не возвращает
   завершённый A в running и не добавляет новый текст к ответу A.
3. Сервер продолжает наблюдение без полного SHA на каждом append B. После
   обработки потомков он окончательно проверяет A и отправляет один результат.
4. Если пользователь закрыл target во время этого чтения, закрытие дожидается
   активного и повторного проходов. Уже сохранённый ответ не превращается в
   «недоступен» только потому, что его проверка ещё выполнялась.

### Edge: target закрыт или turn оборван

Закрытие target, startup failure, provider failure без окончательного proof и process exit переводят run в `waiting_recovery`, а не оставляют `queued` и не объявляют success. Жёлтая карточка одновременно показывает статичную иконку таймера и предупреждение; это не фиолетовый сигнал продолжающейся дочерней работы. Для этих исходов пользователь восстанавливает связь явно, передаёт ошибку сейчас или закрывает вызов без сообщения. Точный StopFailure/JSONL API-error — исключение выше: конечная ошибка передаётся сразу.

Ручной Escape тоже переводит уже начатый run в жёлтое ожидание, но не сообщает родителю ни успех, ни ошибку. При выключенной реакции на Escape таймера нет; при включённой пользователь может снять отсчёт и ждать бессрочно. Если он позже отправляет следующее сообщение в той же target-сессии, новый точный ход автоматически продолжает связь и обычный lifecycle возобновляется; ручное восстановление остаётся запасным действием, когда ожидающих связей несколько и автоматика не имеет права выбрать одну. После deadline ошибка доставляется source; `×` до этого только отвязывает run и не останавливает исполнителя.

### Edge: в source уже набран текст

Completion notification не дописывается к пользовательскому draft. Текст видимого History-input вообще не является PTY composer и остаётся на месте; нативный Claude/Codex draft проверяется отдельным авторитетным preflight даже при `queue:true`. При доказанном конфликте run показывает `waiting-for-input`, а result остаётся доступен по `runId`. После доказанного освобождения composer доставка повторяется по событию; ручное действие карточки существует для восстановления пропущенного delivery-edge, но не разрешает blind duplicate.

### Edge: source остановлен до первого turn

Target может успешно закончить, но source некуда отправить notification: технический Claude UUID ещё не является materialized разговором. Run остаётся completed и доступен по API, а история показывает отдельную ошибку уведомления `session_not_materialized`.

### Edge: результат готов, предупреждение о доставке скрыто

1. Backend завершает run; доставка notification источнику остаётся неизвестной.
2. Пользователь закрывает предупреждение: source не будится, notification не
   повторяется, результат остаётся completed и доступным по прежнему runId.
3. Следующий обычный prompt той же подтверждённой session получает короткий
   факт завершения через общий context handoff, без полного result и нового chip.
4. Если ответ ещё не прочитан и нужен для продолжения, агент читает его один раз;
   уже прочитанный не получает снова. Тот же Send replay сохраняет прежний payload.
   Истинно active run не попадает в terminal facts. Прямой TUI статус сверяется
   через get_delegation, поскольку он не проходит подготовку context.
5. Если раньше подготовленное H1 точно не отправилось, пользователь может
   нажать Retry даже после отправки H2 с тем же коротким фактом. H1 сохраняет
   свой текст, справка повторяется как тот же факт, не новая задача. Unknown H2
   сам повторно не отправляется, ранее прочитанный result не загружается снова.

См. fact-оркестрация-вкладок::Скрытое уведомление.

### Edge: notification становится первым prompt source

Если fresh source Claude уже запущен и input-ready, но пользователь ещё не отправлял сообщений, завершение target может стать первым turn source. Project API отправляет одно короткое notification; ранний hook связывает появившуюся JSONL-запись с staged send ещё до обычного StatusLine binding. После обновления History пользователь видит одну durable строку, а временный handoff исчезает. Остановленный или неготовый source в этот путь не входит и сохраняет результат только по `runId`.

### Вариант: консультация browser-модели и повторный review

1. Исполнитель вызывает `start_external_research` с задачей и путями/диапазонами
   файлов. Для сохраняемого ChatGPT-разговора первый запрос явно несёт
   `mode:chat`, `temporaryChat:false`, `autoClose:true`. В UI появляется обычный
   исходящий orchestration-row к SC Desktop, без новой terminal-вкладки.
2. Инструмент возвращает `runId + jobId`; исполнитель завершает ход. Noted main
   сам ждёт конкретный SC job. Окончанием является только его `done|error`, не
   таймер, текст «готово» и не возврат первоначального MCP-вызова.
3. Source получает короткое user-уведомление и один раз вызывает
   `get_delegation_result`. Ответ даёт browser-текст и постоянные
   `conversationUrl/conversationId`; полный ответ не дублировался в notification.
4. Исполнитель реализует и локально проверяет изменения. Для повторного review
   он вызывает `continue_external_research` с прежним `previousRunId`, новым
   сообщением и актуальными файлами. Это новый run/job в том же conversation:
   первый result не может быть принят за второй.
5. Потеря ACK или restart повторяет только exact request под тем же ID и сначала
   восстанавливает существующий SC job. Конфликт ID даёт ошибку до browser side
   effect. Ошибка source-доставки показывается отдельно; сам готовый browser
   result остаётся читаемым.

### Вариант: готовый ChatGPT-разговор без предыдущего run

1. Если по принесённой ссылке нужно задать новый вопрос, исполнитель вызывает обычный
   `start_external_research` с `conversationUrl`, prompt и новым runId.
2. Если нужен уже существующий ответ, исполнитель вызывает
   `import_external_conversation({url})`. Noted сохраняет обычную external-orchestration,
   а SC открывает отдельную read-only вкладку и не касается picker/composer/Send.
3. Незавершённый current turn не подменяется предыдущим final: операция завершается
   ошибкой либо ждёт при явном `waitForFinal:true`. Готовый final сохраняется локально,
   import-вкладка закрывается, исходный ChatGPT conversation не меняется.
4. Source получает обычное completion-уведомление и один раз читает result. Для ответа,
   появившегося позднее по тому же URL, создаётся новый runId.

См. `knowledge/fact-оркестрация-вкладок.md`, `knowledge/fact-session-history.md`, `knowledge/fact-terminal-mcp.md`.

## Сценарий: работа над вкладкой чужого проекта без потери контекста

Пользователь ведёт задачу в проекте A и хочет заглянуть в сессию проекта B, сохранив перед глазами список вкладок A.

### Основной путь

1. Пользователь в проекте A, боковой список показывает вкладки A, в центре вкладка A.
2. Нажимает `Ctrl+Tab` (или `Cmd+P`) — открывается список всех вкладок всех открытых проектов, отсортированный по свежести; заголовки проектов идут разделителями и пропускаются перебором.
3. Выбирает вкладку проекта B. В центре появляется вкладка B, строка привязки над центром показывает «B · имя вкладки». **Боковой список и подсветка чипа в титлбаре остаются на A** — контекст задачи не потерян.
4. Все поверхности вкладки (нижняя control bar, транскрипт, Timeline, панель задач) переключились на вкладку B; пользователь работает с ней, не покидая список A.
5. Когда действительно нужен проект B целиком — клик по имени проекта в строке привязки. Теперь переезжают и список, и тулбар, и git.

### Edge: вкладка ведёт на исчезнувший файл

Файловая вкладка, чей файл переместили или удалили, помечена красной иконкой в списке, в переключателе и в истории закрытых вкладок. Перебор `Ctrl+Tab` её перепрыгивает, клик не срабатывает. Вкладка при этом НЕ удаляется: файл может вернуться, а вместе со вкладкой пропала бы привязка к сессии.

### Edge: активированная вкладка вне видимой части списка

Если проект бокового меню совпадает с проектом активированной вкладки, список мгновенно (без анимации) подкручивается к её строке: верх к верхнему краю, если она была выше, низ к нижнему, если ниже. Это же происходит после возврата в проект, и приоритет у показа строки выше, чем у восстановления сохранённого положения списка.

## Сценарий: открыть место в окне до выбора Terminal или AI

Согласованный путь реализован в source NWT-1; физическая приёмка после установки
остаётся открытой. Начальное состояние — окно показывает A, в sidebar есть её
обычная рабочая запись.

1. Пользователь дважды кликает свободное место полосы либо нажимает `Cmd+T`
   при клавиатуре в этом окне. Появляется `Новая вкладка` с выбором способа работы;
   строка sidebar и процесс ещё не создаются, A остаётся припаркованным чипом.
2. Строка пути под navbar показывает корень проекта, а не cwd вкладки A. Если
   нужна другая директория, пользователь кликает по самому пути, выбирает папку
   в системном диалоге и подтверждает `Выбрать`. В строке нет новых подписей;
   отмена диалога сохраняет прежний путь, рабочая вкладка всё ещё не создана.
3. Можно открыть ещё одно такое место и закрыть его средним кликом или `Cmd+W`.
   Удаляется только заготовка; окно и первая заготовка остаются, архив не растёт.
4. Пользователь выбирает Terminal либо Claude/Codex/SDK или F. Операция создаёт
   рабочую запись и публикует её вместе с размещением в выбранном месте. Теперь
   есть строка sidebar; все варианты запуска получают выбранную на шаге 2
   директорию. У Terminal можно вводить shell-команды, у AI начинается прежний
   сценарий запуска выбранного агента.
5. Если во время выбора директории или создания пользователь перешёл в другое
   окно/workflow, результат относится к исходному slot ID: папка и вкладка не
   пересаживаются в последнее сфокусированное место. Если место закрыто
   до публикации, создание отменяется без архива и без выхода private tab в UI.
6. Уже опубликованная вкладка живёт по обычным правилам: `Убрать` снимает её из
   окна, `Full` закрывает рабочую запись. Эти действия не подменяются автоматической
   отменой по отсутствию session ID или по «пустому» имени.

Вместо нового процесса можно выбрать существующую вкладку через общую навигацию:
если она заполняет это окно, выбранная заготовка потребляется; если переход ведёт
к уже размещённой вкладке другого окна, заготовка остаётся на прежнем месте.
Без UUID/при отказе fork новая рабочая запись не появляется, ошибка видна,
страница позволяет повторить выбор. Не выбранные заготовки переживают
workflow round-trip и восстановление раскладки без запуска процессов.

ПКМ свободного места полосы → `Terminal tab` / `Claude tab` /
`Codex tab` сразу задаёт выбор для того же пути. Открытие меню не уводит
фокус; один Escape закрывает меню, а не лежащую под ним заготовку.

См. `knowledge/fact-рабочая-область.md::«Новая вкладка»`,
`knowledge/fact-tabs.md::Роль исполнения`; исходные сценарии N01–N16 и границы
проверки — `tmp/окно-вкладок-и-переключатель-фичи.md::NWT-1`.

## Сценарий: продолжить workflow на ноутбуке и вернуться на монитор

Один workflow содержит четыре окна: три колонки, последняя разделена по
горизонтали. В каждом окне свой набор вкладок; перенос приложения не завершает
процессы и не пересобирает эти наборы.

1. На большом мониторе пользователь настраивает sidebar, шрифт и перегородки.
2. Переносит приложение на MacBook. В первый раз видны до двух окон, включая
   прежнее фокусное; затем возвращается сохранённая раскладка этого экрана.
3. Меняет размер sidebar/текста. Эти значения относятся только к MacBook;
   горизонтальные отступы History остаются общей настройкой 4px по умолчанию.
4. В шапке правого окна наводит курсор на счётчик скрытых окон, затем кликает
   карточку нужного. Весь набор чипов появляется справа; прежнее окно целиком
   уходит в скрытые.
5. Обычный переход из sidebar к вкладке скрытого окна делает тот же обмен
   в текущем фокусном месте. Если окно уже видно, меняется только фокус/чип.
6. На Odyssey возвращаются четыре прежних места и их размеры; повторный
   возврат на MacBook показывает выбранную здесь пару с её размерами.

### Edge: закрытие, перезапуск и работа в фоне

Full-закрытая вкладка не возвращается из другого профиля; новое содержимое
окна общее для мониторов. Chooser и vacant `Нет вкладки` сохраняют свою
семантику. Restart восстанавливает окна, а отключение монитора не удаляет
его профиль. Фоновая задача в скрытом окне продолжает работать и может создать
там соседнюю вкладку без переключения UI. Смена ширины/шрифта должна сохранять
читаемый текст через существующий механизм History resize.

Проверка: `scripts/display-workspace-regression.mjs` и
`utils/windowDisplayLayouts.test.mjs`; контракт —
`fact-рабочая-область.md::Монитор выбирает раскладку, окно сохраняет своё содержимое`.

## Сценарий: собрать рабочую область из двух вкладок

Пользователь хочет видеть две сессии одновременно, возможно из разных проектов.

### Основной путь

1. В строке привязки над центром пользователь нажимает кнопку раздвоения.
2. Справа появляется пустая колонка «Нет вкладки». Фокус уже на ней, вокруг белая рамка; заполнить её можно через `Ctrl+Tab`, `Cmd+P` или клик по вкладке слева.
3. Пользователь нажимает `Ctrl+Tab` или кликает вкладку в боковом списке — она заполняет пустую колонку. Теперь две панели, у каждой своя строка привязки.
4. Клик по любой панели делает её фокусной: её вкладка становится вкладкой центра, за ней идут нижняя control bar и Timeline. Боковой список при этом не переезжает.
5. Кнопка терминал/транскрипт в строке привязки панели меняет режим ТОЛЬКО этой панели: слева можно смотреть терминал, справа читать переписку.
6. ✕ в строке привязки убирает названную панель. Одна оставшаяся панель может стать одиночным центром; выбранная/припаркованная «Новая вкладка» и намеренная vacancy сохраняют explicit окно, чтобы схлопывание не выбросило его содержимое.

### Edge: транскрипт запрошен в нефокусной панели

Каждая панель показывает собственную History, включая нефокусную. Фокус
определяет владельца глобальных клавиш, а не право показывать переписку.
Прежнее ограничение «транскрипт только для фокусной панели» больше не действует.

### Edge: несколько AI-сессий работают одновременно

После фонового прогрева десятков окон пользователь возвращается в уже
построенный workflow. Каждая живая Timeline сохраняет пару rows+revision;
main проверяет изменения по этой версии. Если transcript не менялся,
вытеснение из общего remount-кэша не становится причиной повторного разбора
сотен MiB. Новые сообщения и служебные изменения продолжают доходить обычным
refresh. Фоновая отрисовка сама по себе не означает, что все parser caches
обязаны оставаться в RAM; этот путь устраняет лишнее чтение неизменных данных.

Отдельно: после нескольких часов работы с другими сессиями пользователь
отправляет новое сообщение в уже показанной большой History и сразу
переключается в Docs/другой workflow. Файл изменён, а backend parser мог быть
вытеснен: малиновый resource-icon честно показывает cold подготовку. Старая
поверхность сохраняется, тяжёлая классификация старых строк пропускает ввод
между порциями; новый prompt/ответ не теряются и не ждут quiet курсора.
Проверять input→paint отдельно от длительности чтения: сокращение одного
синхронного прохода само по себе не является приёмкой всех native задержек.

Пользователь запускает 5–6 сессий → переходит между уже открытыми workflow →
прокручивает History в одном окне и вводит текст в другом. Показанные строки
и место чтения сохраняются; фоновая работа не должна делать ввод всей страницы
непригодным. Повторить с закрытой и закреплённой картой Run after: scroll History
не сдвигает её toolbar-якорь и не запускает лишний пересчёт карты, собственный
scroll карты продолжает двигать её плавающий editor.

Если возникла пауза, фиксировать время/состояние карты и сопоставлять input→paint
с CPU того же интервала. Маленький старый CPU-счётчик без Mach-нормализации,
наличие свободной памяти или `history-load(open)` сами по себе не выбирают
виновную подсистему. Источник и границы отложенного профиля —
`knowledge/fact-performance-diagnostics.md`; полная отзывчивость production
после ремонта наблюдения 14.09 ещё не подтверждена.

### Edge: изменение размеров во время чтения

Пользователь читает середину длинного сообщения → тянет вертикальный,
горизонтальный разделитель, их пересечение или правый край списка вкладок → границы двигаются, содержимое
до отпускания сохраняет прежнюю раскладку, прокрутка заблокирована → после
отпускания строки переносятся под новую ширину → тот же текст возвращается к
верхнему отступу и прокрутка снова доступна. Несколько ресайзов подряд без
прокрутки не должны постепенно уводить место чтения. Если до жеста History
следовала за последним ответом, после него остаётся у физического низа.

У списка вкладок вместе с границей следует верхняя строка инструментов;
ширина сохраняется один раз в профиле текущего монитора. Повторить при двух
колонках и при одном окне, включая скрытые прогретые вкладки. Escape/потеря
захвата/смена workflow или монитора до release снимают preview без чужой
записи размера; после жеста фокус, черновик и обычный выбор вкладок доступны.

### Edge: новая пустая панель не пригодилась

`Escape` (когда фокус не в поле ввода/терминале и поверх нет меню) или ✕ закрывают пустую колонку. Пока пользователь её не закрыл, пустая колонка рядом с другими сохранёнными окнами остаётся частью раскладки. Если показана «Новая вкладка», Escape закрывает сначала эту заготовку; ✕ остаётся отдельным закрытием всего окна.

### Edge: показанная вкладка убрана или закрыта

`Убрать` снимает только размещение вкладки в этом окне, а `Full` в меню панели и `Close Tab` в sidebar полностью удаляют саму вкладку. Во всех трёх случаях окно остаётся на прежнем месте и в фокусе с надписью «Нет вкладки»: удаление содержимого не является командой удалить построенный пользователем слот или перейти к соседу. Остальные чипы остаются припаркованы в шапке без выбранного владельца; только явный клик, `Ctrl+Tab` или `Cmd+P` снова заполняет окно. Закрытие непоказанного припаркованного чипа текущую вкладку окна не меняет; ✕ окна остаётся отдельным действием.

См. `knowledge/fact-рабочая-область.md`, `knowledge/fact-переключатель-вкладок.md`, `knowledge/fact-история-как-основная-поверхность.md`.

## Сценарий: посмотреть другой Usage-аккаунт, не подменив главный чип

1. В шапке Codex/Claude face показывает лимиты того аккаунта, под которым запустится обычный локальный CLI.

Если current login не доказан, toolbar-face показывает недоступность, а не цифры выбранного historical account. Механика: `knowledge/fact-claude-usage-chip.md`.

## Сценарий: просмотреть цепочки Run After и поправить одну очередь

Пользователь наводится на общий Run After над sidebar — появляется карта активных цепочек. Связь `A → B` читается как «B ждёт завершения всей цепочки A»; будущие зависимости следующих шагов пунктирные, таймер/процент/Loop стоят отметками в строке owner-вкладки. Клик по верхнему Run After закрепляет уже видимое окно без повторного появления.

Обычный клик по цветному tab-chip переводит к его уже существующему месту — при необходимости меняет workflow и фокусирует именно то окно, где вкладка уже открыта, — и не закрывает закреплённую карту. Средний клик — отдельное явное действие: переместить вкладку в текущее окно. Если вкладка ещё нигде не размещена, обычный клик показывает её в текущем окне. Hover по отдельному числу показывает редактор прямо под этим числом, клик закрепляет ту же всплывающую поверхность. Размер и scrollHeight карты не меняются: редактор порталится поверх layout, как локальный Run After. Изменение Post/Loop/порядка/условия сразу относится к локальному Run After той же вкладки, потому что второго состояния нет. Выключенные очереди вне активной цепочки доступны отдельной полкой; раскрытие полки увеличивает естественную высоту окна до viewport-потолка. Повторный клик по верхнему Run After закрывает обзор; отдельного крестика нет.

### Edge: перенести незавершённую диктовку

1. В History input уже стоит оранжевый чип Voice Record, а хвост речи ещё
   распознаётся. Пользователь нажимает `+grab`.
2. Черновик одной операцией становится карточкой Run After вместе с pending-чипом;
   исходный History очищается только при неизменном snapshot. Асинхронное название
   карточки не задерживает этот переход.
3. Replay и auto-run не отправляют `[Dictating …]`. Если trigger уже наступил,
   карточка продолжает показывать ожидание, а вкладка агента не начинает сырой ход.
4. Финал Voice Record заменяет маркер именно в queue-item; текст и изображения
   сохраняют позиции. После последнего маркера продолжается та же уже наступившая
   попытка Run After, а не искусственный новый turn-end.
5. Если пользователь до финала удалил маркер или карточку, поздний результат её не
   воскрешает; полная запись остаётся в истории Voice Record для ручного повтора.

Механика: `knowledge/fact-prompt-queue.md::Pending-диктовка при переносе из History`,
`knowledge/fact-dictation.md::Диктовка Voice Record как чип в композере`.

## Сценарий: включить автокомпакт для Main и продолжить в другом workflow

Пользователь хочет обслуживать текущую работу, не пробуждая старые сессии других проектов.

1. В общем Run After над sidebar выбирает «Автокомпакт», область Main и порог 50%. Под Main видны связанные проекты; запуск подписан выбранной областью.
2. Включает правило. Давно простаивающая или остановленная сессия не получает команду только из-за высокого сохранённого процента.
3. Переключается в другой workflow. Вкладка проекта Main заканчивает новый обычный ответ; актуальный процент достиг порога — начинается compact, затем после доказанного завершения допускается следующий шаг очереди. Фокус пользователя не переключается.
4. Для отдельной вкладки отключает наследование через `…`. Перечёркнутый marker остаётся в её свёрнутой рельсе. Общее выключение/включение и restart сохраняют исключение.
5. При необходимости разово сжать старые сессии открывает «Применить к уже простаивающим…» в той же области и явно выбирает строки. Остановленные заранее помечены как требующие запуска; непосредственно перед отправкой условия проверяются снова.

Показ вкладки в чужом окне не меняет область; перенос самого проекта меняет её для последующих событий. Ручная карточка `/compact` остаётся независимой, а новое завершение compact не запускает сжатие рекурсивно. Реализовано для Claude/Codex PTY; результаты приёмки отделены от описания ожидаемого пути в `tmp/глобальные-очереди-и-автокомпакт.md`. Механизм: `knowledge/fact-prompt-queue.md`.

## Сценарий: перенести группу вкладок в другой проект одним drag-жестом

Пользователь хочет перенести корневую вкладку вместе с визуальными потомками в другой проект, не отпуская мышь между выбором источника, сменой проекта и точным размещением.

### Основной путь

1. В sidebar проекта A пользователь начинает тянуть корневую вкладку. Без модификатора это остаётся обычным локальным изменением порядка или вложенности и не переключает проект либо окно.
2. Не отпуская мышь, пользователь удерживает `Cmd`. Дерево источника перестаёт переставляться, а рядом с курсором появляется имя корня и `×N` полного переносимого блока.
3. Пользователь наводится на проект назначения. Sidebar переключается на него, но физический drag продолжается: смена React-владельца не отменяет взятый root и его потомков.
4. Уже в проекте B пользователь отпускает `Cmd`, выбирает обычным вертикальным/иерархическим preview точное место и отпускает мышь один раз.
5. Root и его потомки появляются в выбранном месте проекта B в прежнем порядке и с прежними связями. В проекте A второй копии не остаётся; после перезапуска результат тот же.

### Edge: жест отменён

`Escape`, потеря pointer-owner или отмена до финального отпускания очищают preview и переносимый чип, но не выполняют частичный перенос. Смена проекта сама по себе не является commit: durable изменение происходит только один раз на завершении того же drag-сеанса.

См. `knowledge/fact-tabs.md::Structured outline DnD во вкладках`, `knowledge/fact-рабочая-область.md::DnD окон, workflow и project chips`, `knowledge/fix-иерархия-перетаскивания.md::Смена проекта теряла source, а скрытая History тормозила drag`.
