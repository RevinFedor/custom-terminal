*Пошаговые пути юзера через несколько фич custom-terminal'а — там где успешный исход зависит от последовательности состояний (background↔foreground, killed→cold-launch, idle→busy→idle, AI-engine выбран → запущен → context preserved). Один сценарий = одна цепочка, которая в любом отдельном `fact-*.md` целиком не помещается. Активируется явно («проверь основной флоу X», «не сломали ли мы Unified AI Launch») или через `docs_search` по запросам про user-journey. Каждый сценарий ссылается в конце на participating fact-файлы, где живёт механика конкретных подсистем.*

## Сценарий: Unified AI Launch (split-button claude | gemini)

Юзер заходит на pristine таб без сессии и хочет начать работу с AI-агентом. Раньше выбор движка жил в правой `InfoPanel`-колонке как split-button. После удаления правой колонки lifecycle-affordance (запуск + Continue/Stop + fork + copy session-id + force-refresh timeline) переехала в `ClaudeControlBar` под Terminal. Стартовая точка одна, дальше пути расходятся по engine'у.

### Основной путь
1. Состояние: pristine таб (`!hasAnySession && !isSDKTab && !isCommandRunning`). В `ClaudeControlBar` виден набор fork-/launch-чипов: `+SDK`, `⑂ Claude-F`, `⑂ SDK-F`. Quick Actions в `ActionsPanel` показывают split-button `claude | gemini` для базового запуска.
2. Юзер выбирает Claude или Gemini кликом по соответствующей половине split-button'а.
3. Запускается PTY-процесс с handshake'ом. OSC 133 D приходит → `isCommandRunning = true`. Fork-чипы прячутся (visibility-guard `!isCommandRunning`, см. `fact-claude-control-bar.md::Visibility guards`).
4. ControlBar адаптируется под движок: для Claude доступен Provider + Effort inline-row + Think + Copy-prompt split-pill + `⑂→SDK` fork-чип. Для Gemini — этих контролов нет (объяснение асимметрии ниже).
5. После первого ответа bridge пишет `claudeSessionId` / `geminiSessionId` в Tab. Триплет `[⎘ session-id | Continue/Stop | ↻ refresh-timeline]` становится постоянно видимым.

### Edge: Engine asymmetry (Claude-only vs Gemini-only)
Часть affordance'ов в баре существует только для Claude и **сознательно отсутствует** для Gemini. `⑂→SDK` (fork в SDK-таб) — SDK не запускает Gemini вообще, у `@anthropic-ai/claude-agent-sdk` нет аналога. Copy-prompt split-pill (`⎘ prompt | + clear`) — Claude забирает текущий input через external-editor hijack (Ctrl+G → `EDITOR=noted-code-grab.js`), у Gemini CLI аналогичного IPC нет. Provider switcher и Effort inline-row — концепты завязаны на Anthropic-side. Скрытие этих кнопок для Gemini — не bug, а контракт engine'а; визуально юзер сразу понимает «это Gemini-таб» по урезанному набору контролов в баре.

### Edge: Continue при возврате после kill
Если процесс был убит (Ctrl+C через UI, manual stop, kill из шапки), таб сохраняет `claudeSessionId`/`geminiSessionId`. В ControlBar триплет показывает `Continue` (не Stop) — клик восстанавливает контекст: для PTY-Claude через `claude --resume <sid>`, для Gemini через `gemini -r <sid>`, для SDK через возврат фокуса в composer + следующий submit с `query()` использующий тот же sid.

См. `fact-claude-control-bar.md`, `fact-claude-sessions.md`, `fact-gemini-sessions.md`, `fact-claude-sdk-tab.md`.

## Сценарий: Multi-select Persistence при работе с ActionsPanel

Юзер выделил несколько вкладок (Shift+Click диапазон или Cmd+Click по одной), хочет применить к ним массовое действие из боковой панели (Update Docs кастомным промптом, batch-copy session, групповая Stop). Раньше любой клик в `ActionsPanel` сбрасывал выделение — пока юзер кликал в textarea для редактирования промпта, multi-select исчезал, и батч-операция отрабатывала только по последнему clicked-табу.

### Основной путь
1. Юзер делает Shift+Click по нескольким табам в `TabBar` → multi-select state в `useWorkspaceStore`. Выделение визуально маркировано (dashed-white border на табах).
2. Юзер перемещает курсор в `ActionsPanel` справа, кликает по textarea кастомного промпта или по toggle'у Settings.
3. Click bubble'ит до document-level `mousedown` handler'а в `TabBar.tsx`, который раньше всегда вызывал `clearSelection`. Сейчас handler сначала проверяет `e.target` и всех его родителей на атрибут `data-keep-selection` — `ActionsPanel`-контейнер этим атрибутом помечен.
4. Выделение **сохраняется**. Юзер свободно вводит текст промпта, переключает toggle'ы.
5. Юзер кликает action-кнопку (Update Docs / Copy / Stop N) — операция отрабатывает по всему выделенному набору.

### Edge: клик вне `TabBar` и вне `data-keep-selection`-зоны
Клик в терминал, в Timeline, в любую другую панель без атрибута → `clearSelection` срабатывает как раньше. Это сознательно: multi-select имеет смысл только пока юзер работает с инструментами над табами; уход в терминал = намерение работать с одним конкретным.

См. `fact-tabs.md::Multi-Select`, `fact-docs-update.md`, `fact-clipboard-tools.md`.

## Сценарий: Browser Tab Navigation — клик на ссылку из логов dev-сервера

Юзер запустил `npm run dev` в табе типа `browser`. Vite печатает в терминал `Local: http://localhost:5173/`. В обычном терминальном табе Cmd+click на ссылку открывает её в Safari/Chrome. Но внутри BrowserTab юзер хочет увидеть результат рядом — переключение фокуса в системный браузер ломает workflow «правлю код → вижу изменения здесь же».

### Основной путь
1. Состояние: таб типа `browser` с активным `view: 'terminal'`. PTY-процесс печатает строку с URL.
2. Юзер зажимает Cmd и кликает по `http://localhost:5173/` в xterm-выводе.
3. `onLinkClick` callback в `Terminal.tsx` различает «внешние» и «контекстные» по `tabType === 'browser'`. Для контекстных — `e.preventDefault()`, IPC не отправляется в `shell.openExternal`.
4. URL подставляется в адресную строку таба, `setBrowserActiveView(tabId, 'browser')` принудительно переключает view, webview грузит страницу.
5. Юзер видит UI приложения рядом с терминалом, может вернуться в `view: 'terminal'` для рестарта сервера.

### Edge: Refresh button после рестарта dev-сервера
Юзер перезапустил `npm run dev` (Ctrl+C → стрелка вверх → Enter), сейчас смотрит в `view: 'terminal'` и видит логи запуска. Кликает Refresh-кнопку в шапке BrowserTab. `setBrowserActiveView(tabId, 'browser')` форсирует переключение даже без флага. Принцип «ожидаемый результат»: после ручного refresh пользователь в 100% случаев хочет видеть UI, не терминал. Не делать вид опциональным — это лишний клик после каждого рестарта.

См. `fact-tabs.md::Browser Tabs`, `fact-terminal-core.md`.

## Сценарий: Interrupted Overlay при cold-launch после неожиданного выхода

Приложение помечает активные AI-сессии `wasInterrupted = true` перед закрытием (`beforeunload`/`before-quit`). При следующем cold-launch юзер видит overlay с предложением `Continue` или `Dismiss` для каждой такой сессии. Ловушка раньше была — закрытие overlay'я не было персистентным: юзер кликал «нет, не восстанавливать», обновлял страницу, и overlay появлялся снова, потому что `beforeunload` повторно видел привязанный `sessionId` к табу.

### Основной путь
1. Состояние: запущенный Claude или Gemini в табе. `wasInterrupted = false`, `overlayDismissed = false`.
2. Юзер закрывает приложение (Cmd+Q / kill / crash). `beforeunload` (renderer) и `before-quit` (main) маркируют сессии: `if (hasSession && !overlayDismissed) → wasInterrupted = true`.
3. Cold-launch. Renderer hydrate'ит табы из SQLite, видит `wasInterrupted=true && sessionId`, рендерит `InterruptedOverlay` поверх Terminal.
4. Юзер видит overlay только если `currentView === 'terminal'` — на Home overlay не блокирует navigation.

### Edge: юзер кликает Continue
`claude --resume <sid>` / `gemini -r <sid>` запускается с handshake'ом. Флаги сбрасываются в БД: `wasInterrupted = false`, `overlayDismissed = false`. Цикл начинается с нуля — следующее аварийное закрытие снова покажет overlay.

### Edge: юзер кликает Dismiss (или Escape)
`dismissInterruptedSession()` → `overlayDismissed = true` в Tab-записи SQLite. Overlay скрывается. Следующая re-загрузка страницы (Cmd+R, авто-рестарт после Vite-hot-reload, повторный cold-launch без новой сессии) НЕ показывает overlay снова: `beforeunload`-проверка `if (hasSession && !overlayDismissed)` теперь false.

### Edge: запуск новой AI-сессии в том же табе после Dismiss
Это важная точка сброса. Юзер dismiss'нул overlay, потом решил запустить новую сессию (например, `claude` свежий, без resume). При `setClaudeSessionId` / `setGeminiSessionId` оба флага (`wasInterrupted` и `overlayDismissed`) обнуляются. Резон: если новая сессия будет прервана, overlay должен появиться **снова** — иначе юзер потеряет доверие к recovery-механизму. Dismiss = «эту конкретную старую сессию не восстанавливать», не «никогда больше не показывать overlay в этом табе».

### Edge: множественные сессии помечены wasInterrupted
Подводный камень в lifecycle — оба writer'а (renderer и main) могут гонкой перетереть друг друга. Полный разбор отброшенных подходов и текущего решения — `fix-interrupted-session-lifecycle.md`. С точки зрения сценария: после правильного фикса юзер при cold-launch видит overlay **только** на тех табах, где реально была активная Claude-сессия в момент выхода, не на всех Claude-табах подряд.

См. `fact-claude-sessions.md::Interrupted Recovery`, `fix-interrupted-session-lifecycle.md`, `fact-data-persistence.md`.

## Сценарий: Cmd+click Refresh в BrowserTab переключает view

Подсценарий Browser Tab Navigation, выделен отдельно потому что описывает не клик на ссылку, а явный Refresh-action. Юзер сидит в `view: 'terminal'` своего BrowserTab'а (только что перезапустил `vite`), хочет увидеть страницу.

### Основной путь
1. Состояние: BrowserTab, `view: 'terminal'`, dev-сервер только что напечатал `ready in 234 ms`.
2. Юзер кликает Refresh-кнопку в шапке таба (icon `↻`).
3. Handler вызывает `setBrowserActiveView(tabId, 'browser')` БЕЗ условия «если уже в browser». View переключается принудительно.
4. Webview перезагружает текущий URL.
5. Юзер видит обновлённую страницу.

Без принудительного переключения юзер должен был кликать `view: 'browser'` отдельно — лишний шаг после каждого refresh. Кнопка Refresh физически живёт в шапке BrowserTab (видна в обоих view), поэтому интерпретация однозначна: «обновить страницу и **показать** результат». Это паттерн «ожидаемого результата» — UI-команда вырабатывает то состояние, которого юзер ожидает увидеть, не оставляет половину работы.

См. `fact-tabs.md::Browser Tabs`, основной сценарий выше про Cmd+click.

## Сценарий: Resume Inactive CLAUDE с мобилы

Когда юзер на мобильном открывает CLAUDE-PTY-таб, в котором Claude-процесс умер (Ctrl+C в десктоп-сессии, crash, app restart) — он должен иметь возможность «вернуть Claude к жизни» в тот же таб, чтобы продолжить сессию по тому же `sessionId` без потери истории и без открытия новой вкладки. Сценарий проходит через состояния `inactive → starting → active`, координирует mobile-web UI, web-server bridge, main session-detector и PTY/Claude TUI.

### Основной путь

1. Юзер тапает CLAUDE-таб в project list мобильного — таб в state `inactive` (серая dot слева от имени). История JSONL уже видна в чате (загружена через `/history` REST, читается напрямую из `~/.claude/projects/...jsonl`).
2. Вместо composer внизу — оранжевый баннер «▶ Resume Claude session / session stopped · JSONL preserved».
3. Юзер тапает Resume. Mobile UI меняет состояние кнопки на loader. POST `/api/sdk-tabs/:id/resume` → bridge `resumeClaudeTab` action в renderer.
4. Renderer проверяет presence через `claude:get-presence` — status уже `inactive` (PTY жив, Claude процесса нет), значит можно слать. Зовёт `markPendingResume(tabId, sid)` (защита от stale bridge.json) + `state.clearInterruptedState(tabId)` (снять desktop overlay «Сессия прервана»). Шлёт `\x15claude --dangerously-skip-permissions --resume <sid>\r` в PTY.
5. PTY проглатывает команду, shell спавнит Claude process. Через 1-3 секунды Claude инициализируется и пишет `~/.claude/bridge/<sid>.json` → main Bridge detector ловит → `_notifyClaudeSession(tabId, sid)` → web-server promote pending watcher + `_webBroadcast({type:'snapshot', sessionStatus:'active'})`. Mobile получает snapshot — UI знает что Claude запустился (но prompt ещё не отрендерён).
6. Mobile отображает «Starting Claude…» strip (вместо composer и вместо Resume-баннера). Через ещё 1-3 секунды Claude Ink TUI рисует `⏵` в PTY-выводе → main глобальный детектор `⏵` → `claudePromptReady.add(tabId)` → `_webBroadcast({inputReady:true, sessionStatus:'active'})`. Mobile flip'нул UI на composer.
7. Юзер пишет промпт, тапает Send. POST `/api/sdk-tabs/:id/send` → bridge `sendMessageAuto` → routes to `terminal:paste {fast:false}` (single-bracket-pair, waitForRender). Claude получает paste через atomic bracketed paste, обрабатывает как обычный prompt.

### Edge: Claude уже живёт в табе на момент Resume

В очень узком окне (~1-2 сек) mobile status может показывать `inactive` тогда как Claude фактически уже поднялся (например, юзер тапает Resume в момент когда desktop AutoResume только что отработал). Если просто послать `\x15claude --resume`, Ctrl+U стёр бы typed text desktop-пользователя И выкинул бы его из Claude TUI обратно в shell.

`resumeClaudeTab` делает pre-check через `claude:get-presence` сразу перед отправкой команды. Если status вернулся `active` или `busy` — refuse: возвращает `{alreadyRunning: true}`, никакой команды в PTY не уходит, mobile сразу видит composer. Параллельно зовётся `state.clearInterruptedState` — overlay снимется, потому что он был stale.

### Edge: ловля sessionId до того как WS subscribe'нулся

Если юзер быстро тапает по табу сразу после создания, mobile WS subscribe'тся, но `getClaudeTabStatus` ещё не вернёт sessionId (Bridge:Fresh не выстрелил). Web-server паркует tabId в `claudeTabWatcherPending: Set` без таймеров. Когда main позже звонит `_notifyClaudeSession(tabId, sid)` — promotion срабатывает: pending удаляется, fs.watch стартует, mobile получает `snapshot` с sessionId.

Если subscriber отвалился (юзер быстро навигировался прочь) — `releaseClaudeWatchersIfOrphan` срабатывает на WS close и чистит pending Set. Никаких orphan timers, всё event-driven.

### Edge: JSONL ещё не на диске

SessionId известен (bridge.json есть), но `findSessionFile` возвращает null — Claude батчит первые писания, JSONL появится через 100-500ms. Web-server ставит **одноразовый** `fs.watch` на `~/.claude/projects/` root: первое появление файла с этим UUID в имени → tryPromote → реальный fs.watch на сам файл. Один-выстрел event-driven, не polling.

См. `fact-mobile-claude-pty.md` для полной механики, `methodology/переносимый-дизайн.md::Event-driven promotion вместо retry-polling` для переносимого принципа.
