# Flow: диагностика логами

Этот файл — рабочий flow для AI-агента, когда пользователь приносит баг класса «иногда зависает», «hover не работает», «loader моргнул», «клик дошёл через секунду», «в логах что-то рядом, но непонятно что виновато». Цель flow — не придумать правдоподобный фикс по коду, а построить причинную трассу: пользовательское действие → доставка input → renderer work → IPC → main event loop → внешние процессы/БД/файлы → видимый UI-результат.

## Instrumentation before guesses

Если по текущим логам нет стопроцентной уверенности, следующий шаг — добавить более точные логи и повторить тот же pipeline. Код может выглядеть «очевидно сломанным», но пока нет наблюдаемого перехода `event → state → UI`, это гипотеза. Особенно это важно для Electron, PTY, hover/Cmd-state, TUI-автоматизации, SQLite и JSONL: баг часто находится между процессами, а не в видимом React-условии.

Для TUI-автоматизации причина засчитывается только когда лог связывает пользовательский intent, записанные клавиши/PTY write, распознанный frame и авторитетное состояние после действия. Если Codex/Claude overlay уже открыт, cleanup-клавиша тоже часть state machine: нельзя предполагать что `Escape` «просто закроет», пока frame/footer и лог не доказывают это. Шрам 2026-06-17 с Codex Rewind выглядел в коде как возможная ошибка навигации, но root cause был установлен только по цепочке `open Esc timedOut=false` → `Error: skipDuplicates is not defined`; без такого лога правильный следующий шаг был бы добавить instrumentation и повторить pipeline.

Timeout/fallback в state machine — это граница ошибки, а не запасной источник истины. Если readiness, selected target, sync marker или restored input не доказаны, следующая команда не должна выполняться «через N секунд всё равно»: нужно упасть, залогировать последний frame/reason и повторить pipeline с дополнительной instrumentation. Шрам 2026-06-18 с Codex Rewind: fallback после input-ready или grab mismatch продолжал бы цепочку уже после того, как `Escape` мог отменить MCP startup или rollback мог примениться не к тому prompt'у.

В xterm/TUI send-flow различай snapshot, render marker и durable artifact. Snapshot сразу после paste может увидеть старый prompt (`source=*:dim-hint`) даже когда Codex уже принял байты; render marker тоже может быть stale или не прийти в hidden/background окне. Для Codex это означает: не объявляй root cause по post-paste UI/render ACK и не делай его обязательным gate'ом перед Enter. Правильная диагностика Codex submit — логировать before-paste draft guard, ordered PTY paste+Enter, затем rollout `user_message` audit по length/hash. Если `hasDraft=null` до paste, лог должен содержать sampled rows/debug: пустая строка после `›` может быть началом multiline draft, и без строк вокруг cursor/tail нельзя отличить реальную пустоту от пропущенного продолжения composer'а.

Минимальный полезный лог содержит не сообщение «функция вызвалась», а измерение: абсолютный timestamp, caller/source, reason, entity id, before/after, duration и expected value. Лог без timestamp'а и причины почти всегда превращается в пересказ: видно что “что-то было рядом”, но нельзя доказать порядок.

Для memory-симптома на большом append-only источнике первый аудит делается streaming-проходом, который не создаёт тот же полный object graph, который мы пытаемся измерить. Выпиши размер файла, число и максимум строк, сумму тяжёлых полей, а затем отдельно посчитай слои копирования: parser cache → UI projection → IPC structured clone → previous/current renderer state → logger queue. Маленький DOM или Virtuoso доказывают только render budget, но ничего не говорят о размере переданного payload. Логи уже завершившегося процесса могут доказать механизм, но не точную атрибуцию пикового RSS: для неё нужен live sample или process metric в момент пика.

Сам logger входит в ту же модель ресурсов. Перед добавлением ещё сотен строк проверь, не форвардится ли одно событие двумя путями, какой размер/свежесть у файла, есть ли rotation по размеру и останавливает ли writer подачу на `write(false)` до `drain`. Неограниченная очередь диагностики может усилить тот же memory-симптом, который она измеряет.

Для редкого сбоя после конкретного действия не включай постоянный сырой лог всей подсистемы. Держи в памяти ограниченное кольцо причинных событий, помечай точным checkpoint само действие и при доказанном отрицательном исходе сохраняй только окно вокруг него: несколько состояний до, все переходы после и identity процесса/поколения. Успешный путь не оставляет файл; если подтверждение пришло поздно, артефакт именно этой попытки удаляется. Параллельные попытки получают разные identity и не перезаписывают друг друга. Такой incident-triggered capture сохраняет нужные байты для разбора редкой гонки, но не превращает обычную работу в бесконечный лог и не делает сам таймаут источником истины. Конкретная реализация этого правила для Claude Enter описана в [`fact-terminal-mcp.md`](../knowledge/fact-terminal-mcp.md).

Для mobile/network pipeline проверяй границы независимо: клиентский запрос, публичный TLS-порт, nginx на VPS, reverse SSH tunnel, локальный Electron endpoint. Успешный TCP connect не доказывает доставку payload: в шраме с `remote-control.f9922.tech` 443 порт принимал handshake TCP, но `tcpdump` на VPS не видел TLS ClientHello, тогда как local endpoint и tunnel были живы. В таких задачах root cause засчитывается только когда каждая граница дала свой наблюдаемый сигнал или отрицательное доказательство.

Для native UI automation доказательство строится так же: жест в Simulator сам по себе не причина и не результат. Нужны четыре независимых наблюдения — accessibility/screenshot до и после, app-side лог с threshold/request/status, серверный или runtime artifact, и финальное видимое состояние. Если WDA сделал swipe, но в логах нет `begin-drag`, проблема в попадании жеста/overlay. Если есть `begin-drag` и `armed=true`, но нет request/refresh-end, проблема уже в app/server path. Если app log file stale, не делай отрицательный вывод: возьми текущий in-app log buffer через UI copy и только потом сравнивай. Физические эффекты вроде haptic не выводятся из расстояния pull-жеста; они доказываются только отдельным app event в месте вызова haptic API.

## Момент измерения — часть измерения

Для текущего приоритетного ремонта History/workflow/input Fedor11.10 требует
сверять технические решения с6AstraPro. Передавай один ограниченный пакет текущего
кода, исходных измерений и проверяемых утверждений; замечания подтверждай локальным
контрпримером и возвращай исправленную дельту на сверку. Модель — дополнительный
ревьюер, не источник истины: её согласие не превращает component test в full DEV
или поздний профиль в доказательство причины исходного жеста.

Инструментация врёт не только неверной формулой, но и неверным моментом съёма. Серия 28.07 (measured-layout в History, девять прогонов): из восьми «дефектов» семь оказались дефектами самих проб, а механизм работал почти сразу. Все семь — один класс: **спросили не тогда**.

- **У умирающего компонента спрашивать нельзя.** `getState` в cleanup владельца резолвится через реактивный граф уже размонтирующегося списка: вызов уходит в никуда молча, без ошибки. Доказательство диагноза было косвенным и решающим — 20 cleanup'ов дали 0 сохранений, при том что 21 строка ДРУГОЙ свежей отладки в том же boot присутствовала, то есть код доехал, а вызов проглотился.
- **Наличие цели ≠ готовность цели.** Замер через один `requestAnimationFrame` бил до монтирования строк (20/20 значений `na`); замер на первом же кадре после появления строки ловил дорихтовку позиции (плохие значения строго на `frames=3/7`, нулевые — на `5+`). Ждать нужно стабилизации: два одинаковых кадра подряд.
- **Цель нужно заморозить до старта.** Перечитывание якоря внутри цикла проверки сравнивало результат с целью, которую пользовательская прокрутка успела сдвинуть — «ошибки» 153px и 331px при визуально идеальной позиции.
- **Счётчик состояния кадра описывает кадр, а не сессию.** Значение, снятое на первом painted-кадре владельца, не меняется от прокрутки; «объект видим, счётчик 0» — слепота пробы, а не сломанная фича.
- **Константа в диагностической строке — ловушка для читателя.** Ветка empty-state печатала `loader=hidden` жёстко, поэтому легитимная отрисованная заглушка была в логе неотличима от запрещённого пустого кадра; независимый ревьюер честно применил правило и завёл несуществующую регрессию. Поле обязано отражать факт, а не намерение автора.

Практическое правило: **строка, которая не различает «не смог измерить» и «измерил ноль», хуже отсутствия проверки** — она создаёт видимость контроля. Отсюда же требование к брифу тестировщика: «увидел аномалию в диагностике → сначала проверь соседний контекст и пользовательскую грань, и только потом называй дефектом продукта». До появления этого правила три прогона подряд обрывались на ложной тревоге; после — прогон дошёл до конца и нашёл настоящий баг.

Для мерцания и промежуточных скачков нельзя оставлять только стабилизированные
снимки: этим фильтром можно удалить сам дефект. Записывай ограниченный непрерывный
интервал входных событий и фактически показанных кадров на одной временной шкале;
финальное совпадение проверяет сохранность, а не отсутствие ошибочного показа
между началами и концами операций. Пример — `fact-terminal-rendering.md::Codex0.154: белый курсор скачет при звёздах Astra`.

## После фикса: классифицируй класс проблемы

Исчезновение исходного симптома ещё не завершает расследование. После фикса восстанови, какое предположение оказалось неверным, кто был источником правды и где менее авторитетный сигнал был принят за него. Затем проверь соседние consumers того же контракта — не потому что их нужно сразу менять, а чтобы понять, локальна ли ошибка. В Codex session-binding один неверный ID одновременно кормил loader, Copy, Timeline, API, SQLite и History, поэтому локальный визуальный фикс не мог закрыть класс.

Финальная классификация всегда одна из четырёх. `local fixed` — неверное предположение ограничено одним путём, а тест доказывает границу. `local but check similar paths` — текущий путь закрыт, но тот же шаблон встречается рядом; добавь точечный тест или лог, не правь соседей без доказательства. `architecture issue` — несколько поверхностей получают разные версии одной истины или одна сущность имеет конкурирующие источники; сначала сформулируй общую модель и список нарушителей. `risk needs logs` — похожий механизм возможен, но текущая трасса не связывает его с симптомом; добавь наблюдение и оставь код нетронутым.

Для каждого результата разделяй «уже исправлено сейчас» и «отдельный следующий шаг». Это не отчётный формализм: без границы архитектурный аудит либо заканчивается слишком рано после одного зелёного теста, либо разрастается в слепой рефакторинг всех похожих мест.

## Наблюдение не стоит перед пользовательским input

Read-only проверка статуса, процесса или writer identity не должна сериализоваться перед физической доставкой уже разрешённого пользовательского жеста. Критическая трасса строится как `event received → PTY write → durable artifact`; reconciliation и обновление UI идут параллельно или после записи, если они не нужны для safety-решения именно этого действия. Иначе «проверить, куда пишем» превращается в 6–15 секунд, в течение которых Enter визуально нажат, но байты ещё не покинули приложение.

Доказательство задержки требует трёх времён: когда жест дошёл до приложения, когда байты реально записаны в PTY и когда появился `user_message`/другой durable artifact. Если длинный интервал находится до PTY write, не обвиняй xterm, Codex или renderer-перерисовку; ищи очередь, lock или дорогой preflight. Если лог не пишет одиночный Enter, классификация остаётся `risk needs logs`, даже когда соседний таб уже доказал тот же механизм.

## Freeze/beachball: наблюдатель вне зависшего loop

Для настоящего freeze обычный in-process logger слеп в момент проблемы. `[Perf:MainLoopGap]`, renderer `LongTask`, EventTiming и `console.log` пишутся только после того, как event loop разморозился. Поэтому внешний watchdog — это не «ещё один лог», а другой класс наблюдения: отдельный процесс получает heartbeat от main/renderer, видит silence снаружи и может снять macOS `sample <pid>` во время зависания.

Практический паттерн:
1. Main шлёт heartbeat watchdog'у через fork IPC и прикладывает snapshot активных операций.
2. Renderer шлёт heartbeat напрямую в unix socket watchdog'а, не через main; иначе frozen main скроет renderer stall.
3. На пропуск heartbeat watchdog пишет `STALL`; при длинной тишине снимает `sample`; на восстановлении пишет `RESUMED`.
   Само молчание не разрешает завершить наблюдателя как orphan: смерть владельца
   подтверждается закрытием его IPC-канала, а лимиты capture продолжают действовать.
4. In-process gap log после разморозки сверяется с watchdog и фактическим интервалом sample. Совпадение с `ipcAgg5s` сужает поиск, но сумма async IPC — не CPU-время. В stripped Electron имя ближайшего native-экспорта с большим offset тоже не доказывает конкретную функцию.

Для жалобы через несколько дней сначала открывай сохранённые CPU-окна и incident-пакет, а не запускай `ps` сейчас и не приписывай его значения прошлому событию. Сравнивай системный CPU, процессы приложения и внешние процессы на одном интервале; различай 100% одного ядра и всей машины. Профиль после сигнала может попасть только в продолжение нагрузки: его `requested/started` и покрытие важнее имени файла. Отсутствие артефакта при квоте/ошибке/пропуске наблюдателя — неизвестность, не отсутствие сбоя. Реализация и ограничения: [отложенная диагностика](../knowledge/логирование-оптимизации.md).

Сам наблюдатель не должен создавать измеряемую паузу. Проверка rate-limit обязана предшествовать дорогому чтению. Geometry/computed-style reads из capture-listener или MutationObserver после изменения стилей могут синхронно заставить весь workspace пройти layout. Фоновые логи input/cursor пишут доставленную цель события и явные состояния; настоящую геометрию проверяет отдельный разрешённый эксперимент.

MacOS “оранжевый курсор/волчок” напрямую перехватывать не надо и обычно нельзя надёжно связать с конкретной строкой JS. Его инженерный эквивалент для Electron — отсутствие heartbeat + sample стека процесса во время stall. UI-симптом описывается словами пользователя, root cause доказывается через watchdog/gap/IPC/DB logs.

## IPC attribution: activeOps недостаточно

`activeOps=0` в gap-логе не значит, что ничего не работало. Если синхронный IPC или SQLite-запрос завершился ровно перед тем, как gap timer получил управление, активная операция уже закрыта. Поэтому нужны два слоя:

- `recentOps5s` — последние завершившиеся операции с duration/caller;
- `ipcAgg5s` — агрегат по каналам, который не теряется даже если per-keystroke каналы шумят или recent-ring вытеснен.

В Home-freeze расследовании это было решающим: без IPC aggregation логи выглядели как `activeOps=0`, и подозрение уходило в Home render, Timeline poll или системную нагрузку. После обвязки стало видно `ipcAgg5s=search:stats:n=1:sum=4102:max=4102`, а рядом `[Perf:IpcSlow] channel=search:stats durMs=4101.6`.

## Caller/reason/visibility вместо “лог рядом”

Лог подсистемы рядом с freeze не доказывает её вину. Timeline/backtrace мог стартовать до Home, продолжить in-flight после перехода или быть вызван другим компонентом. Любой дорогой IPC должен нести контекст:

- `source` / `caller` — кто вызвал;
- `reason` — effect, poll, manual, visibilitychange, statusSync;
- `tabId`, `sessionId`, `projectId` — какая сущность;
- `visible` / `isVisible` / `document.visibilityState` — был ли компонент реально активен;
- `instanceId` — какой React-instance, если компонент persistent-mounted.

Root cause засчитывается только при пересечении по времени: caller/reason/instance попадает в тот же `*Abs` интервал, что input delay, renderer long task, main loop gap или watchdog stall. Если пересечения нет, подсистема остаётся подозреваемой, но не виновной.

## Input delay vs handler work

Называй пользователю конкретную работу: данные уже лежали на SSD, были
разобраны в RAM или уже существовал DOM — это три разных степени готовности.
Далее укажи дорогой измеренный этап: чтение, очередь, создание/изменение DOM,
пересчёт стилей, layout, paint или ожидание доступного CPU. Наличие кэша не
обнуляет следующие этапы, а высокая загрузка Docker не доказывает, что в Noted
нет собственного лишнего расчёта. Сопоставляй CPU групп, системный CPU/ядра,
memory/swap и renderer thread CPU на общей временной границе; неизвестное
звено оставляй неизвестным. После этого объясни, какая правка сокращает работу
или почему узкое место сейчас находится вне приложения.

Для UI-freeze сначала раздели три вещи:

1. Когда пользовательское событие физически произошло (`event.timeStamp` → absolute time).
2. Когда renderer начал его обрабатывать (`processingStart`, capture listener receive time).
3. Сколько занял handler/render после доставки.

Если click handler занимает 12ms, а `inputDelayMs=1600`, чинить handler бессмысленно: приложение не начало обрабатывать input полторы секунды. Тогда ищи renderer loop gap, main loop gap, OS scheduling, hidden-window throttling или блокирующий IPC. Если handler реально долгий — тогда React Profiler/LongTask/commit logs.

Для CDP/E2E логов обязательно проверяй `document.visibilityState`. Hidden renderer может давать фальшивые задержки hover/input из-за throttling, не равные пользовательскому foreground freeze. CPU-профиль скрытого окна также может показывать idle, потому что rAF и отложенные свапы не исполнились. В разрешённом отдельном foreground-эксперименте сначала покажи тестовое окно и проверь `visibilityState === 'visible'`. Автоматическая фоновая диагностика, наоборот, не вправе поднимать production-окно или менять lifecycle ради профиля: она сохраняет фактическую видимость и ограничивает выводы этим состоянием.

Атрибуция `during=` из activity-трейла означает «пересекается по времени с задачей», не «является её причиной»: метка закрывается на следующем кадре и накрывает чужую работу того же кадра. Она сужает круг подозреваемых; поимённый вердикт даёт только CPU-профиль (inclusive по файлам/функциям). Живой пример иерархии: `during=timeline-swap,history-owner-mount` указывал на Timeline, а профиль показал 746мс в `sendSync` внутри cleanup-эффекта композера — блок, который ни одна метка не покрывала.

## Приёмка меряет пользовательский ритм, не свою пробу

Точечная проба легко проходит там, где пользователь страдает. Оптимизация переключения вкладок прошла несколько «PASS» на замере вида «клик → через 60мс один right-click → пауза 1200мс → следующий цикл», а пользователь продолжал ловить фриз — потому что его симптом был не одной большой задачей, а ПОЕЗДОМ кусков по 150-250мс на протяжении секунд после переключения, и он вёл курсор непрерывно. Точечная проба попадает в тихую щель между кусками и меряет тишину; порог «нет задачи > 250мс» пропускает поезд из 86 задач по 200мс целиком. Приёмка перф-фикса обязана воспроизводить непрерывность реального ввода (ховер каждые ~16мс на протяжении 1.5-2с после действия) и судить по гистограмме задержек каждого события за всё окно, плюс считать СУММУ блокировок за окно, а не только максимум одной. Второй слой того же урока: мерить надо «пиксели изменились» (presentationDelay, наблюдатель смены фона в DOM), а не «обработчик сработал» — кадр может выйти сильно позже handler'а.

## Отрицательный вердикт обязан включать каналы отказа

Полнота диагностики проверяется до следующей пользовательской установки.
Не строй серию «добавили время focus → ждём нового репорта → добавили cache miss»:
для затронутой цепочки заранее нужны идентичность действия, границы этапов,
причины fallback/отказов и состояние самого сборщика. Приёмка с известной
паузой должна назвать правильный слой, а не просто напечатать большой duration.
Тяжёлый стек может иметь квоту; дешёвые counters и причины cache miss остаются
доступны независимо. Опоздавший профиль явно маркируется как после жеста.

Раунд фиксов «прошёл по логам», пока grep-фильтры смотрели только на happy-path маркеры (`LOAD_START/APPLY/UNCHANGED` + LongTask). Тем временем каждая загрузка тяжёлой вкладки падала с `LOAD_RESULT_FAIL error=ReferenceError` — кэш никогда не наполнялся, все остальные фиксы работали вхолостую, а фильтр этих строк просто не видел. Один тихий отказ выключил все кэши разом, и это читалось как «пять фиксов, ничего не помогает». Перед вердиктом «фиксы работают» grep обязан включать `FAIL|ERROR|REJECT|CANCEL`-варианты каналов подсистемы наравне с успешными; «в логе нет плохих строк» — валидно только если плохие строки вообще входили в паттерн.

## Data proof before code proof

Когда подозрение уходит в БД/индексы/файлы, сначала проверь реальные данные и план выполнения, а не только код. В Home-freeze `getIndexStats()` выглядел обычным `COUNT`, но реальная база имела ~87K `session_chunks`, ~19K embeddings и query plan `SCAN session_chunks`. Именно это объяснило 4s sync block в main process.

Паттерн:
```bash
sqlite3 "$DB" "EXPLAIN QUERY PLAN <query>;"
sqlite3 "$DB" "SELECT COUNT(*) ...;"
grep -E "<channel>|MainLoopGap|Watchdog|IpcSlow" "$LOG" | tail -80
```

Код без real data часто ведёт к оптимизации не того места: можно переписать React Home, пока реальный freeze сидит в sync SQLite count.

## Что в этом flow сделал Claude и почему это помогло

Работа Claude помогла не тем, что он “угадал фикс”, а тем, что закрыл атрибуционные дыры. Он добавил внешний watchdog, универсальную IPC-обвязку, `ipcAgg5s/recentOps5s`, Timeline caller/reason/visible attribution и boot AutoRepair perf logs. После этого стало можно не спорить, похож ли Home на виновника: логи показали, что Home mount быстрый, tab switch быстрый, Timeline только рядом, а main process стоит внутри `search:stats`.

То есть особенность была не в большем количестве строк логов, а в причинной форме логирования: каждый слой отвечал на конкретный вопрос “где задержка физически находится?”. Это можно было бы добиться и вручную через много повторов, но без такого класса instrumentation повторы давали бы только новые симптомы. Правильный flow сокращает итерации: сначала строишь трассу, потом фиксишь самый толстый доказанный участок.

## Куда класть результат расследования

Flow-файл хранит процедуру: как логировать, какие поля нужны, как читать отрицательные доказательства. Конкретный шрам хранится в `knowledge/fix-*`: например Home freeze от `search:stats` лежит в `knowledge/fix-performance-lags.md`. Механика подсистемы хранится в `knowledge/fact-*`: `fact-semantic-search.md` объясняет stats-path и partial index, `fact-project-home.md` — где Home вызывает Semantic Search, `fact-timeline.md` — почему Timeline требует caller attribution.

Если этот flow повторится в другом проекте без привязки к custom-terminal, его стоит вынести в глобальный skill или global docs-pattern. Пока это project methodology: правила применимы шире, но команды, логи и примеры завязаны на Noted Terminal.
