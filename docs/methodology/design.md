# Design Methodology

Переносимые принципы UX/архитектуры — применимы в любом multi-tab или multi-backend проекте, не только в custom-terminal. Конкретные реализации лежат в `docs/knowledge/fact-*.md` со ссылками сюда.

**Соседние файлы методологии:**
- [`design-bugs.md`](design-bugs.md) — каталог типовых багов, всплывающих при разработке UI: обрезка popup'ов по краям, hover-bridge, click-outside ловушки, рассинхрон видимости и состояния, z-index конфликты. Открывай ПЕРЕД проектированием очередного UI-элемента — большинство «новых» багов уже задокументированы.

## Per-tab tooling state

**Принцип:** в multi-tab UI настройки «инструмента» (модель LLM, фильтр, окружение) не должны быть глобальной переменной. Каждый таб — отдельный контекст, и переключение настройки в активном табе не должно затрагивать фоновые табы.

**Симптом, что принцип нарушен:** пользователь в фоновом табе долго ждёт ответа от модели X, переключается в другой таб, меняет модель на Y «на минуту», возвращается — и видит что ответ в первом табе пришёл от Y вместо X. Доверие к фоновой работе сломано.

**Реализация:** `Map<tabId, state>` в main process + механизм идентификации «к какому табу относится текущий запрос». Идентификатор должен пробрасываться **в каждый запрос**, не храниться как «текущий активный».

**Где пробрасывать tabId** — три варианта по убыванию надёжности:
1. **URL-префикс** (`http://proxy/t/<tabId>/...`) — работает всегда, даже если внешний клиент не умеет custom headers
2. **Custom HTTP header** (`X-App-Tab-Id`) — только если контролируешь клиент. Сторонние CLI (Claude Code, openrouter-style) свои headers шлют by design, кастомные не добавишь
3. **Отдельный port per tab** — изоляция полная, но N портов = N TCP-listener'ов, overhead растёт

В custom-terminal: вариант 1, см. `knowledge/fact-provider-proxy.md::Per-tab routing`.

## Truth from server response, not local UI flag

**Принцип:** когда UI должен показать «что **реально** произошло» (пост-фактум индикация — какая модель ответила, какой бэкенд обработал, какой регион выдал результат) — источник правды только **ответ сервера**, не локальный state UI.

**Симптом, что принцип нарушен:** пользователь переключил backend → UI обновился → ответ пришёл от **старого** backend (потому что запрос ушёл до переключения) → UI показывает новый, а данные старые. Расхождение.

**Применение в коде:**
- Каждое сообщение в истории помечается метаданными из server response (`message.model`, `provider`, `region`)
- UI рендерит badge **из этих метаданных**, не из текущего значения настройки
- Live indicator («сейчас отправляется куда») может опираться на UI-state, но это **другой** индикатор, не путать с post-factum badge

**Применение в архитектуре:**
- API-клиенты пишут в лог/JSONL **то что вернул сервер**, не то что отправили
- Stripe vs PayPal multi-mode payment → quitanze показывает «paid via Stripe», прочитав из response, не из локального selector'а
- В custom-terminal: bridge.sh показывает Claude TUI выбор модели, но **реальный** провайдер берётся из `message.model` JSONL → Timeline footer badge. См. `knowledge/fact-timeline.md::Provider badge` и `knowledge/fact-provider-proxy.md::Bridge врёт про active provider`.

## Two-tier hierarchical selectors

**Принцип:** когда выбор первичной сущности определяет доступные вторичные опции (категория→товары, страна→города, провайдер→модели) — UI разделяет это на **два независимых ряда контролов**, не сливает в один список.

**Симптом, что принцип нарушен:** в одной кнопочной строке смешаны разнородные опции (`[Claude][MM2.5][MM2.7][DSv4F][DSv4P]`). Чтобы переключиться с MM2.7 на DSv4F пользователь читает все 5 опций, мысленно группирует по провайдеру, выбирает. Каждое добавление новой модели делает строку шумнее, шире, плюс лишает структуры.

**Реализация:**
- Ряд 1 — primary (Provider, Category, Country): только базовые сущности
- Ряд 2 — secondary (Model, Item, City): динамически перерисовывается под выбор в Ряду 1
- При смене Ряд 1 — Ряд 2 восстанавливает **последний выбор для этой ветки** (per-provider memory). Возврат к Anthropic после Zen → вспоминается последняя Anthropic-модель, а не дефолт

**Связанные опции зависят от ряда 1.** Если конкретные настройки доступны только для одной первичной сущности (например, Effort только для thinking-моделей) — третий ряд: либо `disabled` для несовместимых, либо скрыт. Не смешивать с Ряд 2 чтобы избежать «опция-сирота».

**Антипаттерн «полный список опций per row»:**
```
[Provider] [Claude] [DeepSeek] [Zen]
[Model]    [default] [sonnet] [opus] [haiku] [V4F] [V4P] [MM2.5] [MM2.7]  ← плохо
```
Пользователь должен сам сортировать опции по провайдеру в голове. Better: Ряд 2 показывает только модели текущего провайдера.

В custom-terminal: см. `knowledge/fact-claude-tui-control.md::Model row` и `knowledge/fact-provider-proxy.md::UI selector`.

## Воспринимаемая задержка UI-команд — асимметрична

**Принцип:** между кликом и видимой реакцией пользователь по-разному переносит одну и ту же физическую задержку в зависимости от того, **есть ли промежуточный визуальный feedback**. Если действие что-то стирает/перемещает/меняет на экране — 80-150ms задержки маскируются этим визуальным событием. Если экран не меняется — даже 80ms ощущаются как «зависание».

**Симптом, что принцип нарушен:** клиент жалуется *«когда у меня уже что-то написано в инпуте — команда срабатывает мгновенно, а когда инпут пустой — почему-то лагает»*. Физически задержка одинаковая. Разница в том что в первом случае Ctrl+S стирает текст (визуальный «удар»), во втором — no-op, экран замирает на ту же длительность, и мозг считывает это как баг.

**Реализация:** при проектировании цепочки `click → side-effect → settle → submit` минимизируй фиксированные паузы (drain'ы, debounce'ы) **в первую очередь для случая когда side-effect невидим**. Конкретно:
- ✅ Заменить «безопасные» 80-150ms фиксированные паузы на event-driven ожидание (`waitForRender`, sync marker, status flag). Когда есть что рендерить — настоящее событие приходит за 5-30ms; когда нечего — ожидание мгновенно возвращается.
- ❌ Не подбирать «средние» цифры (200ms «должно хватить») по worst-case — это всегда переплата для пустого случая, где worst-case = 0ms.

**Связанный антипаттерн — «timeout как safety net вместо причины».** Если ставишь 500-8000ms timeout «на всякий случай если событие не придёт», а потом измеряешь и видишь что реально событие приходит за 10-30ms — timeout не safety, это **маска бага в твоей детекции события**. Найди почему детекция иногда не срабатывает (stale-фильтр, race с подпиской, неправильный baseline) и почини её, не накручивай timeout.

В custom-terminal: см. `knowledge/fact-claude-tui-control.md::Stash Flow` (cleanup паузы после Ctrl+S свели с 80+50+150ms до 20+50ms — для пустого инпута это разница между «лагает» и «мгновенно») и `knowledge/fix-stale-sync-markers.md::markWriteTime` (детектили *наши же* маркеры как stale → timeout 500ms маскировал баг).

## Persistent state across UI transitions: error-branch must clear, not silent-return

**Принцип:** когда UI-state переживает переходы (tab-switch, route change, navigate-away) через persistence-механизм (Map, sessionStorage, in-memory cache), КАЖДАЯ ветка обработки результата — включая error и empty-response — обязана **явно очищать** сохранённый state. Иначе пользователь возвращается в transitional-фазу (loading/pending) без возможности её прервать.

**Симптом, что принцип нарушен:** долгий async (HTTP, IPC, queue worker), пользователь переключился, вернулся через минуту — UI всё ещё в розовой/синей анимации «загрузки», хотя реально операция давно завершилась с ошибкой. Перезапустить нельзя (нет UI-control в transitional-state), отменить нельзя (АbortController уже сработал). Пользователь сидит в зомби-state до перезапуска приложения или ручного обхода (другая кнопка, которая случайно сбрасывает state).

**Реализация:**
- Каждая ветка `if (response.ok)`, `if (data)`, `if (compactText)` имеет **парную** очистку: `else → savedMap.delete(key)`. Не молчаливый `return`.
- На каждой error-ветке — visible toast с HTTP-статусом/кодом ошибки. Молчаливый clear так же опасен — пользователь видит «исчезновение лоадера» без объяснения, считает что просто «ничего не получилось» и не понимает что нужно повторить.
- Same-tab path обычно защищён (`setState(null)` в `catch`/`finally`), cross-tab/persistent path — нет. Аудит persistence-кода: для каждого `savedMap.set(key, state)` найди ВСЕ места очистки и сверь с веткой записи. Если веток записи > веток очистки → есть путь, который оставит zombie-state.
- AbortController **ненадёжен** как единственная защита: HTTP-response может быть буферизирован и придёт после abort signal. Sessionidref-guard / expected-key check после await — обязательны, и они тоже должны вести к очистке.

**Антипаттерн:**
```js
if (data.success) {
  savedMap.set(key, { phase: 'ready', data });
} else {
  // молчаливый return — savedMap всё ещё содержит phase='loading' от tab-switch save
  return;
}
```

**Правильно:**
```js
if (data.success) {
  savedMap.set(key, { phase: 'ready', data });
} else {
  savedMap.delete(key);
  showToast(`Error ${response.status}: ${data.error}`);
}
```

В custom-terminal: см. `knowledge/fact-timeline.md::Edit-Range Persistence on Tab Switch` (cross-tab 503 от Gemini не чистил saved map → бесконечный лоадер; шестой отброшенный подход после уже пяти других итераций по этому коду).

## Auto-focus на конечном поле, а не на промежуточном инпуте

**Принцип:** когда UI открывается с **готовым намерением пользователя** (он явно выбрал «ручной ввод», «редактировать вручную», «открыть пустой чат») — автофокус идёт на **конечное поле**, в которое пользователь собирался писать. Не на промежуточный текстовый инпут, особенно если этот инпут отправляет в нейронку/API/далёкий ресурс.

**Симптом, что принцип нарушен:** пользователь нажал «✏️ Открыть пустой чат» → панель открылась → курсор в textarea → пользователь по привычке (как в любом чате) написал свой текст и нажал Enter → отправилось в Gemini вместо замены готового ответа. То что он искал — поле редактирования первого ответа — было видно рядом, но без фокуса. Двойная работа: ждать ответ Gemini, потом всё равно редактировать.

**Реализация:**
- Если flow имеет несколько мест для текста (chat-input + assistant-response-edit-mode), и пользователь явно зашёл через путь «ручной ввод» — автофокус на edit-mode конечного сообщения (textarea замены), не на chat-input.
- Для этого: prop типа `autoEditInitial: boolean` пробрасывается до компонента; компонент инициализирует `editingMsgId = '<initial-msg-id>'` сразу при mount + `setTimeout(focus, 50)`.
- Если flow стандартный (пользователь сам открыл UI без явного намерения «вручную») — фокус как обычно, на chat-input.

В custom-terminal: см. `knowledge/fact-timeline.md::Прерывание и ручной ввод` (`autoEditInitial` flag для `EditRangePanel` — открывается с edit-режимом первого Gemini-ответа, чтобы юзер мгновенно вставил свой compact-текст).

## Edit affordance в каждой точке входа в просмотр

**Принцип:** если один и тот же контент видим в N разных UI-точках (тултип, popup, sidebar, inline-preview), кнопка «Редактировать» нужна в **каждой** из них — не только в одной «главной». Иначе пользователь видит контент в точке A, но edit-action только в точке B → когнитивная нагрузка: «как это вообще редактируется?».

**Симптом, что принцип нарушен:** пользователь говорит «не редактируется, нет маркера для редактирования» — хотя UI редактирования существует, но за другим тултипом / в context menu. Контент-видимость и action-доступность рассинхронизированы.

**Реализация:**
- Для каждого места рендеринга preview контента — pencil/edit icon рядом. Минимум 12px, hover-state, `e.stopPropagation()` если в Portal.
- Если edit-action открывает большой UI (отдельная панель/модалка) — все pencil-кнопки ведут в один и тот же flow, не дублируют логику. handler один.
- НЕ помещать edit только в context menu (ПКМ) — пользователи не всегда знают про ПКМ, особенно когда основной взаимодействие через hover/click.

В custom-terminal: см. `knowledge/fact-timeline.md::Note-on-Dot Integration::Pencil-кнопка в self-tooltip` (раньше dot-заметка редактировалась только через ПКМ + «Редактировать заметку», хотя её контент виден в self-tooltip самой entry; добавили pencil рядом с inline-preview).

## Создать ≠ переместить: UI зависит от существования сущности

**Принцип:** один и тот же property (position, priority, parent-child) имеет **два разных жеста управления** в зависимости от того, существует ли сущность:
- **Создание (сущности нет):** селектор «куда поставить» — все опции сразу видны как кнопки/dropdown, пользователь выбирает initial location.
- **Редактирование (сущность есть):** инкрементальное движение — стрелки ↑/↓, drag-handle, «move up/down by 1». Пользователь видит ГДЕ сущность сейчас и двигает её относительно.

**Симптом, что принцип нарушен:** пользователь повторно открывает редактирование и видит **тот же** 3-кнопочный селектор что был при создании. Спрашивает «а как мне переместить — снова перевыбрать?». Воспринимает как «фичу нельзя изменить». Или ещё хуже: формулирует имя сам — *«сделать переключение стрелочкой вверх/вниз»* — это сильный сигнал что mental model пользователя уже сформировалась, и UI ей не соответствует.

**Реализация:**
- При mount компонента редактирования: проверить — сущность existing? Если да → render arrow UI. Если new → render selector UI.
- Стрелки disabled на границах (нельзя двинуть выше первой entry / ниже последней).
- Если соседняя позиция занята другой сущностью (UNIQUE constraint в БД) → стрелка скипает и ищет дальше **в направлении движения**, не молча затирает соседа.

**Отброшенный подход:** просто оставить 3-кнопочный селектор для обоих случаев и «надеяться что юзер поймёт». Не работает — пользователь возмутился прямо в живой сессии («блять, нет маркера»), это нарушение читаемости/доверия, не вкусовщина.

В custom-terminal: см. `knowledge/fact-timeline.md::Notes UI: создание ≠ редактирование` (для Timeline notes: 3-button before/dot/after при создании, ↑/↓ стрелки при редактировании сохранённой before/after-заметки; перепривязка к соседней user-entry с флипом position и скипом занятых соседей из-за SQLite UNIQUE).

## Path-prefix tolerance для cwd-сравнений

**Принцип:** когда какой-то guard сравнивает «текущий cwd» с «зафиксированным cwd» для решения «свой/чужой контекст», строгое `===` ломается при первой же навигации `cd` внутри шелла. Если один путь — префикс другого по файлсистеме (родитель или потомок), это естественное движение внутри той же ветки — не «чужой проект». Сравнивать нужно по relation, не по равенству.

**Симптом, что принцип нарушен:** автоматика начинает игнорировать сигналы от подпроцесса после того как юзер сделал `cd ..` или `cd subdir` в шелле перед запуском CLI. Внешне выглядит как «висящий лоадер», «ожидание сессии», «пропавшие данные» — внутри всё корректно работает, но guard режектит сигнал из-за mismatch.

**Реализация:**
```js
const a = childCwd.endsWith('/') ? childCwd : childCwd + '/';
const b = anchorCwd.endsWith('/') ? anchorCwd : anchorCwd + '/';
const isRelated = a.startsWith(b) || b.startsWith(a);
if (!isRelated) {
  // truly foreign — reject
  return;
}
// Related path → accept AND update anchor to the new cwd so future events pass cleanly
anchorMap.set(id, childCwd);
```
Ключевая деталь: добавление `'/'` в конец перед сравнением. Без него `/Users/fedor/Deskto` некорректно сматчится с `/Users/fedor/Desktop` как «префикс».

**Что НЕ ломается этой логикой:** настоящий «чужой проект» (`/A/proj1` vs `/A/proj2`) ни один не префикс другого → reject продолжит работать. Сценарий с symlink'ами не покрыт — если важно, ресолвить через `fs.realpath` перед сравнением.

**Антипаттерн (что было до фикса):**
```js
if (childCwd !== anchorCwd) return;  // ломается на cd ..
```

В custom-terminal: см. `knowledge/fact-session-capture.md::CwdGuard ловушка` (Bridge:CwdGuard скипал bridge-файл при `cd ..` в шелле → InfoPanel застрял в «Ожидание сессии», sessionId не записывался хотя бэк уже знал uid).

## Ink TUI: пробелы как ANSI-команды, текст разорван по чанкам

**Принцип:** при парсинге вывода Ink-based TUI (Claude Code, Gemini CLI, Yargs-prompts) **не используй match из двух+ подстрок в пределах одного PTY chunk** и **не полагайся на литеральные пробелы**. Ink оптимизирует ререндер через ANSI cursor-positioning — между видимыми словами вместо пробелов могут стоять `\x1b[NC` (cursor-forward N cols). И многострочные блоки приходят в 3-5 отдельных PTY writes.

**Симптом, что принцип нарушен:** автоматика парсит TUI-диалоги/меню по фразе вроде `'Yes, switch'`, и работает то стабильно, то с дырами — потому что то слова чанком склеились, то ANSI-кодом разъехались. Тесты на одном дампе проходят, в production падает.

**Реализация:**
- Матчь на **минимальной уникальной подстроке** (одно слово, короткая фраза заголовка), которая надёжно влезает в один chunk. Уникальность важнее длины.
- `stripVTControlCharacters(data)` обязателен — но он удаляет ANSI коды, **не вставляя на их место пробелы**. Поэтому в стрипнутой строке `Yes,switchtolow` слова склеены без разделителей. Не используй регексы типа `/Yes,\s+switch/` — пробелов нет.
- Для многосегментных совпадений (типа «детектировать заголовок + опцию») собирай скользящее окно из последних N байт PTY-вывода и матчись по нему, а не по текущему чанку.

**Antipattern:**
```js
const sc = stripVTControlCharacters(data);
if (sc.includes('Change effort level') && sc.includes('Yes, switch')) { ... }
//   ↑ срабатывает раз из 10 — оба matches должны попасть в один data chunk,
//     а «Yes, switch» после strip становится «Yes,switch»
```

**Правильно:**
```js
const sc = stripVTControlCharacters(data);
if (sc.includes('Change effort level')) { ... }   // одна уникальная подстрока, надёжный chunk
```

**Задержка между detection и автоматическим действием:** Ink дорисовывает меню в 3-5 чанках, между ними десятки миллисекунд. После первого matching chunk дай ему 100-150мс чтобы дорисовать остальные ДО того как пошлёшь подтверждение (`\r`, `Esc`). Без задержки Enter иногда попадает в неопределённое состояние — то «закрывает» неполностью отрендеренный prompt, то теряется. Cooldown 1-2с обязательно — Ink делает re-render и твой match может сработать ещё раз.

В custom-terminal: см. `knowledge/fact-claude-tui-control.md::Auto-confirm «Change effort level?» dialog` (один минимальный match `'Change effort level'`, 120мс задержка перед `\r`, cooldown 2с).

## Категориальные toggle — имена сущностей, не абстракции

**Принцип:** когда UI-категория покрывает >2 разных сущности (имена tools, типы файлов, варианты бэкендов, методов оплаты), лейбл toggle должен быть **списком реальных имён**, а не обобщающим словом. Особенно когда обобщающие слова из разных категорий звучат похоже («Bash» / «Tools», «Network» / «Sync», «Storage» / «Cache») и пользователь не может с первого взгляда разделить их по смыслу.

**Симптом, что принцип нарушен:** пользователь видит две кнопки рядом и говорит *«в чём отличие? непонятно и не интуитивно»* / *«с первого взгляда не понимаю»*. Каждая категория обозначена одним абстрактным словом, и mental model пользователя не строится — он не знает что именно попадёт под фильтр.

**Реализация:**
- Покажи 2-3 канонических имени сущности из категории в monospace, разделённых `·`. Например: `Bash · Monitor` + хинт `shell`; `mcp__* · Web · Agent` + хинт `MCP и прочее`. Хинт — короткое прилагательное-категория, не пересказ списка.
- Имена берутся из **реального источника правды** — у нас это JSONL-tool_use.name. Не «Команды» (русское обобщение), а `Bash` — то имя, которое пользователь увидит в логах если откроет файл.
- Если в категории 5+ имён — покажи 2-3 самых частых + `*` или wildcard (`mcp__*`).
- Лейбл top-level toggle всё ещё может быть обобщающим («🤖 Claude») — там нет конкуренции категорий.

**Антипаттерн:**
```
[ ] Bash
[ ] Tools     ← в чём разница? Bash — это что? Tools — это что? И там и там команды?
```

**Правильно:**
```
[ ] Bash · Monitor               [shell]
[ ] mcp__* · Web · Agent         [MCP и прочее]
```

**Связанный принцип — wildcard для расширяющейся категории.** Если категория автоматически вбирает новые сущности (новые MCP-серверы, новые внешние API), используй wildcard в лейбле (`mcp__*`). Пользователь понимает что toggle вырастет вместе с экосистемой, не нужно ждать UI-апдейта.

В custom-terminal: см. `knowledge/fact-clipboard-tools.md::Hierarchical Copy Groups` (Bash vs Tools — child-rows показывают `Read · Grep · Glob`, `Edit · Write`, `Bash · Monitor`, `mcp__* · Web · Agent` вместо общих `Reading/Editing/Bash/Tools`).

## Master toggle + incremental children

**Принцип:** когда UI-группа состоит из главного toggle и нескольких children, между ними должна быть **детерминированная двусторонняя связь**, а не «N независимых тогглов с интуицией»:
- **Parent → Children (cascade):** parent OFF выключает все children (UI-disabled, значение в store сохраняется). Parent ON восстанавливает прежний выбор children, не сбрасывает в дефолт.
- **Child → Parent (lift):** если хотя бы один child ON, parent ON автоматически. Parent — синтезированный флаг `active = anyChild`, не отдельная переменная.
- **Children ↔ Children (incremental):** в incremental-семье более «полный» вариант форсирует более «базовый», более «базовый OFF» — форсирует «полный» OFF. Пример: «Финальный результат» / «Вся история» — история без результата теряет анкер, поэтому `history ON ⇒ result ON`, `result OFF ⇒ history OFF`.

**Симптом, что принцип нарушен:** пользователь формулирует имя паттерна сам, чтобы объяснить чего хочет: *«они как бы синхрон... инкрементируемые, то есть если я включаю последнее, у меня выключается вся история, и наоборот»*. Это признак того, что в UI нет автоматической логики каскада — пользователь видит N независимых тогглов и в голове строит правила сам, которые UI не реализует. Если он смог их сформулировать — значит они уже у него в mental model, нужно лишь зафиксировать в коде.

**Реализация:**
- Master-toggle клик: если что-то из children было ON → выключает всех. Если все были OFF → включает один (минимально полезный — обычно первый child).
- Store-логика инкремента в setter, не в UI: `setIncludeHistory(v)` внутри ставит `result = v ? true : prev.result`. Это гарантирует что любой callsite (горячая клавиша, импорт настроек, миграция) получит правильное состояние.
- Children disabled при parent OFF — но **значение** в store не трогаем. Возврат parent ON показывает прежний выбор, а не дефолт. Это уважение к работе пользователя: он настраивал children, временно выключил группу — настройки не должны исчезать.

**Антипаттерн:** N независимых toggle, документация в tooltip («чтобы включить историю, сначала включите результат»). Никто не читает tooltip, юзер просто видит что включил history — а результата нет. Доверие потеряно.

В custom-terminal: см. `knowledge/fact-clipboard-tools.md::Hierarchical Copy Groups::Master-toggle + incremental cascade` (User/Claude/Subagent master тогглы; Subagent.Result ↔ History incremental; setter-уровневая cascade-логика).

## Diagnose with instrumentation, not guesses

**Принцип:** при дебаге трудно-наблюдаемого бага (визуальное дрожание, race condition, frame timing, scroll-fight между двумя источниками) **сначала добавь логирование с timestamp и фактическими значениями переменных, потом смотри что происходит**. Не пытайся починить сходу. Гадание стоит итераций — каждая «фикс на ощупь» имеет ~30% шанс попасть, а юзеру через сборку и репро баг занимает 5-10 минут. Один лог-снапшот может показать что вся гипотеза неверна.

**Симптом, что принцип нарушен:** агент предлагает 3-4 разных фикса подряд (*«попробуй tolerance=2»*, *«нет, давай cursor-based»*, *«окей, тогда уберём guard»*), каждый раз делая билд, отправляя юзеру на проверку, получая «не работает» — без единого реального лога о том что происходит. Юзер в какой-то момент прямо требует *«можешь логи глянуть?»* — это сигнал что цикл «гипотеза → фикс → надежда» зашёл слишком далеко.

**Реализация:**
- Логи должны содержать **числа, не пересказ**: `[Diag] scrollToLine(1788) DOM.scrollTop 26796→26935 savedLine=1788 baseY=1789 cursorY=39 rows=44`. Из такой строки за 5 секунд видно: cursor на 39 при rows=44, гипотеза «cursor на rows-1» неверна.
- Логировать **источник и направление действия**: что снапит viewport, в какую сторону, по чьей инициативе. `[WHEEL] deltaY=-50` vs `[SNAP] scrollToLine(N)` — разные события, разные виновники.
- Включай минимум **3 числа**: `before`, `after`, `expected`. Только `after` ничего не показывает.
- Не бойся объёма — 60 одинаковых строк подряд это **сильный** сигнал (стабильный osc/dead-lock), не шум.

**Когда применять:**
- Любой visual jitter / frame-level race
- «Кнопка не работает иногда» (выясни сначала когда работает, потом когда не работает)
- Frame-timing бага: 16ms окна, sub-pixel округления, sync-frames
- Любой баг где у тебя есть гипотеза но нет данных подтверждающих её

В custom-terminal: см. `knowledge/fix-terminal-jitter.md::Cursor-based bottom detection::DIAG-инструментация` — добавление `[ScrollDiag:WHEEL]` и `[ScrollDiag:SNAP]` сразу показало `cursorY=39 rows=44` и сэкономило часы гадания про tolerance.

## Reproduce by the real user path, not synthetic equivalent

**Принцип:** когда «фикс работает» проверяется через программный test-path — убедись что этот path **реально проходит через тот же код** что и user action. Synthetic events часто минуют callback'и которые юзер триггерит вживую. Утверждение «работает» по synthetic-тесту = ложноположительный результат, и юзер найдёт это первым.

**Симптом, что принцип нарушен:** агент пишет фикс на `term.onData((data) => { ... })`, тестирует через `ipcRenderer.send('terminal:input', tabId, data)` — у обоих *одинаковое namespace `terminal:input`*, поэтому кажется что тест валиден. На самом деле IPC отправляет байты **напрямую в PTY**, минуя `term.onData` callback. Тест проходит (фикс «работает»), юзер пробует — баг на месте, потому что у него keystroke идёт через xterm `onData`.

**Реализация:**
- До утверждения «фикс работает» — найди в коде **где именно triggerится твоя логика** (callback, event-listener, hook). Тест должен пройти через эту точку, не «параллельно через тот же API».
- Real user path: trusted browser events (`InputEvent` на `.xterm-helper-textarea`, `WheelEvent` на viewport, `KeyboardEvent` с правильным keyCode), не CDP-инжекция или прямой IPC.
- В тестовом сообщении явно укажи **через что идёт ввод**: «через keyboard event» vs «через IPC». Это позволит юзеру сразу понять валиден ли тест в его сценарии.
- Если real-path repro невозможен (например требует физического tap на trackpad) — явно скажи это и попроси юзера проверить.

**Когда применять:**
- Любая фича где есть callback-цепочка xterm/Codemirror/Monaco — `onData`, `onScroll`, `onKey`, `onPaste`
- React-фичи где есть `onChange` vs прямое мутирование state
- Drag-and-drop где synthetic `dispatchEvent('dragstart')` часто не вызывает trusted-listener'ов в `@atlaskit/pragmatic-drag-and-drop`
- Любой клавиатурный shortcut с modifiers (Cmd/Ctrl): synthetic KeyboardEvent часто не пропагирует metaKey

В custom-terminal: см. `knowledge/fix-terminal-jitter.md::Cursor-based bottom detection::Подвох в тесте через MCP` (фикс `onData → ref clear` проверял через `terminal:input` IPC — не сработал бы; правильный test через `InputEvent` на textarea подтвердил работу).

## Click-outside как universal escape, mouse-leave опционален

**Принцип:** для любого dismissable popup'а (context menu, action menu, tooltip, confirm dialog) должен существовать **хотя бы один escape-жест, работающий в КАЖДОМ внутреннем режиме** popup'а. Mouse-leave можно отключать в чувствительных режимах (confirm для destructive-action, postPrompt с введёнными данными), но click-outside должен оставаться универсальным — это последний рубеж.

**Симптом, что принцип нарушен:** пользователь описывает жест словами — *«я нажимаю "Удалить историю", потом клик на оверлее не срабатывает»*, *«никак не закрыть это окно кроме как нажать Cancel внутри»*. Юзер оказывается заперт в popup'е: единственный путь — конкретная кнопка внутри (Cancel/Close), которая может быть вне области внимания или конфликтовать с моторной памятью «клик в сторону = отмена».

**Реализация:**
- Один global `mousedown`/`click` listener на window, проверка `e.target` через ref-containment ИЛИ через `e.stopPropagation()` на корневом div popup'а (короче, надёжнее, не зависит от структуры внутренних элементов).
- В global handler — **безусловное** закрытие popup'а в любом режиме. Не `if (!confirmMode && !postPromptMode)` — этот гейтинг и есть ловушка.
- Если popup имеет внутренние режимы (confirm/loading/постпромпт) — при закрытии **сбросить их в дефолт**, чтобы при следующем открытии popup был чист.
- Mouse-leave dismiss остаётся отдельной фичей для «легкомысленного» режима popup'а. Когда юзер перешёл в чувствительный режим (нажал «Delete») — выключай mouseLeave (защита от случайного hover-выхода), но **никогда** не выключай click-outside одновременно.

**Антипаттерн (запертый popup):**
```js
const handleClickOutside = (e) => {
  if (!isInDangerousMode) {    // ← убрать это
    closePopup();
  }
};
```
Если `isInDangerousMode` совпал с выключенным `onMouseLeave` — у юзера нет вообще выхода кроме как кликнуть на конкретную кнопку внутри popup'а.

**Связь с `e.stopPropagation()` vs ref-containment:** для предотвращения «протекания» внутренних кликов в global handler есть два пути:
- **`e.stopPropagation()` на корневом div popup'а** — все клики внутри popup останавливаются на корне, не доходят до window. Один listener, простая реализация. Может ломать что-то наверху по дереву, но для self-contained popup в Portal это безопасно.
- **`ref.current.contains(e.target)`** в global handler — проверка что клик был внутри popup. Не требует stopPropagation, но требует ref на DOM-узел popup и проверки в каждом global handler'е.

В portal-popups предпочитай `e.stopPropagation()` — Portal по умолчанию рендерит popup вне иерархии Timeline, никакая внешняя логика не должна перехватывать клики внутри него.

В custom-terminal: см. `knowledge/fact-timeline.md::Range Copy & Edit Range::Inline confirm` (rangeActionMenu всегда закрывается на click-outside, включая confirm/postPrompt режимы; mouseLeave отключён только в чувствительных режимах; `e.stopPropagation()` на корне popup защищает внутренние клики).

## Геометрия popup — от измерения, не от формулы

**Принцип:** popup, anchored к динамическому контейнеру (sidebar, sliding panel, conditional column) — позиционируй через `getBoundingClientRect()` контейнера, **не** через формулу из «известных» ширин соседей. Формула неизбежно расходится с реальностью при условном рендеринге, drag-resize, theme/density changes, mode toggles, и других случаях когда твоя модель layout'а ≠ реальность.

**Симптом, что принцип нарушен:** popup появляется не там, где ожидается. Особенно «прыжки» при определённых сочетаниях UI-состояний — открыт ли соседний sidebar, развёрнут ли tree-mode, какая ширина окна, какая ширина resize'нутой колонки. Пользователь говорит *«странно, popup появляется в центре экрана»*, *«всё равно нарушение в пикселях»* — и это нарушение проявляется только в части сценариев, что означает формула делает скрытое допущение.

**Антипаттерн (формула из «известных» ширин):**
```js
right: `${sidebarWidth + panelWidth - 8}px`
```
Это работает только если sidebar и panel **всегда** рендерятся. Если хотя бы один из них условный (`isOpen ? <Panel /> : null`), формула безусловно вычитает их ширину даже когда они не на экране → popup сдвигается в пустоту.

**Правильно (измерение + ResizeObserver):**
```js
const [popupRight, setPopupRight] = useState(0);
useEffect(() => {
  const el = anchorRef.current;
  if (!el) return;
  const measure = () => {
    const rect = el.getBoundingClientRect();
    setPopupRight(window.innerWidth - rect.left + GAP);
  };
  measure();
  const ro = new ResizeObserver(measure);
  ro.observe(el);
  ro.observe(document.body);   // ← КЛЮЧЕВОЕ
  window.addEventListener('resize', measure);
  return () => { ro.disconnect(); window.removeEventListener('resize', measure); };
}, [/* deps на флаги, которые могут влиять на layout */]);
```

**Ключевая ловушка:** `ResizeObserver` на якорный элемент **не** срабатывает в сценарии «соседняя панель схлопнулась, мой размер не изменился, но мой `left` сдвинулся». Лекарство — наблюдать ещё и за `document.body`: любое изменение flow-layout вызовет resize body, что переизмерит позицию. Не идеально (избыточные обновления при scroll'е), но дешевле чем подписываться на конкретные эвенты каждого соседа.

**Когда формула приемлема:** только если **все** компоненты в формуле — постоянно отрисованные fixed-width элементы без условного рендеринга и без resize. Это редкий случай. В сомнении — измеряй.

В custom-terminal: см. `knowledge/fact-timeline.md::Z-index и геометрия popup` (6 popup'ов используют единый `popupRightPx` state из ResizeObserver на containerRef + document.body; кладбище формулы `notesPanelWidth + (treeMode ? 160 : 32) - 8`, которая безусловно вычитала notesPanelWidth даже при закрытой HistoryPanel).

## 1 prompt — 1 dot. Атрибуты вместо отдельных entries

**Принцип:** когда побочные действия (tool-calls, sub-events, дочерние операции) семантически принадлежат **одной** родительской сущности (user-prompt, commit, post), отображай их как **атрибуты родителя** (цвет, бейдж, inline-info в hover-state) — не как отдельные элементы в той же хронологической ленте. Каждый дополнительный элемент в timeline = шум, размывающий «вот где основное событие N».

**Симптом, что принцип нарушен:** длинные сессии становятся нечитаемыми. Из 50 точек в Timeline 30 — мусорные «промежуточные», 20 — настоящие user-prompts, и пользователь не может быстро найти «где я задал вопрос X». Пользователь формулирует словами: *«не должно быть отдельного элемента в таймлайне для этого, у нас должна быть модалка пользователя»* — он уже сформировал mental model, в которой эти события — часть user-prompt'а, не самостоятельные точки.

**Когда применять атрибутный подход:**
- Под-событие **не имеет смысла без родителя.** `docs_search` сам по себе бессмыслен — он часть «вопроса пользователя, в ответ на который Claude искал в docs». Без user-prompt'а он = строка лога.
- Под-событие **происходит только в ответ** на родителя, не независимо. CI-run на commit, react-emoji на post, retry на failed-request.
- **Точечный шум при множестве:** одно `docs_search` в день — может быть отдельной точкой. 30 docs_search'ей в день в течение часа — обязательно атрибуты.

**Реализация (бэкенд → фронт):**
- Бэкенд при формировании timeline: после каждого parent-entry — look-ahead до следующего parent, собирает child-events в массив `parent.childEvents[]`. Не эмитит child как отдельную entry.
- Фронт: parent-точка меняет цвет/получает бейдж если `childEvents.length > 0`. В hover-state — inline-блок над основным контентом с иконкой/счётчиком/списком.
- **Edge case:** если несколько типов child-events (docsEdit + docsSearch), нужен **precedence rule** — какой цвет побеждает. Семантика: «более сильное действие» перекрывает «более слабое» (Edit > Search, Push > Pull, Delete > Update).

**Антипаттерн (отдельные entry для каждого child):**
```
[user prompt]
[docs_search]      ← мусор
[docs_search]      ← мусор
[docs_edit]        ← мусор
[user prompt]
[docs_edit]        ← мусор
[user prompt]
```
Каждая лишняя точка крадёт внимание у настоящих user-prompts. Пользователь, глянув на timeline, видит «активность» вместо «структуры диалога».

**Правильно (атрибутный):**
```
[user prompt: green dot, hover→"Edited 2 files; Searched 3 queries"]
[user prompt: white dot]
[user prompt: lime dot,  hover→"Searched 1 query"]
```

В custom-terminal: см. `knowledge/fact-timeline.md::Docs-индикаторы как атрибут user-entry` (раньше docs_edit / docs_search были отдельными dot-entries → длинные docs-update сессии теряли структуру; теперь backend look-ahead собирает их в `entry.docsEdited[]` / `entry.docsSearchQueries[]`, цвет user-точки меняется, inline-блок в self-tooltip показывает детали).

## Inline icon-buttons в title row — не отдельная строка

LLM-предложенный дефолт для панелей: первая строка — заголовок, вторая — главная кнопка действия на всю ширину. Это правильно для **широких** кнопок («Save changes», «Run analysis») с явным лейблом — занимает место заслуженно, считывается с расстояния.

Но для **узких** action-кнопок (иконка/точка/один глиф ≤ 24px) отдельная строка — пустая трата вертикали. На компактных оверлеях (sidebar widgets, sticky panels справа от терминала) каждая строка дорогая — отдельная Run-кнопка на 32px высотой в overlay шириной 240px съедает 8% полезной площади ради одной точки-индикатора.

**Правило:**
- Кнопка с текстовым лейблом ≥ 24px ширины → отдельная row, full-width
- Кнопка-иконка / точка / один глиф → инлайн в title row слева от заголовка
- Title row становится визуальным action-trigger + status одновременно (точка пульсирует, заголовок справа — контекст)

**Пример (Prompt Queue overlay, `PromptQueueOverlay.tsx`):**
```
Было:                           Стало:
┌─────────────┐                 ┌─────────────┐
│ Queue (3)   │                 │ ● Очередь·3 │  ← точка слева от заголовка,
├─────────────┤                 ├─────────────┤    клик по ней = arm/disarm,
│ ▶ Run queue │   ← отдельная   │ chip 1      │    пульсирует фиолетом когда
├─────────────┤      строка     │ chip 2      │    очередь активна
│ chip 1      │                 └─────────────┘
└─────────────┘
```

**Inverse signal:** если иконка-кнопка делает что-то критичное и необратимое (Delete project, Force-kill) — наоборот вынеси на full-width row с явным лейблом, потому что click affordance ≠ destructive affordance. Inline-точка ок только для toggle-state с понятной семантикой текущего состояния.

**Расширение — compact toggle groups в title row.** Тот же принцип применим к маленьким toggle-группам (2-4 pill'а высотой ≤ 20px). Если они "выбор первичной сущности" по семантике (Provider, Category, Domain), их можно ставить **в шапку справа от заголовка**, не выделять отдельной row с лейблом `Provider:`. Title row слева → handle названия раздела. Pills справа → handle выбора в этом разделе.

Пример (`InfoPanel.tsx` PROVIDER header):
```
Было:                                Стало:
┌────────────────────┐               ┌────────────────────────────┐
│ КОНТРОЛЬ           │               │ PROVIDER  [⌬Claude] [◇DS]…│
├────────────────────┤               ├────────────────────────────┤
│ Provider: [...] │ ← отдельная row  │ Model: ...                 │
│ Model: ...      │   занимает 23px  │ Effort: ...                │
│ Effort: ...     │                  └────────────────────────────┘
└────────────────────┘
```

Critical: pills должны быть **визуально меньше** чем Model/Effort pills в строках ниже (h=18 vs h=23). Иначе шапка перевешивает контент и читается как primary action row. Subscript-уровень иерархии: заголовок > content rows > header-inline toggles.

## Slideout-якорь к chip'у, не центр экрана

Modal-формы для редактирования элемента списка LLM по дефолту рендерит как centered modal с scrim. Это правильно для **самостоятельных диалогов** (settings, confirm, primary task). Но если редактирование — расширение конкретной строки в списке, центральная модалка **рвёт визуальную связь**: пользователь не понимает, что он редактирует именно эту строку.

**Правильный паттерн для list-row editing:**
- Slideout «прижат» к ряду — top-edge редактора выровнен с top-edge редактируемой строки
- Right-edge редактора выровнен с left-edge панели списка (если панель справа) или наоборот
- Никакого scrim (затемнения) — list позади остаётся видимым, чтобы пользователь видел контекст соседних рядов
- Закрытие по Esc / клику-вне / × — НЕ по клику на список (это break-flow)

**Mirror Editing** (см. секцию выше) — это частный случай: список из 2 колонок, редактор заменяет правую колонку. **Slideout-anchor** — обобщение для single-column lists, где правая граница списка фиксирована (overlay, sidebar).

В custom-terminal: `PromptQueueOverlay.tsx::editorAnchor` хранит `{ top, right }` — top это `chipRef.getBoundingClientRect().top` редактируемого чипа (или panel.top для «новый промпт»), right это `window.innerWidth - panel.left + gap`. Slideout позиционируется `position: fixed; top; right;` — auto-syncs при scroll'е панели потому что viewport-relative.

## Click-toggle-off на single-select pill

Single-select группа кнопок (filter pills, tag selectors, effort level, model picker) — повторный клик на **уже-активную** опцию должен сбрасывать выбор в neutral/auto/off state. Без этого юзер вынужден сначала выбрать другую опцию, потом дернуться к мыши и снять, или открывать context-menu — три действия вместо одного.

**Симптом нарушения:** юзер выбрал `effort: max`, передумал, хочет вернуть default. Клик на `max` ничего не делает (уже active). Клик на `low` → потом клик на `low` ещё раз → нет → теряется. Юзер ищет "deselect" кнопку которой не существует.

**Реализация — один тернарник:**
```ts
const targetLevel = isActive ? defaultValue : level;
onClick(() => setSelection(targetLevel));
```

`defaultValue` зависит от семантики: для effort это `auto` (нейтральный), для DeepSeek effort это `off` (явное отключение thinking), для tag filter это `null` (no filter). Tooltip на active кнопке должен подсказывать: `Click again to deselect (→ auto)`.

**Когда не применимо:** если group **обязательно** должна иметь активную опцию (radio-required), и нет `null/auto` state — например выбор языка приложения. Тогда повторный клик = no-op. Но 90% UI кейсов имеют neutral fallback.

В custom-terminal: `InfoPanel.tsx::effort buttons` — повторный клик возвращает `auto`. Эта же логика применима к Model row, Provider row, и любым будущим pill-группам.

## Toast preview = что именно затронуто

Для destructive/programmatic actions где юзер не видит финальный результат напрямую (copy в clipboard, перенос в очередь, отправка в API, авто-clear input) — toast должен показать **превью** того что именно затронуто, первые 15-30 символов + `…`. Не "Copied", не "Done" — `Copied: "Refactor the user…"` или `Queued: "Read all files…"`.

**Зачем:** юзер не видел финальную нормализованную форму. Claude collapse'ит paste в `[Pasted text #N +M lines]`, clipboard пишет invisible bytes, API получает trimmed строку. Toast = checkpoint **"вот что реально ушло"**. Если ушло не то — юзер ловит ошибку через 1-2 секунды и может откатить.

**Формат:**
- Multi-line → single-line через `text.replace(/\s+/g, ' ')` (иначе toast разрывает layout)
- Truncate с ellipsis: `len > 20 ? text.slice(0, 20) + '…' : text` (20 это компромисс между видимостью и не-шумом)
- Если действие имеет дополнительные effects — упомянуть в верхе: `Copied + cleared: "..."`, `Queued: "..." · 3 📎` (3 image attachments не унесены)

**Антипаттерн:** toast без превью (`Copied to clipboard`) для programmatic copy. Юзер не понимает что именно скопировалось — клавиатурный paste в другое окно может показать совсем не то что ожидалось.

В custom-terminal: `PromptQueueOverlay.tsx::grabCurrent`, `InfoPanel.tsx::Copy prompt` — оба показывают `verb: "first 20 chars…"`. Применимо к любым clipboard buttons, API-result toasts, queue-add operations.

## Secondary action: нейтральная палитра, не конкурирует с primary tint

Когда в одном container'е есть две action-кнопки — primary (главное действие, может быть destructive) и secondary (вспомогательное действие на тот же контекст) — secondary должен иметь **нейтральную палитру** (белый/серый), не accent-цвет primary.

**Симптом нарушения:** в InfoPanel рядом с Copy Session (оранжевый Claude-accent) появилась Copy Prompt тоже в оранжевом — две оранжевые кнопки одинаковой яркости. Глаз не понимает что primary, что вторичное. Юзер: *"мне оранжевый цвет не нравится, нужна какая-то более в белую сторону"*.

**Палитра для secondary:**
- Border `rgba(255,255,255,0.12)` — едва видимая обводка
- Background `rgba(255,255,255,0.03)` — почти прозрачный тёмный
- Color `#bbb` (светло-серый текст)
- Hover: background `rgba(255,255,255,0.06)` + `color: #fff` — контраст растёт при наведении

Primary остаётся в проектном accent-color (Claude orange `#DA7756`, Gemini blue `#4E86F8`). Secondary визуально **рецессирует** в фон, всплывает только при hover.

**Когда оба должны быть в accent:** если действия в группе **равнозначные** (две кнопки одного destructive level — Stop Claude / Stop Gemini в multi-select). Тогда tint разный (orange vs blue), а не один **тоном** ниже. Это другой паттерн (см. `fact-tabs.md::Multi-select Stop с majority badge`).

**Тест:** прикрой ладонью один из buttons, посмотри на оставшийся. Это primary? Хорошо. Это secondary? Hover делает его яркость такой же как у primary в idle — если да, контраст между состояниями achieved, тест пройден.

## Single source of truth для third-party shipping values

Когда UI отображает список значений которые **shipping'аются** внешней системой (CLI versions, API enums, cloud regions, payment-provider scopes, model names от LLM-провайдеров) — этот список **обязан** жить в **одном** canonical-файле проекта, не в виде хардкод-литералов рассыпанных по компонентам.

**Симптом нарушения:** в мае 2026 Claude обновил effort-уровни — `auto` удалён, `xhigh` добавлен между `high` и `max`. В проекте список `['auto','low','medium','high','max']` встречался в 4 местах: useUIStore (type union + validation array), StatusBar (popup levels + labels), InfoPanel (effort pills массив), toggle-off target. Юзер прислал скриншот настоящего Claude TUI с новыми уровнями и попросил починить — пришлось искать grep'ом по всему renderer'у, четыре раза править в синхронизации. **Когда** ещё один уровень добавится через месяц — забудем хоть один файл, UI рассинхронизуется молча.

**Правило:** все списки third-party shipping values живут в `src/<scope>/constants/<provider>.ts`:
```ts
export const CLAUDE_EFFORT_LEVELS = ['low','medium','high','xhigh','max'] as const;
export type ClaudeEffortLevel = typeof CLAUDE_EFFORT_LEVELS[number];
export const CLAUDE_MODELS = ['default','sonnet','opus','haiku'] as const;
```
Все use sites импортируют отсюда. Type-derivation `typeof X[number]` гарантирует что type union в sync с runtime array без отдельного hand-maintained type. Toggle-off / default-fallback value тоже в этом файле как named export (`CLAUDE_EFFORT_TOGGLE_OFF`), не magic literal в onClick.

**Тест:** при следующем shipping-апдейте — должно быть ровно **один edit** в одном файле. Если требуются правки в >1 файлах = anti-pattern, ещё одна точка fan-out пропущена.

**Legacy migration на пересдачу значений:** при удалении value из списка (`auto` → нет) — нужна одноразовая миграция на load из persisted state: `if (saved === 'auto') saved = CLAUDE_EFFORT_TOGGLE_OFF` перед валидацией. Иначе у существующих юзеров value не пройдёт `includes()` гард и сбросится в дефолт молча — пугающий регресс ("настройка пропала").

В custom-terminal: `src/renderer/constants/claudeLevels.ts`. Конкретика — `fact-claude-tui-control.md::Шрамы формата данных`.

## Visible side effect > silent IPC для destructive actions

Когда действие пользователя триггерит **destructive side effect** (kill процесса, удаление файла, очистка clipboard, force-rebuild cache) — этот side effect должен быть **видимым** в основном потоке UI (терминал, лента активности, лог), не выполняться через тихий background IPC + toast.

**Симптом нарушения:** kill dev-ports изначально работал через `ipcRenderer.invoke('system:free-project-ports')` в main — `lsof | kill -9` шёл фоном, в терминал ничего не печаталось. Юзер запускает `npm run dev`, видит только `npm run dev` строчку — не понимает что что-то убилось. Жалоба: *"если она вводится как-то фоном, то в таком случае должно быть уведомление типа «остановлены какие-то порты». Или проще же прям в терминале вводить, или там проблема с таймингами или что"*.

**Решение — инжектить shell-команду в видимый поток:**
```
lsof -ti:5181,3000 2>/dev/null | xargs -r kill -9 2>/dev/null; npm run dev
```
Юзер видит **строку целиком** как будто сам её ввёл, scrollback хранит record, `;` гарантирует ordering (kill завершится **до** npm), history позволяет re-up arrow. Никакого toast не нужно — терминал сам показывает что произошло.

**Почему toast не альтернатива:** toast эфемерный (исчезает за 1.5-3s), не накапливается, не searchable. *"Killed port 5181"* поверх npm-вывода = пользователю надо переключать внимание между двумя источниками правды. Shell-line = одна линия временной правды.

**Когда silent IPC + toast допустим:** действие **non-destructive**, side effect внутренний (state mutation, save to disk, push to queue). *"Copied to clipboard"* — toast OK, потому что clipboard это invisible-by-design системный buffer; юзер сам paste'нет когда захочет проверить. *"Killed 3 processes"* — toast НЕ OK, потому что юзер хочет видеть **кого** убил и в каком порядке.

**Принцип короче:** если действие меняет state ВНЕ нашего приложения (kernel, filesystem, network, child processes) — делай это видимо в shell/log/activity-feed. Если внутри (UI state, in-memory cache) — toast/spinner достаточно.

В custom-terminal: `fact-statusbar-toggles.md::kill dev-ports` — visible shell-line вместо background IPC.

## Brand identity = icon + color, не текст

Когда в UI есть выбор между brand'ами третьих лиц (LLM-провайдеры, cloud-вендоры, payment-методы, package managers) — каждый brand должен идентифицироваться **glyph-иконкой + brand-color**, текстовый label вторичен.

**Симптом нарушения:** Provider toggle в InfoPanel первой версии был `[Claude][DeepSeek][Zen]` — три identical-стилизованные кнопки, все в одном generic-blue accent (`#6B8AFF`) когда active. Юзер: *"тут в принципе и так понятно, что речь идёт про выбор нейронки. Вот, ну и там цвет изменить, типа у них, по-моему, разная цветовая гамма, то есть у Claude это должна быть иконка Claude, вот, и так далее. Для остальных также скачай SVG иконку оригинальную, их цвет"*.

**Правило:**
- **SVG glyph** перед label (Claude sparkle, DeepSeek whale, Zen circles). Inline SVG для tintability через `fill={color}`, без icon-библиотек.
- **Brand color** для active state — официальные HEX из brand guidelines. Claude `#DA7756`, DeepSeek `#4D6BFE`, OpenAI `#000`, Anthropic варианты. Если у brand'а нет official mark (Zen без logo) — выбрать цвет максимально отличный от соседних в палитре проекта.
- **Inactive state** — neutral grey (`#888` text, `rgba(255,255,255,0.04)` bg, серая обводка). Brand-цвета только для active — иначе все три pill'а светятся, юзер не видит выбор.
- **Label** — короткий wordmark (`Claude`, не `Anthropic Claude Code via subscription`). Glyph + tint уже передают brand, label только подтверждает.

**Структура данных:** `PROVIDER_CATALOG: { id, label, tint, Icon, ... }[]` — единый каталог. Иконка как `React.FC` (не path string), цвет как HEX в самой структуре. Один файл = один edit чтобы поменять цвет brand'а или заменить glyph.

**Зачем переносимо:** в любом проекте где есть мульти-провайдерная фича (image-generation выбор между DALL-E/Midjourney/SD; payment Stripe/PayPal; LLM Anthropic/OpenAI/Google) — этот принцип сокращает cognitive load на 1 клик распознавания.

В custom-terminal: `src/renderer/components/icons/ProviderIcons.tsx` (DeepSeek, Zen) + `CopySessionButton.tsx::ClaudeSparkle` (старая локация). `PROVIDER_CATALOG` в `InfoPanel.tsx`.

## Geometric symmetry в spacing, не накопление margin/padding

Когда нужно ровное расстояние между двумя UI-блоками с **визуальным разделителем посередине** (line, dot, icon) — расстояние должно быть **математически разложимо** на симметричные половины, а **не** складывание margin от блока выше + padding внутри блока ниже + border-width разделителя.

**Симптом нарушения:** между секциями AI SESSION и PROVIDER в InfoPanel я поставил `mb-4` (16px) на верхний блок + `pt-3 border-t` (12px padding + 1px line) на нижний. Юзер вручную сложил отступы: *"сверху получается margin равен 12 пикселей. А потом ещё margin-bottom от второго компонента равен 16 пикселей. То есть у нас расстояние между ними должно быть 16 пикселей, в общем. То есть и получается, посередине, то есть на 8 пикселях должна отображаться разделительная полоса. То есть 16 пикселей — это общее расстояние, а у нас проблема в том, что к этому добавляется ещё padding"*.

Проблема: вертикальный gap = `16 + 12 + 1 = 29px`, line не посередине, math не работает. Каждое следующее изменение требует подсчёта трёх слагаемых.

**Правило — standalone divider, симметричные margins:**
```jsx
<div className="mb-2">...верхний блок...</div>
<hr className="border-0 border-t border-[#2a2a2a]" />
<div className="mt-2">...нижний блок...</div>
```
- Divider — own zero-height element с `border-t`, не часть нижнего блока
- Симметрия: `8px + 0 + 8px = 16px`, линия ровно посередине (после 8px от верхнего, до 8px над нижним)
- Изменение gap на N — меняем только две цифры (mb/mt), не три

**Тест:** при чтении JSX gap-math должен быть очевиден без открытия dev-tools. Если нужно посчитать `mb + pt + border` чтобы понять расстояние = плохо. `8 + 0 + 8` = очевидно.

**Когда divider должен быть частью блока:** если разделитель **семантически принадлежит** одному из блоков (например, нижняя граница карточки внутри `Card` компонента). Тогда `border-bottom` на верхнем блоке окей. Но если разделитель **между равными секциями** — standalone лучше.

В custom-terminal: `InfoPanel.tsx` AI SESSION / PROVIDER divider — `<hr/>` standalone, симметрия 8+0+8.
