## Per-tab tooling state

В multi-tab UI настройки «инструмента» (модель LLM, фильтр, окружение) не должны быть глобальной переменной. Каждый таб — отдельный контекст, и переключение настройки в активном табе не должно затрагивать фоновые. Иначе сценарий: пользователь в фоновом табе долго ждёт ответа от модели X, переключается, меняет модель на Y «на минуту», возвращается — и видит что ответ пришёл от Y вместо X. Доверие к фоновой работе сломано.

Реализация — `Map<tabId, state>` в main process плюс механизм идентификации «к какому табу относится текущий запрос». Идентификатор пробрасывается **в каждый запрос**, не хранится как «текущий активный». Способов три по убыванию надёжности: URL-префикс (`http://proxy/t/<tabId>/...`) работает всегда даже если внешний клиент не умеет custom headers; custom HTTP header (`X-App-Tab-Id`) — только если контролируешь клиент, сторонние CLI типа Claude Code свои headers шлют by design и кастомные туда не добавишь; отдельный port per tab даёт полную изоляцию, но N портов = N TCP-listener'ов и overhead растёт. В custom-terminal — вариант 1, см. `knowledge/fact-provider-proxy.md::Per-tab routing`.

## Truth from server response, not local UI flag

Когда UI должен показать «что **реально** произошло» (пост-фактум индикация — какая модель ответила, какой бэкенд обработал, какой регион выдал результат) — источник правды только ответ сервера, не локальный state UI. Иначе классическая рассинхронизация: пользователь переключил backend → UI обновился → ответ пришёл от старого backend (запрос ушёл до переключения) → UI показывает новый, а данные старые.

Каждое сообщение в истории помечается метаданными из server response (`message.model`, `provider`, `region`), и badge рендерится из этих метаданных, а не из текущего значения настройки. Live indicator «сейчас отправляется куда» может опираться на UI-state, но это другой индикатор, не путать с post-factum badge. То же на уровне архитектуры: API-клиенты пишут в лог/JSONL то что вернул сервер, не то что отправили — Stripe vs PayPal multi-mode payment запоминает «paid via Stripe» из response, не из локального селектора.

В custom-terminal bridge.sh показывает Claude TUI выбор модели, но реальный провайдер берётся из `message.model` JSONL → Timeline footer badge. См. `knowledge/fact-timeline.md::Provider badge` и `knowledge/fact-provider-proxy.md::Bridge врёт про active provider`.

## Two-tier hierarchical selectors

Когда выбор первичной сущности определяет доступные вторичные опции (категория→товары, страна→города, провайдер→модели) — UI разделяет это на два независимых ряда контролов, не сливает в один список. Иначе кнопочная строка смешивает разнородные опции (`[Claude][MM2.5][MM2.7][DSv4F][DSv4P]`); чтобы переключиться с MM2.7 на DSv4F пользователь читает все 5 опций, мысленно группирует по провайдеру, выбирает. Каждое добавление новой модели делает строку шумнее, шире, плюс лишает структуры.

Ряд 1 — primary (Provider, Category, Country), только базовые сущности. Ряд 2 — secondary (Model, Item, City), динамически перерисовывается под выбор в Ряду 1; при смене Ряда 1 восстанавливает **последний выбор для этой ветки** (per-provider memory) — возврат к Anthropic после Zen вспоминает последнюю Anthropic-модель, а не дефолт. Если конкретные настройки доступны только для одной первичной сущности (например, Effort только для thinking-моделей) — третий ряд: либо `disabled` для несовместимых, либо скрыт. Не смешивать с Рядом 2, иначе появляется «опция-сирота».

В custom-terminal: см. `knowledge/fact-claude-tui-control.md::Model row` и `knowledge/fact-provider-proxy.md::UI selector`.

## Воспринимаемая задержка UI-команд — асимметрична

Между кликом и видимой реакцией пользователь по-разному переносит одну и ту же физическую задержку в зависимости от того, есть ли промежуточный визуальный feedback. Если действие что-то стирает/перемещает/меняет на экране — 80-150ms задержки маскируются этим визуальным событием. Если экран не меняется — даже 80ms ощущаются как «зависание». Юзер сформулировал это сам: *«когда у меня уже что-то написано в инпуте — команда срабатывает мгновенно, а когда инпут пустой — почему-то лагает»*. Физически задержка одинаковая, но в первом случае Ctrl+S стирает текст (визуальный «удар»), во втором — no-op, экран замирает на ту же длительность, и мозг считывает это как баг.

Из этого следует: при проектировании цепочки `click → side-effect → settle → submit` минимизируй фиксированные паузы (drain'ы, debounce'ы) в первую очередь для случая когда side-effect невидим. Заменяй «безопасные» 80-150ms фиксированные паузы на event-driven ожидание (`waitForRender`, sync marker, status flag): когда есть что рендерить — настоящее событие приходит за 5-30ms, когда нечего — ожидание мгновенно возвращается. Не подбирай «средние» цифры (200ms «должно хватить») по worst-case — это всегда переплата для пустого случая, где worst-case = 0ms.

Связанная ловушка — «timeout как safety net вместо причины». Если ставишь 500-8000ms timeout «на всякий случай если событие не придёт», а потом измеряешь и видишь что реально событие приходит за 10-30ms — это не safety, это маска бага в твоей детекции события. Найди почему детекция иногда не срабатывает (stale-фильтр, race с подпиской, неправильный baseline) и почини её, не накручивай timeout. В custom-terminal: `knowledge/fact-claude-tui-control.md::Stash Flow` (cleanup паузы после Ctrl+S свели с 80+50+150ms до 20+50ms — для пустого инпута разница между «лагает» и «мгновенно») и `knowledge/fix-stale-sync-markers.md::markWriteTime` (детектили *наши же* маркеры как stale → timeout 500ms маскировал баг).

## Persistent state across UI transitions: error-branch must clear, not silent-return

Когда UI-state переживает переходы (tab-switch, route change, navigate-away) через persistence-механизм (Map, sessionStorage, in-memory cache), каждая ветка обработки результата — включая error и empty-response — обязана явно очищать сохранённый state. Иначе сценарий: долгий async (HTTP, IPC, queue worker), пользователь переключился, вернулся через минуту — UI всё ещё в розовой/синей анимации «загрузки», хотя операция давно завершилась с ошибкой. Перезапустить нельзя (нет UI-control в transitional-state), отменить нельзя (AbortController уже сработал). Зомби-state до перезапуска приложения или ручного обхода через другую кнопку, которая случайно сбрасывает state.

Каждая ветка `if (response.ok)`, `if (data)`, `if (compactText)` нуждается в парной очистке `else → savedMap.delete(key)`. Не молчаливый `return`. На каждой error-ветке — visible toast с HTTP-статусом/кодом ошибки: молчаливый clear так же опасен, пользователь видит «исчезновение лоадера» без объяснения, считает что «ничего не получилось» и не понимает что нужно повторить. Same-tab path обычно защищён (`setState(null)` в `catch`/`finally`), cross-tab/persistent — нет; аудит persistence-кода значит для каждого `savedMap.set(key, state)` найти ВСЕ места очистки и сверить с веткой записи. Веток записи > веток очистки → есть путь, оставляющий zombie-state. AbortController ненадёжен как единственная защита: HTTP-response может быть буферизирован и придёт после abort signal — sessionidref-guard / expected-key check после await обязательны, и они тоже ведут к очистке.

Минимальный код-сравнение, который этого избегает:
```js
if (data.success) {
  savedMap.set(key, { phase: 'ready', data });
} else {
  savedMap.delete(key);              // не молчаливый return
  showToast(`Error ${response.status}: ${data.error}`);
}
```

См. `knowledge/fact-timeline.md::Edit-Range Persistence on Tab Switch` (cross-tab 503 от Gemini не чистил saved map → бесконечный лоадер; шестой отброшенный подход после уже пяти других итераций по этому коду).

## Auto-focus на конечном поле, а не на промежуточном инпуте

Когда UI открывается с готовым намерением пользователя (он явно выбрал «ручной ввод», «редактировать вручную», «открыть пустой чат») — автофокус идёт на конечное поле, в которое пользователь собирался писать. Не на промежуточный текстовый инпут, особенно если этот инпут отправляет в нейронку/API/далёкий ресурс. Иначе классический промах: пользователь нажал «Открыть пустой чат» → панель открылась → курсор в textarea → пользователь по привычке (как в любом чате) написал текст и нажал Enter → отправилось в Gemini вместо замены готового ответа. То что искал — поле редактирования первого ответа — было видно рядом, но без фокуса. Двойная работа: ждать ответ Gemini, потом всё равно редактировать.

Реализация — `autoEditInitial: boolean` prop пробрасывается до компонента; компонент инициализирует `editingMsgId = '<initial-msg-id>'` сразу при mount + `setTimeout(focus, 50)`. Если flow стандартный (пользователь сам открыл UI без явного намерения «вручную») — фокус как обычно, на chat-input. См. `knowledge/fact-timeline.md::Прерывание и ручной ввод` (`autoEditInitial` для `EditRangePanel` — открывается с edit-режимом первого Gemini-ответа, чтобы юзер мгновенно вставил свой compact-текст).

## Edit affordance в каждой точке входа в просмотр

Если один и тот же контент видим в N разных UI-точках (тултип, popup, sidebar, inline-preview), кнопка «Редактировать» нужна в каждой из них — не только в одной «главной». Иначе пользователь видит контент в точке A, но edit-action только в точке B; когнитивная нагрузка «как это вообще редактируется?». Узнаётся по фразам типа «не редактируется, нет маркера для редактирования» — хотя UI редактирования существует, но за другим тултипом или в context menu. Контент-видимость и action-доступность рассинхронизированы.

Pencil/edit icon рядом с каждым preview, минимум 12px, hover-state, `e.stopPropagation()` если в Portal. Все pencil-кнопки ведут в один и тот же flow, не дублируют логику — handler один. Не помещать edit только в context menu (ПКМ): пользователи не всегда знают про ПКМ, особенно когда основной взаимодействие через hover/click. См. `knowledge/fact-timeline.md::Note-on-Dot Integration::Pencil-кнопка в self-tooltip` (раньше dot-заметка редактировалась только через ПКМ + «Редактировать заметку», хотя её контент виден в self-tooltip самой entry; добавили pencil рядом с inline-preview).

## Primary action на карточке = клик по самой карточке, не отдельная кнопка в hover-preview

Когда у списочной сущности (history item, recent project, archived chat) есть один доминирующий primary action — Restore, Open, Resume — этот action триггерится **кликом по самой карточке**, не отдельной кнопкой внутри hover-popover'а или preview-panel. Hover-preview по своей семантике = read-only расширенная информация (метаданные, превью контента, родительский контекст). Кнопка «Восстановить» / «Открыть» внутри preview дублирует жест и ломает mental model: юзер видит карточку, думает «кликну чтобы открыть» — уже правильно — но видит ещё одну кнопку внутри hover'а и колеблется (*«может, нужно кликнуть именно её?»*). Дословный фидбек из живой сессии после моей ошибочной попытки оставить такую кнопку: *«эту кнопку, кстати, убери»*.

Edit-affordance в preview оставляется (см. секцию выше) — это другое действие, не дубль primary. Если primary действительно неочевиден (карточка декоративная, без явного click-target) — primary action **на самой карточке** становится affordance'ом (`cursor: pointer`, hover-state, явный лейбл-tooltip) до того как добавлять кнопку в preview. Применимо в любом list-of-recents UI: tab history, recent projects, chat list, undo stack. В custom-terminal: см. `knowledge/fact-project-home.md::Hover Popover` (история таб, Restore через клик по карточке).

## Создать ≠ переместить: UI зависит от существования сущности

Один и тот же property (position, priority, parent-child) имеет два разных жеста управления в зависимости от того, существует ли сущность. Создание (сущности нет): селектор «куда поставить» — все опции сразу видны как кнопки/dropdown, пользователь выбирает initial location. Редактирование (сущность есть): инкрементальное движение — стрелки ↑/↓, drag-handle, «move up/down by 1». Пользователь видит ГДЕ сущность сейчас и двигает её относительно.

Узнаётся по тому, что пользователь повторно открывает редактирование и видит тот же 3-кнопочный селектор что был при создании, спрашивает «а как мне переместить — снова перевыбрать?», воспринимает как «фичу нельзя изменить». Иногда формулирует имя сам — *«сделать переключение стрелочкой вверх/вниз»* — сильный сигнал что mental model уже сформировалась, и UI ей не соответствует. При mount компонента редактирования: existing? → arrow UI; new? → selector UI. Стрелки disabled на границах. Если соседняя позиция занята другой сущностью (UNIQUE constraint в БД) — стрелка скипает и ищет дальше в направлении движения, не молча затирает соседа.

Отброшенный подход — просто оставить 3-кнопочный селектор для обоих случаев и «надеяться что юзер поймёт». Не работает: пользователь возмутился прямо в живой сессии («блять, нет маркера»), это нарушение читаемости/доверия, не вкусовщина. См. `knowledge/fact-timeline.md::Notes UI: создание ≠ редактирование` (для Timeline notes: 3-button before/dot/after при создании, ↑/↓ стрелки при редактировании сохранённой before/after-заметки; перепривязка к соседней user-entry с флипом position и скипом занятых соседей из-за SQLite UNIQUE).

## Path-prefix tolerance для cwd-сравнений

Когда какой-то guard сравнивает «текущий cwd» с «зафиксированным cwd» для решения «свой/чужой контекст», строгое `===` ломается при первой же навигации `cd` внутри шелла. Если один путь — префикс другого по файлсистеме (родитель или потомок), это естественное движение внутри той же ветки — не «чужой проект». Сравнивать нужно по relation, не по равенству. Симптом — автоматика начинает игнорировать сигналы от подпроцесса после того как юзер сделал `cd ..` или `cd subdir` в шелле перед запуском CLI. Внешне выглядит как «висящий лоадер», «ожидание сессии», «пропавшие данные»; внутри всё корректно работает, но guard режектит сигнал из-за mismatch.

```js
const a = childCwd.endsWith('/') ? childCwd : childCwd + '/';
const b = anchorCwd.endsWith('/') ? anchorCwd : anchorCwd + '/';
const isRelated = a.startsWith(b) || b.startsWith(a);
if (!isRelated) return;            // truly foreign — reject
anchorMap.set(id, childCwd);       // related → accept AND update anchor
```

Ключевая деталь — добавление `'/'` в конец перед сравнением, иначе `/Users/fedor/Deskto` некорректно сматчится с `/Users/fedor/Desktop` как «префикс». Настоящий «чужой проект» (`/A/proj1` vs `/A/proj2`) этой логикой не пропускается: ни один не префикс другого, reject продолжает работать. Сценарий с symlink'ами не покрыт — если важно, ресолвить через `fs.realpath` перед сравнением. См. `knowledge/fact-session-capture.md::CwdGuard ловушка` (Bridge:CwdGuard скипал bridge-файл при `cd ..` в шелле → InfoPanel застрял в «Ожидание сессии», sessionId не записывался хотя бэк уже знал uid).

## Ink TUI: пробелы как ANSI-команды, текст разорван по чанкам

При парсинге вывода Ink-based TUI (Claude Code, Gemini CLI, Yargs-prompts) нельзя матчить на двух+ подстроках в пределах одного PTY chunk и нельзя полагаться на литеральные пробелы. Ink оптимизирует ререндер через ANSI cursor-positioning — между видимыми словами вместо пробелов стоят `\x1b[NC` (cursor-forward N cols). А многострочные блоки приходят в 3-5 отдельных PTY writes. Узнаётся по тому что автоматика парсит TUI-диалоги по фразе вроде `'Yes, switch'` и работает то стабильно, то с дырами: то слова чанком склеились, то ANSI-кодом разъехались. Тесты на одном дампе проходят, в production падает.

Матчь идёт на минимальной уникальной подстроке (одно слово, короткая фраза заголовка), которая надёжно влезает в один chunk — уникальность важнее длины. `stripVTControlCharacters(data)` обязателен, но он удаляет ANSI коды **не вставляя на их место пробелы**: в стрипнутой строке `Yes,switchtolow` слова склеены без разделителей, регекс `/Yes,\s+switch/` не сработает. Для многосегментных совпадений (типа «детектировать заголовок + опцию») собирай скользящее окно из последних N байт PTY-вывода и матчись по нему, а не по текущему чанку.

```js
// неверно — оба матча должны попасть в один data chunk:
if (sc.includes('Change effort level') && sc.includes('Yes, switch')) { ... }
// верно — одна уникальная подстрока, надёжный chunk:
if (sc.includes('Change effort level')) { ... }
```

Между detection и автоматическим действием — Ink дорисовывает меню в 3-5 чанках, между ними десятки миллисекунд. После первого matching chunk дай 100-150ms чтобы дорисовать остальные ДО того как пошлёшь подтверждение (`\r`, `Esc`). Без задержки Enter попадает в неопределённое состояние — то закрывает неполностью отрендеренный prompt, то теряется. Cooldown 1-2с обязательно: Ink делает re-render и match может сработать ещё раз. См. `knowledge/fact-claude-tui-control.md::Auto-confirm «Change effort level?» dialog` (один минимальный match `'Change effort level'`, 120мс задержка перед `\r`, cooldown 2с).

## Категориальные toggle — имена сущностей, не абстракции

Когда UI-категория покрывает >2 разных сущности (имена tools, типы файлов, варианты бэкендов, методов оплаты), лейбл toggle должен быть списком реальных имён, а не обобщающим словом. Особенно когда обобщающие слова из разных категорий звучат похоже («Bash» / «Tools», «Network» / «Sync», «Storage» / «Cache») и пользователь не может с первого взгляда разделить их по смыслу. Юзер сформулировал прямо: *«в чём отличие? непонятно и не интуитивно»*, *«с первого взгляда не понимаю»* — каждая категория обозначена одним абстрактным словом, mental model не строится, человек не знает что именно попадёт под фильтр.

Покажи 2-3 канонических имени сущности из категории в monospace, разделённых `·`: `Bash · Monitor` + хинт `shell`; `mcp__* · Web · Agent` + хинт `MCP и прочее`. Хинт — короткое прилагательное-категория, не пересказ списка. Имена берутся из реального источника правды (JSONL-`tool_use.name`), не русское обобщение «Команды», а `Bash` — то имя которое пользователь увидит в логах. Если в категории 5+ имён — покажи 2-3 самых частых + wildcard (`mcp__*`); пользователь понимает что toggle вырастет вместе с экосистемой, не нужно ждать UI-апдейта. Лейбл top-level toggle всё ещё может быть обобщающим («Claude») — там нет конкуренции категорий.

См. `knowledge/fact-clipboard-tools.md::Hierarchical Copy Groups` (Bash vs Tools — child-rows показывают `Read · Grep · Glob`, `Edit · Write`, `Bash · Monitor`, `mcp__* · Web · Agent` вместо общих `Reading/Editing/Bash/Tools`).

## Master toggle + incremental children

Когда UI-группа состоит из главного toggle и нескольких children, между ними должна быть детерминированная двусторонняя связь, а не «N независимых тогглов с интуицией». Parent → Children (cascade): parent OFF выключает все children (UI-disabled, значение в store сохраняется), parent ON восстанавливает прежний выбор. Child → Parent (lift): если хотя бы один child ON, parent ON автоматически — parent это синтезированный флаг `active = anyChild`, не отдельная переменная. Children ↔ Children (incremental): в incremental-семье более «полный» вариант форсирует более «базовый», более «базовый OFF» форсирует «полный» OFF. Пример: «Финальный результат» / «Вся история» — история без результата теряет анкер, поэтому `history ON ⇒ result ON`, `result OFF ⇒ history OFF`.

Узнаётся по тому что пользователь формулирует имя паттерна сам, чтобы объяснить чего хочет: *«они как бы синхрон... инкрементируемые, то есть если я включаю последнее, у меня выключается вся история, и наоборот»*. Это признак того что в UI нет автоматической логики каскада — пользователь видит N независимых тогглов и в голове строит правила сам, которые UI не реализует. Раз сформулировал — правила уже у него в mental model, нужно лишь зафиксировать в коде.

Master-toggle клик: если что-то из children было ON → выключает всех; если все OFF → включает один (минимально полезный, обычно первый child). Store-логика инкремента в setter, не в UI: `setIncludeHistory(v)` внутри ставит `result = v ? true : prev.result` — это гарантирует что любой callsite (горячая клавиша, импорт настроек, миграция) получит правильное состояние. Children disabled при parent OFF, но **значение** в store не трогаем: возврат parent ON показывает прежний выбор, а не дефолт. Это уважение к работе пользователя — он настраивал children, временно выключил группу, настройки не должны исчезать. Антипаттерн «N независимых toggle, документация в tooltip» (типа «чтобы включить историю, сначала включите результат») не работает: никто не читает tooltip, юзер видит что включил history — а результата нет, доверие потеряно. См. `knowledge/fact-clipboard-tools.md::Hierarchical Copy Groups::Master-toggle + incremental cascade`.

## Diagnose with instrumentation, not guesses

При дебаге трудно-наблюдаемого бага (визуальное дрожание, race condition, frame timing, scroll-fight между двумя источниками) сначала добавь логирование с timestamp и фактическими значениями переменных, потом смотри что происходит. Не пытайся починить сходу. Гадание стоит итераций — каждая «фикс на ощупь» имеет ~30% шанс попасть, а юзеру через сборку и репро баг занимает 5-10 минут. Один лог-снапшот может показать что вся гипотеза неверна. Узнаётся по сценарию: агент предлагает 3-4 разных фикса подряд (*«попробуй tolerance=2»*, *«нет, давай cursor-based»*, *«окей, тогда уберём guard»*), каждый раз сборка → юзер на проверку → «не работает». Без единого реального лога. Юзер в какой-то момент прямо требует *«можешь логи глянуть?»* — это сигнал что цикл «гипотеза → фикс → надежда» зашёл слишком далеко.

Логи содержат числа, не пересказ: `[Diag] scrollToLine(1788) DOM.scrollTop 26796→26935 savedLine=1788 baseY=1789 cursorY=39 rows=44`. Из такой строки за 5 секунд видно: cursor на 39 при rows=44, гипотеза «cursor на rows-1» неверна. Логируй источник и направление действия — что снапит viewport, в какую сторону, по чьей инициативе: `[WHEEL] deltaY=-50` vs `[SNAP] scrollToLine(N)` — разные события, разные виновники. Минимум 3 числа: `before`, `after`, `expected`; только `after` ничего не показывает. Не бойся объёма — 60 одинаковых строк подряд это сильный сигнал (стабильный osc/dead-lock), не шум.

Применимо к любому visual jitter / frame-level race, «кнопка не работает иногда» (выясни сначала когда работает, потом когда не), frame-timing багам (16ms окна, sub-pixel округления), любому багу где есть гипотеза но нет данных. См. `knowledge/fix-terminal-jitter.md::Cursor-based bottom detection::DIAG-инструментация` — добавление `[ScrollDiag:WHEEL]` и `[ScrollDiag:SNAP]` сразу показало `cursorY=39 rows=44` и сэкономило часы гадания про tolerance.

## Authoritative artifact > эвристика на input-side, когда первичный сигнал недоступен

Когда нужно детектировать состояние внешнего процесса (turn закончился, операция прервана, файл готов), а первичный сигнал — hook/event/IPC — по какой-то причине не fires в части кейсов, **не угадывай по входному keystroke / клику / таймауту**. Иди в побочный artifact: JSONL transcript, log file, DB row, файл которые сам внешний процесс пишет как побочный эффект своей работы. Юзер сформулировал это сам поверх неработающего фикса: *«это не детерминированный нихуя, это называется костыль»*, *«разве hook у Клода не может отслеживать, если он уже внутри сессии работает, когда мы начинаем стриминг»* — это сильный сигнал что input-side heuristic уже опознан как костыль, нужен другой источник правды.

Признак ложного пути: ловишь `\x1b` / Ctrl+C / клик-paste / scroll и через N секунд решаешь *«наверное, юзер хотел прервать»*. Любой такой keystroke многозначен — `\x1b` это и Esc, и префикс ANSI-последовательности (стрелки, F-клавиши, CSI). Любой такой таймаут — magic number, не привязанный к реальности процесса. И главное: даже если угадаешь правильно по входу, ты не знаешь что **внешний процесс сделал в ответ**. Может он проигнорировал, может продолжил после короткой паузы.

Authoritative artifact решает обе проблемы: ты читаешь **результат действия внешнего процесса** (что он реально записал в свой transcript), а не **догадку о намерении** (что юзер хотел нажав клавишу). `fs.watch` на JSONL + tail-reader + поиск конкретной marker-строки — детерминирован независимо от того как юзер прервал (Esc, Ctrl+C, /interrupt, submit-interrupt). См. `knowledge/fix-claude-aborted-streaming-loader.md` — отбросили `\x1b`-watchdog и перешли на чтение `[Request interrupted by user]` записи в JSONL после того как декомпил Claude'а подтвердил что путь `aborted_streaming` в `query.ts:1051` намеренно не вызывает stopHooks, но запись в JSONL делает гарантированно.

## Программные команды по тому же каналу что юзерские, не через shell-flag-обёртку

Когда у тебя есть managed shell (PTY, embedded REPL, sandbox terminal) с **observability hooks** (OSC 133, telemetry log, prompt-finished callbacks), любая команда отправленная программно — из MCP, из restore-сессии, из автоматического pendingAction — должна идти **тем же путём** что юзерский keystroke: `pty.write(cmd + '\r')` в interactive shell, а не как `shell -c "<cmd>"` обёртка над спавном. Иначе observability работает только для одного канала и молча ломается для другого. Юзер не различает источник команды: *«я даже не знаю, имеет ли значение, что запуск был через MCP, какая разница, если основная проблема в том, что у меня должно происходить считывание, есть ли какой-то активный процесс»* — индикатор активного процесса должен зажигаться одинаково.

Симптом разрыва — фоновая фича работает в одном сценарии и беззвучно отсутствует в другом, при том что код фичи нигде не сломан. В custom-terminal: `zsh -l -c "<cmd>; exec shell"` для MCP-табов давал процессу запуститься, но `-c` mode пропускал precmd/preexec → OSC 133 не fires → зелёный индикатор активного процесса не зажигался. Тот же `npm run dev` запущенный руками в interactive shell сразу триггерил `[OSC 133] B`. Лечится унификацией канала: спавним всегда чистый interactive shell с нашим shell-integration, команду шлём в `pty.write` по первому `OSC 133 A` (детерминированный сигнал что хуки загрузились). См. `knowledge/fix-mcp-spawn-non-interactive-shell.md`.

## Routing по контексту запроса, не по глобальному last-active state

Когда у приложения N параллельных инстансов (dev + prod, разные user-data-dir, разные базы), и каждый принимает внешние запросы на shared IPC-канал (HTTP-сокет, файл-discovery, named pipe), routing «у кого port-файл свежее» рано или поздно ломается. Симптом: юзер работает в инстансе A, внешний клиент (Claude через MCP, CLI-помощник, сторонний скрипт) шлёт запрос с context-hint'ом проекта A, запрос **молча** уходит в инстанс B. На стороне клиента всё успешно («tab created», 200 OK), на стороне юзера ничего не происходит — он сидит не в том окне. Юзер в моменте: *«он реально делает MCP-вызов, я вижу системное сообщение, а вкладки нет»* — это сигнал что запрос дошёл, но не в тот контекст.

Принцип: routing определяется **полем запроса**, не глобальным состоянием discovery-механизма. Каждый инстанс публикует **что он знает** — список открытых проектов / cwd / namespace'ов в своём port-файле. Discovery на стороне клиента — longest-prefix match между hint'ом запроса (явный `cwd` для команд работающих с файлами, декодированный из ID для команд работающих с уже существующими объектами) и опубликованным знанием. Most-recent mtime остаётся **только как fallback** для запросов без контекста (helper-скрипты из `/tmp`, free-form bash). То же на втором уровне — внутри инстанса, обработчик не должен класть таб в `activeProjectId` потому что это глобальное «что юзер видит сейчас», не «что относится к этому запросу»; кладёт в проект, чей path является префиксом запрошенного cwd.

Антипаттерн «работает на одном инстансе, тестировал — всё ок» исчезает только когда оба механизма (cross-instance discovery + within-instance routing) опираются на одно поле запроса, не на N разных глобальных переменных. См. `knowledge/fact-mcp-routing.md::Architecture` — port-файл JSON `{port, pid, openProjectPaths}`, terminal-server `pickInstance(cwd)`, `handleMcpCreate` longest-prefix вместо `activeProjectId`.

## Reproduce by the real user path, not synthetic equivalent

Когда «фикс работает» проверяется через программный test-path — убедись что этот path реально проходит через тот же код что и user action. Synthetic events часто минуют callback'и которые юзер триггерит вживую; утверждение «работает» по synthetic-тесту = ложноположительный результат, и юзер найдёт это первым. Канонический пример: агент пишет фикс на `term.onData((data) => { ... })`, тестирует через `ipcRenderer.send('terminal:input', tabId, data)` — namespace одинаковый, кажется что тест валиден. На самом деле IPC отправляет байты напрямую в PTY, минуя `term.onData`. Тест проходит, юзер пробует — баг на месте, потому что у него keystroke идёт через xterm `onData`.

До утверждения «фикс работает» — найди в коде где именно триггерится твоя логика (callback, event-listener, hook). Тест должен пройти через эту точку, не «параллельно через тот же API». Real user path — trusted browser events (`InputEvent` на `.xterm-helper-textarea`, `WheelEvent` на viewport, `KeyboardEvent` с правильным keyCode), не CDP-инжекция или прямой IPC. В тестовом сообщении явно укажи через что идёт ввод: «через keyboard event» vs «через IPC» — позволит юзеру сразу понять валиден ли тест в его сценарии. Если real-path repro невозможен (требует физического tap на trackpad) — явно скажи это и попроси юзера проверить.

Применимо к любой фиче с callback-цепочкой xterm/Codemirror/Monaco (`onData`, `onScroll`, `onKey`, `onPaste`); React-фичам где `onChange` vs прямое мутирование state; drag-and-drop, где synthetic `dispatchEvent('dragstart')` часто не вызывает trusted-listener'ов в `@atlaskit/pragmatic-drag-and-drop`; любому клавиатурному shortcut с modifiers (Cmd/Ctrl) — synthetic KeyboardEvent часто не пропагирует metaKey. См. `knowledge/fix-terminal-jitter.md::Cursor-based bottom detection::Подвох в тесте через MCP` (фикс `onData → ref clear` проверяли через `terminal:input` IPC — не сработал бы; правильный test через `InputEvent` на textarea подтвердил работу).

## Click-outside как universal escape, mouse-leave опционален

Для любого dismissable popup'а (context menu, action menu, tooltip, confirm dialog) должен существовать хотя бы один escape-жест, работающий в каждом внутреннем режиме. Mouse-leave можно отключать в чувствительных режимах (confirm для destructive-action, postPrompt с введёнными данными), но click-outside должен оставаться универсальным — это последний рубеж. Узнаётся по фразам *«я нажимаю Удалить историю, потом клик на оверлее не срабатывает»*, *«никак не закрыть это окно кроме как нажать Cancel внутри»*: юзер заперт в popup'е, единственный путь — конкретная кнопка внутри которая может быть вне области внимания или конфликтовать с моторной памятью «клик в сторону = отмена».

Один global `mousedown`/`click` listener на window, проверка `e.target` через ref-containment ИЛИ через `e.stopPropagation()` на корневом div popup'а (короче, надёжнее, не зависит от структуры внутренних элементов). В global handler — безусловное закрытие popup'а в любом режиме; не `if (!confirmMode && !postPromptMode)` — этот гейтинг и есть ловушка. Если popup имеет внутренние режимы (confirm/loading/постпромпт) — при закрытии сбросить их в дефолт, чтобы при следующем открытии popup был чист. Mouse-leave dismiss остаётся отдельной фичей для «легкомысленного» режима popup'а: когда юзер перешёл в чувствительный режим (нажал «Delete») — выключай mouseLeave (защита от случайного hover-выхода), но никогда не выключай click-outside одновременно. Если `isInDangerousMode` совпал с выключенным `onMouseLeave` — у юзера нет выхода кроме как кликнуть на конкретную кнопку внутри popup'а.

Для предотвращения «протекания» внутренних кликов в global handler есть два пути: `e.stopPropagation()` на корневом div popup'а (все клики внутри останавливаются на корне, один listener, простая реализация — для self-contained popup в Portal безопасно) либо `ref.current.contains(e.target)` в global handler (не требует stopPropagation, но требует ref на DOM-узел popup и проверки в каждом global handler'е). В portal-popups предпочитай `e.stopPropagation()`. См. `knowledge/fact-timeline.md::Range Copy & Edit Range::Inline confirm` (rangeActionMenu всегда закрывается на click-outside, включая confirm/postPrompt режимы; mouseLeave отключён только в чувствительных режимах; `e.stopPropagation()` на корне popup защищает внутренние клики).

## Two-step inline confirm для destructive в context menu

Когда destructive-кнопка живёт внутри ПКМ-меню (Удалить запрос, Удалить историю, Кill процесса) — не открывай модалку поверх меню для подтверждения. Первый клик по кнопке заменяет её собственный лейбл на «Точно удалить?» с красной заливкой фона, второй клик той же кнопки вызывает действие. Окружение остаётся прежним: popup тот же, остальные пункты на месте, geometry не прыгает, focus не теряется. Юзер действует в одном слое — не оценивает заново «где я и что эта модалка», а просто подтверждает или уводит курсор.

Антипаттерн — модалка с двумя кнопками «Отмена / Подтвердить» поверх ПКМ-меню: вырастает второй уровень UI, click-outside становится двусмысленным (закрывает модалку или меню?), `Esc` тоже двусмыслен, моторика «клик в сторону = отмена» работает только для верхнего слоя. Inline-confirm убирает второй слой и делает escape-жесты однозначными — click-outside закрывает popup целиком, повторное наведение мыши на ту же позицию не триггерит ничего. Применено в двух местах проекта: `rangeActionMenu` для удаления диапазона записей (`knowledge/fact-timeline.md::Range Copy & Edit Range::Inline confirm`) и в context-menu Timeline для удаления одного user-prompt (`knowledge/fix-delete-user-entry.md`). Парный принцип — `Click-outside как universal escape`: confirm-mode выключает только mouseLeave-dismiss, click-outside остаётся доступным как «последний рубеж».

## Геометрия popup — от измерения, не от формулы

Popup, anchored к динамическому контейнеру (sidebar, sliding panel, conditional column), позиционируется через `getBoundingClientRect()` контейнера — не через формулу из «известных» ширин соседей. Формула неизбежно расходится с реальностью при условном рендеринге, drag-resize, theme/density changes, mode toggles. Узнаётся по тому что popup появляется не там, где ожидается, особенно «прыжки» при определённых сочетаниях UI-состояний — открыт ли соседний sidebar, развёрнут ли tree-mode, какая ширина окна. *«Странно, popup появляется в центре экрана»*, *«всё равно нарушение в пикселях»* — и нарушение проявляется только в части сценариев, что означает формула делает скрытое допущение.

```js
// неверно — работает только если sidebar и panel ВСЕГДА рендерятся:
right: `${sidebarWidth + panelWidth - 8}px`

// верно — измерение через ResizeObserver:
const [popupRight, setPopupRight] = useState(0);
useEffect(() => {
  const el = anchorRef.current; if (!el) return;
  const measure = () => setPopupRight(window.innerWidth - el.getBoundingClientRect().left + GAP);
  measure();
  const ro = new ResizeObserver(measure);
  ro.observe(el);
  ro.observe(document.body);   // КЛЮЧЕВОЕ — иначе пропустим «соседняя панель схлопнулась»
  window.addEventListener('resize', measure);
  return () => { ro.disconnect(); window.removeEventListener('resize', measure); };
}, [/* deps на флаги влияющие на layout */]);
```

`ResizeObserver` на сам якорный элемент не срабатывает в сценарии «соседняя панель схлопнулась, мой размер не изменился, но мой `left` сдвинулся». Лекарство — наблюдать ещё и `document.body`: любое изменение flow-layout вызовет resize body, что переизмерит позицию. Не идеально (избыточные обновления при scroll'е), но дешевле чем подписываться на конкретные эвенты каждого соседа.

Подводный камень — body-observer для Portal-child элементов. Совет «наблюдай `document.body`» работает только пока сам измеряющий компонент не живёт в body. Если он рендерится через `createPortal(content, document.body)` и при этом может двигаться (drag-resize, drag-reposition, animation) — получаем feedback-loop: drag перемещает Portal-child → DOM-layout внутри body меняется → `ResizeObserver(document.body)` re-fire → measure → `setState` (новые координаты anchor'а) → re-render Portal-child с новыми координатами → новое движение в body → GOTO. Симптом — дёрганый drag, ползающие позиции при анимациях, лагающий resize Portal-модалок; на уровне отдельного кадра всё работает «правильно», но визуально движение порвано. Лекарство — наблюдать только конкретные anchor-элементы через `ro.observe(anchorEl)` плюс `window.addEventListener('resize', measure)`; `document.body` не подписывается; если у тебя несколько anchor'ов — подпишись на каждый явно, не на body.

Формула приемлема только если все компоненты в ней — постоянно отрисованные fixed-width элементы без условного рендеринга и без resize. Это редкий случай — в сомнении измеряй. См. `knowledge/fact-timeline.md::Z-index и геометрия popup` (6 popup'ов используют единый `popupRightPx` state из ResizeObserver на containerRef + document.body; кладбище формулы `notesPanelWidth + (treeMode ? 160 : 32) - 8`, которая безусловно вычитала notesPanelWidth даже при закрытой HistoryPanel) и `knowledge/fact-notes.md::Tab Notes Slideout` (модалка в Portal к body, drag по правому хендлу + body-observer = jitter; убрали body-observer, оставили `ResizeObserver(openButton) + window.resize`).

## 1 prompt — 1 dot. Атрибуты вместо отдельных entries

Когда побочные действия (tool-calls, sub-events, дочерние операции) семантически принадлежат одной родительской сущности (user-prompt, commit, post), отображай их как атрибуты родителя (цвет, бейдж, inline-info в hover-state), не как отдельные элементы в той же хронологической ленте. Каждый дополнительный элемент в timeline = шум, размывающий «вот где основное событие N». Узнаётся по тому что длинные сессии становятся нечитаемыми: из 50 точек 30 — мусорные «промежуточные», 20 — настоящие user-prompts, и пользователь не может быстро найти «где я задал вопрос X». Юзер формулирует прямо: *«не должно быть отдельного элемента в таймлайне для этого, у нас должна быть модалка пользователя»* — mental model уже сформирована, события воспринимаются как часть user-prompt'а, не как самостоятельные точки.

Атрибутный подход применяется когда под-событие не имеет смысла без родителя (`docs_search` сам по себе бессмыслен — он часть вопроса, в ответ на который Claude искал в docs); происходит только в ответ на родителя, не независимо (CI-run на commit, react-emoji на post, retry на failed-request); или когда массовость превращает шум в стену — одно `docs_search` в день может быть отдельной точкой, 30 `docs_search` за час обязательно атрибуты. Реализация: бэкенд при формировании timeline после каждого parent-entry делает look-ahead до следующего parent и собирает child-events в `parent.childEvents[]`, не эмитит child как отдельную entry. Фронт: parent-точка меняет цвет / получает бейдж если `childEvents.length > 0`, в hover — inline-блок с иконкой/счётчиком/списком. При нескольких типах child-events (docsEdit + docsSearch) нужен precedence rule: «более сильное действие» перекрывает «более слабое» (Edit > Search, Push > Pull, Delete > Update).

См. `knowledge/fact-timeline.md::Docs-индикаторы как атрибут user-entry` (раньше docs_edit / docs_search были отдельными dot-entries → длинные docs-update сессии теряли структуру; теперь backend look-ahead собирает их в `entry.docsEdited[]` / `entry.docsSearchQueries[]`, цвет user-точки меняется, inline-блок в self-tooltip показывает детали).

## Attribution-блок свёрнут по дефолту, expand on demand

Когда parent-сущность (см. `1 prompt — 1 dot` выше) получает атрибуты в hover-tooltip / preview-card (метаданные, child-events, related-items), эти атрибуты рендерятся в свёрнутом виде (заголовок + счётчик в скобках) и раскрываются только по явному click. По умолчанию primary content (текст самого parent'а) виден целиком, attribution-блок занимает 1 строку. Иначе — пользователь наводит на entity, открывается tooltip, но самое главное (текст/имя/основной content) не видно, потому что вверху раскинуты 5-10 строк attribution-метаданных (списки файлов, теги, related links). Скролл tooltip'а не спасает: пользователь сначала ищет где основной content, потом крутит — нарушает «контент за один взгляд». Из живой сессии: *«я не вижу типа сообщение юзера, которое должно показываться»*.

Через три итерации стало ясно что не работает: полный список с переносом строк (5+ атрибутов = такая же высота как primary content; визуально атрибуты равны или больше); inline через запятую (`Label (N) — item, item, item` при длинных именах превращается в 2-3 строки после wrap, экономия мнимая); truncation с ellipsis (обрывает информацию, нужен expand всё равно, при truncate в середине имени непонятно что это за элемент). Работает только счётчик в свёрнутом виде + click → expand под заголовком (полные значения, по строке на элемент, индентация под иконку). Один клик = полное раскрытие, повторный = свернуть. State per-entry (`Set<id>`), сбрасывается при unmount tooltip'а.

Edge case с N=1 — можно показать inline (`Docs updated — design.md`), одна строка всё равно. Но реализационно проще единое поведение: всегда `(N)`, всегда expand-on-click; лишний click на N=1 — приемлемая цена за консистентность. Связь с `1 prompt — 1 dot`: тот принцип про группировку (child-events → attributes родителя), этот про layout-приоритет (attributes ≤ primary content). Применимо к hover-cards над постами (reactions свёрнуть до счётчика), GitHub PR-preview (CI checks свернуть до `(N passing)`), любым details-on-demand UI.

Обобщение — collapse только когда scroll невозможен. Принцип «preview + toggle на full» осмыслен только если у контейнера нет своего max-h + overflow-y: auto. Если контейнер уже скроллится (как code-блок в SyntaxHighlighter с `maxHeight: 480px`), второй toggle `Раскрыть полностью` — дублирующий жест: и scroll, и expand показывают что ниже. Collapse оправдан для контента, который раскладывается вниз растягивая parent (user-сообщение в чате без max-h, attribution-блок в tooltip'е, inline-комментарий в timeline) — у них нет своего scroll-окна. Collapse избыточен для контента у которого уже есть max-h + overflow-y: auto (code-блок Read'а, diff Edit'а, output bash-команды). Truncate ellipsis'ом — отдельный антипаттерн: убивает информационную плотность, три записи с одинаковым префиксом выглядят как дубли. Используется ТОЛЬКО для одно-строчных лейблов в zoomed-out видах (плитки, таблицы со фиксированной шириной колонки), в chat-UI никогда.

См. `knowledge/fact-timeline.md::Inline preview в self-tooltip`. В custom-terminal: `CollapsibleText` для user-prompt'ов в SDK-табе (порог 600, preview 400) — оправдан, текст растягивает thread. `Read`-карточка и `DiffLines` — content в max-h-480px scroll-блоке без toggle. Bash output — также scroll внутри SyntaxHighlighter.

## Destructive action ≠ цвет status-indicator

Цвет, который в системе закреплён за статус-индикатором «процесс/сущность активна» (зелёный = running, online, alive), не должен использоваться для кнопки, которая этот статус прерывает (Stop, Disconnect, Cancel, Kill). Иначе action и индикатор сливаются в одну зону внимания, destructive-кнопка читается как продолжение/подтверждение «всё хорошо», а не как «прервать». Канонический сценарий: в context menu таба running-индикатор слева — зелёная пульсирующая точка, рядом кнопка `Stop <process>` тоже зелёная (`#4ade80`, тот же цвет, та же палитра). Пользователь тянется кликнуть «прервать» — глаз видит две одинаково-зелёные сущности и колеблется. *«Это что, кнопка „продолжай“?»*. Дословный фидбек: *«сделай тут вишнево-красную кнопку, а не зеленую»* — пользователь сам сформулировал решение раньше чем смог объяснить почему.

Цвет статус-индикатора — любой цвет, ассоциированный с positive ongoing state в этом UI: зелёный (online, running, healthy), синий (connected, syncing), жёлтый/оранжевый (warning ongoing, pending — хуже всего, destructive в этих цветах читается как «продолжай разбираться»). Для destructive используй cherry-red `#dc2626` или rose `#e11d48` — однозначно «остановить/уничтожить» в большинстве UI-конвенций (не путать с brand-red Netflix/YouTube — там красный = identity). Brand-tint текущего процесса допустим если в проекте устоялся отдельный визуальный язык per-engine (Claude orange / Gemini blue): destructive-семантика тогда идёт через лейбл `Stop` + явную форму (квадратная точка как stop-icon, отделяет от круглого running-dot). Default — cherry-red.

Исключение — если в системе зелёный = positive action (Confirm, Save, Apply), destructive не зелёный по дефолту, и зелёный для Stop будет дезориентировать так же как красный для Save. Принцип общий: destructive не повторяет цвет позитивного индикатора/действия в этой же области UI. Живой шрам — SCRIPT_TINT в TabBar context-menu был `#4ade80` (тот же green что у running-dot слева от имени таба) с обоснованием *«зрительная связь — это тот процесс который сейчас горит зелёным»*. Логично на бумаге, провально на практике: пользователь читал кнопку как «индикатор», не как «action», колебался при клике. Сменили на cherry-red `#dc2626` — двусмысленность ушла. См. `knowledge/fact-tabs.md::Split Close+Stop для script-табов`. Stop Claude / Stop Gemini сохранили brand-tints (orange/blue) — там destructive-семантика передаётся через лейбл + квадратную форму точки vs круглую у running-dot. Для script-Stop квадратная-vs-круглая дифференциация была недостаточна (квадратная точка маленькая, не считывалась) — потребовалась цветовая дифференциация.

## Inline icon-buttons в title row — не отдельная строка

LLM-предложенный дефолт для панелей: первая строка — заголовок, вторая — главная кнопка действия на всю ширину. Это правильно для широких кнопок («Save changes», «Run analysis») с явным лейблом — занимает место заслуженно, считывается с расстояния. Но для узких action-кнопок (иконка/точка/один глиф ≤ 24px) отдельная строка — пустая трата вертикали. На компактных оверлеях (sidebar widgets, sticky panels) каждая строка дорогая: Run-кнопка на 32px в overlay шириной 240px съедает 8% полезной площади ради одной точки-индикатора.

Правило простое — кнопка с текстовым лейблом ≥ 24px ширины идёт отдельной full-width row; кнопка-иконка / точка / один глиф инлайн в title row слева от заголовка. Title row становится визуальным action-trigger + status одновременно (точка пульсирует, заголовок справа — контекст). Inverse signal: если иконка-кнопка делает что-то критичное и необратимое (Delete project, Force-kill) — наоборот вынеси на full-width row с явным лейблом; click affordance ≠ destructive affordance. Inline-точка ок только для toggle-state с понятной семантикой текущего состояния.

Расширение — compact toggle groups в title row. Тот же принцип применим к маленьким toggle-группам (2-4 pill'а высотой ≤ 20px): если они «выбор первичной сущности» по семантике (Provider, Category, Domain), их можно ставить в шапку справа от заголовка, не выделять отдельной row с лейблом `Provider:`. Title row слева — handle названия раздела, pills справа — handle выбора в этом разделе. Critical: pills должны быть визуально меньше чем Model/Effort pills в строках ниже (h=18 vs h=23), иначе шапка перевешивает контент и читается как primary action row. Subscript-уровень иерархии: заголовок > content rows > header-inline toggles.

## Фикс-ширина для wrap-grid карточек, полное имя через hover-popover

Когда сетка карточек переменной длины имени (`tab-1`, `worker-search`, `back-worker-search`) укладывается в wrap-flex, соседние карточки получают разную ширину — `minWidth: 90 / maxWidth: 140` гарантирует только границы, но не равенство. Результат — колонки внутри одной wrap-строки рваные, визуально читается как «таблица сломалась» (юзер дословно: *«у нас полоска вертикальная, они как-то некорректно поставлены»*, *«сделай блоки одинакового размера, то это некрасиво»*). Лечение: фикс-ширина для всех карточек одного типа (`width: 100` вместо `min/max`), длинные имена обрезаются `truncate`, полное имя всплывает в hover-preview (CMD-popover в этом проекте, обычный Tooltip в более простых UI). Принцип: визуальная решётка важнее «оптимального» использования пикселей под короткие имена — фикс-ширина даёт grid-feel, min/max даёт ragged-feel.

См. `knowledge/fact-project-home.md::Visuals` (Active/Favorites/History cards с 140→100px после уменьшения по запросу юзера; CMD+hover popover как единственный источник полного имени и метаданных, bare-hover Tooltip отвергнут чтобы не дублировать жест).

## Mirror Editing: редактор замещает соседнюю колонку, не плавает поверх

Для двухколонных layout'ов настроек (`Settings → AI`, `Settings → Prompts`, любой `[список] | [список]` интерфейс) форма редактирования не модалка поверх. Она замещает соседнюю колонку: клик по карточке в левой колонке → редактор открывается в правой, карточки правой пропадают (и наоборот). Модалка ломается тремя способами: теряет контекст соседней колонки (пользователь забывает что редактирует «слева», когда поверх всплыл scrim); layout shift (модалка обычно меньше колонки → видимая область уменьшается); cognitive overload — при модалке на экране три контекста (левая + правая + модалка), при mirror editing два (список несоредактируемой категории + редактор).

Контекст сохранён — всегда виден список той категории которую НЕ редактируешь. Layout стабилен — ширина колонок 50/50 не меняется, меняется только содержимое. Single editor invariant — только один активный редактор на экране, исключены ошибки «сохранил в неправильном поле, потому что было два открытых». Применимо в layout с двумя параллельными списками одного типа сущностей или связанных; не применимо к single-column views — там используется `Slideout-якорь к chip'у` (следующая секция).

## Slideout-якорь к chip'у, не центр экрана

Modal-формы для редактирования элемента списка LLM по дефолту рендерит как centered modal с scrim. Это правильно для самостоятельных диалогов (settings, confirm, primary task). Но если редактирование — расширение конкретной строки в списке, центральная модалка рвёт визуальную связь: пользователь не понимает что он редактирует именно эту строку.

Slideout «прижат» к ряду: top-edge редактора выровнен с top-edge редактируемой строки, right-edge — с left-edge панели списка (если панель справа), без scrim — list позади остаётся видимым чтобы пользователь видел контекст соседних рядов. Закрытие по Esc / клику-вне / ×, не по клику на список (это break-flow). Mirror Editing — частный случай (2 колонки, редактор заменяет правую), Slideout-anchor — обобщение для single-column lists, где правая граница списка фиксирована (overlay, sidebar). В `PromptQueueOverlay.tsx::editorAnchor` хранится `{ top, right }`: top это `chipRef.getBoundingClientRect().top` редактируемого чипа (или panel.top для «новый промпт»), right это `window.innerWidth - panel.left + gap`. Slideout позиционируется `position: fixed; top; right;` — auto-syncs при scroll'е панели потому что viewport-relative.

## Click-toggle-off на single-select pill

Single-select группа кнопок (filter pills, tag selectors, effort level, model picker) — повторный клик на уже-активную опцию должен сбрасывать выбор в neutral/auto/off state. Без этого юзер вынужден сначала выбрать другую опцию, потом дернуться к мыши и снять, или открывать context-menu — три действия вместо одного. Канонический сценарий: юзер выбрал `effort: max`, передумал, хочет вернуть default. Клик на `max` ничего не делает (уже active), клик на `low` → потом клик на `low` ещё раз → нет → теряется. Юзер ищет «deselect» которого не существует.

Один тернарник в обработчике: `const targetLevel = isActive ? defaultValue : level`. `defaultValue` зависит от семантики — для Claude effort это `auto` (нейтральный), для DeepSeek effort это `off` (явное отключение thinking), для tag filter это `null` (no filter). Tooltip на active кнопке подсказывает «Click again to deselect (→ auto)». Не применимо если группа обязательно должна иметь активную опцию (radio-required) и нет `null/auto` state — например выбор языка приложения, тогда повторный клик = no-op. Но 90% UI кейсов имеют neutral fallback. См. `InfoPanel.tsx::effort buttons`; та же логика применима к Model row, Provider row, и любым будущим pill-группам.

## Toast preview = что именно затронуто

Для destructive/programmatic actions где юзер не видит финальный результат напрямую (copy в clipboard, перенос в очередь, отправка в API, авто-clear input) toast должен показать **превью** того что именно затронуто, первые 15-30 символов + `…`. Не «Copied», не «Done», а `Copied: "Refactor the user…"` или `Queued: "Read all files…"`. Юзер не видел финальную нормализованную форму: Claude collapse'ит paste в `[Pasted text #N +M lines]`, clipboard пишет invisible bytes, API получает trimmed строку. Toast = checkpoint «вот что реально ушло». Если ушло не то — юзер ловит ошибку через 1-2 секунды и может откатить.

Multi-line → single-line через `text.replace(/\s+/g, ' ')` (иначе toast разрывает layout); truncate `len > 20 ? text.slice(0, 20) + '…' : text` (20 — компромисс между видимостью и не-шумом). Если действие имеет дополнительные effects — упомянуть: `Copied + cleared: "..."`, `Queued: "..." · 3 📎`. Toast без превью (`Copied to clipboard`) для programmatic copy — антипаттерн: юзер не понимает что именно скопировалось, клавиатурный paste в другое окно может показать совсем не то что ожидалось. См. `PromptQueueOverlay.tsx::grabCurrent`, `InfoPanel.tsx::Copy prompt` — оба показывают `verb: "first 20 chars…"`.

## Несовместимость параметров — гасить в точке выбора, не в момент отправки

Когда есть известная клиентски таблица совместимости параметров (LLM effort × model, payment method × region, image-format × resolution, любой `X × Y → boolean`) — UI обязан запрещать невалидный выбор там, где пользователь его делает. Не показывать toast «не сработает» при отправке, не отправлять и ловить downgrade от сервера. «Отложить уведомление до конца действия» — антипаттерн: юзер уже сделал mental commit на выбор («я выбрал max, я ожидаю работу на max»). Toast спустя 3 секунды отправки разрушает контракт: только что выбрал, ничего не изменилось видимо в UI, действие ушло — но оказалось не то действие. Юзер сформулировал прямо: *«откладывать это на потом, чтобы это появлялось когда-нибудь потом, очень плохая идея»*.

Реализация — два слоя. Visual disabled на несовместимых опциях: пилюлю с `max` на Haiku-модели рисуем серой, `cursor: not-allowed`, hover-tooltip *«не поддерживается моделью haiku»*, клик не срабатывает; юзер видит границы выбора, не натыкается на них через ошибку. Auto-downgrade при смене первого параметра: юзер был на `(opus, max)`, переключил модель на `haiku` → текущий `max` невалиден → UI немедленно даунгрейдит effort до ближайшего поддерживаемого (`high`) + короткий info-toast *«effort: max → high»*. Состояние всегда консистентно с возможностями.

Источник таблицы — provider, не наш код. Хардкод *«max работает только на Opus и Sonnet»* устаревает с каждым релизом Anthropic. Когда SDK/API выдаёт metadata (`query.supportedModels()` возвращает `supportedEffortLevels[]` для каждой модели) — читаем оттуда при старте, кэшируем на сессию, обновляется по апгрейду пакета. Хардкод допустим только если provider не выдаёт метаданные — тогда писать однострочный комментарий с датой источника и быть готовым к рассинхрону. Что остаётся для toast'а после downgrade'а в точке выбора: runtime mismatch когда server молча подменил параметр (server-side capacity issues, retired models — реально подменяют). Сравнивать `requested.model` с `response.model` на первом ответе, показывать warning один раз на turn — safety net, не основной сигнал. См. `ClaudeSDKTab.tsx::SDK_MODEL_CAPS` (грузится из `query.supportedModels()` через main IPC), `InfoPanel.tsx` использует caps для greying пилюль и auto-downgrade при смене модели; конкретика — `fact-claude-sdk-tab.md::Effort gating + auto-downgrade`.

## Secondary action: нейтральная палитра, не конкурирует с primary tint

Когда в одном container'е есть две action-кнопки — primary (главное действие, может быть destructive) и secondary (вспомогательное на тот же контекст) — secondary должен иметь нейтральную палитру (белый/серый), не accent-цвет primary. Узнаётся по сценарию: в InfoPanel рядом с Copy Session (оранжевый Claude-accent) появилась Copy Prompt тоже оранжевая — две оранжевые кнопки одинаковой яркости, глаз не понимает что primary, что вторичное. Юзер: *«мне оранжевый цвет не нравится, нужна какая-то более в белую сторону»*.

Палитра для secondary — border `rgba(255,255,255,0.12)`, background `rgba(255,255,255,0.03)`, color `#bbb`, hover поднимает background до `rgba(255,255,255,0.06)` + `color: #fff` (контраст растёт при наведении). Primary остаётся в проектном accent-color (Claude orange `#DA7756`, Gemini blue `#4E86F8`); secondary визуально рецессирует в фон, всплывает только при hover. Если действия в группе равнозначные (две кнопки одного destructive level — Stop Claude / Stop Gemini в multi-select) — тогда tint разный (orange vs blue), а не один тоном ниже; это другой паттерн (см. `fact-tabs.md::Multi-select Stop с majority badge`).

## Single source of truth для third-party shipping values

Когда UI отображает список значений которые shipping'аются внешней системой (CLI versions, API enums, cloud regions, payment-provider scopes, model names от LLM-провайдеров) — этот список обязан жить в одном canonical-файле проекта, не в виде хардкод-литералов рассыпанных по компонентам. Шрам — в мае 2026 Claude обновил effort-уровни (`auto` удалён, `xhigh` добавлен между `high` и `max`). В проекте список `['auto','low','medium','high','max']` встречался в 4 местах: `useUIStore` (type union + validation array), StatusBar (popup levels + labels), InfoPanel (effort pills), toggle-off target. Юзер прислал скриншот настоящего Claude TUI с новыми уровнями — пришлось искать grep'ом, четыре раза править в синхронизации. Когда ещё один уровень добавится через месяц — забудем хоть один файл, UI рассинхронизуется молча.

```ts
export const CLAUDE_EFFORT_LEVELS = ['low','medium','high','xhigh','max'] as const;
export type ClaudeEffortLevel = typeof CLAUDE_EFFORT_LEVELS[number];
export const CLAUDE_MODELS = ['default','sonnet','opus','haiku'] as const;
```

Все use sites импортируют отсюда. Type-derivation `typeof X[number]` гарантирует что type union в sync с runtime array без отдельного hand-maintained типа. Toggle-off / default-fallback value тоже в этом файле как named export (`CLAUDE_EFFORT_TOGGLE_OFF`), не magic literal в onClick. При следующем shipping-апдейте должно быть ровно один edit в одном файле — если требуются правки в >1 файлах = anti-pattern, ещё одна точка fan-out пропущена.

При удалении value из списка (`auto` → нет) нужна одноразовая миграция на load из persisted state: `if (saved === 'auto') saved = CLAUDE_EFFORT_TOGGLE_OFF` перед валидацией. Иначе у существующих юзеров value не пройдёт `includes()` гард и сбросится в дефолт молча — пугающий регресс «настройка пропала». См. `src/renderer/constants/claudeLevels.ts`, конкретика — `fact-claude-tui-control.md::Шрамы формата данных`.

Аналогичная миграция нужна когда меняется не enum, а **numeric default** persisted-настройки, и старое сохранённое значение технически валидно но семантически устарело. Канонический случай: правая колонка ProjectHome раньше была 340px (под 140px-карточки), после уменьшения карточек до 100px новый дефолт стал 220px. Просто прочитать `localStorage.getItem()` и clamp к `[MIN, MAX]` — недостаточно: у существующих юзеров останется 340 (валидно по диапазону), и они увидят пустую полосу справа от 100px-карточек, не понимая что divider можно тянуть. Migration-guard в loader'е: `if (saved >= OLD_DEFAULT_LOWER_BOUND) { removeItem(key); return NEW_DEFAULT; }` — стирает «вероятно стейл» значения и возвращает новый дефолт ровно один раз. Граница `OLD_DEFAULT_LOWER_BOUND` выбирается так, чтобы случайные клиентские drag'и в новой нише (200-280px) не сбросились — берём минимум +50px от нового дефолта. См. `knowledge/fact-project-home.md::Двух-колоночный layout` (220px default, migration-guard для ≥320).

## Visible side effect > silent IPC для destructive actions

Когда действие пользователя триггерит destructive side effect (kill процесса, удаление файла, очистка clipboard, force-rebuild cache) — этот side effect должен быть видимым в основном потоке UI (терминал, лента активности, лог), не выполняться через тихий background IPC + toast. Если действие меняет state ВНЕ нашего приложения (kernel, filesystem, network, child processes) — делай это видимо в shell/log/activity-feed; если внутри (UI state, in-memory cache) — toast/spinner достаточно.

Шрам — kill dev-ports изначально работал через `ipcRenderer.invoke('system:free-project-ports')` в main, `lsof | kill -9` шёл фоном, в терминал ничего не печаталось. Юзер запускает `npm run dev`, видит только `npm run dev` строчку — не понимает что что-то убилось. Жалоба: *«если она вводится как-то фоном, то в таком случае должно быть уведомление типа „остановлены какие-то порты“. Или проще же прям в терминале вводить»*. Решение — инжектить shell-команду в видимый поток: `lsof -ti:5181,3000 2>/dev/null | xargs -r kill -9 2>/dev/null; npm run dev`. Юзер видит строку целиком как будто сам её ввёл, scrollback хранит record, `;` гарантирует ordering (kill до npm), history позволяет re-up arrow. Никакого toast не нужно — терминал сам показывает что произошло.

Toast не альтернатива: эфемерный (исчезает за 1.5-3s), не накапливается, не searchable. «Killed port 5181» поверх npm-вывода — пользователю надо переключать внимание между двумя источниками правды; shell-line = одна линия временной правды. Silent IPC + toast допустим когда действие non-destructive и side effect внутренний (state mutation, save to disk, push to queue): «Copied to clipboard» — OK потому что clipboard invisible-by-design системный buffer, юзер сам paste'нет когда захочет проверить; «Killed 3 processes» — НЕ OK потому что юзер хочет видеть кого убил и в каком порядке. См. `fact-statusbar-toggles.md::kill dev-ports`.

## Brand identity = icon + color, не текст

Когда в UI есть выбор между brand'ами третьих лиц (LLM-провайдеры, cloud-вендоры, payment-методы, package managers) — каждый brand идентифицируется glyph-иконкой + brand-color, текстовый label вторичен. Узнаётся по тому что три провайдера выглядят как одинаковые pill'ы в одном generic-blue accent (`#6B8AFF`); юзер: *«тут в принципе и так понятно, что речь идёт про выбор нейронки. У них разная цветовая гамма, то есть у Claude должна быть иконка Claude. Для остальных также скачай SVG иконку оригинальную, их цвет»*.

SVG glyph перед label (Claude sparkle, DeepSeek whale, Zen circles), inline SVG для tintability через `fill={color}`, без icon-библиотек. Brand color для active state — официальные HEX из brand guidelines (Claude `#DA7756`, DeepSeek `#4D6BFE`, OpenAI `#000`); если у brand'а нет official mark — выбрать цвет максимально отличный от соседних в палитре. Inactive state — neutral grey (`#888` text, `rgba(255,255,255,0.04)` bg, серая обводка): brand-цвета только для active, иначе все три pill'а светятся и юзер не видит выбор. Label — короткий wordmark (`Claude`, не `Anthropic Claude Code via subscription`), glyph + tint уже передают brand.

Структура данных — `PROVIDER_CATALOG: { id, label, tint, Icon }[]`, единый каталог. Иконка как `React.FC` (не path string), цвет как HEX в самой структуре — один edit чтобы поменять цвет brand'а или заменить glyph. Применимо к любой мульти-провайдерной фиче: image-generation между DALL-E/Midjourney/SD, payment Stripe/PayPal, LLM Anthropic/OpenAI/Google. См. `src/renderer/components/icons/ProviderIcons.tsx` (DeepSeek, Zen) + `CopySessionButton.tsx::ClaudeSparkle`, `PROVIDER_CATALOG` в `InfoPanel.tsx`.

## Geometric symmetry в spacing, не накопление margin/padding

Когда нужно ровное расстояние между двумя UI-блоками с визуальным разделителем посередине (line, dot, icon) — расстояние должно быть математически разложимо на симметричные половины, а не складывание margin от блока выше + padding внутри блока ниже + border-width разделителя. Шрам — между секциями AI SESSION и PROVIDER в InfoPanel поставил `mb-4` (16px) на верхний блок + `pt-3 border-t` (12px padding + 1px line) на нижний. Юзер вручную сложил отступы: *«сверху получается margin равен 12 пикселей. А потом ещё margin-bottom от второго компонента равен 16 пикселей. То есть у нас расстояние между ними должно быть 16 пикселей, в общем. И получается, посередине, на 8 пикселях должна отображаться разделительная полоса. У нас проблема в том, что к этому добавляется ещё padding»*. Вертикальный gap = `16 + 12 + 1 = 29px`, line не посередине, math не работает. Каждое следующее изменение требует подсчёта трёх слагаемых.

```jsx
<div className="mb-2">...верхний блок...</div>
<hr className="border-0 border-t border-[#2a2a2a]" />
<div className="mt-2">...нижний блок...</div>
```

Divider — own zero-height element с `border-t`, не часть нижнего блока. Симметрия `8 + 0 + 8 = 16px`, линия ровно посередине. Изменение gap на N — меняем только две цифры (mb/mt), не три. При чтении JSX gap-math очевиден без dev-tools: если нужно посчитать `mb + pt + border` чтобы понять расстояние — плохо. Когда divider должен быть частью блока — если разделитель семантически принадлежит одному из них (нижняя граница карточки внутри `Card`); но если разделитель между равными секциями — standalone лучше. См. `InfoPanel.tsx` AI SESSION / PROVIDER divider.

## Singleton listener для global events, не в conditionally-rendered компонентах

Когда компонент слушает global event (IPC от main, WebSocket, BroadcastChannel, document-level keystrokes, OS-level signals) и реагирует side-effect'ом которому всё равно показан ли компонент на экране (отправить следующий промпт в очереди, разлогинить юзера, обновить badge) — listener не должен жить в этом компоненте. Должен быть singleton hook на корне приложения. Шрам — PromptQueueOverlay первой версии содержал `useEffect` с `prevBusyRef` для отслеживания `claude:busy-state` edge transitions. Когда юзер переключался на другой таб → overlay рендерился по gate `effectiveActive` → React unmount → effect cleanup → ref пропал → следующий `busy: false` событие в фоне никем не обрабатывалось → авто-отправка очереди молча сломалась. Юзер: *«армил Run after, ушёл работать в gemini, вернулся — ничего не отправилось»*.

Если listener обрабатывает события которые могут происходить когда компонент скрыт → singleton hook. Если обрабатывает UI-state компонента который сам видим (hover, focus, scroll) → внутри компонента OK. Hook монтируется один раз на App root: `function App() { useGlobalRunner(); ... }`. Внутри держит state в `useRef<Map<key, value>>` — per-entity tracking без React state churn. Subscribes на IPC / WebSocket / store при mount, unsubscribes только при app unmount.

Похоже-но-не-оно: `useEffect` с `addEventListener` в leaf-компонентах — OK если listener связан с DOM этого компонента (focus, mousedown на элементе, IntersectionObserver). Снос компонента = снос его DOM = listener не нужен. `useEffect` слушающий per-entity state (например `claudeSessionId` конкретного таба) — OK, entity-id = scope этого компонента. См. `hooks/usePromptQueueRunner.ts` (слушает `claude:busy-state` IPC + Zustand store subscription, fires send-command / stop-ai-process независимо от того какая вкладка показана), конкретика — `fact-prompt-queue.md::Auto-runner — singleton hook, не в overlay`.

## Drag-state буфер: store-flush на mouseup, не на mousemove

Drag/resize-gesture пишет в local React state (или ref). В shared store (Zustand/Redux) и persistent storage (localStorage / IPC / SQLite) флушит один раз на `mouseup` / end-of-gesture. Не на каждое mousemove. Узнаётся по фразам *«движение какое-то дёрганное при drag'е»*, *«ползунок мигает»*, *«resize lagging»* — drag-handle следует за курсором, но визуально движение порвано на кадры. Наивный подход (`setStore` на каждом mousemove) ломается так: 60 mousemove/sec → 60 синхронных записей, каждая `setState` в Zustand → re-render всех подписчиков; если store-setter побочно делает `localStorage.setItem` + IPC — ещё synchronous I/O на каждом кадре; рядом стоит `ResizeObserver` на родителях — каждый re-render может re-trigger measure (см. секцию про body-observer для Portal-child) → re-render → measure → setState → re-render, feedback loop; drag handler читает `getBoundingClientRect()` из closure — каждый re-render обновляет closure → handler видит уже сдвинутый rect → расчёт нового положения сдвигается → jitter.

```jsx
const [dragPreview, setDragPreview] = useState(null);
const startDrag = (e) => {
  const start = { x: e.clientX, y: e.clientY, val: store.value };
  setDragPreview(start.val);
  const onMove = (ev) => setDragPreview(start.val + (ev.clientY - start.y)); // только local
  const onUp = () => {
    setDragPreview(curr => {
      if (curr !== null && curr !== store.value) store.set(curr);             // один flush
      return null;
    });
    window.removeEventListener('mousemove', onMove);
    window.removeEventListener('mouseup', onUp);
  };
  window.addEventListener('mousemove', onMove);
  window.addEventListener('mouseup', onUp);
};
const effectiveValue = dragPreview !== null ? dragPreview : store.value;
```

Применяется всегда при drag/resize UI-контролов где значения копятся в shared store с persist'ом: volume slider, color picker, drag-resize панелей, перетаскивание элементов с координатами — любой gesture где промежуточные значения не нужны другим компонентам, preview-state остаётся локальным. Graveyard двух итераций: throttle/debounce store-writes (~16ms) спасает persistent-storage от 60Hz записи, но не от re-render'ов — throttled write всё равно вызовет `setState`, подписчики re-render'ят, drag handler читает stale rect / новые координаты, jitter возвращается; `useRef` вместо `useState` для drag-preview — работает для значения, но рендер не обновится, ref не триггерит re-render, UI замораживается на стартовой позиции до mouseup. Только разделение preview-state и store-state даёт стабильность. См. `knowledge/fact-notes.md::Tab Notes Slideout::Drag-preview буфер` (`notesPanelSize` + `notesPanelOffsetY` копятся в `dragPreview` local state, flush в Zustand + localStorage + SQLite только на mouseup).

Три CSS-ловушки которые любой resize-блок ловит мимо store-логики и снаружи кажутся «store/handler не работает». Первая: card имеет `overflow: hidden` (нужен для `borderRadius` чтобы content не вылез за скруглённые углы), а handles нарисованы на `offset: -5px` от card-стенок — overflow обрезает handles, юзер промахивается мимо невидимой кликабельной зоны. Лекарство — промежуточный wrapper без overflow вокруг card, handles живут на нём, card внутри. Вторая: resizable content-блок с `flex: 1 + maxHeight: limit` даёт effective height равный `min(naturalContent, limit)` — при коротком content (5 строк notes, limit на 8) maxHeight никогда не достигается, drag-up меняет store но визуально ничего не происходит, юзер думает «ползунок не реагирует». Лекарство — `height: limit` напрямую (`flex: 0 0 auto`), блок занимает ровно limit пикселей независимо от content; внутри content скроллится через overflow. Третья: discrete-step преобразование во время drag (`Math.round(dy / lineHeight)`) превращает плавное движение мыши в рывки по lineHeight; ещё хуже когда то же `Math.round` стоит в store-setter — на mouseup live-preview хранил 5.487 строк, store принимает 5, height рамки прыгает на ~0.5 * lineHeight назад. Лекарство — store держит float, дискретная подача нужна только в Settings stepper (там `Math.round(value)` в `value`-prop, не в setter). См. `knowledge/fact-tab-preview-popover.md` (CMD+hover preview с resize handles ловил все три).

## Hover-подсветка resize handle через data-attribute, не JS

Resize handles обычно делают inline-style `onMouseEnter/onMouseLeave` для подсветки. Это ломается так: юзер тянет handle быстро, курсор уходит за пределы handle area → React `onMouseLeave` → подсветка пропадает → drag продолжается невидимо. После mouseup курсор оказывается **не** на handle (handle сместился вместе с рамкой) → `onMouseEnter` не стреляет → юзер должен сам подвинуть мышь чтобы заново получить подсветку. Узнаётся по фразе *«после отпускания пропадает выделение, мне нужно заново навестись на рамку»*.

Лекарство — `data-resize-handle-active='true'` на handle во время drag (паттерн из `react-resizable-panels`, by Brian Vaughn, 2025). Атрибут навешивается в `onMouseDown`, снимается в `onMouseUp`. CSS подсвечивает либо когда курсор над handle, либо когда атрибут стоит:

```css
.handle:hover,
.handle[data-resize-handle-active='true'] { background: rgba(99,102,241,0.4); }
```

После mouseup атрибут удалён → CSS-движок перепроверяет `:hover` для **новой** позиции курсора — если курсор оказался на handle (тянули в пределах), подсветка остаётся; если уехал — пропадает естественно. JS-эмулировать это бесполезно: pointer capture API подавляет `pointerover/leave` на других элементах, `setPointerCapture` не даёт «продолжающийся hover» под курсором. См. `knowledge/fact-tab-preview-popover.md::Resize handles` (5 handles на TabPreviewPopover: right/left/bottom + 2 угла, все управляются одним CSS-правилом).

## React StrictMode: functional updater вызывается дважды, side-effects теряют данные

`setState(prev => { sideEffect(prev); return next })` в React 19 StrictMode invokes функцию **дважды** для detecting impure functions. Если внутри updater'а присваивание внешней переменной (`captured = prev`), второй invoke с `prev = next` (результат первого) затрёт значение — `captured` окажется равен второму состоянию, не первому. Узнаётся по симптому «mouseup захватывает финальный preview, flush в store, рамка возвращается на старое значение» — captured получился `null` (после первого setState'а который вернул `null`) и `if (captured)` пропустил весь блок flush'а.

Лекарство — параллельный `useRef` зеркало state'а. Обёртка `setDragPreview` обновляет **и** `useState` (для render), **и** `previewRef.current` (для синхронного чтения снаружи setState):

```jsx
const [dragPreview, _setDragPreview] = useState(null);
const previewRef = useRef(null);
const setDragPreview = useCallback((next) => {
  previewRef.current = next;
  _setDragPreview(next);
}, []);
// На mouseup:
const captured = previewRef.current;  // прямое чтение, без updater'а
setDragPreview(null);
if (captured) store.flush(captured);  // setters внешним кодом, без side-effects в updater'е
```

Альтернативы которые **не работают**: `flushSync` (форсит commit DOM, но не помогает с double-invoke в updater'е); `useOptimistic` / `useActionState` (это для async server actions, не для sync local state); чтение `Zustand.getState()` (помогает если значение в store, но drag-preview обычно local React state, не в Zustand). Универсальное правило: **никогда не делай side-effects внутри `setState((prev) => ...)` updater'а** — функция должна быть pure, любой capture через external scope сломается под StrictMode. Тест: убери всё кроме `return newValue` и положи side-effect рядом (до или после `setState`). Если значение для side-effect зависит от latest state — храни параллельный ref.

## Hit-area > visual button: расширяй кликабельную зону за пределы видимой кнопки

Если на блоке есть один доминирующий action и видимая кнопка занимает малую долю площади блока (header секции, breadcrumb row, card title), оборачивай весь блок в кликабельный контейнер. Саму кнопку оставляй визуальным индикатором — `<span>` или `<div>` с `pointer-events-none`, цвет привязывай к hover-state контейнера, а не self-hover. Любая интерактивная дочерняя кнопка (✦ generate, ⚙ settings) получает `e.stopPropagation()` и марк-атрибут (например `data-..-interactive`), чтобы контейнерный onClick игнорировал клики по ней через `target.closest('[data-..-interactive]')`. Узнаётся по фразам *«я мажу мимо крошечной кнопки Open»*, *«здесь же видно что это про заметки — почему клик в шапку ничего не делает?»*: пользователь работает со смыслом блока (header = «заметки вкладки»), а не с пикселями кнопки, и каждый промах = трение.

Применимо когда на блоке один доминирующий action (если две независимые кнопки — Save и Delete — оборачивание ломает выбор), кнопка работает как индикатор/affordance а не носитель smart-state, и внутри блока нет других кликабельных элементов с противоречащим action'ом (если есть — закрывай их `data-..-interactive` + `stopPropagation`). Graveyard двух подходов: оставить кнопку как есть и добавить onClick на родителя — при наведении кнопка меняла цвет (свой `:hover`), а контейнер нет, либо наоборот, hover desync; растянуть кнопку на всю ширину (`flex: 1`) — визуально ломает иерархию, кнопка перестаёт выглядеть как кнопка, label рядом теряется. Решение — один источник hover-state (родитель), кнопка читает его как prop. См. `knowledge/fact-notes.md::Tab Notes Slideout::Header hit-area` (весь header «Заметки вкладки» в InfoPanel кликабелен, Open-чип стал `<span pointer-events-none>`, ✦ generate-description имеет `data-notes-header-interactive` + `stopPropagation`).

## Controlled editor: пометь свои dispatch'и аннотацией

Когда два UI экземпляра делят один store-source через reactive selector и каждый отдаёт обратно через `onChange` — программный sync должен быть отличим от пользовательского ввода. Иначе echo превращается в бесконечный pingpong; симптом — при печати в одном из двух editor'ов которые подписаны на одно поле, крах с `Position N is out of range`, `RangeError`, или просто видимый «прыжок» текста между состояниями.

Программный `view.dispatch` (CodeMirror), `editor.replaceRange` (Monaco), `setSelection` (contenteditable) — всегда помечается через transaction annotation / metadata / `userEvent`. Listener эту метку видит и не вызывает `onChange` callback наверх. Контринтуитивная часть — clamp selection перед dispatch'ем (`safeAnchor = min(anchor, newLen)`) корректен внутри одного диспатча, но не лечит источник: echo onChange запустит новый цикл из другого instance, краш произойдёт не в твоём dispatch'е, а во внутреннем CodeMirror state update который уже работает с устаревшим pending selection. Тест-симптом для будущего AI: одинаковая длина content'а 4-5 раз за 30ms через alternating sources (`tab-notes` ↔ `tab-notes-slideout`) = ping-pong, ищи echo onChange. См. `knowledge/fix-codemirror-controlled-editor.md` — конкретное решение через `Transaction.userEvent: 'external-sync'` для пары InfoPanel inline + TabNotesSlideout.

## State-mirror через useState+useEffect — ловушка stale read в async handlers

Когда компонент мирорит reactive-state в локальный `useState` (типичный паттерн `const [x, setX] = useState(''); useEffect(() => setX(liveX), [liveX])`), он получает два невидимых контракта одновременно: (1) локальный snapshot **отстаёт от store на один кадр** — между store update и applied effect; (2) в async-callback'ах внутри компонента `x` **зафризен в closure на момент создания handler'а** — после первого `await` он не обновляется автоматически.

Если внутри такого компонента есть async-handler, который **пишет обратно в store** на основе своего же mirror'а — это concurrent write race. Параллельный writer (другой компонент, другой инстанс, фоновый процесс) может обновить store за время await; mirror всё ещё видит до-await версию; handler собирает «новое значение» поверх старого и затирает свежие правки. Не повредить нельзя — даже если очистить mirror в начале handler'а, store успеет уйти вперёд за время первого `await fetch(...)`.

Правило: не мирорить reactive-store в локальный `useState` если нет конкретной причины (например, оптимизация неконтролируемого input'а с debounce). Читать напрямую через reactive selector в render-цикле. Внутри async-handler — снимать актуальный snapshot **после каждого await** через imperative API store: `useStore.getState()` для zustand, `useRef` обновляемый в effect для случаев когда subscribe нельзя. Конкретный пример — InfoPanel mirror'ил `tab.notes`, `handleGenerateDescription` после `await` затирал параллельные правки слайдаута; см. `knowledge/fix-infopanel-tabnotes-mirror.md`. Это тот же класс что `knowledge/fix-stale-closure-timeline.md` (closure-фриз в Timeline async-handler), просто проявление другое: там findIndex возвращал -1, здесь сначала перезаписывал контент.

## Opt-in affordances через модификатор-клавишу: noise floor

Большинство кнопок UI не нуждаются в tooltip'е. Иконка + контекст → action понятен. Tooltip на каждой кнопке — это шум, который пользователь начинает воспринимать как баг («почему всё подсвечивается?»). Юзер сформулировал прямо: *«тултипы — пиздец, везде шумят»* и начал отключать их вручную в каждом файле через субагента до того как был сформулирован принцип. Explanation overlay (tooltip, help popover, keyboard-shortcut hint) по умолчанию скрыт; появляется только при зажатой модификатор-клавише (`Cmd`/`Alt`/`Ctrl`); опт-аут — флаг `always` для критичных мест где подсказка обязательна.

Реализация на уровне global state: module-level subscription set + один pair keydown/keyup listener; все Tooltip instances читают одно `cmdHeld` state через subscriber-pattern (не каждый со своим хуком — 100+ listeners на странице). При зажатии Cmd над уже-hover'енной кнопкой tooltip появляется мгновенно, отпустил — исчезает. См. `src/renderer/components/UI/Tooltip.tsx` с props `delay`, `disabled`, `always` (default false), global cmd state через module-level `Set<(v: boolean) => void>` подписчиков.

## Mouse-armed pattern для list popovers (Cmd+P / Cmd+/)

Команда-палитра, открытая клавишей при стоящем курсоре, не должна активировать item под курсором — это кража фокуса, пользователь не двигал мышью, не ждёт hover-эффекта. Симптом — нажимаешь Cmd+/, курсор случайно оказался над пунктом «Bold» → palette открывается с уже выделенным Bold вместо первого item. Юзер дважды сформулировал сам: *«у нас есть фича в Cmd+P которая ждёт move курсора. То же самое нужно для Cmd+/. Если курсор уже стоял — у меня этот элемент выделяется»* — самосформулированный принцип, записываем.

CSS `:hover` подсветка работает только после первого `mousemove` внутри popup'а: до этого активный item определяется только стрелками / клавиатурой / `activeIndex` от open-логики.

```css
.cm-command-palette.mouse-armed .cm-command-palette-item:hover { ... }
```
```typescript
const armMouse = () => {
  palette.classList.add('mouse-armed');
  palette.removeEventListener('mousemove', armMouse);
};
palette.addEventListener('mousemove', armMouse);
```

См. `gt-editor/packages/markdown-editor/src/plugins/contextMenu.ts::showCommandPalette` + CSS-правило в `editor.css`. Тот же паттерн в VSCode Cmd+P, Sublime Cmd+P, любой keyboard-first launcher.

## Сегментированная капсула: persistent bg, hover = только цвет

Когда 3+ связанных action'а читаются как «один контрольный элемент» (copy session ID / Claude Stop / refresh timeline → один блок управления текущей сессией), все они должны иметь общий фон всегда, не на hover; hover меняет только цвет текста/иконки (affordance кликабельности без изменения геометрии или fill); сидеть вплотную друг к другу через сегментированные углы (`rounded-l` / no radius / `rounded-r`), не через `gap` — gap делает их визуально независимыми. Юзер прямо возмутился: *«у всех трёх кнопок должен быть бэкграунд, ёбаный в рот»* — чувствует визуальную разрозненность когда фон появляется на hover вместо постоянного. Это не вкусовщина, нарушение перцептивной целостности единого контрольного элемента.

Одиночная утилитарная кнопка (cancel ✕, settings ⚙) может иметь прозрачный фон с появлением bg на hover — она не часть капсулы. См. `panels/InfoPanel.tsx::SessionActionChip` — Stop/Continue chip в triplet'е с ⎘ (copy ID) и ↻ (refresh) имеет `backgroundColor: 'rgba(0,0,0,0.55)'` всегда, на hover меняет только `color`. Stop добавляет faint red wash (`rgba(239,68,68,0.18)`) — единственное исключение, destructive action.

## Один клик = одно изменение, без «логичных» побочных эффектов

Когда у компонента есть несколько сегментов с разной семантикой (split-button, segmented toggle с двумя half'ами, multi-action menu) — клик по сегменту меняет только то что этот сегмент представляет. «Удобные» автоматические side effects вида *«логично же включить родителя если кликнул на дочерний»* запрещены. Юзер сам сформулировал принцип спокойно — самый сильный сигнал для methodology: *«у нас должно быть по философии всё детерминировано. Если суб-агенты выключены и я кликаю на правую часть — у меня меняется правая часть, при этом сам суб-агент не включается»*.

В split-чипе `sub-` левая половина — toggle on/off родителя; правая (`result` / `full`) — меняет только preferred mode независимо от того включён родитель или нет. Если родитель выключен и юзер кликает по правой — preferred mode меняется в state, видимый label обновляется, родитель остаётся off; когда юзер решит включить через левую — родитель активируется в текущем preferred режиме. «Помог юзеру одним кликом сделать два изменения» = предсказание намерения; если предсказание неверное (юзер хотел сначала переключить режим, потом подумать включать или нет) — он не может откатить только половину, кликать обратно дважды. Детерминированный one-click = one-change всегда обратим одним же кликом. Для обычных кнопок (одна семантика — один action) правило вырождается в тривиальное; критично именно для multi-segment контролов где у юзера mental model «я меняю эту конкретную часть». См. `panels/InfoPanel.tsx::sub-pill` — split `sub-` + `result`/`full`, состояние `subPreferred` хранит preferred mode независимо от `includeSubagentResult`/`includeSubagentHistory` флагов.

## State display = текущее состояние, не предсказание клика

Связано с предыдущим, но отдельно: что показано на элементе сейчас = его реальное состояние, а не «что станет после следующего клика». Любой hover-эффект, который меняет label (а не цвет/тень/курсор) — нарушение. Юзер прямо: *«если у меня написано „sub full“, то при наведении почему-то меняется на „result“ и происходит непонятное дёрганье. Убери эту хуйню — должно меняться только при клике»*. Юзер не может прочитать текущее состояние потому что hover мерцает его на предсказание.

Hover может менять цвет фона/текста (affordance кликабельности), курсор (`pointer`, `ns-resize`), тень/border/иконку-вспышку (фокус). Никогда — текстовый label, иконку обозначающую state, цифру счётчика, выделение в multi-select pill. Разница между «текущее» и «предсказание» должна быть в modal-affordance (отдельный tooltip *«Click to switch to full»*), не в самом контроле, иначе юзер при наведении видит state X, при уводе — state Y, теряет ориентацию: *«а что у меня сейчас выбрано?»*. См. `panels/InfoPanel.tsx::sub-pill` — `rightLabel = isFull ? 'full' : 'result'` всегда показывает реальный mode, hover не подменяет.

## Dropdown ≠ modal: не блокируй UI под собой, click-outside закрывает

Плавающий resizable панель/popover должен быть dropdown (как Rewind menu, как Cmd+P), не modal (как Settings, как Edit Project). Различие — у dropdown нет backdrop'а либо invisible click-trap, UI ниже виден и читаем, mental model «временная подсказка/панель»; у modal есть scrim, UI ниже затемнён до нечитаемости, mental model «самостоятельный диалог», z-index поверх всего. Если панель сосуществует с основным UI (юзер продолжает видеть и читать контекст под ней) — это dropdown, никакого backdrop'а; если требует решения перед продолжением работы (settings, confirm, primary task entry) — modal с scrim. Юзер прямо назвал mental model и эталон: *«у нас не должно меняться прозрачность фона, это не модалка, это именно выпадающее меню. Как в случае с Rewind»*.

См. `TabNotesSlideout` (dropdown без backdrop'а, click-outside закрывает) vs `SettingsModal` (modal с backdrop'ом). Различие визуально подсказывает юзеру какая mental model применима.

## Persistence-class для dev settings: SQLite, не localStorage

Любая UI-настройка которая должна переживать смену dev environment (vite-порт меняется → новый origin → localStorage обнуляется) обязана идти в SQLite или эквивалент source-agnostic persistence, не в origin-bound storage. Юзер сразу указал хранилище: *«размеры сохраняются в базу данных, то есть размеры будут единые»* — требование, не догадка. Корневая причина — в dev-режиме vite picks случайный порт (5181 / 5182 / 5183), у каждого свой origin → свой localStorage bucket. Юзер настроил высоту панели на одном порту, перезапустил — порт другой — настройки нет. На production порт не меняется (file:// origin), баг невидим, но dev-workflow страдает каждый перезапуск.

Решение — universal mirror на этапе boot до Zustand initializer'ов: synchronous IPC `app:hydrateLocalStorageSync` тянет все `noted-terminal-*` ключи из SQLite → пишет в localStorage до того как Zustand factories читают (factories синхронны при модуль-import); monkey-patch `Storage.prototype.setItem` / `removeItem` фильтрует по префиксу → synchronous IPC `app:mirrorLocalStorageSync` → SQLite. После этого никакая Zustand-factory не нуждается в правке: legacy `localStorage.setItem(key, value)` автоматически зеркалится. Тест-симптом для будущего: «настройки сбрасываются после перезапуска dev» = origin-shift, не баг store; лекарство — proxy через SQLite. См. `src/renderer/utils/persistedStorage.ts::bootstrapPersistedStorage()` + IPC `app:hydrateLocalStorageSync` / `app:mirrorLocalStorageSync` в `src/main/main.js`.

## Layout reservation для toggle-able children: высота = max, не current

Если внутри контейнера есть children которые могут включаться/выключаться (toggle pills, conditional badges, dynamic list with single item visible) — высота контейнера должна быть зарезервирована под максимум, не под текущее состояние. Иначе toggle двигает соседние секции, юзер при клике видит layout shift. Юзер сформулировал спокойно: *«сделай ограничение по высоте чтобы не было такого что при включении subagents у меня менялась высота сайдбара»* — спокойная формулировка инженерного правила, тоже сигнал.

Для row/grid с flex-wrap и conditional children — `min-height` = высота под максимально возможный набор, `align-content: flex-start`. Контейнер занимает свою максимальную высоту всегда; toggle меняет только видимость chip'а внутри, не реально-занятое пространство. Контр-аргумент «лишнее пустое место»: да, если выключены все conditional children — внизу пустота на 26px. Приемлемая цена за стабильность layout: альтернатива (collapse под current) ломает muscle memory — юзер целится в кнопку под секцией, она прыгает на 26px вверх в момент клика, промахивается.

Min-height не нужен если conditional children не редактируются юзером внутри этого UI flow (badge «unread N» растущий асинхронно от server-push), а компонент сам редко в фокусе — допустимо позволить layout shift. Правило критично для interactive UI где юзер активно манипулирует toggle'ами в этой же области. См. `panels/InfoPanel.tsx::markers-row` под Copy Session — `minHeight: 26` для двух wrapped рядов chip'ов, чтобы включение subagent/fork chips не сжимало КОНТРОЛЬ секцию ниже.

Тот же принцип в горизонтальном измерении для **adjacent panels** (master-detail flyout, split-pane, sidebar + main). Когда правая панель условно скрывается (контент не относится к ней), её ширина бронируется на уровне **обёртки**, а внутренний content-блок рендерится условно. Иначе flex/grid пересчитает раскладку и левая панель уползёт к центру overlay'а — юзер двигает selection ↓ и видит как «основное окно стыкается в середину», как сформулировал юзер при обзоре prompt-picker'а. Реализация — `<div style={{ width: RIGHT_W, flexShrink: 0 }}>{condition && <Panel />}</div>`: внешний div держит слот, внутренний `<Panel />` рендерится только при условии. Конкретика — `knowledge/fact-prompt-picker.md::Layout reservation`.

## Hover-isolation для split-button: подсвечивается то на чём курсор, не весь блок

Split-button / segmented control с несколькими интерактивными половинами должен подсвечивать только ту половину над которой стоит курсор, не весь блок целиком. Каждая половина — независимая hover-зона со своим affordance. Узнаётся по фразам: *«у меня должно выделяться левая часть, не пропадать всё выделение. Так же, как у остальных элементов — просто выделение, ховер-эффект, смена цвета. И разделение на левую и правую часть»*. Юзер навёл курсор на левую половину sub-pill, ожидал увидеть подсветку левой части — увидел исчезновение подсветки на обеих. Хуже чем неинформативный UI: misleading hover.

Каждая половина — отдельный `<button>` с собственным `:hover` / `onMouseEnter`/`Leave`, не один parent-handler менеджащий подсветку через state. Если есть «preview off» эффект (hover слева → весь блок гаснет, обозначая «click → off») — это специальный case, отключён по умолчанию и явно опт-инен. Hover-feedback изолированный по сегментам = mental model «кнопка под курсором кликабельна»; cross-segment dimming ломает эту модель. Контр-аргумент «hover left = preview off — полезный hint» — false economy: юзеру удобнее явный tooltip «sub off» при hover на левую часть, чем «обе половины тускнеют без объяснения». Tooltip — модальная affordance, dimming — нелокальное состояние. См. `panels/InfoPanel.tsx::sub-pill` — две `<button>` (`sub-` + `result`/`full`), у каждой свой `hover:opacity-80`; cross-segment preview-dimming убран после возмущения.

## Координация overlays: primary modal открывается → secondary dismissable панели закрываются

Когда в UI могут одновременно жить modal и dropdown-style панели (slideout, popover, persistent panel), и юзер открывает modal — secondary панели должны сами дисмиссить себя. Не «остаться висеть позади backdrop'а», не «остаться поверх modal'и и блокировать его». Юзер сформулировал нейтрально: *«при открытии настроек у меня автоматически должна эта модалка закрываться»* — требование, сигнал methodology.

Primary modal эмитит событие при открытии (`window.dispatchEvent(new CustomEvent('settings:opened'))`); secondary панели слушают в своих `useEffect`-listener'ах и закрывают себя:

```ts
useEffect(() => {
  if (!isOpen) return;
  const onSettingsOpened = () => handleClose();
  window.addEventListener('settings:opened', onSettingsOpened);
  return () => window.removeEventListener('settings:opened', onSettingsOpened);
}, [isOpen, handleClose]);
```

Через event, а не через store: modal'и обычно managed как local React state (`useState`), перенос в store ради этого паттерна — over-engineering, event-bus легче и не размывает ownership state. Контр-вариант «secondary поверх modal'и» допустим только для связанных контролов (tooltip над modal-кнопкой, autocomplete над modal-input'ом); для независимых панелей (notes slideout vs settings modal) — закрывать secondary. См. `App.tsx::setSettingsOpen` эмитит `settings:opened` при transition false→true; `TabNotesSlideout` подписан и закрывает себя. Без этого backdrop SettingsModal накрывал slideout наполовину — визуальная грязь.

## Удаляй workaround сразу после upstream-fix

Локальный workaround вокруг чужого бага (npm библиотека, OS API, browser engine, downstream сервис) имеет цену — поверхность для собственных edge cases. После того как upstream устранил root cause, оставлять workaround «как defence-in-depth» категорически нельзя: он перестаёт защищать от чего-либо реального и продолжает копить свои баги на новых input patterns.

Узнаётся когда код, работавший стабильно несколько месяцев, начинает падать в новых сценариях — обычно при смене паттерна входных данных (новый протокол, размер чанков, частота вызовов). Это не регрессия workaround'а, это его изначальная хрупкость, которая не проявлялась пока root cause был на месте. Конкретный шрам: наш sync-frame splitter работал стабильно, пока Claude Code v2.1.101 не починил CSI 3J upstream; через несколько недель появились субагенты (Task tool) → мелкие быстрые PTY-чанки → BSU/ESU разрезались между чанками → splitter промахивался → каша символов на экране у юзера.

При появлении upstream-fix удалить всю локальную обвязку, даже если кажется что «может пригодится». Удаление цепное: workaround обычно тянет за собой подпорки (refs, флаги, scroll-snap, race-condition guards) — все они существуют только потому что workaround сам создаёт побочные эффекты, после удаления workaround'а подпорки тоже снимаются. См. `knowledge/fix-terminal-jitter.md::Upstream fix v2.1.101` — sync-frame splitter + protectedWrite + 10 refs + cursor-based check + INPUT_ZONE=6 + onData→ref clear удалены каскадом после комментария Anthropic «Fixed in v2.1.101».

## Tool call = карточка, не сообщение. Шапка одной grid-линией

В AI-чатах tool calls (Bash, Read, Edit, Glob, MCP-вызовы) семантически не часть assistant-сообщения, а отдельные карточки со своим жизненным циклом (running → done/error), своим collapse-состоянием и своими affordances. Стилизовать их как inline-сообщение — терять различие между «модель думает/говорит» и «модель выполнила действие».

Шапка карточки — одна линия flex'ом, не stack из абзацев. Элементы (chevron-toggle, status-dot, tool-icon, UPPERCASE label, badge со счётчиками типа `+5 −2`) выравниваются `flex items-center gap-2` в одной строке с фиксированной `min-h`. Путь / команда / query идёт отдельной строкой ниже, моноширинно, во всю ширину карточки, wrap'ается, но никогда не truncate'ится. Шапка остаётся стабильной по высоте (28px) независимо от длины пути → click-baseline не плывёт. Magic offsets `mt-[2px]` / `mt-[3px]` под каждый элемент чтобы выровнять «по верху иконки» — типичный антипаттерн, через релиз перестаёт выравнивать (изменился размер шрифта → magic offset устарел).

Truncate команды/пути в шапке (`truncate max-w-[300px]`) — антипаттерн: у пользователя единственный реальный вопрос «какой именно файл / какая именно команда», обрезать ответ значит сломать осмысленность всей карточки. Если содержимое не вмещается — выноси в отдельную строку с wrap, не truncate. См. `ToolCard` каркас + `BashCard` / `ReadCard` / `EditCard` / `GenericToolCard` в `knowledge/fact-claude-sdk-tab.md::Tool-call rendering`. Применимо в любом chat-UI поверх tool-use API.

## Composer внутри scroll-flow, не sticky overlay

Input в chat-UI — последняя строка scroll-flow, не плавающий overlay над контентом. `position: sticky` / `position: fixed` для composer'а создаёт визуальный конфликт: при скролле вверх composer остаётся на экране и накрывает контент (последние сообщения, footer'ы, кнопки expand). Пользователь не может «уйти» от input'а, он всегда в кадре, превращается в визуальный шум.

Composer-блок — child scroll-контейнера с `flex-shrink: 0` (не сжимается при overflow). Перед ним messages-div с `flex: 1` (растягивается на свободную высоту). При коротком чате `flex: 1` пушит composer к низу — визуально прижат. При длинном чате composer уходит за viewport вместе со scroll'ом — пользователь не видит его пока не доскроллит до конца. То же поведение, что в Claude Code TUI: input буквально последняя строка терминала, не оверлей.

Антипаттерны: `sticky bottom-0` на composer внутри `overflow: auto` контейнера выглядит правильно для коротких чатов, но при длинном создаёт overlay-конфликт. Вытащить composer наружу scroll-контейнера тоже не выйдет если фреймворк (assistant-ui, langchain-UI) требует input внутри Viewport-context — primitive выдаст runtime error на mount'е («must be used within ThreadPrimitive.Viewport»). См. `knowledge/fact-claude-sdk-tab.md::Composer in-flow + assistant-ui constraint`.

## flushSync + sync layout-read для стабильного scroll при collapse

Когда программно раскрываешь/сворачиваешь блок выше текущего viewport'а — содержимое во viewport'е сдвигается на дельту высоты, и глаз ловит дёрг между двумя кадрами: первый paint'ит новое состояние без компенсации, второй — со скорректированным scroll'ом. Решение — компенсация в том же frame'е что и paint.

До state-mutation запомнить `anchor.getBoundingClientRect().top` + флаг `wasAtBottom = scrollHeight - scrollTop - clientHeight <= 4px`. Затем `flushSync(() => setState(...))` синхронно commit'нуть React-update + recalc layout (браузер ещё не paint'ил). В том же tick'е прочитать новый `anchor.getBoundingClientRect().top`, посчитать `delta = newTop - oldTop`, скорректировать `scroller.scrollTop += delta` — браузер paint'ит один кадр с финальным состоянием.

Не `requestAnimationFrame × 2` — между первым и вторым rAF браузер успевает paint'нуть промежуточный кадр (state применён, scroll не скорректирован), один frame ~16ms = отчётливо видимый дёрг. Не `useLayoutEffect` — работает только если хук имеет свой state на изменении которого можно повесить layout-effect; generic toggle-хук принимающий callback от owner-компонента не знает когда state изменится, flushSync даёт ту же гарантию изнутри click-handler'а. wasAtBottom rule: если до клика пользователь был у самого низа (4px tolerance) — после expand'а scroll догоняет новый низ, не держит anchor стабильным; иначе composer/последнее сообщение уходят за viewport. 4px — типичный размер случайного offset'а (scroll inertia, partial pixels): больше — выходит из «у самого низа», меньше — флапает на pixel-rounding. См. `useStableCollapseToggle` в `ClaudeSDKTab.tsx`, применён ко всем collapse-toggle'ам (Thinking, ToolCard, FullContentToggle, DiffLines, CollapsibleText).

## Smart cancel: outcome зависит от того, что streaming уже произвёл

«Отмена» async/streaming-операции — не один сценарий, а два, выбор делается по факту наличия частичного результата. Streaming произвёл контент (хоть какой-то text/thinking/tool_call) → сохранить как есть, input/композер очистить (turn закрыт), юзер может потом нажать `Edit/Repeat` на своём сообщении если хочет переделать. Streaming не произвёл ничего (отмена в первые мс, до первого assistant-чанка) → сделать вид что turn'а не было: удалить user-сообщение из истории, вернуть его текст в input (готовый к редактированию), откатить запись в журнале/JSONL если уже легла.

Антипаттерн «всё в историю» (оставлять user-сообщение без ответа при мгновенной отмене) превращает чат в кладбище незавершённых turn'ов: юзер не помнит «я нажал отправить или отменил», видит свой prompt висящим без ответа, начинает гадать не упало ли сразу. Антипаттерн «всё откатить» (удалять user-сообщение даже когда ответ уже частично пришёл) теряет работу assistant'а — думал, искал, начал писать; лучше «незавершённый turn в истории» чем «слил 5 секунд compute и не могу вспомнить о чём был запрос».

Граница «хоть какой-то контент» — самый дешёвый детектируемый сигнал: `streaming-placeholder.text || .thinking || .toolCalls.length` — три байта проверок, точно отражает «турн начался физически»; альтернативы (timeout-based, токен-based) лгут на медленных моделях. См. `knowledge/fact-claude-sdk-tab.md::Smart Cancel`.

## Reasoning/thinking: italic + outlined, не dim grey block

AI thinking/reasoning рендерится как outlined-контейнер с italic body-size текстом, не как «приглушённый grey блок». Italic — главный семантический сигнал «это не финальный ответ, это process»; border + лёгкий tinted-bg — визуальное отделение от prose. Dim-grey текст на dim-background сливается на тёмной теме: пользователь не видит блок и думает «модель не думала», хотя думала.

К той же конкретике сошлись Vercel AI Elements, Zed Agent Panel, assistant-ui Chain of Thought: контейнер `rounded-md border border-white/10 bg-white/[0.02]` (тёмная) или `border-zinc-200 bg-zinc-50/50` (светлая); trigger-кнопка — clickable header с brain-иконкой и лейблом «thinking / Thought for Ns»; раскрытый body — `text-sm italic`, цвет `text-muted-foreground` но **с body-size**, не XS (italic делает работу, не размер); опционально авто-collapse через 1s после streaming end чтобы законченный reasoning не съедал внимание у финального ответа.

Антипаттерн `<details><summary>thinking</summary><pre class="text-gray-500 text-xs">...</pre></details>`: серый XS текст в `<pre>` на чёрном сливается, читается как комментарий к коду, не как процесс мышления. Удалить XS, оставить sm+italic. См. `knowledge/fact-claude-sdk-tab.md::Reasoning rendering`.

## Hover-action-bar снаружи bubble, якорь к edge bubble (не к viewport)

Hover-affordances над user-сообщением в чате (`Edit`, `Repeat`, `Copy`, `Reply`) рендерятся снаружи bubble, прижато к его краю. Якорь — bubble's own edge (`right: 100%` относительно bubble), не viewport-absolute (`top-right` относительно окна). Action-bar внутри bubble (`absolute bottom-2 right-2`) накладывается на текст — при длинном сообщении с переносом строк последняя строка частично перекрыта кнопками, ухудшение читаемости, пользователь «прокручивает глазами вокруг кнопок». Снаружи — bubble остаётся чистым контентом, кнопки в whitespace.

Если якорь к viewport (`top-right` окна), action-bar отрывается от своего сообщения визуально: при широком чате плавает где-то справа, не связан с конкретным bubble. Якорь к right-edge bubble (`right: 100%` для right-aligned user-сообщений, `left: 100%` для left-aligned assistant) держит affordance в зоне внимания того сообщения к которому относится. В Slack/Discord старых версий floating action-bar был в правом верхнем углу сообщения прибит к viewport — на широких экранах глаз теряет связь между bubble и его действиями. См. `knowledge/fact-claude-sdk-tab.md::Edit/Repeat anchor`.

## Action-карточки уже prose: отступ справа = scroll-зона + визуальное разделение

Карточки действий (tool calls, thinking-блоки, attachment cards, expandable artifacts) уже по ширине чем окружающая prose ассистента, на 50-80px справа. Не заполняют полную ширину message-bubble. Три причины: scroll-зона для мыши (внутри карточки свои scroll-области — code-блок, diff, output; если карточка fill-width, scroll-event на right-edge либо ловится внутренним scroll'ом, либо main — непредсказуемо; зазор справа гарантированная зона для main scroll'а); визуальная грамматика (prose ассистента занимает полную ширину сообщения, action-карточки — нет; глаз мгновенно различает «речь» vs «действие/артефакт» по контуру без чтения содержимого); hierarchy reading (action-карточка семантически вложена в ответ ассистента — уже ширина = «отступ-вложенность», как indent в коде; полная ширина читалась бы как «равный по статусу элемент»).

В проекте `mr-[60px]` на root `ToolCard` и `ReasoningPart`. < 40px — глаз не успевает зафиксировать разницу; > 80px — карточки выглядят «брошенно слева», теряется горизонтальный ритм с prose; 60 — sweet spot, хорошо читается на ширинах 700-1400px. Применимо к tool call cards в Cursor, attachment-blocks в Slack/Discord, expandable artifacts в Claude.ai, code-cards в ChatGPT (canvas-mode mini-cards) — везде где есть семантическое различие «prose vs action/artifact». Антипаттерн «все блоки fill-width для использования места по максимуму»: места становится больше, но читаемость структуры падает — action-карточки сливаются с prose в одну плоскость, глаз парсит по содержимому (есть chevron — карточка, нет — текст), вместо парсинга по contour.

## UI-тематический font-size наследуется от пользовательской настройки, em для всех потомков

Когда у приложения есть глобальная настройка «размер шрифта терминала / редактора / чата» — все вложенные UI наследуют её через единственную точку (root `style={{ fontSize: ${px}px }}`). Все вложенные размеры — em, не px. Cmd+/− на тулбаре меняет одну переменную, всё дерево пересчитывается само. Если в коде разбросано `text-[13px]`, `text-[11px]`, `text-[12px]` — настройка ничего не меняет (хардкод побеждает наследование); перевод `text-[Npx]` → `text-[N/13em]` (где 13 — base) делает дерево пропорционально-чувствительным к настройке.

Не работают три альтернативы: CSS variable `--base-size` + `font-size: var(--base-size)` требует `var()` в каждом утилитарном классе и Tailwind 4 не дружит; React-context + provider даёт лишний re-render всего дерева, не нужен — browser сам каскадит font-size; JS-перерасчёт всех `text-[Npx]` на render невозможен (Tailwind компилит в статические классы). Работает один `<div style={{ fontSize: px }}>` на корне области + `text-[Nem]` везде.

Подводный камень — inline styles библиотек: SyntaxHighlighter / react-markdown / CodeMirror принимают `customStyle={{ fontSize: '12px' }}` (не Tailwind, но em там тоже работает: `fontSize: '0.92em'` подцепит base из родителя через CSS-каскад). Не забыть переписать и эти inline-styles, иначе code-блоки не масштабируются. См. `knowledge/fact-claude-sdk-tab.md::Font-size inheritance` — SDK-таб наследует `useUIStore.terminalFontSize` через root style, все `text-[Npx]` → `text-[Nem]` (42 замены), `customStyle.fontSize` → `'0.92em'`.

## UI vocabulary ≠ API vocabulary: говори в терминах пользователя

Лейблы в UI должны быть на словаре пользователя, не на жаргоне API. Технические термины SDK / провайдера (`adaptive`, `async`, `idempotent`, `cache_creation_input_tokens`) попадают в UI один раз когда разработчик скопировал из docs — и висят там годами, заставляя гуглить что они значат. Юзер: *«у нас нет режима как adaptive, у нас effort — это и есть режим thinking. Сделай переключатель on/off»*. Юзер не различает adaptive vs effort, для него это один концепт «модель думает или нет». API даёт две независимые ручки (`effort: high` + `thinking: {type: 'adaptive'}`), но в UI нужна одна — on/off — а effort живёт в своей пилюле как «depth».

Перед добавлением API-параметра в UI спроси «как пользователь это назвал бы?», не копируй имя поля. Если два API-параметра отвечают одной mental model — слепи их в один UI-контрол (toggle / pill) и преобразуй на отправку. Внутренние enum'ы хранятся как пришли из SDK (`adaptive`/`disabled`) — это transport-layer; UI-state живёт отдельно: `thinking: boolean` для toggle, преобразование в момент сериализации. Антипаттерн «UI как зеркало API» — `[ Thinking: adaptive | enabled | disabled ]`, юзер спрашивает «adaptive это enabled или нет?». Правильно — `[ Thinking: on | off ]`. См. `knowledge/fact-mobile-web.md::Params header pill` — `params.thinking === 'disabled'` (SDK transport) → отображается `off` в позиции effort-пилюли, не отдельная пилюля «adaptive».

## Status indicator: signal-on-change, не permanent label

В любой карточке с lifecycle (running → done/error) status-индикатор существует только для не-default-состояний. Default success — implied отсутствием badge. Permanent `done` лейбл = visual noise: юзер уже не сомневается что прошло когда видит result. Юзер прямо: *«мой MCP в конце отображается done, какой-то done блять нахуй нужен, занимает место по ширине непонятно для чего»*. Done badge не несёт информации — все три источника (зелёная точка, отсутствие spinner'а, наличие result-блока) уже говорят «успех».

Только `running` / `error` рендерятся как явные badges, success — отсутствие. Цвет status-dot уже несёт информацию (red/orange/green), не нужно дублировать в текст. Связано с `Brand identity = icon + color, не текст` — та же экономия, информация одним каналом, не тремя.

## No redundant dismiss control: backdrop уже закрывает

В ActionSheet / bottom-sheet / popup с backdrop'ом отдельная кнопка «Cancel» внизу избыточна. Backdrop-tap — универсальный escape который пользователь моторно ожидает; явная кнопка занимает место и затрудняет восприятие основного списка опций. Юзер прямо: *«у нас уже оверлей есть, клик по оверлею так и так закрывает меню — Cancel убери»*. Каждая ActionSheet с Cancel внизу заставляет глаз сканировать на один пункт больше (важно когда у списка 3-4 опции, а Cancel становится 5-м).

Backdrop click → dismiss; drag-handle (если sheet swipeable) → drag-down dismiss; Esc (desktop) или swipe (mobile) → dismiss. Явная Cancel только когда backdrop не закрывает по дизайну (destructive confirm) либо внутри sheet идёт асинхронная операция и нужна одна точка остановки. Связано с `Click-outside как universal escape` — там общий принцип, здесь конкретное следствие для action-sheet'ов.

## Visible disabled > hidden для roadmap-кнопок

Placeholder-кнопки будущих фич рендерятся как disabled visible (полупрозрачные, не клик), не скрытые до релиза. Visible disabled — коммуникация «эта возможность планируется» без open ETA. Симптом нарушения — юзер запросил composer-row [+] [🎤] [📚] [↑], первые две (image attach, voice input) ещё не реализованы. Hidden — пользователь не знает что фича вообще существует в roadmap, спросит спустя месяц «а можно добавить голос?». Disabled — сразу видит «оно будет», не пишет лишний feature request.

Disabled state — `opacity: 0.4`, цвет иконки `#3a3a3a` (тёмная тема) или `#bbb` (светлая), `cursor: not-allowed`, no `:active`. Опционально tooltip «coming soon», но не обязательно — иконка сама говорит. Не ставить ярких индикаторов «soon!» или badge'ей: это agressive marketing, а disabled — нейтральный roadmap hint. «Вернёмся когда зарелизим» (скрыть кнопки до релиза) — антипаттерн: спрятанная фича не существует для пользователя, момент появления будет surprise без mental preparation. Не применимо если placeholder загромождает UI (10+ disabled кнопок будущего меню) — лучше show через `«More features ↓»` или roadmap-страницу.

## Display labels тоже single-source-of-truth

Дополнение к `Single source of truth для third-party shipping values` — тот же принцип распространяется на визуальное представление значения, не только на машинно-читаемый список. Симптом — юзер видит в picker'е `default · opus-4.7 [1M]`, в header'е `default [1M]`, в notification `Opus 1M`. Один и тот же выбор называется тремя способами, пользователь не уверен всё ли совпадает. Жалоба: *«не default 1m, а opus-4.7 [1M]. Напиши полное название, точно так же как в Model picker'е»*.

Каждое значение имеет canonical display label в том же constants-файле что и сам value. Каждое UI-место рендерит через один и тот же mapping (`HEADER_MODEL_LABEL[value]` / `MODEL_LABELS[value]`), не свой `.toUpperCase()` / `.replace(...)` / собственное украшение. Если в одном месте нужна сокращённая форма (header-pill), а в другом полная (picker) — оба варианта живут как именованные exports в constants, не один inline в JSX. Никаких `if/switch` в JSX по value → label: если 3 места используют 3 разных свича — рассинхрон обеспечен.

## Active expanded, archive collapsed

Длинный список с двумя классами сущностей по активности: активные показываются развёрнуто с богатыми карточками, остальные сворачиваются под `▾ All (N)` и раскрываются по тапу. Активность определяется реальным флагом (открыт сейчас, выполняется, recent), не датой. Симптом нарушения — mobile-список 16 проектов с одинаковыми карточками, юзер должен скроллить чтобы найти текущий открытый. Юзер: *«текущие активные сверху развёрнуто, остальные в свёрнутом списке»*.

Top section `Active` — карточки с full info, accent-цветом, dynamic state (live indicator, % progress). Bottom section `▾ All (N)` — collapsed button, по тапу разворачивается в plain список (имя + path, без accent'а): элементы маленькие, это архив, доступный но не доминирующий. Sort внутри active — активный сверху (звёздочка ★), остальные active по recency. Empty active section — вместо «ничего» рендери placeholder «No projects open in desktop right now», даёт hint как наполнить. Если список < 10 элементов всего — деление излишне, single flat list. См. `knowledge/fact-mobile-web.md::Endpoint map` (`isOpen` поле в `/api/projects`).

## Animation duration cap для navigation

Анимация перехода/scroll/dismiss длится ≤200ms для коротких дистанций, ≤300ms для full-screen transitions. Native `behavior: 'smooth'` без cap'а зависит от distance — на длинных списках = 1-3 секунды = ощущается как баг. Юзер: *«анимация скролла должна быть меньше 300ms, желательно 200ms. Причём как у мобилки так и у десктопа»*. 800ms scroll-to-bottom после команды — юзер успевает потерять фокус и нажать дважды.

Свой rAF-animator с фиксированной длительностью независимо от distance, ease-out cubic (быстрый старт, плавный конец, feels snappier чем linear или ease-in-out). Для длинных дистанций где даже custom animator jankaет (200+ DOM-нод) — instant jump + dim overlay на 1-2 кадра. Native browser smooth-scroll только для коротких перемещений внутри короткой страницы; везде где список > 50 элементов — свой animator. См. `methodology/design-mobile.md::Jump scroll + dim overlay`.

## Assistant text — column, не bubble

В AI-чатах сообщения ассистента не должны выглядеть как chat-bubble с правым отступом «как от собеседника». Ответ AI на длинный prompt — это document, не реплика. User-message — bubble (короткие, выровнены вправо). Assistant — full-width column (потенциально длинные, выровнены к prose-flow). Юзер: *«нет смысла особо заморачиваться, растяни на всю ширину»* — на мобильном экране ответ AI занимает 85% ширины внутри bubble, правые 15% пусты, а ниже идёт tool-card на 100%. Визуальный конфликт: assistant с margin'ом, его tool — без.

User message — bubble background `#1f3a5f`, `max-width: 85%`, `justify-content: flex-end`. Assistant — no bubble, `color: #cccccc`, full-width до padding'а контейнера, `lineHeight: 1.5`; markdown body использует тот же поток. Tool cards — full-width без bubble (см. `Tool call = карточка`). Thinking — full-width outlined контейнер с italic body. Mental model: user — реплика в диалоге (bubble), assistant — статья/документ (column), tool call — структурированный лог (card). Три разные грамматики, не одна. См. mobile-web `EntryView` — assistant без `S.bubble`, full-width column.

## Success ≠ exit code: валидация по содержимому, не по факту завершения

Когда UI триггерит фоновую команду и показывает пользователю исход (тост «успешно» / «ошибка»), нельзя считать её успешной по `exit code === 0`. Многие скрипты завершаются ноль-кодом даже если внутренне провалили половину файлов / шагов / запросов — выход 0 значит «скрипт дошёл до своего конца», не «задача выполнена». Если показать «успешно» по факту exit'а — UI лжёт, и юзер обнаружит провал только когда столкнётся с последствием (устаревший индекс, недописанный артефакт, частичный backup). Юзер сформулировал требование к детерминированности до того как баг проявился: *«если вылезет какая-то ошибка, чтобы всё откатилось, вылезет тост-уведомление. То есть не будет такого, что у меня лоадер прошёл успешно, а на самом деле там возникло на каком-то этапе какая-то ошибка»*.

Парсить stdout фоновой команды детерминированными regex-ами, собирать набор позитивных и негативных сигналов и считать `success = AND(все позитивные)`: exit code 0 И не убит сигналом (необходимое, не достаточное); видели summary-строку (`Files indexed: X/Y (cached: ..., err: N)`) — её отсутствие = скрипт прервался посреди процесса; поля `err`/`warn`/`fail` в summary == 0; подсчитанные per-event ошибки (`error <file>`, `missing <file>`, `wrapped <file>`) == 0 (двойная страховка против случая когда summary врёт о собственных полях). Тост получает конкретный список причин (`exit code 0; summary missing; 2 file error(s): wrapped:docs/...`) — пользователь не должен читать stderr, детали идут в лог. См. `src/main/ipc/semantic-index-status.js::rebuildIndex` — успех rebuild'а индекса собирается из 6 сигналов: `code===0 && !signal && sawSummary && summaryErrors===0 && summaryWarnings===0 && perFileBad===0`. Также `knowledge/fact-project-toolbar.md::Rebuild validation`.

## Прогресс-индикатор показывает active work, не total volume

При фоновом процессе где большинство шагов пролетают за миллисекунды через кэш / no-op / skip, счётчик прогресса (`N / M`) описывает реально работающие шаги, не общий объём. Иначе восприятие искажается: `5 / 90` создаёт иллюзию «осталось много», хотя 85 из них уже за кадром cached, и пользователю реально ждать 5. Юзер сам сформулировал mental model: *«у нас не отображается то, сколько всего проиндексировано, а сколько сразу осталось проиндексировать»* — попросил подогнать счётчик под неё.

Работает для процессов где есть наблюдаемая разница между «реально работаю» и «пропускаю»: в индексаторе видно по двум разным маркерам в stdout (`[launched ...]` vs `cached`). Для процесса где все шаги равноценны — счётчик честно по всем. Если 90% шагов завершатся за первые 0.5 секунды и пользователь увидит `81/90` мгновенно, а потом несколько минут зависание на `81-86/90` — счётчик неинформативен. Хорошее число для running-индикатора начинается с того что уже занимает время и осталось (`1/5`, не `86/90`). См. `src/main/ipc/semantic-index-status.js` — `outdatedTotal` собирается из `[launched N/TOTAL]` строк (только файлы у которых не совпал hash), `outdatedCompleted` инкрементируется при `ok|wrapped|error` для launched-файлов, `cached` события игнорируются. Цвет индикатора во время rebuild'а — амбер (`#d97706`), не индиго: индикатор сигнализирует «есть работа», а не «всё хорошо». См. `knowledge/fact-project-toolbar.md::SemanticIndex visual language`.

## Local infra > cloud для single-user dev-tool

Для инструмента с одним пользователем (личный CLI, локальная dev-utility, single-developer mobile remote) не разворачивать cloud-инфру (туннели, домены, OAuth, certificate management). Простой local HTTP/WS на 0.0.0.0 + bearer token в файле + ручной copy на устройства — достаточно и быстрее в setup'е. Юзер прямо: *«пошёл ты нахуй, какой сука туннель, какой домен блять, я не буду этого делать, возвращай токен»* — cloud-инфра overkill когда ПК и телефон в одной Wi-Fi.

HTTP+WS на `0.0.0.0:<port>`, доступен через LAN IP. Bearer token генерируется при первом старте, лежит в `~/.<app>/web-token.txt` (mode 0o600). Token копируется на устройства через clipboard / AirDrop / QR (one-time setup). URL формы `http://<lan-ip>:<port>/?token=<hex>` — token из query stripping'ается в localStorage при первом mount'е. Trade-off: ПК должен быть on + в той же сети — не недостаток для dev-tool, он у тебя и так включён когда работаешь. Cloud-инфра нужна только для multi-user продукта, где пользователь не может быть в той же сети что host; для single-developer remote control — никогда. См. `knowledge/fact-mobile-web.md::Token & paths` и `methodology/design-mobile.md::Bridge для UI-state-needing actions`.

## Toggle для expanded long content — наверху и внизу

Когда длинный inline-блок (>1 экрана) сворачивается через toggle — в expanded состоянии toggle обязан жить и сверху, и снизу. Один toggle снизу заставляет пользователя скроллить через весь контент чтобы свернуть, что превращает «свернуть» в «забить и проскроллить мимо». Юзер прямо: *«нужно скроллить в самый низ приложения чтобы свернуть, это крайне неудобно»*.

В collapsed состоянии toggle только снизу (после превью, естественное продолжение текста). В expanded — и сверху (`mb-1` под верхом блока), и снизу, один и тот же handler. Anchor для viewport-preserve (rAF + scroll-restore при сворачивании) общий — оборачивай весь блок одним `<div ref={anchorRef}>`, оба `<button>` внутри. Top-toggle не нужен когда expanded-контент короче ~2 экранов и заведомо помещается без скролла (нижняя кнопка видна сразу). См. `CollapsibleText` в `ClaudeSDKTab.tsx`, конкретика — `knowledge/fact-claude-sdk-tab.md::Сворачивание длинных user-сообщений`.

## position:fixed × ancestor transform — containing-block ловушка

CSS-spec: любой `transform`, `filter`, `perspective`, `will-change`, `backdrop-filter` на ancestor'е делает его containing block для `position:fixed` потомков. После этого `position:fixed; inset:0` рендерится не относительно viewport'а, а относительно этого ancestor'а — обычно крошечного. Симптом — sheet/modal/overlay с `position:fixed; bottom:0` (должен прилипать к низу экрана) внезапно улетает вверх, прилипает к низу маленького контейнера в шапке. Юзер: *«окошко вообще не там где должно быть, въебенях где-то вверху появляется»*.

Если центрируешь header-элемент абсолютно — не используй `transform: translate(-50%, -50%)`. Замени на overlay-pattern: `position:absolute; left:0; right:0; top:0; bottom:0; display:flex; justify-content:center; align-items:center;` с `pointer-events:none` на overlay и `pointer-events:auto` на content. Если transform нужен (анимация, scale) — рендери `position:fixed` потомков через React Portal в `document.body`: Portal вытаскивает их из transform'нутого ancestor'а. Перед коммитом UI-кода для каждого ancestor'а с `transform/filter/will-change` проверь что внутри нет `position:fixed` который должен быть viewport-relative.

## Home-toggle: Dashboard → last-active project одним кликом

Кнопка «Home» (🏠 / иконка-логотип) в большинстве приложений — тупой роутер, всегда ведёт на `/dashboard`. Если пользователь часто переключается между Dashboard и конкретным проектом (создал проект → вернулся в Dashboard проверить список → снова в проект), это два клика каждый раз. Contextual toggle: из любого view Home ведёт в Dashboard, из Dashboard — обратно в последний активный проект (с восстановлением активного таба, позиции, открытых панелей). Реализация требует сохранить `lastActiveProjectId` при входе на Dashboard и `switchToProject(lastActiveProjectId)` при повторном клике на Home.

Применимо к любому приложению с central hub view (Dashboard, Inbox, Project list) + per-item working view (открытый проект, открытое письмо) — сокращает 2 клика до 1 для самого частого navigation pattern. Не применимо если central hub сам является working view (kanban board без drill-down) — toggle тогда возвращает в то же место, бессмысленно. Не путать с Back button: Back возвращает к предыдущему view какой бы он ни был, Home-toggle — специфически к last-project, минуя промежуточную навигацию.

## Scroll-to-bottom arrow для streaming-логов и timeline

Длинные вертикальные списки в которые активно поступают новые данные (chat, terminal log, AI streaming response, live activity feed) создают конфликт: пользователь хочет видеть свежее (бот пишет ответ) и одновременно читать историю (скроллит вверх). Auto-scroll-to-bottom при каждом новом сообщении ломает чтение — пользователь скроллит к нужному фрагменту, его выкидывает в конец. Отключение auto-scroll оставляет «висеть в прошлом», не зная что появилось ниже.

Кнопка-стрелка возврата к низу появляется когда `scrollBottom - currentScroll > N` (порог ~150px чтобы случайные микро-скроллы вверх не показывали кнопку), скрывается при `currentScroll ≥ scrollBottom - 5px` (zone-of-bottom 5-10px), click делает `scrollTo({ top: maxScroll, behavior: 'smooth' })`. Расположение — floating над контентом в правом-нижнем углу контейнера, не sticky bar внизу (занимает место). Видимость управляется прямой манипуляцией `style.display` в scroll handler без React re-render — иначе на каждый scroll-event пересчитывается весь tree. Применяется к auto-scrolling lists с потоком обновлений; не нужно для статичных длинных текстов (документация, статьи) — там обычный браузерный scrollbar достаточен.

## Cached external resource: alive-probe перед использованием

Любой in-memory cache, ссылающийся на внешний ресурс с независимым lifecycle'ом (kernel PID, socket fd, file handle, child process, удалённый session token), обязан валидироваться перед использованием через дешёвый probe (`process.kill(pid, 0)`, `fstat`, `ping`, `HEAD` запрос). Без probe stale-запись в cache переживает смерть ресурса и даёт silent failure с misleading downstream error: операция «работает» по нашим внутренним метрикам, но реальный side-effect уходит в пустоту. Юзер триггерит действие (copy, kill, send-signal), наш код находит закэшированный handle, делает отправку — никаких ошибок, лог «успешно». Но дальше нужен ответ от внешнего ресурса (callback, socket reply, exit code), он не приходит, UI ждёт N секунд, юзер видит generic «operation failed» без подсказки что делать. Реальная причина: cache держал PID/fd процесса, умершего вне нашего scope (юзер ребутнул вручную, OS прибила, parent shell завершился), cleanup hook на это не триггерился.

Перед использованием cached external handle — synchronous alive-probe. Для PID: `process.kill(pid, 0)` (бросит `ESRCH` если процесс мёртв). Для socket: `socket.write('')` с error-handler. Для remote session: `HEAD` запрос с короткими таймаутами. При ESRCH/ENOENT/404 — немедленный возврат специфичного error code (`stale_pid`, `stale_handle`, `session_expired`), не продолжение pipeline. Юзер должен получить конкретную инструкцию («restart the tab», «log in again»), не generic timeout. Probe не замена cleanup hook'ам — Bridge:Fresh / socket.on('close') / process.on('exit') всё равно нужны, probe это last line of defence на путях которые hook'и не покрыли (юзер рестартнул процесс вне spawn-pipeline, kernel OOM-killed, parent shell получил SIGHUP). Probe O(1), не дороже того что мы сэкономили временем кэширования; если дорогой (network RTT) — отдельный TTL у cache (5-30s) и опциональный fallback на full refresh.

Применимо к PID-кешу child-процессов (Claude TUI, Gemini CLI, node-pty), socket-cache внешних демонов (D-Bus, MCP, IPC bridges, Docker daemon), session-id / token cache внешних API, file-descriptor cache long-lived I/O. Не применять к внутреннему state UI (Zustand selectors, React state, Map<tabId, settings>) — он живёт в том же процессе, исчезает синхронно при unmount/restart, alive-probe бессмысленен. Граница с `Persistent state across UI transitions`: та секция про закрытие loading-state когда async вернул error, эта — про обнаружение мёртвого ресурса до запуска async; часто оба нужны одновременно. См. `knowledge/fix-prompt-queue-stale-pid.md` — после Bridge:Fresh для перезапущенного claude'а не сработал, bridgePidCache хранил dead PID на 2.5 часа; `captureClaudeInput` теперь делает `process.kill(claudePid, 0)` перед всем pipeline.

## In-memory ephemeral state ≠ persistent identifier source

Если у объекта есть persistent identifier (sessionId на диске, file path, DB row id) — этот id должен читаться из persistent storage, не из in-memory структуры которая живёт меньше чем сам объект. In-memory кэш может быть производным от persistent (для скорости), но source of truth — диск/БД.

Узнаётся по характерному циклу: «свежий объект → действие создаёт его id в Map → действие закончилось → cleanup чистит Map → следующее действие не находит id → создаёт новый объект → бесконечная rotation». Юзер видит как *«ассистент отвечает в вакууме, не помнит предыдущие сообщения»*. In-memory структуры (`activeSessions`, `runningJobs`, `wsConnections`) — это про active, не про id history; они правильно очищаются на завершении. Caller, которому нужен resume/retry/continuation, должен брать id из persistent store, не из Map.

В custom-terminal эта ловушка стоила 5 итераций отладки: `sdkSessions: Map<tabId>` хранила sessionId и удалялась в `finally`, между turn'ами Map пустой, `send-message` читал sessionId оттуда → каждый turn `--resume=null`. Фикс: renderer/mobile передаёт `resumeSessionId` явно из `tab.claudeSessionId` (Zustand → SQLite). Map осталась для in-flight management. См. `knowledge/fix-sdk-session-amnesia.md`.

## Send / Stop = одна muscle path

Действия, которые взаимоисключают друг друга по времени (start ↔ stop, mute ↔ unmute, play ↔ pause), живут на одной кнопке в одном слоте UI, переключающейся по состоянию. Не две кнопки в разных местах. Не одна disabled, другая active. Один widget — два визуальных состояния.

Симптом нарушения был мобильный: Send-кнопка справа внизу composer'а, Stop-кнопка вверху справа от burger'а. Юзер построил **две** muscle path'и — «отправить» = вниз+вправо, «остановить» = вверх+вправо. Когда Claude начинает генерить, рука всё равно тянется к месту Send (рефлекс не успел переключиться) → промах. Юзер сформулировал прямо: *«стоп нужно переместить на место кнопки отправки, ну блять, это максимально логично»*.

Анимация перехода между состояниями важна: цвет/иконка меняются in-place, без `display:none` (вспышка) и без translate (читается как новая кнопка появилась). См. `knowledge/fact-mobile-web.md::Composer button slot`.

## Прогресс = заполнение, не остаток

Процент-индикатор показывает сколько сделано/занято/израсходовано, не сколько осталось. 5% в начале, 95% к концу. Юзер читает большое число как «много чего-то», большое число у remaining-метрики этому ожиданию противоречит.

Юзер сформулировал словами: *«идти нужно от обратного — должно писаться, сколько потрачено, а не сколько осталось процентов»*. До правки контекст-pill в SDK-табе показывал `92%` для свежего чата (92% свободно). Юзер читал как «контекст почти полный, надо чистить» и шёл чистить пустой чат. Применимо ко всем подобным метрикам: storage usage, context window, rate limit, battery — всегда filled bar, не empty bar. Цветовая шкала по нарастанию: серый 0-75 → амбер 75-90 → красный 90-100, чтобы «больше число = критичнее» совпадало.

См. `knowledge/fact-claude-sdk-tab.md::Context indicator`.

## Create → use, не Create → list

Действие «создать новое X» сразу открывает созданный X в режиме использования, не возвращает в список «вот ты создал, нажми чтобы зайти». Каждый Create = выраженный intent работать с новым объектом, дополнительный тап для перехода — пустая friction. Особенно ощутимо на mobile, где каждый тап стоит больше.

Юзер прямо: *«при создании идёт переход внутрь вкладки тоже»*. Исключение — batch-create («сделай 5 табов сразу»): logical destination не очевидна, остаёшься в списке.

## Cancel write-action = revert to pre-action state

Когда юзер отменяет action до того как тот произвёл наблюдаемый результат, UI возвращается к точному состоянию до action'а. Форма была заполнена — текст возвращается в input. Был выбран файл — selection остаётся. Cancel ≠ destroy.

Юзер описал на mobile: *«если мы нажали рано кнопку отмены промпта, должен просто возвращаться на место инпута»*. Реализационно — два ref'а: `pendingPromptRef` (stash input при send) и `assistantStartedThisTurnRef` (true как только пришёл первый text/thinking/tool_use). На stop: если `assistantStarted=false`, restore stashed prompt; если уже что-то было — не возвращаем, partial остаётся в чате. Распространяется на любую abort/undo write-операцию: undo file move (вернуть исходное место), cancel paste (вернуть в clipboard), abort upload (вернуть selected file в picker).

См. `fact-claude-sdk-tab.md::Cancel restore prompt`.

## Navigation = instant, loader внутри destination

При навигации между экранами/панелями (drawer → chat, list → detail, modal → result) caller-экран закрывается мгновенно, состояние «грузим что-то» рисуется внутри destination'а, не оверлеем поверх caller'а. Иначе юзер не понимает что нажалось: caller всё ещё на экране, индикатор поверх него выглядит как «модалка зависла».

Юзер сформулировал: *«клик на кнопочку нихуя не детерминированный... либо чтобы сразу мгновенно закрывался таймлайн, и также было окно загрузки»* — то есть сначала уходит caller, потом юзер видит destination с индикатором уже внутри. Симптом до фикса: тапает GoTo в drawer'е, drawer остаётся открыт с лоадером поверх, тапает второй раз → действие срабатывает дважды.

Технически: первый кадр должен показать destination route (через `flushSync` или `navigate()`), а данные грузятся уже под видимым skeleton/spinner внутри destination. Async может длиться сколько угодно — это уже не «навигация», это «загрузка контента». См. `fact-mobile-web.md::Expanded state map`.

## Consistent persistence / parity для аналогичных фич

Если фича B архитектурно аналогична существующей фиче A (та же роль для юзера, тот же data shape, тот же лайфсайкл) — она обязана использовать ту же модель хранения, тот же набор UI-affordance'ов, ту же event-семантику. Любое отклонение — флаг технического долга («у нас исторически так»), не feature decision. Узнаётся по фразам *«логика сохранения должна быть такая же, как для обычного клода»*, *«где у меня кнопки „обновить и редактировать“? Они тоже должны быть на мобилке, так же как у нас на компе»* — юзер обнаруживает что аналог работает по-другому, теряет mental model, начинает запоминать где какой surface работает иначе.

Перед добавлением специального хранения / UI для нового варианта — проверь: есть ли существующий вариант той же роли? Используй ту же модель. Парные surfaces (desktop ↔ mobile, light ↔ dark, full ↔ compact) — feature parity по дефолту; asymmetry допустима только если явно обоснована (нет места на узком экране, capability разнится), каждое исключение задокументировано в knowledge. Refactor-триггер: если ловишь себя на «давайте здесь сделаем по-другому потому что так проще» — стоп, сделай как уже есть или подними оба к одной модели. Если для двух аналогичных фич нужны разные объяснения в документации — это ошибка, должно быть одно описание + ссылка «то же для mobile/dark/...». См. SDK-таб: persistence = тот же tabType + claudeSessionId в БД, история = тот же JSONL parser что у обычного Claude (`active-branch-messages` через `findSessionFile`), не свой index. Edit/Repeat кнопки на user-bubble — feature parity между desktop и mobile.

## Persistent UI state hydrated on mount, не ждёт live event

Любой UI-индикатор который может быть восстановлен из persistent storage (БД, IndexedDB, JSONL, file metadata) обязан hydrate на mount. Висеть пустым/прочерком до первого live event'а — нарушение: юзер ждёт что состояние уже есть (он же не ушёл из этой сессии, ничего не очищал). Юзер прямо: *«при заходе не пишет количество процентов... мне нужно какой-то промт отправить. Я только потом отобразится количество процентов оставшихся, это прям грубое нарушение»*. Открывает чат, видит пустой context-indicator: состояние существует (последний assistant-турн с usage есть в JSONL), но рассчитывается только из live stream — пока нет нового хода, индикатор молчит.

На mount пройди по persistent storage, найди последнее значение для каждого индикатора, сразу `setState`; если ничего нет — null/dash, иначе восстановленное. Источники: usage из last assistant-record JSONL, scroll-position из cache, draft text из localStorage, expanded sections из IDB. Live event'ы дополняют hydrated state, не заменяют его с нуля — их роль «обновить», не «заполнить впервые». Антипаттерн «live-only state» — значения существуют только пока компонент живёт, при unmount теряются, на mount считаются с нуля. Допустимо для эфемерных вещей (hover-pos, click-anim), не для metrics/progress/last-known-status. Контекст% индикатор должен hydrate из last assistant message в JSONL при `loadHistory`, не ждать следующего live `claude-sdk:message`; аналогично `lastResolvedModel` берётся из последнего assistant-record, не остаётся `default` пока юзер не отправит первый prompt.

## Context-irrelevant indicator = hide, не show as 0/N/A

UI-индикатор показывается только если метрика реально применима к текущему контексту. Метрика не применима → элемент скрыт целиком, не показан как «0», «N/A», «—», «empty». Юзер прямо: *«у вкладки терминала 0% красным отображается... хотя для терминала мы не должны показывать процентовку»*. `0%` несёт смысл «известно что значение = 0»: когда значение не применимо (метрика не определена для этого типа объекта), `0%` создаёт ложный сигнал тревоги (красный = плохо), `N/A` — занимает место и шумит.

Условный render по семантике: `{indicator.applicable && <Indicator value={...} />}`. Не использовать defaults типа `value ?? 0` — это превращает «не применимо» в «применимо и равно нулю». Граница: применимо/не применимо определяется типом контекста (terminal-tab vs SDK-tab, free-plan vs paid, anonymous vs logged-in), не временным состоянием значения; «ещё не загрузилось» = показать загрузочный state, «принципиально не существует» = скрыть. Контекст-pill в mobile + desktop header скрыт для `tabType !== 'claude-sdk'` (PTY-Claude не имеет SDK usage events).

## Type variant = visual marker, не rename

При создании derivative entity (fork, clone, duplicate, convert) — сохраняй имя оригинала, тип/вариант помечается визуальным маркером (icon, pill, accent color, background variant). Имя про содержание, тип про поведение, не смешивай. Симптом — fork таба `claude-06` создаёт `claude-08` (auto-generated), юзер теряет связь «это форк именно того диалога», должен переименовывать руками. Альтернатива «add suffix `claude-06 (sdk)`» захламляет имя сервисной информацией.

Fork/clone copy'ит `name` источника; auto-generated name только для с нуля созданных. Маркер типа — отдельный визуальный slot (pill `SDK` / `TERMINAL` / `DEV`, accent stripe, background tint, icon), независим от name; при listing'е оба видны: имя для identity, маркер для capability. Прочитай list вслух — имена про что говорит юзер («этот про bug в auth»), маркеры про чем работает («через SDK», «через CLI»). Не должно быть «claude-06-sdk-fork-2» — это смешение двух категорий в одну строку. См. `forkToSDK` бэкенд копирует `srcTab.name` в новый SDK-tab через `state.renameTab`; маркер типа — `CLAUDE` pill в TabRow + accent color, остаётся одинаковым между source/fork.

## Click target = вся семантически связанная зона

По Fitts: clickable target = вся семантически объединённая зона, не только icon/text. Если кнопка `←` соседствует с label «Back to Project» — обе ведут к одному действию. На touch-устройствах критично: ширина пальца ≥ 32-44px, отдельный icon-button = промахи. Жалоба юзера: *«сделай кнопку назад вместе с названием чата оба кликабельными»* — тапает в зону рядом с back-arrow (где label) → ничего не происходит → второй тап на arrow точечно.

Group icon + label в один `<button>` (или `<a>`), не два соседних элемента с одним handler — один большой target. Min touch target 44×44px (iOS HIG) для primary actions; для secondary 32px допустим если визуально отделены. Внутренние children (icon span, label span) — `pointer-events: none` чтобы клик гарантированно ловился на parent button. См. mobile header `[← claude-04]` — один `<button onClick={onBack}>`, ширина ~120px вместо 32px у одиночного icon, конкретика в `methodology/design-mobile.md::Header layout`.

## Stable production + experiment dev = parallel, не serial

Разработческий dev-инстанс и stable production должны коэкзистировать на одной машине без конфликта. Конфликт ресурсов (порт, файл, lock) = разработчик вынужден закрывать production чтобы тестировать, ломается «продолжай юзать stable пока экспериментируешь». Юзер: *«если я запускаю dev-сервер, он типа перебивает порты, либо что? Можно просто запускать два приложения на разных портах?»* — закрывает production app → теряет открытые сессии/контекст → запускает dev → тестирует → закрывает → снова открывает production. Каждый эксперимент стоит дороже чем сама правка.

Все ресурсы которые могут конфликтовать (HTTP port, WS port, IPC socket, lock file, log file path, DB file) параметризованы env var: production использует дефолт, dev — alternative через npm script (`"dev": "RESOURCE_PORT=ALT_VALUE ..."`). Persistent storage может быть общим (token files, config) если dev/prod пишут совместимый shape — иначе разделить. URL/access path для каждого режима стабильный и discoverable: production = `<host>:7878`, dev = `<host>:7979`, юзер запоминает оба не путается. См. `NOTED_WEB_PORT=7979` env override в `npm run dev`, production `/Applications/Noted Terminal.app` слушает 7878, token общий через `~/.noted-terminal/web-token.txt`. Конкретика — `knowledge/fact-mobile-web.md::Dev-port isolation`.

## Виртуализация vs `display:none` для больших списков

`display:none` гасит layout/paint, но **не** останавливает React reconciliation детей. При раскрытии panel'а с 700+ элементами (`display:none → flex` на parent) React синхронно обходит всё дерево, monoflood reconciliation блокирует main thread на секунды. То же самое при mount компонента, который уже владеет большим списком — `setMessages([744 items])` триггерит full reconcile до первого paint, лоадер не успевает появиться. Детерминированный лог из live-сессии: между `setMessages` и первым `MessageRender` — 12 887 мс на 744 элементах × 3 mounted табов. Раскрытие `display:none → flex` тяжёлого таба занимало 1 511 мс reconciliation + 157 мс paint.

«Спрятать через `display:none` чтобы не платить за рендер» — миф. Платится reconciliation за каждое state-обновление родителя независимо от visibility. Решение всегда одно: виртуализатор (`react-virtuoso` / `react-window` / `tanstack-virtual`) ограничивает mounted-children до видимого окна (~30 шт) независимо от длины data. Hidden tab платит за виртуализатор fixed cost ~30 нод вместо linear по списку. Для assistant-ui это означает заменить `ThreadPrimitive.Messages` на `Virtuoso` с per-item `MessageByIndexProvider` — виртуализатор владеет рендером, providers дают каждому видимому item его собственный thread-state subtree. См. `knowledge/fix-sdk-virtualization-tab-switch.md`.

## Skeleton ≠ emptystate во время загрузки

Окно «sessionId известен, history fetch в полёте, messages.length === 0» — это **состояние загрузки**, не пустой контейнер. Показывать в нём CTA «Type a message to start» = врать пользователю: «контента нет, начни писать», когда правда «контент сейчас придёт». Юзер видит CTA на тяжёлом восстановленном табе, успевает прочитать «надо что-то напечатать», думает «потерял диалог», и через 200 мс контент появляется поверх. Юзер прямо: *«пустой экран замени на лоадер... типа скелетон какой-нибудь. Это сейчас просто что-то пустота внутри»*.

Tri-state на load: `idle` (новый контекст, sessionId === null) → emptystate-CTA; `loading` (sessionId есть, history не resolved) → skeleton-bubbles; `done` (loadHistory завершился) → реальный чат **или** emptystate если действительно пусто. Skeleton — content-shaped placeholder (4-6 alternating-side фейковых пузырей с `animate-pulse`), не spinner — он сообщает «вот сюда придёт чат», spinner сообщает «сервер думает». Skeleton ≠ emptystate ≠ spinner — три разных сигнала, нельзя путать.

Принцип верный, но конкретная реализация поверх `useExternalStoreRuntime` + `react-virtuoso` **не получилась**: попытались tri-state hook, безусловный skeleton-fallback и absolute-positioned overlay поверх Virtuoso — ни один не показал skeleton кадр-в-кадр на cold-open тяжёлого таба (warm-cache react-batching съедает loading-state, overlay не виден на пробеле mount→paint). Откатили обратно к single-flavor empty-state, пробел ≤500мс терпим. Конкретика и кладбище попыток — `knowledge/fix-sdk-virtualization-tab-switch.md::Skeleton-overlay для окна mount→first-paint`. Следующая попытка должна стартовать с React DevTools Profiler trace а не с очередного варианта компоновки.

## Глобальный startup-loader охватывает готовность контента, не только store

Если приложение показывает loader при cold start (`Restoring session...`, splash screen) — он должен сниматься когда **видимый контент готов к показу**, не когда in-memory store восстановлен. Иначе сценарий: store rehydrate за 50 мс → loader исчезает → mount компонентов → каждый из них кикает свой async fetch (history, settings, prefs) → юзер 200-500 мс смотрит на blank UI с пустыми табами/сообщениями. Эффективно две фазы загрузки подряд: первая видимая (loader), вторая невидимая (blank). Юзер: *«у нас есть глобальный loader... распространи его также на подгрузку SDK табов, потому что почему типа нам нужно ждать пока подгрузятся в первый раз»* — увеличить **одну** видимую фазу заведомо лучше чем создать незаметную вторую.

Кандидаты на pre-fetch внутри loader-фазы — те, чей результат **обязательно нужен на первом кадре** активного контекста: история открытого чата, current-project file tree, активный backend status. Pre-fetch параллельный (`Promise.all`), результат складывается в module-level cache, компоненты на mount читают из cache (single-shot, self-deletes) и fall through к свежему IPC если cache пустой. Не путать с lazy data, чей рендер откладывается естественно (timeline, search index): их грузить в loader-фазе = удлинять startup для данных которые всё равно не требуются на первом кадре. См. `knowledge/fact-claude-sdk-tab.md::History prefetch in restoreSession`.

## Ordered model output → ordered UI: один список, не N стопок по типу

Когда модель отдаёт ответ как массив разнотипных блоков (`text` / `thinking` / `tool_use` / в будущем — citation, image, что угодно), их **нельзя дробить на параллельные коллекции по типу** для последующего рендера. Шаблон-ловушка: парсер делает `content.filter(b => b.type === 'text')`, `content.filter(b => b.type === 'tool_use')` — и кладёт в три отдельных поля `text/tools/thinking`. Информация о порядке между блоками умирает прямо в filter'ах. Рендер потом всегда выкладывает три стопки в фиксированном порядке (`thinking → text → tools` или любом другом) — ритм ответа модели, в котором tool вызывается **между** двумя кусками текста или после конкретной мысли, превращается в стену текста с хвостом из карточек тулзов в конце.

Источник правды для рендера — **один ordered массив `parts[]`** в той же форме что и `content[]` Anthropic API. Фильтрация по типу — только на месте рендера каждого item'а (`if (p.type === 'text') ...`). Плоские поля (`text`, `toolCalls`) допустимы как **derived** view для search/filter/cancel-detection, но рендер-pipeline их не читает. Тест: если перенумеровать блоки в JSONL и UI-порядок не изменится — рендер сломан, неважно как красиво он выглядит на простых случаях. Конкретика: см. `knowledge/fact-claude-sdk-tab.md::Tool-call rendering: ordered parts[]` — там же латентный риск в `claude-data.js` для sub-agent history.

## Single source of scrolling: или внешний контейнер, или виртуализатор

Виртуализатор и его обёртка не могут оба быть scroll-aware. `react-virtuoso` с `customScrollParent` ставит scroll-listener на внешний div, обработка scroll-event'а делает `flushSync(() => updateRange())` → React commit → parent re-render → ResizeObserver на items пересчитывает → следующий sync flush → новый parent re-render. Бесконечный цикл, видимый в логах как сотни `[Component:RENDER]` от virtuoso `flushSync` стеков, и побочный эффект — manual `scrollTop` writes в parent useEffect блокируют scroll up (виртуализатор перетягивает позицию обратно).

Выбор: либо виртуализатор владеет скроллом (его div = scroller, parent просто flex container с `overflow-hidden`), либо внешний (но тогда не виртуализатор, а `display:contents` на items). В chat-UI всегда первое — виртуализатор внутри `flex-1 minHeight:0`, manual scroll-effects удалены, `followOutput="auto"` + `initialTopMostItemIndex` делают всю работу. См. `knowledge/fix-sdk-virtualization-tab-switch.md::Graveyard`.

## Popup поверх контента — absolute, не in-flow

Autocomplete-меню, поповеры подсказок, плавающие подсказки внутри списка — всегда `absolute` относительно anchor'а, никогда block-flow. Block-flow popup толкает соседний контент вниз: высота окна меняется в зависимости от количества фильтрованных пунктов, scroll-position под popup'ом ездит, юзер теряет место в истории. Юзер сформулировал прямо: *«команды должны быть в позиции absolute, перекрывать историю, не двигать ничего».*

В chat-UI правильное место для popup-меню над composer'ом — `absolute left-0 right-0 bottom-full mb-1 z-30` относительно `position:relative` wrapper'а композера. Композер остаётся прибит к низу, popup рисуется поверх scroll-контента, layout снаружи неизменен. `onMouseDown preventDefault` на root popup'а — иначе клик мышкой по item теряет фокус textarea (blur срабатывает раньше click handler'а). См. `knowledge/fact-claude-sdk-tab.md::Slash autocomplete popup`.

## Selected autocomplete item: Enter = submit, не insert

В popup с подсветкой текущего пункта Enter/Tab/click — это **«отправить выбранное»**, не «вставить и дать дописать». Иначе двойное действие на одно намерение: юзер видит подсвеченную команду, нажал Enter, текст вставился + добавился пробел, теперь жди ещё одного Enter. Юзер сформулировал: *«если выбрал стрелочками — Enter сразу запускает».*

Argument-hint в команде (`<arg>` или `[arg]`) **не** причина блокировать submit — обычно arg optional, юзер сам печатает их если хочет (вместо выбора из popup'а — popup закрывается на пробеле, режим обычного ввода). В Claude SDK почти все hint'ы в angle brackets даже для optional args (`/compact <optional summary>`, `/clear [name]`); попытка различать `<>` vs `[]` усложняет логику и ломает UX для majority команд. См. `knowledge/fact-claude-sdk-tab.md::Slash autocomplete popup` про конкретику.

## Destructive cancel зависит от прогресса: empty → rollback, partial → freeze

Cancel-кнопка/Escape на длинной операции имеет **две выходные ветки** в зависимости от того, успело ли что-то прийти от backend'а. До первого content-event'а cancel = «передумал, ничего не было» — удалить user-message из истории, вернуть текст в input, **сделать как будто turn не начинался**. После любого content-event'а (даже пустого thinking-block'а) cancel = «остановить, но сохранить что есть» — freeze placeholder в done-state, юзер видит частичный thinking + сам решает что делать дальше через Edit/Repeat.

Юзер сформулировал поведение точно: *«если получил thinkblock и нажал Escape → удалился thinkblock И мой запрос, должно было остаться оба»*. То есть для juzер'а thinking-block — это **уже контент**, не «ещё ничего». Любой непустой блок (text/thinking/tool, даже один character thinking) включает freeze-режим.

Что было невидимо: при ordered `parts[]` модели плоские поля `streaming.text`/`streaming.thinking` могут лагать на один tick относительно `parts[]` (parts заполняются первыми, derived fields обновляются через `assembleMessageFields`). `hasContent` должен читать **обе** структуры — parts[] как authoritative. См. `knowledge/fact-claude-sdk-tab.md::Smart Cancel: hasContent читает parts[]`.

## Chevron = expand-affordance, не декор

Иконка `>` (chevron-right) перед текстом сигнализирует *«нажми чтобы раскрылось»*. В коллапсируемых блоках (ToolCard header, ReasoningPart, Files dropdown) chevron поворачивается на rotate(90deg) → визуальная обратная связь «теперь развёрнут». Использовать chevron как чисто декоративный знак-разделитель = врать аффордансом: юзер ждёт click и раскрытие, ничего не происходит. Юзер сформулировал прямо: *«стрелочки должны быть только у раскрывающихся, а тут раскрывать нечего».*

В slash-chip (`/usage` / `/compact`) chevron был добавлен изначально как мини-glyph для визуальной плотности — но раскрывать там нечего, chip целиком inline. Удалили. Любое появление chevron / disclosure-triangle / `>` icon должно одновременно отвечать за expand-state.

## Slash invocation = action-chip, не диалоговая реплика

В chat-UI с поддержкой `/commands` (Slack, Discord, Linear, Cursor, Claude Code) сообщение начинающееся с `/` — это **действие**, а не реплика в диалоге. Визуально должно отделяться: тонкий chip с моноширинным шрифтом, нейтрально-холодный цвет (фиолетовый/индиго) не такой яркий как реальный prompt-bubble, без edit/repeat hover-кнопок (повтор slash-команды проще через композер). Юзер: *«команды должны помечаться как служебные, отображаться каким-то другим цветом, больше в синюю сторону».*

Граница: текст с slash + следующим за ним обычным предложением (`/usage и потом ещё вопрос`) — диалог, не action. Action-chip только если ВЕСЬ текст матчит `^/\w[\w-]*(?:\s|$)` без переносов строк. См. `knowledge/fact-claude-sdk-tab.md::Slash command renders as user-chip`.

## Layout-agnostic shortcuts: event.code для букв, event.key для non-printable

Для буквенных шорткатов (`Cmd+E`, `Opt+V`, `Ctrl+K`) проверяй `e.code` (`'KeyV'`, `'KeyE'`), не `e.key`. `e.key` возвращает глиф который зависит от текущей раскладки клавиатуры **и** модификатор-слоя: Mac в QWERTY на Opt+V даёт `√` (Option layer), на Cyrillic — `М`, на Dvorak — `>`. По `e.key` шорткат ловится только в одной раскладке; стоит юзеру переключить язык — и кнопка молча перестаёт работать. `e.code` указывает физическую клавишу — `'KeyV'` это всегда позиция V в QWERTY-layout независимо от того что юзер сейчас печатает кириллицей. Юзер сформулировал требование одной фразой при запросе фичи: *«не должно влиять разметка клавиатуры»* — короткое спокойное правило, обязательно записываем.

Non-printable клавиши (Arrow/Enter/Esc/Tab) — наоборот, проверяй по `e.key`, потому что их `e.code` (`'ArrowUp'`, `'Enter'`) и `e.key` совпадают, а `e.key` читабельнее и устойчивее к раскладке-как-таковой (нет «другого глифа на этой клавише»). Mixed handler — `e.code === 'KeyV'` для буквы, `e.key === 'Enter'` для управляющей. См. `knowledge/fact-prompt-picker.md::Layout-agnostic`.

## Global shortcut в capture phase: перехват раньше жадных input consumer'ов

В UI с конкурирующими consumer'ами клавиатуры (xterm canvas, contenteditable, monaco/codemirror, assistant-ui textarea) глобальный шорткат должен быть навешен через `window.addEventListener('keydown', handler, true)` — capture phase, не bubble. Bubble идёт snizu вверх: nested input получает событие первым, обрабатывает (вписывает символ, двигает курсор, отправляет text в PTY) и только потом событие всплывает на window. Если global handler сидит в bubble, его работа уже бесполезна — побочный эффект на input произошёл. Юзер диагностировал по факту: *«стрелочки идут на терминал, соответственно, в терминале меняется текст. Такого быть не должно»* — открытый picker должен забирать стрелочки до того как xterm их перенаправит в PTY.

Capture phase идёт сверху вниз: window первый, document второй, дальше parent → child. Listener на window в capture срабатывает первым в DOM-дереве. Нужен полный набор: `e.preventDefault() + e.stopPropagation() + e.stopImmediatePropagation()` — stopPropagation останавливает дальнейшее движение по capture/bubble, но не другие listeners на том же phase в той же ноде; `stopImmediatePropagation` блокирует и их. xterm.js регистрирует свой `attachCustomKeyEventHandler` на canvas-нашитой textarea, тоже на keydown — без `stopImmediate` он получит событие если случайно на ту же phase подписан. Двойная страховка: дополнительно сам consumer (`Terminal.tsx`'s xterm handler) читает store-флаг `promptPickerOpen` и возвращает `false` на arrow/Enter/Esc когда picker открыт — на случай если capture-flow по непредвиденной причине пропустил. См. `knowledge/fact-prompt-picker.md::Capture-phase listener` и смежно `## Singleton listener для global events` (про unmount-resilience, отдельная ось).

## Keybinding parity: терминалы шлют одну ANSI-последовательность — UX объединяет

В Unix-наследии Esc, Ctrl+[, Ctrl+C в interactive-context часто шлют одинаковый или эквивалентный ANSI-байт (`\x1b` для Esc/Ctrl+[, SIGINT для Ctrl+C). Юзер привычно жмёт любую из трёх в зависимости от ситуации/muscle memory. Хорошо спроектированный UI **объединяет** их в одно действие cancel/close, не пытается их различать.

В Claude SDK chat одна `useEffect`-binding ловит `e.key === 'Escape' || (e.ctrlKey && e.key === '[') || (e.ctrlKey && e.key === 'c')` и роутит по приоритету: open overlay → close overlay; running → cancel turn; otherwise → no-op. Юзер не должен помнить «какая клавиша закрывает overlay» — все три работают. См. `knowledge/fact-claude-sdk-tab.md::Ctrl+[ как alias Escape`.

## Fake progress > врать конкретными цифрами когда API не отдаёт

Длинная операция без API-метрики прогресса (Anthropic SDK для `/compact` шлёт только start+end markers — без процентов) — рисуем **indeterminate progress**: бесконечный shimmer, slide-bar, breath-pulse. Не fake-проценты, не «5%...23%...». Юзер: *«а где прогресс в процентах? где вот эти вот чёрточки?»* — после объяснения что SDK не отдаёт это в API surface (доступно только в CLI Ink runtime через `onCompactProgress` hook), согласился на animated bar.

Принцип: lying with specific numbers > honest indeterminate motion. Indeterminate показывает «работа идёт», не «осталось 27%»; юзер не привязывается к числу, обновление через 30 секунд не вызывает «застрял на 50%». Дополнительно — elapsed timer (`~Ns elapsed`) даёт реальную информацию вместо выдуманной. См. `knowledge/fact-claude-sdk-tab.md::Compact loader`.

## Idempotent focus — не дёргать focus() если уже active, не воровать selection

Click-handler «whitespace-click → focus текстарии» (любой паттерн где пустая область контейнера фокусит inner-input) обязан быть idempotent. Повторный `focus()` на уже активный элемент рестартует caret-blink с нулевой фазы → визуальный шов «мигнул» на каждом клике в пустую часть UI. Юзер заметит первым: *«у меня активируется инпут, кликаю второй раз, активируется заново, мигает. Этого нахуй быть не должно».*

Тот же handler не должен воровать selection. Клик внутри scroll-контента (message bubble, list-item с текстом) — потенциальное начало drag-to-select; наш `focus()` сбросит selection до того как mouseup её зафиксирует. Юзер сформулировал инвариант шире: *«если у меня выделение на каком-то куске — внутри инпута либо внутри истории, всё это выделение должно жить».* То есть один visual container = один selection scope; whitespace-click не отменяет selection в его пределах.

Чек-лист idempotent-focus: skip если `document.activeElement === target`, skip если клик внутри `[data-role-...]` content-bubble, skip если есть active live-selection. Только тогда вызов `focus()` валиден. Конкретика — `knowledge/fact-claude-sdk-tab.md::Focus + selection coordination в чате`.

## Focus-vs-selection в scrollable text containers

Три WHATWG-инварианта делают наивные подходы к фокус-менеджменту тупиковыми, и эта связка работает в любом UI где есть прокручиваемая зона с выделяемым контентом плюс соседний controlled-input (composer/editor/search). Первый: `preventDefault()` на mousedown монолитен — один и тот же `defaultPrevented` gate в Blink контролирует И click-focus pipeline, И selection-start pipeline, отменить одно но не другое нельзя. Второй: `tabindex="-1"` всё равно делает div click-focusable (только полное отсутствие атрибута убирает его из click-focus pipeline). Третий: `element.focus()` на form-control коллапсит `window.getSelection()` (focusing-step 7 + Blink convention).

Из этого следует, что классический подход *«scroller получает фокус на click → мы возвращаем фокус в textarea»* не работает: возврат фокуса либо сразу (mousedown/focusin handler) убивает drag-select до начала, либо позже (через setTimeout refocus) ловит уже-скоалепсенную selection. Канонический паттерн ProseMirror/Slate/Slack: parent-scroller рендерится **без tabindex** (non-focusable вообще), затем фокус возвращается в composer **на mouseup** через selection-thresholded recovery — если drag дал осмысленный selection (длина ≥ 5 символов), оставить body active с живой селекшен; если click без drag, focus textarea + restore caret position. Caret snapshot обязательно делать **на mousedown в capture phase** (document-level), а не в onBlur — Blink сбрасывает `textarea.selectionStart=0` до того как React onBlur запустится.

Юзер сформулировал инвариант так: *«вне зависимости от того что я делаю внутри (выделение, что-то ещё), фокус должен остаться»* — и контр-инвариант: *«не нужно нажимать дополнительный клик чтобы убрать выделение перед печатью»*. Оба удовлетворяются связкой: при drag — selection живёт + composer ловит keystroke через `## Global keystroke routing` (см. ниже); при click — focus возвращается с восстановленной кареткой. Конкретика и кладбище отброшенных подходов — `knowledge/fix-controlled-textarea-focus-selection.md`.

## Suppress focus on non-edit buttons in scroll-content

Внутри scrollable content-area (чат, лента сообщений, история операций) кнопки которые **не** ведут в редактирующий UI (раскрывалки, toggle, scroll-to-bottom, чевроны tool-card) обязаны блокировать переход фокуса через `onMouseDown={(e) => e.preventDefault()}`. Click event срабатывает нормально (он от mouseup, не mousedown), но фокус с соседнего composer'а/inputа на кнопку не уходит. Иначе типичный сценарий *«юзер кликнул в раскрывалку → следующий keystroke не попадает в composer»* — потому что button stole focus и keydown идёт ей. Это стандартный pattern Slate/ProseMirror toolbar. Edit/Repeat-кнопки и кнопки которые ведут в другую textarea (inline edit, comment reply) — исключение, им фокус нужен для UX продолжения работы. Конкретика — `knowledge/fact-claude-sdk-tab.md`.

## Global keystroke routing для selection-scope UI

Когда дизайн допускает «есть selection в read-only части + composer всё равно должен принимать ввод» — нельзя полагаться на стандартный `document.activeElement = composer` для маршрутизации keydown. Любая попытка вернуть фокус в composer убивает selection. Решение: document-level keydown listener в **capture phase**, который при `target` вне form-control'ов пишет ввод **программно** в composer через native value setter + InputEvent. Native setter (`Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype, 'value').set`) обходит React's `inputValueTracking` — React патчит per-instance setter и dedupes onChange если tracker == DOM value; через prototype-setter tracker не апдейтится, видит делta, fires onChange.

После первой keystroke listener сам подбирает фокус в composer + clear selection — типичный UX «начал печатать → выделение пропало, я в инпуте». Без этого юзер репортит *«нужно сначала кликнуть мимо чтобы убрать выделение, потом печатать — слишком много шагов»*. Гадости: каждый mounted-копию компонента вешает свой document listener — нужен visibility guard (ref на `isVisible` + проверка в начале handler'а), иначе одна буква пишется N раз в зависимости от количества табов. Конкретика — `knowledge/fix-controlled-textarea-focus-selection.md`.

## Visual selection ≡ functional selection в autocomplete/dropdown

Подсвеченный пункт списка обязан совпадать с тем что committи'тся на Enter/click. Если стрелочки меняют визуал (`.bg-active` класс едет), а commit достаёт «по умолчанию первый» / устаревший индекс — pure-bug, юзер теряет доверие к autocomplete: *«я выбрал стрелочками юзэйч, нажимаю Enter, у меня выбирается экстра-юзэйч».*

Корень обычно в React: keydown-handler мемоизирован без `selectedIndex` / `filteredItems` в deps. Включать в deps нельзя (handler пересоздаётся на каждый keystroke, ломает focus); правильно — refs обновляемые на каждый render (`selectedIdxRef.current = selectedIdx`), handler читает через ref. Без этого правила любой autocomplete с фильтрацией будет иногда submit'ить не то что подсвечено. Конкретика — `knowledge/fact-claude-sdk-tab.md::Slash autocomplete popup`.

## Blocked action = visible 1s feedback, не silent no-op

Кнопка/keystroke которая в текущем состоянии не выполнится (rate-limit, validation fail, parallel turn в progress) должна **показать** что её увидели и отвергли. Тихий no-op читается как «клавиатура сломалась» — юзер жмёт ещё раз, ещё раз. Юзер сформулировал решение для нашего SDK-чата: *«если у нас при этом выполняется команда, то у меня будет мигать на 1 секунду красным цветом, инпут будет мигать».*

Класс паттерна: ~1s flash красным/жёлтым на input/button через CSS transition (no JS animation = нет нагрузки). Timer cleanup в useEffect-unmount чтобы не leak'нуть. Сам action остаётся заблокированным — flash это feedback, не разблокировка. Альтернативы (shake-animation, toast) хуже: shake на small input заметен слабо, toast уносит фокус от места действия. Конкретика — `knowledge/fact-claude-sdk-tab.md::Hard gate на Enter во время turn'а + rejectFlash`.

## Hover на action = подсветка target'а, не только action

Когда action-кнопка (copy/delete/archive/share) работает над **родительским контейнером** (bubble сообщения, list-item, card), hover на кнопке должен подсвечивать **весь target** действия, не только саму кнопку. Юзер сформулировал: *«когда я навожусь на эту кнопку, у меня меняется бэкграунд не только у этой кнопки, а в целом у всего блока, который я собираюсь копировать».*

Это особенно важно когда target большой и неоднозначный по границам: assistant-message с текстом + reasoning + 3 tool-cards = что именно скопируется? Без подсветки target'а юзер гадает. Реализация через Tailwind 4: `has-[.action-trigger:hover]:bg-…` на родителе. Маркер-класс на кнопке (`.aui-copy-trigger`) — anchor для CSS selector'а; alternative `:has()` parent matcher работает в Chrome 105+.

Антипаттерн: hover меняет только саму кнопку (border highlight, scale). Юзер видит «кнопка живая», но не видит scope её действия. Применимо к любому destructive/lossy-action chip над large container. Конкретика — `knowledge/fact-claude-sdk-tab.md::Footer pill` (sticky copy + has-extend).

## Inset content на dark theme = темнее, не светлее

Inline-code, code-block, quote-block, любой «inset» элемент внутри текста — фон **темнее** окружения, не светлее. Юзер сформулировал глядя на бледный inline-code: *«цвет заднего фона более тёмный... тут с тёмным фоном это лучше». То есть на dark theme inset = провал ниже, не выпукло выше.

Это инверсия light-theme convention где inset code обычно светло-серый на белом (надо чтобы выделился). На dark theme окружение уже тёмное; светлее = «всплывающий слой» (modal, tooltip); темнее = «провал, врезка» — что и есть семантика inline-code. GitHub dark: text `#c9d1d9` на body `#0d1117`, inline-code на `#161b22` — **темнее** чем body. Discord/Slack тёмные темы делают то же.

Conkretно: bubble bg = transparent/`#151515` hover → inline-code `#0d0d0d` + faint white border `border-white/5` для контура. Контраст 1.3:1 с фоном — не глаз режет, читается как «врезка». Конкретика — `knowledge/fact-claude-sdk-tab.md::Markdown rendering density`.

## Hierarchy через вес/форму, не через яркость

Заголовки/labels/важные элементы на dark theme выделяются **жирностью + размером**, не яркостью текста. Body text `#d4d4d4` (=212), heading **тем же** `#d4d4d4` + `font-bold` + чуть крупнее = читается как иерархия. Heading на `#e8e8e8` (=232) при том же body — двойной сигнал (ярче + жирнее), визуально кричит, «прыгает» из потока.

Юзер: *«разыгрывается текст, который отображается как заголовок, он как будто бы слишком яркий... ммм, лучше отображать его просто жирным?»* — переформулировал сам, отказавшись от первичной идеи делать заголовки крупнее. Это Ink/CLI convention: терминальные рендереры выделяют bold-аттрибутом, а не цветом — markdown headings там видны через `\x1b[1m`, цвет body остаётся.

Применимо к markdown в любом dark-theme UI (Discord embeds, Telegram code-blocks, Cursor inline diff). Если headings рендерятся через `prose-headings:text-…` отдельным цветом — это light-theme pattern, на dark theme `prose-headings:text-inherit` + `prose-headings:font-semibold` правильнее. Конкретика — `knowledge/fact-claude-sdk-tab.md::Markdown rendering density`.

## Streaming scroll = instant, не animated

Auto-scroll-to-bottom при streaming output'а (LLM-генерация, log tail, chat-history append) должен быть **instant** (`behavior: 'auto'` в `scrollIntoView`), не smooth-animated. Smooth-scroll создаёт chase-feel: контент прибывает каждые 50-100мс, animation на каждый прибавок не успевает завершиться — juzер видит непрерывное «гонимся за хвостом», что воспринимается как лаг.

Юзер: *«нахуй для этой анимации скролла можно убрать»* — после того как смена alias на mobile сделала scroll smooth и поведение стало ощущаться неправильно по сравнению с CLI. CLI и любой mature streaming-UI (htop, less +F, tail -f) — scroll мгновенный, контент «приклеен» к низу. Animated smooth-scroll оправдан **только** для user-initiated navigation (click «scroll to bottom» button, Cmd+End) — там анимация даёт ориентир «куда двигаемся».

Practical rule: если scroll trigger'ится из data-event (new chunk arrived), это всегда instant. Если из user-event (click/hotkey) — может быть smooth с cap'ом 200-300ms (см. `Animation duration cap для navigation`). Конкретика — `knowledge/fact-claude-sdk-tab.md::Composer button slot` (scrollToBottom через `behavior: 'auto'`).

## UI shape независим от backend taxonomy

Сlassifier который API/SDK использует внутри (skill-type, role, kind, command-class) не должен определять UX-важность фичи. Юзер: *«на СДК показывает его как "skip it command"... да мне похуй, как он его показывает, понимаешь, в чём проблема: он должен, э-э, вне зависимости от того, как он его показывает, отображать нормально».*

Backend taxonomy — это internal detail, оптимизированный под API contract. Юзер видит **результат**: что команда выполнила, какой UI она открыла, что в треде осталось маркером. Например, Claude SDK классифицирует `/usage` как `LocalJSXCommandCall`, `/cost` как **alias** к `/usage`, а наш UI не должен показывать оба разными способами — для юзера обе команды делают одно («открой Usage view»). Разделение по skill-type vs project-command в Probe-manifest — фильтр для разработчика, не для презентации.

Применимо к любому UI поверх типизированного backend'а (DB enum'ы, tRPC procedure types, GraphQL union types). Когда таксономия течёт в UI — юзер вынужден учить чужой словарь чтобы понять что делает feature. См. `UI vocabulary ≠ API vocabulary` — это та же мысль, но про **тип** объекта, а не его лейбл.

## Loading phases = деривация из event-state, не event arrival

«Что показать пока ждёт» — функция от того **что пришло**, не от того **что событие пришло**. Юзер сформулировал точно: *«финкинг — это, по-моему, не событие же, это то, что мне нужно событие, которое отображается в лоадере. Ярр в лоадере отображаться не может».*

То есть loader UI — это **derived state** из таблицы event-shape → phase:
- ничего не пришло → `fetching` (network + warmup)
- system:init пришёл → `thinking` (connection ready, ждём первый content)
- assistant chunk с text-blocks → `typing` (loader **уходит**, content стримится сам)
- assistant chunk только thinking → `thinking` (loader держится, текст ещё нет)
- tool_use без result → `tool_use` («running <tool>»)
- result event → `idle`

`'typing'` это **не** loading-state, это «ничего не показывать, контент сам пришёл». Loader виден **только** в фазах активного ожидания. Без этого разделения loader дублирует контент: assistant-bubble уже streamит, и сверху висит «thinking...».

Применимо к любому streaming/progressive UI: SSE-чаты, LLM-генерация, file uploads с per-chunk progress. Антипаттерн: один монолитный `isLoading` boolean — теряет различие «жду первый байт» vs «получаю». Конкретика — `knowledge/fact-claude-sdk-tab.md::Phase machine sdkState`.

## Info-command output replaces composer, не падает в thread

Slash-команды делятся на два класса по тому, **где живёт их output**: «conversation-command» меняет состояние диалога (рендерится в thread, persisted в JSONL) — `/compact`, `/clear`, `/model`. «Info-command» инспектирует состояние и output — ephemeral (показывается **вместо** композера в overlay-panel, закрывается на Escape, в thread не сохраняется) — `/usage`, `/cost`, `/status`, `/context`, `/insights`.

Юзер сформулировал семантику и поведение: *«open usage, дальше это usage, он как бы идет вместо input, и дальше я могу нажать Escape и закрыть его. В истории сохранится сам usage маркер, но именно отображение будет у меня тут, пока я не нажму Escape».* То есть в thread остаётся только **chip-маркер** `/usage` (юзер дал команду), сам output не персистится — это inspection, а не часть разговора.

Класс применим к любому chat-UI с `/commands`: Slack/Discord `/help`, Cursor `/symbols`, Linear `/find`. Output info-команды — это modal/sidebar/overlay поверх композера, **не** очередное сообщение в треде. Иначе через неделю в треде только output'ы /usage'ев — диалог потерян. Whitelist info-команд хранится в коде. Конкретика — `knowledge/fact-claude-sdk-tab.md::SlashCommandOverlay`.

## Collapse measurement = unit content reads in

«Раскрыть полностью (N **строк**)» vs «(N **символов**)» — выбор по природе контента. Code/diff/JSON юзер читает построчно, count в строках информативен («20 строк осталось» — понятно). Plain prose / описание / chat-сообщение читается потоком, char-count даёт лучшее представление длины («2500 символов» примерно = время чтения). Юзер: *«интересует именно количество строчек»* — потому что compact-summary это **structured numbered text**, не сплошной narrative.

Mobile иначе: char-count точнее для коротких prompt'ов (где строк может быть 1-2 даже на 500 символах из-за wrap'а). Правило: code/code-like → lines; prose → chars; mixed → preferring lines если контент содержит `\n` density > 1 per 80 chars. Конкретика desktop — `knowledge/fact-claude-sdk-tab.md::CompactSummaryMsg` (split('\n').length).

## Remove redundant UI когда keyboard path canonical

Когда юзер expected workflow клавиатурный (TUI-наследники, IDE-like UI, code editors), mouse-only кнопки которые дублируют hotkey становятся шумом. Send-кнопка рядом с textarea при Enter=submit + Escape=cancel — лишняя поверхность, дублирующая клавиатуру. Юзер: *«убери кнопку отправки, у нас за остановку будут отвечать клавиши типа Escape».*

Условие применимости: целевая аудитория знает hotkey (CLI-experienced, dev-tool users). Для consumer chat UI (Telegram, WhatsApp, mobile-первый продукт) Send button обязательна — там клавиатурный path не canonical. Граница — спросить «средний юзер тут знает Enter=submit без подсказки?». В Cursor/Claude Code/SDK chat — да. В iMessage — нет.

Удалённая кнопка не должна оставлять «дыру в layout'е» — composer перерасстраивается чтобы textarea заняла освободившееся место. Конкретика — `knowledge/fact-claude-sdk-tab.md::Composer button slot (Send / Stop)`.

## Persistent label slot — default fallback вместо empty

Когда в UI есть слот для значения которое всегда должно показывать **что-то** (модель chat'а, активный provider, выбранная language в editor) — пустое значение `null/undefined` рендерится как **default**, не как `''`. Юзер: *«при самом первом запуске модель слева внизу не отображается, хотя она должна отображаться всегда».*

Семантика: пустой slot читается юзером как «сломалось / не загрузилось», даже если технически правильно. Default fallback показывает **намерение системы** («если ничего не выбрано — это N»). Для Claude SDK default = `claude-opus-4-7` (whatever Anthropic ships as 'default' alias). Когда юзер выбрал явный alias (sonnet/opus/haiku) — alias-first; когда `'default'` или undefined — fallback.

Применимо к любому persistent identity slot: language в IDE, provider в API-чате, active workspace в team-tool. Антипаттерн `loading-spinner вместо default` ложит UX «всё работает, просто ждёт» поверх когда никакого fetch'а не идёт — это нечестно. Конкретика — `knowledge/fact-claude-sdk-tab.md::Model footer: SDK_DEFAULT + alias-first`.

# UI implementation patterns

Готовые реализационные приёмы для конкретных UI-задач. Промежуточный слой между UX-философией выше и React/Zustand-синтаксисом из `knowledge/fix-*` (находятся через `docs_search` по симптому: selector loops, stale closure, Portal click-outside, layering поверх canvas).

## Invisible Bridge: hover между триггером и Portal-окном

При hover-открытии Portal-окна (тултип, превью, dropdown) триггер и окно физически разорваны в DOM — Portal живёт в `document.body`. `relatedTarget` в `onMouseLeave` триггера показывает Portal-окно как «чужую» ветку → окно закрывается мгновенно, пользователь не успевает дойти курсором.

Решение — directional closing: в `onMouseLeave` триггера проверяй направление движения мыши и положение окна. Если курсор движется в сторону окна — закрытие игнорируется, окно остаётся.

```tsx
const handleTriggerLeave = (e: React.MouseEvent) => {
  const rect = e.currentTarget.getBoundingClientRect();
  // окно слева от триггера → курсор уходит влево = в сторону окна
  if (e.clientX < rect.left) return; // не закрывать
  setOpen(false);
};
```

Положение окна (слева / справа / сверху / снизу) определяет, какое направление «дружественное».

Триггер не должен иметь `transform: scale` при hover — изменение размера меняет `getBoundingClientRect`, между «маленьким» и «большим» состоянием возникает миллисекундный gap, в котором курсор находится «вне» обоих → false-leave. Если нужен hover-эффект — менять `background`/`color`, не размер.

Таймеры `setTimeout(close, 200ms)` отвергнуты как альтернатива: ломаются от быстрых пользователей (закроется когда они уже взаимодействуют) и от медленных (300мс на каждое окно складываются в раздражение). Прозрачные `<div>`-мостики тоже не подходят — добавляют DOM-узел, ловят клики «над» соседними элементами, конфликтуют с `pointer-events: none` родителей. Логический мостик не добавляет узлов вообще.

## Cmd+Hover Settings Panel: реактивная видимость для модификатор-зависимых popup'ов

Когда popup открывается комбинацией «модификатор (Cmd/Alt/Ctrl) + hover», обычный `onMouseEnter → show` ломается на ключевом сценарии: курсор уже на месте, пользователь зажимает/отпускает Cmd. `onMouseEnter` не стреляет повторно → popup не появляется/не исчезает.

Решение — derived state из двух флагов hover + глобального cmd-listener:

```tsx
const [triggerHovered, setTriggerHovered] = useState(false);
const [panelHovered, setPanelHovered] = useState(false);
const isCmdPressed = useCmdKey(); // глобальный keyboard listener

const visible = (isCmdPressed && triggerHovered) || panelHovered;
```

`isCmdPressed` живёт в module-scope `Set<setter>` — один пара keydown/keyup listener'ов на весь app, не по экземпляру на Tooltip (иначе 100+ listeners на странице). При нажатии/отпускании Cmd React делает re-render всех подписчиков → `visible` пересчитывается → popup появляется/исчезает без участия mouse events.

Логика входа в panel — pinning через второй флаг: `panelHovered = true` при `onMouseEnter` panel'а делает popup видимым независимо от Cmd (пользователь зашёл внутрь, отпустить Cmd теперь безопасно); `panelHovered = false` при `onMouseLeave` — полный сброс. При выходе курсора из триггера в сторону panel'а используется directional closing (Invisible Bridge выше) — иначе popup закроется на gap'е между ними.

Паттерн применяется для opt-in affordances, скрытых по умолчанию (см. секцию «Opt-in affordances через модификатор-клавишу» выше). Cmd-hover говорит «продвинутый функционал, шум для базового пользователя».

## Native virtualization vs JS libraries: правило 1000 элементов

Для списков с высокой вариативностью высот элементов (markdown с code blocks от 30px до 1000px, чат-сообщения, timeline entries) JS-библиотеки виртуализации (Virtuoso, react-window, virtua) дают scroll jitter — они угадывают высоту неотрендеренных элементов через `defaultItemHeight`, и при ре-измерении `scrollHeight` контейнера меняется, вызывая прыжок позиции.

Для списков до ~1000 элементов нативный CSS работает стабильнее:
```css
.list-container { overflow-y: auto; }
.list-item {
  content-visibility: auto;
  contain-intrinsic-size: auto 100px;
}
```

`content-visibility: auto` заставляет браузер пропускать layout/paint для элементов вне viewport — аналог виртуализации на уровне движка. `contain-intrinsic-size: auto 100px` с ключевым словом `auto` заставляет браузер запомнить реальную высоту после первого рендера; повторный скролл / re-mount использует кэш → jitter исчезает. Плюс встроенный Scroll Anchoring Chromium компенсирует сдвиги сверху курсора пользователя на уровне композитора, всегда плавнее JS-решений.

JS-виртуализация всё-таки нужна для 10k+ элементов или работы с virtualized data source (lazy fetch по mid-scroll). Для типичных list views на 100-1000 элементов native выигрывает по стабильности, размеру бандла (минус ~20KB на библиотеку) и интерактивности (раскрытие/сворачивание элементов не ломает скролл). Если в списке элементы гарантированно одной высоты (table rows, virtualized grid) — любая библиотека работает корректно, разница только в производительности; правило про jitter актуально только для вариативных высот.

## Compositor-thread animations: GPU-слой для индикаторов под Main Thread Block

При тяжёлой работе на Main Thread (React reconciliation 200+ элементов, JSON.parse мегабайтных файлов, blocking sync IPC) все анимации замораживаются — спиннеры останавливаются, hover не реагирует. UI выглядит «висящим», пользователь теряет доверие. Решение — некритичные анимации на compositor thread (GPU):

```css
.spinner {
  will-change: transform;
  animation: spin 1s linear infinite;
}
@keyframes spin { from { transform: rotate(0deg); } to { transform: rotate(360deg); } }
```

`will-change: transform` создаёт отдельный compositing layer; анимация `transform` обрабатывается GPU независимо от Main Thread — спиннер крутится 60fps даже когда JS блокирует поток на 2 секунды.

На GPU выносятся фоновые лоадеры (спиннеры, progress, pulse — пользователь хочет «приложение живо, работает») и decorative animations (subtle background gradients, particle effects — не зависят от user input). Интерактивные анимации (hover feedback, click ripples, accordion expand) остаются на Main Thread: если они «зависают» — это честный сигнал что приложение тормозит, его нельзя маскировать. GPU-анимация создаёт иллюзию параллельной работы — допустимо для информирования («ещё грузится, не зависло»), не для интерактивности.

## Immediate Injection: race-fix для async-create + state-read

Классическая race condition: код создаёт entity (вкладка, проект, документ), который должен сразу иметь некоторый state (sessionId, owner, defaults). Между `createEntity()` и `setEntityState()` — async-промежуток (init worker, PTY ready, network response). Consumer (UI-компонент через polling/effect) в этот промежуток видит entity без state и рендерит пустой/error экран. Симптом — «прыжок»: после действия (Fork, Rollback, New Project) UI на 300-500мс показывает «Нет сессии», потом state появляется.

Решение — передавать state в options создания, чтобы entity-конструктор применил initial values до того как consumer успеет подписаться:

```tsx
// Плохо: создаём пустой → ждём ready → инжектим state
createEntity().then(() => setState(initial));

// Хорошо: state передаётся в момент создания
createEntity({ initialState });
```

Применяется к любой async-creation с предсказуемым initial state. Если state приходит из external source (API response), который ещё не получен — паттерн неприменим, нужен loading-state с явным «ожидание». Показывать `null`-state и надеяться что «пользователь не заметит за 200мс» — антипаттерн: заметит, и не доверяет интерфейсу после первого глюка.

## Manual bounds check: hover-state не сбрасывается при click-outside backdrop

Сценарий: карточка с hover-эффектом (зелёный overlay), внутри открывается dropdown через backdrop `fixed inset-0`. Пользователь кликает в backdrop чтобы закрыть dropdown. Backdrop ловит click → закрывает dropdown. Но карточка не получает `onMouseLeave` — мышь технически осталась в её bounding rect (backdrop сверху, не «снаружи»). Hover-state карточки залипает в `true`.

Решение — ручная проверка координат при backdrop-клике:

```tsx
const handleBackdropClick = (e: React.MouseEvent) => {
  closeDropdown();
  if (!cardRef.current) return;
  const rect = cardRef.current.getBoundingClientRect();
  const outside =
    e.clientX < rect.left || e.clientX > rect.right ||
    e.clientY < rect.top || e.clientY > rect.bottom;
  if (outside) setHovered(false);
};
```

Если клик пришёлся вне границ карточки — синхронно сбрасываем `hovered`. Если внутри (пользователь кликнул в саму карточку через backdrop) — оставляем.

Альтернатива `mouseleave document` listener работает, но шумная: срабатывает на любое движение к краю окна, не только на closing-кейс. Принцип общий — когда backdrop технически «над» интерактивным элементом, браузер не генерирует mouse leave для элемента, нужна явная reconciliation при закрытии overlay'а.

## Mutual panel exclusion: одна тяжёлая боковая панель за раз

Если в проекте есть две+ боковые панели, каждая из которых дорогая для рендера (список 200+ элементов, расширенная timeline, file tree с virtualization), и они расположены в одной зоне экрана — открытие одной автоматически закрывает другую.

Три причины: визуально две панели рядом превращают центральную рабочую область в узкую полоску, пользователь теряет фокус; производительно — обе панели подписаны на active state, одновременный mount даёт O(n²) ре-рендер при изменении; когнитивно — пользователь редко нуждается в обоих контекстах одновременно, choose-one нативное поведение, не ограничение.

```tsx
const openPanelA = () => { setA(true); setB(false); };
const openPanelB = () => { setA(false); setB(true); };
```

Не пытайся сделать «обе открыты, но узкие» — пользователь не разберётся в двух кашах информации в узких колонках. Если панели имеют разный масштаб (одна — узкий nav-rail 48px, вторая — content panel) и дополняют друг друга, mutual exclusion вредит — правило про боковые панели одного класса.

## State-driven async refresh: IPC event + 500ms delay для SQLite commit

Если Main-процесс пишет в SQLite и сразу шлёт IPC-событие renderer'у «обнови данные» — renderer может прочитать до того как транзакция закоммитилась на диск. Результат: запрос вернул старые данные, UI рендерит stale-state.

```tsx
ipcRenderer.on('data:changed', () => {
  setTimeout(() => loadData(), 500); // SQLite WAL commit window
});
```

500мс — эмпирический safe-margin для SQLite WAL mode commit на SSD. Для критичных кейсов (single source of truth) лучше передавать новые данные в самом IPC-событии (`data:changed` с payload), а не делать round-trip через диск.

Polling каждые N секунд «на всякий случай» — антипаттерн: создаёт постоянную нагрузку и всё равно имеет окно неконсистентности 0-N секунд. Event-driven с явным delay-buffer лучше во всех метриках.

## Silent automation cleanup: skipProcessCheck для programmatic close

Если есть UI-checkpoint (confirm dialog «у вас запущен процесс, точно закрыть?»), который защищает пользовательский случайный close — он же ломает программный close из автоматизации (post-task cleanup, batch operations).

Решение — флаг `skipProcessCheck` / `silent` в close API: пользовательское закрытие показывает confirm, программное — без диалога:

```tsx
closeTab(id);                              // confirm
closeTab(id, { skipProcessCheck: true }); // silent
```

Confirm нужен только для случайных действий. Намеренные действия (программные, или подтверждённые пользователем в первой стадии flow) не должны переподтверждаться. Flag-pattern даёт opt-in: API по умолчанию консервативное, автоматизация явно отказывается от защиты. Программными считаются post-task cleanup (закрыть Gemini-таб после Update Docs), MCP tools от sub-agent'ов, restore/rollback (сжигаем старые табы), batch-операции (Close All в Project).

## startTransition для тяжёлых смен контекста

React 19 `startTransition` помечает обновление как низкоприоритетное — браузер продолжает обрабатывать клики, hover, анимации, пока тяжёлая reconciliation выполняется в фоне. Применяется при переключении между «тяжёлыми» представлениями, где новый view рендерит сотни DOM-узлов (открытие проекта с большим деревом терминалов, switch между Dashboard и workspace, route change в SPA).

```tsx
import { startTransition } from 'react';

const switchView = (newView: string) => {
  startTransition(() => set({ activeView: newView }));
};
```

Без `startTransition` React успевает закончить тяжёлую работу и только потом обрабатывает следующий клик/hover. С ним — успевает реагировать на input в параллель, пользователь видит «приложение живое», даже если новый view ещё не отрендерен полностью.

Не для обычных state updates (показ модалки, переключение тогла, изменение поля формы) — это вносит лишнюю асинхронность и `useTransition`-логику без выгоды.

## Tiered debounce: задержка пропорциональна тяжести операции

Когда один пользовательский input запускает несколько операций разного веса (легкий highlight + средняя проверка + тяжёлая загрузка), единый debounce не оптимален: малый таймаут перегрузит тяжёлую операцию, большой — сделает лёгкую медленной. Решение — отдельный debounce per операция, прогрессивный:

```
Виртуальная подсветка (DOM в viewport)   →  100мс
Проверка состояния (сканирует весь буфер) →  500мс
Загрузка с диска + перестроение дерева   →  2000мс
```

Задержка пропорциональна стоимости операции + частоте, с которой её результат меняется. Лёгкие сигналы делают UI «живым» (быстрый отклик на скролл), тяжёлые — экономят CPU.

Применяется к сложным view'ам с многими derived состояниями от одного источника (timeline с подсветкой/check'ами/preload, code editor с syntax/lint/typecheck, search с suggest/filter/full-results). Не для независимых операций, каждая со своим источником ввода — tiered debounce про один input → каскад операций разной тяжести.

## ID-pinned routing > cwd-routing когда инстансы делят cwd

Расширение принципа `Routing по контексту запроса`. Cwd longest-prefix перестаёт давать детерминированный ответ ровно в одном частом сценарии: N инстансов приложения (dev + prod, два production-window'а на разных user-data-dir, тест + основной) одновременно открыли **один и тот же путь** в своём списке проектов. Discovery-файлы обоих содержат один cwd, longest-prefix match длины одинаковый — победитель определяется arbitrary sort-order или mtime, не контекстом запроса. Симптом узнаётся быстро: child-процесс (MCP-сервер, hook-script, helper) **успешно** что-то делает (200 OK, `outcome=acked`, `Tab created`) и при этом видимого эффекта в инстансе из которого юзер триггерил действие нет — окно молчит, лоадер висит, табы не появляются. Юзер: *«MCP создаёт таб, я вижу системное сообщение, а вкладки нет нигде»*.

Решение — авторитативный hint через канал который у Claude'а появляется автоматически: PTY env. Каждый Electron main при `pty.spawn` инжектит `NOTED_MAIN_PID=<process.pid>`; дочерние процессы (Claude → MCP-сервер, Claude → hook-script, Claude → grab-helper) наследуют. `pickInstance(cwd)` в дочернем коде делает три попытки в порядке: (1) `env.NOTED_MAIN_PID` есть и live-instance с таким pid существует → return immediately; (2) longest-prefix cwd; (3) mtime. Cwd-routing остаётся для сторонних tool'ов которые env'а не имеют (helper из `/tmp`, free-form bash), но для всего что родилось из нашего PTY — pid wins. Тот же паттерн полезен для lock-file payload (см. ниже): owner-main пишет свой sock-path в lock, helper читает оттуда — никакой cwd-discovery даже как fallback. См. `knowledge/fact-mcp-routing.md::Priority order`, `knowledge/fact-claude-stop-hook.md::Архитектура`, `knowledge/fact-prompt-queue.md::Lock-file dispatcher`. Полная цепочка четырёх слоёв одного бага — `knowledge/fix-claude-hook-silent-dropouts.md`.

## Probe-before-unlink на shared paths

Когда два процесса конкурируют за один путь на файловой системе (Unix-domain socket, lock-file, pid-file, named pipe) и каждый при старте делает `try { unlinkSync(path) } catch {} → listen(path)` чтобы убрать свой собственный stale-файл от прошлого запуска — паттерн ломается в момент когда оба процесса живы одновременно. Второй стартующий **удаляет живой socket первого** (kernel-side bind остаётся, inode на пути уже другой), первый продолжает listen'ить на отвязанный inode, новые connect'ы идут ко второму. Visible-side первого процесса: всё работает, port жив, OS не ругается; реально никто на него не приходит. Этот паттерн — частая причина silent-broken systemic IPC, особенно когда discovery построен над shared filesystem path.

Лекарство — `try-listen → probe-on-EADDRINUSE → cleanup-only-if-orphan`:

```js
function bindServer(attempt = 0) {
  const server = createServer(handler);
  server.on('error', (e) => {
    if (e.code !== 'EADDRINUSE' || attempt >= 1) return;
    const probe = net.createConnection(path);
    probe.on('connect', () => probe.destroy());  // alive — leave it
    probe.on('error', (err) => {
      probe.destroy();
      if (err.code === 'ECONNREFUSED') {        // orphan — safe to clean
        try { fs.unlinkSync(path); } catch {}
        bindServer(attempt + 1);
      }
    });
  });
  server.listen(path, () => { fs.chmodSync(path, 0o600); /* ... */ });
}
```

Probe-connect успешен → сосед жив, оставляем путь ему (мы просто не первый). ECONNREFUSED → socket-file есть, listener мёртв (crash / kill -9 без cleanup) → unlink + retry один раз. Никогда unconditional unlink перед listen. Применимо к любым `bind`/`listen`-ресурсам которые могут существовать в N экземплярах: D-Bus session services, Redis sentinel files, любые `~/.app/socket-*` discovery setups. Шрам — в этой кодовой базе я повторил unconditional-unlink паттерн **дважды** в одной сессии: сначала фиксил основной socket-collision, потом написал legacy-fallback listener с тем же unlinkSync без probe → создал тот же баг через другую дверь. См. `knowledge/fix-claude-hook-silent-dropouts.md::Слой 2`.

## App-level ack для silent socket transports

Когда producer пишет в socket и видит callback от `client.write()` как успех — это **kernel** confirmation: bytes легли в send buffer, OS их доставит когда сможет. Это **не** confirmation что receiver их прочитал, тем более распарсил и обработал. Если receiver жив но его read-path сломан (event loop залип на синхронной операции, listener был unsubscribed без error, accept queue переполнен) — producer считает что message доставлен, никаких retry/alert не делает, downstream фича молча не работает.

Симптом — две стороны логов расходятся численно: helper-script side пишет «`outcome=sent`» N раз за минуту, app-side server показывает M событий, N >> M. На macOS это часто бывает с Unix domain socket'ами когда два процесса биндят один путь (см. предыдущий принцип): второй биндинг съел listener первого, accept queue первого больше не drain'ится, kernel принимает connection'ы и буферизует, producer видит `connect+write` успешными.

Лекарство — двусторонний application-level ack:

```js
// server (on 'data' callback after parsing line):
sock.write('ok\n');

// client:
client.on('data', (chunk) => {
  ackBuf += chunk;
  if (ackBuf.includes('\n')) finish('acked_' + (Date.now() - wroteAt) + 'ms');
});
setTimeout(() => { if (wroteAt) finish('sent_no_ack'); }, 150);  // alive but reading-broken
setTimeout(() => finish('timeout_250ms'), 250);                  // total budget
```

`acked` ≠ `sent` в client-side log'е делает silent-dropout видимым. Если хочется проще — на server-side `accept` + `read` counter'ы публикуются в `setInterval` snapshot: `Δconn=10 Δevent=0` за окно = 10 connection'ов приняли, ноль envelope'ов распарсили → доказательство read-path-broken. Применимо в любых fire-and-forget IPC: Unix sockets, TCP без response-protocol, UDP, BroadcastChannel, postMessage между worker'ом и main thread. Связан с принципом `Diagnose with instrumentation, not guesses` — Δcounter и app-ack — две инструментации одного класса проблем. См. `knowledge/fix-claude-hook-silent-dropouts.md::Параллельный фикс` (65 `outcome=sent` vs 9 app-side log'ов за окно — мгновенно показало что producer и consumer лгут друг другу).

## Action валиден mid-state — не блокировать по чужому busy-флагу

Когда есть action который специально предназначен для работы со streaming/in-progress объектом (поставить промпт в очередь пока LLM отвечает, добавить trakk в плейлист пока играет другой, оставить комментарий пока документ редактируется), pre-block по «занятости» внешнего процесса = ломает фундаментальную семантику action'а. Юзер прямо: *«+grab наоборот должен работать когда стриминг — это и есть его смысл, поставить в очередь»*.

Соблазн pre-block'а возникает когда action имеет одну видимую failure-mode (`Helper never reported back` toast после 3с timeout если Ctrl+G ate by TUI mid-turn) и хочется «не пускать туда где не сработает». Это путает «нет смысла» (запрещаемый action) с «есть смысл, но в худшем кейсе медленнее»; первый блокируется affordance'ом (disabled state, hover «not supported»), второй — никогда. Правильное решение — **diagnose-on-failure**, не **pre-block**: запустить action всегда, на timeout снять snapshot side-effects (size файлов-логов, состояние external processes, какие counters изменились) — детерминированно распознать причину и показать конкретный toast вместо generic'а.

```js
// неверно — pre-block по чужому состоянию:
if (claudeSpinnerBusy.get(tabId)) return { error: 'claude_busy' };
captureInput(tabId);

// верно — пускаем, на timeout классифицируем:
const helperLogSizeBefore = statSize('/tmp/noted-grab-helper.log');
const result = await captureInput(tabId);
if (result.timeout) {
  const grew = statSize('/tmp/noted-grab-helper.log') > helperLogSizeBefore;
  return { error: grew ? 'editor_not_wired' : 'claude_busy' };
}
```

Helper-log не вырос за 3с → helper не запустился → Ctrl+G ate by TUI → реально `claude_busy`. Helper-log вырос → helper отработал, не достиг socket → реально `editor_not_wired`. Юзер видит один из двух точных toast'ов вместо `Helper never reported back`. Применимо к любому RPC-like action с потенциально-разными failure modes под одним visible timeout'ом. Hook-confirmed «занят» (наш authoritative `claudeTurnBusy` от Stop hook — узкое окно 50-200ms между UserPromptSubmit и первым ответным chunk'ом) допустимо как pre-block потому что в этот момент **никакой** action к Claude не пройдёт — но это не «занят в смысле стрима», это «занят в смысле kernel-side между двумя event'ами». См. `knowledge/fact-prompt-queue.md::Что пробовали::Pre-block grab по claudeSpinnerBusy` и `knowledge/fix-claude-hook-silent-dropouts.md::Слой 4`.

## Synchronous feedback для async-операций с человеческой задержкой
Хоткей или клик, за которым реально стоит цепочка из IPC, спавна процесса и handshake'а (300–800мс на холодном кейсе), без визуального ack'а ощущается как глухой. Юзер успевает повторно нажать комбинацию, думая что первое нажатие не дошло; на стороне приложения это либо запускает дубль, либо хуже — стэк команд, которые приедут с разрывом и юзер потом будет разбирать почему открылись две вкладки.

Лекарство — синхронный визуальный сигнал в **том же frame**, что и keydown/click, **до** await'а. Конкретно: setState флага в zustand-store → компонент-получатель рендерит overlay с короткой animation. Сигнал должен быть приглушённым (не alert-цвет, не дёрганая анимация — задача обозначить «принято, работаю», не «внимание!») и автоматически гаситься через ~600мс, чтобы перекрыться визуальным результатом операции, когда тот наконец появится. Длительность подбирается под верхнюю границу задержки операции — pulse заканчивается одновременно с появлением результата, перекрытие читается как «вспышка → объект».

Тонкости:
- **`background-color`-анимация, не `opacity`**. Screen-recording-кодеки (H.264/JPEG) при низкой битрейтности едят opacity-only изменения — анимация невидима на скринкастах и при OCR-анализе видео. См. CLAUDE.md anti-pattern «AI-Optimized UI & Video Forensics».
- **`pointer-events-none` + `aria-hidden`** на overlay. Индикатор не должен блокировать клики по контенту под ним и не должен зачитываться скринридерами как отдельный элемент.
- Сигнал ставится **до** IPC, не в `.then()`. В `.then()` он бесполезен — async-результат и так покажется тем же путём что и сигнал.

В custom-terminal: Shift+Cmd+T pulse в TabBar (`useUIStore.triggerReopenPulse()`, `animate-reopen-pulse` keyframe в globals.css), вспышка между нажатием и появлением восстановленной вкладки. См. `knowledge/fact-reopen-last-closed-tab.md::Synchronous pulse feedback`.

## Transparent passthrough как дефолт для wrapper'ов

Когда наш слой стоит между юзером и работающим эталонным path (Cmd+V → xterm.js → node-pty → терминал-приложение), дефолт — не вмешиваться. Если в эталоне (iTerm2, Terminal.app, любой reference-приложение) поведение корректное, наш wrapper должен пропускать байты прозрачно. Любая обёртка, преобразование или fallback-логика добавляется **только** после доказательства, что reference-путь сломан, и **только** на той кромке стека, где сломалось.

Конкретный кейс из сессии: попробовали routing manual Cmd+V через `safePasteAndSubmit` с chunking и bracket-обёртками — юзер сразу отверг (*«нет, чанкинг не надо, мне нужен ровно один paste как в iTerm2»*, *«нахуй мы вообще это подключали»*). Откатили на `term.write(data)` pass-through. Реальный root cause оказался ниже по стеку (node-pty silent data loss + Claude alt-screen) — наши обёртки **маскировали** его, а не лечили; вместо одного chip выходило N, разметка ломалась, `\r` внутри текста submit'ились как Enter, и каждая дополнительная попытка «помочь» накапливала свой artifact.

Правило применимости: перед добавлением middleware над стандартным API спрашивай *«в iTerm2/Terminal.app/любом эталоне работает корректно?»*. Да → не вмешивайся, читай эталон как контракт. Нет → ищи разницу на той кромке которая отличается от эталона и фикси её точечно. В коде это видно в [`fix-paste-bracket-mode-loss.md`](../knowledge/fix-paste-bracket-mode-loss.md) — три фикса на трёх разных уровнях (PTY env, node-pty version, manual pass-through), ни один не оборачивает manual paste своей логикой.
