# Делегирование E2E-тестирования одному субагенту

> **Отдельный Overseer MCP удалён.** History-методы теперь входят в Terminal
> MCP, но E2E-тестировщик не должен опрашивать чужую историю вместо проверки
> реального приложения. Живые проверки идут через фактический dev-инстанс,
> main-логи и Claude/Codex rollout.

Ты — родительский агент, который реализует или исправляет сложную фичу. Архитектура, код, unit-тесты и решение найденных проблем остаются у тебя. Для проверки реального UI запускай ровно одного отдельного тестировщика, чтобы действия, скриншоты и сырые логи не заполняли основной контекст.

## Выбор исполнителя: зависит от среды родителя

Правило простое и не обсуждается на ходу — оно определяется тем, где запущен
родительский агент.

**Если родитель работает в Claude Code → тестировщик всегда Sonnet 5.**

Sonnet 5 сам по себе достаточно умён для E2E: он читает skill, находит
семантические цели по скриншоту и отличает свою ошибку от продуктового бага.
Opus для этой роли не нужен — тестировщик не проектирует фикс, он выполняет
сценарий и возвращает доказательства.

Контракт запуска в Claude Code:

- через `Agent` с `subagent_type` именованного агента (например `e2e-sonnet-1m`),
  определённого файлом в `.claude/agents/` или `~/.claude/agents/`;
- точный ID модели (`claude-sonnet-5[1m]`) задаётся **только** во frontmatter
  этого файла. Параметр `model` у самого `Agent` принимает короткие имена
  (`sonnet`/`opus`/`haiku`/`fable`) и полный ID с суффиксом отвергает;
- реестр агентов читается **при старте сессии**. Новый файл определения не
  подхватывается на лету: создал файл — перезапусти родительскую сессию, иначе
  получишь `Agent type not found`;
- субагент по умолчанию стартует с чистым контекстом, отдельный аналог
  `fork_turns: "none"` не нужен.

Для длинных прогонов бери вариант с 1M-контекстом. На обычном окне тестировщик
падает с `Prompt is too long`, если тянет крупный DOM: у этого приложения
десятки вкладок, виртуализированная History и xterm.

**Если родитель работает в Codex → тестировщик `luna_e2e` (`gpt-5.6-luna`).**

Профиль `~/.codex/agents/luna-e2e.toml` закрепляет модель, Fast service tier
(`priority`) и роль. Контракт вызова: `agent_type: "luna_e2e"`,
`task_name: "e2e_test"`, `fork_turns: "none"`. Выбирай именно agent type, а не
прямой model override: `spawn_agent(model="gpt-5.6-luna")` отвергает Luna,
тогда как именованный custom agent запускается корректно. `task_name` — только
имя задачи, `model` — только прямой выбор модели; ни одно из этих полей не
выбирает custom agent, и `model: "luna_e2e"` передавать нельзя. Если в схеме
`spawn_agent` нет поля `agent_type` или среди ролей нет `luna_e2e` — сессия
запущена до загрузки профиля: перезапусти родительскую Codex-сессию. Только
после этой точной проверки разрешён fallback на `gpt-5.6-terra` с тем же brief.

## Effort — опционален

Не выставляй effort рефлекторно. Sonnet 5 и Luna справляются с обычным
сценарием на дефолтном уровне; повышенный effort стоит времени и токенов, а
качество поиска DOM-цели почти не меняет — слабое место моделей здесь подбор
физической траектории клика и drag, а не глубина рассуждения.

Поднимай effort только когда сценарий действительно того требует: длинная
цепочка состояний, неочевидная граница между продуктовым багом и ограничением
харнесса, разбор рассинхрона нескольких источников правды. Для «запусти, кликни,
проверь» дефолта достаточно.

Не запускай второго агента для ревью того же прогона. Если отчёту не хватает одного конкретного доказательства, отправь follow-up тому же тестировщику.

Тестировщик:

- сам проверяет, запускает или переиспользует переданный dev-инстанс через
  свой Bash-сеанс и ведёт его до конца прогона;
- выполняет сценарий как пользователь;
- сам читает названный E2E-skill, project reference, `CLAUDE.md` и релевантные документы через `docs_search`;
- самостоятельно находит семантические DOM-цели;
- собирает скриншоты, узкий срез логов и авторитетные данные после действия;
- откатывает тестовые мутации;
- при первом подтверждённом продукт-баге останавливается и возвращает доказательства.

Тестировщик не редактирует код, не добавляет instrumentation, не проектирует фикс и не запускает собственных субагентов.

## Что родитель передаёт до запуска

Родитель выбирает **контракт test target**, но не обслуживает процесс сам.
Передай тестировщику:

- `projectPath`;
- название skill: `electron-e2e-testing` или `ios-e2e-testing`;
- точную dev/build-команду, ожидаемые CDP/Vite/API-порты и идентичность приложения;
- для iOS — Simulator, bundle id и нужна ли пересборка;
- явное правило, разрешены ли reuse/restart и нужно ли оставить dev после теста;
- проверяемое обещание пользователю — что должно видимо измениться;
- 1–3 сценария, включая основной путь и только самые рискованные edge cases;
- контракт тестовых данных: источник fixture, точная dev-БД/окружение,
  детерминированная команда импорта или клонирования, ожидаемые ID/число
  записей/инварианты и команда rollback;
- начальное состояние, допустимые мутации и обязательный rollback;
- авторитетные доказательства: какие UI-состояния, log-теги, DB/JSONL/filesystem/API rows подтверждают результат;
- лимит попыток.

Смысл и корректность fixture принадлежат родителю. Если для теста нужна
сессия примерно на 100 итераций, родитель выбирает точный источник и либо
готовит её в dev сам, либо передаёт одну точную команду импорта. Тестировщик
может механически выполнить эту команду и проверить заданные инварианты, но
не выбирает похожую сессию, не копирует произвольные production-данные, не
угадывает схему и не конструирует fixture по своему усмотрению. Нет fixture
или нельзя доказать ожидаемое состояние — соответствующий сценарий
возвращается как `BLOCKED` до UI-действий.

Preflight принадлежит тестировщику: он сопоставляет порт, PID, команду и
`cwd`, переиспользует только доказанно правильный dev, а при разрешённом
restart останавливает только процессы этого проекта. Общие
`pkill electron/node/vite`, packaged production и host-инстанс
custom-terminal запрещены. Тестировщик запускает dev через свой Bash-сеанс,
записывает PID и run-log, ждёт детерминированной готовности и после прогона
убирает только то, что сам поднял. Родителю достаточно передать контракт —
его контекст не заполняется lifecycle-командами и сырым выводом.

По умолчанию родитель передаёт семантические цели — «строка файла X», «папка Y», «кнопка Rewind», — а не хрупкие CSS-селекторы. Точный selector передавай только если он является устойчивым контрактом или известной ловушкой из документации. Иначе тестировщик находит его после первого полнооконного скриншота и DOM-inspection.

Это правило не смягчается, даже когда у элементов нет стабильных тестовых
хуков и тестировщику приходится искать цель по видимому тексту интерфейса.
Селектор, добытый родителем из исходников, устаревает так же быстро, но при
этом заставляет тестировщика долбиться в неправильную цель вместо того, чтобы
посмотреть на экран. Цена самостоятельного поиска — один дополнительный запрос
к DOM в изолированном контексте тестировщика; цена неверного селектора —
ложный BLOCKED. Если click-тесты становятся регулярными, ответ — проставить
`data-testid` в самом продукте, а не переносить поиск целей на родителя.

Вместо селектора полезнее передавать знание о ловушке: «список виртуализирован,
не считай позицию в процентах — бери реальные координаты DOM», «этот input
скрыт, клик по нему упадёт», «вложенный блок принимает колесо только после
клика-фокуса». Такие факты устаревают гораздо медленнее имён классов.

## Как запустить

Создай одного субагента по контракту своей среды (см. «Выбор исполнителя»), без
истории основной сессии. В Codex не передавай одновременно полную историю и
custom agent type — такой spawn отклоняется до запуска. В его задачу подставь
этот brief:

```text
Ты — E2E-тестировщик, не разработчик. Не создавай субагентов и не меняй код.
Не опрашивай history-методы Terminal MCP вместо проверки фактического dev-инстанса.

Проект: <projectPath>
Skill: <electron-e2e-testing | ios-e2e-testing>
Test target: <CDP/Vite/API ports + app identity или Simulator/bundle>
Dev/build command: <exact command>
Lifecycle: <reuse разрешён?>; <restart разрешён?>; <оставить после теста?>

Test fixture:
- Source: <точный disposable источник или "не нужен">
- Setup: <точная команда импорта/клонирования в dev>
- Expected state: <ID, число записей и инварианты>
- Rollback: <точная команда либо подтверждение read-only>

Проверяемое поведение:
<что пользователь делает и что должен увидеть>

Сценарии:
1. <основной путь>
2. <edge, если нужен>

Safety:
- не трогай production и реальные пользовательские данные;
- управляй dev через свой Bash-сеанс; сначала докажи PID по port+command+cwd;
- не используй общий pkill и не останавливай чужие dev/host процессы;
- после теста останови только собственный process lease, если не велено оставить;
- используй disposable fixture либо запомни точный baseline;
- после мутации восстанови baseline и докажи восстановление;
- при первом подтверждённом продукт-баге остановись, не исправляй его.

Evidence:
- первый UI-вызов — full-window screenshot;
- screenshot после каждого state-changing действия;
- для drag: baseline, drag-preview, drop-result и rollback;
- verify через видимый UI плюс <DOM/FS/DB/JSONL/API>;
- логи только узким grep по времени, entity ID и тегам <tags>;
- сохрани screenshots, DOM/DB/JSONL proof и узкий срез логов в
  /tmp/<run-name>-<timestamp>/;
- stdout/stderr собственного dev-процесса пиши в отдельный run-log;
- общий app-log не копируй целиком: зафиксируй временную границу прогона,
  сохрани 5–15 относящихся к сценарию строк в narrow-logs.txt и верни также
  путь к исходному файлу;
- не вставляй raw dumps в ответ.

Ограничение собственного контекста:
- не делай полный DOM-snapshot, `fullHtml`, `document.body.innerHTML`,
  `outerHTML` крупных узлов и дамп всего состояния приложения;
- каждый запрос к странице возвращает уже агрегированный результат: число,
  короткую строку или ≤20 строк по ≤80 символов — агрегируй на стороне
  страницы, а не в своём контексте;
- нужен store — бери конкретные поля, а не объект целиком;
- большой skill/reference читай выборочно (grep, offset/limit), а не целиком.

Budget:
- одна основная попытка действия;
- одна корректирующая попытка, только если первая не дала ни product-result, ни доказанного test-harness blocker;
- затем PASS, FAIL или BLOCKED с текущими доказательствами;
- если два наблюдения подряд не дали нового факта — не продолжай смотреть,
  возвращай BLOCKED с тем, что уже есть. Наблюдение без действия не расходует
  попытки, поэтому этот предохранитель обязателен;
- ориентируйся на переданный лимит времени: исчерпан — возвращай отчёт с
  текущими доказательствами, а не начинай новую линию расследования.

Верни компактно:
- verdict: PASS / FAIL / BLOCKED;
- модель/effort самого E2E-тестировщика;
- если тестируется AI-сессия — отдельно модель/effort этой целевой сессии;
- test target и использованный process lease;
- таблицу: время | действие | semantic target/selector | ожидание | факт | artifact path;
- 5–15 ключевых log lines или точные file:line/time ссылки;
- доказательство rollback;
- при FAIL/BLOCKED: последний успешный checkpoint, доказанная граница и отдельно гипотезы;
- 3–6 фактов, которых достаточно родителю для дальнейшего архитектурного расследования.
```

## Как родитель использует ответ

Не перечитывай весь лог с нуля по умолчанию. Сначала используй отчёт как индекс:

1. Проверь verdict, последний checkpoint и rollback.
2. При `PASS` открой только ключевой финальный screenshot, если визуальная грань критична.
3. При `FAIL` прочитай указанные строки и 1–2 связанных screenshot; затем сам восстанавливай архитектурную модель и решай фикс.
4. При `BLOCKED` отдели дефект продукта от ограничения test harness. Если не хватает одного наблюдения, запроси его у того же агента.
5. Сырые артефакты поднимай только когда компактный пакет противоречив или не позволяет связать действие с результатом.

Отчёт тестировщика — индекс, а не единственная копия логов. Общий app-log и
rollout/JSONL остаются на своих обычных путях; stdout/stderr поднятого
тестировщиком dev и screenshots лежат в указанной временной папке. Поэтому
родитель при архитектурном расследовании может открыть исходный лог шире
вокруг точного времени, прочитать полный JSONL или посмотреть конкретный
screenshot, не повторяя весь прогон и не загружая основной контекст заранее.

Тестировщик отвечает на вопрос «что реально произошло». Родитель отвечает на вопрос «почему система так устроена и что нужно менять».
После исправления родитель отправляет follow-up тому же тестировщику:
тот при необходимости перезапускает свой dev-инстанс и повторяет только
провалившийся сценарий.

## Контрольные прогоны

**Codex → Luna.** В сопоставимых прогонах 24 июля 2026 года Terra/xhigh и
Luna/xhigh прочитали skill и проектные reference, подключились к GT Editor,
выполнили physical hierarchical DnD поддерева из двух файлов, доказали
результат через screenshot + DOM + filesystem + watcher logs, проверили отмену
и восстановили baseline. Между baseline и финальным safety-check обе модели
заняли около 5 минут 10 секунд. Luna распознала первую no-op попытку, не выдала
её за успех, со второй попытки сделала физический перенос и вернула компактные
блоки логов отдельно для commit, watcher, Escape и rollback. Поэтому для
ограниченного сценария с явными критериями Luna достаточна и дешевле; Terra
остаётся fallback для окружения без профиля.

**Claude Code → Sonnet 5.** Прогон 25 июля 2026 года на custom-terminal: агент
сам поднял dev, детерминированно дождался CDP, явно записал process lease с
пометкой об исключённом host-процессе, выполнил Start и Stop AI-сессии — оба
клика с первой попытки, с подтверждением через состояние приложения и
main-лог, — и корректно убрал только свой процесс. Проверка родителем показала:
его PID мертвы, порты свободны, host цел. Отдельно он опроверг переданную ему
гипотезу о рассинхроне UI, показав, что интерфейс консистентно ветвится по
одному полю, и честно пометил неразрешённой ту нить, где не исключил
собственную ошибку. Вывод: Sonnet 5 достаточно для E2E-роли, Opus не нужен.

**Общие слабые места.** У всех моделей это подбор физической drag-траектории и
поиск цели без стабильных тестовых хуков, а не глубина рассуждения — поэтому
лимит «одна попытка + одна корректирующая» обязателен, а повышенный effort по
умолчанию не нужен.

Отдельно подтверждено, что чисто наблюдательная фаза не ограничена счётчиком
попыток: в том же прогоне тестировщик потратил больше двадцати минут на
разглядывание до первого клика. Именно поэтому в brief добавлены предохранитель
«два наблюдения без нового факта → BLOCKED» и лимит собственного контекста:
на обычном (не 1M) окне попытка вытянуть крупный DOM убивает тестировщика
раньше, чем он успевает что-либо вернуть.
