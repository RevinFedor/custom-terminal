# Как делегировать настоящие E2E-проверки

Актуальный выбор пользователя с 10.10.2026: **GPT-6-Luna / medium или max**
для обычных проверок, **GPT-6.1-Sol / xhigh или max** для сложных сценариев.
Точную пару выбирай по задаче и проверяй через живой каталог Terminal MCP.

Ты — родительский агент и владелец результата. Сам реализуешь исправление,
выбираешь необходимые проверки, разбираешь найденные дефекты и доводишь
пользовательский сценарий до подтверждённого результата.

## Когда нужен отдельный тестировщик

Преимущество делегирования — экономия токенов основного контекста на
рутинных UI-действиях, чтении данных и сырых артефактах. Это не отдельный
уровень качества и не замена твоей ответственности за проверку.

Можно передать и короткий, чётко заданный прогон кнопок или проверку вёрстки.
Не расширяй его до общего аудита: если подготовка поручения дороже самой
проверки, выполни её сам. Уже полученные доказательства разбирай без нового
прогона, если свежий retake не нужен. Размер фичи или наличие Electron сами
по себе не требуют отдельного агента; длинные сценарии с переходами между
подсистемами, сохранением и перезапуском особенно подходят для делегирования.

Для одной связанной работы используй одного уже существующего тестировщика.
Повтор после исправления выполняет та же сессия. Не создавай второго агента
для перепроверки отчёта: сначала сам проверь конкретные доказательства.

## Что означает полноценный E2E

Проверка проходит весь обещанный пользователю путь:

`реальное действие → реальный UI → действующие adapters/IPC/Main → данные → итоговый UI`

- Web-приложение: работающий frontend/backend и настоящий браузер через Browser
  MCP. Не заменяй его headless-браузером, новым пустым профилем или страницей,
  изображающей продукт. Для HH-отклика нужны также настоящее расширение и HH;
  просмотр уже сохранённого результата не считается новой доставкой отклика.
- Electron: полный DEV-процесс приложения с настоящим Main, renderer и storage,
  а не отдельная React-страница или макет окна.
- iPhone: настоящее приложение в iOS Simulator через iOS MCP, а не web/mobile
  viewport. Ограничения физических возможностей Simulator указывай отдельно.

Родитель задаёт конкретный путь. Проверка только списка результатов не требует
новой отправки, оплаты или вызова AI; она и не доказывает эти отдельные сценарии.

Запускай полное приложение с настоящими компонентами, store и backend/persistence
проверяемого пути. Допустимы заранее подготовленные синтетические данные в
изолированном окружении; это не разрешение подменять исполнителей действия.
Результат должен подтвердиться и на экране, и в авторитетном состоянии.
Если контракт включает сохранность после restart/reopen, проверь также её.

Build, unit-тест, DOM компонента с mock store, offscreen snapshot и synthetic IPC
полезны для своих границ. Они не заменяют E2E полного приложения. Не называй
«полным E2E» тест, в котором настоящий Main, adapter, provider или сохранение
заменены заглушкой. Явно перечисляй подмены и то, что такой тест не доказывает.
Для provider/lifecycle-фич нужен соответствующий настоящий участник в разрешённом
тестовом окружении. Недоступность участника не исправляется выдуманным ACK.

Для визуальной приёмки полного Electron-приложения DEV-окно должно быть видимым.
Докажи `BrowserWindow.isVisible()` или эквивалентный нативный признак и сделай
первый полный кадр окна. Скрытый full-app runner остаётся интеграционной проверкой
с ограничением видимости; он не выдаётся за проверку видимого окна.

Адресный trusted CDP ввод проверяет путь событий в подключённом приложении.
Он не доказывает движение физического курсора, фокус macOS, native modifier flags
или несколько физических дисплеев. Когда баг относится именно к этому уровню,
нужен соответствующий native-сценарий по E2E-skill. Не подменяй его CDP и не
прибегай к произвольным `osascript`/`cliclick`, которые попадут в чужое окно.
Если нужный безопасный канал недоступен, назови точную непроверенную границу.

## Модель и доставка поручения

Перед управлением сессиями прочитай skill `terminal`. Текущую вкладку определяй
через `current_context`; уже полученные актуальные данные не запрашивай повторно.
Проверь живой каталог `list_agent_models` и передавай явные параметры:

| Задача | Модель | Effort |
|---|---|---|
| Протыкать заданные кнопки, снять кадры, проверить простые видимые состояния | `gpt-6-luna` | `medium` |
| Прочитать данные/логи, сопоставить UI с API и сохранённым результатом | `gpt-6-luna` | `max` |
| Сложные зависимости, recovery, гонки или неоднозначная диагностика | `gpt-6.1-sol` | `xhigh`, для наиболее сложных — `max` |

Например, для простого UI-прогона:

```js
{
  toolType: "codex",
  modelSelection: { kind: "catalog", id: "gpt-6-luna" },
  effort: "medium"
}
```

Не наследуй случайную модель/effort старой вкладки. Luna medium теперь разрешена
для простых задач; это не разрешение заменить 6 на 5.6 или другую модель. Если выбранная
модель отсутствует в каталоге, явно сообщи ограничение; не изобретай alias.
Название вкладки и label поручения сами по себе не доказывают runtime-модель.
При сомнении проверь model/effort по exact provider-turn через Terminal API.

E2E передавай через `delegate_to_session` полноценной Codex-сессии.
Для первого связанного поручения новая вкладка по умолчанию дочерняя; для
продолжения передавай прежний `targetTabId`. Не используй временные встроенные
subagent tools вместо такого тестировщика. Родитель при этом может быть Claude
или Codex. Контекстные файлы передавай через `files`, как пути и роли, без
пересылки всей истории основной сессии.

После принятого поручения сохрани `runId` и закончи текущий assistant-turn.
Дождись отдельного completion-уведомления, не опрашивай result, transcript или
terminal output циклом. Полный inline-ответ используй сразу: дополнительный
`get_delegation_result` не нужен. Reader вызывается только при явном указании
на пропущенный/обрезанный результат или при адресном восстановлении.

Оставляй `waitForDescendants: true`. Если тестировщик — дочерняя задача другого
run, его родитель не объявляет завершение до обработки результата. Для короткого
уточнения по готовым артефактам используй `send_message`, для нового выполнения —
новый `delegate_to_session`. Новый ответ о старом прогоне не становится новым E2E.

## Что подготовить до делегирования

Родитель передаёт конкретный, выполнимый brief:

- обещанное пользовательское поведение и 1–3 связанных сценария;
- полный test target: проект/checkout, сборка, app identity, порты или Simulator/bundle;
- точную команду запуска и persistent lifecycle либо identity уже работающего
  экземпляра и разрешение на его переиспользование без нового запуска;
- разрешённые reuse/restart и правило остановки своего процесса;
- fixture, точные ID, исходные связи/счётчики, допустимые мутации и rollback;
- какие UI-признаки и данные доказывают каждый результат;
- новый attempt ID, каталог артефактов, source/build fingerprint;
- лимит действий/времени именно этого поручения и критерий остановки.

Fixture выбирает и готовит родитель. Тестировщик может выполнить точную setup-
команду и проверить инварианты, но не выбирает похожие пользовательские данные
и не угадывает схему. Существующей подходящей сущности достаточно — не добавляй
создание проекта/нативный file picker, если это не предмет проверки. После workflow
cutover не требуй создания Projects ради теста вкладок.

До запуска обеспечь наблюдаемость обещанного поведения. Нужный threshold должен
быть известен, вход — действительно его пересекать. Для гонки в несколько кадров
сначала используй проверку actual-кода с управляемым временем; не заставляй
тестировщика многократно пытаться случайно попасть в миллисекундное окно.
Диагностика не должна менять поведение, подделывать результат или сама вызывать
дорогие DOM/layout измерения на каждом движении.

При параллельных правках нужен изолированный checkout/snapshot вместе с локальными
shared packages. Не оставляй тестовый Vite/HMR подключённым к изменяемому исходнику.
Перед ретестом зафиксируй новую сборку; старый открытый процесс может исполнять
предыдущий код, даже если файлы на диске уже исправлены.

## Процесс, видимость и свежесть запуска

Если поручен отдельный DEV, тестировщик владеет им от preflight до cleanup.
Если родитель передал существующий runtime/browser, тестировщик получает только
оговорённые действия в нём: не перезапускает сервер, не меняет профиль, не открывает
дополнительные окна и не закрывает чужие вкладки без явного разрешения. Родитель
на время прогона не выполняет конкурирующие действия в той же UI-поверхности.
Тестировщик сверяет доступную identity: порт/PID/команду/cwd/сборку для DEV,
browser/window/tab/URL и связь с backend для web, Simulator/bundle для iOS.
Успешный HTTP-ответ, discovery token или строка DevTools listening
без такой связи не доказывают правильное окружение. API-порт проверяется отдельно
перед отправкой токена; production/default port не является fallback.

Для Codex допустим persistent foreground PTY/session, предоставляемый executor:
процесс остаётся живым, tool возвращает session ID для дальнейшего управления.
Не путай его с одноразовой командой `... &`, после которой дерево может погибнуть.
`nohup`/`disown` не доказывают удержание процесса. Если доступная среда не держит
процесс, используй заранее согласованный persistent-канал/готовый lease и проверь
его фактическое выживание; не приписывай это свойству модели Claude/Codex вообще.

Host Noted Terminal, packaged production и чужие DEV не входят в cleanup.
Запрещён общий `pkill electron/node/vite`. Terminal MCP самого тестировщика
маршрутизируется в приложение, владеющее его сессией, и не наследует DEV-порт.
Поэтому он не используется для мутации тестового DEV вместо его доказанного API.

Каждый новый прогон получает отдельный attempt ID и отдельные log/receipt/артефакты.
При новом запуске квитанцию пишет launcher: PID, start time UTC, команда/cwd, порты,
userData, путь журнала и source/build fingerprint. Нельзя восстановить её задним
числом текстом модели. При разрешённом reuse сохрани свежую проверку identity и
ссылку на прежнюю квитанцию, если она есть; не выдумывай новый PID/start time.
Старые screenshot/log/DOM не копируются под новый verdict.
Время изменения файла отчёта не является временем проверенного действия.

Один разрешённый старт — лимит текущего поручения. Завершённый старт предыдущего
run не расходует разрешение нового явно назначенного retake. Если новое исполнение
сценария не было выполнено, результат — NOT RUN, даже если старые доказательства подробны.
Старые ошибки и исправления можно анализировать отдельно, не выдавая за свежий тест.

## Как выполнять сценарий

Сначала полный screenshot окна, затем адресный поиск нужной области и свежие
семантические цели. Для повторяющейся карточки сопоставь stable ID с видимым
названием. Перед жестом сохрани её rect и viewport/DPR. Не бери координаты из
прошлого прогона и не угадывай строку виртуализированного списка по проценту.

Веди последовательность каждого действия:

`до действия → действие через согласованный UI-канал → preview, если есть → результат → данные`

Обычный Browser MCP click может вызывать DOM click, а не trusted CDP-событие:
это допустимый запуск настоящей кнопки, но не доказательство pointer/hover/DnD.
Если проверяется именно ввод, используй поддерживаемый trusted/native канал
в том же приложении и точно укажи его. Не заменяй событие прямым вызовом handler
или мутацией store и не выдавай dispatchEvent за физический жест.

Для DnD фиксируй source set, modifiers, путь, фактическую цель под указателем,
preview до mouseup и итог после него. Источник и target проверяются на текущем
DOM. Если весь выбранный набор не участвует в preview или body target недоступен,
это нельзя скрыть переносом через другой способ. Для отмены докажи отсутствие
commit, а для успешного drop — совпадение сохранения с показанной позицией.

Для вёрстки воспроизведи настройки пользователя: шрифт, padding/gap, размер окна,
плотность, wrapped rows, пустые/длинные имена, файлы и статусные сигналы. Сравнивай
одинаковые данные/настройки до и после. Границы glyph и CSS line box — разные
измерения. Просмотри кадр глазами: один числовой PASS не исключает наложения текста.

Действие запускается реальным UI-путём. Прямой вызов store/IPC/SQL, который делает
работу вместо кнопки или drag, является другой проверкой. Readonly API/IPC и данные
используются для подтверждения. Setup/rollback разрешены только в заданных границах
fixture; они не считаются пользовательским действием проверяемого сценария.

Отдельные screenshot и DOM/API snapshots относятся к своему этапу. Не сравнивай
кадр до Close с данными после Close и не называй намеренное удаление исчезновением.
Не объявляй compositor stale, пока не сверены точные объект, фаза, время и ROI.
Не редактируй raw evidence под вывод: сохраняй ответ инструмента без переписывания
ID/полей; объяснение и исправленный вывод — отдельный файл.

Если окно видимо и пришёл неожиданный pointer с `buttons=0` или координатой вне
CDP-пути, сохрани событие и отличи прерывание ввода от дефекта продукта. Не меняй
защиту отмены ради теста. Не используй глобальную клавиатуру/мышь для обхода
недоступного нативного диалога или неудачного locator.

При первом подтверждённом продукт-баге останови дальнейшие мутации, сними
доказательства, освободи удержанные кнопки/модификаторы и сделай cleanup.
Одна свежая коррекция bbox допустима для установленного промаха harness после
проверки, что предыдущее действие не применилось. Не повторяй действие при
неизвестном результате. Подготовка не расходует попытку продукта, но бесконечное
наблюдение не заменяет запуск: два наблюдения без нового факта требуют сменить
метод или вернуть конкретный BLOCKED, а не собирать ещё тот же DOM.

## Доказательства и вердикт

Сохраняй короткий хронологический ledger: attempt/step, UTC, действие, source/target,
modifiers, ожидание, наблюдение, before/preview/after artifact paths и revisions.
Точные timestamps бери из событий/квитанции; явно отличай UTC от местного времени.
Не подменяй время запуска `mtime` вновь написанного отчёта.

В контекст достаточно кратких полей нужного объекта и узкого среза лога. Большой
raw ответ можно сохранить целиком в артефакт без загрузки в модель. Не делай
`document.body.innerHTML`, full store dump и полный transcript для поиска одной
кнопки. Ограниченный DOM read сохраняется как реально полученный JSON, не как
придуманная после завершения реконструкция.

Отрицательное наблюдение требует доказанного канала: правильные PID/объект/фаза,
полнота нужного интервала, наличие ожидаемой диагностики. Сначала проверь тег
по полному соответствующему журналу без ошибочного фильтра времени, затем точную
привязку к текущему attempt и сущности. Наличие тега в старом прогоне не опровергает
его отсутствие в новом; отсутствие строки в неверном фильтре не доказывает баг.

Вердикт ставится отдельно по достигнутым сценариям:

- PASS — нужный реальный путь выполнен и результат подтверждён текущими артефактами.
- FAIL — предусловия доказаны, действие достигло приложения, результат нарушил контракт.
- PRECONDITION-NOT-MET — выбранный вход не включил проверяемый механизм; этот путь не проверен.
- BLOCKED — новая попытка упёрлась в конкретное ограничение окружения/канала/fixture.
- NOT RUN — нужного нового исполнения не было; старый анализ не меняет этот статус.

Успех компонентной проверки не становится общим PASS. Необследованные сценарии
перечисляй явно. «Ошибок не увидел» и «после исправления должно работать» — не verdict.
Модель max effort тоже не делает неподтверждённый отчёт доказательством.

Cleanup обязателен при любом исходе: отпусти ввод, закрой свои соединения и
восстанови только разрешённые изменения fixture. Свой отдельный DEV останавливай
по контракту с проверкой освобождения портов; переданный на reuse runtime и
его вкладки оставь работающими. Readonly-прогон не требует очистки пользовательских
данных. Заверши ход отдельным финальным
текстом: файл report сам по себе не завершает orchestration.

## Как родитель принимает результат

Сначала проверь свежесть: task → build → launch → UI action → evidence.
Сопоставь launch или свежую reuse identity и hash с поручением. Открой ключевой кадр и сверь несколько
строк исходного лога, а не только вывод тестировщика. Особенно проверяй
отрицательные выводы и переходы между действиями. Для адресной диагностики
разрешены Terminal history/evidence tools; ожидание результата через их polling
по-прежнему запрещено.

Если доказательства противоречат друг другу, сначала восстанови реальные действия
и состояние. Не правь продукт на основании ошибки отчёта. Исправление вердикта
хранится отдельно, исходные artifacts/receipts остаются. Если дефект подтверждён,
родитель исправляет его и назначает той же сессии реальный retake на новом коде.
Не объявляй задачу законченной, пока обязательные оставшиеся пути не проверены.

После завершения всей связанной работы одноразовую вкладку закрой через
`close_tab`, если она больше не нужна. Не закрывай постоянную вкладку владельца
или тестировщика, которому предстоит продолжение.
