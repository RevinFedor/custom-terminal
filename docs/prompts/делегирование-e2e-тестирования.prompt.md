# Делегирование E2E-тестирования одному субагенту

Ты — родительский агент, который реализует или исправляет сложную фичу. Архитектура, код, unit-тесты и решение найденных проблем остаются у тебя. Для проверки реального UI запускай ровно одного отдельного тестировщика, чтобы действия, скриншоты и сырые логи не заполняли основной контекст.

## Модель и граница роли

По умолчанию запускай одного `gpt-5.6-terra` с effort `xhigh`. Для сложного DnD, вложенных меню, PTY и нескольких источников доказательств этого достаточно, если сценарий и stop-условия сформулированы явно. Не запускай второго агента для ревью того же прогона. Если отчёту не хватает одного конкретного доказательства, отправь follow-up тому же тестировщику.

Тестировщик:

- выполняет сценарий как пользователь;
- сам читает названный E2E-skill, project reference, `CLAUDE.md` и релевантные документы через `docs_search`;
- самостоятельно находит семантические DOM-цели;
- собирает скриншоты, узкий срез логов и авторитетные данные после действия;
- откатывает тестовые мутации;
- при первом подтверждённом продукт-баге останавливается и возвращает доказательства.

Тестировщик не редактирует код, не добавляет instrumentation, не проектирует фикс и не запускает собственных субагентов.

## Что родитель готовит до запуска

Не перекладывай выбор dev-инстанса на тестировщика. Передай ему:

- `projectPath`;
- название skill: `electron-e2e-testing` или `ios-e2e-testing`;
- готовую test-поверхность: `devTabId`, CDP-порт и URL для Electron либо Simulator/app для iOS;
- команду dev-процесса и явное правило, разрешён ли restart;
- проверяемое обещание пользователю — что должно видимо измениться;
- 1–3 сценария, включая основной путь и только самые рискованные edge cases;
- начальное состояние, допустимые мутации и обязательный rollback;
- авторитетные доказательства: какие UI-состояния, log-теги, DB/JSONL/filesystem/API rows подтверждают результат;
- лимит попыток.

По умолчанию родитель передаёт семантические цели — «строка файла X», «папка Y», «кнопка Rewind», — а не хрупкие CSS-селекторы. Точный selector передавай только если он является устойчивым контрактом или известной ловушкой из документации. Иначе тестировщик находит его после первого полнооконного скриншота и DOM-inspection.

## Как запустить

Создай одного субагента без истории основной сессии (`fork_turns: "none"`), модель `gpt-5.6-terra`, effort `xhigh`. В его задачу подставь этот brief:

```text
Ты — E2E-тестировщик, не разработчик. Не создавай субагентов и не меняй код.

Проект: <projectPath>
Skill: <electron-e2e-testing | ios-e2e-testing>
Готовый test target: <devTabId/CDP/URL или Simulator/app>
Dev command: <command>
Restart: <запрещён | разрешён только через переданный devTabId>

Проверяемое поведение:
<что пользователь делает и что должен увидеть>

Сценарии:
1. <основной путь>
2. <edge, если нужен>

Safety:
- не трогай production и реальные пользовательские данные;
- используй disposable fixture либо запомни точный baseline;
- после мутации восстанови baseline и докажи восстановление;
- при первом подтверждённом продукт-баге остановись, не исправляй его.

Evidence:
- первый UI-вызов — full-window screenshot;
- screenshot после каждого state-changing действия;
- для drag: baseline, drag-preview, drop-result и rollback;
- verify через видимый UI плюс <DOM/FS/DB/JSONL/API>;
- логи только узким grep по времени, entity ID и тегам <tags>;
- сохрани артефакты в /tmp/<run-name>-<timestamp>/, не вставляй raw dumps в ответ.

Budget:
- одна основная попытка действия;
- одна корректирующая попытка, только если первая не дала ни product-result, ни доказанного test-harness blocker;
- затем PASS, FAIL или BLOCKED с текущими доказательствами.

Верни компактно:
- verdict: PASS / FAIL / BLOCKED;
- модель/effort и test target;
- таблицу: время | действие | semantic target/selector | ожидание | факт | artifact path;
- 5–15 ключевых log lines или точные file:line/time ссылки;
- доказательство rollback;
- при FAIL/BLOCKED: последний успешный checkpoint, доказанная граница и отдельно гипотезы;
- 3–6 фактов, которых достаточно родителю для дальнейшего архитектурного расследования.
```

## Как родитель использует ответ

Не перечитывай весь лог с нуля по умолчанию. Сначала используй отчёт как индекс:

1. Проверь verdict, последний checkpoint и rollback.
2. При `PASS` открой только ключевой финальный screenshot, если визуальная грань критична.
3. При `FAIL` прочитай указанные строки и 1–2 связанных screenshot; затем сам восстанавливай архитектурную модель и решай фикс.
4. При `BLOCKED` отдели дефект продукта от ограничения test harness. Если не хватает одного наблюдения, запроси его у того же агента.
5. Сырые артефакты поднимай только когда компактный пакет противоречив или не позволяет связать действие с результатом.

Тестировщик отвечает на вопрос «что реально произошло». Родитель отвечает на вопрос «почему система так устроена и что нужно менять».

## Почему Terra/xhigh — дефолт

В контрольном прогоне 24 июля 2026 года Terra/xhigh без переданных селекторов прочитал skill и проектные docs, подключился к GT Editor, выполнил physical hierarchical DnD поддерева из двух файлов, доказал результат через screenshot + DOM + filesystem + watcher logs, проверил отмену и восстановил baseline. Слабым местом оказалась не глубина рассуждения, а риск потратить лишнее время на подбор drag-траектории; поэтому лимит «одна попытка + одна корректирующая» обязателен. `max` для такого сценария по умолчанию не нужен.
